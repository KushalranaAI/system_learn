# How services talk

Once code lives in different services, every interaction is a network message. *How* they talk shapes latency,
availability and coupling.

## Synchronous: request and response

The caller waits for an answer.

| Protocol | Notes |
|----------|-------|
| **REST/JSON over HTTP** | Universal, debuggable, cacheable |
| **gRPC** (HTTP/2 + Protobuf) | Fast binary format, typed contracts, streaming; great inside the data centre |
| **GraphQL** | Usually at the edge for clients, aggregating many services |

## The chain problem

```
Client → Orders → Inventory → Pricing → Discounts → Loyalty
```

- **Latency adds up:** 5 hops × (network + work + queueing).
- **Availability multiplies:** if each service is 99.9% available, the chain is 0.999⁵ ≈ **99.5%**. That's ~3.6 hours
  of downtime a month instead of 43 minutes.
- **Tail latency compounds:** any one slow hop makes the whole request slow.

Ways out:
- **Call in parallel** where calls are independent (Inventory and Pricing at the same time).
- **Keep local copies** of slowly changing data (lesson 11.2): no call needed.
- **Make non-essential calls optional:** if Loyalty is down, show the order without points.
- **Go async** where the caller doesn't need the answer now.

## Asynchronous: events and messages

The producer announces something and moves on; consumers react in their own time.

```
Orders: OrderPlaced{id, items, user} ──▶ broker ──▶ Inventory (reserve stock)
                                                ├─▶ Email (confirmation)
                                                └─▶ Analytics
```

| | Sync calls | Async events |
|-|-----------|--------------|
| Coupling | Caller must know and wait for the callee | Producer doesn't know who listens |
| Availability | Callee down = caller fails | Consumer down = it catches up later |
| Latency | Immediate answer | Eventually |
| Debugging | A stack of calls | Flows through a broker; needs tracing |
| Good for | Queries, "I need the answer now" | Notifications, side effects, propagating changes |

Two flavours:
- **Commands:** "Reserve stock for order 42", sent to one specific service, expecting it to act.
- **Events:** "Order 42 was placed", a fact; anyone may react.

Prefer events for spreading facts; use commands when one service must do one specific thing.

## Contracts

Services evolve separately, so the interfaces must evolve **compatibly**:
- add fields; never remove or repurpose them without versioning;
- consumers ignore unknown fields;
- schemas in a shared registry (Protobuf, Avro, JSON Schema) with compatibility checks in CI;
- **consumer-driven contract tests** catch breaking changes before deploy.

## Try it

Checkout calls 6 services in sequence, each with p99 = 80 ms and 99.9% availability. Estimate the chain's worst-case
p99 and availability, and suggest two changes.

<details>
<summary>Answer</summary>

Worst case p99 ≈ 6 × 80 = **480 ms** (percentiles don't add exactly, but sequential tails compound). Availability ≈
0.999⁶ ≈ **99.4%**. Changes: call independent services in parallel; replace lookups of slow-changing data (product
names, prices) with local copies; move side effects (email, loyalty, analytics) to events after the order commits.
</details>

## Key takeaways

- Sync calls are simple but chains add latency and multiply failure.
- Parallelise, keep local copies, and make non-essential calls optional.
- Async events decouple services and tolerate downtime, at the cost of eventual results.
- Evolve contracts compatibly, with schemas and contract tests.

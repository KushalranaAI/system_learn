# Seeing across services

"Checkout is slow." In a monolith you'd profile one process. With 12 services in the request path, you first need to
find **which one** is slow, and that needs observability designed in from the start.

## The three signals

| Signal | Answers | Examples |
|--------|---------|----------|
| **Metrics** | How much, how fast, how often? (aggregates over time) | Request rate, error rate, p99 latency, CPU, queue depth |
| **Logs** | What exactly happened? (individual events) | "payment declined for order 42: insufficient funds" |
| **Traces** | Where did the time go for *this one request*, across services? | A waterfall of spans |

## Correlation ids

Generate a **request id** at the edge, and pass it on every call and every message:

```
X-Request-Id: 7f3a9c…   →  gateway → orders → inventory → payments
                            every log line includes request_id=7f3a9c…
```

Now one search in central logs shows the whole story of a request.

## Distributed tracing

A **trace** is a tree of **spans**; each span is one unit of work with a start, an end and attributes.

```
GET /checkout                          ████████████████████████ 640 ms
 ├─ orders.create                      ████████                 180 ms
 │   └─ postgres INSERT                  ██                      30 ms
 ├─ inventory.reserve                          ███               60 ms
 └─ payments.charge                                ████████████ 380 ms   ← here
     └─ provider API call                           ███████████ 360 ms
```

- Use **OpenTelemetry** for instrumentation; trace context propagates in headers (`traceparent`).
- Include message brokers: put trace context in message headers so async flows connect.
- **Sample** (say 1–10% of traces, plus every error and slow request) to control cost.

## Metrics that matter per service

The **RED** method for request-driven services:
- **R**ate: requests per second;
- **E**rrors: failed requests per second (or %);
- **D**uration: latency distribution (p50/p95/p99).

Plus saturation (CPU, memory, connections, queue depth): the **USE** method for resources.

## Structured logs

```json
{"ts":"2026-10-24T10:15:03.120Z","level":"warn","service":"payments","request_id":"7f3a9c",
 "order_id":42,"msg":"provider timeout","latency_ms":3000,"attempt":2}
```

- JSON, not free text: searchable and aggregatable.
- Consistent field names across services.
- **No secrets or personal data** in logs (card numbers, passwords, tokens).

## SLOs per service

Each service publishes its **SLO** (e.g. "99.9% of `reserve` calls succeed within 100 ms", Module 18). Callers design
their timeouts around it, and alerts fire on SLO burn, not on every CPU spike.

## Try it

Checkout p99 jumped from 400 ms to 2 s after Tuesday's deploys, which touched 4 services. Describe how you'd find the
cause with traces and metrics.

<details>
<summary>Answer</summary>

Compare the RED metrics (Duration p99) per service before and after Tuesday, to see which service's latency moved.
Pull slow checkout traces (p99 exemplars) and look at the waterfall for the span that grew. Check that span's
attributes (endpoint, query, downstream calls) and correlated logs by `request_id`. Correlate with that service's
deploy time; roll back or fix.
</details>

## Key takeaways

- Metrics show trends, logs show events, traces show where one request's time went.
- Propagate a request/trace id through every call and message.
- Instrument with OpenTelemetry; sample traces, but keep errors and slow ones.
- Track RED per service, use structured logs without secrets, and alert on SLOs.

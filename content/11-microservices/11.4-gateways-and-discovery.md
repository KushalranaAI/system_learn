# Gateways and discovery

With 30 services, two questions appear: **how do clients reach them**, and **how do services find each other** when
instances come and go every few minutes?

## API gateway

A single entry point for external clients.

```
mobile / web ─▶ API gateway ─┬─▶ accounts
                             ├─▶ catalogue
                             ├─▶ orders
                             └─▶ payments
```

What it typically does:
- **Routing:** `/orders/*` → orders service.
- **Authentication:** verify tokens once, then pass the identity downstream.
- **Rate limiting** per client (Module 8).
- **TLS termination, compression, request ids, logging.**
- **Aggregation:** one client call fans out to several services (or a **BFF**, a "backend for frontend" per client
  type).

Keep **business logic out** of the gateway. It should route and protect, not decide.

## Service discovery

Instances get new IPs as they scale, crash and redeploy. Hard-coding addresses doesn't work.

| Approach | How | Examples |
|----------|-----|----------|
| **DNS-based** | `orders.internal` resolves to current instances | Kubernetes Services, Consul DNS |
| **Client-side discovery** | The client asks a registry, picks an instance, load-balances itself | Consul, Eureka + client libraries |
| **Server-side discovery** | The client calls a stable address; a load balancer or proxy picks the instance | Cloud LBs, Kubernetes Services |
| **Service mesh** | A sidecar proxy next to each instance handles discovery, retries, mTLS and metrics | Istio, Linkerd, Envoy |

Registries need **health information** (lesson 4.5), so dead instances drop out quickly.

## Service mesh

Instead of every service implementing retries, timeouts, mTLS and metrics in its own language, a sidecar proxy does
it:

```
orders ⇄ [sidecar] ════ mTLS ════ [sidecar] ⇄ inventory
```

- ✅ Uniform policies (timeouts, retries, circuit breaking), encryption and telemetry without code changes.
- ❌ More moving parts, extra latency per hop (small), and real operational complexity.

It's worth it at dozens of services across several teams; overkill for five.

## Configuration and secrets

- Per-environment config from a central source (environment variables, a config service), never baked into images.
- Secrets in a secrets manager (Vault, a cloud secrets manager), rotated, never in git.

## Try it

Your mobile app makes 7 calls to render the home screen (profile, feed, notifications count, promos, cart count, …).
On slow networks it takes 4 s. What would you add at the edge?

<details>
<summary>Answer</summary>

A **BFF / aggregation endpoint** at the gateway (`GET /home`) that calls the 7 services **in parallel** inside the
data centre (fast, low-latency links) and returns one response. The phone makes 1 round trip instead of 7; non-critical
parts (promos) can time out and be omitted.
</details>

## Key takeaways

- An API gateway is the front door: routing, auth, rate limits; no business logic.
- Service discovery maps service names to healthy instances (DNS, a registry, or a mesh).
- A service mesh standardises retries, timeouts, mTLS and telemetry, at an operational cost.
- Aggregate chatty client calls at the edge (BFF).

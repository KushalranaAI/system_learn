# TCP and congestion control

TCP turns an unreliable stream of packets into a reliable, ordered byte stream. The way it does that explains a lot
of latency you'll see in production: why new connections are slow, why one lost packet stalls a whole response, and
why connection reuse matters so much.

## The handshake

```
client                                  server
  | SYN  seq=1000                          |
  |--------------------------------------->|
  |            SYN-ACK seq=5000 ack=1001   |
  |<---------------------------------------|
  | ACK  seq=1001 ack=5001  (+ request)    |
  |--------------------------------------->|
```

One full round trip (RTT) before the client can send its first byte of data. Each side picks a random initial
sequence number, and every byte after that is numbered. The receiver ACKs "the next byte I expect", so a gap shows
up as repeated ACKs for the same number.

Closing has its own cost: the side that closes first holds the socket in **TIME_WAIT** (commonly 60 s on Linux) so
stray old packets can't be mistaken for a new connection. A proxy that opens and closes thousands of short
connections per second to the same backend can run out of ephemeral ports (about 28,000 by default on Linux) because
of this. The fix is the same as for latency: reuse connections.

## Two windows limit how fast you send

| Window | Who sets it | Protects |
|--------|-------------|----------|
| **Receive window (rwnd)** | The receiver, in every ACK | The receiver's buffer |
| **Congestion window (cwnd)** | The sender, by guessing | The network in between |

The sender may have at most `min(rwnd, cwnd)` unacknowledged bytes in flight. Throughput is roughly
`window / RTT`. A 64 KB window over a 100 ms path caps you at 640 KB/s no matter how fat the link is, which is why
window scaling (allowing windows far above 64 KB) exists.

## Slow start, with numbers

A new connection doesn't know the path's capacity, so cwnd starts small: **10 segments** (RFC 6928), about 14.6 KB
with a 1,460-byte MSS. Each ACKed segment grows cwnd by one segment, so cwnd roughly **doubles every RTT** until loss
or a threshold.

Sending a 200 KB response (about 137 segments) on a fresh connection, RTT 100 ms:

```
RTT 1: send 10 segments   (total 10)
RTT 2: send 20            (total 30)
RTT 3: send 40            (total 70)
RTT 4: send 80            (total 150 ≥ 137)  done
```

Four RTTs just for the data. On a warm connection whose cwnd has already grown, the same 200 KB fits in one RTT.

## Loss and congestion control

When loss is detected (three duplicate ACKs or a timeout), the sender assumes congestion and backs off. The
algorithm decides how.

| Algorithm | Signal | Behaviour |
|-----------|--------|-----------|
| **Reno** (classic) | Loss | Halve cwnd on loss, then add one segment per RTT ("AIMD"). Slow to refill fat pipes. |
| **CUBIC** (Linux default since 2006) | Loss | Grows cwnd along a cubic curve, quickly back toward the last size that caused loss, then probes carefully. Good on high-bandwidth paths. |
| **BBR** (Google, 2016) | Measured bandwidth and min RTT | Builds a model of the path and paces sending at the estimated bottleneck rate. Doesn't treat every loss as congestion. |

Loss-based algorithms fill buffers until a packet drops, so on links with deep buffers they add queueing delay
("bufferbloat"), and on lossy wireless links they back off for losses that weren't congestion. BBR does better on
both, at the cost of fairness quirks when competing with CUBIC flows. Many large content providers use BBR on their
servers; it's a sysctl change on Linux (`net.ipv4.tcp_congestion_control=bbr`).

A timeout is far more expensive than duplicate ACKs: the retransmission timeout (RTO) is at least 200 ms on Linux
(1 s per the RFC), cwnd collapses to one segment, and slow start begins again. A single lost packet at the tail of a
response, with no later packets to trigger duplicate ACKs, can add hundreds of milliseconds.

## Head-of-line blocking

TCP delivers bytes **in order**. If segment 5 of 20 is lost, segments 6–20 can arrive but sit in the kernel buffer
until 5 is retransmitted. The application sees nothing for at least one extra RTT.

That's fine for one file. It hurts when you multiplex many independent requests over one connection (HTTP/2): one
lost packet stalls every stream. This is the main reason HTTP/3 moved to QUIC over UDP (lesson 27.4).

## What to do about it

- **Reuse connections.** Keep-alive and connection pools skip the handshake and keep cwnd warm. This is the biggest win.
- **Shorten the RTT.** Terminate TCP (and TLS) at a CDN edge close to the user (lesson 3.7); slow start's rounds are
  then short.
- **Send less in the first flight.** Keep critical HTML and headers small enough to fit in the initial window.
- **Tune servers.** Disable "slow start after idle" for long-lived connections, consider BBR, size buffers for your
  bandwidth-delay product.

## Try it

A mobile user 100 ms (RTT) from your origin opens your app and its first API call returns a 200 KB JSON response over
HTTPS. The second call, a few seconds later, is just as large but much faster. Explain the difference, and estimate
both.

First call, cold:

- DNS lookup: maybe 50–100 ms if not cached.
- TCP handshake: 1 RTT = 100 ms.
- TLS 1.3 handshake: 1 RTT = 100 ms (lesson 27.3).
- Request + response under slow start: about 4 RTTs for 200 KB starting from a 10-segment window = 400 ms, plus
  server time.

Total: roughly **650–700 ms**. Second call on the same kept-alive connection: no DNS, no handshakes, and cwnd has grown
past 137 segments, so the whole response arrives in about **1 RTT ≈ 100 ms** plus server time.

Fixes: reuse connections (keep-alive, one long-lived HTTP/2 or HTTP/3 connection), preconnect at app start, terminate
at an edge 10–20 ms away (cutting every RTT above), TLS session resumption, and trimming the first response.

## Key takeaways

- The handshake costs one RTT; TIME_WAIT and ephemeral ports make short-lived connections expensive.
- Throughput ≈ window / RTT; slow start doubles cwnd per RTT from about 14.6 KB.
- CUBIC reacts to loss; BBR models bandwidth and RTT.
- In-order delivery means one lost packet stalls everything behind it.
- Reusing connections and moving the endpoint closer to users beat almost every tuning knob.

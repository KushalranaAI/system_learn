# Key-range vs hash partitioning

Module 9 introduced sharding as a scaling step. This module looks at how partitioned stores (Cassandra, DynamoDB,
Bigtable, CockroachDB, Kafka, Elasticsearch) actually decide **which node holds which key**, and what that does to
queries.

## Key-range partitioning

Sort keys and split the key space into contiguous ranges:

```
partition 1: a…f   partition 2: g…m   partition 3: n…s   partition 4: t…z
```

- ✅ **Range scans are cheap:** "all orders for user 42 between March and May" reads one partition, in order.
- ✅ Ranges can **split** when they grow (Bigtable, HBase, CockroachDB do this automatically).
- ❌ **Hot spots** when access follows the sort order. Timestamps as keys send every new write to the *last* range.

## Hash partitioning

Hash the key and partition by hash value:

```
partition = hash("user:42") → falls in hash range 3 of 8
```

- ✅ **Even spread**, even for sequential keys.
- ❌ **Range scans hit every partition**, because neighbouring keys are scattered.
- ❌ Changing the partition count naively (`% N`) moves most keys (lesson 14.2 fixes this).

## Compound keys: the best of both

Hash on one part of the key, sort by another within the partition. Cassandra's model:

```
PRIMARY KEY ((user_id), created_at)
             └ partition key (hashed)  └ clustering key (sorted within the partition)
```

- All of one user's rows live together, sorted by time, so "user 42's last 50 events" is a single-partition range scan.
- Users are spread evenly by the hash.

DynamoDB calls these the **partition key** and **sort key**.

## Choosing

| Access pattern | Scheme |
|----------------|--------|
| Point lookups by id | Hash |
| Time-series per entity | Hash(entity) + sort by time |
| Global ordered scans (leaderboards, time ranges across everything) | Range, with care for hot spots |
| Unknown or ad hoc | Don't over-partition yet: a single node plus indexes |

## Time-series hot spots

If you need global time ranges, avoid a key like `2026-10-24T10:15:03`. Prefix it with a bucket:

```
key = (hour_bucket, shard = hash(device_id) % 16, timestamp)
```

Writes spread over 16 partitions per hour; a time-range query reads 16 partitions per hour of data.

## Try it

An IoT platform stores readings from 2M devices, one per minute each. Queries: "the last 24 h for device X" (very
common) and "all readings in the last 5 minutes" (rare, for monitoring). Design the key.

<details>
<summary>Answer</summary>

Partition key `device_id` (hashed), clustering key `timestamp`, possibly bucketed by day (`(device_id, day)`) to cap
partition size. "Device X, last 24 h" is one or two partition reads. For the rare "everything in the last 5 minutes",
don't scan: stream readings into a separate time-bucketed store or a stream processor (Module 17).
</details>

## Key takeaways

- Range partitioning keeps scans cheap but risks hot ranges.
- Hash partitioning spreads load but scatters ranges.
- Compound keys hash the entity and sort within it: the common sweet spot.
- Bucket time-based keys to avoid write hot spots.

# Secondary indexes

Data is partitioned by `user_id`. Now someone asks: "find all orders with status = 'refund_requested'" or "find the
user with email X". Those queries don't include the partition key. How do they find the data without asking every
partition?

## Option 1: Local indexes (document-partitioned)

Each partition indexes **only its own** data.

```
partition 1: orders + index(status) for its orders
partition 2: orders + index(status) for its orders
...
query status='refund_requested' → ask ALL partitions → merge results   (scatter-gather)
```

- ✅ Writes are simple: the row and its index entries live on the same partition (one local transaction).
- ❌ Reads by the secondary key must ask every partition, and the slowest one decides latency.

Used by Cassandra's secondary indexes, MongoDB on sharded collections, and Elasticsearch.

## Option 2: Global indexes (term-partitioned)

The index is partitioned **by the indexed value**, separately from the data.

```
index partition A: status 'cancelled'…'paid'      → [order ids]
index partition B: status 'refund_requested'…     → [order ids]
query → go straight to index partition B → then fetch the orders by id
```

- ✅ Reads by the secondary key hit **one** index partition.
- ❌ Writes touch the data partition **and** one or more index partitions, often on different nodes. Either a
  distributed transaction, or (commonly) the index is updated **asynchronously** and can lag.

DynamoDB global secondary indexes are eventually consistent for exactly this reason.

## Comparison

| | Local index | Global index |
|-|-------------|--------------|
| Write cost | Low, local | Higher, remote; often async |
| Read by the indexed field | Scatter-gather | Targeted |
| Index freshness | Immediate | Possibly lagging |
| Good when | Secondary queries are rare, or always include the partition key | Secondary lookups are frequent and must be fast |

## Lookup tables

For unique, frequent lookups (email → user), keep a small dedicated table partitioned by the lookup key:

```
users_by_email(email PK) → user_id
```

Write it together with the user (or through an outbox), and enforce uniqueness there.

## Search and analytics

For flexible filtering across many fields, don't build ever more global indexes. Stream changes into a **search
engine** (Elasticsearch/OpenSearch) or a **warehouse** (Module 17), and accept seconds of lag.

## Try it

A marketplace partitions listings by `seller_id`. Buyers search by category and price range, constantly. Which index
approach, and why?

<details>
<summary>Answer</summary>

Buyer search doesn't include `seller_id`, so local indexes would mean scatter-gather on every search. Use a
**search engine** (or a global index on category) fed asynchronously from listing changes. Category plus price-range
filtering and ranking are search-engine strengths, and a few seconds of index lag is acceptable for new listings.
</details>

## Key takeaways

- Queries without the partition key need secondary indexes.
- Local indexes make writes cheap and reads scatter-gather.
- Global indexes make reads targeted, and writes remote and often eventually consistent.
- Use lookup tables for unique keys, and search engines for flexible queries.

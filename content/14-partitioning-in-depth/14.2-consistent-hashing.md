# Consistent hashing

With `node = hash(key) % N`, going from 4 to 5 nodes changes the node for about **80% of keys**. For a cache cluster,
that's a mass miss storm; for a database, a huge data migration. Consistent hashing moves only about **1/N** of the
keys.

## The ring

Map the hash space onto a circle (say 0 to 2³²−1). Place each **node** on the ring at `hash(node_id)`. Each **key**
belongs to the first node found going clockwise from `hash(key)`.

```
            0
      N3 ●     ● N1
   k7 ·           · k1
         ring
   k5 ·           · k2
      N2 ●     ●
            (keys walk clockwise to the next node)
```

## Adding and removing nodes

- **Add N4** between N1 and N2: only the keys between N1 and N4 move (from N2 to N4). Everything else stays put.
- **Remove N2:** its keys move to the next node clockwise. Nobody else is affected.

On average, adding one node to N moves **1/(N+1)** of the keys.

## Virtual nodes

With few nodes, random positions give **uneven arcs**: one node might own 40% of the ring. Fix: give each physical
node **many positions** (virtual nodes, say 100–256 each).

- Load evens out statistically.
- When a node leaves, its load spreads over **many** other nodes instead of dumping it all on one neighbour.
- Bigger machines get more virtual nodes, a natural way to weight capacity.

## Replication on the ring

Store each key on the next **R distinct physical nodes** clockwise (Dynamo, Cassandra). Skip virtual nodes belonging
to a node already chosen, and prefer nodes in different racks or zones.

## Rendezvous (highest random weight) hashing

An alternative: for each key, compute `score = hash(key, node)` for every node, and pick the highest. Adding a node
only steals the keys where it scores highest (again ~1/N). It's simple, needs no ring structure and balances well, but
costs O(N) per lookup (fine for tens of nodes).

## Where it's used

- Distributed caches (client-side sharding of Memcached/Redis).
- Dynamo-style databases (Cassandra, Riak, DynamoDB internally).
- Load balancers with session affinity (Maglev, Envoy's ring hash).
- CDNs choosing which edge cache holds an object.

## Try it

A 10-node cache cluster uses `hash % N`. You add an 11th node during peak. Roughly what share of keys miss? With
consistent hashing (plus virtual nodes)?

<details>
<summary>Answer</summary>

With modulo, a key keeps its node only if `hash % 10 == hash % 11`, which is true for roughly 1/11 of keys. So about
**91%** of keys move and miss, a stampede on the database. With consistent hashing, about **1/11 ≈ 9%** move, spread
evenly thanks to virtual nodes.
</details>

## Key takeaways

- `hash % N` remaps almost everything when N changes.
- Consistent hashing places nodes and keys on a ring; adding a node moves ~1/N of the keys.
- Virtual nodes even out load and spread the impact of failures.
- Rendezvous hashing is a simple alternative for small node counts.

# Hot spots

Perfect hashing spreads **keys** evenly. It can't spread **traffic** evenly if one key is wildly more popular than
the rest. A celebrity's profile, a viral post, a flash-sale product, or one giant tenant can overload the single
partition that holds it.

## Recognise the shapes

| Hot spot | Cause | Example |
|----------|-------|---------|
| **Hot key (reads)** | One key read by everyone | A trending post |
| **Hot key (writes)** | One key written constantly | A like counter, a stock count during a sale |
| **Hot range** | Sequential keys under range partitioning | Timestamp keys; auto-increment ids |
| **Hot tenant** | One customer much bigger than the rest | An enterprise tenant in a SaaS |

Measure per partition (requests, CPU, latency), not just cluster averages. A cluster at 30% can have one partition
at 100%.

## Fixes for hot reads

- **Cache in front:** a CDN or Redis, plus a **local in-process cache** on each app server for the hottest keys
  (lesson 3.6).
- **Replicate the hot key:** more replicas serve reads for that partition.
- **Request coalescing:** collapse identical in-flight reads into one.

## Fixes for hot writes

- **Key salting:** split `post:9001:likes` into `…#0` to `…#15`, spread writes, and sum on read (lesson 12.8).
- **Batch and aggregate:** buffer increments in memory and apply them every few seconds.
- **Turn updates into appends:** record events and aggregate asynchronously.

## Fixes for hot ranges

- Prefix sequential keys with a hash or bucket (lesson 14.1).
- Use random or hashed ids for primary keys where order doesn't matter.
- Let the store **split ranges** automatically, and pre-split before known load (e.g. before a launch).

## Fixes for hot tenants

- Give the tenant **its own partitions** (directory-based placement, lesson 9.3).
- Sub-partition within the tenant (`(tenant_id, user_id)`).
- Per-tenant rate limits and quotas (Module 8), so one tenant can't starve the rest.

## Adaptive systems

Modern stores detect and react to hot spots: DynamoDB's adaptive capacity and automatic splitting, Bigtable and
CockroachDB load-based range splits. They help, but a single key can't be split. Hot single keys need the
application-level fixes above.

## Try it

A flash sale puts one product (stock = 5,000) on sale at noon. 200,000 users try to buy within 30 s, and every attempt
decrements `stock` on one row. Propose a design.

<details>
<summary>Answer</summary>

Don't let 200,000 transactions fight over one row. Options: a **waiting room / queue** that admits buyers at a
manageable rate; **pre-split the stock** into, say, 50 buckets of 100 units (salted keys), where each buyer tries a
random bucket and moves on if it's empty; or atomic decrements in Redis (`DECR`, rejecting below 0) as a fast gate,
with orders confirmed asynchronously into the database. The read side (product page) comes from CDN/cache.
</details>

## Key takeaways

- Even hashing can't fix uneven popularity: hot keys, ranges and tenants happen.
- Measure per partition, not just cluster averages.
- Hot reads: cache, replicate, coalesce. Hot writes: salt, batch, append.
- Hot ranges: bucket or hash keys. Hot tenants: isolate and limit.

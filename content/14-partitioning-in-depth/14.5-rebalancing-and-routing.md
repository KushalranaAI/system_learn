# Rebalancing and routing

Clusters change: nodes are added for growth, removed for cost, replaced after failure. **Rebalancing** moves
partitions between nodes; **routing** makes sure every request still finds the right node while that happens.

## Rebalancing strategies

| Strategy | How | Used by |
|----------|-----|---------|
| **Fixed number of partitions** | Create many partitions up front (e.g. 1,024) and assign several to each node; move whole partitions | Elasticsearch shards, Riak, Kafka topics, Couchbase vBuckets |
| **Dynamic splitting** | Partitions split when too big or too hot, and merge when small | HBase, Bigtable, CockroachDB, DynamoDB |
| **Proportional to nodes** | Each node owns a fixed number of partitions (virtual nodes); new nodes take some from others | Cassandra |

Avoid `hash % N` (lesson 14.2).

## Moving a partition safely

```
1. Start copying the partition to the new node (snapshot)
2. Stream ongoing writes to the new copy until it catches up
3. Atomically switch ownership (in the cluster metadata)
4. Redirect traffic; drain and delete the old copy
```

- Move a few partitions at a time, and **throttle** the copying so it doesn't starve live traffic.
- Many systems require (or recommend) an **operator to approve** rebalances: automatic rebalancing during a brief
  overload can make things worse.

## Routing: who knows where a key lives?

| Approach | How | Examples |
|----------|-----|----------|
| **Any node forwards** | Client sends to any node; it forwards to the owner | Cassandra (coordinator node), Riak |
| **Routing tier** | A proxy layer knows the map | Vitess (vtgate), MongoDB (mongos), Redis Cluster proxies |
| **Partition-aware clients** | The client library holds the map and goes direct | Kafka clients, Redis Cluster clients, DynamoDB SDK |

The partition map itself must be reliable and agreed on. It's usually stored in a **consensus system** (ZooKeeper,
etcd, or a Raft-based metadata service), and pushed or gossiped to routers and clients.

## Handling stale maps

During a move, a client may still route to the old owner. Common patterns:
- the old owner replies **"moved, ask node X"** (Redis Cluster `MOVED`/`ASK`), and the client updates its map;
- a version or **epoch** number on the map: requests with an old epoch are rejected and the client refreshes.

## Try it

Your 6-node Elasticsearch-style cluster has an index with 6 primary shards (one per node). You add 6 more nodes. Why
doesn't the index get faster for writes, and what should you have done?

<details>
<summary>Answer</summary>

With a **fixed** count of 6 primary shards, at most 6 nodes can hold primaries; the new nodes only get replicas (which
help reads, not writes). Fix: create the index with more primary shards than nodes from the start (e.g. 24–48, sized
by data per shard), or reindex or split into a new index with more shards.
</details>

## Key takeaways

- Rebalance with many fixed partitions, dynamic splits, or per-node virtual partitions, never `% N`.
- Move partitions by copy → catch up → switch → drain, throttled.
- Route via any node, a routing tier, or partition-aware clients; keep the map in a consensus store.
- Handle stale maps with redirects and epochs.

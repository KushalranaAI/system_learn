# Recommendation systems

Before LLMs, recommendation systems were the largest ML systems in production, and they still drive much of what
people watch, read and buy. Netflix's engineers wrote in 2015 that about **80% of hours streamed** came from
recommendations. The architecture is a **funnel**: from millions of items to the dozen a user sees, in about 100 ms.

## The funnel

YouTube's 2016 paper *Deep Neural Networks for YouTube Recommendations* (Covington, Adams, Sargin) set out the
two-stage shape most systems still use:

```
corpus: millions of videos
   │ 1. candidate generation (several sources, cheap, recall-oriented)
   ▼
hundreds of candidates
   │ 2. ranking (expensive model, many features, precision-oriented)
   ▼
dozens, scored
   │ 3. re-ranking / business rules: diversity, freshness, dedupe, policy, ads
   ▼
the 10-20 items on screen
```

| Stage | Items in → out | Latency share | Model |
|-------|---------------:|---------------|-------|
| Candidate generation | millions → ~1,000 | ~20-30 ms | Two-tower embeddings + ANN, plus heuristics (trending, followed creators, "because you watched") |
| Ranking | ~1,000 → ~100 | ~30-50 ms | Deep network or gradient-boosted trees, hundreds of features |
| Re-ranking | ~100 → ~20 | ~5-10 ms | Rules + diversity algorithms |

In the YouTube paper, ranking was trained to predict **expected watch time** (weighted logistic regression) rather
than click probability, because optimising clicks rewards clickbait. Choosing the objective is the most important
product decision in the system.

## Two-tower models

The workhorse of candidate generation:

```
user tower:  user id, history, context (time, device) ─► MLP ─► user vector u (e.g. 128-d)
item tower:  item id, title, category, creator         ─► MLP ─► item vector v
score = u · v     (trained so that items the user engaged with score high)
```

Because the towers are separate, you can:
- **precompute all item vectors offline** and load them into an ANN index (HNSW, [lesson 34.3](#/lesson/34.3));
- compute the **user vector at request time** (one forward pass, a few ms);
- retrieve the top ~500 items by dot product in milliseconds.

Google's 2019 paper on YouTube (Yi et al., *Sampling-bias-corrected neural modeling*) describes training two-tower
retrieval models with in-batch negatives and correcting the bias toward popular items that this sampling causes.
It is the same idea as embedding retrieval in RAG (module 34): the vector DB doesn't care whether vectors are
passages or videos.

## Feature stores

Ranking models use hundreds of features: user's watch counts by category over 1 h / 7 d / 30 d, item's
click-through rate in the last hour, creator's upload frequency... They must be computed the **same way** for
training (historical, as of each past event) and serving (now, in milliseconds). A **feature store** provides both:

```
events (Kafka) ─► stream jobs (Flink) ─► online store (Redis/Cassandra)  ─► ranking service (reads in ~1-5 ms)
              └─► batch jobs (Spark)  ─► offline store (warehouse)       ─► training data with point-in-time joins
```

Lesson [37.6](#/lesson/37.6) covers feature stores and training-serving skew in depth.

## Serving architecture

```
GET /feed ─► feed service
              ├─ candidate sources in parallel (ANN on two-tower vectors, trending, follows, recent) ─ ~25 ms
              ├─ fetch features for user + ~1,000 candidates from the online store (batched)      ─ ~10 ms
              ├─ ranking model on GPU/CPU inference service (batched scoring)                       ─ ~30 ms
              ├─ re-rank: diversity, dedupe, freshness, policy filters                               ─ ~5 ms
              └─ log impressions (what was shown, at which position, with which scores) ─► Kafka
```

Cache precomputed feeds for inactive users; compute on request for active ones.

## Feedback loops

The system trains on what users clicked among what **it chose to show**. That creates loops:
- **Popularity bias / rich-get-richer:** shown items get clicks, so they get shown more. New items and creators
  never get a chance (**cold start**).
- **Position bias:** top slots get clicks because they're on top. Log the position and model it.
- **Filter bubbles:** narrow interests get narrower.

Countermeasures: reserve a small share of slots for **exploration** (new or random items, bandit algorithms),
diversity constraints in re-ranking, content-based features for new items (the item tower uses title and category,
not only the id), and offline evaluation that accounts for what was shown (counterfactual evaluation). Measure
long-term metrics (retention, satisfaction surveys), not only clicks.

## Where LLMs come in

LLMs are increasingly used to create item features (summaries, topics, embeddings of text and video), to explain
recommendations, and in "generative retrieval" research, but the funnel and its latency budget remain. An LLM
call per candidate (1,000 per request) is not affordable; per-item work is done offline.

Design a "For you" feed for a short-video app: 50M daily users, 100M videos, 20k new videos per hour, feed request

- **Candidates (parallel, ~30 ms):** two-tower ANN over 100M item vectors (sharded HNSW), plus followed creators,

- **Ranking (~50 ms):** multi-task model predicting completion, like, share, skip; final score is a weighted mix tied
  to long-term retention, not just clicks.
- **Re-rank:** no two videos from the same creator in a row, 10% exploration slots, policy filters.
- **Logging:** impressions with positions and scores → Kafka → training data; retrain daily, fine-tune hourly.

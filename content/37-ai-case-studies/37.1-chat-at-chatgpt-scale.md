# Chat at ChatGPT scale

ChatGPT went from launch (November 2022) to one of the largest consumer apps ever; OpenAI said in October 2025 it had
about 800 million weekly users. Its architecture isn't public in detail, but its public incident reports and
statements show the problems any large chat service faces: **GPU capacity is the scarce resource**, demand is spiky,
and the boring parts of the stack (caches, Kubernetes, DNS) cause the big outages.

## The shape of the system

```
clients ─► edge / CDN / WAF ─► API gateway (auth, rate limits by tier)
                                   │
                    conversation service ─► conversation store (history, titles)
                                   │             cache (Redis)
                                   ▼
                     inference router ─► per-model queues ─► GPU clusters (many regions)
                                   │                          continuous batching, KV cache
                     tools: search, code sandbox, image generation, file retrieval
```

Unlike a normal web request (milliseconds of CPU), each chat turn holds GPU memory (its KV cache, [lesson 33.3](#/lesson/33.3)) for
the whole generation, often 5-30 seconds. Capacity is measured in **concurrent sequences and tokens per second**,
not requests per second.

## GPU capacity planning

Work from tokens, then GPUs. An example launch (all inputs are assumptions you'd replace with measurements):

```
users: 2M daily actives, 10 messages/day each      = 20M messages/day
average rate: 20M / 86,400                          ≈ 230 messages/s
peak: 3× average                                    ≈ 700 messages/s
output per message: 500 tokens                      → 350,000 output tokens/s at peak
input per message: 2,000 tokens (history + system)  → prefill load, much of it cacheable
```

Then measure (don't guess) a replica's throughput at your latency target. Suppose one 8-GPU node serving your model
with continuous batching sustains ~3,000 output tokens/s while keeping TTFT under 1 s:

```
decode nodes: 350,000 / 3,000                        ≈ 117 nodes
+ prefill overhead, + headroom to run at ~70-75%     ≈ 160 nodes ≈ 1,300 GPUs
+ N+1 per region, + capacity for a region failover
```

The 70-75% target is queueing theory again ([lesson 4.1](#/lesson/4.1)): near 100% utilisation, TTFT explodes. GPUs take weeks to
months to procure, so the plan also needs **what to do when demand exceeds it**.

## Queueing and degradation under overload

When demand exceeds GPUs, something has to give. The levers, from mildest:
1. **Queue briefly** (users see a slightly slower first token).
2. **Shorten work:** cap output length, route free users to a smaller model.
3. **Rate limit by tier:** paid tiers get higher message caps; free users hit "you've reached your limit".
4. **Waitlist / delay a rollout** for new features or free users.
5. **Shed load** with a clear "at capacity" message rather than timeouts for everyone.

This happened in public. When ChatGPT's image generation launched in late March 2025 and went viral (the Studio
Ghibli-style trend), Sam Altman posted that "our GPUs are melting"; OpenAI added temporary rate limits and delayed the
rollout to free users. A few days later he said they had added one million users in an hour.

## Rate limits and tiers

The API side uses **usage tiers**: an account's rate limits (requests and tokens per minute) grow with its spend
and history. Two lessons for your own product:
- Limit in **tokens**, not just requests: one request can be 100× another ([lesson 8.3](#/lesson/8.3)).
- Tiers are a capacity tool as much as a pricing tool: they decide who degrades first.

## What its outages taught

**March 20, 2023: a cache bug leaked data.** A bug in the open-source Redis client (redis-py) meant a cancelled
request could leave a connection in a bad state, so the next request on it got **another user's** data. Some users
saw other users' conversation titles, and payment details (name, email, address, last four card digits, expiry) of
about 1.2% of ChatGPT Plus subscribers active in a nine-hour window may have been visible. Lesson: connection reuse
and cancellation in shared caches are a cross-tenant data risk. Test cancellation paths; tag cached values with the
owner and verify on read.

**December 11, 2024: the control plane took down everything.** A new telemetry service rolled out across the fleet
made every node issue expensive Kubernetes API calls. The API servers in most large clusters were overwhelmed; DNS
based service discovery depended on them, so services failed. OpenAI's write-up gives about 4 hours of significant
degradation or unavailability (3:16 to 7:38 pm PT). Two details made it worse: **DNS caching delayed the failure**, so
the change had spread widely before symptoms appeared, and engineers needed the control plane to roll back the
change that broke it (**locked out**). The change had been verified in a staging cluster the day before, but staging
was too small to show the load. OpenAI's follow-ups: phased infrastructure rollouts that also watch control-plane
health, fault-injection tests, **break-glass access** to the Kubernetes API "under any circumstances", and decoupling
critical services from Kubernetes DNS.

The general lessons are the classic ones (module 31): stage config and fleet-wide changes, decouple the data plane
from the control plane, and keep an emergency path that doesn't depend on the thing that's broken.

## Try it

Plan GPUs for a launch: an AI writing feature for an existing app with 5M daily users. You expect 20% to try it on
day one, 6 requests each, 400 output tokens and 1,500 input tokens per request; 8 of the 24 hours carry 70% of the
traffic. One node does 2,500 output tokens/s at your latency target.

<details>
<summary>Reference</summary>

- Requests: 5M × 20% × 6 = **6M/day**. Peak window: 70% in 8 h → 4.2M / 28,800 s ≈ 146/s; peak-of-peak ×1.5 ≈ **220/s**.
- Output tokens at peak: 220 × 400 ≈ **88,000 tokens/s** → 88,000 / 2,500 ≈ 35 nodes.
- Headroom to ~70% utilisation → **~50 nodes**, plus prefill (1,500 input tokens; prefix caching helps for the
  shared system prompt), plus N+1 per region.
- Overload plan: per-user daily cap, queue with a progress indicator, fall back to a smaller model for free users,
  feature flag to pause new-user rollout. Launch to 10% of users first and measure real tokens per request.
</details>

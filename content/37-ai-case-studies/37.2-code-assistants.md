# Code assistants

A code assistant (GitHub Copilot, Cursor and others) is really three products with very different budgets:

| Feature | Latency budget | Model | Context |
|---------|----------------|-------|---------|
| **Inline completion** (ghost text as you type) | ~100s of ms end to end, or it's useless | Small, fast, often fill-in-the-middle | Current file + nearby snippets |
| **Chat** about the code | Seconds; streamed | Large | Retrieved code, open files, user selection |
| **Agent** that edits code, runs tests | Minutes | Large, many steps | Searches the repo itself, runs tools |

## Inline completion: a latency problem

The user keeps typing; a suggestion that arrives late is wrong (the cursor moved). Design choices that follow:

- **Debounce** keystrokes and **cancel** in-flight requests when the user types on. Most requests are cancelled;
  servers must stop generation on cancel or they waste GPU.
- **Small models, short outputs:** often just the rest of the line or block; stop at a newline when possible.
- **Fill-in-the-middle (FIM):** send the code before *and after* the cursor, so the model completes a gap rather than
  continuing a file. GitHub reported that FIM gave about a **10% relative** improvement in completion acceptance.
- **Serve close to the user:** model replicas in several regions; keep connections warm (HTTP/2).
- **Client-side context assembly:** the editor (which has the files) builds the prompt, so the server does no extra
  round trips.

## Context from the codebase

The model only knows what's in the prompt, and the prompt is small relative to a repo. Choosing context is the
product.

GitHub described Copilot's prompt building in its engineering blog:
- A **prompt library** collects candidate context (current file, cursor position, imports, file path and language)
  and ranks it into a token budget.
- **Neighboring tabs:** snippets from the other files open in the editor that are similar to the code around the
  cursor. Even weak matches helped: GitHub reported about a **5% relative** increase in accepted suggestions.

For chat and agents, context comes from **indexes**:

| Source | Finds | Built how |
|--------|-------|-----------|
| Embedding index of code chunks | "where do we validate coupons?" (meaning) | Chunk by syntax (functions, classes), embed |
| Lexical / trigram index | Exact identifiers, error strings | Classic code search ([lesson 29.2](#/lesson/29.2)) |
| Symbol graph | Definitions, references, call sites | Language servers / static analysis |
| Git metadata | Recent changes, owners, related files | Commits |

Agents increasingly use **tools over these indexes** (grep, read file, list symbols, semantic search) instead of
one-shot retrieval: they search, read, and search again.

## Indexing a repository: Cursor's design

Cursor published how it indexes codebases for semantic search (*Securely indexing large codebases*, January 2026):
- Changed files are split into **syntactic chunks** and embedded in the background (embedding is the expensive
  step); embeddings are **cached by chunk content**, so unchanged chunks are never re-embedded.
- The client keeps a **Merkle tree** of file hashes (each folder's hash derives from its children). To sync, client
  and server compare trees and walk only the branches whose hashes differ. For a 50,000-file workspace, filenames
  plus SHA-256 hashes are about 3.2 MB, so walking only changed branches matters.
- **Reusing teammates' indexes:** clones of the same repo inside a company are on average about 92% similar. The
  client computes a **simhash** of its Merkle tree; the server finds a similar existing index in the same team and
  starts from a copy.
- **Access control by proof:** until the client's own index is synced, search results are filtered to files whose
  hashes the client's uploaded Merkle tree proves it has. You can't query code you don't possess.
- Effect: median time-to-first-query fell from **7.87 s to 525 ms**, and p99 from **about 4 hours to 21 s**.

## Agents that edit code

A coding agent is the agent loop ([lesson 35.2](#/lesson/35.2)) with tools like `search`, `read_file`, `edit_file` (as a diff),
`run_tests`, `run_command`. Architecture concerns:

- **Sandbox** every command (container or microVM, no production credentials, egress allow-list), [lesson 35.7](#/lesson/35.7).
- **Verification is cheap and strong:** compile, lint, tests. Use them after every edit ([lesson 35.8](#/lesson/35.8)).
- **Edits as diffs** with exact anchors; whole-file rewrites waste tokens and drop code.
- **Output is a PR**, reviewed by a human and by CI, not a direct push to main.
- **Repo content is untrusted input:** a README or issue can carry prompt injection ([lesson 36.4](#/lesson/36.4)).

## Try it

Design repo indexing for a monorepo: 2 million files, 40 GB, 3,000 engineers, ~5,000 commits a day, some
directories restricted to certain teams.

<details>
<summary>Reference</summary>

- **Server-side canonical index of main**, not one per laptop: an indexer subscribes to commits (webhook → queue),
  diffs changed files, re-chunks by syntax, embeds only chunks whose content hash changed (cache keyed by hash).
  5,000 commits/day × ~10 files ≈ 50k file updates/day: small for a worker pool.
- **Three indexes:** trigram/lexical for exact search, embeddings for meaning, symbol graph from build/LSP data.
  Shard by directory (top-level project) so queries can be scoped.
- **Branches:** the server index covers main; each client overlays its local changes (Merkle diff against main's
  tree) with a small local or per-user delta index.
- **Permissions:** store directory ACLs as metadata on each chunk; filter **before** ranking by the engineer's
  groups. Don't index secrets (scan and exclude `.env`, keys).
- **Scale:** 40 GB of code ≈ maybe 50-100M chunks; ANN index sharded and replicated ([lesson 34.3](#/lesson/34.3)); embedding the
  whole repo once is a batch job (batch API or own GPUs), then only deltas.
- **Freshness SLO:** a commit is searchable within ~5 minutes; monitor indexing lag like consumer lag.
</details>

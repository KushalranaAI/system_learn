# Lab: an AI support assistant

An online electronics retailer with **3 million customers** wants an AI assistant in its help widget. It should answer
questions from the help centre, look up orders, and handle simple returns and refunds, handing everything else to the
existing human support team. Work through the design from requirements to a load test. Answer each step yourself
before opening the reference.

> **Interactive version:** [open the AI support agent lab](#/labs/ai-support-agent): it has the decisions as checked
> steps and a canvas to load-test.

## Requirements

- **50,000 conversations a day**, about 4 customer turns each; evenings and Black Friday bring peaks.
- First token in **under 2 s** (p95); a full answer within 8 s.
- Answers must follow the published returns policy (it differs between EU and US).
- Refunds up to **100 EUR** on eligible orders without a human; anything else is escalated.
- Customers can always reach a human. Personal data stays in the EU for EU customers.
- Budget: the CFO wants cost per resolved conversation well under a human's (~4 EUR).

## Step 1: Workflow or agent?

<details>
<summary>Reference</summary>

Both. A **router** (small model, one call) classifies each turn: FAQ / order status / return-refund / other.
FAQ is a **workflow** (retrieve → answer with citations): one LLM call. Order status is a workflow too (one tool
call, one answer). Only return/refund and messy multi-issue conversations need the **agent loop** with tools, which
is where the cost and risk are. "Other" (legal, complaints, "human please") goes straight to the human queue.
See [lesson 35.1](#/lesson/35.1).
</details>

## Step 2: Estimate the load

<details>
<summary>Reference</summary>

```
turns/day = 50,000 × 4                       = 200,000
average   = 200,000 / 86,400                 ≈ 2.3 turns/s
peak      = ×4 (evening) ×2.5 (Black Friday) ≈ 23 turns/s  → design for ~25/s
mix: 50% FAQ (1 call), 25% order status (2 calls), 20% refund agent (~5 calls), 5% human
model calls/turn ≈ 0.5×1 + 0.25×2 + 0.2×5 + router 1 ≈ 3.0
peak model calls ≈ 75/s;  with a 20% semantic-cache hit on FAQ ≈ 70/s
```
Tokens per call ~4,000 in (system + tools + docs + history), ~200 out.
</details>

## Step 3: Estimate the cost

<details>
<summary>Reference</summary>

```
calls/day ≈ 200,000 × 3.0 = 600,000
large model everywhere ($3 / M in, $15 / M out):
  600k × (4,000 × 3 + 200 × 15) / 1M = 600k × $0.015 = $9,000/day  ≈ $270k/month
routed: router + FAQ + status on a small model (~10× cheaper), agent on large;
prefix caching on the ~2,500-token stable prefix:
  ≈ $1,500-2,500/day  ≈ $45-75k/month
per conversation ≈ $0.03-0.05;  per resolved conversation (60% resolved) ≈ $0.05-0.08
```
Far under a human's ~4 EUR, so the constraint is **quality**, not cost. Don't save pennies with a model that fails
evals. See [lesson 36.5](#/lesson/36.5).
</details>

## Step 4: Draw the architecture

<details>
<summary>Reference</summary>

```
widget ─► CDN/WAF ─► API (auth: customer id, region) ─► rate limiter (per customer, tokens/min)
                         │
                         ├─► semantic cache (FAQ answers, per region + policy version)
                         ├─► router (small LLM)
                         ├─► RAG: hybrid index of help articles (vectors + BM25), filtered by region
                         ├─► agent runtime (durable: state in Postgres; step limit 10; budget per task)
                         │      └─► MCP servers: orders (read), returns/refunds (write, limits in code)
                         ├─► model gateway ─► EU region deployment of provider A │ fallback provider B (EU)
                         ├─► guardrails: PII redaction in, policy + groundedness out
                         └─► helpdesk API (escalation tickets with summary)
conversation store · traces (OTel GenAI) · audit log · eval pipeline
ingestion: CMS webhook ─► queue ─► chunk + embed workers ─► vector DB
```
On the canvas: client → lb → server; server → cache, vectordb, agent; agent → llm, vectordb; worker → vectordb for
ingestion.
</details>

## Step 5: Retrieval

<details>
<summary>Reference</summary>

About 2,000 help articles → ~20,000 chunks (section-based, ~300-500 tokens, title and region in metadata). Hybrid
search (product codes like "WH-1000XM5" need BM25), filter by region **before** ranking, rerank top 30 → 4 chunks.
Re-index on every CMS publish via a queue; the semantic cache key includes the policy version, so a policy change
invalidates cached answers. A tiny index: one vector DB replica is enough for capacity, two for availability.
See [module 34](#/lesson/34.4).
</details>

## Step 6: Tools and permissions

<details>
<summary>Reference</summary>

| Tool | Mode |
|------|------|
| `search_help`, `get_order`, `track_shipment` | Automatic, scoped to the logged-in customer |
| `start_return` | Automatic after the customer confirms the item |
| `refund_order` ≤ 100 EUR, delivered < 30 days, no refund yet | Automatic; limits, ownership, idempotency key `conv:step` enforced in code |
| Refund > 100 EUR, repeat refunders, damaged-on-arrival disputes | Human approval (durable wait) |
| `escalate_to_human(summary, reason)` | Always available; honoured immediately on request |

No raw SQL, no admin tokens, no tools that send email or fetch arbitrary URLs: the agent reads customer messages
(untrusted), so it must not also have an exfiltration channel ([lesson 36.4](#/lesson/36.4)).
</details>

## Step 7: Size the model tier

<details>
<summary>Reference</summary>

In this course's simulator a **medium** model replica serves about 5 requests/s and a **small** one about 12. At
~70 calls/s peak, about two-thirds (router, FAQ, order status) go to the small model and one-third (agent steps) to
the medium one: ~47/s ÷ 12 ≈ 4 small replicas, ~23/s ÷ 5 ≈ 5 medium replicas; run them at ≤ 70-75% utilisation →
**6 small + 7 medium**, with continuous batching on. If you use a provider API
instead, check the account's tokens-per-minute limit: 70 calls/s × 4,200 tokens ≈ 17.6M tokens/min at peak, which
needs a raised quota agreed before Black Friday.
</details>

## Step 8: Failure modes

<details>
<summary>Reference</summary>

- **Provider down:** gateway TTFT timeout 4 s, circuit breaker, fallback to provider B (EU, evaluated weekly); if all
  fail, the widget shows help-centre search and a contact form ([lesson 36.6](#/lesson/36.6)).
- **Agent loops:** step limit 10, budget per task, escalate with a summary ([lesson 35.8](#/lesson/35.8)).
- **Crash mid-refund:** durable run state + idempotency key, so a resumed run can't refund twice
  ([lesson 35.6](#/lesson/35.6)).
- **Bad answer about policy:** groundedness check on policy answers; no promises outside tools
  ([lesson 37.7](#/lesson/37.7)).
- **Cache flush on Black Friday:** cold semantic cache adds ~20% model load: keep headroom or pre-warm with the top
  500 questions.
</details>

## Step 9: Evals and launch

<details>
<summary>Reference</summary>

Golden set of ~200 cases (FAQ by region, refunds at/over limits, already refunded, wrong customer's order id,
injection attempts, "human please", other languages). CI gate: 100% on money and escalation cases, groundedness
≥ 95%. Shadow mode for a week (agent drafts, humans send), then 5% → 25% → 100% by region, watching verified
resolution (no re-contact in 7 days), CSAT, escalations, refunds per hour and cost per resolution.
See [lesson 36.1](#/lesson/36.1).
</details>

## Step 10: Load-test it

<details>
<summary>Reference</summary>

Build it in the lab or the [support agent sandbox scenario](#/sandbox?preset=ai-support-agent) and run: steady peak
(25 reads/s), a **spike ×2**, a **cache flush**, and **an LLM replica down**. Pass if p99 stays within budget and
failures stay near zero. Typical findings: without the step limit, runaway tasks inflate model load and p99; without
the cache, a flush pushes the model tier past 85% busy and latency climbs steeply; one replica down needs N+1
headroom. Compare agent steps and limits in the [agent reliability simulation](#/sims/agent-reliability) and routing
in the [model cascade simulation](#/sims/model-cascade).
</details>

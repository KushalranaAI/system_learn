# OAuth 2

Before OAuth, if a budgeting app wanted to read your bank transactions, you gave it your bank password. It could then do
anything you could, forever, and the only way to stop it was to change your password everywhere. **OAuth 2** (RFC 6749,
2012) replaced that with *delegated, limited, revocable access*: the app gets a token for specific permissions, and you
never hand over your password.

OAuth is an **authorization** framework. It says what a client may access; it doesn't, by itself, say who the user is.
That's OpenID Connect (lesson 21.7).

## The four roles

| Role | Example |
|------|---------|
| **Resource owner** | You |
| **Client** | The budgeting app |
| **Authorization server** | The bank's login and consent service (`auth.bank.example`) |
| **Resource server** | The bank's API (`api.bank.example`) |

## Authorization code flow with PKCE

The standard flow for any app with a user: web apps, single-page apps, mobile and desktop apps.

```
 app                          browser                     auth server                    API
  │ 1. make code_verifier (random) and code_challenge = SHA256(verifier)
  │──── 2. redirect ─────────▶│ /authorize?response_type=code&client_id=budget
  │                           │   &scope=transactions:read&redirect_uri=…
  │                           │   &code_challenge=…&state=…        ───────────▶│
  │                           │◀── 3. user signs in, approves "read transactions" │
  │◀─ 4. redirect_uri?code=…&state=… ─│                                         │
  │──── 5. POST /token  code + code_verifier ──────────────────────────────────▶│
  │◀─── 6. access_token (short-lived) + refresh_token ──────────────────────────│
  │──── 7. GET /transactions  Authorization: Bearer <access_token> ─────────────────────────────▶│
```

- **PKCE** (Proof Key for Code Exchange, RFC 7636) stops an attacker who intercepts the `code` from redeeming it,
  because only the real app knows the `code_verifier`. It matters most for apps that can't keep a secret (mobile, SPA),
  and is now recommended for every client.
- **`state`** ties the response to the request (CSRF protection).
- **Redirect URIs must match exactly** what was registered. Loose matching is a classic token-theft bug.
- Mobile apps should use the **system browser** (not an embedded web view) so the app never sees the password.

## Other flows

| Flow | When | Notes |
|------|------|-------|
| **Client credentials** | Machine-to-machine, no user (a nightly export job) | The client authenticates as itself; keep scopes narrow |
| **Device authorization** (RFC 8628) | TVs, consoles, CLIs with no browser | Shows a code; you approve on your phone |
| **Refresh token** | Get a new access token without asking the user again | Rotate on every use; revoke the family if an old one is reused |
| ~~Implicit~~ | Was for browsers | Tokens in URL fragments leak; **don't use** |
| ~~Resource owner password~~ | App collects the password | Defeats the purpose; **don't use** |

## OAuth 2.1

OAuth 2.1 is an IETF draft (not yet an RFC as of late 2026) that consolidates a decade of security advice into one
document: **PKCE required** for the authorization code flow, the **implicit and password grants removed**, exact
redirect-URI matching, and no tokens in query strings. If you build OAuth today, follow it even before it's final.

## Scopes: designing permissions

Scopes are part of your API's contract. Design them around what users understand and what you'll want to grant
separately:

```
accounts:read   transactions:read   payments:write   payees:manage   offline_access
```

- Prefer resource-and-action scopes over one giant `full_access`.
- Request the minimum; ask for more later (incremental consent).
- The API must still check that the **user** may access the **object**: a `transactions:read` token doesn't make
  someone else's transactions readable.

## Try it

Pick the flow: (a) a React single-page app for your own product; (b) a smart TV app; (c) a partner's server that
syncs invoices every hour with no user present; (d) a third-party mobile app reading users' fitness data.

<details>
<summary>Answer</summary>

(a) Authorization code + PKCE (often through a small backend-for-frontend that keeps tokens out of the browser and uses
an HttpOnly session cookie). (b) Device authorization flow. (c) Client credentials, with a scope limited to invoices
(or mTLS-bound tokens). (d) Authorization code + PKCE in the system browser, with narrow scopes and refresh-token
rotation.
</details>

## Key takeaways

- OAuth 2 delegates limited, revocable access without sharing passwords; it's about authorization, not identity.
- Use authorization code + PKCE for anything with a user, client credentials for machines, device flow for TVs.
- Never use the implicit or password grants; OAuth 2.1 removes them.
- Scopes limit the app; the API still checks the user's access to each object.

# TLS for APIs

Every API token, password and personal record your API handles crosses networks you don't own: café Wi-Fi, mobile
carriers, the internet backbone, a cloud provider's internal network. **Transport Layer Security** is what keeps them
private and untampered on the way. Lesson 27.3 explains certificates and handshakes in depth; this lesson is about the
decisions an API designer makes.

## What TLS gives you

| Property | Meaning | Without it |
|----------|---------|-----------|
| **Confidentiality** | Only the two ends can read the traffic | Anyone on the path reads tokens and data |
| **Integrity** | Tampering is detected | Injected or modified responses |
| **Server authentication** | The client knows it's really talking to `api.example.com` (certificate signed by a trusted CA) | Man-in-the-middle with a fake server |
| **Client authentication** (optional, mTLS) | The server knows which client this is | Only tokens identify callers |

TLS does **not** protect data at rest, check authorization, or stop a legitimate client from abusing the API.

## TLS 1.3 in one picture

```
client                                      server
  │── ClientHello + key share ─────────────▶│
  │◀─ ServerHello + key share, certificate,  │   1 round trip, then encrypted
  │   Finished (all encrypted after Hello) ──│
  │── Finished + HTTP request ──────────────▶│
```

TLS 1.3 (2018) needs **one** round trip instead of TLS 1.2's two, removed weak ciphers, and always gives forward
secrecy (stealing the server's key later can't decrypt recorded traffic). With session resumption it can send data in
the first flight (**0-RTT**), but 0-RTT data can be **replayed**, so only allow it for safe, idempotent requests.

## Decisions for API designers

1. **HTTPS only, everywhere.** Don't serve the API over plain HTTP at all (not even to redirect): API clients often
   send the token in the first request before seeing a redirect.
2. **Minimum TLS 1.2, prefer 1.3.** Disable older versions.
3. **HSTS** (`Strict-Transport-Security: max-age=31536000; includeSubDomains`) for browser-facing domains.
4. **Automate certificates** (ACME / Let's Encrypt or your cloud's certificate manager). Expired certificates are a
   classic outage cause.
5. **Decide where TLS terminates.**

```
client ══TLS══▶ CDN / edge ══TLS══▶ load balancer ──?──▶ API servers ──?──▶ database
```

Terminating at the edge is fast (handshakes happen close to the user) but the edge sees plaintext. Re-encrypt between
every hop inside your network too ("zero trust"): internal networks get breached, and many regulations expect it.

## Mutual TLS for services and partners

With **mTLS**, both sides present certificates. It's the standard for service-to-service traffic in a service mesh
(Istio, Linkerd issue a short-lived certificate to every workload) and for high-assurance partner APIs (open banking
regulations often require it). It identifies the *machine or service*; you still need authorization for what it may do.

## Certificate pinning?

Mobile apps can "pin" the expected certificate or public key to resist interception. It also means a certificate
rotation can break every installed app. If you pin, pin to several keys (including a backup), and have a remote kill
switch.

## Try it

A partner integration sends API keys in a header. The architecture is: partner → CDN → regional load balancer →
Kubernetes pods → managed Postgres. Where should TLS be used, and is anything else needed for partners?

<details>
<summary>Answer</summary>

TLS on every hop: partner to CDN (public certificate), CDN to load balancer (TLS to the origin), load balancer to pods
(mesh mTLS or TLS with internal certificates), pods to Postgres (TLS with certificate verification). For partners,
consider mTLS on top of API keys, so a leaked key alone isn't enough, and keep keys hashed at rest. Automate every
certificate's renewal and alert well before expiry.
</details>

## Key takeaways

- TLS gives confidentiality, integrity and server (optionally client) authentication in transit, and nothing more.
- Use HTTPS only, TLS 1.3 where possible, HSTS for browsers, and automated certificates.
- Encrypt every internal hop too; terminate at the edge for speed, then re-encrypt.
- mTLS identifies services and partners; authorization is still a separate check.

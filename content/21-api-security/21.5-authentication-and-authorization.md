# Authentication and authorization

A support agent leaves the company on Friday. Their account is disabled in the identity system within the hour. On
Saturday their laptop, still signed in, keeps pulling customer records from the support API until Sunday night, because
the API trusted a token that was valid for 48 hours. Knowing **who** is calling, and **whether** they may do this right
now, are two separate problems, and each has its own failure modes.

| | Authentication (authN) | Authorization (authZ) |
|-|------------------------|------------------------|
| Question | Who are you? | What may you do? |
| Failure status | `401 Unauthorized` (+ `WWW-Authenticate`) | `403 Forbidden` (or `404` to hide existence) |
| Happens | Once per request, in middleware | For every action and every object |

## Ways to identify callers

| Mechanism | How it works | Good for | Watch out |
|-----------|--------------|----------|-----------|
| **API keys** | A long random secret in a header | Server-to-server, simple public APIs, identifying a *project* | Identifies an app, not a user; leaks in repos and logs; store hashed, allow rotation, scope them |
| **Session cookies** | Server stores a session; browser sends an opaque id cookie | First-party web apps | CSRF (lesson 22.7), needs a session store |
| **Bearer tokens** (OAuth 2 access tokens) | `Authorization: Bearer <token>` issued by an auth server | Mobile apps, SPAs, third-party access | Anyone holding the token is the user, so keep it short-lived |
| **mTLS** | Client certificate | Services, high-assurance partners | Certificate lifecycle |
| **Request signing** (HMAC) | Client signs method, path, body and time with a secret | Webhooks, AWS-style APIs | Clock skew, canonicalisation bugs |

## JWTs

A **JSON Web Token** is a signed, self-contained token: `header.payload.signature`, each base64url encoded.

```json
{ "alg": "RS256", "kid": "2026-10" }
{ "iss": "https://auth.bank.example", "sub": "usr_81", "aud": "api.bank.example",
  "exp": 1761640900, "iat": 1761640000, "scope": "accounts:read payments:write" }
```

The API checks the signature with the auth server's **public key** (fetched from its JWKS URL and cached), then reads
the claims. **No network call per request**, which is why JWTs scale. That's also their weakness: the API can't know a
token was revoked until it expires.

**Rules for JWTs:**

- Pin the accepted algorithms (`RS256` / `ES256` / `EdDSA`); never accept `alg: none`; don't let a token pick
  HMAC with your public key as the secret.
- Always check `exp`, `iss` and `aud`. A token for another API must not work on yours.
- Keep **access tokens short-lived (5-15 min)** and use **refresh tokens** (checked by the auth server, revocable,
  rotated on use) for long sessions.
- Don't put secrets or personal data in the payload; it's only encoded, not encrypted.
- For high-risk actions, add a check against a **denylist** or use **opaque tokens with introspection** (the API asks
  the auth server, with a short cache).

## Authorization models

| Model | Rule looks like | Good for |
|-------|-----------------|----------|
| **RBAC** (roles) | "Admins can delete projects" | Most business apps |
| **ABAC** (attributes) | "Managers can approve expenses under ₹50,000 in their own department during business hours" | Rules that depend on data |
| **ReBAC** (relationships) | "You can edit a document if you're an editor of its folder" | Sharing models like Google Drive (Google's Zanzibar paper; open-source OpenFGA, SpiceDB) |
| **Scopes** (OAuth) | The token allows `payments:write` | Limiting what a *client app* may do on a user's behalf |

Scopes and roles combine: a request is allowed only if the **token's scope** permits the operation **and** the **user**
may do it to **this object**.

Put the policy in one place (a library or a policy engine such as OPA or Cedar) and call it from every handler:
`authorize(user, "approve", expense)`. Log every denial.

## Try it

A banking API has 2 million active users making 6 calls a minute. The auth server handles 5,000 req/s. Find an access
token lifetime that keeps a revoked token working for at most 15 minutes without overloading the auth server.

<details>
<summary>Answer</summary>

Each user refreshes once per lifetime: 2,000,000 ÷ (lifetime in seconds). At 24 hours, refreshes are tiny (23/s) but a
revoked token works for up to a day. At 15 minutes: 2,000,000 ÷ 900 ≈ 2,200 refreshes/s, 44% of the auth server, and
revocation within 15 minutes. At 5 minutes you'd need ~6,700/s, over capacity. Introspecting every request would need
tens of thousands of auth-server calls a second; a JWT plus a Redis denylist gives near-instant revocation for one cheap
lookup per request.
</details>

## Key takeaways

- Authentication answers "who" (401); authorization answers "may they, on this object" (403/404), every time.
- API keys identify apps; bearer tokens identify users through a client; mTLS identifies machines.
- JWTs are verified locally and scale, but can't be revoked: keep them short and use refresh tokens.
- Combine scopes (what the app may do) with roles, attributes or relationships (what the user may do), in one policy
  layer.

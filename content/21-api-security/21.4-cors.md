# Cross-origin resource sharing (CORS)

The web app at `https://app.shop.example` calls `https://api.shop.example` and the browser console shows a red error:
*blocked by CORS policy*. A developer finds a snippet that makes the error go away by echoing back whatever origin
asked, with credentials allowed. The app works. So does every malicious website on the internet, using your users'
cookies.

## The same-origin policy

Browsers isolate websites by **origin**: scheme + host + port. `https://app.shop.example` and
`https://api.shop.example` are different origins. By default, JavaScript on one origin can *send* some requests to
another, but it **can't read the responses**. That's what stops `evil.example` from reading your bank account page
using the cookies in your browser.

**CORS** is how a server opts in to letting specific other origins read its responses.

## Simple requests and preflights

| Request | What the browser does |
|---------|-----------------------|
| "Simple" (GET/HEAD/POST with only basic headers and a form-like content type) | Sends it with an `Origin` header; exposes the response to JS only if the server allows that origin |
| Anything else (`PUT`, `DELETE`, `Content-Type: application/json`, an `Authorization` header…) | First sends a **preflight** `OPTIONS` request asking permission, and only sends the real request if allowed |

```http
OPTIONS /v1/orders HTTP/1.1
Origin: https://app.shop.example
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.shop.example
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: authorization, content-type, idempotency-key
Access-Control-Max-Age: 600
Vary: Origin
```

`Access-Control-Max-Age` lets the browser cache the preflight, saving a round trip on later calls.

## Credentials

If the browser should send cookies (or the response sets them), the request uses `credentials: "include"` and the
server must answer:

```http
Access-Control-Allow-Origin: https://app.shop.example     ← an exact origin, never *
Access-Control-Allow-Credentials: true
```

Browsers refuse `*` together with credentials. That's deliberate.

## Mistakes that open holes

| Mistake | Why it's dangerous |
|---------|--------------------|
| Reflecting any `Origin` with `Allow-Credentials: true` | Every site can make authenticated calls as your users and read the results |
| Matching origins with a loose regex (`.*shop\.example`) | `evilshop.example` and `shop.example.evil.com` match |
| Allowing `null` origin | Sandboxed iframes and local files send `null`; attackers can too |
| Forgetting `Vary: Origin` when the header changes per origin | A CDN caches the response for one origin and serves it to another |
| Thinking CORS is authentication | CORS only restrains **browsers**. curl, servers and scripts ignore it entirely |

## Practical policy

- Keep an **allowlist of exact origins** per environment (`https://app.shop.example`, `https://admin.shop.example`).
- For truly public, non-credentialed data (a public catalogue, a CDN font), `Access-Control-Allow-Origin: *` is fine.
- Prefer **same-origin** setups where you can: serve the API under `https://shop.example/api` through the same domain,
  and CORS disappears.
- Configure CORS once, at the gateway or framework middleware, not per handler.

## Try it

The API currently answers every request with `Access-Control-Allow-Origin: <request Origin>` and
`Access-Control-Allow-Credentials: true`. Write the fixed policy for a web app, an admin panel and a public status page
widget that third-party sites embed.

<details>
<summary>Answer</summary>

- `/v1/*` (authenticated): allow exactly `https://app.shop.example` and `https://admin.shop.example` with credentials;
  send `Vary: Origin`; reject preflights from other origins (no CORS headers).
- `/public/status` (no cookies, no personal data): `Access-Control-Allow-Origin: *`, no credentials.
- Keep authentication and object-level authorization on every endpoint regardless: CORS doesn't replace them.
</details>

## Key takeaways

- The same-origin policy stops sites from reading each other's responses; CORS lets a server relax it for chosen
  origins.
- Non-simple requests trigger a preflight; cache it with `Access-Control-Max-Age`.
- With credentials, allow exact origins only; never reflect arbitrary origins.
- CORS restrains browsers only; it's not access control.

# Validating input

A sign-up endpoint accepts `{"email": "...", "name": "..."}`. Someone sends a 40 MB name. Someone else sends
`"role": "admin"` and, because the handler copies the whole body into the user record, becomes an admin. A third sends a
name containing `'); DROP TABLE users; --`. Everything an API receives comes from someone you don't trust, including
your own app, which attackers can modify.

## Validate at the edge of your code

Validate every request **before** business logic runs, against an explicit schema:

```yaml
# OpenAPI / JSON Schema for POST /users
type: object
additionalProperties: false            # unknown fields are rejected
required: [email, name]
properties:
  email: { type: string, format: email, maxLength: 254 }
  name:  { type: string, minLength: 1, maxLength: 100 }
  locale: { type: string, enum: [en, hi, fr, de] }
```

| Check | Example | Stops |
|-------|---------|-------|
| **Type and format** | integers are integers, ids match `^usr_[A-Za-z0-9]{12}$` | Parser confusion, injection payloads in id fields |
| **Size** | max body size, max string length, max array items, max page size | Memory exhaustion, slow processing (API4) |
| **Allowlists over denylists** | `sort` ∈ {`created_at`, `-created_at`, `price`} | Clever inputs nobody thought to deny |
| **Range and business rules** | `quantity` 1-99, `end > start` | Negative quantities, logic bugs |
| **Unknown fields rejected** | `additionalProperties: false` | Mass assignment (API3) |

Reject with `400` or `422` and a problem body that lists the field errors. Don't silently "fix" input.

## Mass assignment

Never bind a request body straight onto a database model. Keep separate input types per operation that list exactly
what the caller may set:

```typescript
const UpdateProfile = z.object({ name: z.string().max(100), bio: z.string().max(500) }).strict();
// role, isVerified, balance are not here, so they can't be set, whatever the client sends.
```

## Injection

Validation reduces risk; **the real fix is to never build code from strings**:

- SQL: parameterised queries or a query builder, always. (`WHERE id = $1`, not string concatenation.)
- NoSQL: don't pass client objects as query filters (`{"$gt": ""}` matches everything in MongoDB).
- Shell: avoid shelling out; if you must, pass arguments as an array, never through a shell string.
- Templates and HTML: escape on output for the context (HTML, attribute, URL, JS).
- LDAP, XPath, regular expressions: same idea. Never build a regex from user input without escaping it, and watch out
  for patterns with catastrophic backtracking (lesson 31.3, Cloudflare 2019).

## Dangerous inputs

| Input | Risk | Defence |
|-------|------|---------|
| URLs the server will fetch | SSRF to internal services and cloud metadata | Allowlist schemes and hosts, block private IP ranges after DNS resolution, no redirects, egress proxy |
| Files | Malware, zip bombs, images that crash decoders | Size limits, type sniffing, re-encode, scan asynchronously, store outside the web root |
| XML | External entity attacks (XXE), billion-laughs expansion | Disable DTDs and external entities |
| Deeply nested JSON / GraphQL | Stack exhaustion, huge query cost | Depth and complexity limits |
| Unicode | Look-alike usernames, normalisation bugs | Normalise (NFC/NFKC) before comparing and storing |

## Validate outputs too

Return only fields the caller is allowed to see, using explicit response types. A `SELECT *` that later gains a
`password_hash` column shouldn't change the API.

## Try it

Write validation rules for `POST /orders`:
`{"items": [{"sku": "TEA-01", "qty": 2}], "couponCode": "SPRING", "shippingAddressId": "adr_..."}`.

<details>
<summary>Answer</summary>

- `items`: array of 1-50 objects; `sku` matches the SKU pattern and exists; `qty` integer 1-99.
- `couponCode`: optional string, `^[A-Z0-9]{3,20}$`; validity checked by business logic (and rate-limited to stop
  coupon guessing, API6).
- `shippingAddressId`: required, id format, **and it must belong to the caller** (an object-level check).
- No other fields allowed: price, discount and status are computed by the server, never accepted from the client.
- Body size limit (say 32 KB) at the gateway.
</details>

## Key takeaways

- Validate every request against an explicit schema before business logic: types, sizes, allowlists, rules.
- Reject unknown fields and keep per-operation input types to prevent mass assignment.
- Prevent injection by never building queries or commands from strings.
- Treat URLs, files, XML and deep nesting as dangerous, and limit what you return as carefully as what you accept.

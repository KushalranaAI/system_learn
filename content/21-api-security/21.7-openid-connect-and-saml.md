# OpenID Connect and SAML

A company buys your SaaS product and asks for one thing before signing: "Our 4,000 employees must sign in with our
company accounts, and when someone leaves, their access must stop." That's **single sign-on (SSO)**, and you'll meet
two standards for it: **OpenID Connect** for modern apps and **SAML** for the enterprise.

## OpenID Connect (OIDC)

OIDC (2014) is a thin identity layer on top of OAuth 2. Add the `openid` scope to an authorization code flow and the
token response contains an **ID token**: a JWT that says who the user is.

```json
{
  "iss": "https://accounts.example-idp.com",
  "sub": "248289761001",          ← stable user id at this provider
  "aud": "your-client-id",
  "email": "asha@corp.example", "email_verified": true,
  "name": "Asha Rao",
  "iat": 1761640000, "exp": 1761643600,
  "nonce": "n-0S6_WzA2Mj"
}
```

| Token | For | Sent to |
|-------|-----|---------|
| **ID token** | Telling the **client app** who signed in | Nobody else: the app validates and reads it |
| **Access token** | Calling **APIs** | Resource servers, in `Authorization: Bearer` |

Don't use an ID token to call APIs, and don't treat an access token as proof of identity. Identify users by
`iss` + `sub`, never by email (emails change and can be reassigned).

OIDC also standardises **discovery** (`/.well-known/openid-configuration` lists the endpoints and the JWKS key URL), a
`userinfo` endpoint, and logout. "Sign in with Google / Apple / Microsoft" are all OIDC.

## SAML 2.0

**Security Assertion Markup Language** (2005) solves the same SSO problem for browsers, with signed XML **assertions**:

```
user → your app (Service Provider) → redirect with an AuthnRequest → company IdP (Okta, Entra ID, ADFS…)
     ← IdP posts a signed XML assertion back to your app's ACS URL ← user signs in at the IdP
```

The assertion contains the user's id, attributes (email, groups) and validity conditions, signed by the IdP. Your app
verifies the signature with the IdP's certificate.

SAML is older and heavier, and XML signature validation has a long history of subtle bugs (use a well-maintained
library, never hand-roll it), but many large organisations require it.

## Comparing them

| | OIDC | SAML 2.0 |
|-|------|----------|
| Format | JSON / JWT | XML |
| Built on | OAuth 2 | Its own protocol |
| Mobile and SPA friendly | Yes | Awkward (browser POST redirects) |
| Also gives API access tokens | Yes (it's OAuth) | No; SSO only |
| Where you'll meet it | Consumer sign-in, modern IdPs, new B2B apps | Enterprise IdPs, government, education |

## Provisioning: the other half of SSO

SSO lets people sign in; it doesn't tell you when someone **leaves**. Enterprise customers expect **SCIM** (System for
Cross-domain Identity Management), a REST API they call to create, update and deactivate users and groups in your app
automatically. Combine short sessions with SCIM deprovisioning and the Friday-leaver problem from lesson 21.5 goes away.

## Try it

Add "Sign in with your company account" to a B2B project-management app. Customers use Okta, Microsoft Entra ID or
Google Workspace. What do you build?

<details>
<summary>Answer</summary>

- Per-customer SSO connections: OIDC where the IdP supports it (all three do), SAML for customers who insist.
- Route users to their company's IdP by email domain on the sign-in page.
- Link identities by `(issuer, subject)`, and map IdP groups to roles in your app.
- Your app then issues its **own** session or tokens; your APIs keep validating your tokens, not the IdP's.
- SCIM endpoints so the customer's IdP can deactivate leavers immediately; short session lifetimes as a backstop.
- Many teams buy this part (Auth0/Okta CIC, WorkOS, Keycloak, Cognito) rather than build it.
</details>

## Key takeaways

- OIDC adds identity (ID tokens) to OAuth 2; SAML does SSO with signed XML assertions.
- ID tokens are for the client app; access tokens are for APIs. Identify users by issuer + subject.
- Use maintained libraries; XML signatures and token validation are full of traps.
- SSO handles sign-in; SCIM provisioning handles joiners and leavers.

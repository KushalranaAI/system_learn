# Security in layers

No single control secures an API. TLS doesn't check permissions; OAuth doesn't stop SQL injection; a WAF doesn't know
that invoice 1002 belongs to someone else. Good API security is **defence in depth**: several independent layers, each
assuming the others might fail.

## One request through every layer

```
client
  │  TLS 1.3, HSTS, certificate                      ← confidentiality and integrity in transit (21.2)
  ▼
edge / CDN + WAF + DDoS protection                    ← volumetric attacks, known bad patterns, bot signals
  ▼
API gateway                                           ← authentication (keys, JWT validation), CORS (21.4),
  │                                                     rate limits and quotas (22.5), size limits, routing
  ▼
service
  │  input validation against the schema (21.3)
  │  authorization: scope + role + object ownership (21.5)
  │  business-flow limits (per account: sign-ups, OTPs, coupon tries)
  ▼
data layer                                            ← parameterised queries, tenant-scoped access, encryption at rest,
                                                        least-privilege database credentials
  ▼
logs, metrics, audit trail, alerts                    ← detect and investigate what got through
```

## What each layer is good (and bad) at

| Layer | Stops | Can't stop |
|-------|-------|------------|
| WAF | Known attack signatures, obvious injection, abusive IPs | Authorization bugs, business-logic abuse |
| Gateway | Missing or invalid credentials, floods, oversized requests | Whether this user may touch this object |
| Service | Logic and access bugs, if the checks are there | Volumetric attacks |
| Data layer | Injection, cross-tenant reads (with row-level security) | Leaks through legitimate queries |
| Monitoring | Nothing directly | Gives you the chance to notice and respond |

## The parts teams forget

- **Inventory (OWASP API9).** Keep a list of every API, version, environment and owner, generated from the gateway and
  OpenAPI specs. Old versions and staging hosts with real data are classic breach points.
- **Secrets.** No keys in code or images; use a secrets manager, rotate automatically, scan repos and CI logs.
- **Error hygiene.** No stack traces, SQL or internal hostnames in responses; return a request id and log the detail.
- **Audit logs.** Who did what to which object, when, from where, and append-only. Needed for investigations and often
  for compliance.
- **Third-party APIs (OWASP API10).** Validate their responses like user input, set timeouts, and don't follow their
  redirects blindly.
- **Testing.** Automated tests for authorization ("user B can't read user A's invoice") on every endpoint, plus DAST
  scans and periodic penetration tests.

## A launch checklist

| Area | Check |
|------|-------|
| Transport | HTTPS only, TLS 1.2+, HSTS, certificates auto-renewed |
| AuthN | Every endpoint authenticated unless explicitly public; short-lived tokens |
| AuthZ | Object- and function-level checks in one policy layer; tested with two users |
| Input | Schema validation, unknown fields rejected, size limits |
| Output | Explicit response types; no secrets or internal fields |
| Limits | Rate limits, quotas, page-size caps, timeouts, GraphQL cost limits |
| CORS | Exact-origin allowlist; no reflection with credentials |
| Inventory | Listed in the API catalogue; old versions have a retirement date |
| Logging | Request ids, audit events, alerts on auth failures and 5xx spikes |

## Try it

[Open the "public API with no limits" sandbox](#/sandbox?preset=api-public-gateway). One partner's runaway job floods
the API. Which layer should stop it, and what should the partner see?

<details>
<summary>Answer</summary>

The gateway's rate limiter, keyed by API key (or per IP as on the canvas), stops it before it reaches the servers.
The partner gets `429 Too Many Requests` with `Retry-After` and rate-limit headers, so a well-written client slows down,
and an alert tells you (and them) that a client is misbehaving. Everyone else keeps working.
</details>

## Key takeaways

- Security is layered: transport, edge, gateway, service, data and monitoring each catch different failures.
- Authorization lives in the service; no gateway or WAF can do it for you.
- Inventory, secrets, error hygiene, audit logs and authorization tests are as important as the visible controls.
- Use a launch checklist and automate as much of it as you can.

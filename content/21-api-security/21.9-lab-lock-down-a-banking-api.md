# Lab: lock down a banking API

A small bank's API passed its functional tests. Before launch, you review it and find five problems.

> **Interactive version:** [open the banking API lab](#/labs/api-secure-a-bank) to fix each finding as a checked step:
> quizzes, a token-lifetime simulation and a rate limiter on the canvas.

## Finding 1: `GET /accounts/:id` returns any account

<details>
<summary>Reference</summary>

BOLA (OWASP API1). Look up accounts scoped by the caller (`WHERE id = $1 AND owner_id = $2`) or through a shared policy
check, return `404` for other people's accounts, and add a two-user authorization test to CI for every endpoint.
</details>

## Finding 2: the app collects passwords; the export job uses an admin key

<details>
<summary>Reference</summary>

App: OAuth authorization code + PKCE in the system browser. Export job: client credentials with a narrow scope
(`statements:read`), ideally mTLS-bound, rotated automatically.
</details>

## Finding 3: 24-hour JWTs

<details>
<summary>Reference</summary>

Access tokens of 10-15 minutes plus rotating refresh tokens; revoke the refresh token family when a phone is reported
stolen. For payments, also check a denylist (or introspect) so revocation is near-instant.
</details>

## Finding 4: CORS reflects any origin with credentials

<details>
<summary>Reference</summary>

Allow exactly `https://app.bank.example` (and the admin origin) with credentials, send `Vary: Origin`, and reject other
origins. Better: serve the API same-origin under `/api`.
</details>

## Finding 5: credential stuffing on sign-in

<details>
<summary>Reference</summary>

A per-IP limit at the edge (around 100 req/s so shared office and carrier IPs aren't hurt), plus per-account limits
and exponential lockout delays, bot detection or CAPTCHA after failures, breached-password checks, and alerts on
spikes in failed logins. Offer passkeys to remove passwords altogether.
</details>

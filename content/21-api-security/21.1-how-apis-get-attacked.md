# How APIs get attacked

Many of the largest data leaks of the last decade weren't clever exploits. Someone noticed that an API returned a
record for whatever id they put in the URL, and wrote a loop. Every request was authenticated and well formed; the API
simply never asked *"is this caller allowed to see this object?"*. APIs are attractive targets because they expose
data and actions directly, in a machine-friendly way, often to anyone on the internet.

## The OWASP API Security Top 10 (2023)

The Open Worldwide Application Security Project keeps a list of the most common, most damaging API risks. The 2023
edition:

| # | Risk | What it looks like |
|---|------|--------------------|
| API1 | **Broken Object Level Authorization (BOLA)** | `GET /accounts/1002` works for a user who owns only 1001 |
| API2 | **Broken Authentication** | Weak password reset, tokens that never expire, no limit on login attempts, JWTs accepted unsigned |
| API3 | **Broken Object Property Level Authorization** | The response includes `passwordHash` or `isAdmin`; or a client can *set* `role: "admin"` in a PATCH (mass assignment) |
| API4 | **Unrestricted Resource Consumption** | No rate limits, unbounded page sizes, 10 GB uploads, a GraphQL query that nests 50 levels, an SMS endpoint that costs you money per call |
| API5 | **Broken Function Level Authorization** | A regular user can call `DELETE /admin/users/7` because the route only checks "signed in" |
| API6 | **Unrestricted Access to Sensitive Business Flows** | Bots buying all the concert tickets, mass account creation, coupon abuse: each request is legal, the volume isn't |
| API7 | **Server-Side Request Forgery (SSRF)** | `POST /import {"url": "http://169.254.169.254/latest/meta-data/"}` makes your server fetch cloud credentials |
| API8 | **Security Misconfiguration** | Debug endpoints in production, verbose stack traces, permissive CORS, missing TLS, default credentials |
| API9 | **Improper Inventory Management** | A forgotten `/v1` or staging API without the fixes `/v2` got |
| API10 | **Unsafe Consumption of APIs** | Trusting data from a third-party API without validating it, or following its redirects blindly |

Compared with 2019, injection and "insufficient logging and monitoring" dropped off the list as separate entries (they
still matter; lesson 21.3 covers injection), and business-flow abuse, SSRF and unsafe consumption of third-party APIs
were added.

## Why BOLA is number one

Authorization is easy to forget because it's **per object, per request**, scattered across hundreds of handlers.
Authentication happens once in middleware and feels like "security done".

```python
# Vulnerable
@app.get("/invoices/{invoice_id}")
def get_invoice(invoice_id, user=Depends(current_user)):
    return db.invoices.get(invoice_id)                     # any signed-in user, any invoice

# Fixed: scope the lookup by the caller
@app.get("/invoices/{invoice_id}")
def get_invoice(invoice_id, user=Depends(current_user)):
    inv = db.invoices.get(invoice_id, org_id=user.org_id)   # 404 if it isn't theirs
    if inv is None: raise NotFound()
    return inv
```

Defences that scale: scope **every** query by tenant or owner in a shared data-access layer; use a central policy
check (`can(user, "read", invoice)`); test with two users trying to read each other's data, in CI.

## Threat modelling an endpoint

For each endpoint, ask the **STRIDE** questions:

| Threat | Question | Typical control |
|--------|----------|-----------------|
| **S**poofing | Can someone pretend to be another caller? | Strong authentication, short-lived tokens |
| **T**ampering | Can they change data in transit or fields they shouldn't? | TLS, input validation, allowlisted writable fields |
| **R**epudiation | Can they deny doing it? | Audit logs with who, what, when |
| **I**nformation disclosure | Can they read what they shouldn't? | Object and property authorization, minimal responses |
| **D**enial of service | Can they exhaust it? | Rate limits, size limits, timeouts, cost limits |
| **E**levation of privilege | Can they gain powers? | Function-level checks, least-privilege scopes |

## Try it

Threat-model `POST /users/:id/avatar`, which accepts an image URL and downloads it as the user's avatar.

<details>
<summary>Answer</summary>

- **BOLA:** can user A change user B's avatar? Ignore the path id, or check it equals the caller.
- **SSRF (API7):** the server fetches a URL the attacker chose. Allow only `https`, resolve the host and block private,
  loopback and link-local ranges (including cloud metadata at 169.254.169.254), don't follow redirects to them, and
  fetch from an isolated egress proxy. Better still, let clients upload the bytes directly.
- **Resource consumption (API4):** cap the download size and time, and rate-limit the endpoint.
- **Content:** check the bytes really are an image (magic numbers), re-encode it, and strip metadata.
</details>

## Key takeaways

- Most API breaches are authorization failures on well-formed requests, not exotic exploits.
- Know the OWASP API Top 10 (2023); BOLA is number one.
- Check access to every object and every property on every request, in one shared place.
- Threat-model each endpoint with STRIDE; limits and inventory are security controls too.

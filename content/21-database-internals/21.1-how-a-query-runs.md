# How a query runs

SQL says *what* you want, not *how* to get it. Between the text you send and the rows you get back, the database
builds and runs a program. Most "the database is slow" problems are this program being chosen badly. Examples here
use PostgreSQL; MySQL and others follow the same stages.

## The pipeline

```
SQL text
  │ 1. parser        → syntax tree             ("is this valid SQL?")
  │ 2. analyzer      → resolved query tree     (tables, columns, types exist? permissions?)
  │ 3. rewriter      → expand views, rules
  │ 4. planner       → cheapest plan it can find, using statistics + cost model
  │ 5. executor      → pulls rows through the plan tree
rows
```

## The planner's choices

For `SELECT ... FROM orders o JOIN customers c ON c.id = o.customer_id WHERE o.status = 'pending'` the planner must
pick:

- **Access path** per table: sequential scan, index scan, index-only scan, bitmap scan.
- **Join order**: with n tables there are many orders; beyond a threshold (Postgres: 12 tables, `geqo_threshold`) it
  switches to a heuristic search.
- **Join algorithm**:

| Algorithm | How | Good when |
|-----------|-----|-----------|
| Nested loop | For each outer row, look up matches (ideally via index) | Outer side is small |
| Hash join | Build a hash table on the smaller input, probe with the other | Large inputs, equality joins |
| Merge join | Walk two sorted inputs in step | Both already sorted (index) or big sorts are cheap |

## The cost model

Each plan gets a cost in abstract units. Postgres defaults:

| Parameter | Default | Meaning |
|-----------|---------|---------|
| `seq_page_cost` | 1.0 | Read a page sequentially |
| `random_page_cost` | 4.0 | Read a page at random (often lowered to ~1.1 on SSDs) |
| `cpu_tuple_cost` | 0.01 | Process one row |
| `cpu_operator_cost` | 0.0025 | Evaluate one operator |

Worked example: `orders` has 10M rows in 125,000 pages. A sequential scan costs about
`125,000 × 1.0 + 10,000,000 × 0.01 = 225,000`. An index scan fetching 0.1% of rows (10,000 rows, mostly on different
pages) costs about `10,000 × 4.0 + small = ~40,000`: the index wins. Fetching 20% (2M rows) by index would cost
millions; the sequential scan wins. **Which one is right depends entirely on the row estimate.**

## Statistics drive the estimates

`ANALYZE` samples the table (Postgres reads 300 × `default_statistics_target` = 30,000 rows by default) and stores per
column:

- fraction of NULLs, number of distinct values,
- **most common values** with their frequencies,
- a **histogram** of the rest,
- correlation between physical order and value order.

For `status = 'pending'` the planner looks up 'pending' in the most-common-values list: say 0.5% → 50,000 rows. For
two conditions it multiplies selectivities, assuming the columns are **independent**. When they aren't (city and
postcode, status and created_at), estimates can be off by orders of magnitude; extended statistics
(`CREATE STATISTICS`) help.

Estimates go wrong when: stats are stale (bulk load since the last ANALYZE), columns are correlated, a function wraps
the column (`WHERE lower(email) = ...` has no stats and no usable index unless you index the expression), or values
compare across mismatched types.

## The executor: pull-based iterators

Each plan node implements "give me the next row" (the **Volcano** model). The top node pulls from its children,
which pull from theirs. `LIMIT 10` above a sorted index scan stops after 10 rows; above a hash join it may first build
the whole hash table. Analytical engines process batches of values instead of single rows (lesson 22.3).

## Reading EXPLAIN

```sql
EXPLAIN ANALYZE SELECT * FROM users WHERE lower(email) = 'ana@example.com';
```
```
Seq Scan on users  (cost=0.00..48233.00 rows=5000 width=96)
                   (actual time=0.031..612.882 rows=1 loops=1)
  Filter: (lower(email) = 'ana@example.com'::text)
  Rows Removed by Filter: 999999
Planning Time: 0.1 ms
Execution Time: 612.9 ms
```

Read each node as **estimate vs actual**: `rows=5000` estimated (a default guess for an unknown function) vs `rows=1`
actual, and 999,999 rows thrown away. The index on `email` can't be used because of `lower()`. Fix:
`CREATE INDEX ON users (lower(email));` → an index scan in well under a millisecond.

What to look for, in order: the slowest node (`actual time`), big estimate/actual gaps, `loops` multiplying a cheap
inner node, `Rows Removed by Filter`, sorts or hashes spilling to disk (`external merge`, `Batches: 16`).

## Plan caching

Planning costs time (milliseconds for complex joins), so prepared statements can reuse plans. Postgres plans the first
five executions with the actual parameter values (**custom plans**), then switches to a **generic plan** if it isn't
estimated to be worse. A generic plan for `WHERE tenant_id = $1` can be terrible for your one giant tenant. Symptoms:
a query that's fast in `psql` but slow from the app. `plan_cache_mode = force_custom_plan` is the escape hatch.

## Try it

This query got slow after last night's import. Spot the mistake in the plan.

```
Nested Loop  (cost=0.85..52.31 rows=3 width=40) (actual time=0.05..9412.7 rows=412000 loops=1)
  -> Index Scan using orders_status_idx on orders o  (cost=0.43..26.10 rows=3 width=16)
                                    (actual time=0.03..2210.5 rows=412000 loops=1)
        Index Cond: (status = 'pending')
  -> Index Scan using customers_pkey on customers c  (cost=0.42..8.44 rows=1 width=32)
                                    (actual time=0.015..0.016 rows=1 loops=412000)
        Index Cond: (id = o.customer_id)
```

<details>
<summary>Reference</summary>

The planner estimated **3** pending orders; there were **412,000**. The import added hundreds of thousands of
'pending' rows after the last `ANALYZE`, so the statistics still said 'pending' was rare. With 3 rows a nested loop
(3 index lookups) is perfect; with 412,000 it does 412,000 random index lookups (`loops=412000`), and the index scan
on `orders` itself reads rows scattered all over the table.

Fix: `ANALYZE orders;` (and run ANALYZE as part of bulk imports). With correct estimates the planner picks a hash join
over a scan of `customers`, or a bitmap scan on `orders`. If the 'pending' share changes constantly, consider raising
the statistics target on `status` or a partial index for the rare statuses.
</details>

## Key takeaways

- Parse → analyze → rewrite → plan → execute; the planner picks access paths, join order and join algorithms.
- Plans are chosen by estimated cost, and estimates come from statistics; bad stats, bad plans.
- In EXPLAIN ANALYZE, compare estimated and actual rows node by node, and watch `loops`.
- Generic cached plans can be wrong for skewed parameters.

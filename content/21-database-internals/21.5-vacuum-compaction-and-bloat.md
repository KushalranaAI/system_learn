# Vacuum, compaction and bloat

Databases that never overwrite in place (Postgres's MVCC, LSM engines) accumulate garbage: old row versions, deleted
rows, tombstones. Something has to clean it up in the background. When that something falls behind, tables grow
without bound, queries slow down, and in Postgres's worst case the database stops accepting writes.

## Dead tuples

Every `UPDATE` in Postgres leaves the old version behind; every `DELETE` leaves the row marked dead (lesson 21.2).
Once no running transaction could still see a dead version, it's garbage.

```
orders: 10M live rows, 1,000 updates/second
→ 86.4M dead tuples per day if nothing cleans up
```

**VACUUM** scans the table, finds dead tuples older than the oldest snapshot still in use (the **xmin horizon**),
removes index entries pointing to them, and marks their space reusable. It doesn't return space to the OS (except
empty pages at the end of the file); new rows fill the holes.

**VACUUM FULL** (or `CLUSTER`) rewrites the table compactly, but holds an ACCESS EXCLUSIVE lock for the whole rewrite
(lesson 21.3). For big production tables use `pg_repack`, which rebuilds online.

## Autovacuum

The autovacuum launcher vacuums a table when its dead tuples exceed:

```
autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × live rows
            50              +            0.2               × reltuples
```

For a 1,000-row table that's 250 dead tuples. For a **500M-row table it's 100M dead tuples** before anything happens,
and then a single worker (throttled by `autovacuum_vacuum_cost_limit` so it doesn't hog I/O) has to grind through
it. Big, busy tables need per-table settings:

```sql
ALTER TABLE events SET (autovacuum_vacuum_scale_factor = 0.01,
                        autovacuum_vacuum_cost_limit = 2000);
```

## Why vacuum can't clean up

VACUUM can only remove versions that **no snapshot can still see**. Anything that holds an old snapshot pins the
horizon for the **whole database**:

| Culprit | How to find it |
|---------|----------------|
| Long-running query or transaction | `pg_stat_activity` ordered by `xact_start` |
| Session `idle in transaction` (app opened a transaction and forgot) | `state = 'idle in transaction'` |
| Abandoned replication slot (lesson 21.4) | `pg_replication_slots`, `xmin` / `catalog_xmin` |
| Replica with `hot_standby_feedback = on` running long queries | `backend_xmin` in `pg_stat_replication` |
| Forgotten prepared transaction | `pg_prepared_xacts` |

A six-hour analytics query on a busy OLTP database means six hours of dead tuples that vacuum runs over and can't
remove, so the table and its indexes keep growing. That growth is **bloat**: more pages to scan, worse cache hit
rates, bigger backups.

## Transaction ID wraparound

Postgres XIDs are **32-bit**. Visibility compares XIDs modulo 2³², so each transaction sees about **2.1 billion** XIDs
as "the past" and 2.1 billion as "the future". A row created 2.2 billion transactions ago would suddenly look like it
was created in the future, and vanish.

To prevent that, VACUUM **freezes** old tuples: marks them as "visible to everyone, forever", so their XID no longer
matters. Postgres tracks the oldest unfrozen XID per table (`relfrozenxid`) and:

1. When a table's age passes `autovacuum_freeze_max_age` (default **200 million**), it forces an anti-wraparound
   vacuum, even if autovacuum is otherwise off.
2. As the age approaches 2 billion, it logs warnings.
3. When only a few million XIDs remain, it **refuses to assign new XIDs**: no writes, until someone runs VACUUM,
   which on a huge table can take hours.

Real incidents:

- **Sentry, July 2015**: the primary hit wraparound protection and stopped accepting writes for most of a US working
  day. Autovacuum hadn't kept up with a very write-heavy workload; after hours of waiting for vacuums, the team
  truncated the one remaining huge, non-critical table to recover.
- **Mailchimp's Mandrill, February 2019**: a write spike on one of five Postgres shards pushed it into wraparound
  protection. The shard went read-only, and the outage lasted over a day while vacuum ran. Engineers had noticed XID
  age reaching about half the limit months earlier but only filed a ticket to improve monitoring.

Monitor it:

```sql
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
-- alert well before 1 billion; investigate anything above ~500 million
```

## The LSM version: compaction

LSM engines (lesson 19.8) have the same problem in a different shape. Overwrites and deletes are new entries; a
delete is a **tombstone**. Old versions and tombstones are dropped only when **compaction** merges the files that
contain them.

- If compaction falls behind ingest, the number of SSTables grows, reads check more files, and disk fills with
  superseded data.
- Cassandra keeps tombstones for `gc_grace_seconds` (default 10 days) so replicas that missed the delete can learn of
  it via repair; drop them sooner and deleted data can come back. A queue-like table with heavy deletes can make reads
  scan thousands of tombstones.
- Fixes: compaction strategy matched to the workload (time-window for time series, so whole files expire), TTLs
  instead of deletes, and enough I/O headroom.

## Try it

A 300 GB `events` table keeps growing even though the number of live rows is roughly flat (old events are deleted
daily). Diagnose it.

<details>
<summary>Reference</summary>

Live rows are flat but size grows → dead tuples aren't being reclaimed. Check, in order:

1. `pg_stat_user_tables`: `n_dead_tup`, `last_autovacuum`. If autovacuum hasn't run recently, the 20% scale factor on a
   big table is too lazy or it's being throttled/cancelled. Lower `autovacuum_vacuum_scale_factor` for this table and
   raise its cost limit.
2. If autovacuum *is* running but `n_dead_tup` stays high: something holds the xmin horizon. Look for old transactions
   and `idle in transaction` sessions in `pg_stat_activity`, stale replication slots, standbys with
   `hot_standby_feedback`, prepared transactions. Kill or fix them; set `idle_in_transaction_session_timeout`.
3. Check `age(relfrozenxid)` too, so this isn't heading toward wraparound.
4. Once vacuum keeps up, the size stops growing but doesn't shrink; reclaim it with `pg_repack`.
5. Long term: partition by day and **drop old partitions** instead of `DELETE` (lesson 9.2); dropping a partition
   creates no dead tuples at all.
</details>

## Key takeaways

- MVCC and LSM engines leave garbage behind; VACUUM and compaction clean it up in the background.
- Autovacuum's default 20% threshold is too lazy for big tables; tune per table.
- Any old snapshot (long transaction, idle-in-transaction session, stale slot) blocks cleanup database-wide.
- 32-bit XIDs must be frozen before 2 billion transactions; ignore that and Postgres stops accepting writes.
- Monitor dead tuples, horizon holders and `age(datfrozenxid)`; partition and drop instead of mass deletes.

# Inside distributed SQL

Google Spanner, CockroachDB, YugabyteDB and TiDB give you SQL with transactions across many machines and regions,
without you sharding by hand. Underneath they're built from pieces you've already met: key-range partitioning
(lesson 14.1), Raft (lesson 19.7), MVCC (lesson 21.2) and two-phase commit (lesson 16.2). This lesson assembles them.

## Rows become keys, keys become ranges

Every table row and index entry is encoded as a key in one big sorted key space:

```
/accounts/primary/1001   → {owner: "ana", balance: 500}
/accounts/primary/1002   → {owner: "bo",  balance: 80}
/accounts/by_owner/"ana"/1001 → ∅           (secondary index entry)
```

The key space is cut into contiguous **ranges** (CockroachDB) or **splits/tablets** (Spanner, Yugabyte). A range splits
when it grows too big (CockroachDB's default maximum is 512 MiB) or too hot, and ranges move between nodes to balance
load. A small set of **meta ranges** maps key spans to their current location, and every node caches it, so a
gateway node can find the right range in one hop.

## Raft per range

Each range is a separate Raft group, typically **3 or 5 replicas** on different nodes or zones. A large cluster runs
hundreds of thousands of independent Raft groups.

- One replica holds the **lease** (CockroachDB: leaseholder, usually also the Raft leader). It serves consistent reads
  locally without a Raft round, and proposes writes.
- A write is committed when a majority of the range's replicas have it in their Raft logs.
- Losing a node loses one replica of many ranges; each affected range elects a new leader independently, and the
  system re-replicates the missing copies elsewhere.

## Time: ordering transactions without a global clock

MVCC needs timestamps, and timestamps from different machines' clocks disagree (lesson 12.5). Two approaches:

**Spanner's TrueTime.** GPS receivers and atomic clocks in each data centre let `TT.now()` return an interval
`[earliest, latest]` guaranteed to contain true time. The 2012 paper reports the uncertainty ε sawtoothing between
about 1 and 7 ms. To commit, a transaction picks timestamp `s = TT.now().latest`, then performs **commit wait**: it
doesn't report success until `TT.now().earliest > s`. By then `s` is certainly in the past everywhere, so any
transaction that starts afterwards anywhere gets a bigger timestamp. That gives **external consistency**
(linearizability) at the cost of waiting out the uncertainty, usually overlapped with replication.

**CockroachDB's hybrid logical clocks (HLC).** Ordinary NTP clocks plus a logical counter: every message carries a
timestamp, and a node receiving a later timestamp bumps its own clock forward. Clocks are assumed to be within a
**maximum offset** (default 500 ms); a node that detects it's drifted too far shuts itself down. When a read meets a
value whose timestamp is above the read's timestamp but within the offset window (the **uncertainty interval**), it
can't tell whether that write happened before it, so it moves its own timestamp up and retries the read. You get
serializability, with occasional restarts instead of commit waits.

## A write, end to end (CockroachDB)

Transfer 100 from account 1001 to account 7,500,000, which live in different ranges:

```
1. Client → any node (the gateway). The gateway starts txn T at HLC timestamp 1700.000.
2. UPDATE 1001: gateway looks up the range for /accounts/primary/1001 → range R1, leaseholder n2.
   n2 writes an INTENT (a provisional MVCC value tagged with T) through R1's Raft group.
   T's TRANSACTION RECORD lives in R1 too (the range of the first write).
3. UPDATE 7500000 → range R9, leaseholder n5. Intent written through R9's Raft group.
4. COMMIT: "parallel commits": the record is marked STAGING with the list of intents,
   and the final intent writes are replicated in parallel with it. Once all are durable,
   T is committed; the client gets success after roughly one consensus round.
5. Asynchronously, intents are resolved into ordinary committed values,
   and the record becomes COMMITTED.
```

Anyone who meets an intent checks T's transaction record: committed → treat as a value; aborted → ignore; pending →
wait or push the transaction (lower priority may be aborted). This is two-phase commit where the coordinator's
decision is itself replicated by Raft, so a crashed coordinator can't leave participants stuck forever, unlike
classic 2PC.

Spanner does the same shape: each split is a Paxos group; a multi-split transaction uses 2PC with one group as
coordinator, takes locks at the leaders, and applies commit wait before releasing them.

## What it costs

| Operation | Cost |
|-----------|------|
| Single-row read at the leaseholder | Local; no consensus round |
| Single-range write | One Raft round (majority of replicas) |
| Multi-range transaction | Writes to several Raft groups, coordinated; contention means retries |
| Replicas across regions | Every write waits for a cross-region majority: tens of ms or more |

So schema design still matters: keep data that's written together in the same range (interleaving, hash-sharded or
locality-aware primary keys), pin a region's rows to replicas in that region (geo-partitioning), avoid sequential keys
that make one range hot, and make application retries routine (serialization errors are expected).

## Try it

Follow `UPDATE accounts SET balance = balance - 100 WHERE id = 1001` plus `... + 100 WHERE id = 7500000` through
CockroachDB (or Spanner): which machines are involved, when is it durable, and what happens if the gateway node
crashes right after the client sends COMMIT?

The gateway finds each key's range via cached meta ranges. Each leaseholder writes an intent through its range's Raft
group (a majority of that range's replicas must append it). The transaction record (in the first range) moves to
STAGING with the set of intents; when every intent and the record are replicated, the transaction is committed, and
the client is told. Intents are cleaned up asynchronously.

If the gateway crashes after COMMIT: the intents and the staging record are already in Raft logs. The next transaction
that hits an intent looks up the record, sees STAGING, checks whether all listed intents were written, and finishes
the commit (or aborts it if one is missing). No participant blocks forever. The client didn't get an answer, so it must
treat the outcome as unknown and retry idempotently or check (lesson 12.4).

In Spanner: the coordinator group's leader runs 2PC across the two splits' Paxos groups, picks a commit timestamp, waits
out TrueTime uncertainty, then releases locks; coordinator state is in Paxos, so leader failure is survived the same
way.
</details>

## Key takeaways

- Rows and index entries become keys; keys are split into ranges that each run their own Raft (or Paxos) group.
- Leaseholders serve local reads; writes need a majority of the range's replicas.
- Spanner orders transactions with TrueTime and commit wait; CockroachDB uses hybrid clocks, a max offset and
  uncertainty restarts.
- Distributed transactions are 2PC with replicated coordinator state: intents plus a transaction record.
- Latency follows data placement; design keys and locality so most transactions touch one range and one region.

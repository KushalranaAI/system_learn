# Guardrails

Guardrails are checks around a model call, the same way input validation and output encoding sit around a web
handler. The model is a component you can't fully control, so you **check what goes in and what comes out** with
code you can.

```
user input ─► [input checks] ─► context builder ─► LLM ─► [output checks] ─► user / tool
                 │                                           │
                 └─ block, redact, reroute                   └─ block, fix, retry, escalate
```

## Input checks

| Check | How | Typical cost |
|-------|-----|--------------|
| Size and rate limits | Code: max characters, tokens, requests per user | ~0 ms |
| PII detection and redaction | Regex + NER model (e.g. Microsoft Presidio) | 5-30 ms |
| Topic / scope | Small classifier: "is this about our product?" | 10-50 ms |
| Prompt-injection / jailbreak detection | Classifier model | 10-50 ms |
| Moderation (hate, self-harm, ...) | Provider moderation endpoint or classifier | 20-100 ms |

Injection classifiers help but are **not a security boundary**; attackers rephrase until they pass ([lesson 29.4](#/lesson/29.4)).

## PII redaction

Replace sensitive values with placeholders before the text reaches the model or logs, and restore them only where
needed:

```
in:   "Card 4111 1111 1111 1111 was charged twice, email me at ana@example.com"
sent: "Card [CARD_1] was charged twice, email me at [EMAIL_1]"
vault: {CARD_1: "4111...", EMAIL_1: "ana@example.com"}  (per request, short TTL)
out:  model writes "We'll email [EMAIL_1]" → restored before display
```

The model rarely needs the real card number. It needs to know there is one. Tools that need real values get them
from the vault by placeholder, server-side.

## Output checks

| Check | Why |
|-------|-----|
| **Structured validation** | Output must match a JSON Schema; business rules in code (amount ≤ order total) |
| **Groundedness** | Every claim supported by retrieved docs; citations point to real doc ids |
| **Policy filters** | No legal or medical advice, no promises of discounts, no competitor talk |
| **PII leak check** | Output must not contain other customers' data, keys, the system prompt |
| **Safe rendering** | Escape HTML/Markdown; block images and links to unknown domains (exfiltration path) |

What to do on failure, in order of preference: **fix in code** (strip a link), **retry** with the error added
("Your answer cited doc a99 which doesn't exist"), **fallback** to a safe template ("I can't help with that, here is
a human"), and always **log** for review.

## Without doubling latency

Running six checks one after another can add 300+ ms. Patterns that keep it small:

1. **Run input checks in parallel with each other and with retrieval.** The slowest check, not the sum, sets the
   cost:
   ```
   t=0   ├─ injection classifier (40 ms)
         ├─ PII redaction (20 ms)       ─► all done at ~40 ms
         ├─ topic classifier (30 ms)
         └─ retrieval (80 ms)           ─► LLM starts at ~80 ms
   ```
2. **Optimistic start:** begin the LLM call immediately and cancel it if an input check fails. You pay tokens for
   the few blocked requests, but users pay no latency.
3. **Small, specialised models** (or code) for checks, not a second frontier-model call.
4. **Streaming output checks:** check the stream in chunks (e.g. every sentence); stop and replace if a chunk fails.
   Block-level checks (full JSON validation) run on the final output only.
5. **Tier by risk:** a FAQ answer gets cheap checks; a tool call that moves money gets the full set plus code rules.
6. **Cache** check results for identical inputs (common in FAQ traffic).

## Where guardrails live

Put them in a **shared layer** (the model gateway, [lesson 26.4](#/lesson/26.4), or a library every service uses), not copied into
each feature. Version their thresholds like prompts and include them in evals ([lesson 29.1](#/lesson/29.1)): a guardrail that
blocks 5% of legitimate questions is a bug too. Track **false-positive rate** as well as catches.

## Try it

A support chat streams answers with p50 time-to-first-token of 600 ms. You must add PII redaction, an injection
classifier, a topic check, groundedness checking and a policy filter. Arrange them so TTFT grows by less than 100 ms.

<details>
<summary>Reference</summary>

- **Input side, all in parallel with retrieval (~80 ms):** PII redaction (code + small NER), injection classifier,
  topic classifier. Start the LLM call when redaction is done (it changes the prompt); let the two classifiers
  finish while the model is in prefill and **cancel** the stream if either fails. Added TTFT ≈ redaction time, ~20-40 ms.
- **Output side, streaming:** policy filter and PII leak check per sentence on the stream (fast classifier/regex,
  a sentence of delay at most).
- **Groundedness:** needs the whole answer; run it on the final text for **sampled** traffic and on answers that
  trigger actions, or show the answer with citations and run the check async, flagging failures for review.
- **Tool calls:** schema + business rules in code before execution, always.
</details>

# Observability for LLM apps

Classic observability answers "is it up, is it fast, where are the errors?". LLM apps add two questions it can't
answer: **what did the model see and say?** and **was the answer any good?** An AI feature can return HTTP 200 in
1.2 s and still be wrong for a week. Nothing in your existing dashboards will notice.

## Traces of prompts and tool calls

The unit of debugging is the **trace of one request**: every model call, retrieval and tool call, nested, with
inputs, outputs, tokens and timing.

```
POST /chat  trace_id=7f3a  user=8812  2,940 ms
├─ retrieval help-articles       85 ms   query="refund damaged parcel"  top5=[a17,a03,a88,a12,a40]
├─ invoke_agent support-agent  2,790 ms
│  ├─ chat medium-2026-09        640 ms  in=4,210 out=38   finish=tool_calls
│  ├─ execute_tool get_order     120 ms  args={id:A123} → status=delivered
│  ├─ chat medium-2026-09        710 ms  in=4,390 out=41   finish=tool_calls
│  ├─ execute_tool refund_order  310 ms  → R9
│  └─ chat medium-2026-09      1,010 ms  in=4,520 out=96   finish=stop  ttft=380 ms
└─ guardrail output_check         40 ms  pass
```

With this, "why did it refund the wrong amount?" takes minutes: open the trace, see what the model saw.

## OpenTelemetry GenAI conventions

Use OpenTelemetry so AI spans join the traces you already have (API gateway → service → database). The GenAI
semantic conventions (still marked *Development*, now maintained in their own repository) standardise names:

| Attribute / span | Meaning |
|------------------|---------|
| Span name `chat {model}`, `embeddings {model}` | `{gen_ai.operation.name} {gen_ai.request.model}` |
| `invoke_agent {name}`, `execute_tool {name}` | Agent and tool spans |
| `gen_ai.provider.name` | `openai`, `anthropic`, `aws.bedrock`, ... |
| `gen_ai.request.model`, `gen_ai.response.model` | Asked-for model vs the one that answered |
| `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens` | Token counts (input includes cached tokens) |
| `gen_ai.response.finish_reasons` | `stop`, `length`, `tool_calls`, `content_filter` |
| `gen_ai.input.messages`, `gen_ai.output.messages` | Prompt and response content: **opt-in** |

Content capture is opt-in on purpose: prompts contain personal data. Common setup: metadata on 100% of spans,
full content on a sample (or for internal users), redacted ([lesson 29.3](#/lesson/29.3)), stored with a short retention and
restricted access ([lesson 29.7](#/lesson/29.7)). MCP's newest revision also standardises passing `traceparent` in request metadata,
so traces continue into MCP servers.

## Token accounting

Tokens are your variable cost, so meter them like a utility:

```
per call:  tenant, user, feature, model, prompt_version, input_tokens, cached_tokens, output_tokens, $ cost
rollups:   $ per feature per day, $ per tenant, tokens per task (p50/p95), cache hit ratio
```

- Emit token counts as **metrics** (`gen_ai.client.token.usage` histogram) for dashboards and as span attributes
  for drill-down.
- Attribute cost to **features and tenants**, so you can see that "summarise thread" is 40% of the bill.
- Alert on **tokens per task** (an agent that started looping) and **$ per hour** (abuse or a bug) as well as
  errors. OWASP calls runaway usage *LLM10: Unbounded Consumption*.

## Quality signals

| Signal | Source | Cost |
|--------|--------|------|
| Thumbs up/down, copy, regenerate | UI events joined by trace id | Free, sparse |
| Escalations, "talk to human", re-asks | App events | Free |
| Ticket reopened, refund reversed | Downstream systems, days later | Free, delayed |
| Async LLM judges on a sample | Evals pipeline ([lesson 29.1](#/lesson/29.1)) | Some tokens |
| Retrieval scores, empty retrievals, `length` finishes | Spans | Free |
| Human review of a sample | Review queue | Expensive, best |

Put them on the same dashboard as latency and cost, sliced by **prompt version, model version, intent and
language**. Most "the bot got worse" problems are a change in one slice.

## What changes things silently

Keep a **change log** joined to your metrics: prompt edits, model version changes (including the provider updating a
model alias), retrieval config, knowledge base re-indexes, tool schema changes, guardrail thresholds. Version every
prompt (`prompt_version` on every span) like code.

## Try it

Users say answers got worse "since last week". Latency, errors and cost look normal. How do you find the cause?

<details>
<summary>Reference</summary>

1. **Confirm with data:** thumbs-down rate, escalations and judge scores by day. Find the day it changed.
2. **Slice:** by prompt_version, gen_ai.response.model, intent, language, retrieval source. Say it's concentrated in
   billing questions.
3. **Check the change log for that day:** e.g. the help centre was re-indexed with a new chunker, or a model alias
   moved to a new snapshot.
4. **Open traces** of bad billing answers: retrieval returns `a88` (an old pricing page) instead of `a17`; the model
   faithfully answers from the wrong doc. Groundedness is fine, retrieval recall dropped.
5. **Fix and prevent:** roll back the index or fix the chunking; add these cases to the golden set; add retrieval
   recall to the CI gate and an alert on the daily judge score.
</details>

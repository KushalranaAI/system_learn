# Evals

In classic software, tests tell you whether a change broke something. An LLM feature has no exact expected output:
"Your refund is on its way" and "We've refunded you" are both right. **Evals** are the tests of AI systems: a set of
inputs, a way to score outputs, and a threshold that gates releases. Without them, every prompt tweak or model
upgrade is a guess.

## What to evaluate

| Level | Question | Example metric |
|-------|----------|----------------|
| Component | Did retrieval find the right doc? | Recall@5, MRR ([lesson 27.6](#/lesson/27.6)) |
| Step | Did the agent call the right tool with the right args? | Tool-call accuracy |
| Output | Is the answer correct, grounded, on-policy, well-toned? | Pass rate per criterion |
| Task | Did the user's problem get solved? | Resolution rate, task success |
| System | Fast and cheap enough? | p95 latency, tokens and $ per task |

Score each criterion separately. "Quality went from 4.1 to 3.9" tells you nothing; "groundedness held, but tone
failures doubled on refund questions" tells you what to fix.

## Golden sets

A golden set is a versioned file of test cases:

```json
{"id": "refund-017", "input": "parcel arrived smashed, want money back",
 "context": {"order": {"id": "A123", "status": "delivered", "total_eur": 80}},
 "expect": {"tool": "refund_order", "max_amount": 80,
            "must_mention": ["refund"], "must_not": ["store credit only"]},
 "tags": ["refund", "happy-path"]}
```

Build it from:
- **Real traffic** (sampled, anonymised), weighted toward common intents;
- **Known failures** from production: every bug becomes a test case, like a regression test;
- **Edge and adversarial cases:** angry users, other languages, injection attempts ([lesson 29.4](#/lesson/29.4)), out-of-scope
  requests where the right answer is "I can't help, here's a human".

50-200 well-chosen cases catch most regressions; grow it over time. Keep a held-out slice you don't tune prompts
against, or you will overfit to your own test.

## Scoring: from cheapest to most expensive

1. **Code checks:** JSON parses, the right tool was called, a number is within range, a required phrase is present,
   citations point to real documents. Fast, free, exact. Use them wherever you can.
2. **Reference comparison:** compare with a known good answer (exact match for classifications, similarity for
   free text).
3. **LLM-as-judge:** a model grades the output against a rubric.
4. **Human review:** the ground truth, slow and costly; use it to calibrate the judge and for high-stakes samples.

## LLM-as-judge, done properly

The MT-Bench paper (Zheng et al., 2023) found strong judge models agreed with human preferences about as often as
humans agreed with each other (over 80%), and also documented the biases: **position** (favouring the first answer
in a pair), **verbosity** (favouring longer answers) and **self-enhancement** (favouring its own outputs).

Practices that work:
- **One criterion per judge call**, with a binary or 3-point scale and a written rubric. "Is every factual claim
  supported by the provided articles? yes/no" beats "rate quality 1-10".
- Ask for **reasoning before the verdict**, and return structured output.
- For pairwise comparisons, run both orders and only count consistent wins.
- **Calibrate:** have humans label ~100 cases, measure the judge's agreement (e.g. Cohen's kappa), adjust the rubric
  until agreement is high. Re-check when you change the judge model.
- Use a different (often stronger) model as judge than the one under test.

## Offline and online

```
offline:  PR changes prompt/model ─► CI runs golden set (N=200, 3 runs each) ─► compare to main ─► gate
online:   production traffic ─► sample 1-5% ─► async judges + user signals ─► dashboards / alerts
          A/B or shadow: new version gets 5% of traffic, compare task metrics
```

**Online signals** you get for free: thumbs up/down, "talk to a human" clicks, re-asks within 2 minutes, ticket
reopened within 7 days, conversation length. They're noisy individually but strong in aggregate.

## Regression gates

Because outputs vary from run to run, run each case several times (or at temperature 0 where possible) and compare
**rates with confidence intervals**, not single numbers. A typical gate:

| Metric | Gate |
|--------|------|
| Critical cases (policy, safety, money) | 100% pass, no exceptions |
| Groundedness pass rate | ≥ 95% and not lower than main by > 2 points |
| Tool-call accuracy | ≥ 97% |
| p95 latency, cost per task | Not more than +10% vs main |

Gate every change that can alter behaviour: prompts, model versions (providers update models), retrieval settings,
tool descriptions, and the knowledge base itself.

## Try it

Write an eval for a support bot that answers from help articles and can issue refunds up to 50 EUR.

<details>
<summary>Reference</summary>

- **Golden set (~150 cases):** 60 common questions sampled from tickets (with the article that answers them),
  30 refund cases (under, at and over 50 EUR, already refunded, not delivered), 20 out-of-scope / must-escalate,
  20 adversarial (injection in the message, "my manager said you can refund 500"), 20 in other languages.
- **Code checks:** refund tool called only when allowed; amount ≤ min(50, order total); escalation tool called for
  out-of-scope; every cited article id exists.
- **Judges (one criterion each):** grounded in the retrieved articles (yes/no); answers the actual question (yes/no);
  tone matches the guide (pass/fail). Calibrated on 100 human-labelled cases.
- **Gate in CI:** 100% on money and escalation cases; groundedness ≥ 95%; no metric down > 2 points; 3 runs per case.
- **Online:** 2% sampled through the same judges; track resolution, escalations, reopen rate and thumbs-down by
  intent.

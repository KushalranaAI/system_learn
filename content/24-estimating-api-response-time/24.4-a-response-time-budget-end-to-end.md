# A response-time budget, end to end

"Search must feel instant" isn't a requirement anyone can build to. "Search results in under 300 ms at p95 for users
in India" is. A **response-time budget** splits that number across the parts of the path, so each team knows its
share and everyone can see where the time went when the target is missed.

## Start from what users perceive

| Response time | Feels like |
|---------------|------------|
| < 100 ms | Instant (typing feedback, toggles) |
| 100-300 ms | Fast; fine for most actions |
| 300 ms - 1 s | Noticeable delay; show progress |
| > 1 s | Users' attention wanders; show a skeleton or loading state |
| > 10 s | Make it asynchronous with progress or a notification |

## Split the budget

Example: `GET /search` with a target of **300 ms at p95** for users in India, served from a region in Mumbai.

| Part | Budget | Why |
|------|--------|-----|
| Network: DNS + connection | 0 ms on warm connections, ~60 ms on first use | App keeps one HTTP/2 connection open; `preconnect` on the web |
| Network: request + response (RTT ~40 ms on mobile) | 50 ms | One round trip plus jitter |
| Download (20-40 KB, gzip) | 20 ms | Keep results compact; images load separately |
| Gateway (auth, limits, routing) | 5 ms | JWT validation, local rate-limit counters |
| Search service processing | 120 ms | Query parsing, index lookup on 4 shards in parallel, ranking |
| Hydrating results (prices, stock) from cache | 15 ms | One batched cache read |
| Serialise + compress | 5 ms | |
| Headroom for tails and queueing | 85 ms | p95, not p50 |
| **Total** | **300 ms** | |

Each line becomes a target for someone: the search team owns 120 ms at p95, the platform team owns the gateway's 5 ms.

## Rules for budgets

1. **Budget at a percentile** (p95 or p99), not the average.
2. **Sequential parts add up; parallel parts cost the slowest one.** Fan-out to many shards or services makes the slowest
   one's tail your typical case (lesson 11.3).
3. **Leave headroom** for queueing and tails, typically 20-30% of the total.
4. **Network is part of the budget.** If users are far away, the network may take more than half; decide early whether
   you need a closer region or an edge.
5. **Pass deadlines down.** Each downstream call gets what's left of the budget (gRPC deadlines, lesson 20.5), and
   work that's already too late gets cancelled.
6. **Measure each line** with traces and client timings, and review budgets when the design changes.

## When the budget doesn't fit

Order of attack:

1. Remove round trips (connection reuse, batching, one call per screen).
2. Move work off the request path (async jobs, events, precomputation).
3. Parallelise what remains.
4. Cache results that repeat.
5. Move closer to users (edge, regions).
6. Only then optimise code.

## Try it

Write a budget for `POST /rides` (request a ride) with a target of 1 s at p95. The flow: auth, validate pickup and
drop-off, get a price quote (pricing service, 40 ms), check fraud (fraud service, 60 ms), create the ride (8 ms),
start matching drivers (async), respond.

## Key takeaways

- Turn "fast" into a number at a percentile, then split it across network, gateway, services and headroom.
- Sequential parts add; parallel parts cost the slowest; tails dominate fan-out.
- Leave headroom, pass deadlines down, and measure each line.
- When it doesn't fit: fewer round trips, async work, parallelism, caching, proximity, then code.

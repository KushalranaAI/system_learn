# Response time, latency and processing time

"The API takes 40 ms," says the backend team, pointing at their server metrics. "The API takes 900 ms," says the mobile
team, pointing at their crash-reporting tool. Both are right. They're measuring different things. Before you can
estimate or improve how long an API call takes, you need words for its parts.

## The parts

```
 user taps ─┬─ DNS ─ TCP ─ TLS ─┬─ request travels ─┬─ server works ─┬─ response travels + downloads ─┬─ app renders
            │   connection setup │  (half an RTT)    │  processing    │ (half an RTT + transfer time)   │
            └────────────────────┴──── network latency ──────────────┴─────────────────────────────────┘
            └───────────────────────────── response time (what the user waits for) ─────────────────────┘
```

| Term | Meaning | Where you measure it |
|------|---------|----------------------|
| **Processing time** (service time) | Time the server spends on the request: queueing, CPU, database, downstream calls | Server metrics and traces |
| **Network latency** | Time spent getting bytes between client and server: propagation, handshakes, transfer | Client-side timings minus server timings |
| **Response time** | Everything the user waits for, from sending the request to having the response | Client side: real-user monitoring, SDK timings |

```
response time ≈ connection setup + round trip(s) for the request + processing time + transfer time
```

## Why the server's number is the smallest one

A server in a data centre measures from "first byte of the request arrived" to "last byte handed to the kernel". It
never sees DNS, handshakes, the user's congested mobile network, slow start, or the time the app spends parsing JSON.
For users far away or on mobile networks, the network is usually most of the total.

## Percentiles, not averages

Latency distributions have long tails. If 99 requests take 50 ms and one takes 5 s, the average (≈100 ms) describes
nobody's experience.

| Percentile | Meaning |
|------------|---------|
| p50 (median) | Half of requests are faster |
| p95 | 1 in 20 is slower |
| p99 | 1 in 100 is slower; a page making 30 calls hits this on most loads |
| p99.9 | Matters at very high volume or for fan-out (lesson 11.3) |

A screen that makes several calls is as slow as the slowest one, so the tail of each API becomes the typical experience
of the screen.

## What to measure, where

- **Server:** processing time per endpoint (p50/p95/p99), queue time separately from work time, and time per
  dependency (traces).
- **Edge / gateway:** time to first byte and total time per route.
- **Client:** real-user timings broken down by phase (the browser's Resource Timing API gives DNS, connect, TLS, TTFB and
  download for each request; mobile networking libraries expose similar metrics), by region, network type and app
  version.

## Try it

A mobile app reports p95 response time of 1.2 s for `GET /feed`. Server traces show p95 processing time of 110 ms.
List the places the other ~1.1 s could be.

<details>
<summary>Answer</summary>

DNS on cold start; new TCP + TLS handshakes (no connection reuse, or HTTP/1.1 with many parallel connections); a long
round trip (users far from the region, or on poor mobile networks); slow start on a large response (a few hundred KB
of JSON); queueing in a gateway or load balancer not covered by the trace; retries after timeouts; and client-side
JSON parsing on a slow phone. Break the client timings into phases to find out which.
</details>

## Key takeaways

- Response time = connection setup + network round trips + processing time + transfer time.
- Server metrics only see processing time; users see everything.
- Use percentiles; screens that make many calls feel each call's tail.
- Measure on the client, at the edge and on the server, and break client timings into phases.

# Estimating processing time

Before building an endpoint, you can estimate how long the server will spend on it, to within a factor of two, on a
whiteboard. That estimate tells you whether the design can meet its budget, and which part to worry about first.

## Numbers to know

Rough orders of magnitude on current cloud hardware (lesson 1.4 has a fuller table):

| Operation | Time |
|-----------|------|
| In-process function call, map lookup | nanoseconds |
| Serialise / parse 10 KB of JSON | ~50-200 µs |
| Redis GET in the same zone | ~0.2-0.5 ms (mostly the network round trip) |
| Indexed point lookup in Postgres/MySQL (data in memory) | ~0.5-2 ms |
| Query reading thousands of rows, or a sort | 5-50 ms |
| Network round trip to another zone in the same region | ~0.5-2 ms |
| Call to another internal service (with its own work) | 2-20 ms |
| Call to a third-party API (payments, maps) over the internet | 50-500 ms |
| Read from object storage (S3-like) | ~10-50 ms to first byte |
| fsync to SSD (durable commit) | ~0.1-2 ms; network-attached disks more |

## Adding it up

Processing time is the sum of what happens **in sequence**, plus waiting in queues:

```
processing ≈ queue wait + parse + auth + Σ(sequential calls) + max(parallel calls) + compute + serialise
```

Example: `GET /orders/:id` for a shop.

| Step | Time |
|------|------|
| Validate JWT (signature check, cached key) | 0.1 ms |
| Read order + lines (2 indexed queries, sequential) | 2 × 1.5 = 3 ms |
| Product details for 8 lines from cache (one batched MGET) | 0.5 ms |
| Shipping status from the delivery service (parallel with the next) | 8 ms ┐ |
| Loyalty points from the rewards service | 5 ms ┘ max = 8 ms |
| Build and serialise the response (6 KB) | 0.3 ms |
| **Total** | **≈ 12 ms** (p50) |

The p99 is higher: tails of each dependency, GC pauses, cache misses. A rough rule is p99 ≈ 3-5x p50 for a healthy
service, and much worse if any step has a heavy tail.

## Queueing: the hidden term

When a server is busy, requests wait before work starts. Lesson 4.1 showed why latency explodes as utilisation passes
~80%: at 50% busy, waiting roughly equals the service time; at 90%, it's about 9x. Budget for headroom, or the estimate
above is only true at quiet times.

## The usual suspects

When estimates (or traces) come out too slow, it's nearly always one of:

1. **Sequential calls that could be parallel** (independent lookups awaited one by one).
2. **N+1 queries** (one query per item in a list).
3. **A slow external dependency on the request path** that could be async, cached or given a tight timeout.
4. **Big payloads**: serialising and compressing megabytes.
5. **Cold caches** after deploys or restarts.
6. **Lock contention** on hot rows.

## Try it

Estimate the processing time of `POST /orders` for a food delivery app: validate the token, check the restaurant is
open (cache), price the cart (pricing service, 10 ms), check the card with the payment provider (300 ms), insert the
order and its lines in one transaction (4 ms), publish an `order.created` event via an outbox (included in the
transaction), and respond. What would you change?

<details>
<summary>Answer</summary>

Roughly 0.1 + 0.5 + 10 + 300 + 4 + 0.5 ≈ **315 ms**, dominated by the payment call. Options: authorise the card
asynchronously (respond `202` with the order in `pending_payment` and push the result), or keep it synchronous but
parallelise pricing with other checks and set a strict timeout and an idempotency key on the payment call. The database
part is small; the outbox keeps "save order" and "publish event" atomic without a second network call.
</details>

## Key takeaways

- Know rough costs: cache ~0.3 ms, indexed query ~1 ms, internal call ~5-20 ms, third-party call ~50-500 ms.
- Processing time = queueing + sequential steps + the slowest parallel step.
- p99 is several times p50; queueing makes everything slower past ~80% utilisation.
- Look first for sequential calls, N+1 queries and slow dependencies on the request path.

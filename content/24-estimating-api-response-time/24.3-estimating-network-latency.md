# Estimating network latency

Light is fast, but the Earth is big. A request from Sydney to a server in Virginia can't come back in less than
about 160 ms, however good your code is, and a new HTTPS connection needs several of those round trips before the
first byte of the response. This lesson turns that into numbers you can work out by hand.

## Propagation: distance

Light in optical fibre travels at about two thirds of its speed in vacuum: roughly **200 km per millisecond**. Real
routes are longer than straight lines (cables follow coasts and pass through exchange points), so multiply by about
1.5-2.

```
RTT ≈ 2 × distance × 1.6 ÷ 200 km/ms  +  last mile (Wi-Fi ~5 ms, good 4G/5G ~20-40 ms, congested mobile 100+ ms)
```

| Route (approx. distance) | Estimated RTT |
|--------------------------|---------------|
| Same data centre | < 1 ms |
| Mumbai ↔ Bengaluru (~850 km) | ~15-20 ms |
| London ↔ Frankfurt (~650 km) | ~10-15 ms |
| New York ↔ London (~5,600 km) | ~70-90 ms |
| Mumbai ↔ Frankfurt (~6,300 km) | ~100-130 ms |
| Sydney ↔ US East (~16,000 km) | ~200-250 ms |

## Handshakes: round trips before the request

| Connection | Round trips before the request is sent |
|------------|----------------------------------------|
| DNS lookup (not cached) | ~1 to the resolver (often nearby), more if the resolver must ask authoritative servers |
| TCP | 1 |
| TLS 1.2 | +2 |
| TLS 1.3 | +1 |
| HTTP/3 (QUIC, transport + TLS 1.3 combined) | 1 total |
| TLS 1.3 / QUIC resumption with 0-RTT | 0 (the request goes in the first flight; safe requests only) |
| **Reused connection** (keep-alive, HTTP/2, HTTP/3) | **0** |

Then the request and response take **one more round trip**.

## Transfer: bandwidth and slow start

```
transfer time ≈ bytes × 8 ÷ bandwidth  +  extra round trips while the congestion window grows
```

A new TCP or QUIC connection starts by sending about 10 packets (~14 KB, RFC 6928), then roughly doubles every round
trip: 14 KB, 29 KB, 58 KB, 116 KB… A 120 KB response on a new connection needs about 3-4 extra round trips. On a
long-RTT path that's often worse than the bandwidth term. On a warm connection, the window is already open.

## Putting it together

First call from Mumbai to Frankfurt (RTT 120 ms), HTTP/1.1 + TLS 1.2, DNS not cached, 120 KB response at 20 Mbps:

| Phase | Round trips | Time |
|-------|-------------|------|
| DNS (resolver nearby) | ~0.5 | ~80 ms |
| TCP + TLS 1.2 | 3 | 360 ms |
| Request + first bytes | 1 | 120 ms |
| Slow start for 120 KB | ~3 | 360 ms |
| Bandwidth (120 KB at 20 Mbps) | - | ~50 ms |
| **Network total** | | **≈ 950 ms** |

The same call on a reused HTTP/2 connection: one round trip plus bandwidth, about **170 ms**. Try it in the simulation
below.

## What helps

| Fix | Saves |
|-----|-------|
| Reuse connections (keep-alive, HTTP/2, connection pools in SDKs) | All handshakes and slow start after the first call |
| TLS 1.3, HTTP/3 | 1-2 round trips on new connections |
| Terminate TLS at a nearby edge (CDN) | Handshakes become short trips; the edge keeps warm connections to the origin |
| `preconnect` hints | Moves the handshake earlier, in parallel with other work |
| Smaller responses | Bandwidth and slow-start round trips |
| Serve from a closer region | The irreducible round trip itself |

## Try it

Use the simulation: a user 6,300 km away makes a first call. Get it under 450 ms without changing the distance. Then
make repeat calls as fast as you can. What's the floor?

<details>
<summary>Answer</summary>

Moving to HTTP/3 or TLS 1.3 and terminating at a nearby edge removes most handshake time; trimming the response
removes slow-start round trips. Repeat calls on a warm connection are bounded by one round trip to the region
(~120 ms here) plus server work: below that, only a closer region or an edge cache helps.
</details>

## Key takeaways

- RTT ≈ 2 × distance × 1.6 ÷ 200 km/ms + the last mile; distance sets a floor nothing in code can beat.
- New connections cost 1-3 handshake round trips plus slow-start round trips; reused ones cost none.
- Transfer time = bytes ÷ bandwidth, plus extra round trips for large responses on new connections.
- Reuse connections, use TLS 1.3/HTTP/3, terminate near users, shrink payloads, and serve from closer regions.

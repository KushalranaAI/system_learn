# Health checks and timeouts

Having three servers doesn't make you resilient. When one dies, the load balancer must **notice and stop sending it
traffic**. Until it does, one request in three fails.

## Health checks

**Active checks:** the LB calls each server every few seconds.

```
GET /healthz  → 200 OK   (healthy)
              → 503 / timeout / connection refused   (unhealthy)
```

Typical settings: every **5 s**, mark unhealthy after **2–3 failures**, healthy again after **2 successes**. That's
10–15 s to detect a dead server.

**Passive checks (outlier detection):** the LB watches real traffic. A server returning many 5xx responses or timing
out gets ejected for a while. It's faster than active checks and catches "up but broken".

### Liveness vs readiness

| Check | Asks | Failing means |
|-------|------|---------------|
| **Liveness** | "Is the process stuck?" | Restart it |
| **Readiness** | "Can it serve traffic right now?" | Stop routing to it, but don't kill it |

A server that's starting up, warming caches or draining for shutdown is alive but **not ready**.

Keep checks **shallow**. If `/healthz` checks the database and the database blips, *every* server fails its health
check at once and the LB has nowhere to send traffic. Check the server itself; monitor dependencies separately.

## Timeouts

Every network call needs a timeout. Without one, a slow dependency makes requests pile up until the server runs out
of threads, connections or memory.

| Where | Example |
|-------|---------|
| Client → LB | 30 s total |
| LB → server | 10 s |
| Server → database | 2 s per query |
| Server → another service | 300 ms (and maybe one retry) |

Inner timeouts must be **shorter** than outer ones; otherwise the caller gives up while the work continues uselessly.
Better still, pass a **deadline** along the call chain ("this request must finish by 10:15:03.250").

## Graceful shutdown (connection draining)

Deploys stop servers constantly. Do it without dropping requests:

1. Mark the server **not ready**, so the LB stops sending new requests.
2. Wait for in-flight requests to finish (up to, say, 30 s).
3. Close connections, flush logs, exit.

```
SIGTERM → readiness=false → drain (≤30 s) → exit
```

## Try it

Run the [Load balanced preset](#/sandbox?preset=scaled). In the timeline bar choose **Kill: API server 1** and run it.
Then select the load balancer, turn on **health checks**, and run it again. Compare the worst second.

<details>
<summary>What you'll see</summary>

Without health checks, a third of the traffic keeps going to the dead server: success drops to ~67%, and retries add
even more load. With health checks, the other two servers absorb the traffic and success stays near 100%, provided
they have the spare capacity.
</details>

## Key takeaways

- Redundancy only helps if the load balancer detects failures: use active and passive checks.
- Separate liveness (restart me) from readiness (don't route to me).
- Keep health checks shallow, or one dependency blip takes out everything.
- Every call needs a timeout, shorter as you go deeper; drain servers before stopping them.

# Why busy servers get slow

A server that handles 10,000 requests a second is *not* fine at 9,500. Long before it's "full", requests start
waiting in line, and latency climbs much faster than load.

## Utilisation

```
utilisation (ρ) = arrival rate ÷ service capacity
```

At 5,000 req/s on a server that can do 10,000, ρ = 50%. Half the time the CPU is busy, and requests that arrive then
must wait.

## The queueing curve

For a simple queue (random arrivals, one server, known as M/M/1), the average time in the system is:

```
time = service time ÷ (1 − ρ)
```

| Utilisation | Time vs. idle |
|-------------|---------------|
| 10% | 1.1× |
| 50% | 2× |
| 80% | 5× |
| 90% | 10× |
| 95% | 20× |
| 99% | 100× |

Going from 80% to 90% busy doubles latency. From 90% to 99%, it rises tenfold. The p99 behaves the same way, scaled by
a constant: for M/M/1 the 99th percentile is `service time × ln(100) ÷ (1 − ρ)`. That's the formula the simulator in
this course uses for every component.

```
latency
  │                             │
  │                            ╱
  │                          ╱
  │                      _-'
  │               __--''
  │_______----''''
  └─────────────────────────────── ρ
  0        50%        80%  90% 100%
```

## Why it happens

Arrivals are **random**, not evenly spaced. Even at 50% average load, requests sometimes arrive in clumps. The server
can't "bank" idle time, so clumps form a queue. The closer you run to 100%, the less idle time there is to drain the
queue before the next clump.

## What this means for design

- **Plan for headroom.** Run steady-state at 50–70% utilisation, so bursts and failures don't push you onto the
  steep part of the curve.
- **N+1.** If you lose one of N servers, the rest jump in utilisation. 4 servers at 60% become 3 at 80%.
- **Watch saturation, not only averages.** CPU at 85% "average" over a minute often means seconds at 100%.
- **Past 100% it isn't slow, it's broken.** Queues grow without limit; something must drop or reject the excess
  (timeouts, load shedding, 503s).

## Key takeaways

- Utilisation = load ÷ capacity; queueing makes latency grow like 1 ÷ (1 − ρ).
- 80% → 90% doubles latency; 90% → 99% multiplies it tenfold.
- Keep 30–50% headroom for bursts and for losing a server.
- Past 100%, queues grow without bound, so you must shed load.

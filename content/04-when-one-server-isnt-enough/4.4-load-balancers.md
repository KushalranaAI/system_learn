# Load balancers

A load balancer (LB) is the single address clients talk to. It forwards each request to one of many servers, and it
decides which one.

## Layer 4 vs layer 7

| | L4 (transport) | L7 (application) |
|-|----------------|------------------|
| Sees | IP addresses, ports, TCP/UDP | Full HTTP: path, headers, cookies |
| Can route by | Connection | URL, host, header, cookie |
| TLS | Passes it through (or terminates) | Usually terminates TLS |
| Speed | Very fast, very cheap | A little more work per request |
| Examples | AWS NLB, IPVS | nginx, HAProxy, Envoy, AWS ALB |

L7 lets you do `/api/*` → API servers and `/images/*` → image servers, add headers, and retry on another server.
Most web apps use L7.

## Balancing algorithms

| Algorithm | How | Good when |
|-----------|-----|-----------|
| **Round robin** | 1, 2, 3, 1, 2, 3… | Requests are similar and servers are identical |
| **Weighted round robin** | Bigger servers get proportionally more | Mixed server sizes |
| **Least connections** | Send to the server with the fewest open requests | Request durations vary a lot (uploads, reports) |
| **Least response time** | Send to the fastest-responding server | Varied servers or noisy neighbours |
| **Power of two choices** | Pick 2 servers at random, use the less loaded | Large fleets: near-optimal and cheap |
| **Hash (IP, user, key)** | Same key → same server | Server-side caches or sticky state (see 4.6) |
| **Consistent hashing** | Hash ring; few keys move when servers change | Caches and shards (Module 14) |

Round robin with slow and fast requests mixed together leads to uneven queues. Least connections or power-of-two
choices fix that cheaply.

## What else an LB does

- **TLS termination:** decrypt once at the edge, so servers speak plain HTTP inside the network.
- **Health checks:** stop sending to dead servers (lesson 4.5).
- **Connection reuse:** many client connections become few pooled connections to backends.
- **Retries:** resend an idempotent request to another server if the first fails.
- **Rate limits, auth, compression, request ids:** many LBs and gateways do these too.

## Isn't the LB a single point of failure?

It would be, so LBs are made redundant themselves:
- managed cloud LBs run on many machines behind one address;
- self-hosted pairs share a **virtual IP** (keepalived/VRRP): if the active one dies, the standby takes the IP;
- DNS can point at several LB addresses.

## Try it

Your API has two endpoints: `GET /items` (5 ms) and `POST /reports` (5 s). With round robin over 4 servers, some
servers have 40 requests queued while others are idle. Why, and what would you change?

<details>
<summary>Answer</summary>

Round robin ignores how long requests take. Servers that happen to get several 5-second reports build long queues,
and fast requests stuck behind them wait too. Switch to **least connections** (or power of two choices). Better
still, move reports to a background queue (Module 7) so web servers only handle fast requests.
</details>

## Key takeaways

- A load balancer spreads requests and hides servers behind one address.
- L7 routes by HTTP details; L4 is faster but sees only connections.
- Least connections or power-of-two choices beat round robin when requests vary.
- LBs also terminate TLS, check health and retry, and they're made redundant themselves.

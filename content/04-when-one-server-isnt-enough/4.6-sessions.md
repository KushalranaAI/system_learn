# Sessions

HTTP is stateless: each request stands alone. But users log in once and expect to stay logged in. With many servers,
where does "who is this?" live?

## Option 1: Sticky sessions

The load balancer pins each user to one server (by cookie or IP hash). The session stays in that server's memory.

- ✅ No code changes.
- ❌ When that server dies or is deployed, its users are logged out.
- ❌ Uneven load: some servers get heavy users.
- ❌ Scaling in or out reshuffles users.

It's fine as a temporary step; avoid it as the design.

## Option 2: Shared session store

Sessions live in Redis. The cookie holds only a random session id.

```
Cookie: sid=9f8a7c...      →  any server  →  GET session:9f8a7c...  →  {user_id: 42, roles: [...]}
```

- ✅ Any server handles any request.
- ✅ Logout or revoking access is instant (delete the key).
- ❌ One more lookup per request (~0.5 ms) and one more system to keep available.

## Option 3: Signed tokens (e.g. JWT)

The server signs the user's identity into a token. Any server verifies the signature without a lookup.

```
Authorization: Bearer eyJ1c2VyIjo0Miwicm9sZSI6InVzZXIiLCJleHAiOjE3OTM...  (header.payload.signature)
```

- ✅ No session store on the request path.
- ✅ Works across services and regions.
- ❌ **Revocation is hard**: a stolen token works until it expires.
- ❌ Tokens get large if you stuff data into them.

The common compromise: **short-lived access tokens** (5–15 min) plus a **refresh token** checked against a database
when renewing. Revoking the refresh token cuts access within minutes.

## Comparison

| | Sticky | Shared store | Signed token |
|-|--------|--------------|--------------|
| Survives server loss | ❌ | ✅ | ✅ |
| Lookup per request | none | Redis | none (verify signature) |
| Instant logout / revoke | ✅ | ✅ | ❌ (wait for expiry) |
| Cross-service | ❌ | with access to the store | ✅ |

## Security notes

- Session cookies: `HttpOnly; Secure; SameSite=Lax` (or `Strict`).
- Rotate the session id on login, to prevent session fixation.
- Never put secrets or personal data in a JWT payload. It's only base64, not encrypted.

## Try it

A banking app needs "log out of all devices" to take effect immediately, and runs 30 API servers. Which option, and
why?

<details>
<summary>Answer</summary>

A **shared session store** (or very short-lived tokens checked against a revocation list). Immediate logout means the
server must look something up on every request; pure self-contained tokens can't be revoked before they expire.
</details>

## Key takeaways

- Sticky sessions are easy but fragile; avoid them as a final design.
- A shared session store works with any server and allows instant revocation.
- Signed tokens remove the lookup but are hard to revoke: keep them short-lived with refresh tokens.

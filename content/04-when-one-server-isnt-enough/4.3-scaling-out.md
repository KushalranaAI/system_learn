# Scaling out

**Horizontal scaling** (scaling out) means running many copies of your server and spreading requests across them.
Need more capacity? Add a copy. Lose one? The others carry on.

```
            ┌─▶ API 1 ─┐
Client ─▶ LB ├─▶ API 2 ─┼─▶ Database
            └─▶ API 3 ─┘
```

## The catch: state

Scaling out only works if **any server can handle any request**. That means servers must be **stateless**: nothing a
later request depends on may live only in one server's memory or disk.

Typical state hiding in servers:

| State | Problem when scaled out | Where it should live |
|-------|-------------------------|----------------------|
| Login sessions in memory | Next request hits another server: "logged out" | Redis, or a signed token (lesson 4.6) |
| Uploaded files on local disk | Other servers can't find them | Object storage (S3) |
| In-memory caches | Each server has a different copy | Redis (or accept per-server caches for hot data) |
| Scheduled jobs (cron) | Runs N times, once per server | A single scheduler or a job queue with leases |
| Rate-limit counters in memory | Each server allows the full limit | Redis counters |
| WebSocket connections | A message for a user must find "their" server | Pub/sub between servers (Module 6) |

## Making a server stateless: a checklist

1. Sessions → shared store or tokens.
2. Files → object storage; never write user data to local disk.
3. Config → environment variables or a config service, the same on every instance.
4. Background work → a queue (Module 7), not threads inside the web process.
5. Logs → stdout to a collector, not local files.
6. Any server can be **killed at any moment** without losing anything.

That last point is the real test. If you can't kill a server without losing anything, it isn't stateless.

## What scaling out gives you

- **Capacity:** roughly linear. Ten servers handle about ten times the load (until a shared component, usually the
  database, becomes the bottleneck).
- **Redundancy:** with N+1 servers, losing one is a non-event (with health checks, lesson 4.5).
- **Elasticity:** add servers at peak, remove them at night (lesson 4.7).
- **Safer deploys:** update servers one at a time (rolling deploys).

## What it costs

- A load balancer (lesson 4.4).
- Shared state stores to run and secure.
- Harder debugging: "which server handled that request?" means you need request ids and central logs.

## Try it

A photo app stores uploaded files in `/var/uploads` on the server and keeps the logged-in user in a server-side session
map. You add a second server behind a load balancer. List everything that breaks.

<details>
<summary>Answer</summary>

- Users are randomly "logged out" when the LB sends them to the other server.
- Photos uploaded through server A return 404 when fetched through server B.
- Any cron job (thumbnail cleanup, emails) now runs twice.
- Per-server rate limits let users do twice as much.

Fix: sessions in Redis or signed tokens; files in object storage; one scheduler or queue; shared counters.
</details>

## Key takeaways

- Scaling out means many identical servers behind a load balancer.
- It needs stateless servers: any request can go to any server.
- Move sessions, files, jobs and counters into shared services.
- The test: you can kill any server at any time without losing anything.

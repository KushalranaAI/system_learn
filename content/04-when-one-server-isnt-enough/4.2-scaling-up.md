# Scaling up

The simplest response to "the server is too busy" is a bigger server. This is **vertical scaling** (scaling up), and
it's often the right first move.

## Why it's attractive

- **No code changes.** Same app, more CPU and RAM.
- **No new failure modes.** No load balancer, no shared session store, no "which server has my data?"
- **Cheap at small sizes.** Doubling a small machine is a few dollars a month.

Many successful products run for years on a few large machines.

## Why it stops working

### Diminishing returns
Doubling cores rarely doubles throughput. Lock contention, garbage collection, memory bandwidth and the network stack
all become shared bottlenecks.

| vCPUs | Ideal req/s | Typical real req/s |
|-------|-------------|--------------------|
| 2 | 5,000 | 5,000 |
| 4 | 10,000 | ~9,000 |
| 8 | 20,000 | ~16,000 |
| 16 | 40,000 | ~26,000 |
| 32 | 80,000 | ~36,000 |

(These are the numbers the simulator uses: illustrative, and shaped like real benchmarks.)

### A hard ceiling
There's a biggest machine. When your load passes it, no amount of money helps.

### Price grows faster than capacity
Top-end instances often cost more per unit of throughput than mid-sized ones.

### One machine is one failure
A single big server is a **single point of failure**. Hardware dies, kernels panic, deploys go wrong. With one
machine, any of those is an outage.

## When to scale up

| Scale up when | Scale out when |
|---------------|----------------|
| Load fits comfortably in one machine | You're near the biggest size |
| You need it working *today* | You need to survive a server dying |
| The workload is hard to split (a single-writer database) | The work is stateless and easy to split |
| Ops simplicity matters more than redundancy | Traffic swings a lot (scale out and in) |

Databases are usually scaled up much longer than API servers, because splitting a database is hard (Modules 5 and 9).

## Try it

In the [Link shortener lab](#/labs/link-shortener), step 5 asks for 8,000 req/s within $400/month. Solve it by changing
machine sizes only. Then try step 6 with one 32 vCPU server instead of a load balancer. Which constraint fails?

## Key takeaways

- Scaling up is simple and often the right first step.
- Throughput grows slower than cores, and there's a ceiling.
- One big machine is still a single point of failure.
- Scale the database up for a long time; scale stateless servers out.

# MCP: connecting tools and data

Before MCP, every AI app wrote its own glue for every system: a Slack plugin for app A, another for app B, a GitHub
integration for each IDE. N apps × M systems = N × M integrations. The **Model Context Protocol** (MCP), introduced
by Anthropic in late 2024 and now an open standard, does for agents what the Language Server Protocol did for
editors: each system writes **one server**, each app writes **one client**, and they all interoperate.

## The pieces

```
┌──────────── Host (Claude Desktop, an IDE, your agent runtime) ────────────┐
│  LLM  ◄──►  agent loop                                                    │
│              ├── MCP client ──────── stdio ────────► MCP server: local git│
│              ├── MCP client ── Streamable HTTP ────► MCP server: Jira     │
│              └── MCP client ── Streamable HTTP ────► MCP server: orders DB│
└───────────────────────────────────────────────────────────────────────────┘
```

| Role | What it is | Classic analogue |
|------|-----------|------------------|
| **Host** | The AI application the user runs; owns the model, the loop, consent UI | The browser |
| **Client** | A connector inside the host, one per server connection | An HTTP client |
| **Server** | A program that exposes capabilities of one system | A backend API |

Messages are **JSON-RPC 2.0**. A server offers three kinds of things:

| Feature | Who decides to use it | Example |
|---------|----------------------|---------|
| **Tools** | The **model** (it calls them in the agent loop) | `run_query`, `create_ticket` |
| **Resources** | The **app or user** (attached as context) | `file:///README.md`, `db://schema/orders` |
| **Prompts** | The **user** (templates, often slash commands) | `/summarise-incident` |

The client side can offer **elicitation**: a server asks the user for input mid-request (a confirmation, a missing
field). Long-running work goes through the **Tasks** extension: the server returns a handle and the client polls,
like an async job API ([lesson 7.5](#/lesson/7.5)).

## Transports

- **stdio:** the host launches the server as a local subprocess and talks over stdin/stdout. Zero network, inherits
  the user's machine permissions. Good for local tools (files, git), dangerous if the server is untrusted code.
- **Streamable HTTP:** the server is a normal web service; each request is an HTTP POST, and the response can be a
  single JSON body or a stream of events. This is how you expose company systems to many agents.

In the current revision (2026-07-28) the protocol became **stateless**: no handshake, no session id; every request
carries its protocol version and capabilities. That matters for architecture: an MCP server is now an ordinary
stateless HTTP service you put behind a load balancer and scale horizontally, like any API ([lesson 4.3](#/lesson/4.3)). State that
must survive across calls is passed as explicit handles in tool arguments.

## Auth

Remote MCP servers use **OAuth 2.1**. The MCP server is a resource server; your existing identity provider issues
tokens. The agent acts **on behalf of a user**, so the token should carry that user's identity and scopes, and the
server enforces them exactly as your REST API would. Never give a shared "service account" token to an agent that
serves many users: it turns every user into an admin.

## Exposing a database: the safe shape

The tempting server is one tool: `execute_sql(query: string)`. That gives the model (and anyone who can inject text
into its context, [lesson 29.4](#/lesson/29.4)) your whole database.

```
Agent ─► MCP server "orders" ─► Orders service API / read replica
            │
            ├─ tools: get_order(id), search_orders(customer_id, status, from, to)
            ├─ resource: schema of the 3 tables the agent may see
            ├─ authz: user token → only that customer's rows (row-level security)
            ├─ limits: LIMIT 50 rows, 2 s statement timeout, 5 req/s per user
            └─ audit: log every call (user, tool, args, rows returned)
```

Design rules:
1. **Narrow, typed tools** over raw SQL. If analysts need free-form SQL, use a **read-only role** on a **replica**,
   with an allow-list of tables and a statement timeout.
2. **Separate read and write servers**, so a host can connect the read server freely and put the write server behind
   human approval ([lesson 28.7](#/lesson/28.7)).
3. **Redact** columns the model never needs (password hashes, full card numbers, tokens).
4. **Treat returned data as untrusted.** A customer note saying "ignore previous instructions" travels back to the
   model through your server.
5. **Tool descriptions are code.** A malicious or compromised third-party MCP server can lie in its descriptions
   ("tool poisoning"). Pin and review the servers you install, as you would dependencies.

## Where MCP sits in your architecture

MCP doesn't replace your APIs; it is a thin adapter **in front of** them. The MCP server calls the same orders
service your web app calls, so business rules, rate limits and audit stay in one place. Treat it like a BFF
(backend-for-frontend) where the frontend is a model.

## Try it

Expose a PostgreSQL support database (tables `customers`, `orders`, `tickets`, `internal_notes`, `payment_methods`)
to a support agent. List the tools, transport, auth and limits.

<details>
<summary>Reference</summary>

- **Transport:** Streamable HTTP, a stateless service behind the LB, 2+ replicas.
- **Tools (read server):** `get_customer(id)`, `list_orders(customer_id, limit≤20)`, `get_ticket(id)`,
  `search_tickets(customer_id, status)`. No raw SQL.
- **Excluded:** `payment_methods` (except last 4 digits through `get_customer`), `internal_notes` (staff opinions,
  injection risk, privacy).
- **Write server, separate:** `add_ticket_note`, `issue_refund(order_id, amount≤limit)`, behind approval rules.
- **Auth:** OAuth; the token carries the agent's acting staff member or end customer; Postgres row-level security or
  service checks restrict rows.
- **Limits:** read replica, 2 s statement timeout, 50-row cap, per-user rate limit, every call audited.
</details>

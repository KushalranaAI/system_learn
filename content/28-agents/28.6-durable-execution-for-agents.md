# Durable execution for agents

A chat answer takes seconds. An agent that migrates a codebase, researches a market or processes a refund with a
manager's approval can run for **minutes to days**. Over that time, pods restart, deploys happen, the model provider
returns 429s, and humans take a weekend to click "approve". If the agent's state lives only in a process's memory,
every one of those events throws the work away, and the tokens you already paid for.

The fix is an old one from long-running jobs ([lesson 7.5](#/lesson/7.5)) and sagas (module 16): **durable execution**.

## The idea

Record every step's result in a durable log. After a crash, a new worker **replays** the log instead of redoing the
work, and continues from the first step that has no recorded result.

```
Run 42 event history (stored in DB)
 1  llm_call   → "call search(q='EU vector DBs')"     ✓ recorded
 2  tool:search → [10 results]                         ✓ recorded
 3  llm_call   → "call fetch(url=...)"                 ✓ recorded
 4  tool:fetch → ...                                   ✗ worker crashed here
--- new worker picks up run 42 ---
 replay 1-3 from history (no model calls, no cost)
 execute 4 again → continue
```

Engines that do this: **Temporal** (and Cadence), AWS Step Functions, Azure Durable Functions, Restate, DBOS, and
queue-plus-database setups you build yourself. Temporal and OpenAI shipped an integration for the OpenAI Agents SDK in
July 2025 that runs each model call and tool call as a durable activity.

## Mapping an agent onto durable execution

| Agent part | Durable-execution concept |
|-----------|---------------------------|
| The loop (decide next step, check limits) | **Workflow**: deterministic code, replayed from history |
| Each LLM call | **Activity**: result recorded; retried with backoff on 429/5xx |
| Each tool call | **Activity**: timeout, retry policy, idempotency key |
| "Wait for manager approval" | **Signal** / durable timer: the run sleeps for days at no cost |
| Step limit, budget | Workflow state, survives restarts |

The workflow must be **deterministic**: no direct clock reads, random numbers or network calls in the loop code
itself, because replay must take the same path. All non-determinism, including the model, goes in activities whose
results are recorded. The model being random is fine; its recorded answer is what replay uses.

## Idempotent tools

Durability gives you **at-least-once** execution of activities: a worker can crash after the refund API succeeded but
before the result was recorded, so the step runs again. Every side-effecting tool needs an idempotency key
([lesson 7.3](#/lesson/7.3)):

```
key = f"{run_id}:{step_no}:{tool_name}"
POST /refunds  Idempotency-Key: run42:7:refund_order
```

Derive the key from the run and step, never from the model's arguments alone (the model may phrase the second
attempt differently). Read-only tools are naturally safe to repeat.

## Retries, at the right layer

- **Model call errors** (429, 529 overloaded, timeouts): retry in the activity with exponential backoff and jitter,
  maybe fail over to another provider ([lesson 29.6](#/lesson/29.6)).
- **Tool errors** that are permanent (404, validation): don't retry blindly; return the error to the model as a
  result so it can choose another path.
- **Bad model output** (invalid JSON, wrong tool): give the error back and let it try again, counted against the step
  limit.

Retry in one place ([lesson 12.2](#/lesson/12.2)). An SDK that retries 3 times inside an activity that retries 5 times is 15 calls.

## Human approval steps

```
agent proposes refund 450 EUR (> 200 limit)
  ─► workflow writes approval request to DB, notifies manager (Slack/email)
  ─► workflow waits for signal "approved"/"rejected" (timer: 48 h → auto-reject)
manager clicks approve ─► API sends signal to run 42 ─► refund activity executes
```

No process holds memory while waiting. The approval is recorded in the history, which doubles as an **audit trail**
([lesson 28.7](#/lesson/28.7)).

## Long-running tasks and the user

The API pattern is the async job ([lesson 7.5](#/lesson/7.5)): `POST /tasks` returns `202 Accepted` with a task id; the client polls
or subscribes (SSE/WebSocket) for progress; results land in storage. MCP's Tasks extension and A2A tasks use the same
shape.

## Deploying while agents run

A run that started on version 7 of your prompt and tools may still be running when version 8 deploys. Options:
- **Version the workflow** (Temporal has explicit versioning) so old runs replay old code.
- **Drain**: keep old workers until their runs finish; Anthropic used *rainbow deployments* for its research agents.
- Never change a tool's meaning in place; add `refund_order_v2`.

## Try it

A coding agent is 25 steps into a 40-step task (about 9 minutes, $3 of tokens) when its pod is killed by a deploy.
Step 25 was `git push` to a branch. How should the design resume, and what must be true of each piece?

<details>
<summary>Reference</summary>

- Run state (event history: every model response and tool result) is in a durable store; a new worker loads run id,
  **replays steps 1-24 from history** with no model calls, so no tokens are re-spent.
- Step 25 has no recorded result, so it executes again. `git push` of the same commit to the same branch is
  idempotent; anything that isn't (opening a PR, posting a comment) needs a key like `run:step:tool` checked by the
  tool ("PR for run 42 already exists → return it").
- The workspace (checked-out files) must also be durable or reconstructable: snapshot it, or rebuild from the branch
  at step 25.
- Deploy: version the workflow or drain old workers so the run continues on the code it started with.
- Limits (step 40 cap, $ budget) live in workflow state, so the crash can't reset them.
</details>

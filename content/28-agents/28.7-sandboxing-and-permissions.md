# Sandboxing and permissions

An agent is a program whose next action is chosen by text, and some of that text comes from strangers (web pages,
emails, tickets). Assume that at some point it **will** try to do the wrong thing, by mistake or because it was
tricked ([lesson 29.4](#/lesson/29.4)). Security is then about the **blast radius**: what is the worst it can do, and who notices?

OWASP lists this as **LLM06: Excessive Agency**: too much functionality, too many permissions, or too much autonomy.

## Least privilege, for agents

| Principle | In practice |
|-----------|-------------|
| Fewest tools | A support agent needs `get_order` and `refund_order`, not `execute_sql` |
| Narrowest tool | `refund_order(order_id, amount ≤ 200)` instead of `create_payment(any account, any amount)` |
| Acts **as the user** | Use the end user's (or staff member's) token with their scopes, never a shared admin key |
| Read and write separated | Different tools, different credentials, different approval rules |
| Short-lived credentials | Tokens scoped to the task, expiring in minutes |
| Prod is special | Agents work in dev/staging; production changes go through the normal deploy pipeline |

The check happens **in the tool's server-side code**, not in the prompt. "Never refund more than 200 EUR" in a
system prompt is a suggestion; `if amount > 200: reject` is a control.

## Approval gates

Sort actions by how bad and how reversible they are:

```
                 reversible                    irreversible
low impact   │ auto: read, search, draft  │ auto + log: send a templated reply
high impact  │ auto + notify: refund ≤ 50 │ HUMAN APPROVAL: delete data, pay out,
             │ (can be undone)            │ deploy to prod, email all customers
```

Good approval UX shows the **exact action** (tool, arguments, diff), not the agent's description of it. An agent
that says "I'll tidy the table" while the call is `DROP TABLE users` must be caught by the human reading the call.
Too many approvals cause "approval fatigue": people click yes to everything. Keep gates for the actions that matter.

## Isolated execution

Agents that run code (coding agents, data analysis) need a sandbox:

| Isolation | Strength | Startup | Notes |
|-----------|----------|---------|-------|
| Process + seccomp/user | Weak | ms | Shares the kernel; fine for trusted code only |
| Container (Docker) | Medium | ~1 s | Common; harden: no privileged mode, read-only root, drop capabilities |
| gVisor | Strong | ~1 s | User-space kernel intercepts syscalls |
| microVM (Firecracker) | Strong | ~100-200 ms | Separate kernel per sandbox; used by many code-execution services |
| Separate cloud account | Strongest | minutes | For agents that touch infrastructure |

Plus, around the sandbox:
- **Network egress allow-list** (package registry, your git host; nothing else). This also blocks data exfiltration.
- **No secrets inside.** Inject short-lived, scoped credentials through a proxy that adds them to approved requests.
- **Resource limits:** CPU, memory, disk, wall-clock time; kill on breach.
- **Disposable:** a fresh sandbox per task; nothing persists except explicit outputs.

## Audit logs

Every tool call is an action taken on someone's behalf. Log it like a bank would:

```json
{"ts":"2026-10-24T10:02:11Z","run_id":"r42","step":7,"agent":"support-v12",
 "on_behalf_of":"user:8812","tool":"refund_order","args":{"order_id":"A123","amount_eur":80},
 "decision":"auto-approved (≤200)","result":"ok","refund_id":"R9","model":"medium-2026-09"}
```

Append-only storage, retention per policy ([lesson 29.7](#/lesson/29.7)), and alerts on anomalies (refund volume per hour, the same
tool failing repeatedly, calls outside business hours). Logs are also how you answer "why did the agent do that?"
after an incident.

## Kill switches

Have a way to stop all agents of a type in seconds (a feature flag checked before every tool call), and per-tool
circuit breakers: if `refund_order` volume is 10× normal, disable it and page someone.

## Try it

An internal "ops agent" helps engineers. Its tools: `read_logs`, `query_metrics`, `restart_service`,
`scale_service`, `run_sql`, `rollback_deploy`, `send_slack_message`, `delete_s3_objects`. Decide which run
automatically, which need a human, and what else you'd change.

<details>
<summary>Reference</summary>

- **Automatic:** `read_logs`, `query_metrics` (read-only, scoped to the engineer's services).
- **Automatic + notify:** `send_slack_message` to the incident channel only; `scale_service` up within limits
  (e.g. ≤ 2× current, reversible).
- **Human approval (show exact call):** `restart_service` in production, `rollback_deploy`, scaling down.
- **Change the tool:** `run_sql` → read-only role on a replica with a timeout, or remove it. `delete_s3_objects` →
  remove from the agent entirely; at most "mark for deletion" with a lifecycle rule and a human review.
- **Everywhere:** acts with the requesting engineer's identity, sandboxed runner with egress allow-list, audit log,
  kill switch.
</details>

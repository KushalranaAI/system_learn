# Multi-agent systems

A multi-agent system is several agent loops that cooperate: usually one **orchestrator** (lead) that plans and
several **subagents** (workers) that each do part of the job in their own context window. It is the
orchestrator-workers pattern ([lesson 28.1](#/lesson/28.1)) where the workers are agents, not single calls.

## Why split at all

Two reasons, both architectural:

1. **Parallelism.** Independent subtasks run at the same time. Research that takes one agent 20 sequential searches
   takes 4 subagents 5 searches each.
2. **Context isolation.** Each subagent explores with a clean window and returns a **short summary**. The lead's
   window holds conclusions, not 200 pages of search results ([lesson 28.4](#/lesson/28.4)).

## What Anthropic measured

Anthropic described the multi-agent architecture behind Claude's Research feature (June 2025):

- A lead agent (Claude Opus 4) planning and spawning subagents (Claude Sonnet 4) that search in parallel
  **outperformed a single Opus 4 agent by 90.2%** on their internal research eval.
- Token usage alone explained **about 80%** of the variance in performance on the BrowseComp benchmark. Multi-agent
  works largely because it spends more tokens, in parallel.
- Agents used about **4×** the tokens of a chat; multi-agent systems about **15×**.
- The lead typically starts **3-5 subagents**; each uses 3+ tools in parallel, which cut research time by up to 90%
  for complex queries.
- Early versions spawned **50 subagents** for simple questions. Scaling effort to the query had to be taught in the
  prompt (1 agent for a simple fact; 10+ for complex research).

The lesson for a designer: multi-agent buys quality on **broad, parallelisable** tasks at roughly an order of
magnitude more cost. It is worth it when the task's value is high.

## The architecture

```
user ─► lead agent ──plan──► memory store (plan survives truncation)
           │ spawn (task, output format, tools, budget)
   ┌───────┼────────┬─────────┐
   ▼       ▼        ▼         ▼
 sub A   sub B    sub C     sub D        each: own loop, own context, step limit
   │       │        │         │          tools: search, fetch, read
   └── summaries + references (files / artifacts) ──┐
                                                   ▼
                                 lead synthesises ─► citation pass ─► answer
```

How to brief a subagent (this is where most failures come from):
- an **objective** and what is out of scope (so two subagents don't research the same thing);
- the **output format** (e.g. "max 300 words, a list of claims with source URLs");
- which **tools** to use and a **budget** (steps, tokens).

Large outputs should go to a store (object storage, a DB row) and be passed by **reference**, not pasted through the
lead's context: the "telephone game" loses detail and burns tokens.

## When not to use multi-agent

Cognition (makers of Devin) argued in *Don't build multi-agents* (2025) that parallel subagents making **dependent
decisions** produce conflicting work: two subagents building parts of one app each make different assumptions.
Their rule: share full context and traces, and prefer a single-threaded agent when actions depend on each other.

| Good fit | Poor fit |
|----------|----------|
| Breadth-first research, many independent sources | Coding one feature where every change affects the next |
| Checking N documents against the same rules | Tasks needing tight shared state |
| Tasks worth 10-15× the tokens | Cheap, high-volume tasks (support FAQ) |

## Handoffs

A **handoff** is a different shape: control passes from one agent to another, along with the conversation. A triage
agent hands a billing question to the billing agent, which has billing tools and a billing prompt. Architecturally
this is routing ([lesson 28.1](#/lesson/28.1)) with state transfer; keep the shared state in one store keyed by conversation id so
any agent (or a human) can pick it up.

## Agent-to-agent protocols

MCP ([lesson 28.3](#/lesson/28.3)) connects an agent to **tools**. Google's **A2A** (Agent2Agent, announced April 2025, now under the
Linux Foundation; v1.0 is the current spec) connects an agent to **another agent** that may belong to another team or
company and whose internals are opaque:

| A2A concept | Meaning |
|-------------|---------|
| **Agent Card** | JSON at a well-known URL: name, skills, endpoint, auth schemes. Discovery |
| **Task** | Unit of work with a lifecycle: submitted → working → input-required / auth-required → completed / failed / canceled / rejected |
| **Message / Part** | A turn of text, files or structured data |
| **Artifact** | The output of a task |
| Bindings | JSON-RPC, gRPC or HTTP+JSON; streaming for progress, push notifications for long tasks |

Treat a remote agent like any third-party API: timeouts, retries with idempotency, auth, and **untrusted output**:
its answer can carry prompt injection into your agent.

## Failure modes to design for

- **Runaway fan-out:** cap subagents per task and total tokens per task.
- **Duplicate work:** clear task boundaries in the briefing.
- **One slow subagent** holds up synthesis: give each a deadline, synthesise with what arrived.
- **Hard to debug:** trace every agent and tool call under one trace id ([lesson 29.2](#/lesson/29.2)).
- **Long runs and deploys:** Anthropic used *rainbow deployments* (old and new versions run side by side, traffic
  moves gradually) so running agents aren't broken mid-task.

## Try it

Split this task across agents: "Compare the pricing, data-residency options and SLAs of 5 cloud vector databases and
recommend one for an EU healthcare company."

<details>
<summary>Reference</summary>

- **Lead:** writes the plan to memory (5 vendors × 3 dimensions, output table schema), spawns **5 subagents, one per
  vendor** (not one per dimension: each vendor's docs are one place to read).
- **Subagent brief:** "For vendor X, find list pricing for 100M vectors, EU regions and data-residency/BAA terms, and
  SLA %. Return JSON rows with a source URL per cell. Max 15 tool calls."
- **Parallel** run: wall time ≈ the slowest subagent, tokens ≈ 5 subagents + lead (expect 10×+ a single chat).
- **Lead synthesises** the table, flags missing cells, and applies the EU healthcare criteria; a final pass checks
  every claim has a citation.
- **Limits:** deadline per subagent, 5-subagent cap, total token budget; partial results are reported, not hidden.

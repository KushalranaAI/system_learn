# Fastly, Jun 2021: one customer's config

On 8 June 2021, for most of an hour, many of the world's biggest news, shopping and government websites showed error
pages. The cause was a bug in Fastly's CDN software that had been shipped almost four weeks earlier and sat silent
until one customer pushed a perfectly **valid** configuration change that happened to trigger it. Within a minute,
85% of Fastly's network was returning errors.

## What users saw

- Sites served through Fastly returned errors such as "Error 503 Service Unavailable" instead of pages.
- The outage was short but very visible, because so many large sites share one CDN.

## Timeline (UTC)

| Time | Event |
|------|-------|
| 12 May | Fastly deploys software containing a latent bug |
| 8 Jun, 09:47 | A customer pushes a valid config change that triggers the bug; global disruption begins |
| 09:48 | Fastly monitoring identifies the disruption |
| 09:58 | Status page updated |
| 10:27 | Engineers identify the customer configuration involved |
| 10:36 | Services begin to recover (after the configuration is disabled) |
| 11:00 | Majority of services recovered |
| 12:35 | Incident mitigated |
| 17:25 | Permanent bug fix starts rolling out |

Within 49 minutes of the start, 95% of the network was operating normally.

## The trigger

Nothing was wrong with the customer's change. Fastly lets customers change their own service configuration, and
those changes reach Fastly's servers around the world quickly; that speed is part of the product. This particular
configuration, under specific circumstances, hit a code path that the 12 May release had broken.

## Why it spread

```
12 May: release with latent bug ──► 27 days of normal traffic, no symptoms
                                          │
8 Jun 09:47: customer pushes valid config │ (a combination nobody had tested)
        │                                 ▼
        └── config distributed to every POP ──► each server hits the bug ──► errors
                                                    │
                       85% of the network ◄─────────┘  serving errors for *all* customers
```

The important part: **one customer's config affected every customer.** The servers that handled this customer's
traffic also handled everyone else's, so when they failed, everyone's sites failed. There was no isolation between
tenants in the failure path.

Also, the bug was in the **software**, but the trigger arrived as **config**. Software releases are usually staged
and watched. Customer config changes are pushed to the whole network by design, because customers expect them to
take effect at once.

## Why recovery took as long as it did

It didn't take long, and that is worth studying:

- **Detection in 1 minute**, thanks to good global monitoring.
- **About 40 minutes to find the trigger.** The hard part was linking errors everywhere to one customer's change among
  many.
- **Disabling that config** was the fix. Recovery started 9 minutes after it was identified.
- The real code fix came about seven hours later, rolled out carefully, because the immediate danger had already been
  removed.

## What Fastly changed

Fastly's post committed to:

- Deploying the bug fix across the network as quickly and safely as possible (started 17:25 the same day).
- A full post mortem of the incident response.
- Finding out why the bug wasn't caught in quality assurance and testing.
- Evaluating ways to improve remediation time.

## The general lesson

- **Latent bugs wait for the right input.** A release can look healthy for weeks. Staged rollouts catch bugs that
  common traffic triggers; they don't catch bugs that need a rare config. Fuzzing and config-combination testing help.
- **Isolate tenants' blast radius.** One customer's config should, at worst, break that customer. Ideas:
  - Apply new customer configs to a **canary** set of servers first, and roll back automatically if they crash.
  - **Shuffle sharding:** each customer is served by a different subset of servers, so one bad config can't take down
    every server.
  - **Cells:** split the network into independent groups that don't share the same failure.
- **Fast identification needs a change log.** "What changed in the last 5 minutes?" should be one query, across code
  and config, with a one-click disable.
- **Mitigate first, fix later.** Turning off the trigger restored service in minutes; the code fix could wait hours.

## Try it

Shrink a blast radius. You run a CDN with 1,000 servers in 50 POPs. Every server serves every customer, and customer
config changes reach all servers in 10 seconds. Propose two changes that limit how many customers one bad config can
hurt, and estimate the effect.

<details>
<summary>Reference</summary>

1. **Canary config rollout:** apply each customer config change first to 1 server per POP (5% of servers) for 60 s,
   watching crash and error rates; roll back automatically on any crash. A crashing config now takes down at most 5%
   of capacity for a minute, instead of 100%. Cost: config changes take about a minute instead of 10 s.
2. **Shuffle sharding:** assign each customer to a random 8 of 20 server groups per POP. A config that crashes its
   servers hurts only those 8 groups; other customers whose groups don't overlap fully are untouched, and most
   customers still have healthy groups to fail over to.
3. **Process isolation** (optional): parse and validate configs in a separate process or sandbox, so a crash while
   loading kills one worker, not the server.

Together these turn "85% of the network down" into "one customer degraded for a minute."
</details>

# Cloudflare, Nov 2025: a file that doubled

On 18 November 2025 a large share of the web returned Cloudflare error pages for about three hours. Nobody pushed bad
code. A routine database permission change made a generated file twice as big as usual, and the core proxy on every
Cloudflare server crashed when it read it.

## What users saw

- HTTP 5xx error pages on sites behind Cloudflare, saying the failure was inside Cloudflare's network.
- Turnstile (Cloudflare's CAPTCHA replacement) failed to load, so most people couldn't log in to the Cloudflare
  dashboard to see what was going on.
- Workers KV and Cloudflare Access failed too, because their front ends run through the same core proxy.
- Errors came and went every few minutes at first, then became solid.

## Timeline (UTC)

| Time | Event |
|------|-------|
| 11:05 | ClickHouse database permission change deployed |
| 11:28 | Errors on customer HTTP traffic begin |
| 11:31 | First automated test detects the problem |
| 11:35 | Incident call opened; early suspicion of a large DDoS attack |
| 13:05 | Workers KV and Access moved off the failing proxy path; impact reduced |
| 13:37 | Work focuses on rolling the Bot Management file back to a known-good version |
| 14:24 | Generation and propagation of new Bot Management files stopped; old file tested |
| 14:30 | Known-good file deployed globally; main impact over |
| 17:06 | All downstream services restarted; incident closed |

## The trigger

Cloudflare's Bot Management uses a machine-learning model that reads a **feature file**: a list of signals used to
score each request. A query on a ClickHouse cluster regenerates the file every five minutes and the file is pushed to
every server in the network.

At 11:05 a permission change let users see table metadata in a second database (`r0`) as well as `default`. The
feature query didn't filter by database name, so every feature now appeared **twice**. The file doubled.

The proxy pre-allocates memory for at most **200 features**; Cloudflare normally used about 60. The doubled file went
past the limit. The new Rust proxy (FL2) treated that as an error and called `unwrap()` on it, which panics:

```
thread fl2_worker_thread panicked: called Result::unwrap() on an Err value
```

## Why it spread

```
ClickHouse (permission change rolling out node by node)
      │ query every 5 min, no "WHERE database = 'default'"
      ▼
feature file: ~60 features ──► duplicated rows ──► over the 200 limit
      │ pushed to the whole network in minutes (config, not code: no staged rollout)
      ▼
every server's proxy reads it ──► panic ──► 5xx for every request it handles
      │
      ├─► Workers KV, Access (front ends on the same proxy) fail
      └─► Turnstile fails ──► dashboard login fails
```

Two details made it confusing:

- **The flapping.** The permission change was rolling out across the ClickHouse cluster. Each five-minute run hit
  either an updated node (bad file) or an old one (good file), so the network failed, recovered and failed again. That
  looked like an attack, not a bug.
- **The status page went down too.** It is hosted outside Cloudflare, and its failure was a coincidence, but it made
  responders more confident they were being attacked.

The older proxy (FL) didn't crash. It gave every request a bot score of zero instead, so customers with rules that
block bots saw real users blocked.

## Why recovery took as long as it did

- The first hour and a half went to the wrong theory (a DDoS) because of the flapping and the status page.
- Once the file was suspected, they had to **stop the generator** first. Rolling back the file alone would have been
  undone within five minutes by the next run.
- After the core fix at 14:30, services such as the dashboard had a backlog of logins and retries to work through.
  Full recovery came at 17:06.
- Debugging systems added load: enriching uncaught errors with debug data used a lot of CPU and raised latency.

## What Cloudflare changed

1. Treat **Cloudflare-generated configuration files like user input**: validate them before they are loaded.
2. Add more **global kill switches** for features.
3. Stop core dumps and error reporting from **eating the resources** of a struggling system.
4. Review **failure modes** for error conditions across all core proxy modules.

## The general lesson

- **Generated config is input, and input can be wrong.** A file your own pipeline produces still needs a size check,
  a schema check and a sane-diff check ("twice as many rows as last time?") before it ships.
- **Config rollouts need stages too.** Code went through canaries; this file reached everything in minutes. See the
  [staged rollout simulation](#/sims/staged-rollout).
- **Fail safe on bad input.** On an oversized file, the right move was "keep the last good file and alert," not
  "crash the process." The old proxy degraded; the new one died.
- **Hard limits are fine; crashing on them isn't.** The 200-feature cap was a sensible guard. Hitting it should be a
  rejected update, not an outage.

Compare this with Cloudflare's 2019 outage (lesson 24.3), where a WAF rule went global without staging, and Google
Cloud's June 2025 outage (lesson 24.13), where globally replicated bad data hit a code path with no error handling.

## Try it

Add a guard rail to a config pipeline. A job regenerates a 2 MB routing file every five minutes and pushes it to
3,000 servers. Write the checks you would add, and say what happens when one fails.

<details>
<summary>Reference</summary>

At the **producer** (before publishing):
- Schema check; row count and file size within limits that match the consumers' hard limits.
- Diff check against the last published file: refuse if rows changed by more than, say, 20%, or if there are
  duplicate keys. Page a human instead of publishing.

In the **rollout**:
- Ship to a canary group first (1% of servers, one region), watch error rate and crash counts for a few minutes,
  then widen in stages. Automatic halt and rollback on regression.

At the **consumer** (each server):
- Validate before swapping in. On failure keep serving with the **last known-good** file, report the error and never
  crash.

And a **kill switch** that freezes the pipeline so a rollback isn't overwritten by the next run.
</details>

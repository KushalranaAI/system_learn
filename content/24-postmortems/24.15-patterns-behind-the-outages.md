# Patterns behind the outages

Thirteen outages over thirteen years. The triggers were all different: a permission change, a regex, a
data file, a race, a typo, a maintenance command, `rm -rf`, a 43-second network blip, a new Consul feature, a
customer's config, a holiday, a blank field and a missed server. The **ways they grew** were not different at all.
This lesson pulls out the patterns, so you can look for them in your own system before they find you.

Knight's row is empty on purpose: its patterns (partial deploy, dead code, no kill switch) are the deploy hygiene
basics below. Most rows have three or more marks. Outages are chains.

## Pattern 1: the global push

The single biggest pattern. **Code** usually goes through canaries; **config, content, rules, policy and metadata**
often don't, because they are "just data" and need to move fast. Cloudflare (twice), CrowdStrike, Fastly and Google
Cloud all went global in seconds to minutes.

```
code:   build ─► canary 1% ─► 10% ─► 50% ─► 100%      (watched, automatic rollback)
config: write ──────────────────────────────► 100%    (seconds, everywhere)
```

Fix: anything that changes behaviour gets stages, health checks between them, and automatic halt. Keep a fast path
for emergencies, used rarely. Play with it in the [staged rollout simulation](#/sims/staged-rollout).

## Pattern 2: new code paths with no flag

Google's Service Control and CrowdStrike's 21st field both shipped code that **wasn't exercised** until data arrived
later. The binary rollout was staged; the behaviour wasn't. Knight's reused flag is the same idea in reverse.

Fix: new behaviour behind a flag that defaults to off; turn it on in stages; never reuse a flag.

## Pattern 3: crash on bad input

Cloudflare's proxy `unwrap()`, CrowdStrike's out-of-bounds read, Google's null pointer, Fastly's latent bug: each time
one bad input took down the process, and because every server got the same input, every server died together.

Fix: validate at the producer **and** the consumer. On bad input, keep the last known-good version and alert. Bound
the cost of input too (Cloudflare's regex).

## Pattern 4: retries, herds and reconnect storms

Recovery is a load spike. AWS's DWFM collapsed renewing every lease at once; Google's restarts stampeded Spanner;
Roblox let players back 10% at a time to avoid it; Facebook brought power and traffic back in steps.

Fix: exponential backoff with jitter, retry budgets, load shedding ([lesson 12.2](#/lesson/12.2)), circuit breakers
([lesson 12.3](#/lesson/12.3)), and admit traffic gradually after an outage ([lesson 3.6](#/lesson/3.6)).

## Pattern 5: automation that amplifies

Systems designed to heal react to symptoms, and in a broad failure the symptoms lie. Slack's autoscaler removed
servers because CPU was low; AWS NLB removed healthy capacity; Facebook's DNS sites all withdrew; GitHub's failover
promoted across the country.

Fix: rate limits and floors on automation ("never remove more than X% per minute," "never withdraw the last route"),
and a way for humans to freeze it ([lesson 4.7](#/lesson/4.7), [lesson 5.4](#/lesson/5.4)).

## Pattern 6: hidden and circular dependencies

The status page on S3. Monitoring on Consul. Internal tools behind Cloudflare Access. Dashboards across a Transit
Gateway. Badge readers on the production network. Every one was discovered during the outage.

Fix: draw the dependency graph, especially for the things you need **during** an outage: monitoring, alerting,
status page, deploy and rollback, login, out-of-band access. Put them on separate infrastructure and test them in
game days ([lesson 18.6](#/lesson/18.6)).

## Pattern 7: blast radius and cells

When one config, one cluster or one region serves everything, every failure is total. The fix the companies reached
for again and again is **cells**: independent copies of the system, each serving a slice of users, so a failure hits
one slice ([lesson 23.9](#/lesson/23.9), [lesson 23.11](#/lesson/23.11)). AWS partitioned S3's index into cells;
Roblox split Consul; GitHub moved to active/active/active; Fastly-style shared tenancy needs canaries per tenant or
shuffle sharding.

```
one big system:  [ all users ] ── one bad change ──► 100% down
cells:           [ cell 1 ][ cell 2 ][ cell 3 ][ cell 4 ] ── bad change in cell 1 ──► 25% down (and a canary)
```

## Pattern 8: recovery nobody practised

S3's index hadn't been cold-restarted in years. GitLab had never restored a backup. Roblox's cache deploy tool
couldn't start from nothing. AWS had no procedure for DWFM congestive collapse. Knight had no incident procedure and
its rollback made things worse.

Fix: practise restore, cold start and rollback on a schedule. Measure real RTO and RPO ([lesson 5.5](#/lesson/5.5)).

## What the companies changed, in common

| Change | Who |
|--------|-----|
| Staged rollouts for config / content / data | Cloudflare, CrowdStrike, Google |
| Feature flags and kill switches | Cloudflare, Google |
| Validate generated or replicated data | Cloudflare, CrowdStrike, Google |
| Safety limits on tools and automation | AWS (S3 tool, NLB velocity), GitHub (no cross-region promotion) |
| Jittered backoff, throttled recovery | AWS, Google |
| Monitoring and status off the main stack | AWS, Roblox, Slack, Google |
| Cells / splitting shared clusters | AWS S3, Roblox, GitHub |
| Tested restores and drills | GitLab, Facebook |

## Try it

Score your system against the patterns. For a system you work on (or a design from an earlier lab), give one point
for each "yes":

1. Config, rules and feature data go through staged rollout with automatic halt.
2. New code paths ship behind flags, off by default.
3. Every consumer of generated or replicated data validates it and falls back to last known-good.
4. All clients and services retry with jittered backoff and a retry budget.
5. Autoscalers, failover and health-check removal have rate limits and floors.
6. Monitoring, alerting, status page and deploy tooling don't depend on production.
7. The system is split into cells or shards so one bad change can't hit everyone.
8. You have restored from backup and cold-started the system in the last quarter.
9. There is a kill switch for every major feature, and on-call has used it in a drill.
10. Deploys verify every host's version before enabling new behaviour.

<details>
<summary>Reference</summary>

- **8–10:** you have learned from other people's outages. Keep drilling.
- **5–7:** typical for a growing company. Your next big outage is probably in the "no" rows; start with 1, 6 and 8,
  which appear most often in this module.
- **0–4:** pick the cheapest wins first: a backup restore test (8), an external uptime probe and status page on
  another provider (6), and jittered backoff in your HTTP client library (4). Then build staged config rollout (1).

For each "no," name the incident from this module that shows what it costs. That makes the case to your team far
better than a checklist does.

## Key takeaways

- Triggers are small and varied; the ways outages grow are few and repeat.
- Stage everything that changes behaviour, including config and data, and put new code behind flags.
- Bad input should be rejected, not crash every server at once.
- Recovery is its own load spike: jitter, throttle and re-admit gradually.
- Keep the tools you need during an outage off the systems that fail; use cells to cap blast radius.
- Practise the recovery you hope never to need.

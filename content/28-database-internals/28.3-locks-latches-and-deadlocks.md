# Locks, latches and deadlocks

MVCC (lesson 28.2) lets readers and writers ignore each other. Writers still have to coordinate with other writers,
and schema changes have to coordinate with everyone. That's what locks do, and their queues are behind some of the
most confusing outages: a "harmless" `ALTER TABLE` that freezes the whole application.

## Locks vs latches

| | Locks | Latches (Postgres: LWLocks, spinlocks) |
|-|-------|----------------------------------------|
| Protect | Logical things: rows, tables | In-memory structures: a buffer page, a hash table |
| Held for | Until the transaction ends | Microseconds, while touching the structure |
| Deadlock handling | Detected and broken by the database | Avoided by strict acquisition order in the code |
| Visible to you | `pg_locks`, `SHOW ENGINE INNODB STATUS` | Wait events (`LWLock:BufferContent`), mostly a sign of hot pages |

You control locks through SQL. Latch contention shows up as CPU-bound slowness on a few hot pages (e.g. every insert
hitting the right-most leaf of a sequential index) and is fixed by changing access patterns, not with SQL.

## Row locks

- `UPDATE`/`DELETE` lock the rows they change; other writers to those rows wait until commit or rollback.
- `SELECT ... FOR UPDATE` locks rows you intend to change; `FOR SHARE` lets others read-lock but not write.
- `FOR UPDATE SKIP LOCKED` skips rows someone else holds, which makes a table usable as a job queue; `NOWAIT` errors
  instead of waiting.

Postgres records row locks in the tuple itself (its `xmax`), not in a shared lock table, so locking a million rows
doesn't exhaust memory. InnoDB locks **index records**, and at Repeatable Read also the **gaps** between them, so a
range `UPDATE ... WHERE created_at < X` can block inserts into that range.

## Table locks and the lock queue

Every statement takes a table-level lock too. Postgres has eight modes; the ones that matter:

| Statement | Lock mode | Conflicts with |
|-----------|-----------|----------------|
| `SELECT` | ACCESS SHARE | Only ACCESS EXCLUSIVE |
| `INSERT/UPDATE/DELETE` | ROW EXCLUSIVE | SHARE and stronger (e.g. non-concurrent `CREATE INDEX`) |
| `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE | Other schema changes, VACUUM |
| Most `ALTER TABLE`, `DROP`, `TRUNCATE` | **ACCESS EXCLUSIVE** | **Everything**, including plain `SELECT` |

Locks are granted in **queue order**. The classic outage:

```
10:00:00  analytics job: SELECT ... FROM orders (runs 10 minutes)    holds ACCESS SHARE
10:02:00  migration: ALTER TABLE orders ADD COLUMN note text          wants ACCESS EXCLUSIVE → waits
10:02:01  app: SELECT * FROM orders WHERE id = 7                     wants ACCESS SHARE → queues behind ALTER
10:02:01… every app query on orders queues; connection pool fills; site is down
10:10:00  analytics finishes → ALTER runs in 5 ms → queue drains
```

The `ALTER` itself would have been instant. Waiting in line made it block everyone. Defence: set a **lock timeout**
on migrations and retry:

```sql
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN note text;   -- fails fast instead of blocking the queue
```

Also set `statement_timeout` and `idle_in_transaction_session_timeout` for app and reporting users, so long or
forgotten transactions can't hold locks indefinitely.

## Deadlocks

Two transactions each hold a lock the other needs:

```
tx 1: UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- locks row 1
tx 2: UPDATE accounts SET balance = balance - 50  WHERE id = 2;   -- locks row 2
tx 1: UPDATE accounts SET balance = balance + 100 WHERE id = 2;   -- waits for tx 2
tx 2: UPDATE accounts SET balance = balance + 50  WHERE id = 1;   -- waits for tx 1 → cycle
```

Neither can proceed. Databases detect this by building a **wait-for graph** (transaction → transaction it waits on)
and looking for a cycle:

- **Postgres** waits `deadlock_timeout` (default 1 s) before checking, because most waits resolve on their own and
  the check is expensive. It then aborts one transaction with SQLSTATE `40P01`.
- **InnoDB** checks immediately on each wait (by default) and rolls back the transaction that has done the least work.
  Plain waits time out after `innodb_lock_wait_timeout` (default 50 s).

Deadlocks are not corruption; they're a normal, retryable error. But frequent ones mean wasted work and latency.

## Preventing them

1. **Lock in a consistent order.** Transfers always lock the lower account ID first:
   `SELECT ... FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;`
2. **Keep transactions short.** No network calls or user think-time inside a transaction.
3. **Lock everything up front** when you can, instead of escalating midway.
4. **Retry** on `40P01` / `ER_LOCK_DEADLOCK` with a small random backoff (lesson 12.2), and make the work idempotent.

## Try it

Untangle this Postgres log. What happened, and how would you change the code?

```
ERROR:  deadlock detected
DETAIL: Process 4121 waits for ShareLock on transaction 9002; blocked by process 4188.
        Process 4188 waits for ShareLock on transaction 9001; blocked by process 4121.
        Process 4121: UPDATE inventory SET qty = qty - 1 WHERE sku = 'B-200'
        Process 4188: UPDATE inventory SET qty = qty - 1 WHERE sku = 'A-100'
HINT:   See server log for query details.
CONTEXT: while updating tuple (12,7) in relation "inventory"
```

<details>
<summary>Reference</summary>

Two checkouts, each decrementing stock for the same two SKUs in different orders. Process 4121 (transaction 9001)
already updated `A-100` and now wants `B-200`; process 4188 (transaction 9002) already updated `B-200` and now wants
`A-100`. ("Waits for ShareLock on transaction X" is how Postgres shows "waits for X to finish so I can lock the row it
holds".) Cycle → Postgres aborted one after `deadlock_timeout`.

Fix: lock order. Sort the cart's SKUs before updating (`ORDER BY sku`, or one statement:
`UPDATE inventory SET qty = qty - 1 WHERE sku = ANY($1)` after `SELECT ... WHERE sku = ANY($1) ORDER BY sku FOR UPDATE`).
Keep the transaction short, and retry on `40P01` in case other code paths still lock in a different order.
</details>

## Key takeaways

- Locks protect logical data for a transaction; latches protect memory structures for microseconds.
- ACCESS EXCLUSIVE waits in the same queue as everyone else, so a waiting `ALTER` blocks all later queries; use
  `lock_timeout`.
- Deadlocks are cycles in the wait-for graph; the database kills one transaction, and you retry.
- Consistent lock ordering and short transactions prevent most deadlocks.

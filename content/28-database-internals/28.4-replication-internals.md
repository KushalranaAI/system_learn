# Replication internals

Lessons 5.3 and 13.2 covered *why* you replicate and what leader–follower replication looks like from outside. This
lesson opens the pipe: what exactly travels from primary to replica, how the primary knows what a replica still
needs, and which method to pick when you need to move a live database somewhere else.

## Everything starts with the log

Every change is written to a log before it's applied to data pages (the write-ahead log, lesson 26.13). Replication
means shipping that log, or something derived from it, to another machine and replaying it. Positions in the log are
**LSNs** (log sequence numbers) in Postgres, e.g. `0/3A0001F8`; in MySQL they are binlog file + offset, or **GTIDs**.

Three families:

| Method | What's shipped | Replica is | Examples |
|--------|----------------|------------|----------|
| **Physical** (WAL shipping, streaming) | Byte-level page changes ("in block 4711 of file 16384, at offset 96, write these bytes") | An exact copy, same major version, read-only | Postgres streaming replication |
| **Logical** | Row changes ("INSERT into orders (id=7, total=30)") | Any database that can apply them; can differ in version, schema, subset | Postgres logical replication, MySQL row-based binlog, Debezium CDC |
| **Statement** | The SQL text | Re-executes it | MySQL statement-based binlog (legacy) |

## Physical streaming, traced

```
client: UPDATE accounts SET balance = 400 WHERE id = 7;  COMMIT;

primary:  WAL record at LSN 0/3A0001F8: heap update, rel 16384, block 52, new tuple…
          COMMIT record at LSN 0/3A000240
          walsender streams bytes up to 0/3A000240 to the replica

replica:  walreceiver writes them to its own WAL       → reports write_lsn
          fsyncs                                         → reports flush_lsn
          startup process replays them onto pages       → reports replay_lsn
```

`pg_stat_replication` on the primary shows those three positions for each replica; lag is the gap between the
primary's current LSN and each one, in bytes and in time.

**Synchronous** replication makes `COMMIT` wait until a replica reports (depending on `synchronous_commit`) that it has
received, flushed or applied the record: no data loss on failover, but every commit pays a network round trip, and
if the sync replica dies, commits stall unless another is listed.

Physical replication is simple and complete (schema changes, indexes, everything is copied), but the replica must run
the same major version and the same architecture, and you can't replicate one table or one database.

## Logical replication

Postgres **decodes** WAL into row changes through a logical decoding plugin (`pgoutput`, `wal2json`):

```sql
-- on the source
CREATE PUBLICATION shop_pub FOR TABLE orders, customers;
-- on the target (could be a newer Postgres version)
CREATE SUBSCRIPTION shop_sub CONNECTION '...' PUBLICATION shop_pub;
```

The subscriber copies the existing rows, then streams changes. What it **doesn't** do in Postgres's built-in version:
replicate DDL (schema changes must be applied to both sides by you), sequence values, or large objects. Tables need a
primary key (or a replica identity) so updates and deletes can find the row.

MySQL's **binlog** in `ROW` format is the same idea and is what tools like Debezium read for change data capture
(lesson 17.3). `STATEMENT` format is smaller but replays non-deterministic SQL (`NOW()`, `UUID()`, `LIMIT` without
`ORDER BY`) differently on the replica; avoid it.

## Replication slots: the primary's memory of consumers

The primary deletes old WAL once it's no longer needed. But how does it know a replica that disconnected 10 minutes
ago, or a CDC connector, has consumed it? A **replication slot** records each consumer's confirmed position, and the
primary keeps all WAL after the oldest slot position.

This is the failure mode:

```
Mon 09:00  Debezium connector for analytics created with a logical slot
Fri 17:00  connector crashes; nobody notices
           primary keeps all WAL since Friday: 40 GB/hour of writes
Sun 03:00  disk full → primary stops accepting writes → outage
```

An abandoned slot also holds back VACUUM's horizon for the catalog (lesson 28.5). Defences: alert on
`pg_replication_slots` lag in bytes, set `max_slot_wal_keep_size` (Postgres 13+) so a lagging slot is invalidated
instead of filling the disk, and drop slots you no longer use.

## When replication goes wrong

- **Replica conflicts:** a long query on a hot standby needs rows that replay wants to remove; Postgres cancels the
  query after `max_standby_streaming_delay`, or with `hot_standby_feedback` the primary keeps those rows (more bloat).
- **Split brain:** two nodes both believe they're primary after a failover (lesson 13.3). Fencing matters.
- **Rebuilding a replica** means copying the whole database first (`pg_basebackup`). On a multi-terabyte database that
  takes hours, during which you have one less copy. GitLab's January 2017 outage started with a replica that had
  fallen too far behind and needed exactly this resync ([lesson 31.8](#/lesson/31.8)).

## Choosing a method for a migration

| Goal | Method |
|------|--------|
| HA standby, read replicas | Physical streaming (sync for one replica if no data loss is acceptable) |
| Major version upgrade with minimal downtime | Logical replication old → new, then switch over |
| Move to a different database engine or into a warehouse/search index | CDC (logical decoding / binlog → Debezium → Kafka) |
| Copy a subset of tables or split a database | Logical replication of selected tables |

## Try it

You must move a 2 TB Postgres 12 database to a new cluster on Postgres 17, in a different cloud account, with at most
a minute of write downtime. Pick a replication method and outline the cutover.

<details>
<summary>Reference</summary>

Physical replication can't cross major versions, so use **logical replication**:

1. Create the schema on the new cluster (`pg_dump --schema-only`), without secondary indexes at first to speed the
   initial copy (add them before cutover).
2. `CREATE PUBLICATION` for all tables on the old primary; check every table has a primary key or replica identity.
3. `CREATE SUBSCRIPTION` on the new cluster; wait for the initial copy, then for lag to stay near zero. Monitor the
   slot so WAL doesn't pile up on the old primary.
4. Freeze schema changes (DDL isn't replicated) for the duration.
5. Validate: row counts and checksums on sample ranges; run read traffic against the new cluster.
6. Cutover: stop writes (app in read-only mode or pause the writers), wait until the subscriber has caught up to the
   old primary's final LSN, **copy sequence values** (`setval` to above the old maximums), point the app at the new
   cluster, resume writes. Seconds to a minute.
7. Keep reverse replication (new → old) or at least the old cluster for a rollback window; then drop the slot.
</details>

## Key takeaways

- Replication ships the log: physical (bytes, exact copy, same version) or logical (row changes, flexible).
- Replicas report write, flush and replay positions; lag is the distance in the log.
- Slots make the primary keep WAL for every consumer; an abandoned slot can fill the disk.
- Use logical replication or CDC for upgrades and migrations, physical for HA and read replicas.

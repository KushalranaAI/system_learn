# MVCC and isolation under the hood

How can one transaction read a table while another is updating it, without either waiting? **Multi-version
concurrency control**: writers create new versions of rows instead of overwriting them, and each reader sees the
versions that were committed as of its **snapshot**. Readers never block writers, writers never block readers. This
lesson shows the machinery in PostgreSQL and where it leaves gaps.

## Row versions in PostgreSQL

Every row version (a **tuple**) carries hidden header fields:

| Field | Meaning |
|-------|---------|
| `xmin` | ID of the transaction that created this version |
| `xmax` | ID of the transaction that deleted or replaced it (0 if still live) |
| `ctid` | Physical location; an updated tuple points to its newer version |

Transaction IDs (XIDs) increase. An `UPDATE` is really "mark the old version dead (set xmax) + insert a new version".

```
                       xmin  xmax  data
INSERT (tx 100)   →    100   0     balance=500
UPDATE (tx 205)   →    100   205   balance=500     (old version)
                       205   0     balance=400     (new version)
```

You can see it: `SELECT xmin, xmax, ctid, * FROM accounts;`.

## Snapshots

When a snapshot is taken, Postgres records:

- `xmin`: the oldest transaction still running; everything below it is finished.
- `xmax`: the next XID to be assigned; everything at or above it hasn't started.
- `xip`: the list of in-progress XIDs between them.

A tuple is **visible** to a snapshot if its creator committed before the snapshot and its deleter didn't:

```
visible(tuple) =
      xmin committed  AND  xmin not in xip  AND  xmin < snapshot.xmax
  AND (xmax = 0  OR  xmax aborted  OR  xmax in xip  OR  xmax >= snapshot.xmax)
```

Trace with snapshot `{xmin: 200, xmax: 210, xip: [205, 207]}`:

| Tuple | xmin | xmax | Visible? | Why |
|-------|------|------|----------|-----|
| balance=500 | 100 | 205 | **yes** | Created long ago; deleter 205 is still in progress |
| balance=400 | 205 | 0 | no | Creator 205 hadn't committed when the snapshot was taken |

So this reader sees 500, even if 205 commits a millisecond later. Commit status lives in the commit log (`pg_xact`),
cached on the tuple as hint bits after the first check.

MySQL InnoDB does the same thing differently: it updates the row in place and keeps the old versions in **undo
logs**; a reader whose **read view** shouldn't see the change follows the undo chain back to an older version.

## Isolation levels are snapshot policies

| Level (Postgres) | Snapshot taken | Prevents | Still allows |
|------------------|----------------|----------|--------------|
| Read Committed (default) | **Per statement** | Dirty reads | Non-repeatable reads, lost updates in read-modify-write code, write skew |
| Repeatable Read | **Once per transaction** (snapshot isolation) | Non-repeatable reads, phantoms, lost updates (second writer gets a serialization error) | **Write skew** |
| Serializable | Per transaction + **SSI** tracking of read/write dependencies | All anomalies; aborts one transaction of a dangerous pattern | Nothing, but you must retry aborts |

When two transactions update the same row, the second **waits** for the first. Under Read Committed it then re-reads
the new version and proceeds; under Repeatable Read it fails with `could not serialize access due to concurrent
update`.

## Write skew: the doctors

A hospital rule: at least one doctor must be on call. Alice and Bob are both on call and both feel ill, and both click
"go off call" at the same moment. Each transaction runs:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM doctors WHERE on_call AND shift = 1;   -- returns 2
-- app: 2 ≥ 2, so it's safe for me to leave
UPDATE doctors SET on_call = false WHERE name = 'alice';     -- Bob's tx updates 'bob'
COMMIT;
```

```
tx A (Alice)                      tx B (Bob)
snapshot: alice ✓ bob ✓          snapshot: alice ✓ bob ✓
count = 2                         count = 2
UPDATE alice → off                UPDATE bob → off
COMMIT ✓                          COMMIT ✓
                → nobody on call
```

Neither transaction wrote a row the other wrote, so there's no write–write conflict to detect. Each read a snapshot
that was true at the time; the *combination* violates the rule. That's **write skew**, and snapshot isolation allows
it. Booking the last seat via a count, claiming a username via "does it exist?", and double-spending from two accounts
with a joint limit are the same shape.

Fixes:

1. **Serializable**: SSI notices A read what B wrote and vice versa, and aborts one with SQLSTATE `40001`. The app
   retries; the retry sees one doctor on call and refuses.
2. **Lock what you read**: `SELECT ... FROM doctors WHERE on_call AND shift = 1 FOR UPDATE;` B blocks until A commits,
   then (Read Committed) re-checks and sees only one.
3. **Materialise the conflict**: a row per shift that both transactions must update (`UPDATE shifts SET ... WHERE id =
   1`), turning write skew into an ordinary write–write conflict.
4. **Constraint**: where possible express the rule as a database constraint so the database enforces it.

## The cost of versions

Old versions don't disappear on their own. Postgres needs **VACUUM** to reclaim them, and a long-running transaction
holds back the horizon for every table (lesson 28.5). InnoDB's undo logs grow during long transactions the same way.

## Key takeaways

- MVCC keeps multiple row versions; a snapshot (xmin, xmax, in-progress list) decides which one each reader sees.
- Postgres stores versions in the table (xmin/xmax); InnoDB rebuilds old versions from undo logs.
- Read Committed snapshots per statement; Repeatable Read per transaction; Serializable adds dependency tracking.
- Snapshot isolation allows write skew; fix with Serializable + retries, `FOR UPDATE`, or a materialised conflict.

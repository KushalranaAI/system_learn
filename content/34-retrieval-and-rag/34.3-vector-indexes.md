# Vector indexes

You have 100 million embeddings and a query vector. You want the 10 nearest. A B-tree can't help: there is no sort
order for "close in 1,024 dimensions". This lesson covers the index structures that make nearest-neighbour search
fast, and the dial they all share: **recall versus latency and memory**.

## Exact search is a full table scan

Exact (brute-force, "flat") k-NN compares the query with every vector:

```
100M vectors × 768 dims = 7.7 × 10^10 multiply-adds per query
data to read: 100M × 768 × 4 B = 307 GB  → seconds per query on CPU
```

Flat search is perfect for small sets (up to roughly a million vectors, or a filtered subset) and is the ground truth
you measure approximate indexes against. Beyond that you use **approximate nearest neighbour (ANN)** search: give up
a little accuracy for orders of magnitude of speed.

**Recall@k** is the metric: of the true 10 nearest neighbours, how many did the index return? Recall@10 = 0.95 means
on average 9.5 of 10. Production systems typically target 0.9-0.99.

## HNSW: a navigable graph

Hierarchical Navigable Small World graphs (Malkov and Yashunin) connect each vector to its nearby vectors, in layers:

```
layer 2:   A ─────────────────── K                  few nodes, long hops
layer 1:   A ───── E ───── H ─── K ───── P
layer 0:   A─B─C─D─E─F─G─H─I─J─K─L─M─N─O─P─Q        every node, short links
search: enter at the top, greedily move toward the query, drop a layer, repeat
```

Like a skip list ([lesson 26.12](#/lesson/26.12)) but in vector space. A query visits a few hundred to a few thousand
nodes instead of 100 million.

| Parameter | Effect |
|-----------|--------|
| `M` (links per node, e.g. 16-64) | Higher → better recall, more memory, slower build |
| `efConstruction` (e.g. 100-400) | Higher → better graph, slower build |
| `efSearch` (candidate list at query time, e.g. 50-500) | **The runtime dial**: higher → better recall, higher latency |

Trade-offs: the default in most vector databases (pgvector, Qdrant, Weaviate, Milvus, Elasticsearch/OpenSearch).
Excellent recall and latency (single-digit milliseconds), supports inserts. But it wants **everything in RAM**: the
vectors plus about `2 × M × 4 B` of links per vector. Deletes are usually tombstones, so heavy churn degrades it until
you rebuild. Builds of 100M vectors take hours.

## IVF: cluster, then search a few clusters

An inverted file index runs k-means to split the vectors into `nlist` clusters. At query time, find the `nprobe`
closest cluster centres and scan only those clusters.

```
nlist = 65,536 clusters of ~1,500 vectors (for 100M)
nprobe = 32  → scan ~50,000 vectors instead of 100,000,000  (2,000x less work)
```

`nprobe` is the runtime dial. A common starting point is `nlist` on the order of `sqrt(N)` to `16 × sqrt(N)`. IVF is
cheap in memory (just the cluster centroids on top of the vectors), fast to build, and easy to shard and to put on
GPUs. Its weakness: a query near a cluster boundary can miss neighbours in the next cluster unless `nprobe` is raised.

## Product quantisation: compress the vectors

Even IVF still stores and scans full vectors. **Product quantisation (PQ)** compresses them:

```
768-dim vector ─► split into m = 96 sub-vectors of 8 dims
each sub-vector ─► replaced by the ID (1 byte) of its nearest of 256 learned centroids
3,072 bytes (float32) ─► 96 bytes        32x smaller
```

Distances are then computed approximately from lookup tables, which is very fast. Combined as **IVF-PQ** (the FAISS
workhorse), 100M vectors fit in about 10 GB. The cost is recall: PQ distances are approximate, so systems fetch, say,
the top 200 by PQ distance and **re-rank** them with full-precision vectors kept in RAM, as float16, or on SSD.

**DiskANN**-style indexes take the same idea for graphs: compressed vectors in RAM, the full graph and vectors on SSD,
so billion-scale indexes run on one machine at a few milliseconds per query.

## Comparison

| Index | Memory for 100M × 768 | Latency | Recall | Build | Good for |
|-------|-----------------------|---------|--------|-------|----------|
| Flat | 307 GB | seconds | 1.0 | none | small sets, ground truth |
| HNSW | ~320 GB (RAM) | ~1-10 ms | 0.95-0.99 | hours | default when it fits in RAM |
| IVF-Flat | ~307 GB | ~5-20 ms | 0.9-0.99 (via nprobe) | fast | GPUs, simple sharding |
| IVF-PQ + re-rank | ~10 GB + re-rank store | ~5-20 ms | 0.85-0.95 | moderate | huge corpora, tight memory |
| DiskANN | ~10-30 GB RAM + SSD | ~2-10 ms | 0.95+ | slow | billion-scale on one node |

(Orders of magnitude; real numbers depend on hardware, dimensions and parameters. Benchmark on your data.)

## System-design concerns

- **Filtering.** "Nearest vectors where tenant = 42 and lang = 'de'": filtering after the ANN search can return
  nothing (all 10 results belonged to other tenants); filtering during the search is supported by most engines but
  slows down with very selective filters. Per-tenant indexes or partitions are the fix for strict isolation.
- **Sharding.** Split vectors across nodes; every query goes to every shard and the top-k are merged
  (scatter-gather, like a search index, [lesson 29.2](#/lesson/29.2)). The slowest shard sets the latency.
- **Replicas** for query throughput and availability, exactly like read replicas.
- **Freshness.** New vectors are searchable after insertion (HNSW) or after a segment flush and merge (many engines),
  typically seconds.
- **Do you need a separate vector database?** Under tens of millions of vectors, pgvector in your existing Postgres,
  or the vector features of your existing search engine, saves you an entire system to operate.

## Try it

Tune an index for **100M vectors of 768 dimensions**, 500 queries/s, p99 under 50 ms, recall@10 of at least 0.95, and
a filter on `tenant_id`. Machines have 256 GB of RAM.

<details>
<summary>Reference</summary>

**Option A, HNSW sharded in RAM.** ~320 GB (vectors + links at M=16) doesn't fit one machine. Use 4 shards of 25M
(~80 GB each, leaving headroom) and 2 replicas of each for throughput and failover: 8 machines. Tune `efSearch`
upward (e.g. 64 → 128 → 256) on a sample of queries with known exact neighbours until recall@10 ≥ 0.95, then check
p99 including scatter-gather across 4 shards. Use float16 vectors to halve memory and possibly drop to 2 shards.

**Option B, IVF-PQ with re-ranking.** PQ at 96 bytes/vector ≈ 10 GB, fits easily on one machine. nlist ≈ 65,536;
start nprobe at 32 and raise it. PQ alone may stall near 0.85-0.9 recall, so fetch the top 200 and re-rank with
float16 vectors (154 GB, in RAM) to reach 0.95+. Fewer machines (2-3 replicas), slightly more latency.

**Filter:** if tenants are large and few, partition by tenant; if many small ones, use the engine's filtered search
and fall back to flat search within the tenant when the filter is very selective.

**Decide by measuring** recall and p99 on a held-out query set for both; pick the cheaper one that meets the SLO.
</details>

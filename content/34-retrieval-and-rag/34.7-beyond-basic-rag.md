# Beyond basic RAG

Basic RAG makes **one** retrieval with the user's exact words and hopes the answer is in the top few chunks. That
works for "how do I reset my password?". It breaks for questions phrased badly, questions that depend on the
conversation, questions that need facts from several documents ("multi-hop"), and questions about the corpus as a
whole ("what are the main complaints this quarter?"). Each fix below buys quality with extra model calls, so each is
also a latency and cost decision.

## Query rewriting

The user's message is often a poor search query.

| Technique | What it does | Extra cost |
|-----------|--------------|------------|
| **Conversation condensing** | Rewrites "and for the pro plan?" into "What is the refund window for the Pro plan?" using the chat history | 1 small-model call |
| **Multi-query** | Generates 3-5 rephrasings, retrieves for each, fuses with RRF (34.5) | 1 call + N parallel searches |
| **Decomposition** | Splits "Compare the refund policy for EU and US customers" into two sub-queries | 1 call + N searches |
| **HyDE** (hypothetical document embeddings) | Has the model write a fake answer, embeds that, and searches with it, since answers look more like documents than questions do | 1 call before retrieval |
| **Filters from the query** | Extracts product, date range, language into metadata filters | 1 call or rules |

Use a small, fast model for rewriting (33.4): this step sits before the first token, so it adds directly to TTFT
(~100-500 ms). Run the resulting searches **in parallel**.

## Agentic retrieval

Instead of a fixed pipeline, give the model retrieval as a **tool** and let it decide what to search, read the
results, and search again:

```
question ─► LLM: "I need the contractor policy first" ─► search("contractor laptop policy")
         ◄─ results
         ─► LLM: "now who approves exceptions?"     ─► search("hardware exception approver")
         ◄─ results
         ─► LLM: answer with citations from both
```

This handles multi-hop and vague questions well, and can mix tools (vector search, SQL, a web search, an API). The
costs are the agent costs from module 35: every step is another model call, latency grows with the number of steps
(3 steps × ~1-2 s each), and runs can loop. Give it a **step limit**, a token budget per question, and a fallback to
the best answer so far. Many products use a router: plain RAG for simple questions, agentic retrieval only when the
first pass looks insufficient.

In the sandbox, the agent node models exactly this: each task makes `agentSteps` model calls and a vector lookup per
step if a vector DB is wired, and without a step limit a few percent of tasks run away.

## GraphRAG

Vector search retrieves passages that **look like** the question. It can't answer "what are the main themes across
all 10,000 support tickets?", because no single chunk contains the answer. **GraphRAG** (Microsoft Research, 2024)
builds structure at ingestion time:

```
INGEST: chunks ─► LLM extracts entities and relationships ─► knowledge graph
               ─► community detection (clusters of related entities) ─► LLM summarises each community
QUERY:  global question ─► map over community summaries ─► reduce to one answer
        local question  ─► find entities ─► walk their neighbourhood ─► retrieve linked chunks
```

| | Plain vector RAG | GraphRAG |
|---|-----------------|----------|
| Best for | Specific lookups | Corpus-wide "sensemaking" and relationship questions |
| Ingestion cost | Embedding only (cheap) | LLM calls over the whole corpus (far more expensive than embedding) |
| Freshness | Upsert a chunk | Graph and summaries need incremental or periodic rebuilds |
| Query cost | One search | Global queries can touch many summaries |

The ingestion bill is the design issue: an LLM pass over millions of chunks is a large batch job (use batch APIs and
a small model where quality allows). Lighter variants that defer graph work to query time exist, and so does the
simpler step of storing explicit relationships you already have (product → component → known issues) in a database
and joining them in code.

## Long context vs retrieval, revisited

With million-token windows, why not skip retrieval? Compare for one question over a 500k-token corpus:

| | Retrieve 5k tokens | Send all 500k tokens |
|---|-------------------|----------------------|
| Input cost | 1x | ~100x (less with prefix caching on a fixed corpus) |
| TTFT | well under a second | many seconds of prefill |
| Accuracy | limited by retrieval recall | limited by attention over long inputs; can miss facts mid-context |
| Permissions | filter per user | must build a per-user corpus |

Long context wins for one or a few documents used whole (a contract, a codebase subset, a meeting transcript), and as a
complement: retrieve generously (say 30-50 chunks or whole parent sections) instead of 5 snippets, since modern windows
can afford it. Retrieval still wins for large, changing, permissioned corpora.

## Picking an approach

```
single fact in one place ─────────────────────► basic hybrid RAG + reranker
follow-up in a conversation ──────────────────► + conversation condensing
needs facts from 2-3 documents ───────────────► decomposition, or agentic retrieval with a step limit
"across everything" themes and summaries ─────► GraphRAG or precomputed summaries (map-reduce batch job)
one big document the user brought ────────────► long context, cached prefix
```

## Try it

Your company's internal assistant gets questions like "**Which customers on the Enterprise plan are affected by the
bug fixed in release 4.2?**" Facts live in three places: release notes (wiki), a bug tracker, and a CRM. Pick an
approach for these multi-hop questions.

<details>
<summary>Reference</summary>

The question needs a chain: release 4.2 notes → which bug(s) → which component/feature → which customers use it and
are on Enterprise. No single chunk has the answer, so basic RAG fails.

- **Agentic retrieval with tools**, not one vector index: `search_wiki` (hybrid RAG over release notes),
  `get_bug(id)` (bug tracker API), and `query_customers(plan, feature)` (a read-only CRM query). Structured data
  stays structured: the customer list comes from a database query, not from embedding CRM records.
- **Limits:** a step limit (e.g. 6), a token budget, read-only tools, and the caller's permissions applied to every
  tool call.
- **Latency:** ~3-5 steps × 1-2 s ≈ 5-10 s. Stream progress ("Found bug #8812 in the 4.2 notes...").
- **Cheaper path for frequent patterns:** if "who is affected by bug X" is common, precompute bug → feature →
  customer joins in a batch job and expose one tool; the agent then needs 2 steps.
- **Not GraphRAG:** the relationships already exist as foreign keys in the tracker and CRM; extracting a graph from
  text with an LLM would be expensive and less accurate than joining real data.
- **Evaluate** with multi-hop questions in the golden set (34.6), checking each hop's evidence.
</details>

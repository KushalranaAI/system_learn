# Hybrid search and reranking

Vector search understands that "money back" means "refund". It is also surprisingly bad at things keyword search
finds trivially: an error code `E-4012`, a product SKU `X200-PRO`, a person's name, an exact phrase. Production
retrieval almost always combines both, then spends a little extra latency on a **reranker** to put the best passages
first. This is the most reliable quality upgrade in RAG.

## Two retrievers, two kinds of mistakes

| | Keyword (BM25) | Vector (embeddings) |
|---|----------------|---------------------|
| Matches | Exact terms, weighted by rarity ([lesson 29.2](#/lesson/29.2)) | Meaning, paraphrases, other languages |
| Great at | Codes, IDs, names, rare jargon, exact phrases | Natural questions, synonyms, vague wording |
| Fails on | Synonyms ("money back" vs "refund"), typos without fuzzing | Rare tokens it never learned; `E-4012` ≈ `E-4021` ≈ "an error" |
| Index | Inverted index (Elasticsearch, OpenSearch, Postgres FTS) | ANN index (34.3) |

The failures are largely **complementary**, so running both and merging the results recovers most of each one's
misses.

```
query ─┬─► BM25 top 50 ──────┐
       │                     ├─► fuse (RRF) ─► top 50 ─► rerank ─► top 5-20 ─► prompt
       └─► embed ─► ANN top 50┘
           (both in parallel: latency = the slower one, not the sum)
```

Many engines now do this in one query (Elasticsearch, OpenSearch, Weaviate, Qdrant, Vespa and others support hybrid
queries), or you run two searches and merge in the API server.

## Reciprocal rank fusion

BM25 scores (say 4.2-17.9) and cosine similarities (0.71-0.86) aren't comparable, so adding them is meaningless.
**Reciprocal rank fusion (RRF)** (Cormack, Clarke and Büttcher, 2009) ignores scores and uses only ranks:

```
RRF(d) = Σ over each result list  1 / (k + rank of d in that list)        k = 60 by convention
```

Worked example:

| Doc | BM25 rank | Vector rank | RRF score |
|-----|-----------|-------------|-----------|
| D1 | 1 | 5 | 1/61 + 1/65 = 0.0318 |
| D2 | 2 | 2 | 1/62 + 1/62 = **0.0323** |
| D3 | 3 | – | 1/63 = 0.0159 |
| D4 | – | 1 | 1/61 = 0.0164 |

Fused order: **D2, D1, D4, D3**. Documents both retrievers like rise to the top; one retriever's single top hit still
makes the list. The constant `k` damps the advantage of rank 1 over rank 5. RRF needs no tuning and no score
normalisation, which is why it's the default. Weighted variants (e.g. score normalisation plus a tunable weight) can
do slightly better if you have an eval set to tune them on.

## Rerankers

Embeddings are **bi-encoders**: query and document are encoded separately, so document vectors can be precomputed.
Fast, but the model never sees query and document together. A **cross-encoder reranker** reads the pair together and
outputs a relevance score:

```
bi-encoder:     embed(query) · embed(doc)          precomputed docs, ~1 ms per million comparisons
cross-encoder:  score(query + doc together)         one model call per pair, much more accurate
```

You can't run a cross-encoder over millions of documents, but you can over the top 50-150 candidates from hybrid
search. Options: hosted rerank APIs (Cohere, Voyage, Jina and others) or open models (e.g. the BGE rerankers) on your
own GPUs; an LLM itself can also rerank, at higher cost.

| Concern | Typical figure (order of magnitude) |
|---------|-------------------------------------|
| Added latency | ~50-300 ms for 50-100 candidates |
| Candidates in | 50-150 |
| Passages out | 5-20 |
| Effect | Usually a clear gain in the precision of the top few results |

Anthropic's contextual retrieval experiments found that adding reranking on top of hybrid search cut retrieval
failures further, from a 49% to a 67% reduction versus the baseline. Rerankers also let you send **fewer** passages to
the LLM, which saves tokens and reduces distraction. Budget the reranker's latency in the TTFT budget (33.6) and give
it a timeout: if it's slow, fall back to the fused order rather than failing.

## Other tricks that help exact matches

- **Field boosts**: match on `title`, `product_code` and `error_code` fields with higher weight.
- **Tokenisation**: make sure the analyser doesn't split `E-4012` into `e` and `4012`; add a keyword field for codes.
- **Query understanding**: a regex or small model that detects SKUs, order IDs and error codes and turns them into
  filters or exact-match clauses.
- **Metadata filters** (product, version, language) applied to both retrievers.

## Try it

Users of your RAG help assistant ask "**printer shows error E-4012**". The answer is generic advice about paper
jams. The article "Fixing E-4012: fuser temperature fault" exists and is indexed. Retrieval is vector-only, top 5.
Find the cause and fix it.

<details>
<summary>Reference</summary>

**Cause:** the embedding model has no special meaning for `E-4012`; it embeds the query as "printer + error", which
lands near the many generic troubleshooting chunks. The right article may be at rank 30, outside the top 5. A quick
check: run the query against BM25 alone and the article is rank 1.

**Fix:**
1. Add **BM25** over the same chunks (with a keyword field so `E-4012` stays one token) and fuse with **RRF**. The
   article now ranks high in BM25, so it enters the fused top results.
2. Add a **reranker** over the fused top 50; it sees "E-4012" in both the query and the article title and puts it
   first.
3. Optionally detect error-code patterns in the query and boost chunks whose `error_code` field matches.
4. Add this query, and a dozen like it with other codes, to the eval set (34.6) so a future change can't regress it.
</details>

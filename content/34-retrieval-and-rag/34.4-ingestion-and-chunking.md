# Ingestion and chunking

Most RAG quality problems are not in the model or the vector index. They're in the **ingestion pipeline**: a PDF
parsed into garbage, a table split in half, an article deleted last month still being cited, an internal page shown
to a customer. Ingestion is a data pipeline like any in modules 7 and 17, and it deserves the same care.

## The pipeline

```
sources ──► detect changes ──► fetch & parse ──► clean ──► chunk ──► enrich ──► embed ──► upsert
(CMS, wiki,   (webhooks, CDC,    (HTML, PDF,     (nav,     (below)   (metadata,  (batched,   vector index
 tickets,      polling with       Office, OCR)    boiler-             context,    rate-       + keyword index
 drive)        ETags)                             plate)              ACLs)       limited)    + doc store
```

Build it as queue-driven workers ([lesson 7.2](#/lesson/7.2)):

- **Event-driven where possible**: CMS webhooks or change data capture ([lesson 17.3](#/lesson/17.3)) instead of
  nightly full crawls. Fall back to polling with change detection (ETag, `updated_at`, content hash).
- **Idempotent**: chunk IDs are deterministic, e.g. `hash(doc_id, chunk_index, content_hash)`, so a retried job
  upserts instead of duplicating ([lesson 12.4](#/lesson/12.4)).
- **Skip unchanged work**: if a document's content hash didn't change, don't re-chunk or re-embed it.
- **Rate-limited embedding**: batch requests to the embedding API and respect its token limits; a full re-index must
  not starve live updates (separate queues or priorities).
- **Dead-letter** documents that fail to parse, and alert on the count ([lesson 7.4](#/lesson/7.4)).

## Parsing is the hidden quality killer

Garbage in, garbage retrieved. Common traps: PDFs with two columns read across, tables flattened into number soup,
headers and footers repeated on every chunk, navigation menus indexed as content, scanned documents with no text
layer. Keep structure: convert to Markdown-like text that preserves headings, lists and tables, and store the
heading path ("Billing > Refunds > Partial refunds") with each chunk.

## Chunking

Documents are split into **chunks** because embeddings of very long texts blur many topics into one vector, and
because you want to put only the relevant passages in the prompt.

| Chunk size | Upside | Downside |
|------------|--------|----------|
| Small (100-200 tokens) | Precise matches; more chunks fit in the prompt | Loses context ("it", "this plan"); answers split across chunks |
| Medium (300-800 tokens) | Common default; usually one idea per chunk | Still splits some answers across chunks |
| Large (1,000+ tokens) | Self-contained context | Vector is a blur of topics; fewer fit in the prompt; more tokens per query |

Techniques:

- **Structure-aware splitting**: split on headings and paragraphs first, then by size. A help article section is
  often the natural chunk.
- **Overlap** of 10-20% between consecutive chunks so a sentence on the boundary isn't lost.
- **Never split tables or code blocks** mid-way; keep them whole with their caption or heading.
- **Small-to-big**: retrieve on small chunks for precision, but send the surrounding section (the parent) to the model.
- **Contextual chunk headers**: prepend the document title and heading path to each chunk before embedding.

**Contextual retrieval** (Anthropic, 2024) goes further: an LLM writes a 50-100 token sentence situating each chunk in
its document ("This chunk is from ACME's Q2 2023 SEC filing; it discusses revenue growth...") and that is prepended
before embedding and keyword indexing. Anthropic reported the top-20 retrieval failure rate falling by 35% with
contextual embeddings, 49% when also applied to BM25, and 67% with reranking added. The cost is one LLM call per chunk
at ingestion time, made cheap by prompt-caching the document (33.5).

There is no universally best chunk size: pick two or three candidates and measure retrieval recall on your eval set
(34.6).

## Metadata

Store with every chunk:

| Field | Used for |
|-------|----------|
| `doc_id`, `chunk_id`, `url`, title, heading path | Citations, dedup, deletes |
| `updated_at`, `version` | Freshness filters, "prefer newest" |
| `language`, `product`, `region` | Filters at query time |
| `acl` (groups, tenant, visibility) | **Permission filtering** |
| `embedding_model` | Versioning (34.2) |
| `source_hash` | Change detection |

## Permissions

The model will happily summarise anything you put in its prompt. If retrieval returns an internal-only document to a
customer, the answer leaks it. So:

- **Filter at retrieval time**, inside the vector and keyword search, by the caller's identity: `tenant_id = X AND
  (visibility = 'public' OR group IN user_groups)`. Never rely on the prompt ("don't reveal internal docs").
- **Propagate ACL changes** fast: a permission change is an update event that must reach the index metadata, not
  wait for the next full crawl.
- **Deletions are urgent**: deleted or unpublished documents must disappear from the index within your freshness SLA
  (and for privacy requests, from any caches of answers too, 26.5).
- For hard multi-tenant isolation, use a namespace or index per tenant.

## Keeping embeddings fresh

Define a **freshness SLA** ("an edit is answerable within 5 minutes") and monitor it as lag: time from source change to
index upsert, like consumer lag in Kafka. Track index size against source document count to spot drift (missed
deletes, duplicate chunks). Schedule a periodic reconciliation job that compares source IDs with indexed IDs.

## Try it

Design ingestion for a **help centre**: 5,000 articles in a hosted CMS in 3 languages, about 200 edits a day, some
articles internal-only (agents) and some customer-facing, plus a few hundred PDF manuals. Edits must be answerable
within 10 minutes.

<details>
<summary>Reference</summary>

- **Change detection:** CMS webhooks on publish, update, unpublish and delete → a queue. A nightly reconciliation job
  lists all article IDs and fixes drift. PDFs are re-processed only when their hash changes.
- **Workers:** fetch article → convert HTML to structured text (keep headings, tables) → chunk by section (~300-500
  tokens, 15% overlap, tables kept whole) → prepend "Title > Section" header (optionally an LLM-written context
  sentence) → embed in batches → upsert to vector and BM25 indexes. Deterministic chunk IDs; on update, delete the
  article's old chunks that no longer exist.
- **PDFs:** a separate, slower queue with a layout-aware parser and OCR fallback, so a 300-page manual doesn't delay
  article edits.
- **Metadata:** article ID, URL, language, product, `visibility` (internal/public), `updated_at`, embedding model.
- **Query-time filters:** `language = user's` (with fallback to English), `visibility = public` for customers;
  agents get both.
- **Freshness:** alert if webhook-to-upsert lag p95 exceeds 10 minutes; unpublish and delete events jump the queue.
- **Scale check:** 5,000 articles × ~8 chunks × 3 languages ≈ 120k chunks: a full re-embed is minutes and costs little.
  pgvector or the existing search engine is plenty; no separate vector cluster needed.
</details>

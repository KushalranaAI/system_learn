# Evaluating RAG

Every lever in this module (chunk size, embedding model, hybrid weights, reranker, top-k, prompt) changes answer
quality, and none of them shows up on a latency dashboard. Without an evaluation set you are tuning by vibes, and
every change risks a silent regression. The key idea: **evaluate retrieval and generation separately**, because they
fail differently and are fixed differently.

```
question ──► RETRIEVAL ──► chunks ──► GENERATION ──► answer
             "did we find          "did the model use them
              the right chunks?"    correctly and only them?"
```

If the right chunk never reached the prompt, no prompt engineering will fix the answer.

## Retrieval metrics

For each eval question you record which chunks (or documents) are **relevant**. Then for the ranked results:

| Metric | Definition | Reads as |
|--------|------------|----------|
| **Recall@k** | relevant items in the top k ÷ all relevant items | "Did the answer's source make it into the prompt?" The most important one for RAG |
| **Precision@k** | relevant items in the top k ÷ k | How much noise you send the model |
| **MRR** (mean reciprocal rank) | average of 1 / rank of the first relevant item | Is the best chunk near the top? |
| **nDCG@k** | rank-discounted gain, normalised to the ideal order | Graded relevance, order-sensitive |

Example for three questions, first relevant result at ranks 1, 3 and not found in the top 10:

```
MRR = (1/1 + 1/3 + 0) / 3 = 0.44
Recall@10 = 2/3 = 0.67 (one relevant chunk each)
```

Retrieval metrics are cheap, deterministic and fast: run them on every change to chunking, embeddings or the index,
like unit tests.

## Generation metrics

These judge the answer. Frameworks such as RAGAS popularised a standard set, usually scored by an LLM judge:

| Metric | Question it answers | Catches |
|--------|---------------------|---------|
| **Faithfulness / groundedness** | Is every claim in the answer supported by the retrieved context? | Hallucination, mixing in model "memory" |
| **Answer relevance** | Does it actually answer the question? | Evasive or off-topic answers |
| **Context precision** | Were the retrieved chunks relevant, and ranked high? | Noisy retrieval |
| **Context recall** | Does the context contain everything the reference answer needs? | Missing information |
| **Correctness** | Does it match the reference answer's facts? | Wrong answers that sound fine |
| **Citation accuracy** | Do the cited sources support the sentences that cite them? | Fake or misplaced citations |

Also track **refusal behaviour**: for questions the corpus can't answer, the right output is "I don't know", and
an answer there is a hallucination.

## LLM-as-judge, carefully

An LLM judge scales to thousands of answers, but it is a model too:

- Give it a **rubric** and the reference answer; ask for a score with a reason, preferably binary or 1-3, not 1-10.
- **Calibrate** it against human labels on ~50-100 examples; trust it only where it agrees with humans.
- Watch known biases: preference for longer answers, for its own model family's style, and position bias in pairwise
  comparisons (swap the order and average).
- Pin the judge's model version, or scores drift when the judge changes rather than your system.

More on evals in production, including online evals and A/B testing, in lesson 36.1.

## The golden set

A **golden set** is a fixed list of questions, each with the relevant source chunk IDs and a reference answer. Build
it from:

1. **Real user questions** from logs or support tickets (the best source; reflects actual wording).
2. **Subject-matter experts** writing hard and important cases.
3. **Synthetic questions** generated by an LLM from your documents, then reviewed by a human. Useful for coverage,
   but they tend to copy the document's wording, which flatters vector search.

Cover the categories, not just the happy path: simple lookups, paraphrases, exact codes and names, multi-hop
(needs two documents), comparisons, time-sensitive facts, permission-restricted content, and unanswerable questions.
Version the set; when a production failure is found, add it so it can never regress.

## Evaluation as a release gate

```
change (chunking, model, prompt) ─► run retrieval metrics (seconds) ─► run generation evals (minutes)
   ─► compare to baseline ─► block merge if recall@10 or faithfulness drops beyond a threshold
```

Keep a results table per run: config, recall@k, MRR, faithfulness, correctness, p95 latency, cost per answer.
Quality, latency and cost are traded together, and the table makes the trade visible.

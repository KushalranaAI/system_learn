# Design a chat app

"Design WhatsApp / Messenger / Slack" tests real-time delivery: holding millions of connections, getting a message to
the right server, showing the right ticks, and never losing or reordering messages when phones go offline.

## Clarifying questions

- 1:1 only, or groups? How big can groups get? (Both; groups up to ~500.)
- Multiple devices per user? (Yes: phone and desktop.)
- Delivery receipts and read receipts? (Yes: sent, delivered, read ticks.)
- Do we keep history on the server forever? (Yes, synced across devices. End-to-end encryption out of scope for now.)
- Media? (Uploaded to object storage; messages carry a link.)

## Requirements

**Functional**
1. Send 1:1 and group text messages; media by reference.
2. Delivery states: sent (server has it), delivered (recipient device has it), read.
3. Offline users receive everything when they reconnect, in order; history syncs to every device.
4. Online/last-seen presence.

**Non-functional**
- Delivery to an online recipient in < 500 ms p99.
- No message lost once the sender sees "sent"; order preserved within a conversation.
- Highly available; regional outages degrade, not stop, delivery.

## Estimates

```
users:        500M daily, 40 messages sent each      = 20B messages/day ≈ 230k/s, ~700k/s peak
connections:  ~100M online at peak; ~500k idle WebSockets per tuned gateway → ~200 gateways (+ headroom: 300)
storage:      20B × ~200 B (text + metadata)          ≈ 4 TB/day ≈ 1.5 PB/year (before replication)
group fan-out: if 10% of messages go to groups of avg 50 → 2B × 50 = 100B deliveries/day ≈ 1.2M/s
```

Connections and writes are huge; reads are mostly "push what just arrived," not queries.

## API

Clients hold one WebSocket ([lesson 6.1](#/lesson/6.1)) and exchange frames:

```
→ send     {client_msg_id, conversation_id, body}
← ack      {client_msg_id, message_id, seq}                     (single tick: stored)
← message  {conversation_id, message_id, seq, sender, body}
→ delivered{conversation_id, up_to_seq}                         (double tick)
→ read     {conversation_id, up_to_seq}                         (blue ticks)
HTTP: GET /conversations/{id}/messages?after_seq=&limit=        (catch-up and history)
```

## Data model

| Entity | Key | Store |
|--------|-----|-------|
| message | (conversation_id, seq) | wide-column (Cassandra/ScyllaDB), partition by conversation, bucket by time |
| conversation | conversation_id → members, last_seq | SQL or KV |
| device cursor | (user_id, device_id, conversation_id) → delivered_seq, read_seq | KV |
| session route | user_id → [gateway_id per device] | Redis with TTL |
| user inbox | user_id → conversations with new messages | KV / queue |

Partitioning by conversation keeps a chat's history on one partition, the pattern [Discord](#/lesson/23.4) uses.

## High-level design

```
sender ─WS→ gateway A → chat service ─┬─ assign seq, write message (wide-column DB)   → ack to sender
                                      ├─ look up members + their gateways (Redis)
                                      └─ publish to gateway B, C... (pub/sub or direct RPC) ─WS→ recipients
offline recipient: push notification (APNs/FCM); on reconnect, GET messages after last delivered seq
```

## Deep dive 1: ordering and exactly-once display

- The server assigns a **per-conversation sequence number** at write time (a counter in the conversation row, or the
  partition leader). Clients sort by seq, never by device clocks ([lesson 12.5](#/lesson/12.5)).
- The sender's `client_msg_id` makes retries idempotent ([lesson 12.4](#/lesson/12.4)): a resend after a dropped ack
  returns the same message_id instead of creating a duplicate.
- Recipients dedupe by message_id and detect gaps by seq ("I have 41, got 43") and fetch the missing one.

## Deep dive 2: delivery receipts and offline sync

- **Sent** = durably stored (replicated write acknowledged). Only then ack the sender.
- **Delivered** = the recipient device acknowledged up to seq N; store it as a cursor, not a flag per message.
- **Read** = the same, a second cursor. In groups, show "delivered to all" when the minimum cursor passes N.
- **Reconnect** ([lesson 6.5](#/lesson/6.5)): the device sends its last delivered seq per conversation; the server
  returns what's after it. Each device has its own cursors, so phone and laptop sync independently.

## Deep dive 3: connections and group fan-out

- Gateways are stateful; everything else is stateless. Store user → gateway routes in Redis with a TTL refreshed by
  heartbeats ([lesson 6.4](#/lesson/6.4)). A dead gateway's routes expire; clients reconnect elsewhere and catch up.
- Routing a message: look up recipient gateways and send directly, or publish on a channel per gateway
  ([lesson 6.3](#/lesson/6.3)).
- Groups up to ~500: fan out on write to each member's gateway (or inbox if offline). For very large channels
  (Slack/Discord-style), fan out on read: members pull from the channel log when they open it.
- [WhatsApp](#/lesson/23.3) is the reference for holding very many connections per server.

## Bottlenecks and failure modes

- **Gateway crash:** ~500k clients reconnect at once. Add jittered reconnect backoff and make the catch-up query cheap.
- **Hot conversation:** a huge group writes to one partition; bucket by (conversation, day) and cap group size.
- **Push notification provider slow:** queue pushes separately so they never block socket delivery.
- **Region failure:** messages written in one region replicate async; seq allocation stays with a home region per
  conversation to keep ordering.

## What interviewers listen for

- Server-assigned per-conversation sequence numbers and idempotent sends.
- Ticks modelled as per-device cursors.
- A clear story for offline users and reconnects.
- Separation of stateful gateways from stateless chat services, with a route table.

## Common mistakes

- Ordering by client timestamps.
- Acking "sent" before the message is durably stored.
- One giant table keyed by message_id, so loading a conversation is a scatter query.
- Ignoring multiple devices and the reconnect storm after a gateway dies.

## Key takeaways

- Stateful gateways hold sockets; a route table maps users to gateways.
- Per-conversation seq numbers give ordering; client message ids give idempotency.
- Delivered and read are cursors per device; offline sync is "everything after my cursor."
- Fan out on write for small groups, on read for huge channels.

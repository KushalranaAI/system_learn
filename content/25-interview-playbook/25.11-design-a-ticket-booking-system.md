# Design a ticket booking system

"Design Ticketmaster" is a concurrency problem in disguise. Selling seats is easy; selling the **same** 50,000 seats to
2 million fans who all arrive at 10:00:00, without double-selling, crashing or rewarding bots, is the interview.

## Clarifying questions

- Reserved seats or general admission? (Reserved seats; users pick from a map.)
- How long can a user hold seats while paying? (10 minutes.)
- How big are on-sales? (Usually small; a few huge ones: 50k seats, 2M people in the first minute.)
- Fairness requirement? (First come, first served by arrival, and limits per buyer.)
- Payment? (Through a payment provider; design the hold → pay → confirm flow.)

## Requirements

**Functional**
1. Browse events and see the seat map with availability.
2. Hold selected seats for 10 minutes; pay; get tickets.
3. Holds expire automatically; seats return to sale.
4. Waiting room for high-demand on-sales.

**Non-functional**
- **Never sell a seat twice** (strong consistency on seat state).
- Seat map can be a few seconds stale.
- Survive 2M users in a minute without falling over; admit them fairly.
- Booking p99 < 1 s once admitted.

## Estimates

```
on-sale:   2M users in ~60 s                     ≈ 33k arrivals/s, each polling/refreshing → 100k+ req/s
seats:     50k seats sold in ~1 min             ≈ 833 seats/s; ~2-4 seats per order → ~300 orders/s
seat map:  50k seats × ~20 B status             ≈ 1 MB per event (cache it, push diffs)
normal:    10M bookings/month                    ≈ 4/s average (tiny)
```

The writes are small: ~300 orders/s fits one well-tuned database. The danger is the **read stampede and contention on
the same rows**, not raw volume.

## API

```
GET  /events/{id}/seats                                 → seat map (cached, a few seconds stale)
POST /events/{id}/holds      {seat_ids[], idempotency_key}   → 201 {hold_id, expires_at} | 409 seats taken
POST /holds/{id}/checkout    {payment_token}            → 202 {order_id}   (async with the provider)
GET  /orders/{id}                                       → {status: PENDING | CONFIRMED | FAILED}
GET  /queue/{event_id}/position                         → {position, eta}  (waiting room)
```

## Data model

| Entity | Key | Fields | Store |
|--------|-----|--------|-------|
| seat | (event_id, seat_id) | status AVAILABLE/HELD/SOLD, hold_id, hold_expires_at, version | SQL (one event's seats in one shard) |
| hold | hold_id | user, seats, expires_at | SQL, same shard |
| order | order_id | hold_id, payment status, amount | SQL |
| queue token | user + event | position, admitted_at | Redis |

Shard by **event_id**: every seat of an event lives together, so a hold is a single-shard transaction.

## High-level design

```
users → CDN (event pages, static seat-map) → waiting room (Redis queue, admits N/s with signed tokens)
                                                 ↓ admitted only
                     LB → booking service → seats DB (conditional updates, sharded by event)
                                ├─ payment service → provider (idempotency key) → confirm order
                                └─ seat changes → pub/sub → live seat maps
expiry:  sweeper job (or DB TTL) returns expired holds to AVAILABLE
```

## Deep dive 1: holding seats without double-selling

```sql
UPDATE seats
SET status = 'HELD', hold_id = :h, hold_expires_at = now() + interval '10 min'
WHERE event_id = :e AND seat_id IN (:s1, :s2)
  AND (status = 'AVAILABLE' OR (status = 'HELD' AND hold_expires_at < now()));
-- affected rows must equal 2, otherwise roll back and return 409
```

One conditional update in a transaction is the whole trick ([lesson 1.6](#/lesson/1.6), [lesson 16.1](#/lesson/16.1)).
No distributed lock is needed because the seat row is the lock. The `hold_expires_at < now()` clause makes expired
holds reclaimable even if the sweeper is late.

Alternative: Redis `SET seat:{id} hold NX EX 600` for holds, with the database as the record of sales. Faster, but now
two stores must agree; mention it as an option for extreme contention.

## Deep dive 2: the waiting room

Admitting 2M people directly would melt the booking service and reward whoever retries fastest.

- Everyone arriving before the start gets a random position (fair lottery); later arrivals join the back.
- The queue admits users at a fixed rate the booking service can handle (say ~1,000 users/s, and fewer as seats run out), handing
  out a **signed, short-lived token** checked by the booking API.
- Waiting users poll a cheap, cached position endpoint; the page is static and served by the CDN.
- Per-account and per-card limits, CAPTCHA and bot scoring at the entrance.

[Shopify's checkout queue](#/lesson/23.9) uses the same idea for flash sales.

## Deep dive 3: payment and confirmation

1. Checkout calls the payment provider with an **idempotency key** = hold_id ([lesson 12.4](#/lesson/12.4)).
2. On success: in one transaction, mark seats SOLD (`WHERE hold_id = :h AND status = 'HELD'`) and the order CONFIRMED.
3. If the hold expired during a slow payment: either extend holds while a payment is in flight, or refund automatically.
4. Provider timeout = unknown result: query the provider, never charge again blindly ([lesson 25.14](#/lesson/25.14)).

## Bottlenecks and failure modes

- **Seat map reads:** serve from cache and push diffs; never query the seats table per page view.
- **Hot event shard:** one event = one shard; ~300 orders/s is fine, and the waiting room caps it.
- **Sweeper down:** the conditional update treats expired holds as available anyway.
- **Booking DB failover:** use synchronous replication for this table; a lost "SOLD" is a double sale.

## What interviewers listen for

- The atomic conditional update (or equivalent) and why it prevents double-selling.
- Hold expiry handled even when background jobs fail.
- A waiting room that controls admission rate and fairness.
- Payment idempotency and the expired-hold-during-payment edge case.

## Common mistakes

- `SELECT` availability then `UPDATE` in two steps without a condition (race).
- A distributed lock service per seat when the database row already serialises it.
- No admission control, so the system's capacity decides who wins.
- Charging the card before securing the seats.

## Key takeaways

- The seat row is the lock: one conditional update per hold, sharded by event.
- Holds expire by query condition, not only by a sweeper.
- A waiting room turns a stampede into a steady, fair flow.
- Pay with an idempotency key; confirm seats and order together.

# Design a leaderboard

"Design a game leaderboard" sounds like `ORDER BY score DESC LIMIT 10`. It stops being that at 50M players, when every
player wants to know **their own rank** in real time and thousands of scores change every second.

## Clarifying questions

- Which queries? (Top 100, my rank, players around me.)
- All-time only, or daily/weekly boards too? (All-time plus daily and weekly.)
- How real-time? (Top 100 and my rank within a couple of seconds of a game ending.)
- Score semantics: best score, or cumulative? (Cumulative points.)
- Scale? (50M players, 10M daily active, ~10 games each per day.)
- Ties? (Earlier achiever ranks higher.)

## Requirements

**Functional**
1. Update a player's score after each game.
2. Get the top N (N ≤ 100).
3. Get a player's rank and the 5 players above and below.
4. Daily, weekly and all-time boards; maybe per-region boards.

**Non-functional**
- Reads p99 < 50 ms; rank reflects updates within ~2 s.
- Score updates never lost (the database is the source of truth; the ranking store can be rebuilt).
- Handles end-of-tournament spikes.

## Estimates

```
updates:  10M DAU × 10 games         = 100M/day ≈ 1.2k/s average; spikes ×10-20 → ~20k/s
reads:    say 5 rank views per game  → ~6k/s average, ~50k/s peak (top-100 is cacheable)
memory:   Redis sorted set ≈ ~100 B per member incl. overhead → 50M × 100 B ≈ 5 GB per board
boards:   all-time + daily + weekly (+ a few regions) ≈ 10-20 GB total
```

One sorted set of 50M members fits on one Redis node, and 20k updates/s is well within a node's capacity.

## API

```
POST /scores           {player_id, game_id, points}   (idempotent on game_id)
GET  /leaderboards/{board}/top?n=100
GET  /leaderboards/{board}/players/{id}               → {rank, score, neighbours: [...]}
```

`board` = `all`, `daily:2026-10-24`, `weekly:2026-W43`, `region:eu:all`.

## Data model

| Data | Key | Store |
|------|-----|-------|
| game result | game_id → player, points, ts | SQL / wide-column (source of truth) |
| player total | player_id → total | SQL |
| board | `lb:{board}` sorted set: member = player_id, score = points | Redis ZSET |
| top-N cache | `lb:{board}:top100` | Redis string / CDN, 1-2 s TTL |

## High-level design

```
game server → score API → DB (insert game result, idempotent) → Kafka "score_events"
                                                                    ↓
                                             leaderboard workers: ZINCRBY lb:all, lb:daily:..., lb:weekly:...
clients → leaderboard API → top-N cache → Redis ZREVRANGE
                          → my rank: ZREVRANK + ZREVRANGE rank-5..rank+5
```

## Deep dive 1: sorted sets

Redis sorted sets are a [skip list](#/lesson/19.12) plus a hash map:

| Operation | Command | Cost |
|-----------|---------|------|
| add points | `ZINCRBY lb:all 50 player:42` | O(log n) |
| top 100 | `ZREVRANGE lb:all 0 99 WITHSCORES` | O(log n + 100) |
| my rank | `ZREVRANK lb:all player:42` | O(log n) |
| neighbours | `ZREVRANGE lb:all r-5 r+5` | O(log n + 10) |

At n = 50M, log n ≈ 26 steps: microseconds. **Ties:** encode the score as `points × 2^k + (MAX_TS − ts)` (or a
fractional tiebreaker) so earlier achievers sort first.

Periodic boards: one key per day/week with a TTL (`EXPIRE` after the period plus grace). No reset jobs needed.

## Deep dive 2: when one node isn't enough

If the board grows (500M players) or writes exceed one node:

- **Shard by player hash:** writes spread evenly. Top 100 = ask each shard for its top 100 and merge (scatter-gather,
  [lesson 14.4](#/lesson/14.4)). My rank = sum over shards of `ZCOUNT(shard, my_score, +inf)`: N calls per query.
- **Shard by score range:** shard 1 holds the top scores, etc. Rank = (players in higher shards, kept as counters) +
  rank within my shard. Fast reads, but players move between shards and the top shard is hot.
- Usually better: **one exact top tier + approximate ranks** below (next deep dive).

## Deep dive 3: real-time vs periodic, exact vs approximate

- Nobody needs to know they're exactly 31,415,926th. Keep an exact ZSET for the top ~100k; for everyone else,
  compute rank from a **score histogram** (count of players per score bucket, updated as scores change) and show
  "top 63%" or an approximate rank.
- Real-time top 100 from the ZSET; global "final" rankings for a season computed by a batch job from the database
  (exact, auditable, used for prizes).
- Cache top-100 for 1-2 s: 50k reads/s become one Redis call per second per board.

## Bottlenecks and failure modes

- **Redis node dies:** promote the replica; if both are lost, rebuild the ZSET from the database totals (minutes).
- **Duplicate score events** (Kafka redelivery): workers dedupe by game_id before `ZINCRBY`, or recompute from totals
  with `ZADD` (idempotent).
- **Cheaters:** validate scores server-side; flagged players removed with `ZREM`.
- **Spikes at tournament end:** Kafka buffers; workers scale; ranks are a few seconds behind, not wrong.

## What interviewers listen for

- Why `ORDER BY ... OFFSET` or `COUNT(*) WHERE score > x` fails at 50M rows per request.
- Sorted set operations with complexity, plus memory math.
- A sharding answer that addresses "my rank" across shards.
- The database as the source of truth, the ZSET as a rebuildable index.

## Common mistakes

- Computing rank with `SELECT COUNT(*) WHERE score > ?` on every request.
- Forgetting ties and periodic boards.
- Sharding by player and then not explaining how global rank works.
- Treating Redis as the only copy of scores.

## Key takeaways

- A sorted set gives O(log n) updates, top-N and rank; 50M players fit on one node.
- Keep the database as truth and the sorted set as a rebuildable index.
- Periodic boards are separate keys with TTLs; ties need an encoded tiebreaker.
- Shard or approximate only when needed, and explain "my rank" across shards.

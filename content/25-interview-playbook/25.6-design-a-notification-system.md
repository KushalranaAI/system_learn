# Design a notification system

Almost every product sends notifications: push, email, SMS, in-app. The interview tests whether you can build one
pipeline that many services feed, that respects user preferences, never spams, and can blast 10 million pushes in five
minutes without falling over or tripping provider limits.

## Clarifying questions

- Which channels? (iOS and Android push, email, SMS, in-app inbox.)
- Who sends? (Internal services: "order shipped", "new follower", marketing campaigns.)
- Transactional vs marketing: different rules? (Yes. Transactional is urgent; marketing is bulk, throttled, opt-in.)
- Is "exactly once" required? (At most one visible notification per event; a rare duplicate is bad but not fatal.)
- Scale? (100M users; ~500M notifications/day; campaigns to 10M users in 5 minutes.)

## Requirements

**Functional**
1. Services send `notify(user, type, data)`; the system picks channels, renders templates, delivers.
2. Users set preferences per type and channel, plus quiet hours.
3. Priorities: OTP codes and security alerts jump the queue; marketing waits.
4. Dedupe and per-user frequency caps; delivery status tracking.

**Non-functional**
- High-priority notifications delivered to the provider in < 2 s p99.
- Campaign of 10M pushes completes in ~5 minutes.
- Never lose an accepted notification (at-least-once internally, deduped at the edge).
- Provider outages must not block other channels.

## Estimates

```
daily:     500M / 86,400 s            ≈ 6k/s average
campaign:  10M pushes / 300 s         ≈ 33k/s for 5 minutes (on top of normal traffic)
payload:   ~1 KB per notification     → 33 MB/s into the queue during a campaign
storage:   500M × 500 B status record ≈ 250 GB/day; keep 30-90 days, then archive
device tokens: 100M users × ~1.5 devices ≈ 150M tokens × 200 B ≈ 30 GB
```

33k/s is easy for Kafka and workers; the hard limits are **provider throughput** and **not spamming**.

## API

```
POST /notifications   {idempotency_key, user_id | segment_id, type, data, priority?}   → 202 {notification_id}
GET  /notifications/{id}                                                               → {status per channel}
PUT  /users/{id}/preferences  {type: {push: true, email: false}, quiet_hours: {...}}
GET  /users/{id}/inbox?cursor=                                                         (in-app)
```

Return **202 Accepted**: sending is async ([lesson 7.1](#/lesson/7.1)).

## Data model

| Entity | Key | Store |
|--------|-----|-------|
| template | (type, channel, locale, version) | SQL, cached in workers |
| preferences | user_id | KV, cached |
| device token | (user_id, device_id) → token, platform, last_seen | KV |
| notification log | notification_id; index (user_id, created_at) | wide-column with TTL |
| dedupe key | hash(user, type, idempotency_key) | Redis `SET NX` with 24 h TTL |

## High-level design

```
services → Notification API ─→ validate, dedupe, store → Kafka topics by priority (high / normal / bulk)
                                                              ↓
                                      router workers: preferences, quiet hours, caps, render template
                                                              ↓
                              per-channel queues: push-ios │ push-android │ email │ sms │ in-app
                                                              ↓
                              channel senders (rate-limited) → APNs / FCM / email provider / SMS provider
                                                              ↓
                                     delivery receipts, bounces, invalid tokens → status store
campaigns: segment service expands segment → batches of user ids → bulk topic
```

## Deep dive 1: priorities and campaigns

- **Separate topics and worker pools per priority** (bulkheads, [lesson 12.3](#/lesson/12.3)). A 10M campaign fills the
  bulk topic; OTPs flow through the high topic untouched.
- Expanding a segment: a job pages through matching users and emits batches of ~1,000, so one message doesn't hold
  10M ids.
- 33k pushes/s with ~100 ms provider calls means ~3,300 in flight. Use HTTP/2 multiplexed connections to APNs and FCM
  (both support many concurrent requests per connection), and spread across ~30-50 sender instances.
- Stagger by time zone or quiet hours rather than waking up a continent at 3 a.m.

## Deep dive 2: dedupe and frequency caps

- **Idempotency key from the caller** (e.g. `order-123-shipped`): `SET NX` in Redis; if it exists, drop the duplicate
  ([lesson 7.3](#/lesson/7.3)). Kafka redelivery hits the same key, so retries don't double-send.
- **Collapse keys:** "5 new likes" instead of five notifications; buffer low-priority types for a minute and merge.
- **Caps:** at most N marketing pushes per user per day, a counter with TTL, like a [rate limiter](#/lesson/8.2).

## Deep dive 3: provider failures

- Retries with exponential backoff and jitter ([lesson 12.2](#/lesson/12.2)) only on retryable errors; honour
  provider `429`s.
- Invalid token responses → delete the token so you stop paying for dead devices.
- SMS/email: keep two providers and fail over with a circuit breaker; route by cost and country.
- After N attempts → dead-letter queue ([lesson 7.4](#/lesson/7.4)) and mark failed; OTPs may fall back to another
  channel.

## Bottlenecks and failure modes

- **Preferences lookup** at 33k/s: cache aggressively; batch lookups per segment chunk.
- **Provider throttling:** the channel queue backs up; backpressure ([lesson 7.6](#/lesson/7.6)) keeps workers from
  hammering it, and other channels keep flowing.
- **Duplicate storm after a worker crash:** idempotency keys make reprocessing safe.
- **Bad template deployed:** version templates and roll out gradually; a rendering error should fail one type, not all.

## What interviewers listen for

- Async with 202, queues per priority and per channel.
- Idempotency and dedupe, said out loud with where the key comes from.
- User preferences, quiet hours and caps: the "don't spam" requirement.
- Provider limits and failures treated as first-class.

## Common mistakes

- One queue for everything, so a campaign delays password-reset codes.
- Calling APNs/FCM synchronously from the service that triggered the event.
- Claiming exactly-once delivery to the phone (providers themselves are at-least-once).
- Forgetting token cleanup and unsubscribes (legal requirements for email).

## Key takeaways

- Accept fast (202), then route through priority topics and per-channel queues.
- Dedupe with caller idempotency keys; cap and collapse to avoid spam.
- Isolate priorities and providers so one slow path doesn't block the rest.

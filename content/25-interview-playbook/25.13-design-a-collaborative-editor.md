# Design a collaborative editor

"Design Google Docs" asks how several people can type into the same document at once and all end up with the same text,
with low latency, even when someone's laptop goes offline mid-sentence. The heart of it is a merge algorithm (OT or a
CRDT); around it sit presence, persistence and scaling one document's session.

## Clarifying questions

- Rich text or plain text? (Rich text, but reason with plain text first.)
- How many simultaneous editors per document? (Usually 1-5, up to ~100; viewers can be more.)
- Offline editing? (Short offline periods; long offline is a stretch goal.)
- Comments, suggestions, version history? (Version history yes; comments out of scope.)
- Scale? (10M daily users, ~1M documents open at peak.)

## Requirements

**Functional**
1. Several users edit one document concurrently; everyone converges to the same content.
2. Live cursors and selections of other editors (presence).
3. Version history and restore.

**Non-functional**
- Local typing feels instant (apply locally, never wait for the server).
- Remote edits appear in < 200-300 ms.
- No lost keystrokes; convergence guaranteed.
- A document session survives a server restart without data loss.

## Estimates

```
open docs:   ~1M at peak, average ~2 active editors
typing:      ~3 ops/s per active typist (batched every ~50-100 ms) → assume 1M typists → ~3M ops/s overall
per doc:     ~5-300 ops/s even with 100 editors: one server easily handles one document
connections: ~2M WebSockets → ~10-20 gateway servers at ~100-200k each
storage:     op ~50 B; 3M ops/s × 86,400 ≈ 260B ops/day ≈ 13 TB/day of raw ops → compact into snapshots
```

The global load is big but **each document is small and independent**, so we shard by document.

## API

```
GET  /docs/{id}                → {snapshot, version}
WS   /docs/{id}/session
  → op       {client_id, base_version, ops: [insert(pos, "x") | delete(pos, n) | format(...)]}
  ← ack      {version}
  ← remote   {version, ops, author}
  ↔ presence {cursor, selection}            (ephemeral, not stored)
GET  /docs/{id}/versions ; POST /docs/{id}/restore {version}
```

## Data model

| Data | Key | Store |
|------|-----|-------|
| document metadata, ACLs | doc_id | SQL |
| op log | (doc_id, version) | append-only log (wide-column / Kafka-like), durable before ack |
| snapshots | (doc_id, version) | object storage, every N ops or minutes |
| session owner | doc_id → server | coordination service / consistent hashing |
| presence | doc_id → users, cursors | in memory on the session server only |

## High-level design

```
clients ─WS→ gateway → routed by doc_id → document session server (one owner per doc, in memory)
                                         ├─ order ops, transform/merge, assign version
                                         ├─ append to op log (durable) → ack sender, broadcast to others
                                         └─ snapshotter: every ~1,000 ops → snapshot to object storage
open doc: load latest snapshot + replay ops after it
```

## Deep dive 1: OT vs CRDTs

Both make concurrent edits converge; they put the complexity in different places.

| | Operational Transformation (OT) | CRDTs |
|-|-------------------------------|-------|
| Idea | Transform an op against concurrent ops: insert at 5 becomes insert at 6 if someone inserted before it | Give every character a unique, ordered id, so inserts and deletes commute |
| Needs a server? | Usually a central server ordering ops (Google Docs-style) | No; peers can merge in any order (good for offline, P2P) |
| Metadata | Small: positions only | Per-character ids and tombstones (larger; modern libraries compress well) |
| Complexity | Transform functions are notoriously hard to get right for rich text | Data structure is the hard part; merging is simple |
| Examples | Google Docs | Yjs, Automerge |

Example: text "cat", Alice inserts "s" at 3, Bob deletes at 0 concurrently. With OT, the server applies Bob's delete
first, then transforms Alice's insert to position 2 → "ats". With a CRDT, Alice's "s" is anchored after the "t"'s id,
so it lands correctly whatever order the ops arrive in.

A good interview answer: **server-ordered OT (or a CRDT with a server relay) and say why.** Central ordering is simpler
when you already need a server for auth and persistence; CRDTs win for offline-first. Figma uses a server-authoritative
model with per-property last-writer-wins, which is simpler because design objects aren't text
([lesson 23.12](#/lesson/23.12)). Background: [lesson 13.7](#/lesson/13.7).

## Deep dive 2: one owner per document

- Route every connection for a doc to the same session server (consistent hashing on doc_id,
  [lesson 14.2](#/lesson/14.2)). That server is the single orderer; no distributed locking per keystroke.
- Durability: append ops to the log **before** acking; if the session server dies, a new owner loads snapshot + log and
  clients resend unacked ops (idempotent by client_id + sequence).
- Ownership changes need a lease with fencing so two servers never both act as owner ([lesson 12.7](#/lesson/12.7)).

## Deep dive 3: presence and snapshots

- **Presence** (cursors, "Alice is here") is ephemeral: broadcast via the session server, throttle to ~10 updates/s,
  never store it. Losing it on a crash is fine; clients resend.
- **Snapshots** every ~1,000 ops or few minutes bound load time; version history = snapshots + named checkpoints.
- Old ops beyond the snapshot window can be compacted or moved to cold storage.

## Bottlenecks and failure modes

- **Very popular doc** (a company all-hands doc with 1,000 viewers): separate viewers from editors; viewers get a
  throttled broadcast via a fan-out tier.
- **Session server crash:** a few seconds of reconnection; no loss because of log-before-ack.
- **Long offline client:** with OT, rebasing hours of edits is costly; CRDTs or a "merge as a suggestion" UX help.
- **Huge documents:** paginate loading; snapshot per section.

## What interviewers listen for

- A clear explanation of OT vs CRDT with one concrete example.
- Local-first typing with server ordering and acknowledgement.
- Sharding by document with a single owner and failover.
- Ephemeral presence separated from durable ops; snapshots + log for loading.

## Common mistakes

- Locking the document or paragraph while someone types.
- Sending the whole document on every keystroke.
- Last-write-wins on the whole document.
- Storing presence in the database.

## Try it

**Merge concurrent edits.** Starting text: `"abc"` (positions 0-2). Alice inserts `"X"` at position 1; Bob, at the same
time, deletes the character at position 2. The server receives Bob's op first. What does the server do with Alice's op
under OT, and what is the final text?

<details>
<summary>Reference</summary>

Bob's delete at 2 removes `"c"`: text `"ab"`, version 1. Alice's op was based on version 0. Transform it against Bob's
delete: Alice inserts at 1, which is before the deleted position 2, so her position is unchanged: insert `"X"` at 1 →
`"aXb"`. The server sends Alice Bob's delete transformed against her insert: delete at 2 becomes delete at 3 (her insert
shifted it right); applied to her local `"aXbc"` it gives `"aXb"`. Both converge on `"aXb"`. With a CRDT, `"X"` is
anchored after `"a"`'s id and `"c"` is tombstoned by id, giving the same result in any order.
</details>

## Key takeaways

- OT transforms positions using a central order; CRDTs use unique ids so ops commute.
- Apply locally, send ops, log durably, then ack and broadcast.
- One owner per document, sharded by doc id; presence is ephemeral; snapshots bound load time.

# At-least-once and idempotency

A worker charges a customer's card, then crashes **before** acknowledging the job. The queue redelivers it. Another
worker charges the card again.

## Delivery guarantees

| Guarantee | Meaning | How you get it |
|-----------|---------|----------------|
| **At-most-once** | Never twice; may be lost | Ack *before* processing |
| **At-least-once** | Never lost; may repeat | Ack *after* processing (the usual default) |
| **Exactly-once** | Once, always | Not achievable in general across a network; approximated |

The problem is the gap between "did the work" and "told the queue". A crash, timeout or network blip in that gap
always leaves one side unsure. So real systems choose **at-least-once delivery + idempotent processing**, which is
effectively once.

## Idempotent: same result, however many times

| Operation | Idempotent? |
|-----------|-------------|
| `SET status = 'shipped'` | ✅ |
| `balance = balance - 100` | ❌ |
| `INSERT INTO emails_sent (job_id) …` with a unique `job_id` | ✅ (the second insert fails harmlessly) |
| "Send an email" | ❌, unless you record that it was sent |
| Upload the thumbnail to `thumbs/42_200.jpg` | ✅ (overwrites with the same bytes) |

## Making jobs idempotent

### 1. Deduplicate by job id
```sql
BEGIN;
INSERT INTO processed_jobs (job_id) VALUES ($1);   -- fails if already done → skip
UPDATE accounts SET balance = balance - 100 WHERE id = $2;
COMMIT;
```
Record the job and its effect in **one transaction**. Two separate steps would recreate the gap.

### 2. Use natural keys and upserts
```sql
INSERT INTO photo_sizes (photo_id, size, url) VALUES (42, 200, '…')
ON CONFLICT (photo_id, size) DO UPDATE SET url = EXCLUDED.url;
```

### 3. Pass idempotency keys to external services
Payment providers accept an idempotency key (lesson 2.3). Use the job id: a retried charge returns the first result
instead of charging again.

### 4. Check state before acting
"If the order is already `shipped`, do nothing." Conditional updates make this race-free:
```sql
UPDATE orders SET status = 'shipped' WHERE id = $1 AND status = 'packed';
-- 0 rows updated → someone already did it
```

## Ordering is not guaranteed either

Most queues don't guarantee order, and retries reorder jobs anyway. If "update price to 90" runs after "update price
to 80", the old value wins. Fixes: include a version or timestamp and ignore older updates; or route all jobs for one
entity to a single ordered partition (Module 15).

## Try it

A job sends a welcome email: `send_email(user)` then `mark_welcomed(user)`. Sometimes users get two emails. Why, and
how would you fix it?

<details>
<summary>Answer</summary>

If the worker crashes, or the job times out, after sending but before marking (or acking), the job is redelivered and
sends again. Fix: before sending, atomically claim it with
`INSERT INTO welcome_emails (user_id) … ON CONFLICT DO NOTHING`, and only send if the insert succeeded. Also pass the
job id as the email provider's idempotency key. You accept a tiny chance of *no* email if the crash lands after
claiming but before sending, and handle that with a sweeper that retries unsent claims.
</details>

## Key takeaways

- Queues deliver at least once; duplicates will happen.
- Exactly-once delivery isn't achievable in general; at-least-once plus idempotent jobs is.
- Deduplicate by job id in the same transaction as the effect; use upserts and conditional updates.
- Don't rely on ordering; use versions or ordered partitions.

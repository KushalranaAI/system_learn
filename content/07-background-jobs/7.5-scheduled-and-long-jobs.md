# Scheduled and long jobs

"Every night at 2 am, send each user their weekly summary." On one server, that's a cron line. On twenty servers,
it's twenty copies of every email.

## Run scheduled work exactly once

| Approach | How | Notes |
|----------|-----|-------|
| **One scheduler service** | A single process (or a managed scheduler: Cloud Scheduler, EventBridge, k8s CronJob) enqueues jobs | The scheduler only **enqueues**; workers do the work |
| **Leader election** | All servers run the scheduler, but only the elected leader fires | Needs a lock service (etcd, Consul, a DB row) |
| **Lock per run** | Each server tries `INSERT INTO runs (job, date) …` with a unique key; only one succeeds | Simple and robust for daily/hourly jobs |

The pattern: **schedule → enqueue small jobs → workers process them.** Don't run "email 2M users" as one giant job
inside the scheduler.

## Split big work into small jobs

```
nightly_summary (scheduler)
  └─ enqueue 2,000 jobs: "send summaries for users 0–999", "1,000–1,999", …
       └─ each job processes ~1,000 users and can retry independently
```

- A crash loses at most one small chunk, not the whole night's run.
- Parallelism comes for free: more workers finish sooner.
- Progress is visible: 1,450 of 2,000 chunks done.

## Long-running jobs

Some work takes minutes or hours: video transcoding, a big export, a migration.

| Problem | Fix |
|---------|-----|
| The visibility timeout expires mid-job, and a second worker starts it | **Extend the lease** (heartbeat to the queue every N seconds) |
| A crash 90% through restarts from zero | **Checkpoint** progress ("done up to row 3,400,000") and resume from there |
| A deploy kills workers | Graceful shutdown: stop taking new jobs, finish or checkpoint the current one |
| Nobody knows if it's stuck | Report progress; alert when no progress for N minutes |

## Leases: a lock that expires

A lease is a lock with a timeout: "worker 7 owns job 42 until 10:15:30". The worker renews it while alive. If it
dies, the lease lapses and another worker can take over.

**The danger:** worker 7 pauses (a long GC pause, a VM freeze) past its lease. Worker 9 takes over. Worker 7 wakes up
and keeps writing. Now two workers write results. Fix: **fencing tokens**, where each lease carries an increasing
number and the database rejects writes with an older token (Module 12).

## Time zones and "at 2 am"

- Run schedules in UTC; compute per-user local times explicitly.
- Daylight saving time: 2:30 am happens **twice** on one day and **never** on another. Avoid scheduling in that window,
  or make jobs idempotent per (user, date).

## Try it

A billing job runs at midnight on every one of 6 API servers via cron, charging each user's monthly subscription.
Customers report double and triple charges. Redesign it.

<details>
<summary>Answer</summary>

Remove cron from the API servers. Use one scheduler (or a unique `INSERT INTO billing_runs (month)` lock) that
enqueues one job per batch of users. Each charge is idempotent: a unique `(user_id, billing_month)` row, and the
payment provider's idempotency key = `user_id:month`. Retried or duplicated jobs then can't double-charge.
</details>

## Key takeaways

- Scheduled work must fire once: use a single scheduler, leader election or a unique run lock.
- Schedulers enqueue; workers do the work in small, retryable chunks.
- Long jobs need lease extension, checkpoints and graceful shutdown.
- Leases can overlap after pauses; fencing tokens keep stale workers out.

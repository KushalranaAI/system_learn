# Not everything must happen now

A user uploads a profile photo. The request resizes it to three sizes, scans it for abuse, updates search, sends a
"looking good!" email, and only then returns. It takes 4 seconds, and fails entirely if the email service is down.

Most of that work didn't need to happen **before the response**.

## Ask: what does the user need right now?

| Work | Needed before responding? |
|------|---------------------------|
| Validate the upload, store the original | ✅ yes: the user needs to know it was accepted |
| Resize to 3 sizes | ❌ can finish a few seconds later (show a placeholder) |
| Abuse scan | ❌ usually async (hide the photo until it passes, if needed) |
| Update the search index | ❌ |
| Send an email | ❌ |

Move the ❌ items to **background jobs**:

```
POST /photos → store original → enqueue {resize, scan, index, email} → 202 Accepted (80 ms)
                                         ↓
                              workers do the slow parts
```

## What you gain

- **Fast responses:** the user waits for the essentials only.
- **Isolation:** the email provider being down no longer breaks uploads; the job retries later.
- **Smoothing:** a burst of 10,000 uploads becomes a queue that workers drain at a steady rate, instead of 10,000
  simultaneous resizes melting your servers.
- **Independent scaling:** add workers for the slow parts without touching the web tier.

## What you pay

- **Eventual completion:** the result appears *later*. The UI must handle "processing…".
- **Failure handling:** jobs fail and must be retried safely (lessons 7.3, 7.4).
- **More moving parts:** a queue, workers, monitoring of backlog and failures.
- **Harder debugging:** "where did my job go?" needs job ids and tracing.

## Typical background work

- Emails, SMS and push notifications.
- Image and video processing.
- Generating reports and exports.
- Syncing to search indexes, analytics and third parties.
- Recalculating aggregates (follower counts, recommendations).
- Scheduled maintenance (cleanup, expiring data, billing runs).

## Responding honestly

Use **202 Accepted** with a way to check the status:

```http
POST /exports        → 202 Accepted   Location: /exports/981
GET  /exports/981    → 200 { "status": "running", "progress": 0.4 }
GET  /exports/981    → 200 { "status": "done", "url": "https://…/export.csv" }
```

Or push the result when it's ready (Module 6).

## Try it

Checkout today: charge the card → create the order → decrement stock → send the confirmation email → notify the
warehouse → update loyalty points → respond. Which steps stay synchronous?

<details>
<summary>Answer</summary>

Keep synchronous whatever the user must know **succeeded** before you say "order placed": charging the card (or
authorising it), creating the order and reserving stock. Email, warehouse notification and loyalty points go to
background jobs, triggered reliably from the committed order (see the outbox pattern in Module 16).
</details>

## Key takeaways

- Do only what the user needs before responding; defer the rest.
- Background jobs give fast responses, isolation from slow dependencies, and burst smoothing.
- The cost is eventual completion, retries and more moving parts.
- Use 202 Accepted plus a status endpoint (or push) for long work.

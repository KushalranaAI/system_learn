# Queue vs log

Module 7 used queues for background jobs. As systems grow, services start **publishing events** for many others to
consume, and a different kind of broker shines: the **log**.

## Two models

| | Message queue (RabbitMQ, SQS) | Log (Kafka, Pulsar, Kinesis, Redpanda) |
|-|-------------------------------|----------------------------------------|
| Data structure | Messages waiting to be taken | An append-only, ordered sequence of records |
| After consumption | **Deleted** (acked) | **Kept** for the retention period (days, or forever) |
| Multiple consumers | Compete for messages (each gets some) | Each **consumer group** reads everything independently |
| Replay | No | Yes: rewind to any offset |
| Ordering | Usually none, or per-queue FIFO with limits | Strict order **within a partition** |
| Per-message routing | Rich (routing keys, priorities, delays) | Simple (topic + partition key) |
| Best for | Tasks: "do this job once" | Events: "this happened", for many readers |

## The log in one picture

```
topic "orders", partition 0:
offset:  0      1       2       3       4       5
       [placed][paid][placed][shipped][placed][paid] → new records appended here

consumer group "email":     at offset 3
consumer group "analytics": at offset 5
consumer group "search":    at offset 1   (it was down for a while; it catches up)
```

Each group tracks its own **offset**. Adding a new consumer means starting a new group, maybe from offset 0, to
backfill all history. The producer doesn't change at all.

## Why logs changed architecture

- **Decoupling:** producers publish facts; any number of services consume them, now or later.
- **Replay:** fix a bug in a consumer, reset its offset, and reprocess last week's events.
- **Buffering:** consumers can be slow or down; the log holds the data (with retention measured in days, not minutes).
- **A source of truth for streams:** event sourcing, CDC and stream processing (Module 17) build on it.

## When a queue is still better

- Individual job semantics: per-message acks, retries with delays, dead-letter queues, priorities.
- Many small independent tasks without ordering needs.
- Low volume, where running Kafka is overkill.

Many systems use both: a log for events between services, queues for work within a service.

## Try it

Choose a queue or a log:
1. Send password-reset emails.
2. Publish every order change so that billing, search, analytics and fraud services can each react.
3. Rebuild a recommendations model from the last 30 days of clicks.

<details>
<summary>Answer</summary>

1. **Queue**: one-off tasks with retries and a DLQ.
2. **Log**: many independent consumers of the same facts.
3. **Log**: replay of retained events (or a warehouse fed from the log).
</details>

## Key takeaways

- Queues hand out tasks and delete them; logs keep an ordered record for many readers.
- Each consumer group tracks its own offset in a log, so adding consumers or replaying is free for producers.
- Logs give decoupling, replay and buffering, and underpin streaming.
- Use queues for per-job retry semantics; use logs for events.

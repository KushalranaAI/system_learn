# Delivery guarantees

Messages can be lost or duplicated at three points: when the **producer** sends, while the **broker** stores, and
when the **consumer** processes. A guarantee is only as strong as its weakest link.

## Producer side

| Risk | Defence |
|------|---------|
| Network blip, the producer retries, a duplicate is written | **Idempotent producer** (`enable.idempotence=true`): the broker drops duplicates by producer id and sequence |
| Broker dies before replicating | `acks=all` + `min.insync.replicas=2` |
| App crashes after the DB commit but before sending the event | **Outbox pattern** (Module 16): write the event to the DB in the same transaction, and relay it |

## Broker side

Replication factor 3 across zones; don't allow "unclean" leader election (an out-of-date replica becoming leader),
which would silently lose acknowledged records.

## Consumer side

```
poll → process → commit offset        at-least-once (duplicates after a crash)
poll → commit offset → process        at-most-once (loss after a crash)
```

At-least-once is the usual choice, so **processing must be idempotent** (lesson 12.4).

## "Exactly-once" in Kafka

Kafka offers **transactions**: a consumer-producer can atomically write output records *and* commit its input
offsets. For **Kafka → Kafka** pipelines (read, transform, write), each input affects the output exactly once.

The guarantee stops at Kafka's boundary. If processing also writes to Postgres or calls an email API, those effects
need their own idempotency:
- store the processed offset (or event id) **in the same database transaction** as the effect;
- or dedupe by event id in the target system.

## Choosing per topic

| Data | Acceptable | Setup |
|------|------------|-------|
| Click analytics | Rare loss or duplicates are fine | `acks=1`, at-least-once, approximate counts |
| Orders, payments | No loss; duplicates harmless | Outbox, `acks=all`, idempotent producer, idempotent consumers |
| Kafka-to-Kafka aggregations | Exact | Kafka transactions / Streams `exactly_once_v2` |

## Ordering and retries

With the idempotent producer, Kafka keeps per-partition ordering even with retries. Without it, retries with
several in-flight requests can **reorder** records. Another reason to enable idempotence.

## Try it

A service consumes `PaymentSucceeded` events and inserts a row into `invoices`. After a consumer crash, some customers
got two invoices. Give a fix that works even though the consumer will keep reprocessing after crashes.

<details>
<summary>Answer</summary>

Make the insert idempotent: a unique constraint on `invoices.payment_id` (or the event id), with
`INSERT … ON CONFLICT DO NOTHING`. Optionally store the consumed offset in the same transaction and resume from it on
restart. Reprocessed events then hit the constraint and change nothing.
</details>

## Key takeaways

- Loss and duplication can happen at the producer, the broker or the consumer.
- Use idempotent producers, `acks=all` with `min.insync.replicas=2`, and the outbox for DB+event atomicity.
- Consumers are at-least-once by default; make processing idempotent.
- Kafka transactions give exactly-once only within Kafka; external effects need their own dedupe.

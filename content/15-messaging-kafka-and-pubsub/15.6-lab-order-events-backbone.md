# Lab: an order events backbone

An e-commerce company wants every service (billing, inventory, shipping, email, search, analytics, fraud) to react to
order changes through one event backbone, with no more point-to-point calls.

> **Interactive version:** [open the Order events lab](#/labs/order-events) for the decisions as checked steps.

## Step 1: Topics and keys

<details>
<summary>Reference</summary>

One topic `orders` carrying `OrderPlaced`, `OrderPaid`, `OrderShipped`, `OrderCancelled`… Key = `order_id`, so each
order's events stay in order. 48 partitions for growth. Schemas in a registry with backward compatibility.
</details>

## Step 2: Producing reliably

<details>
<summary>Reference</summary>

The orders service writes the order **and** an outbox row in one DB transaction; a relay (or CDC, Debezium) publishes
outbox rows to Kafka with an idempotent producer, `acks=all`, `min.insync.replicas=2`.
</details>

## Step 3: Consumers

<details>
<summary>Reference</summary>

One consumer group per service. Each consumer is idempotent (dedupe by event id in the same transaction as its
effect). Lag alerts per group, in minutes. A dead-letter topic per group for poison events.
</details>

## Step 4: Replay and new consumers

<details>
<summary>Reference</summary>

Retain 14 days (plus a compacted "order-state" topic with the latest state per order). A new fraud model starts a new
group from 14 days ago to backfill, with no change to producers.
</details>

# Consumer groups

A **consumer group** is a set of consumer instances that share the work of reading a topic. Each partition is
assigned to **exactly one** consumer in the group at a time, which is how Kafka gets both parallelism and per-partition
ordering.

```
topic with 6 partitions, group "billing" with 3 consumers:
 C1 ← P0, P1      C2 ← P2, P3      C3 ← P4, P5
```

- Add consumers (up to the partition count) to process faster.
- Consumers beyond the partition count sit **idle**.
- Different groups (billing, search, analytics) each get **all** the data independently.

## Rebalancing

When a consumer joins, leaves or crashes, partitions are **reassigned**.
- During a classic ("eager") rebalance, the whole group pauses briefly.
- **Cooperative / incremental** rebalancing moves only the affected partitions. Prefer it.
- A consumer that takes too long between polls (`max.poll.interval.ms`) is considered dead and triggers a rebalance.
  Keep the per-batch work bounded.

## Consumer lag

**Lag** = latest offset − committed offset, per partition. It's the number one metric for consumers.

```
P0: end 1,204,331 · committed 1,204,300 → lag 31      ✅
P3: end 1,207,990 · committed 1,141,002 → lag 66,988  ⚠️ falling behind
```

- Growing lag on **all** partitions: the group is too slow, so add consumers (if partitions allow) or make processing
  faster.
- Growing lag on **one** partition: a hot key or a stuck consumer.
- Alert on lag in **time** ("events are 5 minutes behind"), which is what the business cares about.

## Committing offsets

| Strategy | Effect |
|----------|--------|
| Commit **before** processing | At-most-once: a crash after commit loses the record |
| Commit **after** processing | At-least-once: a crash before commit reprocesses it (the default; make processing idempotent) |
| Commit with the output **in one transaction** | Effectively-once within Kafka (transactions), or store offsets in your DB with the results |

## Parallelism within a partition

Need more throughput than one consumer per partition gives, while keeping order per key? Process **by key** inside
the consumer: records for different keys in parallel, records for the same key in order (e.g. Confluent's parallel
consumer). Or increase partitions up front.

## Poison records

A record that always fails blocks its partition, because ordering means you can't skip ahead. Retry a few times, then
send it to a **dead-letter topic** with the error and move on, accepting that this key's later events may now be
processed without it. Decide whether that's acceptable per topic.

## Try it

A group of 4 consumers reads a 4-partition topic. Lag is growing steadily on all partitions during peak. You scale to
8 consumers, but lag doesn't improve. Why, and what are the options?

<details>
<summary>Answer</summary>

With 4 partitions, only 4 consumers can be active: the extra 4 are idle. Options: speed up per-record processing
(batching, async I/O, fewer synchronous calls); parallelise by key within each consumer; or increase the partition
count (planned carefully, since it changes key → partition mapping).
</details>

## Key takeaways

- A group shares a topic's partitions; one consumer per partition at a time.
- Parallelism is capped by the partition count.
- Watch lag per partition, in time; prefer cooperative rebalancing.
- Commit after processing and make it idempotent; dead-letter poison records.

# Topics, partitions and offsets

Kafka's model is small: **topics** split into **partitions**, each an ordered log of records with **offsets**.
Almost every design decision is about the partition key.

## Topics and partitions

```
topic "orders" (6 partitions)
 P0: o17 o42 o17 o88 …
 P1: o3  o3  o91 …
 …
 P5: o56 o12 …
```

- A **partition** is the unit of ordering, parallelism and storage. Each lives on a broker (with replicas on others).
- **Ordering is guaranteed only within a partition**, never across the topic.
- More partitions means more parallelism, but also more files, more leader elections and more rebalance work. Size
  them for expected throughput with room to grow; tens to low hundreds per topic is common.

## The partition key

A producer sends `(key, value)`; Kafka picks the partition with `hash(key) % partitions`.

| Key | Effect |
|-----|--------|
| `order_id` | All events for one order are in order; orders spread across partitions |
| `customer_id` | All of a customer's events in order (e.g. balance changes) |
| none (null) | Spread round robin; **no ordering** between related events |
| `country` | Few distinct values: India's partition becomes a hot spot |

Choose the key by **what must stay in order**, with enough distinct values to spread the load.

> Changing the partition count changes `hash % N`: keys move to different partitions, and ordering across the change
> is lost. Plan partition counts up front.

## Offsets and retention

- Each record in a partition has an increasing **offset**.
- Consumers commit the offset they've processed; on restart they resume from there.
- **Retention** is by time (e.g. 7 days) or size. Records are kept whether or not anyone read them.
- **Log compaction** (optional) keeps only the latest record per key, turning a topic into a durable table of
  "current values" (great for changelogs).

## Durability settings

| Setting | Meaning |
|---------|---------|
| `replication.factor=3` | Each partition on 3 brokers |
| `acks=all` | The producer waits until all in-sync replicas have the record |
| `min.insync.replicas=2` | Writes fail if fewer than 2 replicas are in sync (prevents silent loss) |
| `enable.idempotence=true` | Producer retries don't create duplicates within a partition |

`acks=all` with `min.insync.replicas=2` and RF=3 is the usual "don't lose data" baseline.

## Throughput intuition

A single partition handles roughly tens of MB/s. Throughput scales with partitions × brokers. Consumers scale too, up
to **one consumer per partition per group** (lesson 15.3).

## Try it

A payments topic must keep each account's debits and credits in order. Traffic is 40,000 events/s; one consumer
instance processes ~2,000 events/s. Choose the key and the partition count.

<details>
<summary>Answer</summary>

Key = **`account_id`** (per-account ordering; many accounts spread load). You need ≥ 20 consumers in parallel, so ≥ 20
partitions. Choose **48–64** for growth headroom, since changing the count later reshuffles keys. RF = 3, `acks=all`,
`min.insync.replicas=2`, idempotent producer.
</details>

## Key takeaways

- Topics are split into partitions: the units of order, parallelism and storage.
- Order exists only within a partition; choose the key by what must stay ordered.
- Offsets let consumers resume; retention keeps data regardless of reads; compaction keeps the latest per key.
- RF = 3, `acks=all`, `min.insync.replicas=2` and idempotent producers prevent loss and duplicates.

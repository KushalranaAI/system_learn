# When a model becomes a component

For 32 modules the boxes on your diagrams have been predictable. A database returns the row you wrote. A cache
returns the value or a miss. A service either answers in 20 ms or times out. Add a large language model (LLM) and
you get a box that breaks all three habits: it is **probabilistic**, it is **slow**, and every call **costs real
money**. This lesson is about what changes in the rest of the architecture because of that one box.

## Three properties that change everything

| Property | Classic service | LLM call | What it forces on the design |
|----------|-----------------|----------|------------------------------|
| Output | Deterministic: same input, same output | A sample: same prompt can give different answers, some wrong | Validation, evals, guardrails, "is this answer good?" as a metric |
| Latency | 5-50 ms | 0.3-1 s to the first token, 5-30 s for a long answer | Streaming, async jobs, timeouts measured in seconds |
| Cost per call | Fractions of a millionth of a dollar | About $0.001-$0.05 for a typical chat turn (order of magnitude) | Per-request cost accounting, budgets, caching, routing |
| Capacity | Thousands of req/s per server | A handful of req/s per GPU replica | GPU capacity planning, queues, token-based rate limits |

Lesson 33.2 turns these into numbers. For now notice the ratios: an LLM call is roughly **100x slower** and
**10,000x more expensive** than the database query next to it.

## A request, before and after

```
Before:   client → LB → API server → cache → database            ~30 ms, ~$0.000001

After:    client → LB → API server ─┬→ semantic cache (33.5)
                                    ├→ vector DB  (retrieval, module 34)
                                    ├→ LLM gateway (33.4) → model API or GPU fleet (33.3)
                                    └→ database   (history, users, billing)
                                                                  ~1-10 s, ~$0.01
```

Everything you already know still applies. The LLM is just another dependency, but one whose latency, cost and
error rate are all two to four orders of magnitude worse than anything else on the path.

## What changes in the architecture

**1. Long-lived connections.** A 10-second answer is unacceptable as a blank wait, so you stream tokens over
server-sent events (lesson 33.6). Now your load balancers, proxies and API servers hold many concurrent streams, the
same problem as [lesson 6.2](#/lesson/6.2). Idle timeouts of 30-60 s on proxies start cutting off long answers.

**2. Timeouts and retries get expensive.** A retry of a database read costs nothing. A retry of a 4,000-token
generation costs another 4,000 tokens and another 10 seconds. The rules of [lesson 12.2](#/lesson/12.2) still hold,
but the timeout is now 30-120 s and you retry at most once, ideally on a different provider (33.4).

**3. Rate limits are in tokens, not requests.** Providers limit you by tokens per minute as well as requests per
minute. One user pasting a 100-page PDF uses as much quota as 500 normal users. Your own limiter
([module 8](#/lesson/8.3)) must count tokens too.

**4. Cost is a per-request property.** You need token accounting per user, per feature and per tenant, the same way
you track latency. A bug that loops a prompt can spend thousands of dollars in an afternoon.

**5. Async becomes normal.** Summarise a document, classify a ticket backlog, embed a corpus: these go through a
queue and workers ([lesson 7.2](#/lesson/7.2)), often using a provider's batch API at a discount, because nobody is
waiting.

**6. Quality is a new failure mode.** The call returned 200 OK in 2 seconds, and the answer is wrong. Your
dashboards will not show it. You need evals (lesson 36.1), sampling of real traffic and user feedback signals. "Up"
is no longer the same as "working".

**7. New data flows and new data risks.** Prompts contain user data, retrieved documents and system instructions. They
go to a third party unless you self-host (33.7). Logs of prompts are now sensitive data. Retrieved documents can
contain instructions that hijack the model (prompt injection, lesson 36.4).

## Where the model's weakness is the design's job

| Model behaviour | Design response |
|-----------------|-----------------|
| Makes things up | Retrieval with citations (module 34); "answer only from context" plus a groundedness check |
| Output shape varies | Structured outputs (JSON schema), validate and retry once |
| Slow | Stream; cache; smaller model for easy requests; precompute in background |
| Expensive | Cache, route, trim prompts, cap output tokens, per-tenant budgets |
| Provider outages and 429s | Gateway with fallbacks to another provider or model; degraded mode without AI |
| Non-deterministic | Log prompt, model version and parameters on every call so you can replay it |

The last row matters more than it looks. Pin the model version (for example a dated snapshot, not "latest"),
because a silent provider upgrade changes your product's behaviour without a deploy.

## A degraded mode is part of the design

Ask the same question you asked about every dependency in [lesson 12.3](#/lesson/12.3): what does the product do
when this is down? For a help centre the answer might be "show the top search results without a generated
summary". For a coding tool it might be "fall back to a smaller model". Design this before launch, not during the
first provider outage.

## Exploring it in the sandbox

The sandbox has three AI node kinds: **LLM inference** (model tier small, medium or large; replicas; continuous
batching on or off), **vector database** (replicas) and **agent runtime**. Wire an API server to an LLM and its reads
become prompts that flow cache (as a semantic cache) → vector DB → model. Start from the
[chat serving scenario](#/sandbox?preset=ai-chat-serving) and notice how few requests per second one model replica
serves compared with the database next to it.

## Try it

You run a recipe website: server-rendered pages, Postgres, Redis, a CDN, 2,000 requests/s at peak. Product wants an
"ask the chef" chat box on every recipe page. List what changes in the architecture.

<details>
<summary>Reference</summary>

- **New dependency path:** API server → LLM gateway → model provider (or GPUs). Expect 1-10 s per answer versus
  ~30 ms for a page.
- **Streaming:** SSE endpoint; raise proxy and LB idle timeouts; disable response buffering; count concurrent
  streams as a capacity metric.
- **Capacity and cost:** if 2% of page views ask a question, that's 40 chats/s at peak, maybe 2,000 input and 300
  output tokens each. Budget it per day, set per-user limits in tokens, cap `max_tokens`.
- **Rate limits:** token-based limits per user and per IP to stop someone using you as a free LLM.
- **Caching:** the CDN can't cache chat. Add a cache for common questions per recipe ("can I freeze this?") and
  structure prompts so the recipe text is a stable prefix that providers can cache (33.5).
- **Context:** pass the recipe (and maybe related recipes from a vector search) into the prompt.
- **Quality and safety:** an eval set of chef questions, output filters (allergy and food-safety claims), logging of
  prompts and model versions, a feedback button.
- **Failure:** timeout ~30 s, one retry on a fallback model, and a degraded mode that hides the box or shows an FAQ.
- **Privacy:** decide what user data goes into prompts and how long prompt logs are kept.
</details>

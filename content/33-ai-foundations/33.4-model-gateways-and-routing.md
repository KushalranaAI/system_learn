# Model gateways and routing

Once two teams call two model providers, you see the same problems everywhere: API keys copied into ten services, no
idea who spent what, every service writing its own retry loop, and an outage at one provider taking down every AI
feature. The fix is the one you already know from API gateways ([lesson 11.4](#/lesson/11.4)): put a **gateway** in the middle.

## What an LLM gateway does

```
services ──► LLM gateway ──┬──► provider A (frontier model)
                            ├──► provider B (same-class model, fallback)
                            ├──► provider C (cheap small model)
                            └──► self-hosted vLLM fleet
          ▲
          └ logs, token accounting, budgets, caching, guardrails
```

| Job | Detail |
|-----|--------|
| One API | Usually an OpenAI-compatible endpoint; services name a logical model (`support-default`), not a provider |
| Credentials | Provider keys live only in the gateway; services get scoped virtual keys |
| Token accounting | Input, cached and output tokens per key, team, feature and tenant; cost in dollars |
| Budgets and rate limits | Tokens per minute and dollars per day, per key or tenant |
| Reliability | Timeouts, retries, fallbacks, cooldown of unhealthy deployments, load balancing across regions or keys |
| Caching | Exact and semantic caches (33.5) |
| Policy | PII redaction, guardrails, logging rules, which data may go to which provider |

Open-source options include LiteLLM's proxy; managed options include Cloudflare AI Gateway and similar features in
cloud platforms and API management products. It is also a natural home for observability (lesson 36.2).

The gateway adds a hop of a few milliseconds, which is noise next to a 1-10 s model call. The real risk is that it
becomes a **single point of failure** for every AI feature: run it stateless, replicated, with its state (budgets,
counters) in Redis like any rate limiter ([lesson 8.4](#/lesson/8.4)).

## Fallbacks

Providers return 429s (rate limited), 5xx and overloaded errors, and sometimes just get slow. A fallback chain:

```
support-default:
  1. provider A, model X     timeout 30 s, 1 retry on 429/5xx with backoff
  2. provider B, model Y     (similar quality, different provider)
  3. provider C, small model (degraded but answers)
cooldown: a deployment that fails 3 times in a minute is skipped for 60 s
```

This is the circuit breaker from [lesson 12.3](#/lesson/12.3) applied to providers. Two cautions:

- **Fallback models behave differently.** Prompts tuned for one model may break output formats on another. Run your
  evals against every model in the chain, not just the primary.
- **Don't retry what will fail again.** A 400 for a too-long context will fail on every provider with the same window.
  Fall back to a model with a bigger window, or truncate.

## Token-based rate limits

Request counts are a poor proxy for load: one request can be 200 tokens or 200,000. Gateways limit on **tokens per
minute** (TPM), using the token bucket from [lesson 8.2](#/lesson/8.2), with tokens as the unit:

1. Before the call, **estimate**: count input tokens, add `max_tokens` for output. Reserve that from the bucket; reject
   with 429 if empty.
2. After the call, **reconcile** with the actual usage the provider reports and refund the difference.

Layer the limits: per user (stop abuse), per tenant (fairness), per feature (protect the checkout path from the
batch summariser), and a global cap that stays under your provider quota with headroom.

## Routing: not every prompt needs the big model

Price differences between model tiers are often **10-50x**. Many requests ("reset my password", "translate this
sentence") are easy. Routing sends each request to the cheapest model likely to do it well.

| Strategy | How | Trade-off |
|----------|-----|-----------|
| Static rules | By feature, tenant tier, prompt length, language | Simple, predictable, coarse |
| Classifier router | A small model or trained classifier predicts "needs big model?" | Extra ~10-50 ms; needs labelled data |
| Cascade | Try the small model first; check the answer; escalate if it fails | Escalated requests pay twice and wait longer |

Research such as FrugalGPT and RouteLLM reported large cost reductions (around 2x or more at similar quality on their
benchmarks) from routing and cascades. Your mileage depends entirely on your traffic mix, so measure it.

### Cascade math

Small model costs 1/20 of the big one (relative cost 0.05); 70% of answers pass the check.

```
router (perfect):  0.7 × 0.05 + 0.3 × 1        = 0.335  → ~3x cheaper
cascade:           1.0 × 0.05 + 0.3 × 1 + check = 0.35 + check
latency (cascade): 70% fast; 30% pay small-model time + check + big-model time
```

The check is the hard part: a self-reported confidence, a verifier model, a schema validation, or a cheap heuristic
(did it refuse? did it cite a source?). A bad check either escalates everything (no savings) or lets wrong answers
through (quality loss). Measure both on a labelled set.

## Try it

Your support assistant sends everything to a frontier model. Logs show: 55% of requests are FAQ-style ("where is my
order", "change my email"), 30% need reasoning over the user's account, 15% are complaints that need care. The small
model costs 1/25 of the frontier model. Design routing for easy prompts.

<details>
<summary>Reference</summary>

- **Router:** a small classifier (or the small model with a short classification prompt) labels each request FAQ,
  account or complaint. Rules add signals: very long inputs and enterprise tenants go to the big model.
- **FAQ (55%) → small model** with retrieved help articles. Validate: answer must cite an article; otherwise escalate.
- **Account reasoning (30%) → frontier** (or a mid-tier model if evals show it's good enough).
- **Complaints (15%) → frontier**, with a human hand-off option.
- **Cost:** if 90% of FAQ answers pass, relative cost ≈ 0.55 × 0.04 + 0.55 × 0.1 × 1 + 0.45 × 1 ≈ 0.022 + 0.055 +
  0.45 ≈ **0.53**, about half the bill.
- **Guard quality:** run the eval set per route; sample production FAQ answers for review; track escalation rate and
  thumbs-down rate per route. Put routing in the gateway so services keep calling one logical model name.
</details>

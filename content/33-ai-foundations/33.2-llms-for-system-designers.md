# LLMs for system designers

You don't need to know how a transformer is trained to design around one. You need five things: what a token is,
what the context window limits, the two phases of a call (prefill and decode), the two latency numbers that come out
of them (TTFT and tokens per second), and how the bill is computed. All of them are measured in tokens.

## Tokens

A model reads and writes **tokens**: sub-word pieces from a fixed vocabulary (typically 100k-200k entries).

| Rule of thumb (English) | Value |
|-------------------------|-------|
| Characters per token | about 4 |
| Words per token | about 0.75 (so 1,000 words ≈ 1,300 tokens) |
| A page of prose | about 500-700 tokens |
| Code, JSON, non-Latin scripts | noticeably more tokens per character |

Every limit, price and latency number is in tokens, so the first step of any estimate is "how many tokens in, how
many out?" Always count with the provider's tokenizer before trusting an estimate.

## The context window

The **context window** is the maximum tokens per call, input plus output: from about 8k on small open models to
128k-1M+ on hosted frontier models. Design consequences:

- A chat has no memory: **every turn resends the whole conversation**. Turn 20 carries turns 1-19.
- Long context is not free: cost and prefill time grow with input length, and models use information in the middle
  of a long prompt less reliably than at the start or end ("lost in the middle").
- You need a policy for what to drop or summarise when a conversation outgrows the window (lesson 35.4).

## Prefill and decode

A call has two phases with different bottlenecks:

```
prompt (6,000 tokens) ──► PREFILL: process all input tokens in parallel ──► first token
                          compute-bound, ~100s of ms
first token ──► DECODE: one token per forward pass, each depends on the last ──► ... ──► token 400
                memory-bandwidth-bound, ~10-30 ms per token
```

**Prefill** is like a big matrix multiply over all input tokens at once: GPUs are good at it. Rough FLOPs are
`2 × parameters × input tokens`. For a 70B model and 2,000 tokens: 2 × 70e9 × 2,000 = 2.8e14 FLOPs. Four H100s at
about 1e15 FLOP/s each and ~50% efficiency do that in about **0.14 s**.

**Decode** is sequential. To produce each token the GPU must read **all the weights** from memory. A 70B model in
16-bit is 140 GB; four H100s together read about 13 TB/s, so one decode step takes at least 140 / 13,400 s ≈
**10 ms**, a ceiling of about 100 tokens/s for one sequence no matter how fast the compute is. This is why serving
systems batch many sequences together (33.3): one pass over the weights then produces a token for each of them.

## The two latency numbers

| Metric | What it is | Typical hosted range | Driven by |
|--------|------------|----------------------|-----------|
| **TTFT** (time to first token) | request sent → first token arrives | 0.2-1 s; seconds for huge prompts | queueing, network, prefill (input length) |
| **TPOT / tokens per second** | time per output token after the first | 30-150 tokens/s per stream | model size, batch size, hardware |

```
total latency ≈ TTFT + output_tokens / tokens_per_second
```

Output length dominates. 500 output tokens at 50 tokens/s is 10 s, whatever you do to TTFT. The cheapest latency
win is usually **asking for shorter answers** (and setting `max_tokens`). Reasoning models add hidden "thinking"
tokens before the visible answer: they cost and take time like any other output token.

Reading speed is about 4-5 words per second, so a stream at 30+ tokens/s already outruns the reader. With streaming,
TTFT becomes the number users feel (33.6).

## Pricing by token

APIs charge per million tokens, with separate prices for input and output. Output is typically **3-5x** the input
price because decode is the expensive phase. Approximate 2025-2026 ranges (they change often, so treat these as
orders of magnitude):

| Tier | Input, $ per 1M tokens | Output, $ per 1M tokens |
|------|------------------------|--------------------------|
| Small / "mini" models | ~0.05-0.5 | ~0.2-2 |
| Mid-tier models | ~1-3 | ~5-15 |
| Frontier / reasoning models | ~3-15+ | ~15-75+ |

Discounts that matter in design: **cached input** (prefix caching, 33.5) is billed at a fraction of the normal input
price, and **batch APIs** for non-urgent work are typically about half price.

## A worked chat turn

A support chat on a mid-tier model, with illustrative prices of $2 per million input and $10 per million output
tokens:

| Part of the prompt | Tokens |
|--------------------|--------|
| System prompt and instructions | 1,500 |
| Conversation so far (5 turns) | 3,000 |
| Retrieved help articles | 2,000 |
| User's new message | 100 |
| **Input total** | **6,600** |
| Output | 400 |

```
cost    = 6,600 × $2/1M + 400 × $10/1M = $0.0132 + $0.0040 ≈ $0.017 per turn
latency ≈ TTFT 0.5 s + 400 / 60 tokens/s ≈ 0.5 + 6.7 ≈ 7 s (streamed)
at 1M turns/day ≈ $17,000/day before caching
```

Notice that input dominates cost here, even at a fifth of the price, because chat resends history. Prefix caching
the system prompt and earlier turns, and trimming the history, attack exactly this term.

## Capacity is in tokens too

Providers grant you **tokens per minute (TPM)** and **requests per minute (RPM)** per model. At 7,000 tokens per turn,
a 2M TPM quota allows about 285 turns per minute, under 5 per second. Plan capacity in tokens, not requests.

## Try it

Estimate the cost and latency of one chat turn for a coding assistant: 2,000-token system prompt, 8,000 tokens of
code context, 1,000 tokens of history, a 50-token question and a 600-token answer. Use $3 per million input,
$15 per million output, TTFT 0.8 s, 70 tokens/s. Then: what if 6,000 of the input tokens hit a prefix cache billed
at 10% of the input price?

<details>
<summary>Reference</summary>

Input = 2,000 + 8,000 + 1,000 + 50 = 11,050 tokens.

- Cost: 11,050 × 3/1M = $0.0332; output 600 × 15/1M = $0.0090; total ≈ **$0.042 per turn**.
- Latency: 0.8 + 600 / 70 ≈ 0.8 + 8.6 ≈ **9.4 s** total, first token after 0.8 s if streamed.
- With 6,000 cached tokens: 5,050 × 3/1M + 6,000 × 0.3/1M = $0.0152 + $0.0018 = $0.0170 input, so ≈ **$0.026 per
  turn**, about 38% cheaper. TTFT also drops because the cached prefix skips prefill.
- The output (8.6 s) is now the biggest latency term: asking for a shorter answer, or a diff instead of the whole
  file, helps more than anything on the input side.
</details>

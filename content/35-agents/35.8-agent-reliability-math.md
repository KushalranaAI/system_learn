# Agent reliability math

Availability math ([lesson 18.2](#/lesson/18.2)) says components in series multiply: three 99.9% services in a chain give 99.7%.
Agents obey the same rule, except each "component" is a model step that is right maybe 95-99% of the time, not
99.9%. That is why impressive demos turn into unreliable products.

## Compounding step errors

If each step succeeds independently with probability *p*, a task of *n* steps succeeds with *pⁿ*:

| Per-step success | 5 steps | 10 steps | 20 steps | 50 steps |
|-----------------:|--------:|---------:|---------:|---------:|
| 90% | 59% | 35% | 12% | 0.5% |
| 95% | 77% | 60% | 36% | 8% |
| 99% | 95% | 90% | 82% | 61% |
| 99.5% | 98% | 95% | 90% | 78% |

For a 10-step task to succeed 95% of the time, each step needs 0.95^(1/10) ≈ **99.5%**. Few raw model steps are
that good. (Real errors aren't fully independent, and a good agent can notice and fix an earlier mistake, so this is
a rough guide, but the shape holds: long chains of unchecked steps fail.)

## Three levers

### 1. Fewer steps

- Better tools: one `get_customer_summary` instead of four calls ([lesson 35.2](#/lesson/35.2)).
- Move fixed logic out of the model into code (a workflow, [lesson 35.1](#/lesson/35.1)). Code steps are ~100% reliable.
- 5 steps at 99% = 95%. Halving the steps can do more than a better model.

### 2. Verify and retry

Add a check after risky steps: schema validation, a unit test, a rule in code, or a second model call that grades the
output. If the check fails, retry the step.

Let the step be right 95% of the time and the verifier catch a share *d* of the bad outputs. Per attempt:
good 0.95, bad-but-caught 0.05·d, bad-and-missed 0.05·(1−d).

| Verifier catches | Retries | Step success | 10-step task |
|-----------------:|--------:|-------------:|-------------:|
| none | 0 | 95.0% | 60% |
| 90% | 1 | 99.28% | 93% |
| 90% | 2 | 99.47% | 95% |
| 99% | 1 | 99.70% | 97% |

```
step fails = missed·(1 + caught + caught²...) + caught^(retries+1)
90%, 2 retries: 0.005·(1 + 0.045 + 0.045²) + 0.045³ ≈ 0.0053  → step 99.47%
```

The **verifier's catch rate** matters more than the number of retries: once errors slip past the check, retries
don't help. Cheap deterministic checks (does it compile, does the JSON match, does the total add up) are the best
verifiers you have.

### 3. Step limits and escalation

Some runs never converge: the model retries a failing tool, re-reads the same page, or argues with itself. A step
limit turns an unbounded run into a bounded failure, which you then **escalate** (to a human, or "I couldn't finish;
here's what I found"). A clean escalation is a success from the user's point of view; a 4-minute spinner is not.

## Cost per task

Each step re-sends the growing context. With a 3,000-token start, 1,500 tokens added per step and 300 output tokens
per step:

```
input  = Σ (3,000 + 1,500·(i−1)) for i = 1..10 = 30,000 + 67,500 = 97,500 tokens
output = 10 × 300 = 3,000 tokens
at $3 / M input, $15 / M output: 0.29 + 0.045 ≈ $0.34 per task
```

Retries add about (1 − p_step) of extra steps; a model-graded verifier adds a call per checked step. Prefix caching
cuts the repeated input sharply ([lesson 33.5](#/lesson/33.5)); compaction keeps the per-step input from growing without bound
([lesson 35.4](#/lesson/35.4)).

The long tail matters more than the mean. In this course's simulator, about 4% of agent tasks run away to 30 steps
when there is no step limit:

```
mean steps without limit (8-step tasks) = 0.96 × 8 + 0.04 × 30 = 8.9   (+11% cost)
p99 steps = 30                                                       (3.75× latency and cost)
```

That is why the limit is mainly a **tail-latency and budget control**, and why you budget for *cost per successful
task*: `cost per attempt ÷ success rate`. A $0.34 agent that succeeds 60% of the time costs $0.57 per success, plus
the human time to handle the 40%.

## Measuring it for real

You won't know *p* from theory. Run the agent on an eval set many times ([lesson 36.1](#/lesson/36.1)), log every step ([lesson 36.2](#/lesson/36.2)),
and track: task success rate, steps per task (p50/p99), cost per successful task, escalation rate, and which step
type fails most. Improve the worst step first.

## Try it

Your 10-step agent succeeds 60% of the time (about 95% per step). Make it 95% reliable. You can't change the model.

<details>
<summary>Reference</summary>

Target: 0.95^(1/10) ≈ 99.5% per step, or fewer steps.

1. **Cut steps:** merge lookups into higher-level tools and move fixed parts into code: 10 model steps → 6.
   At 95% that alone gives 0.95⁶ ≈ 74%.
2. **Verify each remaining step:** deterministic checks where possible (schema, totals, tests), a grader call
   elsewhere; aim for 90%+ catch rate, up to 2 retries → ~99.5% per step → 0.995⁶ ≈ 97%.
3. **Step limit** (e.g. 12) with escalation, so failures end fast and visibly instead of running to 30 steps.
4. **Measure** on an eval set; check that the cost per successful task went *down* even though checks add calls.
</details>

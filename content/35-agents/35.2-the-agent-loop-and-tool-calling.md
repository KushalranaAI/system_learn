# The agent loop and tool calling

Every agent, however it is marketed, is this loop:

```
messages = [system prompt, tool definitions, user task]
loop:
    response = llm(messages)                  # think
    if response has no tool calls: return response.text      # done
    for call in response.tool_calls:          # act
        result = run_tool(call.name, call.args)
        messages.append(call, result)         # observe
    if steps > STEP_LIMIT or cost > BUDGET: stop and escalate
```

The model never executes anything. It **emits a request** ("call `get_order` with `{"id": "A123"}`"), and **your
runtime** decides whether to run it, runs it, and feeds the result back as text. That gap between "the model asked"
and "the code did" is where you put validation, permissions and logging.

## Anatomy of one step

```
            ┌──────────────── context window ────────────────┐
runtime ──► │ system + tool schemas + history + last result  │ ──► LLM
            └────────────────────────────────────────────────┘
LLM ──► { "tool": "get_order", "args": { "id": "A123" } }
runtime: validate args against schema → check permission → call Orders API (timeout 2 s)
runtime ──► append { "result": {"status": "shipped", "eta": "2026-10-27"} } ──► next step
```

Each step is a full model call over the **whole growing context**. Step 10 re-reads steps 1-9 (prefix caching,
[lesson 33.5](#/lesson/33.5), makes that cheaper but not free). Latency and cost grow with the number of steps, and the input grows
with each step, so cost grows faster than linearly unless you trim context ([lesson 35.4](#/lesson/35.4)).

## Tool schemas

A tool is a name, a description and a JSON Schema for its arguments:

```json
{
  "name": "refund_order",
  "description": "Refund a delivered order. Use only after get_order shows status=delivered. Max 200 EUR; above that, call escalate_to_human.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "pattern": "^A[0-9]{3,10}$" },
      "amount_eur": { "type": "number", "minimum": 0, "maximum": 200 },
      "reason": { "type": "string", "enum": ["damaged", "late", "not_received", "other"] }
    },
    "required": ["order_id", "amount_eur", "reason"]
  }
}
```

The description is a prompt: the model reads it to decide when to call the tool. Treat tool design like API design
for a junior developer (Anthropic calls it the agent-computer interface):

- **Few, high-level tools** beat many thin ones. `get_customer_summary` beats `get_customer` + `get_orders` +
  `get_tickets` that the model must stitch together.
- **Make mistakes hard:** enums instead of free text, absolute paths instead of relative ones, ids validated by
  pattern.
- **Return what the model needs**, not your whole database row. A 40 KB JSON response eats context on every later
  step.
- **Errors are results.** Return `"error: order A123 not found; check the id with the customer"`, not a stack trace.
  The model can recover from a clear message.

## Structured outputs

Most providers can constrain the model's output to a JSON Schema ("structured outputs" or "strict" tool mode), so the
arguments always parse. That removes parse errors, not **logic** errors: a valid `amount_eur: 200` can still be the
wrong amount. Validate business rules in code, on the server side of the tool, exactly as you would for a public API.

## Stopping conditions

An agent needs several ways to stop, because the model's own "I'm done" is not enough:

| Condition | Why |
|-----------|-----|
| Model returns a final answer (no tool calls) | Normal success |
| **Step limit** (e.g. 15) | Stops loops: retrying the same failing tool forever |
| **Token or money budget** per task | Caps the long tail of expensive runs |
| **Wall-clock deadline** | A user-facing request can't wait 5 minutes |
| Repeated identical tool call | Cheap loop detector |
| A tool returns "needs human" | Hand off instead of guessing |

When a limit trips, **escalate** (hand to a human, return a partial answer with a note) rather than fail silently.
In the simulator's agent node, about 4% of tasks run away to 30 steps when there is no step limit; the
[agent reliability simulation](#/sims/agent-reliability) shows what that does to cost and p99.

## Latency budget of a run

A step costs one model call (time to first token plus output) plus the tool call:

```
step ≈ 0.6 s (model, short output) + 0.2 s (tool) = 0.8 s
8 steps ≈ 6.4 s, plus a final answer streamed to the user
```

Ways to cut it: run independent tool calls **in parallel** in one step (most APIs allow several tool calls per
response), keep outputs short, use a small model for simple steps, and stream progress ("Looking up your order...")
so the wait feels shorter.

## Try it

Trace one run. A user writes: "My order A123 arrived broken, I want my money back." Tools: `get_order`,
`refund_order` (limit 200 EUR), `escalate_to_human`. The order is 80 EUR and delivered. Write the steps, the messages
added to the context, and where your code (not the model) checks something.

<details>
<summary>Reference</summary>

1. **Think/act:** model calls `get_order({"order_id": "A123"})`. Runtime validates the id pattern, checks the order
   belongs to the logged-in customer (the model can't be trusted to do this), calls the Orders API.
2. **Observe:** result `{status: delivered, total_eur: 80}` appended.
3. **Act:** model calls `refund_order({"order_id": "A123", "amount_eur": 80, "reason": "damaged"})`. Runtime checks
   schema, amount ≤ order total, amount ≤ 200, no refund already exists, then calls Payments with an
   **idempotency key** (e.g. `refund:A123`) so a retry can't refund twice.
4. **Observe:** `{refund_id: R9, status: pending}` appended.
5. **Final answer:** no tool calls; model writes the reply. Stop.

Four model calls, two tool calls, about 3-4 s. Checks that live in code: ownership, amount limits, duplicate refund,
idempotency, step limit (say 10) and an overall timeout.
</details>

# Workflows vs agents

"Agent" is the most overloaded word in AI. For a system designer the useful split comes from Anthropic's
*Building effective agents* post:

- A **workflow** runs LLM calls and tools along **code paths you wrote**. Your code decides what happens next.
- An **agent** lets the **model decide** what happens next: which tool to call, with what arguments, and when it is
  done.

That one difference decides almost everything else: how predictable latency and cost are, how you test it, and what
can go wrong.

| | Workflow | Agent |
|--|----------|-------|
| Control flow | Your code (a DAG or state machine) | The model, inside a loop |
| Number of LLM calls | Known in advance (e.g. 3) | Varies per task (3 to 30+) |
| Latency and cost | Predictable, easy to budget | A distribution with a long tail |
| Testing | Unit-test each step | Evals over many runs ([lesson 36.1](#/lesson/36.1)) |
| Failure | A step fails, you retry the step | The model can loop, wander or pick the wrong tool |
| Best for | Tasks you can describe as steps | Open-ended tasks whose steps you can't predict |

The building block of both is the **augmented LLM**: a model call that can also use retrieval, tools and memory.

## The five workflow patterns

### 1. Prompt chaining

Split the task into fixed steps; each call works on the previous output. Put a cheap code check (a "gate") between
steps.

```
draft outline ──► [gate: has 5 sections?] ──► write sections ──► translate
```

Trades latency for accuracy: each call has an easier job.

### 2. Routing

Classify the input, then send it to a specialised prompt, tool set or model.

```
           ┌─► refund flow (small model + refund tools)
ticket ─► classifier ─► technical question (RAG over docs)
           └─► angry / legal ─► human queue
```

This is the same as an API gateway routing by path, except the "path" comes from a classifier. Routing easy traffic
to a small model is also the main cost lever ([lesson 36.5](#/lesson/36.5)).

### 3. Parallelisation

Run calls at the same time and combine the results.
- **Sectioning:** independent subtasks in parallel (check tone, check facts, check policy).
- **Voting:** the same task several times; take the majority or require agreement (e.g. 3 reviewers must all pass a
  code change).

Wall-clock time is the slowest call, not the sum. Cost is the sum.

### 4. Orchestrator-workers

A central LLM breaks the task into subtasks **at run time**, hands them to workers, and merges the results. Use it
when you can't know the subtasks ahead (which files does this change touch?). It is the bridge to agents and to
multi-agent systems ([lesson 35.5](#/lesson/35.5)).

### 5. Evaluator-optimizer

One call produces, another grades against clear criteria, and the loop repeats until it passes or hits a limit.
Works when "good" can be stated (tests pass, all facts cited, under 200 words).

```
generate ─► evaluate ─► pass? ─yes─► done
   ▲                     │no (max 3 rounds)
   └──── feedback ◄──────┘
```

## When you really need an agent

Use an agent when **the number and order of steps depend on what you find along the way**: debugging a failing test,
researching a question across many sources, resolving a support case that needs lookups in three systems.

Do not use an agent when:
- the steps are always the same (use a chain);
- one LLM call with good retrieval answers it (most Q&A);
- a wrong action is expensive and can't be checked (move money, delete data) and you can't put a human in front.

Anthropic's advice is to start with the simplest thing (one call, then a workflow) and add autonomy only when it
measurably helps. Agents cost more and take longer per task; you are paying for flexibility.

## How each fits into an existing system

Workflows are ordinary backend code: a request handler or a job in a queue, calling an LLM gateway and your APIs.
Agents add a new runtime component that holds a loop:

```
client ─► API ─► agent runtime ─► LLM gateway ─► model provider
                    │   ▲
                    ▼   │ tool results
               tool layer ─► your services (orders API, search, DB read replica)
```

The agent runtime needs what any long-running worker needs: timeouts, a step limit, state you can resume
([lesson 35.6](#/lesson/35.6)), and permissions per tool ([lesson 35.7](#/lesson/35.7)).

## Try it

For each task, choose: single call, workflow (which pattern), or agent.

1. Summarise each new support ticket into 3 bullet points.
2. Translate product pages into 12 languages, then check each translation for banned terms.
3. "Why did our checkout conversion drop on Tuesday?" answered from dashboards, logs and deploy history.
4. Classify incoming email as sales, support or spam and send it to the right team.

<details>
<summary>Reference</summary>

1. **Single call.** Fixed input, fixed output; nothing to decide.
2. **Workflow: parallelisation (sectioning) + prompt chaining.** 12 parallel translations, each followed by a
   check step (code for a word list, or an evaluator call). Steps are known ahead of time.
3. **Agent.** Which dashboards and logs to look at depends on what the first look shows. Give it read-only tools,
   a step limit and a budget.
4. **Workflow: routing.** One classifier call, then plain code sends it on. A small model is enough.

Rule of thumb: if you can draw the flowchart before the request arrives, it's a workflow.
</details>

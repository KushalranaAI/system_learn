# Embeddings

Keyword search finds documents that share words with the query. Users don't share your words: they type "money back"
when your article says "refund policy". **Embeddings** let you search by meaning. For a system designer they are
also a new kind of derived data, with storage costs, a compute pipeline, and a nasty versioning problem.

## Vectors for meaning

An **embedding model** maps a piece of text to a fixed-length list of numbers, a vector, such that texts with similar
meaning land close together.

```
embed("How do I get my money back?")   → [ 0.021, -0.113, 0.087, ..., 0.042 ]   (1,024 numbers)
embed("Refund policy for orders")      → [ 0.019, -0.098, 0.091, ..., 0.037 ]   close
embed("Change your shipping address")  → [-0.064,  0.022, 0.013, ..., -0.071]   far
```

Embedding models are trained (contrastively) on enormous numbers of text pairs that mean the same thing or answer
each other: questions and their answers, titles and their pages, paraphrases. Training pulls matching pairs together
and pushes unrelated texts apart. Because "refund" and "money back" keep appearing in matching pairs and in the same
contexts, they end up near each other, even though they share no letters.

## Similarity

Closeness is measured with **cosine similarity** (the angle between vectors) or, for normalised vectors, the
equivalent **dot product**:

```
cos(a, b) = (a · b) / (|a| × |b|)        1 = same direction, 0 = unrelated
```

Absolute values are model-specific: one model may give unrelated texts 0.2 and related ones 0.8, another 0.6 and
0.9. Never copy a threshold between models (this bit you in 26.5's semantic cache).

## Dimensions and storage

Common models produce 384 to 3,072 dimensions. Storage is simple arithmetic:

```
bytes = vectors × dimensions × bytes per number
10M chunks × 1,024 dims × 4 B (float32) = 41 GB
100M chunks × 1,024 dims × 4 B          = 410 GB   (before any index overhead)
```

| Lever | Saving | Cost |
|-------|--------|------|
| float16 | 2x | negligible quality loss |
| int8 quantisation | 4x | small loss |
| Binary quantisation | 32x | larger loss; usually re-score top results with full vectors |
| Fewer dimensions (Matryoshka models let you truncate, e.g. 3,072 → 256) | up to 12x | some loss; measure |
| Product quantisation in the index (27.3) | 16-64x | approximate distances |

Dimensions also drive query cost: every distance computation touches every dimension.

## Choosing a model

| Question | Why it matters |
|----------|----------------|
| Quality on **your** data | Public leaderboards (e.g. MTEB) are a starting filter, not an answer; test on your own queries (27.6) |
| Languages and domain | Multilingual? Code? Legal or medical vocabulary? |
| Max input length | Chunks longer than the model's limit get truncated silently |
| Dimensions | Storage, RAM and latency (above) |
| Hosted API vs self-hosted | Cost per token, latency (~10-50 ms per query over the network), data leaving your network |
| Query vs document modes | Many models expect a prefix such as "query:" vs "passage:"; mixing them up quietly hurts recall |

Embedding is cheap next to generation: embedding models are small, and API prices are typically a small fraction of
LLM input prices. The cost that bites is **re-embedding the whole corpus**.

## Versioning: the hard part

Vectors from different models live in **different spaces**. A query embedded with model B compared against documents
embedded with model A returns garbage, and nothing errors. So:

- Store `embedding_model` and version alongside every vector; query only matching vectors.
- Changing the model (or its dimension, or even your chunking) means **re-embedding everything**.
- Do it like a database migration, blue/green:

```
1. create index v2 (new model)             4. shadow-query v2, compare recall on the eval set
2. backfill: re-embed all chunks → v2      5. switch reads to v2 (flag), keep v1 for rollback
3. dual-write: new/changed docs → v1 & v2  6. drop v1
```

Back-of-envelope for the backfill: 100M chunks × 300 tokens = 30B tokens. At thousands of chunks per second it's a day
or more of work and the API bill to match: run it through a queue with rate limiting
([lesson 7.6](#/lesson/7.6)), resumable and idempotent (chunk ID as the key).

Also version the **query** side: a model upgrade in the API server must ship together with the index switch.

## Explore it

In the sandbox, workers and consumers can write into a vector database: that's the embedding pipeline. Upserts cost
more than queries (a replica handles about half as many). Try a re-embedding backfill in the
[RAG help desk scenario](#/sandbox?preset=ai-rag-helpdesk) by raising write traffic, and watch it compete with
queries for the same replicas.

## Try it

A user searches your help centre for "money back" and gets the article titled "Refund policy", which never contains
the words "money" or "back". Explain why this works, and name two things that would make it silently stop working.

<details>
<summary>Reference</summary>

The query and the article were embedded with the same model into the same vector space. The model was trained on
millions of pairs where "money back" and "refund" appear in matching questions and answers, so it places them in
nearly the same direction. The vector index returns the article whose vector has the highest cosine similarity to
the query's, regardless of shared words.

It silently breaks if:
- The query is embedded with a **different model or version** than the documents (e.g. the API server was upgraded
  but the index wasn't re-embedded): the spaces don't match and results become random.
- The query is embedded in **document mode** instead of query mode (for models that use prefixes), or the article was
  **truncated** past the model's input limit so the refund section was never embedded.
- Also possible: a language mismatch with a monolingual model, or an over-aggressive quantisation without re-scoring.
</details>

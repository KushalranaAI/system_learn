# Why retrieval-augmented generation

A model only knows what was in its training data, frozen months before you use it, and it knows nothing about your
company's documents, tickets or customers. When asked anyway, it produces a fluent, plausible guess. **Retrieval-augmented
generation (RAG)** fixes this the way a good engineer answers a question: look it up first, then answer from what you
found, and say where it came from.

## The basic loop

```
question ──► retrieve: search your corpus for the k most relevant passages
         ──► augment:  put them in the prompt ("Answer using only these sources...")
         ──► generate: the model answers and cites the passages it used
```

As a system, RAG is two pipelines that meet at an index:

```
OFFLINE (ingestion, 27.4)                      ONLINE (query path)
docs ─► parse ─► chunk ─► embed ─┐             user ─► API ─► embed query ─┐
                                 ▼                                         ▼
                           [vector index + keyword index] ◄─── search ─────┘
                                                                   │ top-k chunks
                                                                   ▼
                                                        rerank (27.5) ─► LLM ─► answer + citations
```

The online path is a read path like any other: it has a latency budget (26.6), it can be cached, and its index must
be kept fresh by the offline path, exactly like a search index or a materialised view
([lesson 17.2](#/lesson/17.2)).

## What retrieval buys you

| Benefit | Why it matters |
|---------|----------------|
| **Grounding** | Answers come from your documents, not the model's memory, so far fewer invented facts |
| **Freshness** | Update the index, not the model: a new policy is answerable minutes after it's published |
| **Citations** | Users and reviewers can check the source; you can measure whether answers are supported (27.6) |
| **Permissions** | Retrieval can filter by what this user may see; a model's weights can't |
| **Cost and size** | Send 2-5k relevant tokens instead of the whole corpus |
| **Deletion** | Remove a document from the index and it's gone from answers (important for privacy requests) |

RAG doesn't make a model truthful. It fails when retrieval misses the right passage (the model then guesses or
says "I don't know"), when the passage is outdated, or when the model ignores or misreads it. Module 27 is mostly
about reducing those failures.

## RAG vs fine-tuning vs long context

Three ways to get your knowledge into an answer:

| | RAG | Fine-tuning | Long context |
|---|-----|-------------|--------------|
| What it is | Search, then put results in the prompt | Further train the model on your examples | Put the whole document(s) in the prompt |
| Good at | Facts that change; large corpora; citations; per-user access | **Behaviour**: style, format, tone, a domain's jargon, a narrow task done cheaply by a small model | One or a few documents, cross-references within them, small stable corpora |
| Bad at | Questions needing the whole corpus at once ("summarise all tickets"); multi-hop reasoning without extra work (27.7) | Teaching new facts reliably; updates (retrain each time); citations; deleting data | Big corpora (millions of tokens); cost per query; quality drops with very long inputs |
| Freshness | Minutes (re-index) | Weeks (retrain, re-evaluate, redeploy) | Immediate |
| Cost profile | Index infrastructure + ~2-5k tokens/query | Training runs + hosting the custom model | Many input tokens on every query (prefix caching helps) |

They combine. A common production shape: a fine-tuned or prompted small model for the format, RAG for the facts, and
long context for "this one contract the user just uploaded".

Rules of thumb:

- **Knowledge that changes, or is big, or needs citations → RAG.**
- **Behaviour you can't get by prompting → fine-tune.** Try prompting and few-shot examples first.
- **Fits in the window and is used whole → long context**, with the document as a cached prefix (26.5).

Long context windows (hundreds of thousands to a million tokens) make the third option tempting, but compare costs:
a 500k-token corpus resent on every question costs about 100x more input than a 5k-token retrieval, and still gets
slower and less reliable as the input grows. Retrieval remains the default for anything corpus-sized; 27.7 revisits
this trade-off.

## Try it

Choose RAG, fine-tuning or long context (or a combination) for each product, and say why:

1. An internal assistant that answers employees' questions about HR policies, benefits and IT procedures (3,000
   pages, updated weekly, some pages restricted to managers).
2. A feature that turns free-text support tickets into a structured JSON record (category, product, urgency) at
   2 million tickets a day.
3. "Chat with this contract": a lawyer uploads one 60-page agreement and asks questions about it.

<details>
<summary>Reference</summary>

1. **RAG.** The corpus is too big for the window, changes weekly (re-index, don't retrain), answers need citations so
   employees can check the policy, and permission filters keep manager-only pages out of other employees' answers.
2. **Fine-tuning** (a small model). This is a fixed behaviour and format, not knowledge. A fine-tuned small model
   produces consistent JSON far more cheaply than a large prompted model at 2M calls/day. Start with a prompted
   model to collect labelled examples, then fine-tune on them. Add a small retrieval of the product catalogue only if
   product names change often.
3. **Long context.** 60 pages is about 30-40k tokens: it fits, the whole document matters (clauses reference each
   other), and it's used for one session. Put the contract first in the prompt so follow-up questions hit the prefix
   cache. Switch to RAG over the document only if users upload hundreds of pages.
</details>

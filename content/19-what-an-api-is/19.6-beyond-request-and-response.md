# Beyond request and response

Plain HTTP has one shape: the client asks, the server answers. Plenty of features don't fit it. A chat message has to
reach you without you asking. A shop needs to know when a payment settles three minutes later. An internal service
wants to call another one as if it were a local function. Each of these has its own pattern.

## Remote procedure calls (RPC)

RPC makes a network call look like a function call:

```
total = pricing.Quote(cart_id="c_91", currency="EUR")   # actually a network request
```

The idea goes back to the 1980s (Sun RPC); modern versions are **gRPC**, **Thrift**, **JSON-RPC** and tRPC. RPC APIs
are organised around **operations** (verbs) instead of **resources** (nouns).

The danger is in the illusion. A local call takes nanoseconds and never half-fails; a remote one takes milliseconds, can
time out after the work was done, and needs a deadline, retries and idempotency (module 12). Good RPC frameworks make
those things explicit rather than hiding them. Lesson 20.5 covers gRPC.

## Getting updates from the server

| Pattern | How it works | Good for | Watch out for |
|---------|--------------|----------|---------------|
| **Short polling** | Client asks every N seconds | Rare updates, simple clients | Most responses say "nothing new"; delay up to N |
| **Long polling** | Server holds the request until there's news or a timeout, then the client asks again | Works through any proxy | One request per event; awkward at high rates |
| **Server-Sent Events (SSE)** | One long HTTP response streams `data:` lines; browsers reconnect automatically with `Last-Event-ID` | One-way feeds: scores, notifications, LLM token streams | Server → client only; text only |
| **WebSockets** | HTTP connection upgraded to a two-way message channel | Chat, collaboration, games, trading | Stateful connections to scale and load-balance; you design reconnects and message formats yourself |
| **WebTransport** | Two-way streams and datagrams over HTTP/3 | Low-latency media and games in browsers | Newer; support still growing |

Module 6 measured the costs (try the push vs poll simulation in lesson 6.1). The API-design questions are:

- **How does a client resume?** Give every event a sequence number; on reconnect the client sends the last one it saw
  and the server replays what was missed (lesson 6.5).
- **What's the message format?** Define event types and schemas just as carefully as HTTP bodies.
- **How is the connection authenticated?** Browsers can't set custom headers on WebSocket handshakes, so tokens go in
  a cookie or in the first message (not in the URL, which ends up in logs).

## Server-to-server: webhooks

When the "client" is another company's server, there's no open connection to push to. Instead it registers a URL and
you **POST events to it**:

```http
POST https://shop.example/hooks/payments
Content-Type: application/json
Webhook-Signature: t=1761640000,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd

{"id": "evt_1Q2", "type": "payment.succeeded", "data": {"payment": "pay_88"}}
```

Webhooks are "reverse APIs": you're now the client of someone else's server, with all its outages and slowness.
Lesson 22.6 covers signatures, retries, ordering and duplicates.

## Choosing

```
Does the server need to tell the client something it didn't ask for?
├── no  → request/response (REST, GraphQL, RPC)
└── yes → Is the receiver a browser or app with the screen open?
          ├── yes → one-way? SSE  ·  two-way or high-rate? WebSocket  ·  rare? poll
          └── no (another company's server) → webhooks (plus an events API to catch up)
```

## Try it

Pick a channel for each: (a) a dashboard tile showing yesterday's revenue; (b) live football scores on a website;
(c) a multiplayer whiteboard; (d) telling a merchant's server that a refund completed.

<details>
<summary>Answer</summary>

(a) Plain request/response with caching; it changes once a day. (b) SSE: one-way, many viewers, automatic
reconnect. (c) WebSockets: two-way and frequent. (d) A signed webhook, with a `GET /refunds/:id` the merchant can call
to confirm, and an events list endpoint to catch up after downtime.
</details>

## Key takeaways

- RPC organises APIs around operations; remember that remote calls fail differently from local ones.
- For server-to-client updates, pick polling, long polling, SSE or WebSockets by direction, rate and simplicity.
- Every push channel needs a resume story: sequence numbers and replay.
- Webhooks push events to other servers; they make you a client of someone else's infrastructure.

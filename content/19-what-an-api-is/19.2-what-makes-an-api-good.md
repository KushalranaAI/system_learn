# What makes an API good

Two payment APIs do the same thing. With the first, a developer has a test payment working in ten minutes and never
opens the docs again. With the second, they spend two days on a signature format, discover that `amount` is in
dollars on one endpoint and cents on another, and get `{"error": "failed"}` when something goes wrong. Both are
"correct". Only one gets adopted.

A good API is one that's **easy to use correctly and hard to use wrongly**. In practice that comes down to a handful of
properties.

## The properties

| Property | What it means | Example of getting it wrong |
|----------|---------------|-----------------------------|
| **Predictable** | Once you've learned one endpoint, you can guess the next | `GET /users/:id` but `POST /createOrder` and `/order_list` |
| **Consistent** | Same names, formats and patterns everywhere | `created_at` here, `creationDate` there; cents here, dollars there |
| **Hard to misuse** | Unsafe states are impossible, defaults are safe | A `DELETE /accounts` that deletes all accounts when the id is missing |
| **Small** | Few concepts, few ways to do the same thing | Three different endpoints that each "sort of" update a user |
| **Clear errors** | Errors say what went wrong and what to do | `500 {"error": "failed"}` for a missing field |
| **Evolvable** | Can grow without breaking callers | Exposing database column names that you'll want to rename |
| **Documented by example** | Every endpoint has a real request and response | A reference page with types and no examples |
| **Secure by default** | Access checks, limits and TLS aren't optional extras | An admin flag clients can set in a request body |

## Design for the caller, not the database

The most common mistake is to expose your tables. The API should match **what callers want to do**, which is often
different from how you store it.

```
Mirrors the database                     Matches what callers do
GET  /order_header/42                    GET  /orders/42            (header + lines + totals)
GET  /order_line?order_id=42             POST /orders/42/cancel     (one action, not 3 updates)
PUT  /order_header/42 {status: 7}
```

Hiding storage details also keeps you free to change them later.

## Make errors useful

An error response is part of the contract, so give it a fixed shape. The standard one for HTTP APIs is **problem
details** (RFC 9457, which replaced RFC 7807 in 2023):

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/invalid-field",
  "title": "A field is invalid",
  "status": 422,
  "detail": "amount must be a positive integer number of cents",
  "instance": "/payments",
  "errors": [{ "field": "amount", "reason": "must be > 0" }]
}
```

A good error tells the caller **which** request failed, **why**, and whether **retrying** can help (a `429` or `503`
can; a `400` never will).

## Conventions to decide once

Write these down in an API style guide before the first endpoint, then apply them everywhere:

- **Naming:** plural nouns for collections (`/orders`), one case style for fields (`snake_case` or `camelCase`).
- **Identifiers:** opaque strings, not auto-increment integers (they leak volume and invite guessing).
- **Time:** RFC 3339 / ISO 8601 timestamps in UTC (`2026-10-28T09:30:00Z`).
- **Money:** integer minor units plus a currency (`{"amount": 4999, "currency": "INR"}`), never floats.
- **Lists:** always paginated, with the same parameters everywhere (lesson 22.3).
- **Nulls and absence:** decide whether a missing field and `null` mean different things, and say so.

## Try it

Review this endpoint list for a to-do app. What would you change?

```
POST /addTask              {title, due}           → 200 {ok: true}
GET  /tasks/all                                   → 200 [ ...every task ever... ]
GET  /task?id=17                                  → 200 {...} or 200 {error: "not found"}
POST /tasks/17/update      {done: 1}
GET  /deleteTask?id=17
```

<details>
<summary>Answer</summary>

- Use resources and methods: `POST /tasks` (201 + the created task + `Location`), `GET /tasks`, `GET /tasks/:id`,
  `PATCH /tasks/:id`, `DELETE /tasks/:id`.
- Paginate `GET /tasks` and allow filters like `?done=false`.
- Return real status codes: `404` with a problem body, not `200 {error}`.
- `done` should be a boolean, not `1`.
- **Never delete with GET**: GETs are assumed safe, so crawlers, link previews and prefetchers will happily call it.
</details>

## Key takeaways

- A good API is predictable, consistent, small and hard to misuse.
- Model what callers want to do, not your tables.
- Errors are part of the contract: one shape (RFC 9457 problem details), with a clear reason and retry hint.
- Decide naming, ids, time, money and pagination once, in a style guide.

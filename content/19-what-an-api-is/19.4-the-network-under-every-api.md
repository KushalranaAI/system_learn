# The network under every API

An API that answers in 15 ms on the developer's laptop takes 900 ms for a user in another continent on a train. The
code didn't get slower. The network got longer. You can't design a fast API without a mental model of what's
underneath it. This lesson is that model; module 27 goes deeper into DNS, TCP, TLS and QUIC.

## The narrow waist

The internet is a stack of layers. Many technologies sit at the bottom (Wi-Fi, 5G, fibre) and many at the top (HTTP,
gRPC, WebSockets, video calls), but in the middle there is essentially **one** protocol: **IP**.

```
     HTTP/1.1  HTTP/2  HTTP/3  gRPC  WebSocket  DNS  SMTP ...     applications
            \      |      |       |      /       |    /
                 TCP              UDP (QUIC runs on UDP)           transport
                          \      /
                            IP                                    ← the narrow waist
                          /      \
          Ethernet   Wi-Fi   4G/5G   fibre   satellite ...         links
```

Because everything agrees on IP, any application can run over any link. For API designers this means: your API
inherits the behaviour of whatever path the packets take, and you control almost none of it.

## Latency and throughput are different things

| Term | Meaning | Typical numbers |
|------|---------|-----------------|
| **Latency** (round-trip time, RTT) | Time for a tiny message to go there and back | 1 ms in a data centre, 20-40 ms in a country, 150-300 ms across oceans or on bad mobile |
| **Bandwidth** | How many bits per second the path can carry | 1-20 Mbps weak mobile, 100+ Mbps home fibre, 10-100 Gbps in a data centre |
| **Throughput** | What you actually achieve | Less than bandwidth: protocols, congestion, slow start |

A useful rule:

```
time for one request ≈ (round trips needed × RTT) + (bytes × 8 ÷ bandwidth) + server time
```

For most API calls the **round trips dominate**, not the bytes. A 5 KB JSON response takes 4 ms on a 10 Mbps link,
but a fresh HTTPS connection to a server 180 ms away needs two or three round trips before the request is even sent.

### Bandwidth-delay product

How much data is "in flight" on a path at once: `bandwidth × RTT`. On a 100 Mbps link with 100 ms RTT that's
1.25 MB. A new TCP connection starts by sending only about 14 KB per round trip (**slow start**) and doubles from there,
so a big response on a fresh connection pays extra round trips while the window grows. Reusing connections avoids that.

## Sockets: what your server actually sees

A **socket** is the operating system's handle for one end of a connection, identified by
`(protocol, local IP, local port, remote IP, remote port)`.

```
server: listen on 0.0.0.0:443  ──accept()──▶  one socket per client connection
client: connect to 203.0.113.7:443 from an ephemeral port like 51544
```

What it means for APIs:

- **Connections are expensive to set up** (handshakes) and cheap to reuse. HTTP keep-alive, HTTP/2 multiplexing and
  connection pools in your clients matter more than micro-optimising handlers.
- **Each open connection costs memory and a file descriptor.** Servers holding 100,000 WebSockets need tuning
  (module 6).
- **TCP** gives you a reliable, ordered byte stream (and head-of-line blocking: one lost packet stalls everything behind
  it). **UDP** gives you independent packets with no guarantees, which is why games and video calls use it, and why
  HTTP/3 builds its own reliability on top of UDP with QUIC.

## Try it

A phone 6,000 km from your servers (RTT ≈ 120 ms, 4 Mbps) makes its first call to your API: DNS is cached, the
connection is new (TCP + TLS 1.3 = 2 round trips), and the response is 40 KB. The server takes 30 ms. Estimate the
total.

<details>
<summary>Answer</summary>

- Handshakes: 2 × 120 = 240 ms.
- Request and response: 1 × 120 = 120 ms.
- Slow start: 40 KB needs the window to grow from ~14 KB, about 2 extra round trips = 240 ms.
- Transfer at 4 Mbps: 40 KB × 8 ÷ 4,000 kbps ≈ 80 ms (overlaps partly with slow start, so call it ~40 ms extra).
- Server: 30 ms.

Roughly **650-700 ms**, of which the server is 30. Reusing the connection would remove ~480 ms of that. The
latency budget simulation in module 24 lets you play with these numbers.
</details>

## Key takeaways

- IP is the narrow waist: every API rides on a path it doesn't control.
- Latency (round trips) usually matters more than bandwidth for API calls.
- New connections cost handshakes and slow start; reuse them.
- TCP is reliable and ordered (with head-of-line blocking); UDP is fast and unreliable; QUIC brings TCP-like
  reliability to UDP.

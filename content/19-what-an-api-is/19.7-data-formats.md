# Data formats

An IoT company's devices upload sensor readings every ten seconds as JSON. At a million devices that's 100,000
requests a second, and the bill shows most of the money going on bandwidth for repeated words like
`"temperature":`. Switching the device protocol to a binary format cuts traffic by two thirds. The data didn't change,
only how it was written down.

## Text formats

| Format | Looks like | Strengths | Weaknesses |
|--------|------------|-----------|------------|
| **JSON** | `{"id": 7, "ok": true}` | Universal, readable, native in browsers | Repeats field names; numbers are text (and parsers disagree beyond 2⁵³); no dates, no binary |
| **XML** | `<user id="7"><ok>true</ok></user>` | Schemas (XSD), namespaces, still common in enterprise, finance and SOAP | Verbose, complex parsers, security traps (XML external entities) |
| **CSV** | `id,ok\n7,true` | Tiny, spreadsheet-friendly, good for bulk exports | No types, no nesting, quoting rules vary |
| **YAML** | `id: 7` | Readable configs | Not for APIs: ambiguous types (`no` becomes `false`), slow, unsafe loaders |

## Binary formats

| Format | Schema? | How it saves space | Used by |
|--------|---------|--------------------|---------|
| **Protocol Buffers** | Required (`.proto`) | Field **numbers** instead of names, varint integers, defaults omitted | gRPC, Google APIs, many internal systems |
| **Avro** | Required, travels with the data or a registry | No field tags at all; the schema says the order | Kafka pipelines, data lakes |
| **MessagePack** | None | Like JSON (keys included) but binary numbers and short length prefixes | Caches, some realtime protocols |
| **CBOR** | Optional | Like MessagePack, standardised (RFC 8949) | IoT, WebAuthn |

Here's one record in JSON (63 bytes) and Protobuf (20 bytes):

```
JSON      {"sensorId":5012,"ts":1761600000,"temperature":21.75,"ok":true}

message Reading {             Protobuf bytes (hex):
  int32  sensor_id = 1;       08 94 27                     field 1, varint 5012
  int64  ts = 2;              10 80 c4 ff c7 06            field 2, varint 1761600000
  double temperature = 3;     19 00 00 00 00 00 c0 35 40   field 3, 8-byte double
  bool   ok = 4;              20 01                        field 4, true
}
```

## How formats evolve

A format decides what happens when the schema changes, and it will change.

| Change | JSON (tolerant reader) | Protobuf | Avro |
|--------|------------------------|----------|------|
| Add a field | Old clients ignore it if written to | Safe: unknown field numbers are skipped | Safe with a default value |
| Remove a field | Breaks readers that need it | Safe if you **reserve** the number and never reuse it | Safe if readers have a default |
| Rename a field | Breaking | Safe (names aren't on the wire) | Use aliases |
| Change a type | Breaking | Only between compatible types | Only compatible promotions |

The one rule for Protobuf: **never reuse or change a field number**.

## Choosing

- **Public HTTP APIs:** JSON, with compression (`gzip` or Brotli) and an OpenAPI schema. Readability and universal
  support beat a few kilobytes.
- **Internal, high-volume service calls:** Protobuf with gRPC. Smaller, faster to parse, typed generated code.
- **Event streams and analytics:** Avro or Protobuf with a schema registry, so producers and consumers can evolve
  independently.
- **Constrained devices:** CBOR or Protobuf.

Compression narrows the size gap (repeated keys compress very well) but costs CPU on both sides, and doesn't help
parse time. Measure your own payloads: the simulation below encodes real records in four formats.

## Try it

Your mobile API returns 200 records of mostly numbers per page, 2,000 times a second. Use the simulation to estimate
what moving from JSON to Protobuf saves in egress per month at $0.08/GB. What do you give up?

<details>
<summary>Answer</summary>

With the default "sensor readings" shape, JSON is about 18 KB per response and Protobuf about 7 KB. At 2,000
responses/s that's roughly $7,800 vs $2,800 a month in egress, and a phone on a 2 Mbps link downloads each page in
~27 ms instead of ~75 ms. You give up human readability, ad-hoc debugging with curl, and you need a shared `.proto` (and
generated code) on every client. For articles that are mostly text, the saving is small, because text costs the same
bytes in every format.
</details>

## Key takeaways

- JSON is the default for public APIs: universal and readable, but verbose.
- Binary formats (Protobuf, Avro, MessagePack, CBOR) are smaller and faster, and most need a schema.
- A format's evolution rules matter as much as its size: plan for adding and removing fields.
- Compression closes much of the gap for text-heavy data; measure your real payloads.

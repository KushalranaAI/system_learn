# APIs as a product and a business

Stripe, Twilio and Google Maps sell almost nothing *but* APIs. For them, the API is the product: its docs are the
shop window, its error messages are customer support, and a breaking change is a price rise customers didn't agree to.
Even if your API is only used inside your company, thinking of it as a product with customers leads to better
decisions.

## Who is the API for?

| Audience | Example | What they need most |
|----------|---------|----------------------|
| **Private** (internal) | The orders service called by the checkout service | Speed of change, strong typing, low latency |
| **Partner** | A bank's API for accounting software it has contracts with | Stability, onboarding help, SLAs, audit trails |
| **Public** | Payments, maps, messaging, weather | Self-service sign-up, great docs, fair limits, a long deprecation policy |

The same company often runs all three, and they deserve different rules. An internal API might change every week;
a public one might promise years of support for each version.

## Business models

| Model | How it works | Examples |
|-------|--------------|----------|
| **Pay per use** | A price per call, per unit (minute, message, transaction) or per "SKU" | Payments take a percentage per transaction; SMS per message |
| **Free tier + usage** | A monthly free allowance, then pay per use | Google Maps Platform: since March 2025, a free monthly allowance **per SKU** (for example 10,000 calls for "Essentials" SKUs) instead of a flat $200 credit |
| **Subscription tiers** | Fixed monthly price for a quota | Many data APIs: Free / Pro / Enterprise |
| **Indirect** | The API is free; it drives sales of something else | Shopify and Salesforce APIs make the platform stickier |
| **Pricing changes** | Can reshape who uses the API | X (Twitter) moved from free access to paid tiers in 2023, then to pay-per-use as the default in February 2026 |

Pricing is part of the contract. Large pricing changes have the same effect as breaking changes: integrations stop,
and developers lose trust.

## Developer experience (DX)

For a public API, the main competitor is often "build it ourselves". What wins developers:

- **Time to first successful call** in minutes: sign up, get a test key, copy a curl example, see a response.
- **A sandbox / test mode** that behaves like production (test card numbers, fake SMS delivery).
- **Docs with runnable examples** in several languages, generated from the same OpenAPI spec as the server.
- **SDKs** for the popular languages (they also let you hide retries, pagination and auth).
- **Clear errors** and a request id in every response that support can look up.
- **A changelog and a deprecation policy** that tells people how long things will keep working.

## Every API has a running cost

| Cost | Why it matters |
|------|----------------|
| Infrastructure | Each version and endpoint you support has to be served, monitored and secured |
| Support | Bad errors and unclear docs turn into tickets |
| Change | Every breaking change costs **every** consumer engineering time; for a public API, that's thousands of teams |
| Abuse | Free tiers attract scrapers and fraud; limits and verification cost money too |

That is why designs that can **evolve without breaking** (module 22) are a business decision, not just a technical
nicety.

## Try it

You're launching a weather API. Free users are mostly students and hobbyists; a few logistics companies need
high-volume, reliable access. Sketch the tiers and what each tier's contract promises.

| Enterprise (contract) | Custom quotas, bulk downloads, dedicated endpoints | 99.95% SLA with credits, 12-month deprecation notice |

Every tier gets the same API (different keys and limits), so moving up a tier needs no code changes. Limits are
returned in headers and documented (lesson 22.5).

## Key takeaways

- Treat an API as a product with customers, even when the customers are other teams.
- Private, partner and public APIs need different change and support rules.
- Pricing and limits are part of the contract; changing them can break integrations as surely as a field rename.
- Developer experience (time to first call, sandboxes, examples, clear errors) decides adoption.

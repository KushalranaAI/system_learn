# HTTP for API designers

HTTP is older than most of the people designing APIs on it, and it already solves many problems teams re-invent:
caching, retries, content negotiation, conditional updates, redirects. Using its methods and status codes the way
they're defined means every client library, proxy, CDN and monitoring tool understands your API for free.

## A request and a response

```http
POST /v1/orders HTTP/1.1
Host: api.shop.example
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json
Accept: application/json
Idempotency-Key: 8a3f0c2e-6d1b-4b7e-9f2a-1c5d7e9b3a40

{"items": [{"sku": "TEA-01", "qty": 2}]}
```

```http
HTTP/1.1 201 Created
Location: /v1/orders/ord_7Hx2
Content-Type: application/json
X-Request-Id: req_51f0c9

{"id": "ord_7Hx2", "status": "pending", "total": {"amount": 1198, "currency": "EUR"}}
```

Method, path, headers, body; status, headers, body. Everything else is detail.

## Methods: meaning, safety, idempotency

| Method | Meaning | Safe? | Idempotent? | Typical success |
|--------|---------|-------|-------------|-----------------|
| `GET` | Read a resource | ✅ | ✅ | 200, 304 |
| `HEAD` | Like GET, headers only | ✅ | ✅ | 200 |
| `POST` | Create, or run an action | ❌ | ❌ | 201 (+ `Location`), 200, 202 |
| `PUT` | Replace a resource with this body (or create at a known URL) | ❌ | ✅ | 200, 204, 201 |
| `PATCH` | Partially update | ❌ | Not necessarily | 200, 204 |
| `DELETE` | Remove | ❌ | ✅ | 204, 200, 202 |
| `OPTIONS` | What's allowed here (used by CORS preflight) | ✅ | ✅ | 204 |

- **Safe** means the request doesn't change state. Crawlers, prefetchers and caches assume GETs are safe, so never put
  side effects behind a GET.
- **Idempotent** means doing it twice has the same effect as once. Clients and proxies may **retry idempotent requests
  automatically**. For POST, you add idempotency yourself with an `Idempotency-Key` (lesson 22.4).

## Status codes: say what happened

| Family | Meaning | The ones you'll use most |
|--------|---------|--------------------------|
| 1xx | Informational | `103 Early Hints` (lesson 23.2) |
| 2xx | It worked | `200 OK`, `201 Created`, `202 Accepted` (queued for later), `204 No Content` |
| 3xx | Look elsewhere | `301`/`308` permanent, `302`/`307` temporary, `304 Not Modified` (your cached copy is fine) |
| 4xx | **The client** should change something | `400` malformed, `401` who are you?, `403` not allowed, `404` not found, `409` conflicts with current state, `412` precondition failed, `422` valid syntax but invalid content, `429` slow down |
| 5xx | **The server** failed | `500` bug, `502` bad upstream, `503` overloaded or down (send `Retry-After`), `504` upstream timed out |

Two rules that save a lot of pain:

1. **Never return 200 for an error.** Clients, retries, dashboards and alerts all key off the status code.
2. **4xx means "don't retry this as is"; 5xx and 429 mean "you may retry later"**. Get this right and client retry
   logic becomes simple (lesson 23.4).

## Headers worth knowing

| Header | What it does |
|--------|--------------|
| `Content-Type` / `Accept` | The body's format, and the formats the client accepts (content negotiation) |
| `Authorization` | Credentials, usually `Bearer <token>` |
| `Cache-Control`, `ETag`, `If-None-Match` | Caching and cheap revalidation (lesson 23.3) |
| `If-Match` | Optimistic concurrency: "update only if it's still version X", else `412` |
| `Location` | Where a created resource (or a redirect) lives |
| `Retry-After` | When to try again after `429` or `503` |
| `Idempotency-Key` | Lets the server detect retries of a POST (IETF draft, widely used) |
| `traceparent` | Distributed tracing context (W3C Trace Context) |

## HTTP/1.1 → HTTP/2 → HTTP/3

| Version | Transport | What changed for APIs |
|---------|-----------|------------------------|
| HTTP/1.1 (1997) | TCP | Text protocol; one request at a time per connection, so browsers open ~6 connections per host |
| HTTP/2 (2015) | TCP | Binary framing, **many concurrent requests on one connection**, header compression (HPACK); needed by gRPC |
| HTTP/3 (2022, RFC 9114) | **QUIC over UDP** | Combined transport + TLS 1.3 handshake (1 round trip, 0-RTT on resume), no TCP head-of-line blocking, connections survive a network change (Wi-Fi → 5G) |

The semantics (methods, status codes, headers) stay the same in all three, so your API design doesn't change, but
fewer handshakes and multiplexing change how chatty an API can afford to be. Lesson 27.4 covers the details.

## Try it

Pick the status code:

1. The request JSON doesn't parse.
2. A valid token, but the user may not delete this project.
3. Creating a user with an email that's already registered.
4. The client sent 200 requests in a second, over its limit.
5. A report export was accepted and will be ready in a few minutes.
6. The database is down.

<details>
<summary>Answer</summary>

1. `400 Bad Request`. 2. `403 Forbidden`. 3. `409 Conflict`. 4. `429 Too Many Requests` with `Retry-After`.
5. `202 Accepted` with a `Location` to a status resource like `/exports/:id`. 6. `503 Service Unavailable` with
`Retry-After` (or `500` if it's a bug); never `200`.
</details>

## Key takeaways

- Use HTTP methods for their defined meaning: GET is safe; PUT and DELETE are idempotent; POST is neither.
- Status codes are the first thing every tool reads. 4xx is the client's problem, 5xx and 429 may be retried.
- Standard headers already cover caching, concurrency, retries and tracing.
- HTTP/2 and HTTP/3 keep the same semantics but make connections cheaper and multiplexed.

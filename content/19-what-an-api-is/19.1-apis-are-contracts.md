# APIs are contracts

Your team ships a small change: the `price` field in the product response is now a string (`"49.99"`) instead of a
number, because a finance system wanted exact decimals. Your own website is updated the same day. An hour later the
support queue fills up: a partner's checkout shows **NaN** for every price, and an old version of your Android app
crashes on launch. Nothing in your code is broken. You broke a **promise**.

That promise is the API.

## What an API is

An **Application Programming Interface** is the agreed way one piece of software asks another to do something. It
says what you can ask for, how to ask, and what you'll get back, and it hides *how* the work is done.

| Kind | Example | The contract is… |
|------|---------|-------------------|
| Library API | `json.loads(text)` in Python | function names, arguments, return types, exceptions |
| Operating system API | `open()`, `read()` system calls | calls, flags, error codes |
| **Web API** | `GET https://api.example.com/v1/orders/42` | URLs, methods, headers, bodies, status codes, behaviour |

This part of the course is about **web APIs**: the ones that cross a network, between a client and a server or between
two services. They are harder than library APIs in three ways:

1. **The other side is someone else's code.** You can't recompile your callers.
2. **The network is in the middle.** Calls are slow, can fail halfway, and can arrive twice (module 12).
3. **Old clients live for years.** Mobile apps, partner integrations and scripts call whatever they were built against.

## Producers and consumers

```
 consumers (you don't control most of them)          producer (you)
 ┌──────────────┐
 │ web app      │──┐
 ├──────────────┤  │   the contract        ┌──────────────────────────────┐
 │ iOS 2023 app │──┼──  GET /v1/orders/42 ─▶│ code, database, cache, queues │
 ├──────────────┤  │   ◀── 200 {json} ──────│   (free to change)            │
 │ partner ERP  │──┘                        └──────────────────────────────┘
 └──────────────┘
```

Everything to the right of the contract can change: the language, the database, the number of servers. What's on the
contract can't change without coordinating with every consumer. That's why API design is mostly about **choosing what
to promise**.

## The contract is bigger than the docs

A contract has a written part and an unwritten part.

| Written | Unwritten (but relied on anyway) |
|---------|----------------------------------|
| Paths, methods, fields, types | The **order** of items in a list |
| Status codes and error formats | How **fast** it answers |
| Auth and rate limits | Fields that happen to always be present |
| Versioning and deprecation policy | The exact wording of error messages |

This is **Hyrum's law**: *with enough users, every observable behaviour of your API will be depended on by somebody*,
whatever the docs say. The defence is to be deliberate: document what you promise, and avoid exposing accidental
behaviour (for example, return lists in a documented order, or randomise an order you don't promise).

## Contract first

Good teams write the contract **before** the code:

1. Agree on resources, operations and examples with the people who will call it.
2. Write it down in a machine-readable form (an **OpenAPI** document for HTTP APIs, a `.proto` file for gRPC, a schema
   for GraphQL; module 20).
3. Generate docs, mock servers and client stubs from it, so consumers can start before the server exists.
4. Test the implementation against the contract in CI, so it can't drift.

## Key takeaways

- An API is a promise about what callers can ask for and what they'll get, not how it's implemented.
- Web APIs are hard to change: callers are other people's code, behind a network, and live for years.
- Callers depend on observable behaviour, written down or not (Hyrum's law), so promise things deliberately.
- Design the contract first, in a machine-readable format, and test the code against it.

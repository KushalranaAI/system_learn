# gRPC

Inside a data centre, the checkout service calls pricing, inventory and fraud on every order, thousands of times a
second. Each call is a few microseconds of real work wrapped in milliseconds of JSON parsing, HTTP/1.1 connection
juggling and hand-written client code that drifts from the server. gRPC is Google's answer: a strict contract, compact
messages, one multiplexed connection, and generated clients in a dozen languages.

## The contract is a `.proto` file

```protobuf
syntax = "proto3";
package pricing.v1;

service Pricing {
  rpc Quote (QuoteRequest) returns (QuoteReply);                        // unary
  rpc WatchPrices (WatchRequest) returns (stream PriceUpdate);          // server streaming
  rpc UploadReadings (stream Reading) returns (UploadSummary);          // client streaming
  rpc Negotiate (stream Offer) returns (stream Offer);                  // bidirectional
}

message QuoteRequest { string cart_id = 1; string currency = 2; }
message QuoteReply   { int64 total_minor = 1; string currency = 2; repeated LineQuote lines = 3; }
```

`protoc` generates server stubs and typed clients. The field **numbers** are the wire contract: never change or reuse
one (lesson 19.7); `reserved 4;` stops anyone from doing it by accident.

## How it runs

- **HTTP/2** underneath: one TCP connection carries many concurrent calls (streams), with binary framing and header
  compression. Messages are length-prefixed Protobuf.
- **Four call types**, shown above. Streaming is first-class, which is awkward in REST.
- **Deadlines:** every call carries one (`grpc-timeout` header), and it propagates: if checkout gives pricing 200 ms
  and 150 ms are gone, pricing's own downstream calls get the remaining 50 ms. Work nobody is waiting for gets
  cancelled.
- **Status codes** of its own: `OK`, `INVALID_ARGUMENT`, `NOT_FOUND`, `ALREADY_EXISTS`, `PERMISSION_DENIED`,
  `UNAUTHENTICATED`, `RESOURCE_EXHAUSTED` (rate limited), `UNAVAILABLE` (safe to retry), `DEADLINE_EXCEEDED`,
  `INTERNAL`… plus rich error details.
- **Interceptors** (middleware) for auth, logging, metrics and tracing, and built-in support for retries, hedging and
  client-side load balancing via service config.

## Where gRPC is awkward

| Limitation | Why | Workaround |
|------------|-----|------------|
| Browsers can't call it directly | Browsers don't expose HTTP/2 framing and trailers to JavaScript | **gRPC-Web** through a proxy (Envoy), or Connect; or transcode to REST/JSON at the edge |
| Not human-readable | Binary Protobuf | `grpcurl`, server reflection, JSON transcoding |
| L7 load balancing needed | One long-lived HTTP/2 connection carries all calls, so L4 balancers send everything to one backend | Client-side balancing, or a proxy/mesh that balances per request |
| No HTTP caching | All calls are POSTs | Cache in the application |
| Everyone needs the `.proto` | Strong contract | A shared schema repo or registry (Buf) with breaking-change checks in CI |

## gRPC vs REST in numbers

The difference is mostly **per-message overhead**: smaller payloads (often 3-10x smaller than JSON for numeric data),
cheaper parsing, and no connection setup per call. For a chatty internal path (tens of calls per user request) that
adds up to real latency and CPU. For one public call per user action, it rarely matters.

Many teams define APIs in Protobuf once and serve **both**: gRPC for internal clients and REST/JSON for everyone else,
via `google.api.http` annotations and a transcoding gateway. Google Cloud's public APIs work this way.

## Try it

Define a gRPC service for a ride-hailing app's driver location feed: drivers' phones send their position every 2
seconds; the dispatch service wants a live stream of positions in one city. Which call types do you use?

<details>
<summary>Answer</summary>

```protobuf
service DriverLocations {
  // Each driver keeps one client-streaming call open and sends positions; the server replies once when it closes.
  rpc Report (stream Position) returns (ReportAck);
  // Dispatch subscribes to a city and receives a server stream of updates.
  rpc Watch (WatchRequest) returns (stream Position);
}
message Position { string driver_id = 1; double lat = 2; double lng = 3; int64 ts_ms = 4; float heading = 5; }
message WatchRequest { string city_id = 1; }
```

Phones on mobile networks reconnect often, so the server must accept a new `Report` stream at any time, and `Watch`
clients should resume from "now" (positions older than a few seconds are useless). Lesson 25.13 discusses whether
phones should use gRPC, WebSockets or MQTT.
</details>

## Key takeaways

- gRPC = Protobuf contracts + HTTP/2 + generated clients, with unary and streaming calls.
- Deadlines that propagate, typed status codes and interceptors make it well suited to service-to-service calls.
- Browsers need gRPC-Web or a REST gateway; load balancing must work per request, not per connection.
- Define once in Protobuf and expose REST/JSON at the edge if outside clients need it.

# Choosing a style

There's no winner between REST, GraphQL and gRPC; there's only a fit for a particular audience. A good decision starts
from who calls the API, from where, and what they need, and is often "more than one".

## Side by side

| | REST + JSON | GraphQL | gRPC |
|-|-------------|---------|------|
| Contract | OpenAPI (optional) | Schema (required) | `.proto` (required) |
| Shape of responses | Server decides per endpoint | Client decides per query | Server decides per method |
| Round trips for a complex screen | Many, unless you add `?include=` or a BFF | One | Many, unless you add an aggregating method |
| Over-fetching | Common | Rare | Some |
| HTTP caching / CDNs | Excellent | Needs persisted queries | None |
| Streaming | SSE / WebSockets alongside | Subscriptions | Built in, both directions |
| Browser support | Native | Native | Needs gRPC-Web / a proxy |
| Payload size and speed | Medium | Medium | Small and fast |
| Learning curve for outside developers | Lowest | Medium | Highest |
| Server-side cost control | Easy (fixed endpoints) | Hard (arbitrary queries) | Easy |
| Typical home | Public and partner APIs | Product APIs for many client apps | Internal service-to-service |

## Common combinations

```
                 ┌──────────────── public / partner ───────────────┐
partners ───────▶│ REST + JSON (OpenAPI), webhooks for events       │
                 └──────────────────────────────────────────────────┘
                 ┌──────────────── first-party apps ───────────────┐
web, iOS, ──────▶│ GraphQL gateway  or  one BFF per client type     │
Android          └───────────────┬──────────────────────────────────┘
                                 │ gRPC (deadlines, streaming, typed)
                     ┌───────────┼───────────┬────────────┐
                  users       orders      pricing      search        internal services
                                 │ events (Kafka)
                             analytics, email, search indexing        asynchronous consumers
```

## Backends for frontends (BFF)

A **BFF** is a small server-side API owned by a client team, shaped exactly like that client's screens: `GET
/mobile/home` returns everything the home screen needs. It calls internal services in parallel over a fast network and
returns one compact response.

| BFF | GraphQL |
|-----|---------|
| Endpoints are fixed and cache well | One flexible endpoint |
| A service per client type to maintain | One gateway for all clients |
| Cost and performance are predictable | Cost depends on each query |
| Changing a screen may need a BFF deploy | Changing a screen is a query change |

Both solve the same problem: chatty clients on slow networks. The simulation below compares them with plain REST.

## Questions that decide it

1. **Who are the callers?** Unknown developers in any language → REST. Your own apps → GraphQL or BFF. Your own
   services → gRPC.
2. **Where do they run?** Browsers and phones on slow networks care about round trips; data-centre services care about
   per-call overhead.
3. **How varied are the clients' needs?** Many different screens over the same data → GraphQL.
4. **Is caching central?** Public, read-heavy, cacheable data → REST.
5. **Is it a stream?** Continuous data in either direction → gRPC streams or WebSockets.
6. **What can your team operate?** A GraphQL gateway with cost limits, or a schema registry for Protobuf, is real work.

## Try it

A fitness app has (1) gyms and insurers pulling workout summaries, (2) iOS, Android and web apps whose screens combine
profile, workouts and social data, and (3) a workout service streaming heart-rate samples to analytics. Pick a style
for each and use the simulation to compare REST, GraphQL and a BFF for one screen on a 200 ms network.

<details>
<summary>Answer</summary>

(1) REST + JSON with OpenAPI docs and webhooks for "new workout" events. (2) GraphQL with persisted queries and
DataLoader (or one BFF per client type). (3) gRPC client streaming. In the simulation, chatty REST takes ~22 sequential
round trips (over 4 s); one call through GraphQL with DataLoader or a BFF takes ~230-250 ms.
[The pick-a-style lab](#/labs/api-pick-a-style) makes these choices as checked steps.
</details>

## Key takeaways

- REST for broad reach and caching, GraphQL for many client apps with varied screens, gRPC inside the data centre.
- Most systems combine styles: REST or GraphQL at the edge, gRPC between services, events for async work.
- A BFF is a simpler alternative to GraphQL for client-shaped responses.
- Decide by audience, network, variety of needs, caching and what you can operate.

# Designing a RESTful API

Lesson 2.2 covered the basics (resources, methods, status codes). This lesson is about the parts that get hard once
an API is real: things that aren't CRUD, nested resources, partial updates, bulk operations, work that takes minutes,
and writing it all down.

## Naming

- **Plural nouns for collections**, ids for items: `/projects`, `/projects/prj_8f2`.
- **Nest only for ownership**, and only one or two levels: `/projects/prj_8f2/tasks` is fine; deeper chains
  (`/orgs/1/projects/2/tasks/3/comments/4`) are awkward. Once an item has a globally unique id, give it a top-level
  path too: `/tasks/tsk_91`.
- **Lowercase, hyphens in paths**, one case style in JSON fields.
- **No verbs in paths** for normal operations (`/createProject` → `POST /projects`).

## Actions that aren't CRUD

Some operations are really state transitions: cancel an order, publish a draft, retry a payment. Three honest options:

| Option | Example | When |
|--------|---------|------|
| Update a field | `PATCH /orders/42 {"status": "cancelled"}` | The transition is simple and has no side effects of its own |
| An action sub-resource | `POST /orders/42/cancel` | The action has rules, side effects or its own inputs (reason, refund) |
| Create a resource for it | `POST /refunds {"order": 42}` | The action has a lifecycle you'll want to query later |

Google's API design guide calls the second form a **custom method** (`POST /orders/42:cancel`). Pick one form and use it
everywhere.

## Partial updates

`PUT` replaces the whole resource, so a client that doesn't know about a new field would wipe it. For updates of a few
fields, use `PATCH` with one of two standard formats:

```http
PATCH /tasks/tsk_91
Content-Type: application/merge-patch+json        (RFC 7396)

{"title": "Ship v2", "assignee": null}             ← null means "remove"
```

```http
PATCH /tasks/tsk_91
Content-Type: application/json-patch+json         (RFC 6902)

[{"op": "replace", "path": "/title", "value": "Ship v2"},
 {"op": "remove",  "path": "/assignee"}]
```

Merge patch is simpler and covers most cases. Add **optimistic concurrency** so two editors don't overwrite each
other: return an `ETag` on GET, require `If-Match: "<etag>"` on PATCH, answer `412 Precondition Failed` if it changed.

## Errors

Use one error shape for every endpoint: RFC 9457 problem details (lesson 19.2). Include a stable `type` URI that
clients can switch on, a human `detail`, field-level errors for validation, and the request id.

## Bulk operations

Creating 5,000 contacts one request at a time is slow. Offer a batch endpoint, and decide up front:

```http
POST /contacts:batchCreate
{"contacts": [ {...}, {...} ]}              ← cap the size, e.g. 100 or 1,000 items

207 Multi-Status  (or 200 with per-item results)
{"results": [ {"index": 0, "status": 201, "id": "c_1"},
              {"index": 1, "status": 422, "error": {...}} ]}
```

Is a batch all-or-nothing or per item? Per item is friendlier for imports; all-or-nothing needs a transaction. Say
which in the docs.

## Long-running operations

If the work takes longer than a few seconds (a video transcode, a data export), don't hold the request open:

```http
POST /exports {"format": "csv", "range": "2026-Q3"}
→ 202 Accepted
  Location: /operations/op_5c1

GET /operations/op_5c1
→ 200 {"status": "running", "progress": 0.42}
→ 200 {"status": "succeeded", "result": {"url": "https://…/export.csv"}}
```

The client polls the operation (with a `Retry-After` hint) or gets a webhook when it finishes.

## Write it down: OpenAPI

An **OpenAPI** document (version 3.1 is current and aligns with JSON Schema) describes every path, parameter, body,
response and security scheme. From one file you get reference docs, mock servers, client SDKs, request validation and
contract tests. Write it first and review it like code, in the same pull requests as the implementation.

```yaml
paths:
  /tasks/{id}:
    patch:
      operationId: updateTask
      parameters: [{ name: id, in: path, required: true, schema: { type: string } }]
      requestBody:
        content: { application/merge-patch+json: { schema: { $ref: '#/components/schemas/TaskPatch' } } }
      responses:
        '200': { description: Updated, content: { application/json: { schema: { $ref: '#/components/schemas/Task' } } } }
        '412': { $ref: '#/components/responses/PreconditionFailed' }
```

Design the API for a project tracker: projects contain tasks; tasks can be assigned, commented on, moved between

## Key takeaways

- Plural nouns, shallow nesting, no verbs in paths, one naming style.
- Model non-CRUD actions as a field update, an action sub-resource or a new resource, consistently.
- Use PATCH with merge patch for partial updates, and ETags with If-Match against lost updates.
- Batch endpoints need size caps and a clear partial-failure rule; slow work returns 202 and an operation resource.
- Describe the API in OpenAPI and treat that file as the source of truth.

# Architectural styles at a glance

"Should we use REST or GraphQL?" is often the first question a team asks, and it's usually asked too early. An API
**style** is a set of constraints on how clients and servers talk. Each style makes some things easy and others hard.
Knowing what each one constrains lets you pick on purpose instead of by fashion.

## The main styles

| Style | Organised around | Typical transport and format | You'll recognise it by |
|-------|------------------|------------------------------|------------------------|
| **REST** | Resources (nouns) with a uniform set of methods | HTTP, JSON | `GET /orders/42`, `POST /orders` |
| **RPC** (gRPC, JSON-RPC, Thrift) | Operations (verbs) | gRPC: HTTP/2 + Protobuf | `OrderService.GetOrder({id: 42})` |
| **GraphQL** | A typed graph the client queries | HTTP (usually one `POST /graphql`), JSON | `query { order(id: 42) { total items { sku } } }` |
| **Event-driven / async** | Messages and events on channels | Kafka, AMQP, MQTT, webhooks, WebSockets | `order.created` on a topic |
| **SOAP** | Operations described in WSDL | XML over HTTP | `<soap:Envelope>` |

## A short history

- **1990s-2000s: RPC and SOAP.** CORBA, then SOAP with WSDL contracts and WS-* standards (security, transactions).
  Powerful, heavy, and still found in banking, telecoms and government integrations.
- **2000: REST.** Roy Fielding's dissertation described the style the web itself uses. By the 2010s "REST + JSON" was
  the default for public APIs.
- **2015: GraphQL** (open-sourced by Facebook, which built it for its mobile apps in 2012) and **gRPC** (open-sourced
  by Google, from its internal Stubby RPC system).
- **Today:** most companies use several styles at once: REST or GraphQL at the edge, gRPC between services, events for
  anything asynchronous.

## What each style optimises for

| | REST | gRPC | GraphQL | Events |
|-|------|------|---------|--------|
| Easy for any client, tool and language | ✅✅ | ➖ (needs codegen; browsers need a proxy) | ✅ | ➖ |
| HTTP caching and CDNs | ✅✅ | ❌ | ➖ (needs persisted queries) | n/a |
| Fetch exactly what a screen needs | ➖ | ➖ | ✅✅ | n/a |
| Low latency, small payloads, streaming | ➖ | ✅✅ | ➖ | ✅ |
| Strong typed contract | ➖ (OpenAPI helps) | ✅✅ | ✅✅ | ✅ (with a schema registry) |
| Decoupling in time (producer doesn't wait) | ❌ | ❌ | ➖ (subscriptions) | ✅✅ |

## It's about constraints

Every style **gives up** freedom to **gain** something:

- REST gives up arbitrary operations (everything is a resource and a method) to gain uniformity and cacheability.
- gRPC gives up human-readable payloads and easy browser use to gain speed, streaming and generated types.
- GraphQL gives up simple per-URL caching and predictable server cost to gain client-shaped responses.
- Events give up an immediate answer to gain decoupling and buffering.

The next lessons look at each in turn; lesson 20.6 brings them together into a decision.

## Try it

Name the style: (a) the Stripe API, (b) the GitHub API used by its own web UI, (c) Google Cloud's internal service
calls, (d) a bank's 2008-era account-opening integration, (e) Shopify's order webhooks.

<details>
<summary>Answer</summary>

(a) REST (resource-oriented, JSON, form-encoded requests). (b) GitHub offers both REST (v3) and GraphQL (v4); its
newer UI features lean on GraphQL. (c) gRPC / Protobuf (Google's public Cloud APIs are also defined in Protobuf and
exposed as both gRPC and REST/JSON). (d) Very likely SOAP with a WSDL. (e) Event-driven: HTTP webhooks carrying JSON
events.
</details>

## Key takeaways

- A style is a set of constraints that trades some freedoms for some guarantees.
- REST (resources), RPC (operations), GraphQL (client-shaped queries) and events (async messages) solve different
  problems.
- Most real systems mix styles: one at the edge, another between services, events for async work.

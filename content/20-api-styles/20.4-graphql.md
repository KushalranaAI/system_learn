# GraphQL

A mobile profile screen needs a user's name, their last 20 posts, and a like count and author avatar for each post.
With resource-per-endpoint REST that's a request for the user, one for the posts, and then 20 more, one after another,
each returning far more fields than the screen shows. On a 200 ms mobile round trip the screen takes seconds. Facebook
hit exactly this problem in 2012 and built GraphQL to solve it.

## The idea

The server publishes a **typed schema** of everything that can be fetched. The client sends a **query** that names
exactly the fields it wants, in the shape it wants, and gets back JSON in that shape, in one round trip.

```graphql
type User { id: ID!  name: String!  avatarUrl: String  posts(first: Int = 10, after: String): PostConnection! }
type Post { id: ID!  text: String!  likeCount: Int!  author: User! }
type Query { user(id: ID!): User }
type Mutation { likePost(id: ID!): Post! }
type Subscription { postLiked(postId: ID!): Post! }
```

```graphql
query Profile($id: ID!) {
  user(id: $id) {
    name
    posts(first: 20) {
      edges { node { id text likeCount author { avatarUrl } } }
      pageInfo { endCursor hasNextPage }
    }
  }
}
```

- **Queries** read, **mutations** write, **subscriptions** push updates (usually over WebSockets).
- The schema is introspectable, so tools give autocomplete, type checking and generated client types.
- The spec is maintained by the GraphQL Foundation; the September 2025 edition (the first since 2021) added things
  like `@oneOf` input objects. Incremental delivery (`@defer`, `@stream`) is still outside the spec.

## How the server runs a query

Each field has a **resolver**: a function that fetches that field for its parent. The engine walks the query and calls
resolvers level by level.

```
user(id)            → 1 query: SELECT * FROM users WHERE id = ?
  posts(first: 20)  → 1 query: SELECT * FROM posts WHERE user_id = ? LIMIT 20
    author          → 20 queries: SELECT * FROM users WHERE id = ?   ← the N+1 problem
```

### N+1 and DataLoader

Naive resolvers run one query per item. The standard fix is **DataLoader**-style batching: within one tick, collect all
the ids that resolvers at the same level ask for, then run one query (`WHERE id IN (…)`) and hand each resolver its
row. 22 queries become 3. The simulation below lets you count them.

## What it costs you

| Problem | Why it happens | Usual answer |
|---------|----------------|--------------|
| **HTTP caching** is hard | Queries are POSTs to one URL | Client-side normalised caches (Apollo, Relay); **persisted queries** sent as `GET /graphql?id=<hash>` that CDNs can cache |
| **Expensive queries** | A client can nest `friends { friends { friends … } } }` | Depth limits, **query cost analysis** (points per field, like GitHub's rate limit), timeouts, and allowing only persisted queries from first-party apps |
| **Authorization** per field | Data from many sources in one response | Check access in the business layer every resolver calls, not in each resolver ad hoc |
| **Errors** | One response can be partly successful | `data` plus an `errors` array; design for partial results |
| **Monitoring** | Every request is `POST /graphql 200` | Track per operation name, not per URL |

## Federation

Large companies split one graph across teams: each service owns part of the schema (users, posts, payments) and a
**gateway / router** composes them (Apollo Federation, GraphQL Fusion, and others). The client still sees one graph.

## When GraphQL fits

- ✅ Many different clients (web, iOS, Android, TVs) with different screens over the same data.
- ✅ Data from several backends that one screen needs together.
- ✅ Teams that want a typed, introspectable contract with great tooling.
- ❌ Simple public APIs where cacheability and predictability matter most.
- ❌ File uploads, streaming bulk data, or a few fixed operations.

## Try it

Write the query for an order details screen that shows the order's status, total, each line's product name and image,
and the courier's name. Then say how many database queries a naive server runs for an order with 8 lines, and how many
with DataLoader.

<details>
<summary>Answer</summary>

```graphql
query Order($id: ID!) {
  order(id: $id) {
    status
    total { amount currency }
    lines { quantity product { name imageUrl } }
    delivery { courier { name } }
  }
}
```

Naive: 1 (order) + 1 (lines) + 8 (one product per line) + 1 (delivery) + 1 (courier) = 12. With DataLoader the 8
product lookups become 1 batched query: about 5. In both cases the client makes **one** round trip.
</details>

## Key takeaways

- GraphQL lets clients ask for exactly the fields they need, in one round trip, against a typed schema.
- Resolvers make N+1 queries easy to create; batch them with DataLoader.
- You trade simple HTTP caching and predictable cost for flexibility; persisted queries and cost limits win most of it
  back.
- It shines with many clients and many backends; it's overkill for small, stable public APIs.

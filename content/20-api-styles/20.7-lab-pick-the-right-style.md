# Lab: pick the right style

A fitness app serves partners, its own mobile apps and its internal services. Choose a style for each, then fix a slow
screen and a GraphQL N+1.

> **Interactive version:** [open the pick-a-style lab](#/labs/api-pick-a-style) to make the choices and measure the
> screen in the fetch-patterns simulation.

## Step 1: Partners

<details>
<summary>Reference</summary>

REST + JSON, an OpenAPI document, API keys or OAuth client credentials per partner, cursor pagination, and webhooks
for new data. Partners use every language and tool, and the data is a stable feed.
</details>

## Step 2: Service to service

<details>
<summary>Reference</summary>

gRPC with a client-streaming call for heart-rate samples (one long-lived stream, compact Protobuf), deadlines on every
call, and a shared `.proto` repository with breaking-change checks.
</details>

## Step 3: The profile screen

The app calls `GET /users/1`, then `GET /users/1/workouts`, then `GET /workouts/:id/stats` for 20 workouts, over a
200 ms round trip.

<details>
<summary>Reference</summary>

22 sequential round trips ≈ 4.4 s before server time. Parallel requests over HTTP/2 help (4 waves), but the stats calls
still wait for the list. One call shaped like the screen fixes it: a BFF endpoint `GET /mobile/profile/1`, or one
GraphQL query. Either gets the screen to ~250 ms.
</details>

## Step 4: The N+1

<details>
<summary>Reference</summary>

The `stats` resolver runs once per workout: 22 queries per screen. Batch it with DataLoader so each level of the query
issues one `WHERE id IN (…)` query: 3 queries.
</details>

## Step 5: Caching GraphQL

<details>
<summary>Reference</summary>

Persisted queries: the app registers its queries at build time and sends `GET /graphql?id=<sha256>&variables=…`. CDNs
can cache those, and the server can reject queries it doesn't know.
</details>

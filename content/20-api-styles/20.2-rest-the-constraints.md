# REST: the constraints

Almost every HTTP+JSON API calls itself RESTful. Few of them follow what REST originally meant. That's fine in
practice, but knowing the original constraints explains *why* REST APIs behave well when they do: why they cache, scale
and survive change.

## Where it comes from

**Representational State Transfer** was described by Roy Fielding in his 2000 PhD dissertation as the architectural
style of the web. The web had to work across millions of independent servers and clients, through proxies and
caches, and keep working as both sides changed independently. REST is the list of constraints that made that
possible.

## The six constraints

| Constraint | What it says | What it buys you |
|------------|--------------|------------------|
| **Client-server** | UI and data storage are separate | Each side evolves independently |
| **Stateless** | Each request carries everything needed to understand it; no session state on the server between requests | Any server can handle any request: easy load balancing and scaling out (module 4) |
| **Cacheable** | Responses say whether and for how long they can be cached | Clients, proxies and CDNs can answer without the server |
| **Uniform interface** | One fixed set of operations on resources, self-describing messages, hypermedia links | Generic tools (browsers, caches, crawlers) work with every API |
| **Layered system** | A client can't tell whether it's talking to the server or an intermediary | Load balancers, gateways and CDNs can be inserted freely |
| **Code on demand** (optional) | Servers may send code to run on the client | JavaScript in browsers |

"Stateless" doesn't mean the system has no state; the database has plenty. It means the **conversation** has no
hidden state: request 2 doesn't depend on something the server remembers from request 1. Auth tokens, cursors and
ETags travel with each request instead.

## Resources and representations

A **resource** is anything you can name: an order, a user's cart, "today's exchange rates". A URI identifies it. What
travels over the wire is a **representation** of its current state, in a format the client asked for:

```http
GET /orders/42
Accept: application/json        → {"id": 42, "status": "shipped"}
Accept: text/csv                → id,status\n42,shipped
```

Clients change resources by sending representations back (`PUT`, `PATCH`) or by posting to them.

## Hypermedia (HATEOAS)

"Hypermedia as the engine of application state" means responses include **links** to what the client can do next,
so clients follow links instead of building URLs:

```json
{
  "id": "ord_42",
  "status": "pending",
  "_links": {
    "self":   { "href": "/orders/ord_42" },
    "cancel": { "href": "/orders/ord_42/cancel", "method": "POST" },
    "pay":    { "href": "/payments?order=ord_42", "method": "POST" }
  }
}
```

The server can then change URLs, or remove the `cancel` link once an order ships, without breaking clients. This is
how websites work (you click links), but most API clients are written against fixed URLs, so few APIs go this far.
Pagination links (`next`, `prev`) are the part almost everyone uses.

## The Richardson maturity model

A popular way to describe how "RESTful" an API is:

| Level | Description | Example |
|-------|-------------|---------|
| 0 | One URL, one method, actions in the body (RPC over HTTP) | `POST /api {"action": "getOrder", "id": 42}` |
| 1 | Separate URLs per resource | `POST /orders/42 {"action": "get"}` |
| 2 | HTTP methods and status codes used properly | `GET /orders/42` → `200`, `DELETE /orders/42` → `204` |
| 3 | Hypermedia controls | Responses carry links to next actions |

**Level 2 is where most good APIs sit**, and it's a fine target. It gets you caching, safe retries and tooling for
free.

## Try it

This API calls itself REST. Which constraints does it break?

```
POST /api/login            → sets a server-side session; the next calls depend on it
POST /api/getOrders        → 200 {"error": "not logged in"} when the session expired
GET  /api/orders/42        → Cache-Control: no-store on every response, including the product catalogue
```

<details>
<summary>Answer</summary>

- **Stateless:** later requests depend on server-side session state from `/login`, so requests can't go to any
  server without a shared session store (or sticky sessions). Use a token sent with every request.
- **Uniform interface:** `POST /getOrders` is an RPC action, not a resource with GET; and errors come back as `200`.
- **Cacheable:** the catalogue never changes per user, yet it's marked `no-store`, so no CDN or browser can help.
</details>

## Key takeaways

- REST is the architectural style of the web: client-server, stateless, cacheable, uniform interface, layered.
- Statelessness lets any server handle any request; cacheability lets intermediaries answer for you.
- Resources are named by URIs; clients exchange representations of them.
- Most good APIs are "Level 2": real resources, methods and status codes. Hypermedia is optional but useful for
  pagination and workflows.

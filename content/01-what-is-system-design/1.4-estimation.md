# Back-of-the-envelope estimation

You don't need exact numbers. You need to know whether something is 10, 1,000
or 100,000 per second, because each of those is a different design.

## Handy constants

| Fact | Value | Rounded for mental math |
|------|-------|--------------------------|
| Seconds in a day | 86,400 | **~100,000 (10⁵)** |
| Seconds in a month | ~2.6 million | ~2.5 × 10⁶ |
| 1 KB / 1 MB / 1 GB / 1 TB | 10³ / 10⁶ / 10⁹ / 10¹² bytes | |
| Peak vs average traffic | 2–10x | use **3x** if unsure |

## Latency numbers worth knowing (orders of magnitude)

| Operation | Roughly |
|-----------|---------|
| Read from RAM | ~100 ns |
| Read 1 MB sequentially from RAM | ~10 µs |
| Random read from an SSD | ~20–100 µs |
| Round trip inside one data centre | ~0.5 ms |
| Redis GET over the network | ~0.5–1 ms |
| Simple indexed DB query | ~1–5 ms |
| Round trip across a continent | ~50–80 ms |
| Round trip across the world | ~150–250 ms |

Takeaway: **memory is fast, the network is slow, and distance is slowest.**
Avoid extra network hops and cross-region calls on the hot path.

## The four estimates

### 1. Requests per second (QPS)
```
QPS = daily actions ÷ 100,000
peak QPS = QPS × 3
```
*10M daily users, each opening 10 links/day = 100M/day → **1,000/s average,
~3,000/s peak**.*

### 2. Read:write ratio
Count reads and writes separately. A URL shortener might be **100:1**
(many redirects per created link). Read-heavy systems get caches and replicas;
write-heavy ones need a different approach (queues, partitioning).

### 3. Storage
```
storage/year = new items per day × size per item × 365
```
*1M new links/day × 500 bytes = 500 MB/day → **~180 GB/year**.* That fits on
one database for years, which is a useful thing to learn early.

### 4. Bandwidth
```
bandwidth = QPS × response size
```
*3,000 req/s × 2 KB = 6 MB/s ≈ 48 Mbit/s.* That's fine. But 3,000 req/s of
2 MB images = 6 GB/s, so you need a CDN.

## Worked example: a photo-sharing app

- 5M daily active users; each views 50 photos and uploads 0.2 photos a day.
- **Views:** 250M/day → 2,500/s average → **~7,500/s peak**.
- **Uploads:** 1M/day → ~10/s average → ~30/s peak.
- **Read:write** ≈ 250:1, so cache and CDN everything.
- **Storage:** 1M photos × 2 MB = 2 TB/day → **~730 TB/year**. That calls for
  object storage (like S3), not a database.
- **Bandwidth at peak:** 7,500 × 200 KB (resized) ≈ 1.5 GB/s, so a CDN is
  mandatory.

Four lines of arithmetic told you: object storage, CDN, cache, and a modest
database for metadata.

## Try it

Estimate for a **chat app** with 2M daily users, each sending 40 messages a day
of ~200 bytes, with messages kept forever:
1. Messages per second (average and peak)
2. Storage per year
3. Is it read-heavy or write-heavy? (Hint: each message is read by how many
   people?)

<details>
<summary>Answer</summary>

80M messages/day → ~800/s average, ~2,400/s peak.
80M × 200 B = 16 GB/day → ~5.8 TB/year (plus indexes and replicas).
Reads depend on group size: 1:1 chats are about 1 read per write; large groups
make it read-heavy at delivery time.
</details>

## Key takeaways

- Round aggressively: a day is about 10⁵ seconds.
- Estimate QPS, read:write ratio, storage and bandwidth.
- Know the latency ladder: RAM ≪ SSD ≪ network ≪ distance.
- The numbers tell you which parts you need, and which you don't.

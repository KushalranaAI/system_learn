# Functional vs non-functional requirements

Nobody hands you a neat list of requirements. You get a conversation, a
screenshot, or a one-line ticket. Your job is to turn that into two lists.

## Functional requirements: what it does

These are features, written as things a user can do:

- A user can create a short link from a long URL.
- A user can open a short link and land on the original page.
- A user can see how many times their link was clicked.

Check: **if you remove it, does the product lose a feature?** If so, it's
functional.

## Non-functional requirements: how well it does it

These are qualities. They usually decide the architecture:

| Quality | Question to ask | Example target |
|---------|-----------------|----------------|
| **Latency** | How fast must it feel? | Redirect p99 < 100 ms |
| **Throughput** | How much traffic at peak? | 50,000 redirects/s |
| **Availability** | How often may it be down? | 99.9% (≈ 43 min/month) |
| **Durability** | Can we ever lose data? | A created link is never lost |
| **Consistency** | Must everyone see the latest data instantly? | New link works within 1 s |
| **Cost** | What's the budget? | < $500/month |
| **Security/privacy** | Who may see what? | Only owners see click stats |

Two apps with identical features can need completely different systems because
of these numbers.

## How to find them

Users rarely say "99.9% availability". They say things that *imply* it. Learn
to translate:

| They say | You hear |
|----------|----------|
| "It has to be instant." | Latency target. Ask: instant for which action? |
| "We're launching on TV next week." | A traffic spike. Estimate the peak. |
| "Losing an order would be a disaster." | Durability + consistency on writes. |
| "It's an internal tool for 20 people." | Low scale. Keep it simple and cheap. |
| "Users are mostly on mobile in rural areas." | Slow networks. Small payloads, offline support. |

Good questions to ask every time:
1. Who are the users, and how many?
2. What are the 2–3 most important actions?
3. Which action must never fail? Which can be slow?
4. Is the traffic read-heavy or write-heavy?
5. What happens if data is a few seconds stale?

## Scope it down

Write a third list: **out of scope**. "Custom domains: not in v1." This keeps
the design focused, and shows you made a choice rather than forgot.

## Try it

A bakery owner says: *"I want customers to order cakes online and pick them up.
Saturdays are crazy."*

Write:
- 3 functional requirements
- 3 non-functional requirements, with numbers you'd confirm with her
- 2 things that are out of scope

<details>
<summary>One possible answer</summary>

**Functional:** browse cakes; place an order for a pickup time slot; the owner
sees and updates orders.
**Non-functional:** handle the Saturday-morning peak (say 50 orders in an hour,
so tiny); never lose a paid order; the order page loads in < 2 s on mobile.
**Out of scope:** delivery; loyalty points.

The lesson in this one: the scale is small. A single server and database is the
right design, so don't over-build.
</details>

## Key takeaways

- Functional = features; non-functional = qualities with numbers.
- Non-functional requirements drive the architecture.
- Translate vague phrases into measurable targets, and confirm them.
- Write down what's out of scope.

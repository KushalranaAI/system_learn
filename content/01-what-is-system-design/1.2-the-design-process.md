# The design process

Designs rarely start as diagrams. They start as a sentence: *"Can we let
customers track their delivery live?"* This lesson is the path from that
sentence to something people can build.

## Five steps

### 1. Clarify the problem
Ask questions before drawing anything.
- Who uses it? Customers, drivers, restaurants?
- What exactly must it do? See the location on a map? Get an ETA? Get notified?
- What does "live" mean: every second or every 30 seconds?

Write the answers down as **requirements** (next lesson).

### 2. Estimate the size
Rough numbers decide the design (lesson 1.4).
- 50,000 active deliveries at peak.
- Each driver's phone sends a location every 5 s, so **10,000 updates/s**.
- Each customer watching a map adds read traffic.

A design for 10 updates/s and one for 10,000 updates/s look very different.

### 3. Sketch a first version
The simplest thing that could work:

```
Driver app ──POST /location──▶ API server ──▶ Database
Customer app ──GET /delivery/:id──▶ API server ──▶ Database
```

Define the **API** (what requests exist) and the **data** (what's stored)
before adding boxes.

### 4. Find the bottlenecks
Push the sketch against your numbers.
- 10,000 writes/s of positions that are useless after 10 seconds. Does that
  belong in the main database?
- Customers polling every second doubles traffic. Could the server push
  updates instead?

Each answer changes the design. Maybe the latest positions go into an
in-memory store, and live updates go over a WebSocket.

### 5. Review and write it down
Explain the design to someone else, list what could fail, and record each
decision and its reason. Next month, you or a teammate will ask "why did we do
it like this?"

## It's a loop, not a line

You'll go around steps 3–5 several times. Every bottleneck you find sends you
back to the sketch. That's normal, and it's the actual work.

```
clarify → estimate → sketch → find bottlenecks → review
                       ▲               │
                       └───────────────┘
```

## Try it

Run the five steps on **"a to-do list app that syncs across phone and laptop"**:
1. Write five clarifying questions.
2. Guess users and requests per second.
3. Sketch client → server → database, with three API endpoints.
4. Name one bottleneck or failure you'd worry about first.

## Key takeaways

- Start with questions, not boxes.
- Numbers decide designs, so estimate early.
- Sketch the simplest version, then let bottlenecks drive each change.
- Write down decisions and their reasons.

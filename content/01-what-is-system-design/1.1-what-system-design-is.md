# What system design is

You open a food delivery app, tap a restaurant and the menu appears in under a
second. Behind that tap is a set of computers, each doing one job, wired
together so the right data reaches you quickly. Someone chose those computers,
those jobs and those wires. **That choosing is system design.**

## Design vs. code

Writing code answers *"how does this function work?"*.
System design answers bigger questions:

- **What pieces do we need?** One server or ten? A database? A cache? A queue?
- **How do they talk?** Who calls whom, and what happens if the call fails?
- **Where does data live?** Which store, in what shape, with how many copies?
- **What happens under pressure?** 10x the users, a crashed machine, a slow network.

A good design can be built by many people and still holds up when the app
grows. A bad one works perfectly for the demo and falls over on launch day.

## The building blocks

Almost every backend is put together from a small set of parts:

| Part | Its job | Everyday analogy |
|------|---------|------------------|
| **Client** | The app or browser that sends requests | A customer placing an order |
| **API server** | Runs your code for each request | The cook |
| **Database** | Stores data durably | The pantry |
| **Cache** | Keeps hot data in memory for fast reads | Ingredients on the counter |
| **Load balancer** | Spreads requests across servers | The host seating guests at free tables |
| **Queue** | Holds work to be done later | The order ticket rail |
| **CDN** | Serves files from near the user | A local branch of the restaurant |

Over this course you'll add each part *only when a real problem demands it*.
That habit, adding complexity only when it's needed, is the most useful skill in
system design.

## There is no single right answer

Two experienced engineers can design the same app differently and both be
right, because they made different **tradeoffs**: one optimised for cost, the
other for speed. What makes a design good is that it **meets its requirements**
and that **its author can explain why** each choice was made.

## Try it

Pick an app you use every day (a chat app, a music player, a ride app). On
paper, draw:

1. The client.
2. The servers it might talk to.
3. Where your messages, songs or trips are stored.

Don't worry about being correct. You'll redraw it at the end of the course and
compare.

## Key takeaways

- System design is choosing the parts of a system, how they connect, and how
  they behave under load and failure.
- A handful of building blocks cover most backends.
- Good designs meet their requirements and come with reasons.

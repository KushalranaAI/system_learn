# Distributed locks

"Only one worker may process invoice 42 at a time." On one machine, a mutex does it. Across machines, you need a
**distributed lock**, and it's much harder to get right than it looks.

## The naive Redis lock

```
SET lock:invoice:42 worker-7 NX PX 30000     # acquire if absent, expire after 30 s
... do work ...
DEL lock:invoice:42                          # release
```

Problems:
1. **Releasing someone else's lock:** worker 7's work takes 35 s, the lock expires, worker 9 acquires it, then worker
   7 finishes and `DEL`s worker 9's lock. Fix: release only if the value is still yours (compare-and-delete in a Lua
   script).
2. **Expiry during work:** worker 7 pauses (GC, a VM freeze, a slow disk) past 30 s. Worker 9 gets the lock. **Both
   now believe they hold it.** No lock algorithm alone can prevent this, because worker 7 doesn't know it was paused.
3. **Redis failover:** the lock was written to the primary, which died before replicating it; the new primary has no
   lock, so a second worker acquires it.

## Fencing tokens

The real fix for problem 2: make the **resource** reject stale lock holders.

```
lock service hands out increasing tokens: worker 7 gets token 33, later worker 9 gets token 34
every write to the resource includes the token:
  UPDATE invoices SET … , fence = 34 WHERE id = 42 AND fence < 34
worker 7 wakes up and writes with token 33 → rejected (33 < 34)
```

Now even if two workers think they hold the lock, only the newest can change anything.

## Stronger lock services

For correctness-critical locks, use a **consensus-based** system: etcd, ZooKeeper, Consul. Their leases are backed by
a replicated, majority-agreed log (Raft or ZAB), so failover can't silently lose a lock. They provide monotonically
increasing revision numbers that work as fencing tokens.

## Do you need a lock at all?

Often there's a simpler, safer design:

| Instead of a lock | Use |
|-------------------|-----|
| "Only one worker processes job X" | Queue visibility timeouts + idempotent jobs (Module 7) |
| "Don't sell the same seat twice" | A conditional update / unique constraint in the database |
| "Only one instance runs the cron" | A unique `INSERT INTO runs(job, date)`, or a single scheduler |
| "Update this counter safely" | Atomic `INCR` / `UPDATE … SET x = x + 1` |
| "All updates to account A in order" | Route them to one partition or consumer (Module 15) |

Locks are for **efficiency** (avoiding duplicate work) more often than for **correctness**. When correctness depends
on it, you need fencing or a database constraint underneath.

## Try it

Two workers sometimes send the same weekly email because a Redis lock with a 60 s TTL expires while sending takes
longer. Propose two fixes, one with locks and one without.

<details>
<summary>Answer</summary>

With locks: renew the lease while working (heartbeat extension) and release with compare-and-delete. Even then, a
long pause can cause a duplicate, so record "sent" behind a fencing token or constraint. Without locks: claim the email
with `INSERT INTO sent_emails (user_id, week) … ON CONFLICT DO NOTHING` and only send if the insert won (lesson 7.3).
</details>

## Key takeaways

- Simple Redis locks break on long pauses, wrong releases and failover.
- Fencing tokens make the resource reject stale lock holders.
- Use consensus-backed lock services when correctness depends on the lock.
- Often, a constraint, a conditional update or a queue removes the need for a lock.

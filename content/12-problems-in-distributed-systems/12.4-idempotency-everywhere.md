# Idempotency everywhere

You've met idempotency in APIs (lesson 2.3) and jobs (lesson 7.3). In distributed systems it stops being a nice
property and becomes a **requirement for every operation that may be retried**, which is all of them.

## Why "exactly once" is a myth

To do something exactly once, the sender must know whether the receiver did it. But the reply can be lost (lesson
12.1). So the sender must either risk never doing it (at-most-once) or risk doing it twice (at-least-once). There's
no third option on an unreliable network.

What systems call "exactly-once" is really: **at-least-once delivery + idempotent processing = effectively once.**

## Techniques

### 1. Idempotency keys
The caller attaches a unique key per *intent*; the receiver stores `key → result` and returns the stored result on
repeats.

```
POST /payments  Idempotency-Key: ord42-attempt   → first time: charge, store, return 201
                                                  → again: return the stored 201, no charge
```

### 2. Natural idempotence
Design operations as **"set to"** rather than **"change by"**:

| Not idempotent | Idempotent |
|----------------|------------|
| `balance += 100` | Record transfer `t_981` (unique id); balance = sum of transfers |
| "Add item to cart" | `PUT /cart/items/:sku {qty: 2}` |
| "Increment view count" | Insert `(view_id)` once; count rows |

### 3. Conditional writes (compare-and-set)
```sql
UPDATE orders SET status = 'paid', version = version + 1
WHERE id = 42 AND version = 7;        -- 0 rows → someone else changed it; re-read and decide
```

### 4. Deduplication on consumers
Keep a table (or Redis set with TTL) of processed message ids. Insert and apply the effect **in the same
transaction**.

## Where keys come from

- **Client-generated** (a UUID created when the user taps "Pay"): survives app retries.
- **Derived from the business** (`order_id + "charge"`): retries anywhere in the system map to the same key.
- Store keys long enough to cover realistic retry windows (hours to days), scoped by user or tenant.

## Idempotency in a chain

If A retries B, and B calls C, then B must call C with a key **derived from A's key** (not a fresh one per attempt).
Otherwise A's retry creates a new, distinct C operation.

```
A: key=K  →  B: uses K → calls C with key = K + ":reserve"
```

## Try it

An "add loyalty points" consumer reads `OrderPaid{order_id, points}` events and runs
`UPDATE users SET points = points + $points`. After a broker failover, some users got double points. Make it
idempotent.

<details>
<summary>Answer</summary>

```sql
BEGIN;
INSERT INTO points_ledger (order_id, user_id, points) VALUES ($1, $2, $3)
  ON CONFLICT (order_id) DO NOTHING;
-- only if a row was inserted:
UPDATE users SET points = points + $3 WHERE id = $2;
COMMIT;
```
Or skip the counter entirely and compute points as `SUM(points) FROM points_ledger`. Redelivered events then hit the
unique `order_id` and change nothing.
</details>

## Key takeaways

- On unreliable networks, exactly-once delivery is impossible; effectively-once is achievable.
- Use idempotency keys, "set to" operations, conditional writes and consumer deduplication.
- Derive keys from the original intent and pass them down the chain.
- Record the key and the effect atomically.

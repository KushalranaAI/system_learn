# Clocks

"Order events by timestamp" sounds safe. Across machines it isn't: every machine's clock is slightly wrong, and they
are wrong by different amounts.

## Physical clocks drift

- Quartz clocks drift (tens of ppm, roughly a few ms per minute without correction).
- **NTP** keeps them close, typically within a few milliseconds in a data centre, but sometimes 100+ ms, and it can
  step clocks **backwards**.
- VMs pause; leap seconds happen; misconfigured hosts run minutes off.

So two events on two machines can't be ordered reliably by wall-clock time if they're closer than the clock error.

```
Server A (clock +40 ms fast): writes x=1 at "10:00:00.050"
Server B (accurate):          writes x=2 at "10:00:00.030"  (really happened 20 ms later)
Last-write-wins by timestamp → x=1. The later write is lost.
```

## Use the right clock for the job

| Need | Use |
|------|-----|
| Measuring durations, timeouts | **Monotonic clock** (never goes backwards); never wall-clock subtraction |
| Human-readable times, rough ordering | Wall clock (UTC) |
| Ordering events that are causally related | **Logical clocks** (below) |
| Strong global ordering | A single sequencer, or bounded-uncertainty clocks (e.g. Spanner's TrueTime) |

## Lamport clocks

A counter per node:
- increment before each event;
- send the counter with each message;
- on receive: `counter = max(local, received) + 1`.

If event A **caused** event B (A happened before B, via messages), then `L(A) < L(B)`. The reverse isn't guaranteed:
a smaller number doesn't prove causation. Break ties with the node id to get a consistent total order.

## Vector clocks

Each node keeps a vector of counters, one per node. Comparing two vectors tells you whether A happened before B, B
before A, or they're **concurrent** (neither saw the other). Concurrent writes are exactly the conflicts a system must
resolve (Module 13). Vector clocks grow with the number of nodes, so systems use variants (version vectors per key,
dotted version vectors).

## Hybrid logical clocks (HLC)

Combine wall time with a logical counter: timestamps stay close to real time (readable, roughly ordered) and still
respect causality. Used by CockroachDB, MongoDB and others.

## Practical rules

- Store and compare times in **UTC**.
- Never use timestamps alone to decide which concurrent write wins if losing a write matters. Use versions,
  sequence numbers or conflict resolution.
- For ordering within one entity (a chat, an account), use a **per-entity sequence** assigned in one place.
- Measure timeouts with monotonic clocks.

## Try it

Two data centres accept edits to the same document and use last-write-wins by server timestamp. Users complain their
edits sometimes vanish. Explain why, and suggest two alternatives.

<details>
<summary>Answer</summary>

The clocks differ, so a write that really happened later can carry an earlier timestamp and lose. Also, truly
concurrent edits are silently dropped. Alternatives: version vectors to **detect** concurrent edits and merge them or
ask the user; route all writes for one document to a single home region (a single sequencer); or use CRDTs or
operational transforms for collaborative editing (Module 13).
</details>

## Key takeaways

- Wall clocks drift and jump; machines disagree by ms to seconds.
- Use monotonic clocks for durations, logical clocks for causality.
- Lamport clocks order causally related events; vector clocks detect concurrency.
- Don't let timestamp comparison silently decide conflicts; use versions or a single sequencer.

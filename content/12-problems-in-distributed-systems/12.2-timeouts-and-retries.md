# Timeouts and retries

Retries are the most useful and the most dangerous tool in distributed systems. Used well, they hide transient
failures. Used badly, they turn a small slowdown into a full outage.

## Choosing a timeout

- Base it on the dependency's **measured latency**: a bit above its p99 (e.g. p99 = 120 ms → timeout 250–300 ms).
- Respect the **caller's deadline**: if the user request has 1 s left, don't wait 5 s for a sub-call.
- **Propagate deadlines** down the chain (gRPC does this natively): each hop knows how much time remains.
- Set **connect** timeouts (short: 100s of ms) separately from **request** timeouts.

No timeout means waiting forever. Threads and connections pile up behind one slow dependency until your service dies
too.

## When to retry

| Retry | Don't retry |
|-------|-------------|
| Connection errors, timeouts on **idempotent** calls | Non-idempotent calls without an idempotency key |
| 503, 429 (honour `Retry-After`) | 400, 401, 403, 404, 422: the answer won't change |
| Deadlocks, serialisation failures | When the deadline has already passed |

## Backoff and jitter

```
sleep = random(0, min(cap, base × 2^attempt))      # "full jitter"
```

Without jitter, 10,000 clients that failed together retry together, every time.

## Retry storms

A dependency slows down, so callers time out and retry, so the dependency gets **more** load, so it slows further.
With 3 retries at each of 3 layers, one user request can become **3 × 3 × 3 = 27** calls to the bottom service.

```
user → A (3 tries) → B (3 tries each) → C (3 tries each)   = up to 27 calls to C
```

In the simulator, the timeline's "Clients retry" option adds 70% of failed requests back as new load each second.
Watch how it deepens and lengthens every incident.

Defences:
- **Retry at one layer only** (usually the outermost or the one that knows idempotency).
- **Retry budgets:** retries may add at most ~10% to normal traffic; beyond that, fail.
- **Circuit breakers** (12.3): stop calling a failing dependency.
- **Server-side load shedding:** reject quickly when overloaded, so clients don't wait for a timeout.

## Hedged requests

For read-only calls with long tails: if no answer arrives by the p95 time, send a **second** request to another
replica and use whichever answers first. It cuts tail latency for a few percent of extra load. Use it only for
idempotent reads.

## Try it

Service A (timeout 2 s, 3 retries) calls B (timeout 2 s, 3 retries), which calls C. C slows to 3 s per request. How
long does a user wait, and how many calls hit C per user request?

<details>
<summary>Answer</summary>

Every C call times out at B (2 s); B tries 3 times (6 s+), but A's 2 s timeout fires first and **A retries 3 times**,
each starting a new B with up to 3 C calls: up to **9 calls to C** per user request, and the user waits ~6 s (3 × A's
timeout) for a failure. Fix: one retry layer, inner timeouts shorter than outer ones (deadline propagation), retry
budgets and a circuit breaker on C.
</details>

## Key takeaways

- Every call needs a timeout derived from the dependency's latency and the caller's deadline.
- Retry only transient errors on idempotent operations, with exponential backoff and jitter.
- Retries multiply across layers: retry at one layer, use budgets and circuit breakers.
- Hedged requests can trim tail latency for idempotent reads.

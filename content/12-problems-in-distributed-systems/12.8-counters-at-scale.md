# Counters at scale

A celebrity posts; 80,000 likes arrive in a minute. Every one runs `UPDATE posts SET likes = likes + 1 WHERE id = 9001`.
They all queue on **one row lock**, and the database crawls, though it's only "counting".

## Why one counter is a hotspot

A single row (or a single Redis key) can be updated by one writer at a time. Lock contention, replication of every
increment, and a single cache node for that key all limit throughput, no matter how big the cluster is.

## Sharded counters

Split the counter into N sub-counters; writers pick one at random; readers sum them.

```
likes:9001:0 … likes:9001:15        (16 shards)
write: INCR likes:9001:{random 0-15}
read:  SUM of all 16  (cache the sum for a second or two)
```

- Writes spread across 16 rows or keys, so roughly 16x less contention.
- Reads cost N lookups, so cache the total briefly.
- Grow N only for hot items (most posts need one counter).

## Batch and flush

Count in memory or Redis, and write to the database periodically:

```
INCR in Redis per like  →  every 5 s a job does: UPDATE posts SET likes = likes + :delta
```

- The database sees one write per post per 5 s instead of thousands.
- You can lose a few seconds of counts if the cache dies (usually acceptable for likes and views).

## Count events, not totals

For counts that must be exact and auditable (votes, money), record each event with a unique id and **derive** the
count:

```
likes(post_id, user_id) PRIMARY KEY      -- also prevents double-liking
count = SELECT count(*) … (precomputed asynchronously into a summary)
```

## Approximate counts

When "about 1.2M views" is fine:
- **HyperLogLog** counts *unique* items (unique visitors) in ~12 KB with about 1% error (lesson 19.4);
- **Count-min sketch** estimates frequencies of many items in fixed memory (lesson 19.3).

## Displaying counts

Users don't need exact live numbers: "1.2M" is fine, and updating the displayed count every few seconds is fine. Exact
counts matter only where they're business-critical (inventory, balances), and those use transactional designs, not
counters.

## Try it

A video platform increments `videos.views` on every play: 30,000 plays/s at peak, mostly on 200 trending videos.
Design the view counter.

<details>
<summary>Answer</summary>

Increment in Redis, sharded across 8–32 sub-keys for trending videos. A job flushes deltas to the database every 10 s.
Display counts from a cached sum, refreshed every few seconds. For "unique viewers", use a HyperLogLog per video per
day. For anti-fraud or royalties, also stream play events into an analytics pipeline that computes exact, deduplicated
counts later.
</details>

## Key takeaways

- One hot counter row or key is a bottleneck no matter how big the cluster.
- Shard hot counters and sum on read; batch increments and flush periodically.
- Count events with unique ids when counts must be exact.
- Use approximate structures (HyperLogLog, count-min) when estimates are enough.

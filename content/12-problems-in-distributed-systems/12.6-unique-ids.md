# Unique IDs

One database can hand out `1, 2, 3, …`. A hundred servers creating orders at once, possibly across regions, need ids
that are unique **without asking a central counter** every time.

## The options

| Scheme | Size | Sortable by time? | Coordination | Notes |
|--------|------|-------------------|--------------|-------|
| Auto-increment | 8 B | ✅ | One database | Bottleneck and single point of failure; guessable |
| **UUID v4** (random) | 16 B | ❌ | None | Collision chance negligible; random inserts scatter B-tree indexes |
| **UUID v7** (time + random) | 16 B | ✅ | None | Modern default: unique anywhere, index-friendly |
| **ULID** | 16 B | ✅ | None | Similar idea, base32 string form |
| **Snowflake-style** | 8 B | ✅ | Worker ids assigned once | Compact, ordered, very fast |
| Ticket server / ranges | 8 B | ~ | Fetch a block of 1,000 ids occasionally | Simple; ids are dense |

## Snowflake layout (64 bits)

```
| 1 bit sign | 41 bits ms since custom epoch | 10 bits worker id | 12 bits sequence |
   0          ~69 years of milliseconds        1,024 workers       4,096 ids per ms per worker
```

- Each worker generates ids locally: timestamp, its worker id, and a per-millisecond counter.
- Ids are roughly time-ordered, which keeps B-tree inserts at the "right edge" of the index (efficient).
- **Worker ids** must be unique: assign them at deploy time or lease them from a coordination service.
- **Clock going backwards** (lesson 12.5) could repeat ids. Generators must detect it and wait, or refuse.

## Why ordering matters for databases

Random UUID v4 primary keys insert all over the index. Pages split and the cache churns, so write throughput suffers
on large tables. Time-ordered ids (UUID v7, Snowflake) append near the end, like auto-increment, without central
coordination.

## Exposing ids

- Sequential ids leak business data (order #10,482 → "they've had ~10k orders"), and invite enumeration
  (`/orders/10483`).
- For public URLs, use random or opaque ids, or encode internal ids (with a keyed hash) so they're not guessable.
- Never rely on an id being secret for security. Always check authorisation.

## Try it

You need ids for 50,000 events/s across 40 servers in 2 regions. Ids should sort by time, and fit in a 64-bit column.
Pick a scheme and say what must be coordinated.

<details>
<summary>Answer</summary>

**Snowflake-style** 64-bit ids. 40 servers fit easily in the 10-bit worker space (e.g. region bits + server bits).
4,096 ids per ms per worker far exceeds ~1,250 events/s per server. Coordinate only the **worker id assignment** (once
per deploy or lease), and guard against clock rollback.
</details>

## Key takeaways

- Central counters don't scale and are single points of failure.
- UUID v7 and Snowflake give unique, time-ordered ids without per-id coordination.
- Time-ordered ids keep database indexes efficient; random v4 scatters them.
- Don't expose guessable sequential ids publicly; never treat ids as secrets.

# Testing failure

Every redundancy and failover mechanism in this course has one thing in common: **it doesn't work until you've
seen it work.** Chaos engineering is the practice of breaking things on purpose, safely, to find out.

## The method

1. **Define steady state** with metrics users care about (success rate, p99, orders per minute).
2. **Form a hypothesis:** "If one API server dies, success stays above 99.9% and p99 below 300 ms."
3. **Inject a failure** in a controlled way.
4. **Observe:** did steady state hold?
5. **Fix** what broke, then **repeat** regularly, eventually automatically.

That's what you've been doing in the simulator's timeline: hypothesis (the lab constraints), failure injection (the
incident), observation (the chart and summary).

## Things to break

| Experiment | Tests |
|------------|-------|
| Kill an instance | Health checks, N+1 capacity, graceful restarts |
| Kill the DB primary | Failover time, app reconnects, idempotent retries |
| Add 300 ms latency to a dependency | Timeouts, circuit breakers, bulkheads |
| Drop 5% of packets | Retries, gray-failure detection |
| Fill a disk / exhaust memory | Alerts, eviction, crash recovery |
| Expire a certificate (in staging) | Monitoring of expiry, rotation |
| Take out a zone | Multi-AZ capacity and routing |
| Flush the cache | Stampede protection, DB headroom |
| Revoke a credential | Secret rotation runbook |

## Doing it safely

- Start in **staging**, then production with a **small blast radius** (one instance, one cell, 1% of traffic).
- Have an **abort switch** and clear stop conditions ("abort if the error rate is above 1%").
- Run during working hours with the owning team present.
- Communicate beforehand; announce afterwards what was learned.

## Game days

A scheduled team exercise: simulate a realistic incident (region failover, a major dependency down) and run the real
response: alerts, on-call, runbooks, communication. You'll find stale runbooks, missing permissions, dashboards nobody
can find, and alerts that never fired.

## Learning from incidents

After real incidents, write **blameless postmortems**: timeline, impact, root causes, what helped, what didn't, and
action items with owners. Turn each finding into a test (a chaos experiment, an alert, an automated check) so the
same failure can't surprise you twice.

## Key takeaways

- Failover and redundancy are unproven until tested.
- Chaos method: steady state → hypothesis → inject → observe → fix → repeat.
- Start small, with abort switches and stop conditions; run game days.
- Blameless postmortems turn incidents into tests.

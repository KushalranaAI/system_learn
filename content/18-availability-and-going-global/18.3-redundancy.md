# Redundancy

A **single point of failure (SPOF)** is any component whose failure takes the service down. Finding and removing
them, at the right level, is the core of availability engineering.

## Finding SPOFs

Walk every request path and ask "what if this dies?":

| Component | SPOF if… | Fix |
|-----------|----------|-----|
| Load balancer | One instance | Managed LB or an active-passive pair with a floating IP |
| API servers | One server, or N without health checks | N+1 behind an LB with health checks |
| Database | One primary, no replica | Replica + automatic failover (lesson 5.4) |
| Cache | One Redis, if the DB can't survive without it | Replicated Redis with failover, plus DB headroom |
| Queue/broker | Single node | Clustered broker with replication |
| DNS | One provider | Two DNS providers, or a highly available managed one |
| Config/secrets service | Needed at startup with no cache | Cache config locally; tolerate the service being down |
| A third-party API | Only one provider | A second provider, or graceful degradation |
| **People and process** | Only one person knows how to fail over | Runbooks, automation, drills |

## Levels of failure

| Failure domain | Example | Redundancy |
|----------------|---------|------------|
| Process | Crash, memory leak | Restart, multiple instances |
| Host | Hardware fault | Multiple hosts |
| Rack / switch | Top-of-rack switch dies | Spread across racks |
| **Availability zone** | A data centre loses power | **Multi-AZ**: the standard for production |
| **Region** | A region-wide outage, a bad control-plane change | Multi-region (lesson 18.4) |
| Provider | A global outage at one cloud | Multi-cloud (rarely worth it) |

Most production systems should be **multi-zone**: instances in at least 2–3 zones, a database with a synchronous or
semi-synchronous replica in another zone, and load balancers spanning zones.

## N+1 and N+2

Redundancy needs **spare capacity**, not just copies. If 4 servers are needed at peak:
- **N+1 = 5** servers: survive one failure at peak;
- per zone: with 3 zones, losing one zone loses a third of capacity, so plan for that (e.g. 6 servers, 2 per zone, each
  running ≤ 66% at peak).

## Correlated failures

Redundant copies often fail together:
- the **same deploy** pushed everywhere at once (the most common cause of big outages);
- the same expiring certificate, the same config change, the same leap-second bug;
- a shared dependency (one DNS, one auth service, one database behind "redundant" services).

Defences: **staged rollouts** (one zone or cell at a time), canaries, automatic rollback, and avoiding shared fate.

## Cells

Split the system into independent **cells**, each a full copy of the stack serving a subset of customers. A bad
deploy or a poison request affects one cell, not everyone. This "blast radius" reduction is how many very large
services reach very high availability.

## Try it

Your app runs 3 API servers in one zone, a Postgres primary with an async replica in the same zone, and a single Redis.
List the SPOFs and fixes, in priority order.

<details>
<summary>Answer</summary>

1. **The zone itself**: everything is in one zone. Spread servers across 3 zones and put the replica in another zone
   (semi-sync).
2. **The DB failover process**: make it automatic (Patroni or managed failover).
3. **Redis**: replicated with failover, and make sure the DB can survive a cold cache (lesson 3.6).
4. Check LB health checks and N+1 capacity per zone.
5. Staged deploys, so one bad release can't take out all servers at once.
</details>

## Key takeaways

- Walk every path and ask "what if this dies?", including people and processes.
- Make production multi-zone; add regions when the SLO or users require it.
- Redundancy needs spare capacity (N+1, per zone).
- Correlated failures (deploys, configs, shared dependencies) defeat naive redundancy; stage rollouts and use cells.

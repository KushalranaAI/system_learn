# Shopify: surviving flash sales

Shopify hosts millions of shops on one platform. Most of the year, load is spread across all of them. Then one
celebrity drops a product at 9:00 and a single shop gets more traffic than thousands of others combined, and on Black
Friday Cyber Monday (BFCM) **every** shop has its biggest day at once. Shopify's architecture is built to stop one
shop's spike from becoming everyone's outage.

## The problem at their scale

| Number | BFCM 2024 | BFCM 2025 |
|--------|-----------|-----------|
| Merchant sales over the weekend | $11.5 billion | $14.6 billion |
| Peak edge requests | 284 million/minute | 489 million/minute |
| Peak app-server requests | 80 million/minute | over 117 million/minute |
| Peak sales rate | $4.6 million/minute | $5.1 million/minute |
| Other | 10.5 trillion DB queries, 1.17 trillion DB writes, 12 TB/minute on Black Friday | 31.8 million API requests/minute at peak |

Flash sales have the opposite problem: load is concentrated, not spread out. Shopify's own example is Kylie
Cosmetics, which ran sales every week or so. In **February 2016** one of those sales overloaded the database shard it
lived on and took down other stores on that shard too.

## The architecture

```
 buyers ─► edge (Nginx/OpenResty + Lua) ─► Sorting Hat: shop → pod  ─► shared app servers (Rails)
             │  checkout throttle /               adds a header           │ each request talks to
             │  waiting room                                              │ ONE pod only
             ▼                                                            ▼
        cached storefront pages                ┌─────────── pod 1 ───────────┐  ┌──── pod 2 ────┐
                                               │ MySQL primary + replicas    │  │ ...           │
                                               │ Redis, Memcached, job queues│  │               │
                                               │ active in one region,       │  │               │
                                               │ standby copy in another     │  │               │
                                               └─────────────────────────────┘  └───────────────┘
```

## Key decisions and why

**1. Pods: cells of shops with isolated data stores.** By 2015 Shopify could no longer buy a bigger database server,
so it sharded. But code that touched all shards meant one bad shard could break a feature for every shop. In 2016 it
introduced **pods**: a set of shops on a fully isolated set of datastores (MySQL, Redis, Memcached). Stateless
resources (app servers, job workers, load balancers) are shared, but each request or job talks to **exactly one pod**.
An overloaded pod hurts only its own shops. A tool called Pod Mover can move a pod to its recovery data centre in
about a minute. This is cell-based architecture; see [lesson 18.3](#/lesson/18.3) and [lesson 9.4](#/lesson/9.4).

**2. Route at the edge.** Sorting Hat runs inside the load balancers, matches each request to its pod using a list of
rules, and adds a header. The application then connects only to that pod's datastores.

**3. A checkout throttle instead of a crash.** Checkout was the bottleneck: each session created a MySQL row and every
step updated it. The 2017 fix was a **leaky bucket** in the OpenResty edge tier that lets through a set number of
checkouts per period, based on measured capacity. Customers over the limit get a cached waiting page that polls, not a
429 error, because to shoppers an error looks like a broken store. See [lesson 8.2](#/lesson/8.2) and
[lesson 7.6](#/lesson/7.6).

**4. Rehearse BFCM all year.** For 2025, Shopify started capacity planning in March and ran five scale tests from
April to October with its load generator **Genghis**, across three cloud regions. Scale test 4 reached **146 million
requests/minute and over 80,000 checkouts/minute**, and the final test targeted 200 million requests/minute (about 150%
of the previous BFCM). Game days covered checkout, payments, order creation and fulfilment, with network faults
injected using Toxiproxy. See [lesson 18.6](#/lesson/18.6).

## What went wrong along the way

- **Shared shards (2016).** The Kylie sale took neighbours down with it. Isolation via pods was the answer.
- **The first throttle wasn't fair.** Waiting users polled at random intervals, so getting in was a lottery. Some
  buyers waited 40 minutes for a sale that lasted 40 minutes and missed out. Part II of the series added ordering
  based on when each buyer first tried to check out. Later, throttling moved from the edge into the Rails application
  tier, where it was easier to test and improve.
- **The 2025 tests broke things, as intended.** Early tests threw errors and backed up checkout queues. Test 4 hit
  limits that triggered an unplanned regional failover and showed routing-priority problems. Analytics pipelines
  needed more Kafka partitions, and connection timeouts exhausted pools. All of it was found months before the real
  weekend.

## Try it

A sneaker brand on your platform drops 20,000 pairs at 10:00. You expect 2 million people on the product page and
600,000 checkout attempts in the first minute. Their pod's database safely handles about 1,500 checkout completions per
second, and each checkout makes about 6 writes. Other shops share the pod. How do you keep checkout up for this shop
and its neighbours?

<details>
<summary>Reference</summary>

**Math:** 600,000 attempts in 60 s = **10,000/s**, about 7x what the pod can complete. Only 20,000 can succeed anyway.
At 1,500/s the stock sells out in about 13 s, so letting everyone in only produces errors.

**Plan:**
1. **Product page from cache/CDN.** 2M page views must not touch MySQL. Show stock as "available" or "sold out" from a
   cached counter updated every second.
2. **Checkout waiting room at the edge.** Admit about 1,000/s (leaving headroom for neighbours), ordered by first
   arrival time. Give admitted buyers a signed token. Everyone else waits on a cached page that polls.
3. **Stop admitting when stock is gone.** Track reserved units in a fast counter (for example Redis `DECR` with a
   floor of 0). When it hits 0, flip the waiting page to "sold out". This turns 580,000 doomed attempts into one
   cached page.
4. **Reserve inventory for a few minutes per admitted buyer**, and release on timeout, so payment failures don't
   strand stock ([lesson 16.3](#/lesson/16.3)).
5. **Protect neighbours:** per-shop limits inside the pod. If this shop's share passes its budget, shed its requests
   first. If needed, move the shop to its own pod before the drop.
6. **Bots:** require the token for checkout and rate-limit per account/card/IP ([lesson 8.3](#/lesson/8.3)).
</details>

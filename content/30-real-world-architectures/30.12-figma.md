# Figma: real-time multiplayer

In Figma, several people edit the same design file at once and see each other's cursors move live. Collaborative
editing is often presented as a research problem (operational transforms, CRDTs). Figma's published design is
deliberately simpler: **one server process per document decides the order of changes, and conflicts are resolved
per property, last writer wins.** Behind the multiplayer servers, a single Postgres instance grew into a sharded
fleet.

No sandbox scenario for this one. The [file sync interview scenario](#/sandbox?preset=iv-file-sync) covers related
ground.

## The problem at their scale

| Number | Value | When |
|--------|-------|------|
| Monthly active users | more than 13 million | Q1 2025 (S-1) |
| Database stack growth | almost 100x since 2020 | 2024 post |
| Database layout | one Postgres on AWS's largest instance | 2020 |
| Database layout | about a dozen vertically partitioned Postgres databases | end of 2022 |
| First horizontally sharded table | shipped | September 2023 |
| Multiplayer serialisation after Rust rewrite | over 10x faster | 2018 |

The design constraints: edits must appear instantly for the editor (no waiting on the server), converge to the same
document for everyone, survive going offline, and stay fast for files with many thousands of objects.

## The architecture

```
 browser A ─┐                              ┌── one process per document ─────────────────┐
 browser B ─┼── WebSocket ── multiplayer ──┤  holds the live document in memory           │
 browser C ─┘             service          │  Map<ObjectID, Map<Property, Value>>         │
                                           │  receives changes, orders them, rebroadcasts │
                                           │  checkpoints the file to storage             │
                                           └──────────────────────────────────────────────┘
 web API (files, teams, permissions, comments) ─► DBProxy (Go) ─► Postgres shards (by UserID, FileID, OrgID)
```

## Key decisions and why

**1. A central server, not peer-to-peer, and not OT.** Figma considered operational transforms (used by Google Docs)
too complex for a design tool, which edits a tree of objects rather than a run of text. Because a server is always in
the loop, it can **define the order of events**. That removes the hardest part of decentralised CRDTs. Figma
describes the result as inspired by CRDTs, without being one.

**2. Conflicts resolved per property.** A document is a tree of objects, each with an ID and a set of properties.
Two people changing **different** properties of the same shape (one the colour, one the width) never conflict. Two
people changing the **same** property: the last value the server receives wins. Values are atomic, so a text property
ends up as one person's version, never a mix. To avoid flicker, a client ignores server updates to a property it has
changed but not yet had acknowledged. See [lesson 13.7](#/lesson/13.7) for last-writer-wins and its alternatives.

**3. IDs and ordering without coordination.** Each client has a unique client ID that is built into the IDs of objects
it creates, so objects can be created offline with no collisions ([lesson 12.6](#/lesson/12.6)). Order among siblings
uses **fractional indexing**: a position is a fraction between 0 and 1, and inserting between 0.4 and 0.5 gives 0.45.
A move changes one property instead of renumbering every sibling. Parent and position are stored as one property, so a
move is atomic. The server rejects re-parenting that would create a cycle.

**4. Shard Postgres horizontally, behind a proxy.** By late 2022, vertical partitioning (one database per group of
tables) had run out: some tables were several terabytes with billions of rows, vacuums hurt reliability, and the
busiest tables neared RDS's IOPS limit. Figma looked at CockroachDB, TiDB, Spanner, Vitess and NoSQL, and chose to
shard its existing RDS Postgres itself because migrating to a new database was too risky on its timeline. Tables that
share a shard key are grouped into **colos** (shard keys: UserID, FileID, OrgID), so joins and transactions within one
key still work. **DBProxy**, a Go service, parses each query and routes it. Sharding was first done **logically**
(Postgres views per shard on the same machine, reversible by a config change), and only then **physically**. See
[lesson 9.3](#/lesson/9.3) and [lesson 14.5](#/lesson/14.5).

## What went wrong along the way

- **One slow document blocked others (2018).** The original multiplayer server was single-threaded TypeScript, with many
  documents per worker. Encoding one huge file stalled every document on that worker, and GC added latency spikes.
  Figma rewrote the hot path in Rust, with **one Rust process per document**, which was only affordable because Rust
  used so little memory. Serialisation got over 10x faster. This is bulkheading by document
  ([lesson 12.3](#/lesson/12.3)).
- **Running out of the biggest box.** In 2020 everything ran on one database on the largest instance available. By
  the end of 2022 it was a dozen vertical partitions plus caching and read replicas, and those too were near their
  limits. Each step bought time but not an end state.
- **Sharding costs features.** Figma's design gave up atomic cross-shard transactions, and schema changes must be
  coordinated across shards. The first physical shard failover caused about **10 seconds** of partial availability on
  primaries.

## Try it

Ana and Ben edit the same rectangle `R` while both online. At the same moment Ana sets `R.fill = red` and
`R.width = 200`, and Ben sets `R.fill = blue` and `R.height = 50`. The server receives Ana's message first. Then Ben
drags `R` into frame `F` while Ana drags `R` into frame `G`. What does everyone see in the end, and what does each
client show in the meantime?

<details>
<summary>Reference</summary>

**Properties:** `width = 200` (only Ana set it) and `height = 50` (only Ben set it) both apply, with no conflict.
`fill` is set by both. The server applied Ana's `red` first and Ben's `blue` second, so **blue wins** (last received).

**In the meantime:** Ana sees red immediately (local apply). When the server relays Ben's `blue`, Ana's client applies
it, because her own `red` has already been acknowledged, so everyone converges on blue. Ben sees blue throughout. If
Ana's red arrived at Ben's client while his blue was still unacknowledged, his client ignores it, so his screen doesn't
flicker red, then blue.

**Re-parenting:** `(parent, position)` is one property, so the same rule applies: whichever move the server receives
last wins, and `R` ends up wholly in `F` or wholly in `G`, never half in each. Each client shows its own move until
the server's decision arrives. If a move would create a cycle (dragging a frame into its own child), the server
rejects it, and the client reverts.

**Why this is acceptable:** the people editing can see each other's cursors. When two people really edit the same
property of the same object, LWW plus fast feedback is what users expect: they see the change and fix it.
</details>

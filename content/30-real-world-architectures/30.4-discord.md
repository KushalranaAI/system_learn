# Discord: trillions of messages

Discord stores every message ever sent, and people scroll back through years of history. Most of that history is cold
and rarely read, but a few channels are extremely hot: a giant community server during a launch, or a World Cup final.
Discord's storage history is a case study in **hot partitions**: one key getting far more traffic than the node that
owns it can serve.

## The data model

```
messages table
  partition key: (channel_id, bucket)      bucket = a fixed window of time
  clustering key: message_id DESC          message_id is a Snowflake: time-ordered

  channel 42, bucket 1901 ─► [msg 9, msg 8, msg 7 ...]    one partition, on 3 replicas
  channel 42, bucket 1902 ─► [msg 15, msg 14 ...]         next partition, maybe other nodes
```

"Show the latest 50 messages in this channel" is a single read from the newest bucket, already sorted. Time buckets
stop a busy channel's partition from growing forever. Snowflake IDs ([lesson 26.11](#/lesson/26.11)) sort by time,
with no coordination needed.

## The architecture

```
 clients ─► API monolith (Python) ─► data services (Rust, gRPC)  ─► ScyllaDB cluster
                                      routed by channel_id            (was Cassandra)
                                      (consistent hashing)
                                      ┌─────────────────────────┐
           1,000 users load #general  │ request coalescing:     │
           at the same moment ───────►│ 1st request queries DB, │──► 1 query
                                      │ others subscribe to it  │
                                      └─────────────────────────┘
```

## Key decisions and why

**1. Partition by channel and time.** It fits the access pattern: almost all reads are "recent messages in one
channel". The cost is that load follows popularity. A channel with a million members puts its whole current bucket
on three replicas. See [lesson 14.3](#/lesson/14.3).

**2. Put a data-service layer in front of the database.** In 2022 Discord added thin Rust services with roughly one
gRPC endpoint per query and no business logic. Their job is to protect the database:
- **Request coalescing.** If many users ask for the same rows at once, the first request starts the query, and the
  others wait for its result. A thousand identical reads become one. This is the same cure as for cache stampedes
  ([lesson 3.6](#/lesson/3.6)).
- **Consistent-hash routing by channel_id.** All requests for one channel reach the same data-service instance, so
  coalescing actually finds the duplicates ([lesson 14.2](#/lesson/14.2)).

**3. Swap Cassandra for ScyllaDB.** Both use the same data model and protocol, and both are LSM-tree stores
([lesson 26.8](#/lesson/26.8)). Cassandra runs on the JVM, and Discord fought garbage-collection pauses and compaction
backlogs. ScyllaDB is written in C++ with a shard-per-core design and no GC. Discord had moved its other databases to
ScyllaDB first, and messages last.

**4. Rewrite the migrator for speed.** The first Spark-based plan estimated three months. A rewrite in Rust, reusing
the data-service code, copied up to 3.2 million messages per second and finished in nine days.

## What went wrong along the way

- **Hot partitions spread.** Reads and writes used quorum consistency. When one hot partition slowed a node, every
  query that needed that node slowed too, so one busy channel caused latency for unrelated users.
- **Firefighting.** The team regularly did the "gossip dance": taking a node out of rotation so it could compact
  without serving traffic, then putting it back. GC pauses caused latency spikes, and the cluster needed constant care.
- **Tombstones.** The migration stalled at 99.9999% on token ranges full of uncompacted tombstones (delete markers).
  Compacting them let it finish. Deletes in LSM stores aren't free.
- **It held.** At the World Cup final in December 2022, message sends spiked nine times, once per goal and in the
  penalty shootout, and the new stack handled it without strain.

## Try it

A game studio's Discord server has 800,000 members. At a launch announcement, 200,000 clients open `#announcements`
within 10 seconds, and chat in `#general` jumps to 2,000 messages/s. Everything for each channel is in one
`(channel_id, bucket)` partition on 3 replicas, each of which handles about 5,000 reads/s. What breaks, and how do you
fix the hot partition without changing every other channel?

<details>
<summary>Reference</summary>

**What breaks:** 200,000 reads in 10 s = 20,000 reads/s on one partition. With quorum reads (2 of 3 replicas), each
read touches 2 nodes, so the 3 replicas see about 40,000 reads/s against about 15,000 capacity. The nodes saturate, and
every other partition on those nodes slows too.

**Fixes, cheapest first:**
1. **Coalesce:** route by `channel_id` to one data-service instance, and collapse identical "latest 50 messages"
   reads. During a burst most requests are the same query, so 20,000/s can become tens per second.
2. **Cache the head of hot channels** in the data service for a second or two. A 1-second-stale announcement is fine.
3. **Read with consistency ONE** for these history reads if your model allows it, which halves replica load.
4. **Writes in #general:** 2,000/s to one partition is a lot for an LSM write path, but it is append-only. Smaller
   buckets for very hot channels spread *older* data, but the current bucket stays hot. For extreme cases, slow mode
   (a product-level rate limit) is a legitimate fix ([lesson 8.1](#/lesson/8.1)).
</details>

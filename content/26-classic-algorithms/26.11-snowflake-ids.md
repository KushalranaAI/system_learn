# Snowflake IDs

Lesson 12.6 compared id schemes. Here's a complete Snowflake-style generator, how to decode an id, and the edge cases
real implementations handle.

## Layout (64 bits)

```
 0 | 41 bits: ms since epoch | 10 bits: worker | 12 bits: sequence
```

## A generator

```ts
const EPOCH = 1_735_689_600_000n;           // 2025-01-01T00:00:00Z, your custom epoch
class Snowflake {
  private lastMs = -1n; private seq = 0n;
  constructor(private worker: bigint) { if (worker < 0n || worker > 1023n) throw new Error("worker 0-1023"); }
  next(): bigint {
    let now = BigInt(Date.now());
    if (now < this.lastMs) throw new Error("clock moved backwards");   // or wait until lastMs
    if (now === this.lastMs) {
      this.seq = (this.seq + 1n) & 4095n;
      if (this.seq === 0n) while ((now = BigInt(Date.now())) <= this.lastMs) {} // 4,096 used: wait for next ms
    } else this.seq = 0n;
    this.lastMs = now;
    return ((now - EPOCH) << 22n) | (this.worker << 12n) | this.seq;
  }
}
```

## Decoding

```ts
function decode(id: bigint) {
  return {
    time: new Date(Number((id >> 22n) + EPOCH)),
    worker: Number((id >> 12n) & 1023n),
    seq: Number(id & 4095n),
  };
}
```

Handy when debugging: any id tells you when and where it was made.

## Edge cases

| Issue | Handling |
|-------|----------|
| **Clock moves backwards** (NTP step, VM migration) | Refuse, or wait until the clock passes `lastMs`. Never reuse old timestamps |
| **Sequence exhausted** (over 4,096 in 1 ms) | Spin until the next millisecond |
| **Worker id collisions** | Assign from deploy config, or lease from etcd/ZooKeeper/a DB table with expiry |
| **Epoch overflow** | 41 bits ≈ 69 years from your epoch; pick a recent epoch |
| **JavaScript numbers** | 64-bit ids exceed `Number.MAX_SAFE_INTEGER`, so send them to browsers **as strings** |

## Variations

- **Fewer worker bits, more sequence bits** if you have few, very busy generators.
- **Region bits** inside the worker field (e.g. 3 bits for region, 7 bits for the machine).
- **Sonyflake:** 10 ms ticks, more machines, a longer lifetime.
- **UUID v7:** the same "time first" idea in 128 bits with random bits instead of a worker id, so no coordination at all.

## Try it

Decode the id `0x1A2B3C4D5E6F7` (assume the epoch above): what are the worker and sequence?

<summary>Answer</summary>

`0x1A2B3C4D5E6F7` = 460,367,961,908,983 in decimal. Sequence = id & 4095 = **0x6F7 = 1,783**. Worker =
(id >> 12) & 1023 = (0x1A2B3C4D5E) & 0x3FF = **0x15E = 350**. Timestamp = id >> 22 = 109,760,275 ms ≈ 1.27 days after
the epoch.

## Key takeaways

- Snowflake = timestamp | worker | sequence, generated locally and time-ordered.
- Handle clock rollback, sequence exhaustion and unique worker ids.
- Decode ids for debugging; send them to JavaScript clients as strings.
- UUID v7 offers the same ordering without worker coordination, at 128 bits.

# Bloom filters

"Is this username taken?" "Has this user seen this article?" "Could this key exist in this file on disk?" A **Bloom
filter** answers set-membership questions in a tiny amount of memory, with one catch: it may say "maybe" when the
answer is "no", but **never** "no" when the answer is "yes".

## How it works

A bit array of `m` bits, all 0, and `k` hash functions.

```
add(x):    set bits h1(x), h2(x), …, hk(x) to 1
check(x):  if ALL of those bits are 1 → "probably in the set"
           if ANY is 0               → "definitely not in the set"
```

```
add("alice") → bits 3, 9, 14     add("bob") → bits 1, 9, 20
check("carol") → bits 3, 14, 20 → all 1 → false positive! (set by others)
check("dave")  → bits 2, 9, 14  → bit 2 is 0 → definitely not present
```

## Sizing

For `n` items and a target false-positive rate `p`:

```
m = −n · ln(p) / (ln 2)²        bits
k = (m / n) · ln 2              hash functions
```

| False-positive rate | Bits per item | Hashes |
|---------------------|---------------|--------|
| 10% | 4.8 | 3 |
| 1% | 9.6 | 7 |
| 0.1% | 14.4 | 10 |

**1 billion items at 1% ≈ 1.2 GB**, versus tens of GB to store the items themselves.

## Code

```ts
class Bloom {
  bits: Uint8Array;
  constructor(public m: number, public k: number) { this.bits = new Uint8Array(Math.ceil(m / 8)); }
  private idx(x: string, i: number) {                 // double hashing: h1 + i*h2
    const a = fnv(x), b = fnv(x + "#") || 1;
    return (a + i * b) % this.m;
  }
  add(x: string) { for (let i = 0; i < this.k; i++) { const j = this.idx(x, i); this.bits[j >> 3] |= 1 << (j & 7); } }
  has(x: string) {
    for (let i = 0; i < this.k; i++) { const j = this.idx(x, i); if (!(this.bits[j >> 3] & (1 << (j & 7)))) return false; }
    return true;
  }
}
function fnv(s: string) { let h = 2166136261; for (const c of s) h = Math.imul(h ^ c.charCodeAt(0), 16777619) >>> 0; return h; }
```

## Where they're used

- **LSM-tree databases** (Cassandra, RocksDB, LevelDB): one Bloom filter per on-disk file, so lookups skip files that
  can't contain the key. That saves most disk reads for missing keys (lesson 26.8).
- **CDNs and caches:** "only cache an object after its second request". A Bloom filter remembers the first requests
  cheaply.
- **"Have I seen this?":** crawlers' visited URLs, recommendation dedupe, malicious-URL checks in browsers.
- **Username availability:** a fast "definitely available" before checking the database.

## Limits

- No deletion (clearing a bit could remove other items). **Counting Bloom filters** or **cuckoo filters** support it.
- The false-positive rate rises as you add more than the planned `n`. Rebuild or use a scalable variant.
- It can't list its members.

## Try it

You must check 500M usernames for availability and accept a 0.1% false-positive rate. How much memory does the filter
need? What happens on a false positive?

<details>
<summary>Answer</summary>

14.4 bits × 500M ≈ 7.2 Gbit ≈ **900 MB**, with ~10 hash functions. A false positive says "maybe taken" for a free
name, so you check the database to confirm. A "definitely not" answer skips the database entirely, which is the
common case.
</details>

## Key takeaways

- Bloom filters answer "definitely not" or "probably yes" in very little memory.
- About 10 bits per item gives 1% false positives.
- LSM databases, CDNs and crawlers use them to skip expensive lookups.
- No deletes (use counting or cuckoo filters), and size them for the expected item count.

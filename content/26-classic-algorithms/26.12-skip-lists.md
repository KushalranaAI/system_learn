# Skip lists

Redis sorted sets (`ZADD`, `ZRANGE`, `ZRANK`) power leaderboards, priority queues, rate-limit logs and time-ordered
feeds. Underneath is a **skip list**: a sorted linked list with "express lanes" that make search O(log n), and it's far
simpler to implement than a balanced tree.

## The structure

```
level 3:  head ─────────────────────────────▶ 50 ───────────────▶ nil
level 2:  head ─────────▶ 20 ───────────────▶ 50 ─────▶ 70 ─────▶ nil
level 1:  head ──▶ 10 ──▶ 20 ──▶ 30 ──▶ 40 ──▶ 50 ──▶ 60 ──▶ 70 ──▶ nil
```

- Level 1 holds every element in order.
- Each element is promoted to the next level with probability ½ (Redis uses ¼): a coin flip on insert.
- Higher levels skip over more elements.

## Search

Start at the top level; move right while the next value is smaller than the target; otherwise drop down a level.

```
find 60: L3: 50 < 60 → go to 50; next is nil → drop
         L2: next 70 > 60 → drop
         L1: next 60 → found
```

The expected work is **O(log n)**, like a balanced tree, but with no rotations or rebalancing. Inserts just flip
coins for the new node's height and splice it into each level.

## Why Redis chose it

- Simple code; easy to reason about under concurrency.
- **Range queries** are natural: find the start, then walk level 1.
- **Rank queries** (`ZRANK`: "what position is this player?") work by storing a **span** (how many elements each
  express link skips) and summing spans along the search path.
- A sorted set pairs the skip list (ordered by score) with a **hash map** (member → score), so lookups by member are
  O(1).

## A leaderboard

```
ZADD lb 3120 "asha"      ZADD lb 2980 "ravi"      ZINCRBY lb 50 "ravi"
ZREVRANGE lb 0 9 WITHSCORES      → top 10
ZREVRANK lb "ravi"               → ravi's position
ZRANGEBYSCORE lb 2500 3000       → everyone in a score band
```

Everything here is O(log n) on millions of members, in memory.

## Scaling a leaderboard

- One sorted set per leaderboard fits easily up to tens of millions of members on one Redis node.
- For global leaderboards of hundreds of millions, shard by score range or region, keep per-shard top-K, and merge
  the tops (exact ranks for top players, approximate ranks for the long tail).
- Persist the scores in a database; Redis is the fast, rebuildable index.

## Try it

You need: the top 100 players, a given player's rank, and "players just above and below me" for 30M players, updated
5,000 times a second. Is a single Redis sorted set enough?

<details>
<summary>Answer</summary>

Yes, most likely: 30M members ≈ a few GB of memory, `ZINCRBY` is O(log n) at 5,000/s (well within one node's
capacity), and `ZREVRANGE 0 99`, `ZREVRANK` and `ZREVRANGE rank-5 rank+5` are all O(log n + k). Add a replica for
reads and failover, and persist scores to the database to rebuild after a loss.
</details>

## Key takeaways

- A skip list is a sorted linked list with random express lanes: O(log n) search, insert and delete.
- It's simpler than balanced trees, with natural range and rank queries (via spans).
- Redis sorted sets = skip list + hash map; ideal for leaderboards and time-ordered sets.
- Shard huge leaderboards; keep the source of truth in a database.

# HyperLogLog

"How many **unique** visitors did this page have today?" Storing every visitor id costs memory proportional to the
answer, so gigabytes for big sites. **HyperLogLog (HLL)** estimates distinct counts of billions in about **12 KB**,
with ~1% error.

## The intuition

Hash each item to a random-looking bit string. Look at how many **leading zeros** it has:

- 50% of hashes start with `1` (0 leading zeros);
- 25% start with `01`;
- 1 in 2ᵏ start with k zeros.

If the most leading zeros you've ever seen is 20, you've probably seen about 2²⁰ ≈ 1M distinct items. Duplicates hash
the same, so they **don't** change the answer. That's why it counts *distinct* items.

One observation is noisy, so HLL splits hashes into `m` **buckets** (using the first bits to pick a bucket), tracks the
max leading-zero count per bucket, and combines them with a harmonic mean plus bias corrections.

```
hash(x) = 0110 | 0001011…
          └ bucket 6      └ count leading zeros of the rest (3) → registers[6] = max(registers[6], 3+1)
estimate ≈ α · m² / Σ 2^(−register)
```

## Accuracy and memory

Standard error ≈ **1.04 / √m**.

| Buckets m | Memory (6-bit registers) | Error |
|-----------|--------------------------|-------|
| 1,024 | ~768 B | ~3.2% |
| 16,384 | ~12 KB | **~0.81%** |
| 65,536 | ~48 KB | ~0.4% |

Redis uses 16,384 registers: `PFADD visitors:2026-10-24 user42`, `PFCOUNT visitors:2026-10-24`.

## Mergeable

Merging two HLLs takes the **max of each register**, so the union of sets comes free:
- per-day sketches merge into weekly uniques;
- per-server sketches merge into global uniques;
- `PFMERGE` in Redis.

Intersections aren't directly supported (you can estimate them via inclusion–exclusion, with poor accuracy for small
overlaps).

## Uses

- Unique visitors, unique searchers, distinct IPs.
- `COUNT(DISTINCT …)` approximations in analytics engines (BigQuery `APPROX_COUNT_DISTINCT`, Presto/Trino, Druid).
- Cardinality estimates in query planners and stream processors (lesson 17.6).

## Try it

You need daily unique viewers for 2 million videos. Compare the memory for exact sets (assume 1,000 viewers per
video on average, 8-byte ids) with one 12 KB HLL per video.

<details>
<summary>Answer</summary>

Exact: 2M × 1,000 × 8 B = **16 GB** per day (plus set overhead, so realistically 2–3x more). HLL: 2M × 12 KB =
**24 GB**. That's *worse* here, because most videos have few viewers! Use **sparse HLL** encodings (Redis does this
automatically for small counts, using just bytes), or exact sets for small videos and dense HLLs only for popular
ones. HLL shines when per-key cardinalities are large.
</details>

## Key takeaways

- HyperLogLog estimates distinct counts in ~12 KB with ~0.8% error.
- It relies on leading zeros of hashes across many buckets; duplicates don't affect it.
- Sketches merge (max per register) for unions across time and servers.
- For many small sets, use sparse encodings; HLL shines at high cardinality.

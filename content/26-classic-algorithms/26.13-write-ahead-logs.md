# Write-ahead logs

Almost every durable system (Postgres, MySQL, SQLite, Kafka, etcd, Redis AOF, file systems) rests on one rule:
**write down what you're going to do, durably, before doing it.** That record is the write-ahead log (WAL).

## Why

Updating data files in place is slow (random I/O) and dangerous: a crash halfway through a page write leaves a torn,
corrupt page. Appending to a log is fast (sequential I/O) and easy to make atomic.

```
transaction commits:
  1. append "tx 81: set row 42 balance=900" to the WAL
  2. fsync the WAL                          ← now durable: the commit can be acknowledged
  3. update the page in memory (dirty page)
  4. later, a checkpoint writes dirty pages to the data files
```

## Crash recovery

After a crash, data files may be missing recent changes, but the WAL has them:

```
1. find the last checkpoint
2. REDO: replay WAL records after it, reapplying committed changes to the pages
3. (UNDO: roll back transactions that hadn't committed; ARIES-style engines)
```

Records carry a **log sequence number (LSN)**; each page remembers the LSN of its last change, so replay is
idempotent: skip records the page already has.

## fsync and group commit

`fsync` forces data to stable storage, and it's slow (~0.1–10 ms). **Group commit** batches many concurrent
transactions into one fsync, so throughput stays high while every commit is still durable.

Durability knobs trade safety for speed:

| Setting | Effect |
|---------|--------|
| fsync every commit (default) | No committed data lost on crash |
| Async commit (`synchronous_commit=off` in Postgres) | Faster; may lose the last few hundred ms of commits on crash (no corruption) |
| Redis `appendfsync everysec` | Lose up to ~1 s of writes on crash |

## The log is everything

Once you have an ordered log of every change, many features follow naturally:

| Feature | Built on the log |
|---------|------------------|
| **Replication** (lesson 13.2) | Ship WAL to followers; they replay it |
| **Point-in-time recovery** (lesson 5.5) | Snapshot + replay archived WAL up to a moment |
| **Change data capture** (lesson 17.3) | Read the WAL and emit change events |
| **Consensus** (lesson 26.7) | Raft *is* a replicated log |
| **Kafka** (Module 15) | The log is the product |
| **Event sourcing** (lesson 17.1) | An application-level log as the source of truth |

That's the closing thought for this course: **the log is the backbone of distributed systems.** Databases, queues,
streams and consensus are different views of the same idea: an ordered, durable, replayable sequence of changes.

## Try it

A service writes a record and returns 200 as soon as the write is in the OS page cache (no fsync). The machine loses
power. What's lost, and how would you get durability without making every request wait 5 ms for its own fsync?

<details>
<summary>Answer</summary>

Anything not yet flushed from the page cache (possibly seconds of acknowledged writes) is lost. Fix: append to a WAL
and fsync before acknowledging, using **group commit** (one fsync covers all requests that arrived in the last few
milliseconds), so latency rises slightly while throughput stays high. Or replicate to another machine before
acknowledging (a quorum), trading fsync for a network round trip.
</details>

## Key takeaways

- Log the change durably first, then apply it: fast sequential writes and crash safety.
- Recovery replays the WAL from the last checkpoint; LSNs make replay idempotent.
- Group commit keeps per-commit fsync affordable; async commit trades durability for speed.
- Replication, PITR, CDC, consensus and Kafka are all built on logs.

# Make the DB do less

Before adding hardware, remove work. The cheapest query is the one you don't run; the next cheapest is the one that
touches fewer rows.

## Kill N+1 queries

```python
posts = db.query("SELECT * FROM posts ORDER BY created_at DESC LIMIT 20")
for p in posts:
    p.author = db.query("SELECT * FROM users WHERE id = %s", p.author_id)   # 20 more queries!
```

That's 21 round trips per page. Fetch in one go:

```sql
SELECT p.*, u.name AS author_name
FROM posts p JOIN users u ON u.id = p.author_id
ORDER BY p.created_at DESC LIMIT 20;
-- or: SELECT * FROM users WHERE id = ANY($1)  with the 20 ids
```

ORMs hide N+1 easily. Turn on query logging in development, and count the queries per request.

## Select less

- `SELECT *` drags every column, including large text and JSON blobs, across the network. Select what you need.
- Paginate (lesson 2.3). Never "load all, filter in code".
- Push filtering and aggregation into SQL instead of fetching rows to count them in the app.

## Precompute expensive reads

| Technique | Example | Cost |
|-----------|---------|------|
| **Counter columns** | `posts.comment_count`, updated on insert | Extra write per comment; hot-row risk on viral posts |
| **Denormalised fields** | `orders.customer_name` copied at order time | Must decide what happens when the source changes |
| **Materialised views** | Daily sales by region, refreshed every 10 min | Staleness; refresh cost |
| **Summary tables** | `user_stats(user_id, posts, followers)` updated by a job | A background job to maintain |

## Batch writes

```sql
-- 1,000 round trips
INSERT INTO events VALUES (...);  -- ×1000

-- 1 round trip
INSERT INTO events VALUES (...), (...), ... ;  -- or COPY
```

Batching cuts round trips, transaction overhead and log flushes. Queues (Module 7) make batching natural.

## Move work off the hot path

- Analytics and reporting → a **replica** or a **data warehouse**, not the primary.
- Full-text search → a search engine fed from the database.
- Slow, non-urgent work (emails, thumbnails, recalculations) → a queue.

## Keep transactions short

Long transactions hold locks and stop vacuum from cleaning up old row versions (which bloats tables). Never call an
external API, or wait for a user, inside a database transaction.

## Try it

A profile page runs: 1 query for the user, 1 for their 30 most recent posts, then 1 per post for its like count and 1
per post for its comment count. How many queries is that, and how would you get it to 2?

<details>
<summary>Answer</summary>

1 + 1 + 30 + 30 = **62 queries**. Get it to 2: the user query, plus one posts query that includes counts, either via
`comment_count`/`like_count` counter columns, or with
`LEFT JOIN (SELECT post_id, count(*) ... GROUP BY post_id)` for the 30 post ids.
</details>

## Key takeaways

- Eliminate N+1 queries; count queries per request.
- Fetch only needed columns and rows; aggregate in SQL.
- Precompute expensive reads with counters, materialised views and summary tables.
- Batch writes, move analytics off the primary, and keep transactions short.

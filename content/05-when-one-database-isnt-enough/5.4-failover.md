# Failover

The primary database dies at 3 am. Reads can keep going from replicas, but **every write fails** until something
takes over. Failover is the process of promoting a replica to be the new primary.

## The steps

1. **Detect** that the primary is gone: missed heartbeats for N seconds.
2. **Choose** a replica: the one with the most recent data (the least lag).
3. **Promote** it: it starts accepting writes.
4. **Redirect** clients: update DNS, a virtual IP or a proxy so apps connect to the new primary.
5. **Fence** the old primary: make sure it can never accept writes again if it comes back.

Typical automatic failover (Patroni, managed cloud databases): **15–60 seconds**. In the simulator it's 15 s, and you
can watch writes fail for exactly that window.

## What can go wrong

### Lost writes
With async replication, writes the dead primary acknowledged but hadn't shipped yet are **gone**. Fewer losses need
synchronous or quorum replication: you trade write latency for durability.

```
RPO (recovery point objective) = how much data you may lose
async ≈ seconds of writes   ·   sync ≈ zero
```

### Split brain
The primary was merely unreachable (a network partition), not dead. A replica gets promoted, and now **two primaries**
accept writes. The data diverges, and merging it is painful or impossible.

Defences:
- **Fencing**: power off or revoke the old primary before promoting (STONITH, "shoot the other node in the head").
- **Quorum-based decisions**: a promotion needs a majority of a 3+ member cluster (etcd, Consul, Raft) to agree, so an
  isolated minority can't promote itself.
- **Leases**: a primary may only accept writes while holding a short, renewable lease.

### Flapping
Too-sensitive detection fails over on a brief blip, then fails back. Every failover drops connections and risks data.
Tune detection to tolerate short hiccups.

## Application side

- Reconnect automatically and **retry idempotent operations** (lesson 2.3) after connection errors.
- Use a single endpoint (DNS name or proxy) that always points at the current primary.
- Keep DNS TTLs low (≤ 30 s) if DNS is used for failover.

## Key takeaways

- Failover = detect, choose, promote, redirect, fence; it usually takes 15–60 s.
- Async replication can lose recent writes on failover; sync trades latency for safety.
- Split brain is the big danger: use fencing, quorums and leases.
- Apps must reconnect and retry idempotently.

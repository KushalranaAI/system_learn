# Lab: a growing blog platform

A blogging platform's readership exploded: **40,000 reads a second** and **800 writes** (posts, comments, likes). The
API servers are fine. One database is not.

> **Interactive version:** [open the Blog platform lab](#/labs/blog-platform).

## Step 1: Where's the bottleneck?

<details>
<summary>Reference</summary>

A 16 vCPU primary handles ~45,000 reads/s; at 40,000 reads plus 800 writes it's ~96% busy, so the p99 explodes. It's
read-heavy (98% reads), so read replicas are the right tool (along with caching from Module 3).
</details>

## Step 2: Add replicas

<details>
<summary>Reference</summary>

Three 8 vCPU databases (1 primary + 2 replicas), with every API server wired to all three. Reads spread across them
(~13,000 each); writes go to the primary and are replayed on each replica. That's cheaper than one giant machine,
with room to grow.

Watch out for **replication lag**: after publishing a post, the author's own reads should go to the primary for a few
seconds (read-your-writes).
</details>

## Step 3: The primary dies

<details>
<summary>Reference</summary>

Turn on automatic failover. Writes fail for the ~15 s it takes to detect the failure and promote a replica, then the
system recovers on its own. Reads keep working throughout, because replicas serve them. Make sure the app retries
writes idempotently.
</details>

## Reflect

- What would you do if writes, not reads, grew 10x?
- Which requests should always read from the primary?

# Connection pooling

You scale from 4 API servers to 40. Each opens a pool of 50 database connections. Postgres now has **2,000
connections**, and falls over, even though it was handling the queries fine before.

## Why connections are expensive

- **Opening one** costs a TCP + TLS handshake plus authentication: several milliseconds.
- **Each open connection** costs memory on the database: in Postgres, each one is a separate process, often around
  10 MB once it's done real work.
- **Too many active connections** fight over CPU, locks and cache. Throughput *drops* past a certain point.

A database does its best work with roughly **a few connections per CPU core** actively running queries, not thousands.

## Pools

An application-side pool keeps a fixed number of connections open and lends them to requests:

```
request → borrow connection → run query → return connection
```

- No handshake per request.
- A hard cap on how much the app can hit the database.
- When all connections are busy, requests **wait** (with a timeout) instead of overwhelming the database.

## The multiplication problem

```
total connections = servers × processes per server × pool size
                  = 40 × 4 × 25 = 4,000
```

Autoscaling makes this worse: more servers mean more connections, at exactly the moment the database is busiest.

## A central pooler

Put a proxy such as **PgBouncer** (or RDS Proxy, or pgcat) between apps and the database:

```
40 servers × 100 client connections ─▶ PgBouncer ─▶ 100 real connections ─▶ Postgres
```

In **transaction pooling** mode, a real connection is assigned only for the duration of a transaction, so thousands of
mostly idle app connections share a hundred real ones.

Caveat: transaction pooling breaks session-level features (session `SET`, advisory locks held across transactions,
some prepared-statement setups). Know which ones your code relies on.

## Sizing

A starting point that works surprisingly often:

```
active connections ≈ (CPU cores × 2) + number of disks
```

For a 16-core database, that's tens of connections, not thousands. Measure: increase the pool until throughput stops
improving, then stop.

## Try it

Each of 30 API pods uses a pool of 20. The database has 8 cores and `max_connections = 500`. During autoscaling to 60
pods, errors spike with "too many clients". Give two fixes.

<details>
<summary>Answer</summary>

60 × 20 = 1,200 connections > 500. Fixes: (1) put PgBouncer in transaction mode in front, with ~40–60 real
connections to the database; (2) shrink per-pod pools (e.g. 5) so the total stays bounded as pods scale. Also cap the
autoscaler's maximum pod count, knowing the database is the real limit.
</details>

## Key takeaways

- Connections are costly to open and to hold; databases want few, busy ones.
- Pools reuse connections and cap the load the app can put on the database.
- Connections multiply with servers; a central pooler keeps the total bounded.
- Size pools by measurement, starting around 2 × cores.

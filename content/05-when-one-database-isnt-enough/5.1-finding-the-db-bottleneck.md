# Finding the DB bottleneck

The API servers scale out easily. Then every one of them talks to the same database, and it becomes the bottleneck.
Before buying hardware, find out **which resource** is exhausted. The fix depends on it.

## The four resources

| Resource | Symptoms | Common causes | First fixes |
|----------|----------|---------------|-------------|
| **CPU** | CPU near 100%, all queries slower | Missing indexes, expensive queries, too many queries | Indexes, query tuning, caching, read replicas |
| **Disk I/O** | High I/O wait, slow scans | Working set bigger than RAM, big scans, heavy writes | More RAM, indexes, faster disks, archiving |
| **Locks** | Queries waiting, low CPU, timeouts in bursts | Long transactions, hot rows (one counter), table locks from migrations | Shorter transactions, avoid hot rows, online migrations |
| **Connections** | "too many connections", stalls under load | Every server opening its own big pool | Connection pooling (lesson 5.2) |

## Where to look (Postgres examples)

```sql
-- Which queries cost the most total time?
SELECT query, calls, total_exec_time, mean_exec_time
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

-- What's running or waiting right now?
SELECT pid, state, wait_event_type, wait_event, now() - query_start AS running, query
FROM pg_stat_activity WHERE state <> 'idle' ORDER BY running DESC;

-- Is the working set in memory? (want > 99%)
SELECT sum(blks_hit) * 100.0 / nullif(sum(blks_hit) + sum(blks_read), 0) AS cache_hit_pct
FROM pg_stat_database;
```

The top of `pg_stat_statements` usually tells the story: **one or two queries account for most of the load.** Fixing
them beats any hardware change.

## Reads or writes?

Measure the split. It decides the strategy for the rest of this module.

| Workload | Main tools |
|----------|------------|
| **Read-heavy** (90%+ reads) | Caching (Module 3), read replicas (5.3), query tuning |
| **Write-heavy** | Batch writes, queues (Module 7), fewer indexes, a bigger primary, and eventually partitioning (Module 9) |
| **Both** | All of the above, starting with the cheapest |

Replicas add **read** capacity only. Every replica still has to apply every write.

## The cheapest fixes first

1. Fix the top 3 queries (indexes, rewriting, removing N+1 query patterns).
2. Cache hot reads.
3. Pool connections.
4. Scale the primary up.
5. Add read replicas.
6. Move slow or bursty writes behind a queue.
7. Partition or shard (Module 9). That's the expensive, last step.

## Try it

A dashboard shows Postgres CPU at 35%, but API requests time out in bursts every few minutes, and
`pg_stat_activity` shows many queries waiting on `Lock`. What's the likely cause and fix?

<details>
<summary>Answer</summary>

CPU is fine, so this isn't a capacity problem but **lock contention**. Likely culprits: a long transaction (a batch
job or a migration) holding locks; or many requests updating the same hot row (a global counter). Fix: find the
blocker with `pg_locks` / `pg_blocking_pids()`, shorten transactions, batch the job in small chunks, and replace
hot-row counters with sharded counters or async aggregation.
</details>

## Key takeaways

- Identify the exhausted resource: CPU, I/O, locks or connections. Each has different fixes.
- A few queries usually cause most of the load; `pg_stat_statements` finds them.
- Know your read/write split: replicas help reads only.
- Apply the cheapest fixes first; sharding is last.

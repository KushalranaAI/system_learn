# Read replicas

Most apps read far more than they write. A **read replica** is a copy of the database that continuously applies the
primary's changes and serves reads. Add replicas and read capacity grows, but writes still go to one place.

```
              writes ─▶ Primary ──replication stream──▶ Replica 1
API servers ─┤                    └───────────────────▶ Replica 2
              reads  ─▶ (any of them)
```

## How replication works

The primary writes every change to its log (the **WAL** in Postgres, the **binlog** in MySQL). Replicas stream that
log and replay it.

| Mode | The primary waits for… | Effect |
|------|------------------------|--------|
| **Asynchronous** (default) | Nothing | Fast writes; replicas lag a little; recent writes may be lost if the primary dies |
| **Synchronous** | At least one replica to confirm | No data loss on failover; every write pays a round trip; a slow replica slows writes |
| **Semi-sync / quorum** | Some replicas | A middle ground |

## Replication lag

With async replication, replicas are **behind** by milliseconds normally, and by seconds or minutes under heavy
writes, long queries on the replica, or network trouble.

The classic bug:

```
1. User saves a new post        → primary
2. Page reloads, lists posts    → replica (20 ms behind)
3. "Where's my post?!"
```

Lag also grows with **write load**: replicas must apply every write the primary takes. In the simulator, lag climbs as
the primary's write utilisation rises.

## Living with lag

| Technique | How |
|-----------|-----|
| **Read-your-writes** | After a user writes, send *their* reads to the primary for a few seconds (track "last write at" in the session) |
| **Monotonic reads** | Pin a user to one replica so they never see time go backwards |
| **Route by freshness need** | Checkout and settings → primary; feeds and search → replicas |
| **Wait for position** | Read from a replica only once it has replayed past the write's log position (LSN) |
| **Monitor lag** | Alert when lag exceeds a threshold; pull lagging replicas out of rotation |

## What replicas don't fix

- **Write capacity.** Every replica applies every write. If the primary is write-bound, replicas are just as busy
  replaying.
- **Storage size.** Each replica holds the full dataset.
- **A slow query.** It's slow on a replica too. Fix the query.

## Try it

In the [Cache + replicas preset](#/sandbox?preset=cached), raise writes from 300 to 3,000 per second. Watch the
"Replica lag" metric and the replica's utilisation. Why does the replica get busier even though it takes no writes
from the app?

<details>
<summary>Answer</summary>

The replica must replay every write the primary commits. More writes mean more replay work (higher utilisation) and
more lag, which is why replicas add read capacity but not write capacity.
</details>

## Key takeaways

- Replicas copy the primary's log and serve reads; writes still go to the primary.
- Async replication means lag: reads may be stale.
- Use read-your-writes and route fresh-critical reads to the primary.
- Replicas don't add write capacity or storage, and don't fix slow queries.

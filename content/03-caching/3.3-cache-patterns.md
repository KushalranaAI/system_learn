# Cache patterns

*Who* puts data in the cache, and *when* the database is written, defines the pattern. Each one trades freshness,
latency and complexity differently.

## Cache-aside (lazy loading): the default

The application manages the cache itself.

```python
def get_product(id):
    p = redis.get(f"product:{id}")
    if p is not None:
        return p                          # hit
    p = db.query("SELECT ... WHERE id = %s", id)
    redis.set(f"product:{id}", p, ex=300) # fill on miss, 5-minute TTL
    return p

def update_product(id, fields):
    db.update(id, fields)
    redis.delete(f"product:{id}")         # invalidate; next read refills
```

- ✅ Only requested data gets cached.
- ✅ If Redis dies, reads fall back to the database (slower, but working).
- ❌ The first read of each key is a miss.
- ❌ A race can leave stale data (lesson 3.5).

## Read-through

The cache library sits in front of the database and loads misses itself. The app only talks to the cache. It behaves
like cache-aside, but the logic lives in one place (common with in-process caches like Caffeine, or a DAX-style
layer).

## Write-through

Every write goes to the cache **and** the database before returning.

```
write(x) → DB ✓ → cache ✓ → "saved"
```

- ✅ The cache is warm and fresh for written keys.
- ❌ Writes get slower (two systems).
- ❌ You cache data that may never be read.

It's often combined with cache-aside: write-through on create, so the creator's next read is a hit.

## Write-behind (write-back)

Writes go to the cache, are acknowledged, and are flushed to the database later in batches.

- ✅ Very fast writes; absorbs write bursts (counters, likes, view counts).
- ❌ **If the cache dies before the flush, the writes are lost.**
- ❌ The database is behind; other readers of it see old data.

Use it only for data you can afford to lose a little of, or with a durable log in front.

## Refresh-ahead

Popular keys are refreshed in the background **before** their TTL expires, so users never hit the miss. It's good for
a small set of very hot keys (a home page, top products).

## Comparison

| Pattern | Read latency | Write latency | Freshness | Risk |
|---------|--------------|---------------|-----------|------|
| Cache-aside | Miss on first read | Normal | TTL / invalidation | Stale races |
| Read-through | Same | Normal | Same | Same |
| Write-through | Warm | Slower | Fresh | Extra work |
| Write-behind | Warm | Fastest | DB lags | **Data loss** |
| Refresh-ahead | Always warm (hot keys) | Normal | Fresh-ish | Wasted refreshes |

## Try it

Pick a pattern for:
1. Product catalogue pages
2. A "views" counter on every video
3. A user's profile, edited rarely, viewed right after editing

<details>
<summary>Answer</summary>

1. **Cache-aside** with a TTL and delete-on-update.
2. **Write-behind**: `INCR` in Redis and flush every few seconds. Losing a few views is fine.
3. **Cache-aside + write-through on update**: write the new profile to the cache on save so the user sees it
   immediately.
</details>

## Key takeaways

- Cache-aside is the default: simple, and it degrades gracefully when the cache fails.
- Write-through keeps written keys fresh at the cost of slower writes.
- Write-behind gives the fastest writes, but can lose data.
- Mix patterns per data type.

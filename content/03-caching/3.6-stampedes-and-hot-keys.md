# Stampedes and hot keys

Caches don't only fail by being wrong. They fail by being **empty at the wrong moment** or by having **one key that
everyone wants**.

## The cache stampede (thundering herd)

The home page is cached with a 60 s TTL and read 10,000 times a second. At second 60 it expires:

```
t=60.000  key expires
t=60.001  request 1: miss → query DB (takes 200 ms)
t=60.002  request 2: miss → query DB
...
t=60.200  2,000 identical queries hit the database at once
```

The database slows down, each query takes longer, more requests miss in the meantime, and it can spiral into an
outage. The same happens on a larger scale when **the whole cache restarts empty** (a cold cache). Try it in the
[sandbox](#/sandbox?preset=cached) with the "Cache restart" incident.

## Defences

| Technique | How it helps |
|-----------|--------------|
| **Request coalescing** (single flight) | Only the first miss for a key queries the DB; the others wait for its result |
| **Lock / lease on miss** | `SET lock:key NX EX 5`: the winner refills, the others serve stale data or wait briefly |
| **Stale-while-revalidate** | Keep serving the expired value while one request refreshes it in the background |
| **TTL jitter** | Keys cached together expire at different times |
| **Refresh-ahead** | Refresh hot keys before they expire |
| **Warm the cache before traffic** | After a restart or deploy, preload the hottest keys |
| **Database headroom** | The DB must survive the miss rate during warm-up; replicas help |

Coalescing in pseudo-code:

```python
inflight = {}   # key → future

def get(key):
    v = cache.get(key)
    if v: return v
    if key in inflight:
        return inflight[key].wait()      # piggy-back on the first request
    inflight[key] = future = Future()
    try:
        v = db.load(key); cache.set(key, v, ex=ttl_with_jitter())
        future.set(v); return v
    finally:
        del inflight[key]
```

## Hot keys

A celebrity posts. One key, `post:9001`, gets 200,000 reads a second. A Redis node handles ~100,000 ops/s, and that
key lives on **one** node, so the node melts while the rest of the cluster idles.

| Fix | How |
|-----|-----|
| **Local (in-process) cache for hot keys** | Each API server keeps `post:9001` in memory for 1–5 s, so Redis sees one read per server per few seconds |
| **Key replication** | Store copies `post:9001#1` … `#8` on different nodes; readers pick one at random |
| **Read replicas for the cache** | Spread reads of that node across replicas |
| **Detect hot keys** | Sample access counts (Redis `--hotkeys`, client-side counters) and promote them automatically |

## Try it

A flash sale starts at 12:00:00. The sale page is cached with a TTL of exactly 300 s, set at 11:55:00 by a warm-up
script, along with 5,000 product keys. What happens at 12:00:00, and how would you change the warm-up?

<details>
<summary>Answer</summary>

Every key warmed at 11:55:00 expires at **12:00:00**, exactly when traffic peaks. That's a stampede on 5,000 keys at
once. Fixes: add TTL jitter (e.g. 300–420 s), use stale-while-revalidate or coalescing so expiry never sends a herd
to the DB, and refresh-ahead the sale page itself.
</details>

## Key takeaways

- A stampede is many simultaneous misses for the same data; a cold cache is a stampede on everything.
- Coalesce misses, add TTL jitter, serve stale while revalidating, and warm caches before traffic.
- A hot key overloads one cache node; local caching and key replication spread it out.
- Size the database to survive cache warm-up.

# Stale data and invalidation

A seller changes a price from ₹999 to ₹799. Ten minutes later, customers still see ₹999. Somewhere a cache didn't
hear about the change. This lesson is about making sure it does, and about the races that break it anyway.

## Update or delete on write?

```python
# Option A: update the cache
db.update(product)
redis.set(key, product)

# Option B: delete the cache entry (preferred)
db.update(product)
redis.delete(key)        # next read refills from the DB
```

**Prefer delete.** With two concurrent writers, Option A can leave the *older* value in the cache:

```
Writer 1: db.update(price=799)
Writer 2: db.update(price=699)
Writer 2: redis.set(699)
Writer 1: redis.set(799)     ← cache now says 799, DB says 699. Wrong until TTL.
```

Deleting is idempotent and order-independent: whoever deletes last, the next read loads the truth.

## The read-write race (even with delete)

```
Reader: cache miss → reads OLD value from DB
Writer: updates DB → deletes cache key
Reader: writes OLD value into the cache      ← stale until TTL
```

It's rare (the reader must be slow at exactly the wrong moment) but real at scale. Defences:
- **TTL as a safety net**: stale data heals within the TTL.
- **Delayed double delete**: delete, then delete again ~1 s later.
- **Versioned values**: store `(version, data)` and only overwrite with a higher version (`SET` only if newer, via a
  Lua script).
- **Invalidate from the database's change stream** (CDC, Module 17): a single process sees every committed change in
  order and deletes keys.

## Invalidating many keys

One product change may affect `product:42`, `category:shoes:page:1`, `search:...`, the home page…

| Technique | How |
|-----------|-----|
| **Tagging** | Track which keys belong to `product:42`; delete them together |
| **Version in the key** | `catalog:v17:...`. Bump to `v18` and old keys simply stop being used (and expire) |
| **Short TTLs on aggregates** | Lists and pages refresh every 30–60 s; only the item is invalidated precisely |

Usually: invalidate the **item** precisely, and let **lists and pages** expire on short TTLs.

## How stale is acceptable?

Ask per field, not per system.

| Field | Acceptable staleness |
|-------|----------------------|
| Product description | Minutes |
| Review count | Minutes |
| Price shown in the listing | Seconds to a minute |
| Price charged at checkout | **None**: read from the DB inside the order transaction |
| Stock "only 3 left" | Seconds; the final check happens at purchase |

This is the most practical rule in caching: **cache for display, verify at the moment of truth.**

## Try it

A user edits their display name and refreshes. The old name shows for five minutes. The code is cache-aside:
`db.update` followed by `redis.set(key, new_profile)`. Two edits sometimes happen quickly from two tabs. What's
wrong, and how do you fix it?

<details>
<summary>Answer</summary>

Two problems. First, `set`-on-write can store an older value when two writes race; switch to `delete` after the DB
update. Second, if the old name still appears, something else caches it (a CDN or page cache) or the delete failed.
Keep a TTL as a safety net. For the editor's own view, read from the database for a few seconds after their write
(read-your-writes).
</details>

## Key takeaways

- On writes, delete the cache entry rather than updating it.
- Races can still leave stale data, so TTLs are the safety net; versions or CDC give stronger guarantees.
- Invalidate items precisely; let lists and pages expire on short TTLs.
- Cache for display, verify at the moment of truth.

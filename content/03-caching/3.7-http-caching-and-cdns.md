# HTTP caching and CDNs

The fastest request is the one that never reaches you. HTTP has caching built in. You control it with response
headers, and browsers and CDNs obey.

## Cache-Control

```http
Cache-Control: public, max-age=31536000, immutable     # versioned static file: cache for a year
Cache-Control: public, max-age=60, stale-while-revalidate=300   # public page: 1 min fresh, then refresh in background
Cache-Control: private, max-age=0, must-revalidate     # personal data: browser only, always check
Cache-Control: no-store                                # never store anywhere (sensitive)
```

| Directive | Meaning |
|-----------|---------|
| `public` / `private` | Shared caches (CDN) may store it / only the user's browser may |
| `max-age=N` | Fresh for N seconds: use without asking the server |
| `s-maxage=N` | Like max-age, but only for shared caches (lets the CDN cache longer than browsers) |
| `stale-while-revalidate=N` | After expiry, serve the stale copy for up to N s while refreshing |
| `no-cache` | May store, but must revalidate before every use |
| `no-store` | Never store |

## Revalidation with ETags

When a cached copy expires, the browser can ask "has it changed?" instead of downloading it again:

```http
→ GET /api/products/42
← 200 OK   ETag: "a1b2c3"   Cache-Control: max-age=60

(60 s later)
→ GET /api/products/42   If-None-Match: "a1b2c3"
← 304 Not Modified       (no body: tiny and fast)
```

## Redirect caching (a classic trap)

| Status | Cached by browsers? | Use for |
|--------|---------------------|---------|
| `301` / `308` Permanent | **Yes, possibly for a very long time** | Moves that will never change |
| `302` / `307` Temporary | No (unless headers say so) | Short links you want to count or change |

A URL shortener returning `301` gets faster, but loses click analytics and can never change a link's target for
users who already followed it.

## CDNs

A CDN is a network of edge servers in many cities. Users connect to the nearest edge:

```
User (Mumbai) ─5 ms─▶ Edge (Mumbai) ──HIT──▶ response
                            │ MISS
                            └──120 ms──▶ Origin (Frankfurt) ──▶ cached at the edge for next time
```

Beyond caching, CDNs terminate TLS close to users (saving handshake round trips), absorb DDoS traffic and compress
responses.

**What to put on a CDN**
- Static assets (JS, CSS, images, video segments): always.
- Public HTML and API responses: with short TTLs plus `stale-while-revalidate`.
- Personalised responses: only with care. Vary the cache key on the right header or cookie, or don't.

**Invalidation**
- Versioned URLs for assets (`/img/logo.7d3f.png`): never purge.
- Purge APIs for content (`purge /products/42`): takes seconds to propagate worldwide.
- Short TTLs for pages that change often.

## Try it

Write `Cache-Control` headers for:
1. `/assets/app.9f2c1.js`
2. `/api/trending` (same for everyone, changes every minute)
3. `/api/me/orders`

## Key takeaways

- `Cache-Control` tells browsers and CDNs what they may store and for how long.
- ETags turn re-downloads into tiny `304` responses.
- 301s are cached hard; use 302/307 when you may change the target or need to count clicks.
- CDNs cut latency and origin load; use versioned URLs to avoid purges.

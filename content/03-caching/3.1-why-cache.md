# Why cache

Your product page gets 20,000 views a second. The database answers about 15,000 queries a second before it falls
over. You could buy a much bigger database, or notice that **the same 2,000 products account for most views**.

## The idea

A **cache** keeps a copy of data somewhere faster and closer than where it lives. A request checks the cache first:

```
read(product 42):
  cache has it?   → HIT  → answer in ~1 ms
  cache doesn't?  → MISS → ask the database (~10 ms), store the answer in the cache, return it
```

Caches work because real traffic is **skewed**: a small share of keys gets most of the requests (often called the
80/20 rule; social feeds and links are even more extreme). Keep the hot keys in memory and most reads never reach the
database.

## Hit ratio math

```
database reads = total reads × (1 − hit ratio)
```

| Hit ratio | DB reads at 20,000 req/s | Database load |
|-----------|--------------------------|---------------|
| 0% | 20,000 | overloaded |
| 50% | 10,000 | busy |
| 80% | 4,000 | comfortable |
| 95% | 1,000 | idle |
| 99% | 200 | almost nothing |

Going from 90% to 99% hits cuts database traffic **10x**. Small hit-ratio gains at the top end are worth a lot.

## Latency gets better too

Average read time = `hit × cache time + miss × (cache time + DB time)`.

At a 90% hit ratio, with a 1 ms cache and a 10 ms database: `0.9 × 1 + 0.1 × 11 = 2 ms` instead of 10 ms. The p99 is
still a miss, so misses must stay fast too.

## What's worth caching

| Good candidates | Poor candidates |
|-----------------|-----------------|
| Read much more than written (product pages, profiles, configs) | Written as often as read (live counters) |
| Expensive to compute (rendered pages, aggregates) | Cheap to fetch anyway |
| Okay to be slightly stale | Must be exact (balances at checkout) |
| Shared by many users | Unique per request (search with random filters) |

## The cost

A cache is a **second copy** of the data, and copies drift. Every cache brings the questions you'll answer in this
module:
- When the data changes, how does the cache find out? (3.5)
- What happens when the cache is empty or restarts? (3.6)
- What goes in, and for how long? (3.4)

> "There are only two hard things in computer science: cache invalidation and naming things." (Phil Karlton)

## Key takeaways

- A cache serves repeated reads from fast memory; skewed traffic makes it effective.
- DB load = reads × (1 − hit ratio); the last few percent of hit ratio matter most.
- Cache data that's read often, changes rarely, and can be slightly stale.
- Every cache is a copy that can go stale, empty or wrong.

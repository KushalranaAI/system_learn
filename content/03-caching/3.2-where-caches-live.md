# Where caches live

"Add a cache" can mean six different places. The closer to the user, the faster and cheaper a hit is, and the harder
it is to invalidate.

```
User ─▶ [1 Browser] ─▶ [2 CDN edge] ─▶ [3 Reverse proxy] ─▶ API server [4 in-process] ─▶ [5 Redis] ─▶ DB [6 buffer pool]
```

| # | Layer | What it holds | A hit saves | Invalidation |
|---|-------|---------------|-------------|--------------|
| 1 | **Browser cache** | Responses with `Cache-Control` headers | The entire request | Hard: you can't reach into users' browsers |
| 2 | **CDN** | Static files, public pages, API responses | The trip to your data centre | Purge APIs, TTLs, versioned URLs |
| 3 | **Reverse proxy** (nginx, Varnish) | Whole HTTP responses | App server work | Purge or TTL |
| 4 | **In-process** (a map in your server's memory) | Hot objects, config | Network hop to Redis | Per server, so each one drifts separately |
| 5 | **Distributed cache** (Redis, Memcached) | Objects, query results, sessions | Database query | You control it directly |
| 6 | **Database buffer pool** | Recently used pages | Disk reads | Automatic |

## Picking layers

**Browser and CDN** suit things that are the **same for everyone** and change rarely: images, JS/CSS bundles,
logged-out pages. Use **versioned file names** (`app.3f9a1c.js`) with long TTLs: a new deploy means a new name, so
nothing needs purging.

**In-process** is the fastest application-level cache (nanoseconds, no network), but:
- each server has its own copy, so 20 servers means 20 caches that can disagree;
- memory is limited, and it empties on every deploy.

Use it for small, hot, rarely changing data: feature flags, config, the top 100 products.

**Redis** is the workhorse: shared by all servers, large, sub-millisecond, and it survives deploys. It's the usual
answer to "add a cache" in a design discussion.

## Layering

Big systems stack them. A product page might be:
- HTML shell → CDN (1 minute);
- product JSON → Redis (5 minutes);
- price → always fresh from the database.

Each layer catches what the one above missed.

```
100,000 req/s ──CDN 80% hit──▶ 20,000 ──Redis 90% hit──▶ 2,000 ──▶ database
```

## Private vs shared data

Never cache a user's private response in a **shared** layer (CDN or proxy) unless the cache key includes the user.
Mark private responses with:

```http
Cache-Control: private, max-age=60
```

A shared cache that serves Alice's account page to Bob is a security incident, not a performance bug.

## Try it

For a news site, place each in a cache layer (or none):
1. The site logo
2. Today's front page (same for everyone, updates every few minutes)
3. "Your saved articles"
4. Article view counter

<details>
<summary>Answer</summary>

1. Browser + CDN, versioned URL, cached for a year.
2. CDN with a short TTL (30–60 s), or Redis behind the app.
3. Redis keyed by user, or no cache. Never a shared CDN without the user in the key.
4. Don't cache the count as truth. Increment in Redis and flush to the DB periodically, or count asynchronously.
</details>

## Key takeaways

- Caches exist at every layer from the browser to the database.
- Closer to the user means a bigger saving, but less control over invalidation.
- Versioned URLs make CDN and browser caching safe.
- Never put private data in a shared cache without the user in the key.

# Keys, TTLs and eviction

Three small decisions control whether a cache helps or hurts: what you name each entry, how long it lives, and what
gets thrown out when memory is full.

## Cache keys

A key must identify **exactly** the data it holds, nothing more and nothing less.

| Key | Problem |
|-----|---------|
| `product` | Every product shares one entry: users see the wrong product |
| `product:42` | ✅ |
| `product:42:user:7:ip:1.2.3.4` | Too specific: no two requests share an entry, hit ratio ≈ 0% |
| `product:42:lang:en` | ✅ when the response really differs by language |
| `v3:product:42` | ✅ a version prefix lets you invalidate everything by bumping `v3` → `v4` |

Rules:
- Include **every input that changes the output** (id, language, currency, user if personalised).
- Exclude inputs that don't (tracking params, client IP, request id).
- Keep keys readable: `<type>:<id>[:<variant>]`.

## TTL (time to live)

Every entry should expire eventually, even if you also invalidate on writes. TTLs are the safety net for missed
invalidations.

| Data | Typical TTL |
|------|-------------|
| Static asset with a versioned URL | 1 year |
| Product details | 5–60 minutes, plus delete on update |
| Home page / trending list | 30–60 seconds |
| Session | Matches the login lifetime |
| Price / stock at checkout | Don't cache, or a few seconds |

Longer TTLs mean more hits and more staleness. **Add jitter** (TTL = 300 s ± 10%) so keys cached at the same moment
don't all expire at the same moment (lesson 3.6).

## Eviction: when memory is full

Redis has a memory limit. When it's reached, the **eviction policy** decides what goes.

| Policy | Evicts | Good for |
|--------|--------|----------|
| **LRU** (least recently used) | What hasn't been touched longest | General caching: the default choice |
| **LFU** (least frequently used) | What's used least often | Stable hot sets: keeps popular items through bursts of one-off reads |
| **TTL-based** (`volatile-ttl`) | What expires soonest | Mixed data where some keys must stay |
| **noeviction** | Nothing; writes fail | When Redis is used as a database, not a cache |

A burst of one-off reads (a crawler) can push hot keys out of an LRU cache. LFU resists that.

## Sizing a cache

```
memory ≈ number of hot keys × (key size + value size + ~50 bytes overhead)
```

*500,000 hot products × (30 B key + 2 KB value + 50 B) ≈ 1 GB.* Add headroom (×1.5–2) for growth and fragmentation.

You rarely need to cache *everything*. With skewed traffic, caching the hottest 10–20% of keys often gets you 80–90%
of hits. Measure the hit ratio and grow memory until it stops improving.

## Try it

A cached search endpoint has a 3% hit ratio. Its key is
`search:{query}:{page}:{session_id}:{timestamp}`. Fix it.

<details>
<summary>Answer</summary>

Drop `session_id` and `timestamp`: they make every request unique. Normalise the query (lowercase, trim, sort
filters) so equivalent searches share a key: `search:v1:{normalised_query}:{page}`. Add a short TTL (e.g. 60 s), since
results change as new items arrive.
</details>

## Key takeaways

- A key must include every input that changes the output, and nothing else.
- Always set TTLs, with jitter; also invalidate on writes.
- LRU is the default eviction policy; LFU protects stable hot sets.
- Size for the hot set, not the whole dataset.

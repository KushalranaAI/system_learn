# Push vs pull

A chat message, a goal in a live match, an order changing to "out for delivery": some news can't wait for the user to
refresh. There are four ways to get it to them.

## 1. Short polling

The client asks every few seconds.

```
every 5 s:  GET /orders/42/status   → "preparing" … "preparing" … "out for delivery"
```

- ✅ Trivial; works everywhere; stateless servers.
- ❌ Delay of up to one interval.
- ❌ Wasteful: 1M users polling every 5 s is **200,000 req/s**, almost all answering "nothing new".

## 2. Long polling

The client asks, and the server **holds the request open** until there's news (or a timeout of ~30 s), then the
client immediately asks again.

- ✅ Near-instant delivery over plain HTTP.
- ❌ Each waiting client holds a connection; reconnect churn after every message.

## 3. Server-Sent Events (SSE)

One long-lived HTTP response; the server streams events down it.

```http
GET /events   Accept: text/event-stream

data: {"order": 42, "status": "out_for_delivery"}

data: {"order": 42, "eta_min": 12}
```

- ✅ Simple, HTTP-native, automatic reconnect with `Last-Event-ID`.
- ❌ One-way (server → client). The client still sends with normal requests.

## 4. WebSockets

An HTTP request is upgraded into a persistent, two-way, full-duplex connection.

- ✅ Lowest latency, both directions, little per-message overhead.
- ❌ Stateful connections: harder load balancing, scaling and deploys; you build your own protocol on top.

## Choosing

| Use case | Good choice | Why |
|----------|-------------|-----|
| Order status, every few minutes | Polling (15–30 s) or SSE | Rare updates; polling is fine at modest scale |
| Notifications, live scores, dashboards | **SSE** | Server → client only; simple |
| Chat, multiplayer, collaborative editing | **WebSockets** | Frequent messages in both directions |
| Mobile app in the background | **Push notifications** (APNs/FCM) | Apps can't hold connections when backgrounded |

## The cost model flips

- **Polling** costs **requests per second** = users ÷ interval.
- **Push** costs **open connections** = concurrent users, plus messages per second.

A million connected users mostly doing nothing is cheap in CPU but expensive in **memory and file descriptors**
(lesson 6.2).

## Try it

A delivery app has 400,000 users watching an active order at dinner time. Status changes about 6 times per order over
40 minutes. Compare polling every 5 s with SSE.

<details>
<summary>Answer</summary>

Polling: 400,000 ÷ 5 = **80,000 req/s**, and ~99.9% of responses say "no change". SSE: 400,000 open connections, plus
only 400,000 × 6 ÷ 2,400 s ≈ **1,000 messages/s**. SSE wins on server work and freshness; its cost is holding the
connections.
</details>

## Key takeaways

- Short polling is simple but wasteful and delayed; long polling is a workaround.
- SSE streams server → client over HTTP; WebSockets are two-way.
- Background mobile apps need platform push notifications.
- Push trades request volume for open connections.

# Reconnects and missed messages

A user goes through a tunnel. For 40 seconds the connection is dead; three messages were sent meanwhile. When the
connection comes back, they must appear, exactly once and in order.

## Assume connections drop

On mobile, connections drop constantly. Design the protocol so that **a drop loses nothing**:

1. Every message has a **sequence number** (per conversation, or per user stream).
2. The client remembers the **last sequence it has seen**.
3. On reconnect, the client says "resume after seq 1841".
4. The server sends everything after 1841 (from the database or a recent-message buffer), then switches to live.

```
client: CONNECT  resume_from={chat:42 → 1841, chat:77 → 309}
server: chat:42 #1842, #1843, chat:77 #310 … then live events
```

SSE has this built in: the `Last-Event-ID` header is sent automatically on reconnect.

## Exactly once, from the user's view

The network gives you at-most-once or at-least-once delivery. **Make duplicates harmless** instead:
- every message has a unique id (often generated by the sender's client);
- the client drops ids it has already shown;
- the server stores with `INSERT … ON CONFLICT DO NOTHING` on that id, so a resent "send" doesn't create two messages.

## Client reconnect logic

```
delay = min(30 s, 0.5 s × 2^attempt) × random(0.5, 1.5)    # exponential backoff + jitter
```

- **Backoff** stops a dead server from being hammered.
- **Jitter** stops 100,000 clients from retrying in lockstep after an outage (a reconnect storm).
- Reset the backoff after a stable connection.
- Detect dead connections with heartbeats (lesson 6.2), not just TCP errors, which can take minutes to surface.

## Sending while offline

- Queue outgoing messages locally, with their client-generated ids.
- Show them as "sending…", and retry on reconnect.
- The server acknowledges with the assigned sequence number, and the client replaces its pending copy.

That's how messaging apps show one tick (sent to server) and two ticks (delivered to the recipient's device). Each tick
is an acknowledgement at a different hop.

## How far back can you resume?

Keep a short **buffer** of recent events in memory or Redis (say 5 minutes) for fast resumes. Beyond that, the client
does a full sync from the API (the database is the source of truth). If the gap is huge, send "you missed 2,000
messages, load the latest" instead of replaying everything.

## Try it

A chat client reconnects and receives messages #1842, #1844, #1845 for a conversation. What should it do?

<details>
<summary>Answer</summary>

It has detected a **gap** (#1843 is missing). Show what it has in order, and request `GET /conversations/42/messages?after=1842`
(or an explicit fetch of #1843) to fill the gap before marking the conversation as up to date.
</details>

## Key takeaways

- Sequence numbers plus "resume from last seen" make drops lossless.
- Unique message ids make duplicates harmless, so retries are safe.
- Reconnect with exponential backoff and jitter; detect dead links with heartbeats.
- Keep a short replay buffer; fall back to a full sync from the database.

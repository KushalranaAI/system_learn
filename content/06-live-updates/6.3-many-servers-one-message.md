# Many servers, one message

Alice is connected to gateway 3. Bob sends her a message, and his request lands on API server 7. How does server 7
get the message onto Alice's socket on gateway 3?

## Option 1: A connection registry

Keep a map of `user → gateway` in Redis. Server 7 looks up Alice, then sends to gateway 3 directly.

```
Alice connects to gw-3 → SET conn:alice gw-3 EX 60 (refreshed by heartbeats)
Bob → API-7 → GET conn:alice = gw-3 → RPC gw-3.deliver(alice, msg)
```

- ✅ Each message goes only where it's needed.
- ❌ The registry must stay accurate (stale entries after crashes); users on several devices need a set of entries.

## Option 2: Pub/sub

Every gateway subscribes to channels for the users (or rooms) it holds. Publishers don't need to know where anyone is.

```
gw-3:  SUBSCRIBE user:alice  room:general
API-7: PUBLISH user:alice "{...}"   → the broker delivers to gw-3
```

Brokers: **Redis Pub/Sub** (simple, fire-and-forget), **NATS** (fast, built for this), **Kafka** (durable, replayable;
Module 15).

- ✅ Decoupled; handles rooms and broadcasts naturally.
- ❌ Fire-and-forget pub/sub drops messages if a subscriber is briefly disconnected, so you need a catch-up path
  (lesson 6.5).

## Rooms and fan-out

A message to a room with 50,000 members means 50,000 socket writes.

| Room size | Strategy |
|-----------|----------|
| Small (DMs, groups) | Publish once per room; every gateway with members delivers |
| Large (live event, 1M viewers) | Publish once per gateway-room; batch, sample or throttle ("1,203 new comments") |

At huge scale, a broadcast to every gateway costs more than the messages themselves. Only gateways that actually hold
room members should subscribe.

## Ordering

Users expect messages in order. Pub/sub over many servers can reorder them.
- Assign **sequence numbers per conversation** (from the database, or a single writer per conversation).
- Clients sort and detect gaps by sequence number.

## The durable path

Live delivery is an optimisation. The truth lives in the database:

```
1. Store the message (conversation_id, seq, body)   ← durable
2. Publish it for live delivery                     ← best effort
3. Offline or missed? The client fetches messages after its last seq on reconnect
```

## Try it

A team chat app runs 20 gateways. Channels average 30 members, and messages must arrive in order. Sketch the flow from
"Bob hits Send" to "Alice sees it" when they're on different gateways.

<details>
<summary>Answer</summary>

Bob → API server: insert the message with the next `seq` for the channel (a transaction or a per-channel counter) →
`PUBLISH channel:123 {seq, body}` → each gateway subscribed to `channel:123` (those holding members) pushes to its
sockets → clients order by `seq`, and fetch `seq > last_seen` from the API if they detect a gap.
</details>

## Key takeaways

- Messages must reach the gateway holding the user's connection.
- Use a registry for targeted delivery, or pub/sub for decoupling and rooms.
- Big rooms need batched or throttled fan-out.
- Store first, deliver live second; sequence numbers give ordering and gap detection.

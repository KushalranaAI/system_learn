# Holding many connections

With push, the question changes from "how many requests per second?" to "how many **connections** can one server
hold?" The answer is often 50,000–500,000, if you design for it.

## What a connection costs

| Resource | Per connection | Notes |
|----------|----------------|-------|
| **File descriptor** | 1 | OS default limits are often 1,024. Raise `ulimit -n` |
| **Kernel socket buffers** | a few KB to tens of KB | Tunable |
| **Application memory** | 2 KB – 100 KB+ | Depends on the runtime: an async event loop is cheap, a thread per connection is expensive |
| **CPU** | ~0 when idle | Heartbeats and messages cost CPU |

### Threads vs event loops

- **Thread per connection:** 100,000 connections means 100,000 threads, each with an MB-scale stack. That's
  impractical.
- **Event loop / async I/O** (Node.js, Go goroutines, Netty, Rust tokio, Elixir/Erlang): one process multiplexes
  hundreds of thousands of mostly idle sockets.

## Sizing a fleet

```
servers = concurrent connections ÷ connections per server (with headroom)
2,000,000 users ÷ 100,000 per server × 1.5 headroom = 30 gateway servers
```

Message rate matters too. A broadcast to 2M users is 2M writes. Check CPU and outbound bandwidth, not only connection
counts.

## Separate the connection tier

Keep connections out of your normal API servers. A dedicated **gateway** tier holds sockets and does little else; the
business logic stays in stateless API servers.

```
clients ═══ WebSocket gateways ──(pub/sub)── API servers ── databases
          (stateful, long-lived)          (stateless, scale freely)
```

Deploying business logic then doesn't disconnect everyone.

## Load balancing long connections

- Use an LB that supports WebSockets/SSE, with **long idle timeouts** (or heartbeats below the timeout).
- New connections should go to the **least-loaded** gateway. Round robin drifts badly with long-lived connections.
- **Rebalancing:** after scaling out, new servers sit empty while old ones stay full. Gradually ask some clients to
  reconnect.

## Heartbeats

Networks silently drop idle connections (NATs, proxies, mobile carriers). Send a ping every 20–30 s:
- it keeps NAT mappings alive;
- it detects dead clients, so you can free their resources;
- it tells the client its connection is dead, so it can reconnect.

## Deploys and reconnect storms

Restarting a gateway drops all its connections, and they all reconnect at once.
- Drain slowly: stop accepting new connections, then close existing ones gradually.
- Clients reconnect with **exponential backoff plus jitter**, so 100,000 clients don't arrive in the same second.

## Try it

You expect 600,000 concurrent WebSocket users. Each gateway holds 80,000 connections at safe CPU and memory. How many
gateways do you run, and what else must you plan for?

<details>
<summary>Answer</summary>

600,000 ÷ 80,000 = 7.5, so 8, plus headroom for losing one and for deploys: **10**. Also plan file-descriptor limits,
LB idle timeouts and heartbeats, least-connection placement, gradual draining on deploys, and client backoff with
jitter.
</details>

## Key takeaways

- Push scales by connections: file descriptors and memory, not request rate.
- Use event-loop/async servers and a dedicated gateway tier.
- Balance by least connections; heartbeat to keep and detect connections.
- Drain gradually and make clients reconnect with backoff and jitter.

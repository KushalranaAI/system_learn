# Rate limits and quotas in the contract

Module 8 built rate limiters: algorithms, keys, counters across servers. This lesson is about the other side: how
limits appear **to the people calling your API**. A limit that clients can't see or predict feels like an outage. One
that's documented, signalled in headers and fair per customer is just part of the product.

## Limits vs quotas

| | Rate limit | Quota |
|-|------------|-------|
| Window | Seconds or minutes | A day, a month, a billing period |
| Purpose | Protect the service from bursts and floods | Fair use and pricing tiers |
| Example | 100 requests/s per API key, burst 200 | 1,000,000 calls/month on the Pro plan |
| When hit | `429 Too Many Requests`, retry shortly | `429` (or `403`) until the period resets or the plan changes |

Most public APIs have both, plus **concurrency limits** (at most N requests in flight) for expensive endpoints, and
separate limits for costly operations (search, exports, SMS sends).

## Telling clients

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 12
RateLimit-Policy: "burst";q=200;w=1, "daily";q=100000;w=86400
RateLimit: "burst";r=0;t=12
Content-Type: application/problem+json

{"type": "https://api.example.com/errors/rate-limited", "title": "Too many requests",
 "detail": "Burst limit of 200 requests per second exceeded for key ak_live_…3f9", "status": 429}
```

- **`Retry-After`** (seconds or a date) is standard HTTP and every good client honours it.
- **`RateLimit-Policy` and `RateLimit`** come from the IETF HTTP API working group's draft (revision 10, September
  2025, still a draft): the policy (quota `q`, window `w`) and what's **r**emaining and when it resets (`t`). Many APIs
  still use older `X-RateLimit-Limit / -Remaining / -Reset` headers; GitHub and others document their own.
- Send the headers on **every** response, not just 429s, so clients can slow down before they hit the wall.

## What to count

- **Per API key or OAuth client** for partners, so one customer can't use up another's capacity.
- **Per user** inside a client app, so one heavy user doesn't exhaust the app's whole allowance.
- **Per IP** only at the edge for unauthenticated traffic (sign-up, login), with headroom for shared IPs (lesson 8.3).
- **By cost, not by request**, when requests differ a lot. GitHub's GraphQL API assigns points per query based on how
  many nodes it could return; LLM APIs limit tokens per minute, not just requests.

## Tiers

Limits are usually part of pricing (lesson 19.3):

| Plan | Rate limit | Monthly quota | Burst | Support |
|------|------------|---------------|-------|---------|
| Free | 10 req/s | 100k | 20 | Community |
| Pro | 100 req/s | 10M | 200 | Email |
| Enterprise | Negotiated | Negotiated | Negotiated | SLA |

Keep the API identical across tiers; only the key's limits change.

## Being a good limiter

- **Fail open** if the counter store is down (with a local fallback), except for abuse-sensitive endpoints like login
  (lesson 8.5).
- **Don't penalise retries that you caused**: during your own incident, consider relaxing limits.
- **Use 503, not 429, for overload** that isn't the client's fault, with `Retry-After`.
- **Monitor 429s per client**; a spike means a customer's integration is broken or abusive, so reach out.

## Key takeaways

- Rate limits protect the service in seconds; quotas enforce fair use and pricing over days and months.
- Signal limits on every response; answer 429 with Retry-After and a clear problem body.
- Count per API key, user or cost, not just per IP; make tiers differ only in limits.
- Watch 429s per client and treat your limiter's own failure modes deliberately.

# Evolving without breaking

The orders API returns `total` as a number of rupees with decimals, and finance wants integer paise to stop rounding
errors. You can't just change it: thousands of app installs read `total`. You can't ship `/v2` for one field either.
Most real API evolution is this: small changes made safely, one step at a time.

## Expand and contract

The pattern for any change that would otherwise break clients:

```
1. Expand    add the new thing alongside the old        total: 49.99  +  totalMinor: 4999
2. Migrate   move clients over, measure who still uses the old one
3. Contract  remove the old thing once usage reaches ~zero (or after the announced date)
```

The same works for renaming an endpoint (serve both paths), changing a format (accept both on input, emit both on
output), or splitting a resource.

## Tolerant readers, strict writers

- **Clients** should ignore unknown fields, handle unknown enum values, and not depend on field order.
- **Servers** should be precise in what they send and validate what they receive, but keep accepting old input shapes
  during a migration.

Put the client rules in your docs and SDKs on day one; they're what make additive change safe.

## Telling clients something is going away

HTTP now has standard headers for this:

```http
HTTP/1.1 200 OK
Deprecation: @1767225600                         ← RFC 9745 (March 2025): deprecated since this date
Sunset: Wed, 30 Sep 2026 23:59:59 GMT            ← RFC 8594: it stops working after this
Link: <https://developer.shop.example/migrate/track-v2>; rel="deprecation"; type="text/html"
```

Machine-readable signals reach code that nobody reads blogs for: SDKs can log warnings, and API gateways and linters can
flag them. The Sunset date must not be earlier than the Deprecation date.

## Know who's still calling

You can't retire what you can't measure. Log the **version, endpoint and client** (API key, app version, SDK version) for
every request, and build a dashboard of deprecated usage. Then:

1. Announce with a date (changelog, email to registered developers, headers).
2. Contact the top remaining callers directly.
3. Run short, scheduled **brownouts**: switch the old endpoint off for 10 minutes, then an hour, weeks before the
   sunset. Forgotten callers surface while there's still time.
4. Switch off, and return `410 Gone` with a link to the migration guide.

## Hyrum's law in practice

Callers depend on behaviour you never promised (lesson 19.1): error message text, response order, timing, the number of
items on a page. Defend against it:

- Return documented sort orders explicitly; don't let the database pick.
- Make error `type` URIs the stable contract, not the message text.
- Give pagination an explicit `limit` with a documented default and maximum.
- Test with **contract tests** (consumer-driven, e.g. Pact) so you learn which behaviour your consumers actually use.

## Schema checks in CI

Run a breaking-change detector on every pull request: `oasdiff` or similar for OpenAPI, `buf breaking` for Protobuf,
GraphQL Inspector for GraphQL schemas. A removed field or a type change should fail the build unless someone approves
it deliberately.

## Try it

`GET /v1/orders/:id/track` is being replaced by a WebSocket feed. Plan its retirement over nine months.

- Months 1-6: dashboard of callers by API key and app version; email the remaining integrators; ship app updates that

## Key takeaways

- Expand, migrate, contract: add the new beside the old, move clients, remove the old.
- Tolerant readers and strict writers make additive change safe; document the client rules up front.
- Use `Deprecation` (RFC 9745) and `Sunset` (RFC 8594) headers, usage dashboards and brownouts to retire things.
- Detect breaking schema changes automatically in CI.

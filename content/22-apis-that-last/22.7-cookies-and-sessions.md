# Cookies and sessions

A single-page app stores its access token in `localStorage` because a tutorial did. Months later, a third-party analytics
script is compromised and reads `localStorage` on every page. Every signed-in user's token is copied to an attacker's
server. Where a browser keeps credentials matters as much as how they're issued.

## Cookies in one paragraph

A server sets a cookie with `Set-Cookie`; the browser stores it and sends it back automatically on matching requests.
That automatic sending is both the convenience and the danger.

```http
Set-Cookie: __Host-session=9f3c…e1; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=28800
```

| Attribute | Meaning | Why it matters |
|-----------|---------|----------------|
| `Secure` | Only sent over HTTPS | No leaks over plain HTTP |
| `HttpOnly` | JavaScript can't read it | An XSS bug can't steal the session |
| `SameSite=Lax` (default in modern browsers) / `Strict` | Not sent on most cross-site requests | Main defence against CSRF |
| `SameSite=None; Secure` | Sent cross-site | Needed for embedded third-party widgets; brings CSRF risk back |
| `Max-Age` / `Expires` | Lifetime | Short sessions limit damage |
| `Domain` / `Path` | Where it's sent | Narrower is safer |
| `__Host-` prefix | Requires `Secure`, `Path=/`, no `Domain` | Can't be set or overwritten by a subdomain |

## Sessions vs tokens in the browser

| | Server session + cookie | Token in JS memory / storage |
|-|-------------------------|------------------------------|
| Where the credential lives | An opaque id in an HttpOnly cookie | A JWT or access token readable by JS |
| XSS steals it? | No (it can still *use* it while the page is open) | Yes, if it's in `localStorage` |
| CSRF? | Possible; mitigate with SameSite and CSRF tokens | No (not sent automatically) |
| Revocation | Delete the session row: instant | Wait for expiry or use a denylist |
| Works across domains and for mobile | Awkward | Natural |

The common recommendation for browser apps today is the **backend-for-frontend (BFF) pattern**: a small server on your
own domain does the OAuth flow, keeps tokens server-side, and gives the browser only an HttpOnly, `SameSite` session
cookie. The browser calls the BFF; the BFF calls APIs with the access token. Mobile and server clients use tokens
directly.

## CSRF

Cross-site request forgery: a malicious page makes the victim's browser send a request to your API with their cookies
attached.

Defences, in layers:

1. `SameSite=Lax` or `Strict` cookies.
2. **Never change state with GET.**
3. For cookie-authenticated, state-changing requests, require a **CSRF token** (a value the page must echo in a header),
   or require a custom header like `X-Requested-With` together with a strict CORS policy (cross-site pages can't set
   custom headers without a preflight you'd refuse).
4. Check the `Origin` (or `Sec-Fetch-Site`) header on state-changing requests.

## Third-party cookies

Safari and Firefox block third-party cookies by default. Chrome still allows them as of 2025, after Google dropped its
plan to phase them out, but don't build anything that depends on them: embedded widgets and cross-site sign-in should
use OAuth/OIDC redirects, or partitioned cookies (`CHIPS`, the `Partitioned` attribute), instead.

## Session lifetimes

- **Idle timeout** (e.g. 30 minutes for banking, days for social apps) and **absolute timeout** (re-authenticate
  after 8-24 hours for sensitive apps).
- **Rotate the session id** at sign-in and privilege changes (prevents session fixation).
- **Step-up authentication** for sensitive actions (change email, add a payee): ask for a passkey or OTP again.
- Let users see and revoke their active sessions.

Secure the session for a web banking app on `bank.example` whose API is at `api.bank.example`.

## Key takeaways

- Cookies are sent automatically: mark them `Secure`, `HttpOnly`, `SameSite`, and narrow their scope.
- Tokens in `localStorage` are exposed to any script on the page; prefer HttpOnly cookies via a BFF for browsers.
- Defend against CSRF with SameSite, no-GET-mutations, CSRF tokens or custom headers, and Origin checks.
- Don't depend on third-party cookies; give sessions idle and absolute timeouts and rotate ids.

# Data fetching patterns

An API can be correct and still feel slow because of **how clients have to fetch**: too many round trips, too much
data per response, or lists that shift under the user's thumb. These patterns let clients get what they need in as few
trips as possible, without turning every endpoint into a custom report.

## Pagination

Lesson 2.3 introduced offset and cursor pagination. The rule of thumb holds for every list in an API:

| | Offset (`?offset=40&limit=20`) | Cursor (`?after=<opaque>&limit=20`) |
|-|-------------------------------|--------------------------------------|
| Jump to page 37 | ✅ | ❌ |
| Stable while items are added or deleted | ❌ duplicates and skipped items | ✅ |
| Cost of a deep page | Grows with the offset (the DB walks every skipped row) | Constant (an index seek) |
| Total count | Easy (but expensive on big tables) | Optional, often approximate |

```json
GET /v1/orders?limit=20&after=eyJ0IjoiMjAyNi0xMC0yOFQwOTozMDowMFoiLCJpZCI6Im9yZF85MSJ9
{
  "data": [ ... ],
  "next_cursor": "eyJ0IjoiMjAyNi0xMC0yOFQwOTowMToxMloiLCJpZCI6Im9yZF83MCJ9",
  "has_more": true
}
```

Make cursors **opaque** (base64 of the sort key and id), cap `limit` (say 100), and give every list a default. The
simulation below pages through a real feed while items are inserted and deleted.

## Choosing fields

| Pattern | Example | Used by |
|---------|---------|---------|
| **Sparse fieldsets** | `?fields=id,name,price` | JSON:API, Google APIs (`fields=`) |
| **Expansion / include** | `?expand=customer,lines.product` | Stripe (`expand[]`), JSON:API (`include`) |
| **Field masks** (gRPC) | `FieldMask { paths: ["name", "price"] }` | Google APIs |
| **GraphQL** | The query lists fields | GraphQL APIs |

Expansion turns N follow-up calls into one, but each expansion must be bounded (how deep, how many items), and
expensive ones should count more against rate limits.

## Batching

When a client needs many items by id, give it one call:

```
GET /v1/products?ids=p_1,p_2,p_3,…        (cap at ~100 ids)
POST /v1/products:batchGet {"ids": [...]}  (when the list is too long for a URL)
```

On the server, the same idea fixes N+1 queries (DataLoader, lesson 20.4).

## Client-adapting APIs

Different clients need different shapes: a watch shows three fields, a TV shows rich artwork, the web shows
everything. Options, from simplest to most flexible:

1. **One general API** with `fields` and `expand`. Clients choose.
2. **Backends for frontends** (lesson 20.6): a small API per client type, shaped like its screens.
3. **GraphQL**: one graph, every client writes its own queries.
4. **Device hints**: `Accept`, `Save-Data`, client hints (`Sec-CH-Viewport-Width`) to choose image sizes and payloads.

## Conditional fetching

Avoid sending what the client already has:

- `ETag` + `If-None-Match` → `304 Not Modified` with no body (lesson 23.3).
- Delta sync: `GET /v1/contacts?updated_since=2026-10-27T00:00:00Z` (or a sync token) returns only changes, including
  tombstones for deletions. This is how mail, calendar and contacts apps stay in sync on mobile networks.

## Try it

Use the simulation: page 500 pages into an order history while 3 new orders arrive and 1 old order is deleted between
page loads. Compare offset and cursor pagination: duplicates, skipped orders and the last page's query time.

<details>
<summary>Answer</summary>

With offsets, every insert pushes rows down (the next page repeats them) and every deletion above your position pulls
rows up past you (you never see them), and the last page walks ~10,000 rows. With a cursor there are no duplicates and
no skips, and each page reads only its 20 rows. The [orders API lab](#/labs/api-evolve-orders) uses this as a checked
step.
</details>

## Key takeaways

- Paginate every list; default to opaque cursors with a capped limit.
- Let clients choose fields and expand related resources, within bounds.
- Offer batch reads by id; batch on the server too.
- Adapt to clients with field selection, BFFs or GraphQL, and avoid resending data with ETags and delta sync.

# Versioning

An API that's never changed is an API nobody uses. Products evolve, mistakes get found, new payment methods and
regulations arrive. Versioning is how you make changes that would break existing clients without breaking them: old
clients keep the old contract while new ones get the new one.

## What counts as breaking

A change is **breaking** if a correctly written client that worked yesterday can fail today.

| Usually safe (additive) | Breaking |
|-------------------------|----------|
| Add an endpoint | Remove or rename an endpoint or field |
| Add an optional request field | Make an optional field required |
| Add a response field | Change a field's type or format (`"12"` → `12`, cents → dollars) |
| Add a new error code to a documented "other" bucket | Change what a status code or error means |
| Relax validation (accept longer names) | Tighten validation (reject what used to work) |
| Make something faster | Change default sorting, page size or behaviour |

Two grey areas catch teams out:

- **Adding an enum value** (`status: "partially_refunded"`) breaks clients with a strict `switch` and no default.
  Document from day one that enums can grow, and tell clients to handle unknown values.
- **Adding response fields** breaks clients that validate responses strictly. Document the *tolerant reader* rule:
  ignore what you don't recognise.

## Where the version lives

| Scheme | Example | Pros | Cons |
|--------|---------|------|------|
| **URL path** | `/v1/orders`, `/v2/orders` | Obvious, easy to route, cache and test in a browser | Encourages big-bang versions; URLs change |
| **Header** | `Api-Version: 2026-10-01` | Clean URLs, fine-grained | Invisible in logs and links unless you add it |
| **Media type** | `Accept: application/vnd.shop.v2+json` | True to HTTP content negotiation | Clunky for clients and tools |
| **Query parameter** | `?api-version=2024-10-21` (Azure) | Easy to set | Mixes with real parameters |
| **No versions, evolve forever** | GraphQL schemas, many internal APIs | No version sprawl | Requires strict additive discipline and deprecations |

Most public REST APIs use a **major version in the path** (`/v1`) and only bump it rarely, plus additive changes in
between.

## Date-based versions: the Stripe model

Stripe pins every account to the API version that was current when it first made a request. Requests can override it
with a `Stripe-Version` header. Internally, the newest code runs for everyone, and a chain of small **version
transformations** rewrites requests and responses back to what each older version expects. Since the
`2024-09-30.acacia` release, Stripe ships monthly versions with only non-breaking changes and two named major releases a
year (Acacia, Basil, Clover, …) that may contain breaking changes.

The result: integrations from years ago keep working untouched, and each merchant upgrades on their own schedule,
testing one version at a time.

## Versioning costs

Every live version is code you test, secure, document and monitor. Keep the count low:

- Prefer **additive changes**; most changes never need a new version.
- When you must break, **bundle** breaking changes into one new version instead of drip-feeding them.
- Translate old versions to the new model at the edge (like Stripe's transformations) so business logic exists once.
- Publish a **support policy**: how long each version lives after its successor ships (12-24 months is common for
  public APIs).

## Try it

Your API is used by your own apps (web updates instantly, mobile apps lag months) and 300 external developers. Choose
a versioning scheme and a support policy.

<details>
<summary>Answer</summary>

A major version in the path (`/v1`) for the external API, with additive changes shipped continuously and documented
rules (tolerant readers, enums can grow). If a breaking change is ever needed, ship `/v2` with all of them at once,
support `/v1` for at least 12-18 months, and translate `/v1` requests into the `/v2` model at the edge. For your own
mobile apps, also track app versions in a header so you know when old builds have died out before removing anything.
</details>

## Key takeaways

- Breaking = a working client can fail. Removals, renames, type changes and stricter rules are breaking; additions
  usually aren't.
- Document from day one that clients must ignore unknown fields and handle unknown enum values.
- Path versions are simplest; date-pinned versions (Stripe) give each client its own upgrade schedule.
- Every live version costs money: prefer additive change, bundle breaks, translate old versions at the edge.

# Lab: evolve an orders API

A food delivery company's orders API has been live for three years. Old app builds still call it every day, and
restaurants receive orders by webhook. Make the changes the product team wants without breaking anyone.

> **Interactive version:** [open the orders API lab](#/labs/api-evolve-orders) for checked quizzes and two simulations
> (pagination drift and double orders).

## Step 1: Safe or breaking?

Rename `total` → `amount`; add `tipAmount`; change `createdAt` to ISO strings; require `deliveryNote`.

<details>
<summary>Reference</summary>

Only adding `tipAmount` is safe. For the others, expand and contract: add `amountMinor` and `createdAtIso` beside the old
fields, keep `deliveryNote` optional (validate it only for new app versions), and remove nothing until usage reaches
zero.
</details>

## Step 2: Retire the tracking endpoint

<details>
<summary>Reference</summary>

`Deprecation` + `Sunset` + `Link` headers, a usage dashboard per client and app version, direct contact with the
remaining users, brownouts, then `410 Gone`.
</details>

## Step 3: The order history export

<details>
<summary>Reference</summary>

Switch from `?offset=` to an opaque cursor over `(created_at, id)`, with an index on those columns. No duplicates, no
skipped orders, constant cost per page. Offer `?updated_since=` for incremental syncs.
</details>

## Step 4: Double orders

<details>
<summary>Reference</summary>

The app sends an `Idempotency-Key` generated once per tap of Place order and reused on every retry; the server stores
the key, a request fingerprint and the response in the same transaction as the order, for at least 24 hours.
</details>

## Step 5: Webhooks to restaurants

<details>
<summary>Reference</summary>

Signed events (HMAC over id, timestamp and body), retries with backoff, an events API for catch-up. Receivers verify,
return 2xx immediately, dedupe by event id, and fetch the order when events arrive out of order.
</details>

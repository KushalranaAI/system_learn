# Events and webhooks

A shop integrates your payments API. It needs to know the moment a payment succeeds, a refund completes or a dispute
opens, sometimes minutes or days after its own request ended. Polling every payment every few seconds would be wasteful
for both of you. Instead, your API **calls them**: a webhook. It sounds simple, and it's where many integrations quietly
lose events.

## Anatomy of a webhook

```http
POST https://shop.example/webhooks/payments
Content-Type: application/json
Webhook-Id: msg_2KWPBgLlAfxdpx2AI54pPJ85f4W
Webhook-Timestamp: 1761640000
Webhook-Signature: v1,K5oZfzN95Z9UVu1EsfQmfVNQhnkZ2pj9o9NDN/H/pI4=

{
  "id": "evt_1Q2w3",
  "type": "payment.succeeded",
  "created": "2026-10-28T09:46:40Z",
  "api_version": "2026-09-01",
  "data": { "object": { "id": "pay_88", "amount": 4999, "currency": "INR", "status": "succeeded" } }
}
```

(The header names follow the open Standard Webhooks convention; many providers use their own.)

## The provider's side

| Concern | Design |
|---------|--------|
| **Authenticity** | Sign `id.timestamp.body` with an HMAC secret per endpoint; include the timestamp to stop replays (reject anything older than ~5 minutes); support two secrets during rotation |
| **Delivery** | Queue every delivery; workers POST with a short timeout (~10 s); success is any 2xx |
| **Retries** | Exponential backoff with jitter over hours or days (e.g. 5 s, 1 min, 10 min, 1 h, … up to 3 days) |
| **Failing endpoints** | Disable after repeated failures and email the owner; show delivery logs and a "resend" button in the dashboard |
| **Ordering** | Not guaranteed. Include `created` and the object's version; consumers shouldn't assume order |
| **Catch-up** | An events API (`GET /events?after=evt_…`) so consumers can recover after downtime |
| **Safety** | Don't call private IPs (SSRF), cap payload sizes, don't follow redirects |

The [webhook delivery sandbox](#/sandbox?preset=api-webhooks) models the delivery queue and workers.

## The consumer's side

Tell integrators to:

1. **Verify the signature** before trusting anything (constant-time comparison).
2. **Return 2xx quickly** and process asynchronously; slow handlers time out and get retried.
3. **Dedupe by event id**: retries and replays mean the same event can arrive more than once.
4. **Not rely on order**: if `payment.updated` arrives before `payment.created`, fetch the current object from the API.

## Thin vs fat events

| | Fat ("snapshot") | Thin ("notification") |
|-|------------------|------------------------|
| Payload | The whole object at the time of the event | Just the type and the object id |
| Consumer | Can act without calling back | Calls `GET /payments/pay_88` for current state |
| Risks | Stale or out-of-order snapshots; more data exposure | Extra API calls; more load on you |

Many providers send fat events but tell consumers to re-fetch when correctness matters.

## Describing events

- **CloudEvents** (a CNCF specification) standardises the envelope: `id`, `source`, `type`, `time`, `datacontenttype`,
  `data`, so events look the same across transports.
- **AsyncAPI** is to event-driven APIs what OpenAPI is to REST: channels, messages, schemas, and generated docs.
- Version event schemas like any contract (lesson 22.1); include the API version that produced the payload.

## Try it

Design webhooks for a delivery app that tells restaurants about orders. What does the restaurant's receiver look like,
and how does it recover after a 2-hour outage?

<details>
<summary>Answer</summary>

Provider: signed `order.created / order.updated / order.cancelled` events with an id, a timestamp and the order version;
queued deliveries with exponential backoff for up to 3 days; dashboard logs; an events API.

Receiver: verify the HMAC signature and the timestamp window; insert the event id into a `processed_events` table with
a unique constraint (duplicate → return 200 and stop); enqueue the work and return 200 within a second; when applying
an update, ignore it if the stored order version is newer. After the outage, retries arrive on their own, and the
receiver can call `GET /events?after=<last seen>` to fill any gap.
</details>

## Key takeaways

- Webhooks push events to other servers; treat delivery as a queue with retries, backoff and logs.
- Sign with HMAC plus a timestamp; consumers verify, return 2xx fast, dedupe by id and don't trust order.
- Offer an events API for catch-up and the object's current state for correctness.
- Describe events with CloudEvents and AsyncAPI, and version them like any contract.

# Idempotency in API design

A customer taps **Pay**. The request reaches your server, the card is charged, and the response is lost when the
train enters a tunnel. The app sees a timeout. Should it retry? If it does, and your API can't tell a retry from a new
payment, the customer pays twice. If it doesn't, the customer may not have paid at all. **The client cannot know.**
Only the API can make retrying safe.

Lesson 12.4 covered idempotency inside distributed systems; this lesson is about designing it into an API contract.

## Which operations are already safe to retry

| Operation | Idempotent by nature? |
|-----------|-----------------------|
| `GET /orders/42` | ✅ reading twice changes nothing |
| `PUT /users/7/settings {full object}` | ✅ the second write leaves the same state |
| `DELETE /cart/items/9` | ✅ the item is gone either way (the second call may return `404`, which is fine) |
| `PATCH /tasks/3 {"done": true}` | ✅ setting a value |
| `PATCH /accounts/3 {"balance": "+100"}` | ❌ relative change |
| `POST /payments` | ❌ creates something new every time |

Prefer designs that are naturally idempotent: `PUT` to a client-chosen id (`PUT /uploads/<uuid>`), "set" instead of
"add". For the rest, there's the **idempotency key**.

## The Idempotency-Key header

```http
POST /v1/payments
Idempotency-Key: 4f9d2c1a-8b3e-4f6a-a1d7-2e9c5b7f0a13
Content-Type: application/json

{"amount": 4999, "currency": "INR", "source": "card_tok_77"}
```

The client generates a unique key **once per intent** (one tap of Pay) and sends the **same key on every retry**. The
server:

```
key never seen          → lock it, do the work, store (key, request fingerprint, response) → return it
key seen, same request  → return the stored response; do nothing again
key seen, still running → 409 Conflict ("a request with this key is in progress"); client retries later
key seen, different body → 422 (or 409): the key was reused for a different request
```

This is how Stripe, Adyen, PayPal and many others work, and it's being standardised by the IETF HTTP API working group
(`draft-ietf-httpapi-idempotency-key-header`, still an Internet-Draft in 2025-26).

## Getting the implementation right

1. **Same transaction.** Save the key and the effect (the payment row) atomically. If they're separate writes, a
   crash in between brings back the duplicate.
2. **Scope the key** per account (and per endpoint), so two customers can't collide.
3. **Keep keys longer than any retry**. Stripe's v1 API keeps them for 24 hours. Apps that retry after restarting the
   next morning need longer.
4. **Fingerprint the request** (hash of method, path and body) to detect a reused key with a different body.
5. **Store the response**, including errors that happened *after* side effects; don't store `5xx` errors that happened
   before anything changed, so a retry can actually retry.
6. **Make it the SDK's job.** Client libraries should generate the key and reuse it across their own retries
   automatically.

## Idempotency downstream

The API is only as idempotent as what it calls. Pass the key (or a derived one) to the payment processor and to any
message you publish, and make consumers dedupe by it (lesson 7.3). The outbox pattern (lesson 16.4) makes "write and
publish" atomic.

## Try it

Run the simulation with no key, then with a new key per attempt, then with one key per intent but saved separately
from the charge, then saved atomically. Finally, shorten the key TTL below the late-retry delay.

<details>
<summary>Answer</summary>

With 5% of responses lost and 3 retries: about 540 double charges per 10,000 payments with no key, almost as many with
a new key per attempt (each retry looks new), a handful with one key per intent saved non-atomically (crashes between
charge and save), and **zero** when the key is saved in the same transaction. With a 1-hour TTL and retries that come 2
hours later, duplicates come back. Turning retries off removes duplicates but leaves hundreds of payments never made.
</details>

## Key takeaways

- After a timeout the client can't know if the work happened; only the API can make retries safe.
- GET, PUT and DELETE are idempotent by definition; design "set" operations where you can.
- For POST, use an Idempotency-Key per intent, stored atomically with the result, scoped, fingerprinted and kept
  longer than any retry.
- Carry idempotency downstream to processors and event consumers.

# Batch vs stream

Should a computation run **once over a big pile of data** (batch) or **continuously as data arrives** (stream)? Many
teams default to one and regret it. Pick per use case.

## The comparison

| | Batch | Stream |
|-|-------|--------|
| Input | A bounded dataset (yesterday's files, a table snapshot) | An unbounded event stream |
| Latency | Minutes to hours | Milliseconds to seconds |
| Correctness | Easy: all the data is there | Harder: late and out-of-order events |
| Reprocessing | Rerun the job | Replay the stream (needs retention) |
| Cost | Efficient for large, periodic work | Always running; state to manage |
| Tools | Spark, SQL warehouses (BigQuery, Snowflake), dbt | Flink, Kafka Streams, Spark Streaming |

## Choose by the question being asked

| Use case | Fit |
|----------|-----|
| Monthly invoices, payroll | Batch |
| Daily business report | Batch |
| Training ML models on history | Batch |
| Fraud check before approving a payment | Stream (or an online service) |
| Live dashboards, alerting | Stream |
| Recommendations updated as you browse | Stream features + batch-trained model |
| Search index updates | Stream (CDC) |

**Rule of thumb:** if a decision must be made, or a human is watching, within minutes, stream it. Otherwise batch is
simpler and cheaper.

## Combining both

### Lambda architecture
Run a **batch layer** (accurate, recomputed periodically) and a **speed layer** (fast, approximate) side by side, and
merge at query time.
- ✅ Fast and eventually exact.
- ❌ **Two codebases** for the same logic, which drift apart.

### Kappa architecture
Use **one streaming pipeline** for everything; to recompute, replay the log from the beginning with the new code.
- ✅ One codebase.
- ❌ Needs long retention (or a lake of archived events) and a streaming engine able to process history fast.

Modern practice often lands in between: streaming for freshness, plus a warehouse or lakehouse (Delta, Iceberg,
Hudi) where the same tables are written by streams and queried by batch SQL.

## Reconciliation

Streams can miss late or broken events. A common, robust pattern: **stream for speed, batch to reconcile.** The live
dashboard uses the stream; a nightly batch job recomputes yesterday exactly and corrects the stored numbers.

## Try it

A ride app needs: (a) driver earnings statements every week; (b) surge pricing that reacts to demand within 30 s; (c)
a city operations dashboard. Batch or stream for each?

<details>
<summary>Answer</summary>

(a) **Batch**: weekly, must be exact, easy to rerun. (b) **Stream**: demand vs supply per area over sliding windows,
with seconds of latency. (c) **Stream** for live tiles, plus batch reconciliation for the historical charts.
</details>

## Key takeaways

- Batch is simple, exact and cheap for periodic work; streams give freshness at the cost of complexity.
- Choose by how fast a decision or a viewer needs the result.
- Lambda runs both paths (two codebases); Kappa uses one stream with replay.
- Stream for speed, batch to reconcile.

# Event sourcing

Most databases store **current state**: the account balance is ₹4,200. **Event sourcing** stores **what happened**,
and derives state from it:

```
AccountOpened(₹0) → Deposited(₹5,000) → Withdrew(₹1,000) → Deposited(₹200)  ⇒  balance = ₹4,200
```

The event log is the source of truth. Current state is a **projection**, computed by replaying events.

## What you gain

- **A complete audit trail** for free: every change, who made it and when. Banks and ledgers have always worked this
  way.
- **Time travel:** "what was the balance on 1 March?" Replay up to that date.
- **New views from old data:** build a new projection (a report, a search index) by replaying history.
- **Debugging:** reproduce a bug by replaying the exact events that caused it.
- **Natural fit with event-driven systems:** the events you store are the events you publish.

## How it works

```
command: Withdraw(₹1,000)
  → load the account's events → rebuild state (balance ₹5,000)
  → validate (enough funds?)
  → append Withdrew(₹1,000) with expected version = 2
  → (if another writer appended version 3 first → conflict → reload and retry)
```

- Events are **immutable** and append-only, per aggregate (one account, one order).
- **Optimistic concurrency** on the aggregate's version prevents conflicting appends.
- **Snapshots** (state at version 1,000) avoid replaying a million events every time.

## What you pay

- **Querying is indirect:** "all accounts with balance > ₹1L" needs a projection (lesson 17.2).
- **Schema evolution:** old events live forever. You need event versioning and "upcasting" old shapes to new ones.
- **Deleting data** (privacy laws) is hard in an immutable log. Use crypto-shredding: encrypt personal fields with a
  per-user key and delete the key.
- **A learning curve** and more moving parts. It's overkill for simple CRUD.

## When to use it

| Good fit | Poor fit |
|----------|----------|
| Ledgers, payments, inventory movements | Simple CRUD admin screens |
| Domains where history and audit matter | Data nobody will ever replay |
| Complex workflows with many state transitions | Teams new to the pattern, on a deadline |

You can apply it to **one** part of a system (the ledger) and keep plain CRUD elsewhere.

## Try it

An inventory system stores `stock = 37` per item. Operations ask "why did item 9 go negative last Tuesday?" and nobody
can tell. How would event sourcing help, and what would the events be?

<details>
<summary>Answer</summary>

Store movements instead of totals: `Received(+50, po=…)`, `Reserved(−3, order=…)`, `Released(+3)`, `Shipped(−2)`,
`Adjusted(−1, reason=damaged, by=…)`. The stock level is the sum. Replaying item 9's events for last Tuesday shows the
exact sequence (say, a double `Shipped` from a non-idempotent consumer) that drove it negative.
</details>

## Key takeaways

- Event sourcing stores immutable events as the truth; state is derived by replay.
- You get audit, time travel and new projections from history.
- Use optimistic concurrency per aggregate, and snapshots for long histories.
- Querying, event versioning and deletion need extra design, so use it where history matters.

# Stream processing

Batch jobs answer "what happened yesterday?" Stream processors answer "what is happening **right now**?": clicks per
minute, fraud signals within seconds, live leaderboards. They compute continuously over unbounded event streams.

Common engines: **Apache Flink**, **Kafka Streams**, **Spark Structured Streaming**, and managed services such as
Kinesis Analytics or Dataflow.

## Stateless vs stateful

- **Stateless:** each event on its own: filter, map, enrich from a static table. Easy to scale.
- **Stateful:** remember things across events: counts, sums, joins, "has this user done X before?". Needs durable,
  partitioned state and checkpoints.

## Windows

To count "per minute", you must decide which events belong to which minute.

| Window | Shape | Example |
|--------|-------|---------|
| **Tumbling** | Fixed, non-overlapping | Clicks per minute: 10:00–10:01, 10:01–10:02 |
| **Hopping / sliding** | Fixed size, overlapping | Last 5 minutes, updated every 1 minute |
| **Session** | Gaps of inactivity close the window | A user's browsing session (30 min idle ends it) |

## Event time vs processing time

- **Processing time:** when the processor sees the event.
- **Event time:** when it actually happened (a timestamp in the event).

Phones go offline and upload events minutes later; partitions lag. If you window by processing time, late events land
in the wrong minute. **Window by event time.**

## Watermarks and late events

A **watermark** is the processor's estimate that "events before time T have (probably) all arrived". When the
watermark passes the end of a window, the window's result is emitted.

```
window 10:00–10:01 closes when the watermark reaches 10:01 (+ allowed lateness, say 2 min)
an event for 10:00:30 arriving at 10:05 → too late: drop it, send it to a side output, or update the result
```

That's the tradeoff: wait longer for completeness, or emit sooner for freshness.

## State and fault tolerance

Stateful operators keep state (counts per key) locally, partitioned like the input. Periodic **checkpoints** snapshot
state plus input offsets to durable storage. After a crash, the job restores the checkpoint and replays from those
offsets. With transactional sinks, that gives exactly-once results (lesson 15.4).

## Joins

- **Stream–table:** enrich clicks with the current product category (the table comes from a compacted topic or CDC).
- **Stream–stream:** match `AdShown` with `AdClicked` within 10 minutes (windowed join).

## Try it

You need "orders per city per minute" for a live dashboard. Mobile orders can arrive up to 3 minutes late. Results
must be shown within 10 s of each minute ending, and corrected if late orders come in. Design the window and lateness
handling.

<details>
<summary>Answer</summary>

**Tumbling 1-minute windows on event time**, keyed by city. Watermark = max event time seen − ~5 s, so a result is
emitted ~10 s after the minute ends. **Allowed lateness of 3 minutes**: late events update the window's result and
emit a correction (the dashboard upserts by (city, minute)). Events later than that go to a side output for the
nightly batch reconciliation.
</details>

## Key takeaways

- Stream processors compute continuously over unbounded data.
- Windows (tumbling, sliding, session) group events in time; use event time, not processing time.
- Watermarks decide when a window is complete; allowed lateness trades freshness for completeness.
- Checkpointed state plus replayable inputs give fault tolerance and exactly-once results.

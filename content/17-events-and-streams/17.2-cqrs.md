# CQRS

**Command Query Responsibility Segregation** means using **different models for writing and reading**. The write side
is shaped to enforce rules; read sides are shaped to answer specific queries fast.

```
commands ──▶ write model (normalised, validated, transactional) ──events──▶ projector(s)
                                                                        ├─▶ read model A: "order list" (denormalised table)
queries  ◀──────────────────────────────────────────────────────────────┼─▶ read model B: search index
                                                                        └─▶ read model C: dashboard aggregates
```

## Why separate them?

Reads and writes want different things:

| | Writes | Reads |
|-|--------|-------|
| Shape | Normalised, one fact in one place | Denormalised, ready to display |
| Concern | Invariants, transactions | Speed, filtering, sorting |
| Volume | Often lower | Often 10–1000x higher |
| Scaling | Vertically, carefully | Horizontally, with cheap copies |

A single model forced to do both ends up with slow joins for reads, or awkward denormalised writes.

## Read models (projections)

A **projector** consumes change events and updates a read model:

```python
def on_order_placed(e):
    db.upsert("order_summaries", id=e.order_id, customer=e.customer_name,
              total=e.total, status="placed", placed_at=e.at)

def on_order_shipped(e):
    db.update("order_summaries", id=e.order_id, status="shipped")
```

- Each read model serves one screen or API and can live in the best store for it (Postgres table, Elasticsearch,
  Redis, a warehouse).
- Read models are **disposable**: delete one and rebuild it by replaying events (lesson 17.1) or the change stream
  (lesson 17.3).
- Projectors must be **idempotent** and process events **in order per entity**.

## Eventual consistency in the UI

Read models lag the write side by milliseconds to seconds. After a user submits a command:
- return the new state directly from the command response; or
- show "processing…" until the read model catches up (track the event version); or
- route this user's next read to the write model (read-your-writes).

## When CQRS is worth it

- Read and write workloads differ a lot in shape or scale.
- Several very different read views of the same data (list, search, analytics).
- Combined with event sourcing (where you *need* projections to query).

It's overkill for straightforward CRUD, where one model with a few indexes is simpler and consistent.

## Try it

An admin dashboard shows "revenue by city by hour" over 200M orders. The query takes 40 s on the main database and
slows checkout. Design a CQRS read model.

<details>
<summary>Answer</summary>

A projector consumes `OrderPaid`/`OrderRefunded` events and incrementally updates
`revenue_by_city_hour(city, hour, revenue, orders)`, using upserts that add or subtract, deduplicated by event id, in
a separate database or warehouse. The dashboard reads that small table in milliseconds; checkout's database never runs
the heavy query. Lag of a few seconds is fine for a dashboard.
</details>

## Key takeaways

- CQRS uses separate models for commands (rules) and queries (speed).
- Projectors build read models from events; read models are disposable and rebuildable.
- Read models are eventually consistent; design the UI for the lag.
- Use it when read and write needs diverge; skip it for simple CRUD.

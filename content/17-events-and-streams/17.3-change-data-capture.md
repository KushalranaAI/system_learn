# Change data capture

Your Postgres database already records every change: it's in the write-ahead log (WAL). **Change data capture (CDC)**
reads that log and turns every insert, update and delete into a stream of events. Other systems can then stay in sync
without the application doing dual writes.

```
app ──▶ Postgres ──WAL──▶ CDC connector (Debezium) ──▶ Kafka topics ──▶ search index
                                                                   ├─▶ cache invalidation
                                                                   ├─▶ data warehouse
                                                                   └─▶ other services
```

## What a CDC event looks like

```json
{ "op": "u", "table": "products", "ts_ms": 1793000000000,
  "before": { "id": 42, "price": 999 },
  "after":  { "id": 42, "price": 799 },
  "source": { "lsn": "0/16B3748", "txId": 9817 } }
```

Every committed change, **in commit order**, with before/after values and its position in the log.

## Why CDC beats dual writes

| Approach | Problem |
|----------|---------|
| App writes to DB, then to the search index | Crash in between → index out of sync forever |
| App writes to both "at once" | No shared transaction; partial failures |
| Nightly batch export | Hours stale; heavy load |
| **CDC** | Captures exactly what committed, in order, with seconds of lag, and no app changes |

The outbox pattern (lesson 16.4) is often implemented *with* CDC: the connector streams only the outbox table, so you
publish deliberate domain events instead of raw table changes.

## Uses

- **Search indexes and caches** that stay in sync (invalidate `product:42` when its row changes, lesson 3.5).
- **Data warehouse / lake** loading in near real time.
- **Service migration:** stream a monolith's tables to a new service while you move traffic.
- **Audit logs** of every change.
- **Zero-downtime database migrations:** copy, then stream changes until cut-over (lesson 9.4).

## Things to watch

- **Raw table events are an internal schema.** Exposing them couples consumers to your tables. Prefer the outbox (or
  transform the events) for cross-team contracts.
- **Initial snapshot:** connectors first snapshot existing rows, then stream. Plan for the load.
- **Log retention:** if the connector falls behind and the database discards old WAL, you must re-snapshot. Monitor
  the replication slot lag (in Postgres, an unconsumed slot also makes WAL pile up on disk).
- **Schema changes** flow through. Use a schema registry and compatible changes.

## Try it

The product catalogue is in Postgres; search runs on OpenSearch. Today the app updates both, and searches sometimes
show old prices. Redesign the sync.

<details>
<summary>Answer</summary>

Stop writing to OpenSearch from the app. A CDC connector streams `products` changes (or outbox `ProductChanged`
events) to Kafka; an indexer consumes them in order per product id and upserts documents, idempotently and keyed by id
with a version check to ignore older events. Search lags by seconds, never drifts permanently, and a full reindex is a
replay.
</details>

## Key takeaways

- CDC turns the database's log into an ordered stream of committed changes.
- It keeps search, caches, warehouses and other services in sync without dual writes.
- Prefer outbox events over raw table changes for cross-team contracts.
- Monitor connector lag and log retention; plan the initial snapshot.

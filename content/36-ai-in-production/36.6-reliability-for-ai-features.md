# Reliability for AI features

A model API is a dependency with unusual properties: responses take seconds, not milliseconds; latency varies 10×
with output length; capacity is shared with every other customer; and it **does go down**. On 11 December 2024, all
OpenAI services were badly degraded or unavailable for about four hours (a telemetry rollout overloaded their
Kubernetes control planes, lesson [37.1](#/lesson/37.1)). Every product built on one provider went down with it,
unless it was designed not to.

Everything from module 12 applies. This lesson is what's different.

## Timeouts for slow, streaming calls

One timeout isn't enough for a call that streams for 20 seconds:

| Timeout | Typical value | Catches |
|---------|---------------|---------|
| Connect | 1-2 s | Provider unreachable |
| **Time to first token** | 2-5× normal TTFT (e.g. 5 s) | Overloaded queue at the provider |
| **Inter-token stall** | 5-10 s with no new token | Stream hung mid-answer |
| Total | Based on max output (e.g. 60 s) | Runaway generation |
| Task deadline (agents) | Minutes | Loops; see [lesson 35.8](#/lesson/35.8) |

A TTFT timeout is the most useful: it fails over **before** the user has seen any output, so a retry elsewhere is
invisible. After tokens have streamed, retrying means restarting the answer on screen.

## Rate limits

Providers limit **requests per minute and tokens per minute** per account and model. Treat 429s as normal:
- Honour `retry-after`; back off with jitter ([lesson 12.2](#/lesson/12.2)).
- **Enforce your own limits first**, per user and tenant (tokens, not just requests), so one heavy customer can't
  use the whole account quota. Classic token buckets, counting tokens ([lesson 8.2](#/lesson/8.2)).
- **Priority queues:** interactive traffic first; batch and background work waits or goes to batch APIs.
- Spread across **several accounts, regions or deployments** of the same model (e.g. the provider's API plus the
  same model on a cloud platform).

## Provider failover

Put a **model gateway** ([lesson 33.4](#/lesson/33.4)) between your app and providers:

```
app ─► gateway ─┬─► primary: provider A, model X        (circuit breaker, health)
                ├─► secondary: provider A, other region/deployment
                ├─► tertiary: provider B, comparable model
                └─► last resort: self-hosted small model / degraded mode
```

What makes failover real rather than a diagram:
- **Prompts tested on the fallback model.** A prompt tuned for one model can behave differently on another; run the
  eval suite ([lesson 36.1](#/lesson/36.1)) against every fallback, regularly.
- **Tool-call format differences** abstracted in the gateway.
- **Circuit breakers** ([lesson 12.3](#/lesson/12.3)) on error rate *and* on TTFT, so you stop sending traffic into a slow provider.
- **Capacity on the fallback:** if everyone fails over to provider B at once, B rate-limits you. Pre-arrange quota.
- **Data rules:** the fallback must be allowed by your data-processing agreements and residency rules ([lesson 36.7](#/lesson/36.7)).

## Degraded modes

Decide, per feature, what happens when no model is available. This is product design, done in advance:

| Feature | Degraded mode |
|---------|---------------|
| Support chat | Show help-centre search results (plain BM25) + "contact us" form; queue for humans |
| Writing assistant | Hide the button, editor works normally |
| Search with AI summary | Show classic search results without the summary |
| Code completion | Fall back to local, non-AI completion |
| Agent running a long task | Pause (durable state, [lesson 35.6](#/lesson/35.6)), resume when the provider is back |

The core product must work without the AI feature. A checkout page that calls an LLM synchronously to "personalise"
it has made the LLM provider part of checkout's availability.

## Caches as a shield

Response and semantic caches ([lesson 33.5](#/lesson/33.5)) keep answering popular questions during an outage, as a CDN keeps
serving stale pages (`stale-if-error`). For a support bot, the top 500 questions may be half the traffic.

## Overload on self-hosted models

If you serve models yourself, GPUs are expensive, so you run them hot. Admission control matters: cap queue length
per replica and reject early ([lesson 7.6](#/lesson/7.6)) instead of letting TTFT grow to 30 s for everyone. Shed low-priority traffic
first.

## Try it

Your support assistant uses one provider's large model. Design it to stay useful during a 4-hour provider outage.

<details>
<summary>Reference</summary>

- **Gateway** with TTFT timeout (5 s), circuit breaker per provider/model, and a fallback chain: same provider other
  region → comparable model at a second provider (prompts and tools evaluated against it weekly, quota pre-arranged)
  → self-hosted small model for FAQ-type questions.
- **Semantic + exact caches** for top questions, served even when stale.
- **Degraded mode:** if all models fail, the widget switches to help-article search and offers a ticket form; the
  status is shown honestly ("our assistant is limited right now").
- **Agents and actions:** pending refund workflows pause durably and resume.
- **Protect the fallback:** per-tenant token limits and priority for interactive traffic; batch jobs stop.
- **Test it:** a game day that blocks the primary provider in staging ([lesson 18.6](#/lesson/18.6)).
</details>

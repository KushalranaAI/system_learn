# Cloudflare, Jul 2019: one regular expression

On 2 July 2019 a single new rule in Cloudflare's Web Application Firewall (WAF) pushed CPUs across the whole network
to nearly 100%. For 27 minutes sites behind Cloudflare returned 502 errors, and Cloudflare lost about 80% of its
traffic. The rule was a regular expression that backtracked catastrophically, and it went to every server at once.

## What users saw

- "502 Bad Gateway" pages on Cloudflare-proxied sites worldwide.
- Customers couldn't reach the Cloudflare dashboard or API to change anything, because both run through the same edge.

## Timeline (UTC)

| Time | Event |
|------|-------|
| 13:31 | Engineer merges a pull request with new XSS detection rules |
| 13:37 | CI builds the rules; tests pass |
| 13:42 | Rules deployed globally through the normal automated process |
| 13:45 | First page: WAF fault. Many more alerts follow |
| 14:00 | WAF identified as the cause; attack ruled out |
| 14:02 | Team proposes a "global terminate" of the WAF |
| 14:07 | Global WAF kill executed |
| 14:09 | Traffic and CPU back to normal worldwide |
| 14:52 | WAF re-enabled globally after testing in one city |

## The trigger

The new rule was meant to run in **simulate mode**: it would log matches but block nothing. Simulate mode still runs
the regex on every request, so it still uses CPU. The dangerous part of the pattern was:

```
.*(?:.*=.*)
```

Two greedy `.*` in a row followed by `=`. When a string doesn't match, the engine tries every way to split the input
between the first `.*` and the second before giving up. Cloudflare's post counts the steps for the simplified
`.*.*=.*` (the real rule also had a `;` after it, which made it far worse):

| Input | Steps |
|-------|-------|
| `x=x` | 23 |
| `x=` + 20 x's | 555 |
| 20 x's, no `=` | 4,067 |
| `x=` + 20 x's, with the trailing `;` | 5,353 |

The work grows much faster than the input (polynomially for this pattern), and request fields can be long. Every core on every server was
busy running one regex.

## Why it spread

```
PR merged ─► CI tests (functional only, no CPU check) ─► WAF rule SOP: deploy globally
                                                             │ Quicksilver: changes reach
                                                             │ every server in seconds
                                                             ▼
                        every edge server runs the regex on HTTP traffic ─► CPU ~100%
                                                             │
                                  502s ◄─ proxy can't reach the overloaded process
```

- **Global by design.** Normal software went through staged PoPs (DOG, PIG, then Canary). WAF rules skipped all of
  that, deliberately, so Cloudflare could respond to new attacks within minutes.
- **A safety net had been removed.** A protection against regexes using too much CPU had been taken out by mistake
  weeks earlier, during a refactor meant to make the WAF use *less* CPU.
- **Tests checked correctness, not cost.** The rule did what it was supposed to do; nobody measured how long it took.

## Why recovery took as long as it did

27 minutes is fast for a global outage, but the post explains what slowed even that:

- Cloudflare's own internal tools sat behind Cloudflare Access, which was down. Some engineers' credentials had
  expired under an inactivity rule.
- Jira and the build system needed a rarely used **bypass** that people hadn't practised.
- Once identified, the global WAF kill switch worked within two minutes. Having it at all is why this was 27 minutes
  and not hours.

## What Cloudflare changed

- Restored the CPU protection that had been removed.
- Manually checked all 3,868 WAF managed rules for dangerous backtracking.
- Added performance profiling of every rule to the test suite.
- Planned a move to a regex engine with run-time guarantees (re2 or the Rust regex crate), which can't backtrack
  exponentially.
- Changed the procedure so WAF rules go through **staged rollouts**, keeping an emergency global path for active
  attacks only.
- Built a way to take the dashboard and API off the edge in an emergency, and automated status page updates.

## The general lesson

- **Global push is a loaded gun.** Fast global config is a real feature (you want new attack rules everywhere
  quickly), but it needs a staged default and an emergency path that is used rarely. Try the
  [staged rollout simulation](#/sims/staged-rollout).
- **Test the cost, not just the result.** A rule, query or regex can be correct and still too expensive. Put CPU time
  or step budgets in CI.
- **Use bounded engines for untrusted input.** Linear-time regex engines (RE2, Rust `regex`) remove this whole class.
- **Don't route your recovery tools through the thing that's broken.** The same lesson returns in Facebook 2021
  (31.7) and Roblox 2021 (31.10).
- **Kill switches pay for themselves.** One switch turned a potential multi-hour outage into a 27-minute one.

Six years later Cloudflare's November 2025 outage (lesson 31.2) followed a similar path: a non-code change pushed
quickly to every server.

## Try it

Spot a dangerous regex. Which of these could backtrack badly on a long, non-matching input, and how would you fix it?

1. `^[a-z0-9]+$`
2. `^(a+)+$`
3. `.*.*=.*`
4. `^\d{3}-\d{4}$`

<details>
<summary>Reference</summary>

- **1** is safe: one quantifier, one way to match each character.
- **2** is the classic catastrophic case: nested quantifiers give exponentially many ways to split `aaaa…aX`.
  Rewrite as `^a+$`.
- **3** is the Cloudflare pattern: adjacent `.*` give polynomial blow-up on long input without a match. Rewrite to
  something specific, such as `[^=]*=.*`, so there is only one way to split.
- **4** is safe: fixed lengths.

Whatever the pattern, run untrusted input through a linear-time engine (RE2, Rust `regex`, Go `regexp`) and give
each rule a CPU time budget in tests.
</details>

# Google Cloud, Jun 2025: a null pointer everywhere

On 12 June 2025, Google Cloud APIs failed with 503 errors in regions around the world, taking down or degrading
dozens of Google Cloud and Workspace products for about three hours, and some for longer. A new code path in
**Service Control**, the system that checks every API request against policy and quota, had shipped two weeks
earlier with no feature flag and no error handling. A policy record with blank fields reached it in every region
within seconds, and the binary crashed on a null pointer, over and over.

## What users saw

- 503 errors from Google Cloud APIs in many regions: IAM, Cloud Storage, BigQuery, Compute Engine, Cloud Run and
  many more; Workspace products such as Gmail, Drive and Meet were also affected.
- Existing running resources (VMs, streams) kept working. Calls to *manage* or *use* services through APIs failed.
- Google's own status dashboard took about an hour to post anything, because it was affected too. Some customers'
  monitoring, which ran on Google Cloud, also went quiet.

## Timeline (PDT)

| Time | Event |
|------|-------|
| 29 May | New quota policy check added to Service Control; rolled out region by region. Code path not exercised yet |
| 12 Jun, ~10:45 | A policy change with unintended blank fields is written to the regional Spanner tables |
| seconds later | The data replicates to every region; Service Control crashes on a null pointer everywhere |
| 10:49–10:51 | API errors start worldwide |

| +10 min | Root cause found; "red button" to disable the serving path being prepared |
| +25 min | Red button ready to roll out |
| +40 min | Red button rolled out everywhere; smaller regions start recovering |
| ~11:46 | First post on the Cloud Service Health dashboard |
| up to ~2 h 40 min | us-central1 recovers last, slowed by a herd effect on Spanner |
| 18:18 | Last affected product (Vertex AI Online Prediction) fully recovered |

## The trigger

Service Control sits in the request path of Google Cloud APIs: for each call it checks authorisation, policy and
quota. On 29 May a new feature added extra quota policy checks. The code that read the new policy data had **no
error handling for blank fields** and was **not behind a feature flag**. Because no policy used the feature yet, the
code path never ran during the staged rollout of the binary, so the staged rollout proved nothing about it.

On 12 June someone inserted a policy that did use it, with blank fields.

## Why it spread

```
29 May: binary with new code path ──► staged region-by-region rollout ──► all regions
                                         (path never executed, so nothing to see)

12 Jun: policy with blank fields ──► Spanner ──► replicated globally in seconds
                                                     │
                                ┌────────────────────┼────────────────────┐
                                ▼                    ▼                    ▼
                         Service Control      Service Control      Service Control
                         (us-central1)        (europe-west1)       (asia-...)
                         null pointer ─► crash ─► restart ─► read policy ─► crash  (loop)
                                                     │
                                                     ▼
                                    every API request needing a policy check ──► 503
```

The code was rolled out in stages. The **data** wasn't: policy metadata was designed to replicate globally within
seconds, so it hit every region at once. A staged code rollout can't protect you from a global data push that
activates the code later.

## Why recovery took as long as it did

- **The fix was fast.** Root cause in 10 minutes, red button rolled out in 40.
- **us-central1 took up to about 2 h 40 min.** As Service Control tasks restarted, they all hit the same Spanner
  table at once. Service Control **didn't have randomised exponential backoff**, so the restarts formed a herd that
  overloaded the database. Engineers had to throttle task creation and route load to multi-regional databases.
- **Downstream products** had their own backlogs and restarts, so some took hours more.
- **Communication lagged.** The status dashboard ran on affected infrastructure, so the first post came about an hour
  in.

## What Google changed

From the incident report:

- Modularise Service Control so that a failing check **fails open** instead of blocking API requests.
- Audit systems that consume **globally replicated data**, and propagate changes incrementally with time to validate.
- **Require feature flags**, off by default, for new code in critical binaries.
- Improve static analysis and testing for error handling.
- Audit all systems for **randomised exponential backoff**.
- Keep monitoring and communication infrastructure running during outages; improve automated and human communication.
- Freeze changes to Service Control and manual policy pushes until this is done.

## The general lesson

- **Gate new code paths behind a flag, off by default.** Turning the flag on gradually (per region, per percent) is
  the staged rollout for the *behaviour*; the binary rollout only stages the bits. See the
  [staged rollout simulation](#/sims/staged-rollout).
- **Globally replicated data is a global push.** Config, policy and metadata need stages too (Cloudflare 2025,
  [lesson 31.2](#/lesson/31.2); CrowdStrike, [lesson 31.4](#/lesson/31.4)).
- **Handle bad input without crashing.** Skip the bad record, log it, keep serving with the last good policy.
- **Decide fail-open vs fail-closed per check.** For a quota check, briefly allowing requests is better than
  rejecting all of them. For an authorisation check, it may not be.
- **Restarts need jitter.** Thousands of tasks restarting together are a thundering herd on their dependencies
  ([lesson 12.2](#/lesson/12.2), [lesson 3.6](#/lesson/3.6)).
- **Keep your status page off your own stack** (S3 2017, [lesson 31.6](#/lesson/31.6)).

## Try it

Gate a new code path behind a flag. You're adding a new rule type to an API gateway's policy engine; rules are stored
in a globally replicated database. Write how the new code should be shipped and turned on, and what it should do with
a malformed rule.

<details>
<summary>Reference</summary>

1. **Ship dark:** the new code is in the binary, but a flag `new_rule_type_enabled` defaults to **off**. While off,
   rules of the new type are ignored (and logged).
2. **Turn on gradually:** enable the flag in one small region, then a few percent of traffic per region, then more,
   watching crash rate, error rate and latency at each step. One switch turns it off everywhere in seconds.
3. **Validate data on write:** the API that writes rules rejects missing or blank required fields.
4. **Defend on read:** if a rule is malformed, skip it, increment a metric, alert, and keep using the last good rule
   set. Never crash the serving process on bad data.
5. **Fail mode:** if the policy engine itself errors, fail **open** for quota-like checks and **closed** for
   authorisation, chosen per rule type.
6. **Restart safety:** on startup, load policy with jittered exponential backoff so a fleet restart doesn't stampede
   the database.
</details>

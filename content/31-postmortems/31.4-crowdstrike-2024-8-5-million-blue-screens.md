# CrowdStrike, Jul 2024: 8.5 million blue screens

On 19 July 2024 a security content update from CrowdStrike crashed about **8.5 million Windows machines** (Microsoft's
estimate). Airlines grounded flights, hospitals and banks went to paper, and shop tills showed blue screens. The bad
file was live for only 78 minutes, but fixing the machines took days, because most needed a person at the keyboard.

## What users saw

- Windows PCs and servers running the CrowdStrike Falcon sensor crashed with a blue screen (BSOD), rebooted, and
  crashed again while booting.
- Mac and Linux machines were not affected. Neither were Windows machines that were offline during the window.

## Timeline (UTC)

| Time | Event |
|------|-------|
| Feb 2024 | Sensor 7.11 ships a new IPC Template Type (detects attacks that abuse named pipes) |
| 5 Mar–24 Apr 2024 | First four IPC Template Instances deployed in Channel File 291; no problems |
| 19 Jul, 04:09 | Two new IPC Template Instances released in a new version of Channel File 291 |
| 04:09 onwards | Windows hosts that receive it crash and boot-loop |
| 05:27 | CrowdStrike reverts the channel file |
| 19 Jul onwards | Manual recovery: boot into safe mode or recovery, delete the bad file, reboot |
| 29 Jul | About 99% of Windows sensors back online compared to before the update |

Only machines that were online between 04:09 and 05:27 UTC got the bad file.

## The trigger

Falcon has two kinds of update:

- **Sensor content:** code, shipped as sensor versions that customers can stage (N, N-1, N-2).
- **Rapid Response Content:** data files ("channel files") pushed from the cloud, often several times a day, so new
  attack patterns can be detected without a code release. Customers could not stage these.

The IPC Template Type **defined 21 input fields**, but the sensor code that called the Content Interpreter **supplied
only 20 values**. For months nobody noticed, because every template instance, in tests and in the field, used a
**wildcard** for the 21st field, so the interpreter never actually read it.

On 19 July one new instance used a **non-wildcard** match on field 21. The Content Validator checked it against the
definition (21 fields) and passed it. On the machine, the interpreter tried to read the 21st entry of a 20-entry array:
an out-of-bounds read, inside a **kernel driver**. In the kernel, that crashes the whole operating system.

```
Template Type definition: 21 fields ──► Content Validator: "21 fields, looks fine" ✔
Sensor code at runtime:   20 values ──► Interpreter reads value[20] ──► out of bounds ──► BSOD
```

## Why it spread

```
CrowdStrike cloud ──► channel file 291 (data, not code)
      │  same file to every online Windows sensor, no canary, no customer staging
      ▼
 millions of hosts ──► kernel driver reads it on next IPC event ──► crash
                   └─► reboot ──► driver loads the file early in boot ──► crash again
```

- **No staged rollout for content.** The file went to all customers at once. Customers who carefully ran sensor N-1
  got it too, because staging only applied to code.
- **Kernel blast radius.** A bug in a normal app kills the app. A bug in a kernel driver kills the machine.
- **The fault survives a reboot.** The driver loads at boot, reads the same file and crashes again before the machine
  can download the fix.

## Why recovery took as long as it did

The fix was published 78 minutes after release. But a boot-looping machine can't receive it:

- Each machine needed someone to boot into Safe Mode or the Windows Recovery Environment and **delete the bad channel
  file** (`C-00000291*.sys`).
- Many corporate machines use **BitLocker** disk encryption, so each needed its recovery key, often stored on servers
  that were themselves blue-screening.
- Some machines recovered by rebooting many times, if the network won the race and the fix downloaded before the crash.
- Cloud VMs needed their disks detached and repaired from another VM.

Rollback speed doesn't matter when the rollback can't reach the patient.

## What CrowdStrike changed

From its Root Cause Analysis (6 August 2024):

- Validate the number of input fields at **sensor compile time**.
- Add **runtime bounds checks** in the Content Interpreter, and check that the input array size matches what content
  expects.
- Test every Template Type with non-wildcard criteria in every field; fuzz the interpreter.
- Fix the Content Validator and test instances inside the real interpreter, not just against the definition.
- **Staged deployment** of Rapid Response Content: canary rings first, watching sensor health, then wider.
- **Customer control** over when content updates are deployed, as they already had for sensor versions.

## The general lesson

- **Config and content are code.** If a data file can crash the program, it needs the same staged rollout as code.
  Try the [staged rollout simulation](#/sims/staged-rollout).
- **A canary would have caught it in minutes.** Every machine that loaded the file crashed. Even 1% of machines for
  15 minutes would have shown a 100% crash rate.
- **Validate where you execute.** The validator checked the file against the definition; the crash happened in the
  real interpreter with real inputs. Test in the real execution path.
- **Never trust input in privileged code.** Bounds-check everything in kernels, proxies and other places where a crash
  takes everything with it.
- **Design recovery for a machine that can't help itself.** Last-known-good fallbacks (skip content that crashed the
  previous boot) would have let machines heal themselves.

## Try it

Design a staged rollout for agent updates. You ship a detection data file to 10 million endpoints at customers in
every industry. New attack patterns need to reach everyone within a few hours. Write the rings, the health signal
and the rules for stopping.

<details>
<summary>Reference</summary>

| Ring | Who | Size | Soak |
|------|-----|------|------|
| 0 | Your own company's machines | ~5,000 | 15 min |
| 1 | Early-adopter customers who opted in | ~1% | 30 min |
| 2 | Wider canary across OS versions and regions | ~10% | 30 min |
| 3 | Everyone else, unless the customer chose "delay by N hours" | 100% | n/a |

- **Health signal:** agents send a heartbeat after loading new content. Count crashes, boot loops (an agent that
  restarts and loses heartbeat), CPU and memory, against the previous version.
- **Stop rules:** any rise in crash rate halts the rollout automatically and reverts that ring; no human needed.
- **On the endpoint:** if the last boot crashed after loading content version X, skip X and use the last known-good.
- **Emergency path:** for an active in-the-wild attack, a faster schedule (minutes per ring), but never skip ring 0.

That gets full coverage in about 90 minutes, and a bug like Channel File 291 stops at ring 0.
</details>

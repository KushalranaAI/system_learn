# AWS S3, Feb 2017: one mistyped command

On 28 February 2017 Amazon S3 in us-east-1 stopped serving requests for about four hours. An engineer debugging a
billing problem ran an approved playbook command to remove a few servers, typed one input wrong, and removed far more
than intended, including servers behind S3's core index. Restarting the index took hours because it hadn't been
restarted from cold in years. And AWS's own status page couldn't say so, because it depended on S3.

## What users saw

- Websites and apps that kept images, files or whole static sites in S3 broke or loaded without assets.
- Other AWS services in the region that use S3 (for example new EC2 launches, EBS volumes restored from snapshots,
  and Lambda) were impaired.
- For the first two hours AWS couldn't update individual services on its Service Health Dashboard. Updates came
  through Twitter and a banner at the top of the dashboard instead.

## Timeline (PST)

| Time | Event |
|------|-------|
| 09:37 | Command run to remove a small number of servers from a billing subsystem; wrong input removes many more |
| 09:37 | Index and placement subsystems lose too much capacity; both must be fully restarted |
| 09:37 onwards | S3 GET, LIST, PUT and DELETE requests fail in us-east-1 |
| 11:37 | Service Health Dashboard able to show individual service status again |
| 12:26 | Index partially back: GET, LIST and DELETE working |
| 13:18 | Index fully recovered |
| 13:54 | Placement subsystem recovered; PUTs work; S3 back to normal |

About 4 hours 17 minutes from the command to full recovery.

## The trigger

The S3 team was debugging slowness in the billing system. Following an established playbook, an authorised engineer
ran a command meant to take a small number of servers out of a billing-related subsystem. One input was entered
incorrectly, and a much larger set of servers was removed. Some of them belonged to two critical subsystems:

- **Index:** the metadata and location of every object in the region. Needed for every GET, LIST, PUT and DELETE.
- **Placement:** decides where to store new objects. Needs the index to work.

## Why it spread

```
ops tool: "remove N servers"  ── typo ──► removes far more than N
                                            │  no minimum-capacity check, removed all at once
                                            ▼
   index subsystem below the capacity it needs ──► must fully restart
           │                                           │
           ▼                                           ▼
   all S3 reads/lists/deletes fail          placement (needs index) fails ──► all PUTs fail
           │
           ├─► customer sites and apps on S3
           ├─► AWS services in the region that use S3
           └─► Service Health Dashboard admin console (depends on S3) ──► status page can't be updated
```

The tool did exactly what it was told. It had no idea that "remove this many" would take a subsystem below the
minimum it needs to run.

## Why recovery took as long as it did

- **Cold restarts nobody had practised.** AWS hadn't fully restarted the index or placement subsystems in its larger
  regions **for many years**. S3 had grown enormously in that time.
- **Safety checks at scale.** On restart, the index validates the integrity of its metadata. With that much metadata,
  the checks took far longer than expected.
- **Ordering.** Placement could only start after the index worked, so the two recoveries ran one after the other.

The system was designed to survive losing *some* capacity, and it did that well every day. It was not designed, or
tested, for coming back from losing most of it.

## What AWS changed

- The capacity-removal tool now removes capacity **more slowly**.
- It **refuses** to remove capacity if that would take any subsystem below its **minimum required capacity**.
- Other operational tools were audited for the same kind of safety checks.
- The index subsystem is partitioned into smaller **cells**, so a failure hits less and a restart is faster. AWS
  moved this work up to start immediately.
- The status page's admin console now runs across **multiple regions**.

## The general lesson

- **Make the tool safe, not the human perfect.** People will mistype. Tools that do destructive things need limits
  (never below minimum capacity), rate limits (remove slowly) and a preview of what they will do. This is blameless
  thinking in practice ([lesson 31.1](#/lesson/31.1)).
- **Practise cold start.** "We've never restarted it" means "we don't know how long a restart takes." Rehearse it in
  game days ([lesson 18.6](#/lesson/18.6)).
- **Cells shrink blast radius and recovery time.** A smaller index cell restarts faster and fails alone. Compare
  Shopify's pods ([lesson 30.9](#/lesson/30.9)) and DynamoDB's design ([lesson 30.11](#/lesson/30.11)).
- **Your status page must not depend on what it reports on.** Host it on separate infrastructure, in another region or
  provider. Cloudflare (31.3), Google Cloud (31.13) and Slack (31.12) all hit versions of this.
- **Storage is a dependency of everything.** Object storage ([lesson 29.1](#/lesson/29.1)) sits under images, builds,
  logs, backups and other cloud services.

## Try it

Add safety limits to an ops tool. You maintain `drain-hosts --service=<name> --count=<n>`, which takes hosts out of
service. Write the checks it should run before and during removal.

<details>
<summary>Reference</summary>

Before acting:
- **Show the plan:** list the exact hosts and ask for confirmation, with a `--dry-run` default.
- **Minimum capacity:** refuse if remaining healthy hosts would drop below the service's declared minimum (for
  example, enough to serve peak load with one zone down).
- **Size limit:** refuse to remove more than, say, 5% of a service at once without a second approver.
- **Scope check:** every host must belong to `--service`; refuse if any belongs to another service.

While acting:
- **Remove slowly**, in batches, waiting for health and load to settle between batches.
- **Stop automatically** if error rate or latency rises.

After:
- Log who removed what, so a mistake is quick to see and undo.
</details>

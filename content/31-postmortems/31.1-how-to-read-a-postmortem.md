# How to read a postmortem

Big companies publish detailed write-ups when their systems fail. They are the cheapest education in system design
you will ever get: someone else paid for the outage, and you get the lessons for free. This module walks through
thirteen of them. This first lesson is about how to read one without missing the point.

## Blameless culture

A postmortem asks **"what in the system allowed this to happen?"**, not **"who did it?"**

- People make mistakes at a steady rate. If a single typo can take down a region (lesson 31.6), the problem is the
  tool that accepted the typo, not the person who typed it.
- If people are punished for honest mistakes, they hide them. Hidden mistakes can't be fixed, and the next outage is
  worse.
- Blameless doesn't mean nobody is accountable. Teams are accountable for the **action items**: the guard rails,
  tests and alarms that make the same mistake harmless next time.

A good test: after reading the postmortem, could a different engineer have made the same mistake on the same day?
Almost always the answer is yes, and that's why the fix has to be in the system.

## The parts of a postmortem

| Section | What it tells you | What to look for |
|---------|-------------------|------------------|
| Summary | What broke, for whom, how long | Scope: one service, one region, or everything? |
| Impact | Users affected, error rates, data lost | Numbers, not adjectives |
| Timeline | What happened, minute by minute | Gaps: where did time go? |
| Root cause | Why it happened | Is it a chain, or just "human error"? |
| Recovery | How service came back | Why it took hours, not minutes |
| Action items | What will change | Do they fix the class of problem or just this instance? |

## Trigger vs root cause vs contributing factors

These three words get mixed up. Separating them is the single most useful reading skill.

- **Trigger:** the event that started it. Often small and ordinary: a config push, a command, a database permission
  change, a customer's valid settings.
- **Root cause:** the latent weakness that let the trigger do damage. It usually existed for weeks or years before.
- **Contributing factors:** things that made it bigger or longer: no staged rollout, monitoring that depended on the
  broken system, retries that piled on, a recovery path never tested.

Example, Cloudflare in November 2025 (lesson 31.2):

```
trigger:      a database permission change (routine, reviewed)
                  │
root cause:   a query without a database filter → duplicate rows → a file twice as big
              + proxy code that crashed on a file over its hard limit
                  │
contributing: the file shipped to every server in minutes, no staged rollout;
              the bad file came and went every 5 minutes, which looked like an attack
```

Most big outages have **no single root cause**. They are a chain, and every link was a place where the outage could
have stopped. The best postmortems name all of them.

## Reading a timeline

A timeline tells you where the time went. Split it into phases:

```
 start ──► detect ──► diagnose ──► mitigate ──► recover ──► fully normal
       TTD        (where most          TTM          (cold caches,
                   time goes)                         backlogs)
```

| Phase | Typical question |
|-------|------------------|
| Time to detect | Did alerts fire, or did customers tell them? |
| Time to diagnose | Were the tools they needed working? |
| Time to mitigate | Was there a kill switch or a rollback? |
| Time to recover | Did systems come back by themselves, or need a slow cold start? |

Patterns you will see again and again in this module:

- **Detection is fast.** Fastly saw the problem in one minute (31.11), Google's SREs were on it in two (31.13).
- **Diagnosis is slow when tools share fate with production.** Facebook's internal tools used the DNS that had
  disappeared (31.7). Roblox's monitoring ran on the Consul cluster that was failing (31.10).
- **Recovery is slower than anyone expects.** Systems that are never restarted from cold don't know how to: S3's
  index (31.6), Roblox's caches, AWS's EC2 lease manager (31.5).

## Questions to ask of every postmortem

1. What was the **blast radius**, and why was it that big? (One customer, one region, the world?)
2. Was the change **staged**, or did it reach everything at once?
3. Did a **retry, autoscaler or failover** make things worse?
4. What **hidden dependency** showed up: status page, monitoring, login, badges?
5. What was the **slowest phase**, and what would have shortened it?
6. Do the action items fix **this bug** or the **class of bug**?

The lessons that follow each answer these in the same structure: what users saw, the timeline, the trigger, why it
spread, why recovery took as long as it did, what changed, and the general lesson. Lesson 31.15 pulls the patterns
together. Most incident lessons also have a sandbox scenario that replays the failure on the simulator canvas.

## Try it

Write the timeline for an outage you saw: at work, or a public one you lived through as a user. Use UTC times, mark
the phases (detect, diagnose, mitigate, recover) and label the trigger, the root cause and at least two contributing
factors.

<details>
<summary>Reference</summary>

A good answer looks like this (a made-up example):

| Time (UTC) | Event | Phase |
|-----------|-------|-------|
| 14:02 | Deploy of v412 to all API servers | trigger |
| 14:05 | p99 latency 120 ms → 4 s; error rate 8% | impact starts |
| 14:11 | Alert fires on error rate (5-min window) | detected (TTD 9 min) |
| 14:25 | On-call finds connection pool exhausted on DB | diagnosed |
| 14:31 | Rollback to v411 | mitigated (TTM 29 min) |
| 14:48 | Error rate back under 0.1% after pool drains | recovered |

- **Trigger:** the deploy.
- **Root cause:** v412 opened a new DB connection per request in one code path; the pool limit was 100.
- **Contributing:** deployed to 100% at once (no canary); the alert window was 5 minutes; the rollback took 6 minutes
  because the button needed a second approver who was in a meeting.
- **Action items that fix the class:** canary deploys watching error rate; a load test that checks connection counts;
  one-person emergency rollback.
</details>

## Key takeaways

- Read for the system, not the person: blameless postmortems fix tools, not people.
- Separate the trigger (small, ordinary), the root cause (latent) and contributing factors (what made it big or long).
- Split the timeline into detect, diagnose, mitigate and recover; diagnosis and recovery are where hours go.
- Judge action items by whether they fix the whole class of failure.

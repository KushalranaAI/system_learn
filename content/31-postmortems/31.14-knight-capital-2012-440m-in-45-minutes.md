# Knight Capital, 2012: $440M in 45 minutes

On 1 August 2012 Knight Capital, then one of the largest market makers in US stocks, lost about **$440 million in 45
minutes** (its own figure the next day; the SEC later put the loss at over $460 million). A new feature was deployed
to seven of eight servers. On the eighth, a flag that now meant "use the new feature" still meant what it had meant
nine years earlier: "run Power Peg," dead code that no longer knew when to stop buying. Knight needed an emergency
investment of about $400 million within days and was taken over the next year.

This lesson has no sandbox scenario: it isn't a capacity failure, it's a deployment failure. The lesson is about the
deploy process.

## What users saw

- For the first 45 minutes of trading, Knight's router flooded the market with orders. From **212** customer orders it
  sent millions of child orders, and got **over 4 million executions** in **154 stocks**, for **more than 397 million
  shares**.
- Prices of some stocks jumped or fell sharply. In 37 stocks, Knight was over half the trading volume and the price
  moved more than 10%.
- Knight ended up holding about **$3.5 billion** of unwanted long positions in 80 stocks and **$3.15 billion** of short
  positions in 74 stocks.

## Timeline (Eastern time)

| When | Event |
|------|-------|
| 2003 | Knight stops using the "Power Peg" feature in its router, SMARS. The code stays on the servers |
| 2005 | The "cumulative quantity" check (stop when the order is filled) is moved earlier in the code. Power Peg is not retested; it can no longer tell when to stop |
| 27 Jul 2012 onwards | New code for NYSE's Retail Liquidity Program (RLP) deployed to SMARS servers in stages over several days. It reuses Power Peg's flag. One technician doesn't copy it to the **eighth** server. No second person checks |
| 1 Aug, 08:01 | Pre-market RLP orders produce automated "Power Peg disabled" error emails. **97** are sent before the open. Nobody treats them as alerts |
| 09:30 | Market opens. RLP orders arrive with the flag set. Seven servers run RLP. The eighth runs Power Peg, sending child orders without stopping |
| ~09:30–10:15 | Engineers search for the cause in live trading. They **remove the new code from the seven good servers**, which makes all eight run Power Peg |
| ~10:15 | Knight stops the orders, about 45 minutes after the open |
| 2 Aug | Knight reports a pre-tax loss of about $440 million |
| Oct 2013 | SEC fines Knight $12 million for inadequate market-access controls |

## The trigger

A **manual deploy** that missed one server out of eight. Nothing checked that all eight were running the same version.

## Why it spread

```
order arrives with flag = "yes"
          │
   ┌──────┴──────────────────────────────┐
   ▼                                     ▼
servers 1–7 (new code)               server 8 (old code)
flag = "use RLP" ✔                   flag = "use Power Peg"
                                         │  cumulative-quantity check moved away in 2005
                                         ▼
                              send child order ─► filled ─► send another ─► filled ─► ... forever
                                         │
              no check comparing orders out vs orders in; no automatic kill switch
              account limit ($2M on the "33 account") not wired to any automated control
```

Every layer that could have stopped it was missing:

- **Dead code on production servers** for nine years, still callable.
- **A reused flag**, so old and new code gave the same input completely different meanings.
- **No deployment verification**: no automated check that all servers had the new version, no second reviewer, no
  written procedure.
- **Warnings that weren't alerts**: 97 emails naming the exact problem went to a mailbox nobody watched.
- **No circuit breaker on output**: nothing compared orders leaving SMARS to orders entering it, or halted the system
  when positions exploded.

## Why recovery took as long as it did

- There was **no incident procedure** and no kill switch. Engineers debugged in production while the system traded.
- The obvious fix, **roll back the new code**, made it worse. With the RLP code removed, the seven good servers also
  fell back to the flag's old meaning, and now all eight ran Power Peg.
- In trading, 45 minutes is forever: every minute of the bug cost about $10 million.

## What changed

Knight was rescued by a group of investors with about $400 million within a week, and agreed to merge with Getco in
December 2012. The SEC's order (October 2013) required Knight to pay a $12 million penalty and hire a consultant to
review its controls. It spelled out what was missing: written deploy procedures, a second technician to review
deployments, a protocol for unused code, tests after changing shared code, and automated controls that halt a system
showing "aberrant activity."

## The general lesson

- **Delete dead code.** Code that isn't used but is still callable is a trap. Remove it, don't just stop calling it.
- **Never reuse a flag or field for a new meaning.** Make a new one. Old binaries will read the old meaning.
- **Verify every deploy.** Automated deploys that confirm the version on every host, and a fleet check that refuses
  traffic until all hosts match. Staged rollouts ([staged rollout simulation](#/sims/staged-rollout)) also need
  "did every host actually get it?"
- **Rollback is a change too.** Know what rolling back does to the state the system is in now.
- **Put a circuit breaker on outputs.** A system that can spend money or send messages needs hard limits that stop
  it automatically ([lesson 12.3](#/lesson/12.3)).
- **Errors must reach a human.** If a system emits "Power Peg disabled" 97 times, that should page someone.

## Try it

Design a safe deploy checklist for a service that runs on eight servers and can move money. Include steps before,
during and after the deploy.

<details>
<summary>Reference</summary>

Before:
- [ ] Old code paths the change replaces are **deleted** in this or an earlier release, not left callable.
- [ ] No flag, field or message type is **reused** with a new meaning; new ones are added.
- [ ] The new behaviour is behind a **feature flag, off by default**.
- [ ] A second engineer reviews the change and the deploy plan; rollback steps are written down and their effect on
      live state is understood.

During:
- [ ] Deploy with a tool, not by hand; it deploys host by host and **verifies the version on every host** afterwards.
- [ ] The fleet refuses to enable the flag until **all hosts report the same version**.
- [ ] Turn the flag on for a small share of traffic first, with metrics compared to the old path.

After / always on:
- [ ] Automated **output limits**: orders out vs orders in, position and loss limits, with an automatic halt.
- [ ] A **kill switch** anyone on call can use, practised regularly.
- [ ] Error messages from the service route to on-call alerting, not just email.
</details>

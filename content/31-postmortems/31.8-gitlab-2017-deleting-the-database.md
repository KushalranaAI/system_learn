# GitLab, Jan 2017: deleting the database

On 31 January 2017 an engineer at GitLab, hours into fighting a spam-driven load spike and a broken replica, ran `rm -rf` on the
data directory of the **primary** PostgreSQL database instead of the broken secondary. He stopped it within seconds,
but about 300 GB was gone. Then the team discovered that none of their backup methods could restore it. GitLab.com
was down for about 18 hours and lost about six hours of data. GitLab published its working notes live and streamed
the recovery, which is why this postmortem is so detailed.

## What users saw

- GitLab.com offline for about 18 hours.
- When it came back, issues, comments, snippets, user accounts and projects created in a window of about six hours
  (17:20 to 23:30 UTC) were gone: around 5,000 projects, 5,000 comments and 700 new user accounts.
- Git repositories and wikis were not lost; they live on separate storage. Self-hosted GitLab was unaffected.

## Timeline (UTC)

| Time | Event |
|------|-------|
| 31 Jan, ~17:20 | Engineer takes an LVM snapshot of production to load into staging (for unrelated testing) |
| ~19:00 | Database load spikes, apparently from spam; users can't post comments |
| ~23:00 | Secondary falls too far behind; WAL it needs is already gone from the primary. Rebuild needed |
| ~23:00–23:30 | `pg_basebackup` hangs; settings changed; several attempts |
| ~23:30 | Engineer runs `rm -rf` on the data directory of db1 (primary) instead of db2 (secondary). ~300 GB removed |
| ~23:30 onwards | Team checks backups one by one; none usable except the 6-hour-old staging snapshot |
| 1 Feb | Snapshot copied from staging to production over slow disks (~18 hours) |
| 1 Feb, ~17:00 | GitLab.com back online, without webhooks |
| 1 Feb, ~18:00 | Webhooks restored; final checks done |

## The trigger

```
terminal 1: db1.cluster.gitlab.com   (primary, production)
terminal 2: db2.cluster.gitlab.com   (secondary, being rebuilt)

$ rm -rf <postgres data directory>        ← meant for db2, typed in db1
```

In the postmortem's words, the engineer wiped the directory "errantly thinking they were doing so on the secondary."
The team had been working for hours on a problem that kept getting worse, on two hosts with nearly identical names.
That's an ordinary human slip, the kind blameless postmortems ([lesson 31.1](#/lesson/31.1)) expect.

## Why it spread: five safety nets, none worked

GitLab's notes that night put it bluntly: "out of five backup/replication techniques deployed none are working
reliably or set up in the first place."
The final postmortem groups them as four procedures plus the alerting around them:

| Method | What was wrong |
|--------|----------------|
| Daily `pg_dump` to S3 | Ran pg_dump 9.2 against PostgreSQL 9.6, so it failed every time. The bucket was **empty** |
| Failure alerts for those dumps | Sent by cron email, which was **rejected** (DMARC wasn't set up for those mails). Nobody saw them |
| Azure disk snapshots | Enabled for the file servers, **not** for the database servers |
| Replication to a secondary | Fragile, poorly documented, and the secondary was the thing being rebuilt (and then the target of the wipe) |
| LVM snapshots | Taken every 24 hours to copy prod into staging, not designed as backups. The best one happened to be ~6 hours old |

```
primary deleted
   ├─► pg_dump backups? ─────── empty bucket (silent failure)
   ├─► disk snapshots? ──────── never enabled for DB
   ├─► replica? ─────────────── wiped as part of the rebuild
   └─► LVM snapshot ─────────── 6 h old, on staging (luck) ──► restore, lose 6 h
```

The pattern: **every backup was configured; none was ever restored.** A backup you haven't restored is a hope, not a
backup.

## Why recovery took as long as it did

- The only usable copy was on **staging**, which ran on slow Azure classic disks throttled to about 60 Mbps. Copying
  the data back took about 18 hours. The disks, not the people, set the recovery time.
- There was no runbook for "restore production from scratch," because it had never been done.
- After restore, all database ID sequences were bumped by 100,000 so new rows wouldn't reuse IDs that had existed in
  the lost window.

## What GitLab changed

From the postmortem's list of follow-up issues:

- **Hourly** LVM snapshots of the production database (was every 24 hours), and Azure disk snapshots for databases.
- **Automated testing of backup restores**, with monitoring and a public dashboard showing backup status.
- Point-in-time recovery with continuous WAL archiving (WAL-E and similar tools were investigated).
- A named **owner for data durability**.
- Better replication runbooks, multiple secondaries, sane `max_connections`.
- Making recovery procedures easy to test and roll back, rather than relying only on nobody running the wrong command.

## The general lesson

- **Test the restore, not the backup.** A backup job that "succeeds" proves nothing. Restore it, regularly and
  automatically, into a real server, and check the data ([lesson 5.5](#/lesson/5.5)).
- **Alert on missing success, not on failure.** "No successful backup in 25 hours" catches a job that died silently
  or an email that bounced. "Backup failed" emails don't.
- **Know your RPO and RTO and measure them.** GitLab's real RPO was 6 hours and RTO was 18 hours. Nobody had chosen
  those numbers; the slow disk chose them.
- **Make dangerous commands hard to run on the wrong host.** Distinct prompts and colours for production, a
  confirmation that names the host, and tools instead of raw `rm -rf`.
- **Replication is not a backup.** A replica copies deletes and corruption too ([lesson 5.4](#/lesson/5.4) and
  [lesson 13.2](#/lesson/13.2)).

## Try it

Test a restore, not a backup. Your nightly database backup goes to object storage. Design an automated check that
proves you can restore it, and say what it alerts on.

<details>
<summary>Reference</summary>

A daily job, run somewhere other than production:

1. Pick the newest backup (and, once a week, a random older one).
2. Restore it into a fresh database server from scratch, exactly as you would in a disaster, using the runbook.
3. Replay WAL to a target time if you use point-in-time recovery.
4. Run checks: row counts within a few percent of production at backup time; the newest row's timestamp is recent;
   a set of known records exist; the app's test suite passes against it.
5. Record the **restore duration** (your real RTO) and the **data age** (your real RPO).

Alert when: no successful restore test in 26 hours; restore time above the RTO target; data age above the RPO target;
any check fails. Put the result on a dashboard everyone can see.
</details>

# AWS us-east-1, Oct 2025: a DNS race

On 19–20 October 2025, AWS's oldest and biggest region, us-east-1 (Northern Virginia), had a disruption that lasted
about 14.5 hours. The trigger was a race condition in the automation that manages DynamoDB's DNS records: it left the
name `dynamodb.us-east-1.amazonaws.com` with **no IP addresses at all**. DynamoDB itself was healthy. Nobody could find
it, including many AWS services built on top of it.

## What users saw

- Apps and sites across the internet built on us-east-1 failed or slowed: logins, payments, games, smart-home devices.
- AWS customers saw DynamoDB errors, then failures to launch EC2 instances, Lambda throttling and delays, load balancer
  connection errors, and failed console sign-ins.
- Some effects reached other regions: sign-in through `signin.aws.amazon.com` and Redshift queries with IAM
  credentials, because they relied on APIs hosted in us-east-1.

## Timeline (PDT)

| Time | Event |
|------|-------|
| 19 Oct, 23:48 | DynamoDB endpoint record emptied; DynamoDB API errors begin |
| 23:48 onwards | EC2's DropletWorkflow Manager (DWFM) can't check in with DynamoDB; server leases start expiring |
| 20 Oct, 02:25 | DNS records restored by hand |
| 02:40 | Cached DNS entries expire; DynamoDB fully recovered |
| 02:25–04:14 | DWFM tries to re-establish leases for the whole fleet at once; congestive collapse |
| 04:14 | Engineers throttle DWFM's incoming work and restart its hosts |
| 05:28 | All server leases re-established |
| 05:30–14:09 | Network Load Balancer health checks flap; NLB removes healthy capacity |
| 06:21–10:36 | Network Manager works through a backlog; new instances lack network connectivity |
| 09:36 | Automatic NLB health-check failover disabled |
| 13:50 | EC2 APIs and launches normal |
| 14:20 | Last services (ECS, EKS, Fargate) recovered |

## The trigger

DynamoDB's DNS is managed by two pieces of automation:

- **DNS Planner** watches load balancer health and capacity and produces a numbered **plan**: which load balancers,
  with which weights, for each endpoint.
- **DNS Enactor** applies plans to Route 53. Three copies run, one per Availability Zone, for redundancy.

The race (plan numbers are made up for illustration):

```
Enactor A (slow, retrying)              Enactor B (fast)
─────────────────────────               ─────────────────
checks: "plan 100 is newer than live" ✔
... delayed for a long time ...         applies plan 145 to all endpoints
                                        cleanup: delete plans far older than 145
applies plan 100 to the regional ─────► (overwrites 145 with stale plan 100)
endpoint                                cleanup deletes plan 100 (it's old)
                                              │
                                              ▼
        dynamodb.us-east-1.amazonaws.com ──► record points at a deleted plan ──► 0 IPs
```

Enactor A's "is my plan newer?" check had been true when it ran, but it went stale during A's long delay. And the
system was left in an inconsistent state that stopped *any* Enactor from applying the next plan. The automation
couldn't fix itself; operators had to.

## Why it spread

DynamoDB is a building block for AWS itself. The region's dependency chain looked like this:

```
DynamoDB DNS (empty)
   │
   ├─► DynamoDB clients: every app and AWS service using DynamoDB in us-east-1
   │
   └─► EC2 DWFM (tracks leases on physical servers, stores state in DynamoDB)
          │ leases expire ──► no new instance launches
          ▼
       Network Manager (backlog) ──► new instances have no network
          │
          ▼
       NLB health checks fail on new capacity ──► NLB removes nodes ──► connection errors
          │
          ▼
       Lambda, ECS/EKS/Fargate, STS, Connect, Redshift ...
```

Running EC2 instances kept running. What failed was the ability to **change** anything: launch, scale, re-route.
That's the worst time to lose it, because every customer's autoscaler was trying to react to the outage.

## Why recovery took as long as it did

DNS was fixed in under three hours. The rest of the day went to the systems that had stalled in the meantime:

- **Congestive collapse.** When DynamoDB came back, DWFM tried to renew leases on the whole fleet at once. The work
  took so long that renewals timed out and were retried, filling the queues further. It made no forward progress until
  engineers throttled it and restarted hosts. There was no practised procedure for this, because it had never happened.
- **Backlogs downstream.** Network Manager then had hours of queued network updates to propagate.
- **Health checks that hurt.** NLB saw new instances without network as unhealthy and removed them, then put them
  back, then removed them. Engineers turned automatic failover off at 09:36 to stop the flapping.

## What AWS changed

- Disabled the DynamoDB DNS Planner and Enactor automation **worldwide** until the race is fixed and protections are
  added against applying an incorrect plan.
- NLB: a **velocity control** that limits how much capacity a single NLB can remove when health checks fail.
- EC2: a test suite for DWFM's recovery workflow, and **rate limiting of incoming work based on queue size**.

## The general lesson

- **Check-then-act is a race.** "Is my plan newer?" checked once, then acted on much later, is a time-of-check to
  time-of-use bug. Use a compare-and-set on a version, or a fencing token (lesson 12.7), at the moment of the write.
- **DNS failures look like total outages** even when every server is healthy. See [lesson 27.1](#/lesson/27.1).
- **Your foundations have dependents you forget.** One managed service sat under EC2, which sat under almost
  everything. Draw the graph before an outage draws it for you.
- **Recovery is its own workload.** A system that is fine at steady state can collapse when everything reconnects at
  once. Throttle recovery, add jittered backoff ([lesson 12.2](#/lesson/12.2)) and test cold start.
- **Automated failover needs a speed limit.** Health checks that remove capacity during a broad failure make it worse
  ([lesson 4.5](#/lesson/4.5)).
- **Regions are a blast-radius boundary only if nothing global hides inside one.** See
  [lesson 18.4](#/lesson/18.4) on multi-region.

## Try it

Map the dependencies of one region. For a service you know (or a made-up shop running in one cloud region), list
every dependency a request needs, then mark which ones are regional, which are global, and which are needed only to
**change** the system (launch, scale, deploy, log in).

<details>
<summary>Reference</summary>

| Dependency | Scope | Needed to serve | Needed to change |
|-----------|-------|-----------------|------------------|
| DNS for your domain | global | yes | yes |
| Load balancer | regional | yes | yes |
| App servers (running) | regional | yes | n/a |
| Instance launch API | regional | no | **yes** (autoscaling) |
| Database / KV store | regional | yes | yes |
| Identity / token service | often one "home" region | to log in | **yes** |
| Container registry | regional or global | no | **yes** (deploys) |
| Monitoring and status page | often same region | no | needed to see the outage |

The insight: steady-state serving may survive, but the **control plane** (launch, scale, deploy, sign in) often
depends on more, and more central, services. Make sure your autoscaling isn't the thing you need during the outage
of the thing your autoscaling depends on, and host monitoring and the status page somewhere else.
</details>

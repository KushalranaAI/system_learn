# Slack, Jan 2021: the first Monday back

On Monday 4 January 2021, the first working day after the holidays, Slack went down for millions of people starting
their year. The trigger was AWS Transit Gateways (TGWs) not scaling fast enough for Slack's post-holiday traffic
surge. What turned packet loss into a full outage was Slack's own automation: the autoscaler read low CPU as "too
many servers," removed some, then tried to add 1,200 at once, and the provisioning system buckled.

## What users saw

- Slack slow, then unable to load or send messages for a large part of the morning in the Americas.
- At 06:57 PST, 99% of messages were being sent successfully, against a normal rate above 99.999%. By 07:00 Slack
  was down.

## Timeline (PST)

| Time | Event |
|------|-------|
| Early morning | External monitoring pages Slack: error rates creeping up. Internal dashboards and alerts then fail |
| Before 07:00 | Packet loss between Slack's VPCs; web servers wait on network, CPU drops; autoscaler removes some servers |
| 06:57 | 99% message success (normal: >99.999%) |
| 07:00 | Hourly traffic peak plus packet loss saturates the web tier; Slack unavailable |
| ~07:00 | Downscaling disabled after engineers lose SSH sessions on removed hosts |
| 07:01–07:15 | Autoscaler tries to add **1,200 servers** to the web tier; provisioning fails |
| ~08:15 | provision-service fixed (Linux open-files limit and an AWS quota raised) |
| 09:15 | Enough healthy web hosts; Slack degraded but usable |
| ~10:40 | AWS manually raises TGW capacity in all zones; network back to normal |

## The trigger

Slack's architecture connected its many VPCs through AWS Transit Gateways, which scale automatically with traffic.
After two weeks of holiday, clients worldwide reconnected that morning with **cold caches**, pulling far more data
than on an ordinary Monday. Traffic rose faster than the TGWs scaled, and they started dropping packets.

## Why it spread

```
post-holiday surge (cold client caches)
      │
      ▼
TGW can't scale fast enough ──► packet loss between VPCs
      │                                │
      ▼                                ▼
web servers wait on network       dashboards/alerting (in a different VPC from their DB)
      │                           go blind
      ▼
CPU utilisation falls ──► autoscaler: "too many servers" ──► removes servers
      │
07:00 hourly peak ──► fewer servers + slow network ──► web tier saturated ──► OUTAGE
      │
autoscaler (now on thread utilisation): add 1,200 servers at once
      │
provision-service, also on the degraded network, hits open-files limit + AWS quota ──► new servers fail
```

Three automatic systems made it worse:

- **Autoscaling on CPU.** When servers are blocked waiting on the network, their CPU is low even though they are
  overloaded. The autoscaler saw spare capacity and scaled **down** ([lesson 4.7](#/lesson/4.7)).
- **The giant scale-up.** Then the thread metric shot up and it asked for 1,200 hosts in minutes, far more than
  the provisioning system had ever handled, on a network that was dropping packets.
- **Health checks** removed instances that were struggling and replaced them with new ones that couldn't provision.

And observability shared the failure: Slack's dashboards ran in a different VPC from their database, so they needed
the TGWs too.

## Why recovery took as long as it did

- The real bottleneck, TGW capacity, was inside AWS. Slack couldn't scale it; AWS engineers had to raise it manually,
  which completed around 10:40.
- Until then Slack fought its own systems: stopping downscaling, fixing the provisioning service's limits, getting
  enough working web servers. That gave partial service at 09:15.
- Engineers worked partly blind, because the dashboards were affected.
- Slack's existing protections (panic mode in load balancing, retries with backoff, circuit breakers) are what let it
  serve a degraded service from 09:15, instead of staying fully down.

## What Slack changed

- AWS reviewed TGW scaling for large increases in packets per second.
- Slack planned to ask for **TGW capacity to be pre-scaled** before the next holiday return.
- Moved dashboard instances into the **same VPC as their database**, so monitoring doesn't depend on the TGW.
- Load-tested provision-service and fixed its limits.
- Re-evaluated **health check and autoscaling** configurations.

## The general lesson

- **Known spikes should be pre-scaled, not autoscaled.** The first Monday of January, a sale, a big match: scale up
  before, and ask your providers to as well. Compare Disney+ Hotstar ([lesson 30.2](#/lesson/30.2)).
- **Autoscale on the right signal.** CPU is a poor measure when the bottleneck is I/O or network. Use request latency,
  queue depth or concurrency, and cap how fast the autoscaler can move in either direction.
- **Automation can amplify a failure.** Autoscalers, health checks and retries all react to symptoms; in a broad
  failure they can make it worse ([lesson 12.2](#/lesson/12.2) on retry storms).
- **Your scale-up path must work when things are bad.** Provisioning that fails under load is useless when you need it.
- **Monitoring must not depend on what it monitors** (Roblox, [lesson 31.10](#/lesson/31.10)).
- **Managed services have limits too.** "Scales automatically" has a rate; know it before your biggest day.

## Try it

Pre-scale for a known spike. Your chat app's normal Monday 09:00 peak is 40,000 req/s on 200 web servers. After a long
holiday you expect 2.5x on the first morning, and cold client caches will double bytes per request. Write the plan:
what to scale, by how much, and when.

<details>
<summary>Reference</summary>

- **Web tier:** 2.5 × 40,000 = 100,000 req/s → ~500 servers at the same utilisation; add 20% headroom → ~600.
  Scale up the evening before, and **set the autoscaler minimum to 600** so it can't scale down overnight or
  during a network blip.
- **Network:** 2.5x requests × 2x bytes = **5x bandwidth and packets per second** through gateways, load balancers and
  NAT. Ask the cloud provider to pre-warm or pre-scale gateways and load balancers; check quotas (instances, IPs,
  connections).
- **Provisioning:** load-test the provisioning path at the size of the planned scale-up; raise file and API limits.
- **Autoscaler:** scale on latency and concurrency, not CPU; limit scale-in to a few percent per 10 minutes.
- **Clients:** stagger reconnects with jitter and serve cached bootstrap data where possible.
- **People:** staff the on-call rota that morning and freeze deploys.
</details>

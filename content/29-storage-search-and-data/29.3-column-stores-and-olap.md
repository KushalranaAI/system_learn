# Column stores and OLAP

Your Postgres handles "fetch order 7 and its items" in a millisecond. Ask it "revenue by country per day for the last
year" over 2 billion order lines and it grinds for minutes. Analytical (OLAP) queries read few columns of very many
rows; transactional (OLTP) queries read all columns of very few rows. Column stores are built for the first shape.

## Row vs column layout

Same table, `events(ts, user_id, country, event_type, amount, ... 20 columns)`:

```
Row store (Postgres, MySQL): each page holds whole rows
  page 1: [ts,user,country,type,amount,…][ts,user,country,type,amount,…]…

Column store (ClickHouse, Redshift, BigQuery, Snowflake, Parquet files):
  ts.bin:       ts1 ts2 ts3 ts4 …
  country.bin:  DE  DE  DE  FR  FR  …
  amount.bin:   12.5 3.0 7.25 …
```

`SELECT country, sum(amount) FROM events WHERE ts >= '2026-10-01' GROUP BY country` touches **3 of 20 columns**. A
row store reads all 20 from disk; a column store reads 3, about 15% of the bytes before compression even starts.

The flip side: fetching or updating one whole row means touching 20 files, and single-row inserts are expensive.
Column stores want data in **batches** (thousands to millions of rows per insert), and updates/deletes are usually
handled by rewriting parts in the background.

## Compression loves columns

A column holds values of one type, often sorted or repetitive, so it compresses far better than mixed rows:

| Technique | Example | Result |
|-----------|---------|--------|
| **Dictionary** | country: 200 distinct strings → 1-byte codes | "Germany" (7 B) → 1 B |
| **Run-length (RLE)** | Sorted by country: `DE ×1,204,331, FR ×981,220…` | Millions of values → a few bytes |
| **Delta** | Timestamps `1700000000, 1700000001, 1700000003` → `+1, +2` | 8-byte ints → 1–2 bits each |
| **Bit-packing** | Values 0–100 need 7 bits, not 64 | 9× smaller |
| General-purpose | LZ4 / ZSTD on top | Further 2–4× |

Compression ratios of 5–10× over raw are normal, and the engine can often operate on compressed data directly
(compare dictionary codes, sum run lengths).

## Skipping data

Columns are stored in chunks (ClickHouse granules, Parquet row groups/pages), each with **min/max statistics** (zone
maps). `WHERE ts >= '2026-10-01'` skips every chunk whose max `ts` is earlier. If the table is **sorted** by
`(ts)` or `(country, ts)`, most chunks are skipped outright. Choosing the sort key is the column-store equivalent of
choosing indexes. Partitioning by month or day lets the engine drop whole partitions too.

## Vectorised execution

A row engine calls `next()` per row through every operator (lesson 28.1): billions of function calls, branchy code,
poor CPU cache use. A **vectorised** engine processes a batch of values, a few thousand at a time, per operator call:

```
filter:  ts_batch[0..2047] >= cutoff   → selection bitmap      (tight loop, SIMD)
agg:     for i in selected: sums[country_code[i]] += amount[i]
```

Tight loops over arrays of one type let the CPU use SIMD instructions and keep data in cache. Combined with reading
fewer, compressed bytes, analytic queries run 10–100× faster than in a row store on the same hardware. Many engines
also run each query in parallel across all cores and, in warehouses, across many machines (MPP).

## The landscape

| Kind | Examples | Shape |
|------|----------|-------|
| Cloud warehouse | Snowflake, BigQuery, Redshift | Storage (often object storage) separated from compute; pay per query or per cluster |
| Real-time OLAP | ClickHouse, Apache Druid, Apache Pinot | Fast ingest from Kafka; sub-second queries for dashboards and user-facing analytics |
| Embedded | DuckDB | In-process, great for a laptop or a single service |
| Open table formats | Parquet files + Iceberg/Delta/Hudi on S3 | "Lakehouse": many engines (Spark, Trino, warehouses) query the same files |

Pre-aggregation is the other big lever: materialised views or rollup tables that keep `per minute per country` sums
as data arrives, so a dashboard reads thousands of rows instead of billions.

## Key takeaways

- OLAP reads few columns of many rows; column stores read only the columns a query needs.
- Single-typed columns compress 5–10× with dictionary, RLE, delta and bit-packing.
- Min/max statistics plus a good sort key let engines skip most data.
- Vectorised execution processes batches with tight loops and SIMD; combined, 10–100× faster than row stores for
  analytics.
- Batch your inserts and pre-aggregate for dashboards.

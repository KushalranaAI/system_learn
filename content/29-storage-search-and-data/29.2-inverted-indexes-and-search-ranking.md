# Inverted indexes and search ranking

`WHERE body LIKE '%paris%'` scans every row. A search engine (Lucene, and so Elasticsearch, OpenSearch and Solr;
also Tantivy, Vespa) instead keeps an **inverted index**: for every word, the list of documents that contain it.
Finding documents becomes looking up a few lists and combining them, and ranking decides which of the matches you see
first.

## From text to terms

Indexing runs each document through an **analyzer**:

```
"The Quick Foxes jumped!"
  tokenize        → [The] [Quick] [Foxes] [jumped]
  lowercase       → [the] [quick] [foxes] [jumped]
  stop words      → [quick] [foxes] [jumped]            ("the" dropped)
  stem            → [quick] [fox] [jump]
```

The **same analyzer runs on queries**, so "jumping fox" becomes `[jump] [fox]` and matches. Choices here decide what
can be found: stemming merges "organization" and "organ" in aggressive stemmers; dropping stop words breaks the
query "to be or not to be"; languages without spaces (Chinese, Japanese) need dictionary or n-gram tokenizers.
Autocomplete often indexes edge n-grams (`par`, `pari`, `paris`).

## Posting lists

For each term, the index stores a **posting list** of document IDs in order, often with the term frequency and
positions:

```
term     postings: docID(tf: positions)
fox   →  3(1: 2)   17(2: 4, 31)   42(1: 0)
jump  →  3(1: 3)   8(1: 7)       42(1: 1)
quick →  3(1: 1)   99(1: 5)
```

- **AND** query `quick fox`: intersect the lists (walk both sorted lists, skip ahead using skip pointers) → doc 3.
- **OR** query: union them, score each.
- **Phrase** query `"quick fox"`: intersect, then check positions are adjacent (1 then 2 in doc 3 ✓).

Lists are compressed: store gaps between IDs instead of IDs (`3, 17, 42` → `3, 14, 25`), then pack the small numbers
into few bits (variable-byte or block bit-packing). Common terms with millions of postings shrink to a byte or less
per posting. A **term dictionary** (a sorted structure or finite-state transducer in Lucene) maps each term to its
list.

## Segments: an LSM in disguise

Lucene writes immutable **segments**: new documents are buffered in memory, then flushed as a new small segment with
its own index. A search queries every segment and merges results; background **merges** combine small segments into
big ones (like LSM compaction, lesson 26.8). Updates are delete + re-add; deletes are a bitmap until a merge drops them.

Elasticsearch makes new documents searchable on **refresh**, every 1 second by default, which is why it's "near
real-time": a document you just indexed may not appear in a search for up to a second. Bulk loads often turn refresh
off until they finish.

## Ranking: BM25

Matches need an order. **BM25** (the default similarity in Lucene since version 6) scores each query term in each
document and sums:

```
score(D, q) = Σ over terms t in q:   IDF(t) × f(t,D) × (k1 + 1)
                                     ───────────────────────────────────────────
                                     f(t,D) + k1 × (1 − b + b × |D| / avgdl)

IDF(t) = ln(1 + (N − n(t) + 0.5) / (n(t) + 0.5))
```

| Symbol | Meaning | Typical value |
|--------|---------|---------------|
| f(t,D) | How many times t occurs in D | |
| \|D\| (len D), avgdl | Length of D in terms, average length | |
| N, n(t) | Number of docs, docs containing t | |
| k1 | How fast term frequency saturates | 1.2 |
| b | How strongly long docs are penalised | 0.75 |

The ideas:

- **Rare terms matter more** (IDF): "lighthouse" in your query is more telling than "the".
- **Term frequency saturates**: in an average-length doc with k1 = 1.2, the TF part is 1.0 for one occurrence,
  1.38 for two, 1.77 for five, 1.96 for ten, never above 2.2. Repeating a word 100 times doesn't win.
- **Length normalisation**: one mention in a 10-word title counts for more than one mention in a 5,000-word page.

Production ranking layers more on top: field boosts (title over body), freshness, popularity, personalisation, and
often a second-stage machine-learned or vector re-ranker over the top few hundred BM25 hits (hybrid search,
[lesson 34.5](#/lesson/34.5)).

## Sharding a search index

| Strategy | How | Trade-off |
|----------|-----|-----------|
| **Document-partitioned** (common) | Each shard holds a full index of a subset of documents | Every query fans out to all shards (scatter-gather), each returns its top k, coordinator merges |
| **Term-partitioned** | Each shard holds the posting lists for a subset of terms | A query touches only the shards for its terms, but multi-term queries move large lists between machines; rarely used |

With document partitioning, a query's latency is the **slowest shard's** latency (tail latency at scale; replicas and
hedged requests help). IDF is computed per shard, so small or skewed shards can rank inconsistently; Elasticsearch
offers a global-statistics mode (`dfs_query_then_fetch`) for that. Elasticsearch fixes the number of primary shards at
index creation; aim for shards of tens of GB and replicas for read throughput.

## Try it

Index these three documents by hand (lowercase, drop "to", "in", "and"; stem plurals), then rank them for the query
`cheap paris` with BM25 (k1 = 1.2, b = 0.75).

- D1: "Cheap flights to Paris"
- D2: "Hotels in Paris"
- D3: "Cheap hotels and cheap flights"

N = 3; "cheap" and "paris" each appear in 2 docs: IDF = ln(1 + 1.5 / 2.5) = ln 1.6 ≈ 0.47.

- D1: both terms, tf 1, length = avg → TF part = 2.2 / (1 + 1.2) = 1.0 each → 0.47 + 0.47 = **0.94**
- D3: cheap tf 2, length 4 → norm = 0.25 + 0.75 × 4/3 = 1.25 → 2 × 2.2 / (2 + 1.5) = 1.26 → 0.47 × 1.26 ≈ **0.59**
- D2: paris tf 1, length 2 → norm = 0.25 + 0.75 × 2/3 = 0.75 → 2.2 / (1 + 0.9) = 1.16 → 0.47 × 1.16 ≈ **0.54**

Ranking: D1 (matches both terms) > D3 (one term, twice, but saturated and in a longer doc) > D2.

## Key takeaways

- Analyzers turn text into terms; the same analyzer must run on documents and queries.
- An inverted index maps each term to a compressed, sorted posting list; queries intersect or union lists.
- Lucene indexes are immutable segments merged in the background; Elasticsearch refreshes every second by default.
- BM25 rewards rare terms, saturates repeated terms and normalises by length.
- Shard by document and scatter-gather; tail latency and per-shard statistics are the costs.

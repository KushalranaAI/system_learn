# Speeding up page loads

Users don't experience your API's p50 server time. They experience the page: DNS, handshakes, HTML, CSS, scripts,
fonts, images and API calls, many of them waiting on each other. Most of the wins come from three ideas: **send fewer
bytes**, **make fewer round trips**, and **start important work earlier**.

## Send fewer bytes

| Technique | Typical win |
|-----------|-------------|
| **Compression**: Brotli or gzip for text (HTML, JSON, JS, CSS); zstd is supported by recent browsers | 60-80% smaller text |
| **Modern images**: AVIF/WebP, responsive `srcset`, correct dimensions | Often the largest bytes on a page |
| **Less JavaScript**: code splitting, tree shaking, dropping unused libraries | Faster parse and execution on phones (better INP) |
| **Smaller API responses**: only the fields the screen needs (lesson 22.3) | Faster on slow links |
| **Caching**: long `max-age` for fingerprinted assets (`app.3f9a1.js`) | Repeat visits load almost nothing (lesson 23.3) |

## Make fewer round trips

- **Reuse connections**: HTTP/2 or HTTP/3 multiplex everything over one connection per origin. Fewer origins means
  fewer DNS lookups and handshakes.
- **Avoid request waterfalls**: when the page must load JS, which then fetches data, which then fetches more data,
  each step costs a full round trip. Fetch data in parallel, render it on the server, or inline critical data in the HTML.
- **Batch API calls** for a screen (BFF or GraphQL, lesson 20.6).

## Start important work earlier: resource hints

```html
<link rel="preconnect" href="https://api.shop.example" crossorigin>       <!-- DNS + TCP + TLS now -->
<link rel="dns-prefetch" href="https://images.shop.example">              <!-- just DNS, cheap -->
<link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin>   <!-- needed soon, fetch now -->
<link rel="modulepreload" href="/assets/product-page.js">
<link rel="prefetch" href="/checkout.js">                                  <!-- likely next page, low priority -->
<img src="hero.avif" fetchpriority="high">                                 <!-- this is the LCP image -->
<img src="footer-logo.png" loading="lazy">                                 <!-- off-screen: later -->
```

- **`preconnect`** to the API origin saves one to three round trips on the first API call.
- **`103 Early Hints`**: the server (or CDN) sends a `103` response with `Link: rel=preload` headers **before** the
  real response is ready, so the browser starts fetching CSS and fonts while the server is still rendering.
- **Speculation rules** (Chromium) let a page prerender likely next pages.

Hints are cheap but not free: preloading things that aren't needed wastes bandwidth and competes with what is.

## Calling APIs less often from the UI: debounce and throttle

Search-as-you-type, scroll handlers, resize events and autosave can fire dozens of times a second.

| Technique | Behaviour | Use for |
|-----------|-----------|---------|
| **Debounce** | Wait until the events stop for N ms, then call once | Search boxes, autosave, validation |
| **Throttle** | Call at most once per N ms while events keep coming | Scroll position, live previews, analytics |

```javascript
let timer, controller;
input.addEventListener("input", () => {
  clearTimeout(timer);
  timer = setTimeout(async () => {
    controller?.abort();                       // cancel the previous, now out-of-date request
    controller = new AbortController();
    const q = input.value.trim();
    if (q.length < 2) return;
    const res = await fetch(`/api/suggest?q=${encodeURIComponent(q)}`, { signal: controller.signal });
    render(await res.json());
  }, 150);
});
```

Debouncing cuts requests; **aborting or ignoring stale responses** prevents a slow reply for "ip" from overwriting the
results for "iphone". The simulation below uses real typing rhythms.

## Try it

Make search-as-you-type send at most 5 requests per search, show final results within 450 ms of the last keystroke,
and never flash stale results, with an API whose p99 is 600 ms.

<details>
<summary>Answer</summary>

Sending on every key costs ~9-10 requests per search and flashes stale results in most searches. A 150 ms debounce,
starting at 2 characters, with stale replies ignored gives ~4.8 requests per search, final results ~270 ms after the
last key, and no stale flashes. A 250 ms debounce cuts requests further but pushes the delay to ~360 ms. Throttling
keeps results flowing while typing at the cost of more requests.
</details>

## Key takeaways

- Fewer bytes (compression, images, less JS), fewer round trips (connection reuse, no waterfalls), earlier starts
  (hints, Early Hints).
- `preconnect` to your API origin and mark the LCP image as high priority.
- Debounce or throttle UI-driven API calls, and cancel or ignore out-of-date responses.

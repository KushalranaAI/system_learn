# Server-side vs client-side rendering

A shop rebuilds its product pages as a single-page app. On a fast laptop it feels snappy. On a mid-range phone on
4G, shoppers stare at a white screen for three seconds while 1.5 MB of JavaScript downloads, parses and then calls
three APIs. Search traffic drops too. Where the HTML gets built decides which APIs run when, and how long users wait
before they see anything.

## The options

| Mode | Where HTML is built | First thing the user sees | Good for |
|------|---------------------|---------------------------|----------|
| **Client-side rendering (CSR)** | In the browser, from JSON APIs | Empty shell until JS runs and data loads | App-like tools behind a login (dashboards, editors) |
| **Server-side rendering (SSR)** | On the server, per request | Real content in the first response | Content and commerce pages, SEO, slow devices |
| **Static generation (SSG)** | At build time | Instant, from a CDN | Docs, blogs, marketing, rarely changing pages |
| **Incremental / on-demand static** | Built once, cached, regenerated on change or after a TTL | Instant, mostly fresh | Large catalogues |
| **Streaming SSR** | On the server, sent in chunks as data arrives | The page shell and fast parts first | Pages with one slow section |

With SSR, the browser still downloads JavaScript to make the page interactive (**hydration**). Newer approaches
(React Server Components, islands architecture as in Astro, resumability as in Qwik) send less JavaScript by keeping
non-interactive parts as plain HTML.

## What changes for the API

```
CSR:   browser ──GET /app.js──▶ CDN      browser ──GET /api/product/42──▶ API      (user's network, each trip)
                                         browser ──GET /api/reviews?p=42──▶ API
SSR:   browser ──GET /product/42──▶ web server ──(data-centre network, parallel)──▶ product, reviews, stock APIs
                                    ◀── HTML with the content already in it
```

- With **CSR**, every API call crosses the user's network, so round trips and payload size matter enormously (module
  24). APIs must be public-facing, CORS-enabled and cacheable.
- With **SSR**, the server calls APIs over a fast internal network, in parallel; the API can be internal (gRPC is fine)
  and the user waits for one HTML response. The server needs capacity for rendering, and caching rendered pages at the
  CDN becomes important.

## How to measure: Core Web Vitals

Google's user-centred metrics, measured on real users' devices:

| Metric | What it measures | "Good" threshold |
|--------|------------------|------------------|
| **LCP** (Largest Contentful Paint) | When the main content appears | ≤ 2.5 s |
| **INP** (Interaction to Next Paint) | How quickly the page responds to taps and clicks (replaced FID in March 2024) | ≤ 200 ms |
| **CLS** (Cumulative Layout Shift) | How much content jumps around while loading | ≤ 0.1 |

Measure at the 75th percentile of real users (RUM), not just in lab tools on a fast machine. Also watch **TTFB** (time to
first byte): SSR moves work there, so slow APIs behind SSR show up as a slow TTFB.

## Choosing per page

Most products mix modes:

| Page | Mode |
|------|------|
| Home, category and product pages | SSR or incremental static, cached at the CDN, with client-side islands for "add to cart" |
| Search results | SSR for the first page (shareable, SEO), client-side for filters and infinite scroll |
| Cart, checkout | SSR or CSR; never cached in shared caches |
| Account settings, seller dashboard | CSR behind login |
| Help centre, blog | Static |

## Try it

Pick a rendering mode for (a) a news article page, (b) a stock-trading dashboard, (c) a 2-million-item product catalogue.

<details>
<summary>Answer</summary>

(a) Static or incremental static, regenerated when the article changes, served from the CDN; comments loaded
client-side. (b) CSR with a WebSocket price feed; it's an app behind a login and updates constantly. (c) SSR with CDN
caching (`s-maxage` + `stale-while-revalidate`) or on-demand static generation, so popular products are pre-rendered
and the long tail renders on first request; price and stock fetched client-side or revalidated frequently.
</details>

## Key takeaways

- CSR builds pages in the browser from APIs; SSR and static generation send real HTML first.
- CSR puts every API round trip on the user's network; SSR moves them into the data centre.
- Measure with Core Web Vitals (LCP, INP, CLS) at the 75th percentile of real users.
- Choose per page; most products mix static, SSR and client-side parts.

# Monitoring APIs

The dashboard is green: average latency 45 ms, error rate 0.2%. Meanwhile your biggest partner has been getting `403`s
for six hours since a permissions change, and Android users in one country are seeing 4-second responses. Averages
across all traffic hide exactly the problems that matter. API monitoring means watching from the **consumer's** point
of view: per endpoint, per client, at the tail.

## RED for every endpoint

| Signal | What | Slice by |
|--------|------|----------|
| **R**ate | Requests per second | Endpoint (route template, not raw URL), method, client / API key, version |
| **E**rrors | Share of `5xx` (your fault) and, separately, `4xx` (often theirs, but a spike means you broke something) | Status code, error `type`, client |
| **D**uration | Latency **percentiles**: p50, p95, p99 | Endpoint, region, client type |

Add **saturation** (CPU, connection pools, queue depth) for the services behind the API: the four "golden signals".

## SLOs per endpoint

Not every endpoint deserves the same target (lesson 18.1):

| Endpoint | SLI | SLO |
|----------|-----|-----|
| `POST /payments` | Share of requests that succeed (non-5xx) in under 1 s | 99.95% over 28 days |
| `GET /search` | Share answered in under 300 ms | 99% |
| `POST /exports` | Share of exports finished within 10 minutes | 99% |

Alert on **error-budget burn rate** (for example, "we're burning a month's budget 14x faster than allowed over the last
hour"), not on single spikes. It pages people for real problems and stays quiet for blips.

## See it like a user: synthetic checks

Real traffic tells you about users who got through. **Synthetic monitoring** runs scripted API calls every minute from
several regions: sign in, create a test order, fetch it, cancel it. It catches DNS, certificate, routing and auth
breakages, including at 3 a.m. when real traffic is low.

## Follow one request: logs and traces

- Return a **request id** (`X-Request-Id`) in every response and log it everywhere. Support asks for it; you find the
  logs in seconds.
- **Structured logs** (JSON) with route, status, latency, client id, user id (or a hash), error type.
- **Distributed tracing** with W3C `traceparent` headers and OpenTelemetry: one trace shows the request crossing the
  gateway, three services and the database, and where the time went (lesson 11.5).
- Never log secrets, tokens or full card numbers; redact by default.

## API analytics: the product view

Beyond health, measure how the API is **used**:

- Top clients by traffic and by errors; new integrations this week.
- Calls to deprecated endpoints and versions, by client (lesson 22.2).
- Time to first successful call for new developers (lesson 19.3).
- `429`s by client, which shows who needs a higher tier or has a broken integration.

## Key takeaways

- Measure rate, errors and duration per endpoint and per client, with percentiles, not averages.
- Set SLOs per endpoint and alert on error-budget burn rate.
- Synthetic checks see what real traffic can't; request ids and traces explain single failures.
- API analytics (usage, deprecations, 429s, onboarding) is part of running an API as a product.

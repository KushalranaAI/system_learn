# Retries and circuit breakers from the client

Module 12 showed how retries can turn a 15-second blip into an outage that never ends (the retry-storm simulation
in lesson 12.2). An API's design decides whether clients **can** retry safely, and its SDKs and docs decide whether
they **do** it well. This lesson is the client-side rulebook that an API provider should give, and build into its SDKs.

## What's safe to retry

| Response | Retry? |
|----------|--------|
| Network error before any response, connection reset, timeout | Yes, **if the request is idempotent** (GET, PUT, DELETE, or POST with an Idempotency-Key, lesson 22.4) |
| `429 Too Many Requests` | Yes, after `Retry-After` |
| `503 Service Unavailable`, `502`, `504` | Yes, with backoff (and after `Retry-After` if present) |
| `500 Internal Server Error` | Maybe once; it's often a bug that will fail again |
| `400`, `401`, `403`, `404`, `409`, `422` | **No**: the same request will fail the same way. Fix it (or refresh the token on 401) |

An API helps by being consistent about this: correct status codes, `Retry-After`, and idempotency keys on every
non-idempotent write.

## How to retry

```
attempt 1 fails
wait  random(0, min(cap, base × 2^attempt))      ← exponential backoff with "full jitter"
attempt 2 ...
stop after N attempts, or when the overall deadline is spent
```

- **Exponential backoff** gives a struggling service room to recover.
- **Jitter** spreads retries out so thousands of clients don't come back in the same second.
- **A retry budget** caps retries at a fraction of normal traffic (say 10%); beyond that, fail fast.
- **Deadlines, not just per-attempt timeouts**: the whole operation has a time limit; each attempt gets what's left.
- **Retry at one layer only.** If the app, the BFF, the gateway and the service each retry 3 times, one failure becomes
  81 requests.

## Circuit breakers

When a dependency keeps failing, stop calling it for a while.

```
          failures over threshold                 cool-down elapsed
 CLOSED ────────────────────────────▶ OPEN ───────────────────────────▶ HALF-OPEN
   ▲      (calls go through)           (fail immediately,                │ (let a few test calls through)
   │                                    use the fallback)                │
   └──────────── test calls succeed ────────────────────────────────────┘
                 test calls fail → back to OPEN
```

Combine with a **fallback**: cached data, a default ("bestsellers" instead of personalised recommendations), a degraded
feature, or a clear error. Lesson 12.3 has the server-side version (bulkheads, load shedding).

## For mobile and offline clients

- Queue writes locally with their idempotency keys and replay them when the network returns.
- Don't retry in a tight loop when the device is offline; listen for connectivity changes.
- Persist the idempotency key with the queued request, so a retry after an app restart uses the same key.

## What the provider should ship

- SDKs with retries, backoff, jitter, idempotency keys and `Retry-After` handling built in and on by default.
- Docs listing which errors are retryable.
- Server-side protection that assumes some clients will retry badly anyway: rate limits, load shedding, short queues.

## Try it

Write the retry policy for a mobile app calling a payments API: which errors, how many attempts, what delays, and
what happens when everything fails.

<details>
<summary>Answer</summary>

- Every `POST` carries an Idempotency-Key created once per payment and stored with the pending request.
- Retry on network errors, timeouts, `429`, `502`, `503`, `504`: up to 4 attempts, full-jitter backoff starting at
  0.5 s, capped at 8 s, always honouring `Retry-After`, with an overall deadline of ~30 s while the user is on screen.
- Never retry `4xx` other than `429`; on `401`, refresh the token once and retry.
- If it still fails, show "We're checking your payment" and resolve it later with `GET /payments/:id` (or a push
  notification from the webhook), never by asking the user to pay again.
- A circuit breaker around non-essential calls (offers, recommendations) with fallbacks.
</details>

## Key takeaways

- Retry only idempotent requests, and only errors that can succeed later (network, 429, 5xx).
- Exponential backoff with jitter, a retry budget, an overall deadline, and retries at one layer only.
- Circuit breakers stop hammering a failing dependency; pair them with fallbacks.
- Providers should build good retry behaviour into SDKs and still protect the server from bad clients.

# Caching at every layer

The fastest API request is the one that never reaches your servers. Between a user's tap and your database there are
five or six places that could have answered: the app, the browser, a CDN, the gateway, the service's own cache, and the
database's buffer pool. Module 3 covered caching inside the backend; this lesson is about designing an **API** so every
layer can help, safely.

## The layers

```
app / browser cache ─▶ CDN / edge ─▶ API gateway ─▶ service + Redis ─▶ database buffer pool
  private, per user     shared         shared         shared              shared
  controlled by headers controlled by headers + config  controlled by code   automatic
```

| Layer | What it caches | Who controls it |
|-------|----------------|-----------------|
| Client (browser HTTP cache, app's local store) | Responses for this user | Your `Cache-Control` headers; app code |
| CDN / edge | Public responses near users | Headers (`s-maxage`), CDN rules, purges |
| Gateway / reverse proxy | Responses or auth decisions | Gateway config |
| Application cache (Redis, in-process) | Objects, query results, computed views | Your code (lesson 3.3) |
| Database | Pages and indexes in memory | The database |

## The headers that drive HTTP caches

```http
Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=600, stale-if-error=86400
ETag: "p42-v17"
Vary: Accept-Encoding, Accept-Language
```

| Directive | Meaning |
|-----------|---------|
| `public` / `private` | May shared caches (CDNs) store it, or only the user's own client |
| `max-age=N` | Fresh for N seconds in any cache |
| `s-maxage=N` | Override for shared caches only |
| `no-cache` | May store, but must revalidate before every use |
| `no-store` | Never store (payments, personal data you don't want on disk) |
| `stale-while-revalidate=N` | Serve stale for N seconds while fetching a fresh copy in the background |
| `stale-if-error=N` | Serve stale for N seconds if the origin is failing |
| `immutable` | Will never change (fingerprinted assets) |
| `Vary` | The response differs by these request headers: part of the cache key |

## Revalidation: cheap "is it still the same?"

```http
GET /v1/products/42                      →  200, ETag: "p42-v17", body (3 KB)
GET /v1/products/42  If-None-Match: "p42-v17"  →  304 Not Modified, no body
```

A `304` still costs a round trip, but no body and usually little server work (compare a version number). ETags also
power safe updates (`If-Match`, lesson 20.3).

## What's cacheable in an API

| Endpoint | Headers |
|----------|---------|
| `GET /products/:id` (public, changes a few times a day) | `public, max-age=60, s-maxage=300, stale-while-revalidate=600` + ETag |
| `GET /search?q=sofa` (public, popular queries repeat) | `public, s-maxage=30` |
| Static assets with a hash in the name | `public, max-age=31536000, immutable` |
| `GET /me`, `GET /cart` (per user) | `private, no-cache` + ETag |
| `POST /checkout`, anything with secrets | `no-store` |

Rules: never put per-user data in a shared cache (watch out for responses that vary by an `Authorization` header or
cookie); make URLs canonical (sorted query parameters, consistent case) so the same thing has one cache key; version
assets and tile URLs so you can cache them forever.

## Invalidation

You can expire (TTLs), revalidate (ETags) or **purge**: most CDNs can purge by URL or by **tag** (`Surrogate-Key`,
`Cache-Tag`) in seconds. Tag product pages with `product-42`; when product 42 changes, purge the tag. Keep TTLs short
enough that a failed purge is tolerable.

## Try it

Set cache headers for: `GET /v1/menu` of a restaurant (changes daily, same for everyone), `GET /v1/orders/:id` (one
user's order, changes as it's delivered), `GET /v1/restaurants/:id/photo.jpg?v=12`, `POST /v1/orders`, and
`GET /v1/eta?order=…` (changes every few seconds).

<details>
<summary>Answer</summary>

- Menu: `public, max-age=300, s-maxage=3600, stale-while-revalidate=86400` + ETag, purge by tag on change.
- Order: `private, no-cache` + ETag (the app revalidates; a 304 is cheap). Never cached at the CDN.
- Photo with `?v=12`: `public, max-age=31536000, immutable` (a new photo gets a new version).
- `POST /orders`: `no-store`.
- ETA: `private, max-age=5` or no caching, ideally pushed over SSE or WebSocket instead of polled.
</details>

## Key takeaways

- Every layer can answer: client, CDN, gateway, application cache, database.
- `Cache-Control` decides who may store a response and for how long; `Vary` is part of the key.
- ETags make revalidation cheap and updates safe.
- Cache public data aggressively, keep per-user data private, never store sensitive responses; purge by tag.

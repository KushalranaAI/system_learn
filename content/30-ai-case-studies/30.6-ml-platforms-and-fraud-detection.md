# ML platforms and fraud detection

Fraud scoring is the classic **real-time ML** problem: a payment arrives, and within tens of milliseconds a model must
say "allow", "challenge" or "block", using features about the card, device and merchant that are seconds old. Get it
wrong one way and you lose money to fraud; the other way and you block real customers. The platform patterns it
needs (feature stores, online/offline features, avoiding skew) are the backbone of every production ML system.

## Stripe Radar

Stripe has described Radar in its engineering blog:
- Radar decides in **under 100 ms** whether a payment is likely fraudulent, evaluating **more than 1,000
  characteristics** of the transaction.
- Fraud is rare: roughly **1 in 1,000** payments. Radar wrongly blocks about **0.1%** of legitimate payments. With
  such a skewed base rate, even a small false-positive rate means many good customers blocked: a tuning trade-off,
  not a solved problem.
- Models moved from logistic regression to an XGBoost + deep network ensemble, and in mid-2022 to a single,
  multi-branch deep network (inspired by ResNeXt). Dropping XGBoost cut training time by over 85%, to under two hours,
  which lets them retrain and experiment more often.
- Its advantage is **network data**: a card seen in fraud at one merchant is a signal at every other.

## Uber Michelangelo

Uber's 2017 post on Michelangelo, its ML platform, is the reference design for an in-house ML platform:
- A shared **feature store** of about 10,000 features, shareable across teams, with owners and SLAs.
- **Offline features** computed from the HDFS data lake with Spark/Hive for training and batch prediction.
- **Online features** precomputed into Cassandra for serving: batch-loaded (a restaurant's average prep time over
  7 days) or **near-real-time** via Kafka + Samza streaming (average prep time over the last hour).
- Serving: P95 under **5 ms** for models without Cassandra features, under **10 ms** with them; the busiest models
  served over **250,000 predictions per second**.
- Workflow: manage data → train → evaluate → deploy → predict → monitor.

## Online vs offline features

| | Offline | Online |
|--|---------|--------|
| Used for | Training, batch scoring, analysis | Real-time scoring |
| Store | Warehouse / data lake (Parquet, Hive, BigQuery) | Key-value: Redis, Cassandra, DynamoDB |
| Freshness | Hours to a day | Seconds |
| Read pattern | Scan millions of rows | Point lookup by key in ~1-5 ms |
| Example | Card's chargeback rate over 180 days | Payments on this card in the last 10 minutes |

A **feature store** (Michelangelo's, Feast, Tecton, cloud equivalents) defines each feature **once** and materialises
it to both stores.

```
payment events ─► Kafka ─► stream processor (Flink): windowed counts per card/device/IP/merchant
                               ├─► online store (Redis)     ← read at scoring time
                               └─► offline store (log)      ← training with point-in-time joins
```

## Training-serving skew

The silent killer of ML systems: the model sees different feature values in production than in training.

| Cause | Example | Fix |
|-------|---------|-----|
| Two implementations | Training SQL counts refunds; serving code doesn't | One feature definition for both paths |
| **Time leakage** | Training uses "chargebacks on this card" computed *today*, including ones that happened *after* the payment | **Point-in-time joins**: features as of the event timestamp |
| Freshness mismatch | Training assumes real-time counts; serving's stream lags 5 minutes | Model the lag in training, or monitor and alert on lag |
| Defaults | Missing feature = 0 in training, null → error in serving | Shared preprocessing code |

Best defence: **log the features used at serving time** with each prediction, and train on those logs ("log and
wait"), so training sees exactly what serving saw.

## Labels arrive late

A chargeback can come **weeks to months** after the payment. So the latest training data has incomplete labels, and
fraudsters adapt faster than labels arrive. Use proxy labels (early refunds, manual review outcomes), retrain
frequently, and combine the model with **rules** analysts can deploy in minutes ("block cards from this BIN range
over 500 EUR"). Radar, too, combines ML with rules users can write.

## Real-time scoring architecture

```
checkout ─► payments API ─► fraud service (deadline 50 ms)
                              ├─ fetch online features (Redis, batched MGET)       ~3 ms
                              ├─ model inference (CPU, in-process or sidecar)       ~5-10 ms
                              ├─ rules engine (allow/deny lists, velocity rules)    ~1 ms
                              └─ decision: allow / 3-D Secure challenge / block / review queue
                              └─ log features + score + decision ─► Kafka
on timeout or error: fail open with limits (allow small amounts, challenge large ones)
```

The failure mode is a business decision: fraud service down should not mean all payments down ([lesson 29.6](#/lesson/29.6)), nor
"allow everything".

## Try it

Score payments in 50 ms (p99) at 10,000 payments/s peak.

<details>
<summary>Reference</summary>

- **Budget:** network in/out 5 ms, features 10 ms, model 15 ms, rules 2 ms, slack ~15 ms.
- **Features:** Flink computes per-card, per-device, per-IP and per-merchant counters (1 min, 1 h, 24 h windows)
  into Redis Cluster; one batched read of ~20 keys per payment: 200k key reads/s, comfortably sharded.
  Slow-moving features (180-day chargeback rate) loaded nightly into the same store.
- **Model:** gradient-boosted trees or a compact DNN served in-process on CPU (no network hop), ~1-5 ms; scale the
  fraud service horizontally (10k/s ÷ ~1k/s per instance ≈ 10 instances + headroom, multi-AZ).
- **Fallback:** if features or model time out at 40 ms, use rules only; decide fail-open limits with the risk team.
- **Skew:** one feature definition for stream and backfill; log served features with each score and train on them.
- **Loop:** decisions and later chargebacks → labels; retrain weekly, monitor score distribution drift daily.
</details>

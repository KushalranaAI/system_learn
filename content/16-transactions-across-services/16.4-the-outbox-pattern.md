# The outbox pattern

Almost every service has this code:

```python
db.commit(order)          # 1
broker.publish(OrderPlaced(order))   # 2
```

If the process crashes between 1 and 2, the order exists but **no one hears about it**: no email, no stock
reservation, no analytics. Swap the order and a crash after publishing announces an order that **never committed**.
This is the **dual-write problem**: two systems, no shared transaction.

## The fix: write the event in the same transaction

```sql
BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (id, aggregate_id, type, payload, created_at)
       VALUES (gen_random_uuid(), 42, 'OrderPlaced', '{...}', now());
COMMIT;
```

The order and its event now commit (or fail) **atomically**: one database, one transaction.

## Relaying the outbox

Something must move outbox rows to the broker:

| Relay | How | Notes |
|-------|-----|-------|
| **Polling publisher** | A worker selects unpublished rows, publishes them, marks them sent | Simple; adds polling load and a little latency |
| **Change data capture (CDC)** | Tail the database's log (WAL/binlog) and publish outbox inserts (e.g. Debezium) | Low latency, no polling, preserves commit order |

Either way, delivery is **at-least-once**: a crash after publishing but before marking sent republishes. Consumers
dedupe by the event's `id` (lesson 15.4).

## Ordering

Publish per aggregate in order: use `aggregate_id` as the partition key, and relay in commit order (CDC does this
naturally). Consumers then see `OrderPlaced` before `OrderPaid` for the same order.

## The inbox (consumer side)

The mirror image: a consumer records each processed event id in an `inbox` table **in the same transaction** as its
own changes. Redelivered events hit the unique id and are skipped. Outbox on the producer + inbox on the consumer =
effectively-once between services.

## Housekeeping

- Delete or archive published outbox rows (e.g. after 7 days) so the table stays small.
- Monitor the outbox **age**: unpublished rows older than N seconds means the relay is stuck.
- Keep payloads versioned (schema registry, lesson 11.3).

## Try it

A signup flow does: insert user → publish `UserSignedUp` (welcome email, CRM sync). Occasionally new users get no
welcome email, and the logs show the broker was briefly unavailable. Redesign it.

<details>
<summary>Answer</summary>

Insert the user **and** an outbox row (`UserSignedUp`) in one transaction. A CDC or polling relay publishes the event
whenever the broker is reachable, retrying as needed. The email and CRM consumers dedupe by event id. A broker outage
now only delays welcome emails instead of losing them.
</details>

## Key takeaways

- Writing to a database and a broker separately loses or invents events on crashes.
- The outbox writes the event in the same DB transaction as the change.
- A polling or CDC relay publishes outbox rows at-least-once; consumers dedupe.
- Pair it with an inbox on consumers, and monitor outbox age.

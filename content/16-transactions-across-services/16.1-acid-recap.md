# ACID recap

Before splitting a transaction across services, be precise about what a single-database transaction actually gives
you, and what it quietly doesn't at default settings.

## ACID

| Letter | Promise |
|--------|---------|
| **Atomicity** | All of the transaction's changes happen, or none do |
| **Consistency** | Constraints (foreign keys, uniqueness, checks) hold before and after |
| **Isolation** | Concurrent transactions don't see each other's half-done work, *to a degree set by the isolation level* |
| **Durability** | Once committed, it survives crashes |

## Isolation levels and their anomalies

| Anomaly | What happens |
|---------|--------------|
| **Dirty read** | You read another transaction's uncommitted change, which is then rolled back |
| **Non-repeatable read** | You read a row twice and get different values |
| **Phantom** | You re-run a query and new rows appear |
| **Lost update** | Two read-modify-write transactions overwrite each other |
| **Write skew** | Two transactions each check a condition, then write different rows, together breaking the rule |

| Level | Prevents | Notes |
|-------|----------|-------|
| Read uncommitted | (almost nothing) | Rarely used |
| **Read committed** | Dirty reads | **Postgres default.** Lost updates and write skew are still possible |
| Repeatable read / snapshot | + non-repeatable reads, (mostly) phantoms | Each transaction sees one snapshot; Postgres also detects lost updates here |
| **Serializable** | Everything: as if transactions ran one at a time | Some transactions abort and must be retried |

## The lost update

```sql
-- two concurrent requests, both at read committed:
SELECT stock FROM items WHERE id = 7;      -- both read 5
UPDATE items SET stock = 4 WHERE id = 7;   -- both write 4 → one sale "vanished"
```

Fixes:
- an **atomic update**: `UPDATE items SET stock = stock - 1 WHERE id = 7 AND stock > 0`;
- a **row lock**: `SELECT … FOR UPDATE` before modifying;
- **optimistic concurrency**: a `version` column with `WHERE version = :read_version`.

## Write skew

Rule: at least one doctor must be on call. Alice and Bob are both on call; both check "is anyone else on call?" (yes)
and both go off call, each updating *their own* row. No row conflicted, yet the rule is broken.

Fixes: run at **serializable**, or lock the rows the decision depends on (`SELECT … FOR UPDATE` on all on-call
doctors), or materialise the constraint into a row both must update.

## Why this matters for microservices

Inside one database, these tools are cheap and reliable. Split the data across services and you lose them **across
the boundary**: no shared transaction, no cross-service locks, no constraints spanning services. The rest of this
module is about getting acceptable guarantees anyway.

## Try it

A wallet transfer runs at read committed:
`SELECT balance FROM wallets WHERE id = A` → check ≥ 100 → `UPDATE wallets SET balance = :new WHERE id = A` → credit B.
Two transfers of 100 from a wallet with 150 both succeed. Explain, and fix.

<details>
<summary>Answer</summary>

Both read 150, both pass the check, and both write 50: a lost update that let 200 leave a 150 wallet. Fix with an
atomic conditional update: `UPDATE wallets SET balance = balance - 100 WHERE id = A AND balance >= 100` (check that 1
row changed), debit and credit in the same transaction, or `SELECT … FOR UPDATE`, or serializable with retries.
</details>

## Key takeaways

- ACID's "I" depends on the isolation level; read committed allows lost updates and write skew.
- Use atomic conditional updates, row locks, version checks or serializable isolation.
- Know these tools well, because they don't cross service boundaries.

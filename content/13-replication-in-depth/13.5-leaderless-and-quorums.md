# Leaderless replication and quorums

No leader at all: clients (or a coordinator) send each write to **several replicas**, and read from several too.
Dynamo, Cassandra, ScyllaDB and Riak work this way.

## N, W, R

- **N**: how many replicas hold each key (often 3).
- **W**: how many must acknowledge a write before it counts.
- **R**: how many must answer a read.

If **W + R > N**, every read set overlaps every write set in at least one replica, so a read sees the latest
acknowledged write (with caveats below).

| N | W | R | W + R > N? | Character |
|---|---|---|------------|-----------|
| 3 | 2 | 2 | ✅ | Balanced: a common default ("quorum") |
| 3 | 3 | 1 | ✅ | Fast reads, slow and fragile writes |
| 3 | 1 | 3 | ✅ | Fast writes, slow reads |
| 3 | 1 | 1 | ❌ | Fastest; reads may be stale (eventual) |

Each read returns values with **versions**; the client takes the newest.

## Repairing stale replicas

- **Read repair:** when a read sees a replica with an old version, write the newest value back to it.
- **Anti-entropy:** a background process compares replicas (with Merkle trees, lesson 19.5) and fixes differences.
- **Hinted handoff:** if a replica is down during a write, another node keeps a "hint" and delivers it when the
  replica returns.

## Sloppy quorums

During failures, the system may accept writes on *any* W reachable nodes, even ones that aren't the key's usual
replicas. Availability goes up, but the W + R > N overlap guarantee no longer strictly holds until hinted handoff
completes.

## Caveats of "quorum consistency"

W + R > N is weaker than it sounds:
- **Concurrent writes** to the same key still conflict, and need resolution (last-write-wins by timestamp can lose
  data, lesson 12.5).
- A write that reached fewer than W nodes **fails**, but isn't rolled back on the nodes it did reach; later reads may
  or may not see it.
- Sloppy quorums break the overlap temporarily.

For strict guarantees (linearisability), you need consensus (lesson 13.3) or extra mechanisms.

## Tunable per request

Many leaderless databases let you pick the consistency per query:

```
Cassandra: CONSISTENCY LOCAL_QUORUM   -- majority within the local data centre
           CONSISTENCY ONE            -- fastest, may be stale
```

Use stronger levels for important reads and writes, weaker ones for high-volume, tolerant data.

## Try it

N = 3. You need writes to survive one replica being down, and reads to see the latest acknowledged write. Choose W and
R. Then: what if you need writes to keep working with **two** replicas down?

<details>
<summary>Answer</summary>

**W = 2, R = 2**: writes succeed with one replica down, and 2 + 2 > 3 gives overlap. With two replicas down, only
**W = 1** keeps writes working. To keep overlap, R must then be 3, so reads fail whenever any replica is down.
Otherwise accept stale reads (R = 1), or raise N to 5 (W = 3, R = 3 tolerates two failures).
</details>

## Key takeaways

- Leaderless systems write to and read from several replicas; there's no failover.
- With N replicas, W + R > N makes read and write sets overlap.
- Read repair, anti-entropy and hinted handoff heal stale replicas.
- Quorums don't remove conflicts; tune consistency per request.

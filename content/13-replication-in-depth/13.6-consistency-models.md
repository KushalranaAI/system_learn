# Consistency models

"Is it consistent?" has no yes/no answer. A **consistency model** is a precise promise about what reads can return
given the writes that happened. Stronger promises are easier to program against, and cost more.

## The spectrum

| Model | Promise | Example of what it rules out |
|-------|---------|------------------------------|
| **Linearizable** (strong) | Behaves like one copy; once a write completes, every later read sees it | Reading the old balance after a transfer returned "done" |
| **Sequential** | All nodes see operations in the same order (not necessarily real-time order) | Two users seeing two writes in opposite orders |
| **Causal** | If A could have caused B, everyone sees A before B | Seeing a reply before the message it replies to |
| **Read-your-writes / monotonic reads** | Per-session guarantees (lesson 13.2) | Your own comment vanishing on refresh |
| **Eventual** | If writes stop, replicas eventually converge | Nothing in the short term; you may read anything recent |

Stronger at the top: more coordination, more latency, less availability during partitions.

## CAP

During a network **P**artition, a system must choose for each operation between:
- **C**onsistency (linearizable): refuse or wait, rather than return possibly stale data;
- **A**vailability: answer anyway, possibly with stale data or accepting conflicting writes.

There's no "pick two out of three", because partitions aren't optional. CAP says: **when partitioned, choose C or A.**

## PACELC: the everyday tradeoff

Partitions are rare. Latency is constant. PACELC adds: **E**lse (no partition), choose **L**atency or
**C**onsistency.

| System | If partitioned | Else |
|--------|----------------|------|
| Single-leader SQL with sync replica | C (minority stops) | C (waits for the sync copy) |
| Dynamo-style, low quorums | A | L |
| Spanner / CockroachDB | C | C (pays latency for consensus) |

## Choosing per feature

You don't pick one model for the whole system. Pick per operation:

| Feature | Needs | Why |
|---------|-------|-----|
| Bank transfer, inventory decrement | Linearizable (or serializable transactions) | Money and stock must not double-spend |
| Username uniqueness | Linearizable | Two people can't claim one name |
| Chat messages in a thread | Causal + per-thread order | Replies after questions |
| Profile edits | Read-your-writes | The author must see the change |
| Like counts, view counts | Eventual | Approximate is fine |
| Search index | Eventual | Seconds of delay are fine |

## Try it

Classify each requirement by the weakest model that's still correct:
1. "After I change my password, the old one must stop working everywhere immediately."
2. "Comments should appear under the post they reply to, never before it."
3. "The trending list can be a minute old."

<details>
<summary>Answer</summary>

1. **Linearizable** for the credential check: route auth to the leader or a consensus store.
2. **Causal.**
3. **Eventual.**
</details>

## Key takeaways

- Consistency models are precise promises about what reads can return.
- Linearizable is strongest and costliest; eventual is weakest and cheapest; causal is often the sweet spot.
- CAP: under partition, choose consistency or availability. PACELC: otherwise, latency or consistency.
- Choose the model per feature, not per system.

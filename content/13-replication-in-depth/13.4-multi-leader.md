# Multi-leader replication

With single-leader replication, a user in São Paulo writing to a leader in Mumbai pays ~300 ms per write. Put a
**leader in each region**, let each accept local writes, and replicate between them asynchronously.

```
   Mumbai leader  ⇄  async  ⇄  Frankfurt leader  ⇄  async  ⇄  São Paulo leader
        ▲                           ▲                            ▲
   local writes               local writes                 local writes
```

## What you gain

- **Local write latency** everywhere.
- **Region independence:** a region keeps accepting writes even when cut off from the others.
- **Offline clients** are a form of multi-leader too: a phone app editing locally and syncing later behaves exactly
  like a tiny leader.

## The price: write conflicts

Two regions can change the same record at the same time:

```
Mumbai:    title = "Q3 plan"     (10:00:00.100)
Frankfurt: title = "Q3 roadmap"  (10:00:00.120)
both replicate → each region now has a different value
```

Single-leader systems never face this. Multi-leader systems must **resolve** every conflict (lesson 13.7), and the
resolution must be deterministic, so all regions end up with the same result.

## Avoiding conflicts

The most practical strategy is to make conflicts rare:
- **Home each record in one region** (a user's data is written in their home region). It's effectively single-leader
  per record, with multi-leader across records.
- **Partition by ownership:** documents edited mostly by one team live in that team's region.
- **Append-only data** (comments, events) rarely conflicts: two new comments are both kept.

## Other pitfalls

- **Auto-increment ids** collide across leaders. Use UUIDs or Snowflake ids (lesson 12.6).
- **Constraints** (unique usernames, "stock ≥ 0") can't be enforced locally: two regions may both accept the last
  item. Route such operations to a single home region, or accept compensating actions.
- **Replication topology:** with more than two leaders, changes can arrive out of order through different paths.
  Version vectors help detect that.

## Try it

A global note-taking app wants fast saves everywhere. Most notes are edited by one person; some are shared and edited
by a team. Choose a replication strategy.

<details>
<summary>Answer</summary>

Home each note in its **owner's region** (single-leader per note): saves are local for the owner, and other regions
read async copies. For shared notes edited concurrently, use a CRDT or operational-transform merge (lesson 13.7) so
concurrent edits combine instead of overwriting. Accept a short delay for collaborators far from the home region.
</details>

## Key takeaways

- Multi-leader gives local writes and region independence.
- The price is write conflicts, which must be resolved deterministically.
- Avoid conflicts by homing records, partitioning by ownership, and preferring append-only data.
- Global constraints and ids need special care.

# Resolving conflicts

Multi-leader, leaderless and offline-first systems all hit the same moment: two replicas hold **different values for
the same thing**, both legitimately written. Something must decide the final value, the same way on every replica.

## Detecting conflicts

First, know that a conflict happened. **Version vectors** (lesson 12.5) track which writes each version has seen:

```
v1 = {mumbai: 3, frankfurt: 1}
v2 = {mumbai: 2, frankfurt: 2}
neither dominates the other → concurrent → conflict
```

If one version dominates (it has seen everything the other has), just keep the newer one. There's no conflict.

## Resolution strategies

| Strategy | How | Risk |
|----------|-----|------|
| **Last-write-wins (LWW)** | Keep the highest timestamp | Silently loses the other write; clock skew picks the "wrong" one |
| **Merge by rule** | Domain-specific merge (union of sets, max of counters, per-field merge) | Must be designed per data type |
| **Keep both (siblings)** | Store both versions; let the app or user choose | Pushes complexity to the app and UI |
| **CRDTs** | Data types whose merges always converge | Limited to the supported types; metadata overhead |
| **Operational transform (OT)** | Transform concurrent edit operations against each other | Complex; usually needs a central server |

LWW is fine for data where losing a concurrent update is acceptable (a cache entry, "last seen" time). It's dangerous
for anything users care about.

## CRDTs: conflict-free replicated data types

CRDTs are designed so that **any order of merges gives the same result**: merges are commutative, associative and
idempotent.

| CRDT | Use | How it merges |
|------|-----|---------------|
| **G-Counter** | Grow-only counter | Each replica counts separately; value = sum; merge = per-replica max |
| **PN-Counter** | Counter with increments and decrements | Two G-Counters (plus and minus) |
| **G-Set / OR-Set** | Sets (tags, likes, cart items) | Union; OR-Set tracks unique add ids so removes work |
| **LWW-Register** | A single value | Highest timestamp (documented, deliberate LWW) |
| **Sequence CRDTs** (RGA, Yjs, Automerge) | Collaborative text | Every character has a unique, ordered id |

Collaborative editors (Figma-style multiplayer, Yjs/Automerge-based apps) use CRDTs so every client converges with no
central lock.

## Shopping-cart example

```
Phone (offline):  add "shoes"
Laptop:           add "socks", remove "hat"
merge with an OR-Set → {shoes, socks}    (the hat stays removed; both adds kept)
```

With LWW on the whole cart, one device's changes would simply disappear.

## Design advice

- **Avoid conflicts first:** home records in one region, make data append-only (lesson 13.4).
- For each data type, decide: is LWW acceptable? If not, define a merge or use a CRDT.
- Make resolution **deterministic**: every replica must reach the same answer independently.
- Surface true business conflicts (two people booked the last room) to humans or compensating processes.

## Try it

A to-do app syncs across devices offline. Both devices edit the same item: one ticks "done", the other renames it.
LWW on the whole item loses one change. What's better?

<details>
<summary>Answer</summary>

Merge **per field**: `done` from one edit, `title` from the other. Each field is its own LWW register (or `done` is a
flag that wins once set, if that's the product rule). Only concurrent edits to the *same* field need a tie-break.
</details>

## Key takeaways

- Detect concurrent writes with version vectors before resolving.
- LWW is simple but loses data; use it only where that's acceptable.
- CRDTs merge deterministically for counters, sets, registers and text.
- Avoid conflicts by design; make resolution deterministic; escalate real business conflicts.

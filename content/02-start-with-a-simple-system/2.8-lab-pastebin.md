# Lab: a pastebin

A pastebin lets anyone paste text, get a short link, and share it. It's small enough to design end-to-end, and it
touches everything in this module.

> **Interactive version:** [open the Pastebin lab](#/labs/pastebin) to design the API and build the system on the
> simulator canvas. This page is the paper version with reference answers.

## Requirements

**Functional**
1. Create a paste (text up to 1 MB) and get a link back.
2. Read a paste by its link.
3. Pastes can expire (10 minutes, 1 day, 1 week, never).

**Non-functional**
- 200 reads/s and 2 creates/s at launch; plan for 3,000 reads/s.
- Reads p99 < 100 ms.
- Links must not be guessable. People paste private things.

## Step 1: Estimate

<details>
<summary>Reference</summary>

- 2 creates/s × 86,400 s ≈ 170k pastes/day ≈ **63M/year**.
- Average paste ~10 KB → 1.7 GB/day → **~630 GB/year**. That's too much for one database long-term, so plan to
  move bodies to object storage later and keep them in Postgres for now.
- Read:write ≈ 100:1, so it's read-heavy (caching comes in Module 3).
</details>

## Step 2: API

<details>
<summary>Reference</summary>

```
POST /pastes        { content, expires_in }        → 201 { id, url, expires_at }
GET  /pastes/:id                                    → 200 { content, created_at, expires_at }
                                                    → 404 if missing or expired
```
Creating uses an `Idempotency-Key` header so a retried create doesn't make two pastes.
</details>

## Step 3: Data model

<details>
<summary>Reference</summary>

```sql
CREATE TABLE pastes (
  id          text PRIMARY KEY,          -- 8 random base62 chars ≈ 2.2 × 10^14 options
  content     text NOT NULL CHECK (octet_length(content) <= 1048576),
  created_at  timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz                 -- NULL = never
);
CREATE INDEX pastes_expiry ON pastes (expires_at) WHERE expires_at IS NOT NULL;
```
- **Random ids**, not auto-increment: `/pastes/1001` would let anyone walk through every paste.
- The primary key is already an index, so `GET` by id is a single index lookup.
- The partial index lets a cleanup job delete expired rows cheaply:
  `DELETE FROM pastes WHERE expires_at < now() LIMIT 10000`.
- On an id collision (astronomically rare), the insert fails on the primary key; generate a new id and retry.
</details>

## Step 4: Architecture v1

<details>
<summary>Reference</summary>

```
Client ─▶ API server ─▶ Postgres
                    └─▶ cleanup job every minute: delete expired rows
```
At 200 reads/s, one small server and one small database are plenty (in the simulator: ~10% busy). The read path is one
round trip to the DB with an index lookup, about 10–20 ms.
</details>

## Step 5: 3,000 reads/s

Scale **up** first: a bigger server and a bigger database. It's the cheapest change and adds nothing to operate. In
Module 3 you'll add a cache, and in Module 4 a load balancer.

## Reflect

- What breaks first if a single paste goes viral at 50,000 reads/s?
- When would you move paste bodies out of Postgres, and into what?

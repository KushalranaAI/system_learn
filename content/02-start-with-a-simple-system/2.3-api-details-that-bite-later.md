# API details that bite later

Four decisions look small on day one and are very hard to change once clients depend on them.

## 1. Pagination

Never return "all the things". Lists grow.

### Offset pagination
```
GET /posts?limit=20&offset=40
```
- ✅ Simple; you can jump to page 7.
- ❌ `OFFSET 100000` makes the database walk and throw away 100,000 rows, so it gets slower the deeper you go.
- ❌ If a new post arrives while someone is paging, items shift: they see duplicates or miss items.

### Cursor (keyset) pagination
```
GET /posts?limit=20&after=2026-10-24T10:15:00Z_9481
→ { "items": [...], "next": "2026-10-24T09:58:12Z_9460" }
```
```sql
SELECT * FROM posts
WHERE (created_at, id) < ('2026-10-24 10:15:00', 9481)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```
- ✅ Every page costs the same, thanks to an index on `(created_at, id)`.
- ✅ Stable while new items arrive.
- ❌ No "jump to page 7".

**Default to cursors** for feeds and anything large. Make the cursor an **opaque** string (base64 it), so you can
change what's inside later.

## 2. Filtering and sorting

```
GET /orders?status=shipped&created_after=2026-10-01&sort=-created_at
```
- Only allow filters and sorts **you've indexed for**. An open-ended `?sort=anything` lets one client run a full table
  scan.
- Validate and reject unknown parameters with `400`.

## 3. Versioning

Clients you don't control (mobile apps!) keep calling old shapes for years.

| Approach | Example |
|----------|---------|
| URL version | `/v1/notes` → `/v2/notes` |
| Header version | `Accept: application/vnd.notes.v2+json` |

Most teams use the URL: it's visible and easy to route. Either way:
- **Adding** a field is safe. Clients must ignore fields they don't know.
- **Removing or renaming** a field, or changing its type, is a breaking change that needs a new version.

## 4. Idempotency keys

A phone sends `POST /payments`, the network drops, and the app retries. Did the first one go through? Without
protection, you might charge twice.

```http
POST /payments
Idempotency-Key: 6f1c0e4a-2b7d-4a55-9a43-5e0f0b6a7c11

{ "amount": 4999, "currency": "INR" }
```

The server stores the result per key:

```
first request  → key unseen → process payment → save (key → response) → 201
retry          → key seen   → return the saved response, process nothing → 201
```

- Clients generate the key once per *intent* (one tap of "Pay"), not once per attempt.
- Keep keys for a sensible window (say 24 h) and scope them per user.
- Save the key and the effect in **one transaction**, or a crash between the two brings the duplicate back.

## Try it

A social app's `GET /feed?page=N` uses offset pagination. Users complain they see the same post twice while
scrolling, and page 500 takes 4 seconds. Redesign it.

<details>
<summary>Answer</summary>

Switch to a cursor: `GET /feed?limit=20&after=<cursor>` with an index on `(created_at, id)` and a `WHERE` on the
cursor values. Every page becomes an index range scan (constant time), and new posts don't shift what you've already
seen. Return `next` in the response; clients just follow it.
</details>

## Key takeaways

- Prefer cursor pagination with an opaque cursor; offsets get slow and unstable.
- Only expose filters and sorts that are indexed.
- Additive changes are safe; anything else needs a new version.
- Idempotency keys turn "retry" from dangerous into safe for POSTs.

# Modelling data

Code is easy to change. Data that's already stored, billions of rows of it, is not. A good data model makes the
common queries simple and the wrong states impossible.

## Entities and keys

Start from the nouns in your requirements. For an online course platform: **user, course, lesson, enrolment,
progress**.

Each entity becomes a table with a **primary key**: a value that identifies exactly one row.

```sql
CREATE TABLE users (
  id          bigserial PRIMARY KEY,
  email       text NOT NULL UNIQUE,
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

Choosing ids:

| Kind | Pros | Cons |
|------|------|------|
| Auto-increment (`bigserial`) | Small, fast, ordered | Guessable (`/users/1001`); needs one place to hand them out |
| UUID v4 | Unguessable; any server can make one | 16 bytes; random order spreads index writes |
| Time-ordered (UUID v7, Snowflake) | Unique anywhere *and* roughly ordered | Slightly more machinery |

## Relationships

**One-to-many:** a course has many lessons. Put the foreign key on the "many" side.

```sql
CREATE TABLE courses (id bigserial PRIMARY KEY, title text NOT NULL, author_id bigint NOT NULL REFERENCES users(id));
CREATE TABLE lessons (
  id         bigserial PRIMARY KEY,
  course_id  bigint NOT NULL REFERENCES courses(id),
  position   int    NOT NULL,
  title      text   NOT NULL,
  UNIQUE (course_id, position)
);
```

**Many-to-many:** users enrol in many courses, and courses have many users. Use a **join table**, which often carries
its own data.

```sql
CREATE TABLE enrolments (
  user_id     bigint NOT NULL REFERENCES users(id),
  course_id   bigint NOT NULL REFERENCES courses(id),
  enrolled_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, course_id)          -- can't enrol twice
);
```

```
users 1───* enrolments *───1 courses 1───* lessons
```

## Let the database enforce the rules

Constraints are rules the database guarantees, even when your code has a bug or two requests race each other.

| Constraint | Prevents |
|------------|----------|
| `NOT NULL` | Missing required data |
| `UNIQUE` | Duplicate emails, double enrolments |
| `REFERENCES` (foreign key) | Lessons pointing at deleted courses |
| `CHECK (price >= 0)` | Impossible values |

## Normalise first

**Normalisation** means storing each fact once. The author's name lives in `users`, not copied into every course row.
Change it once and it's right everywhere.

Later, for speed, you may **denormalise** on purpose: copy `author_name` into `courses` to skip a join on a hot page.
That's a tradeoff (lesson 1.5). You now have to keep the copies in sync, so do it deliberately and write it down.

## Model the access patterns

List the queries before finalising tables:

1. "Show a course with its lessons in order": `lessons WHERE course_id = ? ORDER BY position`.
2. "My courses": `enrolments WHERE user_id = ?`.
3. "Mark lesson done, show % complete": needs a progress table.

```sql
CREATE TABLE lesson_progress (
  user_id      bigint NOT NULL REFERENCES users(id),
  lesson_id    bigint NOT NULL REFERENCES lessons(id),
  completed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, lesson_id)
);
```

If a query has no good path through your tables, the model isn't done yet.

## Try it

Model a **library app**: books, physical copies of each book, members, and loans (a member borrows a copy and returns
it later). A copy can only be on one active loan at a time.

<details>
<summary>One possible model</summary>

```sql
books   (id PK, isbn UNIQUE, title, author)
copies  (id PK, book_id FK → books, barcode UNIQUE)
members (id PK, email UNIQUE, name)
loans   (id PK, copy_id FK → copies, member_id FK → members,
         borrowed_at, due_at, returned_at NULL)

-- at most one active loan per copy:
CREATE UNIQUE INDEX one_active_loan ON loans (copy_id) WHERE returned_at IS NULL;
```
The partial unique index makes "two people borrowed the same copy" impossible, even under races.
</details>

## Key takeaways

- Entities become tables; pick primary keys deliberately.
- One-to-many uses a foreign key on the many side; many-to-many uses a join table.
- Put rules in constraints so the database guarantees them.
- Normalise by default; denormalise on purpose, for measured reasons.
- Check every important query against the model.

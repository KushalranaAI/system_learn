# Measuring speed

"Is it fast?" means nothing without numbers. Two numbers describe speed: **throughput** and **latency**. One mistake
ruins most dashboards: looking at averages.

## Throughput vs latency

| | Throughput | Latency |
|-|-----------|---------|
| **Question** | How much work per second? | How long does one request take? |
| **Unit** | requests/s, queries/s, MB/s | milliseconds |
| **Analogy** | Cars per hour through a toll plaza | Time one car spends at the plaza |

They're linked. As throughput approaches a component's capacity, requests start to **queue**, and latency rises
sharply. You'll see this curve in the simulator (and in Module 4):

```
latency
   │                         ╱
   │                       ╱
   │                    ╱
   │             ___---
   │_____-------
   └──────────────────────────── utilisation
   0%                  85%   100%
```

## Percentiles, not averages

Suppose 99 requests take 20 ms and one takes 3,000 ms. The average is ~50 ms and looks fine. But **one user in a
hundred waited three seconds**, and a page that makes 20 API calls hits that slow one most of the time.

| Metric | Meaning |
|--------|---------|
| **p50** (median) | Half of requests are faster than this |
| **p95** | 95% are faster; 1 in 20 is slower |
| **p99** | 99% are faster; 1 in 100 is slower |
| **p99.9** | the tail: 1 in 1,000 |

**Targets are written as percentiles**: "p99 < 200 ms for `GET /feed`". The simulator in this course reports p99 for
the same reason.

### Tail latency multiplies

If one page load calls 10 services in parallel, each with a 1% chance of being slow, the page is slow whenever *any*
of them is:

```
P(page is fast) = 0.99^10 ≈ 0.90   → 10% of page loads hit someone's p99
```

That's why big systems care so much about p99 and p99.9.

## A latency budget

Split your target across the hops a request takes.

**Target: `GET /product/:id` p99 < 150 ms**

| Hop | Budget |
|-----|--------|
| Network to the user (CDN edge → origin) | 40 ms |
| Load balancer | 2 ms |
| API server (auth, logic, serialisation) | 20 ms |
| Cache lookup | 2 ms |
| Database query (on a cache miss) | 15 ms |
| Calls to the pricing service | 30 ms |
| **Headroom** | 41 ms |

When something gets slower, the budget tells you who's over. Without one, everyone is "a bit slow" and nobody owns it.

## Measure it

- **Load test** before launch with k6, Locust or wrk. Ramp traffic up until latency bends, and note that point.
- **Measure in production** with histograms (Prometheus, OpenTelemetry) per endpoint: p50, p95, p99, plus error rate
  and throughput.
- Watch the **four golden signals**: latency, traffic, errors, saturation.

## Try it

An endpoint has p50 = 30 ms, p99 = 900 ms. The team says "it's fast, average is 45 ms."
1. What does the p99 tell you?
2. Name two common causes of a long tail.

<details>
<summary>Answer</summary>

1. 1 in 100 requests waits nearly a second, and pages making many calls will hit it often.
2. Common causes: queueing when a component runs near capacity; garbage-collection pauses; a cache miss falling
   through to a slow query; lock contention; retries after timeouts; a noisy neighbour on shared hardware.
</details>

## Key takeaways

- Throughput is work per second; latency is time per request. Near capacity, latency rises steeply.
- Use percentiles (p95, p99), never just averages.
- Tail latency compounds when a request fans out to many services.
- Give every endpoint a latency budget split across its hops.

# Anatomy of a request

You type `notes.app/n/42` and press Enter. About 200 ms later the note is on screen. Before you design anything, it
helps to know where those milliseconds go.

## The journey

```
Browser ──1. DNS──▶ "notes.app = 203.0.113.7"
        ──2. TCP handshake──▶ server
        ──3. TLS handshake──▶ server        (now encrypted)
        ──4. HTTP request: GET /n/42──▶ API server ──5. SQL──▶ Database
        ◀──────── 6. HTTP response: 200 OK + JSON ◀────────
```

| Step | What happens | Typical cost |
|------|--------------|--------------|
| **1. DNS lookup** | Turn the name into an IP address. Usually cached by the browser and OS | 0 ms cached, 20–100 ms cold |
| **2. TCP handshake** | SYN → SYN-ACK → ACK opens a reliable connection | 1 round trip |
| **3. TLS handshake** | Agree on keys and check the server's certificate | 1 round trip (TLS 1.3) |
| **4. HTTP request** | Method, path, headers, maybe a body | 1 round trip, plus server time |
| **5. Server work** | Parse, authenticate, query the DB, build the response | 1–50 ms in a healthy system |
| **6. Response** | Status code, headers, body; bigger bodies take longer to send | depends on size |

A **round trip** costs whatever the distance costs: about 1 ms inside a city, 70 ms across a continent, 200 ms across
the world. A cold request from far away pays for 3+ round trips **before your code even runs**.

## What this means for design

- **Reuse connections.** HTTP keep-alive and HTTP/2 skip steps 2–3 for every request after the first. Your servers
  should also keep connection pools to the database.
- **Move closer to users.** A CDN or a regional server cuts the round-trip cost, which no code optimisation can do.
- **Count your hops.** Each call your server makes to another service or database adds at least one network round
  trip, plus that service's queueing time.

## HTTP in one minute

```http
GET /n/42 HTTP/1.1
Host: notes.app
Authorization: Bearer eyJhbGciOi...
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=0

{"id": 42, "title": "Groceries", "body": "milk, eggs"}
```

- The **method** says what you want to do (`GET` read, `POST` create…).
- The **path** says which thing.
- **Headers** carry metadata: auth, content type, caching rules.
- The **status code** says how it went (`200` OK, `404` not found, `500` server broke).

## Try it

Open your browser's dev tools (F12) → **Network** tab, and reload any website. Click the first request and open
**Timing**.
1. How long did DNS, the initial connection and SSL take?
2. How long was "Waiting for server response"? That's the server's own time.
3. Reload again. What disappeared, and why?

<details>
<summary>What you should see</summary>

On a second load, DNS, connection and SSL usually drop to about 0 because the browser cached the DNS answer and
reused the open connection. What's left is mostly server time plus one round trip.
</details>

## Key takeaways

- A request pays for DNS, TCP, TLS and HTTP round trips before your code runs.
- Distance sets the cost of each round trip, so reuse connections and get close to users.
- Every extra hop on the server side adds latency, so keep the hot path short.

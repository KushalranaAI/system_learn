# Choosing a database

"Which database should we use?" is the wrong first question. The right one is: **what are the access patterns, and
what guarantees does the data need?**

## The main families

| Family | Examples | Data shape | Shines at | Struggles with |
|--------|----------|-----------|-----------|----------------|
| **Relational** | Postgres, MySQL | Tables, rows, joins | Transactions, constraints, flexible queries | Massive write scale on one node |
| **Document** | MongoDB, Firestore | JSON-like documents | Reading/writing a whole object at once; evolving fields | Joins across documents, multi-document transactions |
| **Key-value** | Redis, DynamoDB | `key → value` | Very fast lookups by key, huge scale | Any query not by key |
| **Wide-column** | Cassandra, ScyllaDB | Rows partitioned by key, sorted columns | Enormous write volume, time series | Ad-hoc queries, strong consistency |
| **Search** | Elasticsearch, OpenSearch | Inverted indexes | Full-text search, faceting | Being the source of truth |
| **Graph** | Neo4j | Nodes and edges | Deep relationship traversals | Bulk analytics, simple CRUD at scale |
| **Object storage** | S3, GCS | Files (blobs) | Images, video, backups, cheap and durable | Small, frequent updates; queries |

## A decision path

1. **Is it files (images, video, PDFs)?** Use object storage. Keep only metadata (owner, size, URL) in a database.
2. **Do you need transactions across several records** (money, inventory, bookings)? Use relational.
3. **Do you need flexible queries you can't predict yet?** Use relational.
4. **Is every access "get or put by a known key" at huge scale?** Use key-value or wide-column.
5. **Is it search over text?** Use a search engine, fed from your main database.

For most new products the answer is: **Postgres for the core data, object storage for files, Redis for caching.** Add
specialised stores when a measured need appears.

## Access patterns decide

Same app, different stores per feature:

| Feature | Access pattern | Good fit |
|---------|----------------|----------|
| Orders and payments | Transactions, constraints, reporting | Postgres |
| Product images | Large immutable blobs, served via CDN | S3 + CDN |
| Shopping cart | Read and write by `user_id`, short-lived | Redis or DynamoDB |
| Product search | Full text, filters, typo tolerance | OpenSearch |
| Click events | Append-only firehose, aggregated later | Kafka → columnar warehouse |

Using several stores is called **polyglot persistence**. Every extra store adds operations work and a new sync
problem, so justify each one.

## SQL vs NoSQL myths

- *"NoSQL scales, SQL doesn't."* A well-indexed Postgres on one large machine handles tens of thousands of queries a
  second, and replicas and partitioning go further (Modules 5 and 9).
- *"NoSQL means no schema."* The schema still exists, just in your code. Someone must handle old document shapes.
- *"Pick one forever."* Data can move later. That's expensive, but not impossible, so choose for the next 2–3 years.

## Try it

Pick a store for each:
1. A ride app's live driver locations, updated every 4 s, read "near me".
2. A bank's account balances and transfers.
3. User-uploaded profile photos.
4. A chat app's message history: billions of messages, always read by conversation, newest first.

<details>
<summary>Answers</summary>

1. **Redis** (geo commands) or another in-memory store: data is tiny, changes constantly and is useless after seconds.
2. **Relational** (Postgres): transfers need atomic multi-row transactions and strict constraints.
3. **Object storage + CDN**, with the URL in the users table.
4. **Wide-column** (Cassandra-style), partitioned by `conversation_id`, sorted by time. Postgres also works for a long
   time with the right index, and partitioning later.
</details>

## Key takeaways

- Start from access patterns and guarantees, not brand names.
- Relational is the default for core data; files go to object storage.
- Specialised stores solve specific problems, and each one costs operations work.
- Different features can use different stores.

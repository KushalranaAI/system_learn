# Designing an HTTP API

The API is the contract between your clients and your servers. Clients will depend on it for years, so it's worth
getting the shape right before writing code.

## Think in resources

Name the **things** (nouns), then use HTTP methods as the **verbs**.

| Action | Method + path | Success |
|--------|---------------|---------|
| List my notes | `GET /notes` | `200 OK` |
| Read one note | `GET /notes/:id` | `200 OK` |
| Create a note | `POST /notes` | `201 Created` |
| Replace a note | `PUT /notes/:id` | `200 OK` |
| Edit some fields | `PATCH /notes/:id` | `200 OK` |
| Delete a note | `DELETE /notes/:id` | `204 No Content` |
| Notes in a folder | `GET /folders/:id/notes` | `200 OK` |

Avoid verbs in paths (`/createNote`, `/getNotes`): the method already says it.

## Methods have promises

| Method | Safe (no changes)? | Idempotent (repeat = same result)? |
|--------|--------------------|------------------------------------|
| GET | ✅ | ✅ |
| PUT | ❌ | ✅ |
| DELETE | ❌ | ✅ |
| PATCH | ❌ | usually not |
| POST | ❌ | ❌ |

These promises matter. Browsers, proxies and retry logic assume a `GET` changes nothing, and that repeating a `PUT`
or `DELETE` is harmless. A `POST` that's retried after a timeout can create two notes. Lesson 2.3 fixes that.

## Status codes that matter

| Code | Meaning | Use when |
|------|---------|----------|
| 200 | OK | Success with a body |
| 201 | Created | A `POST` made something; include its location or body |
| 204 | No Content | Success with nothing to return |
| 301 / 302 | Moved | Redirects: permanent / temporary |
| 400 | Bad Request | The input is invalid |
| 401 | Unauthorized | Not logged in |
| 403 | Forbidden | Logged in, but not allowed |
| 404 | Not Found | No such resource (or you mustn't know it exists) |
| 409 | Conflict | The state conflicts (already exists, version mismatch) |
| 422 | Unprocessable | Well-formed but semantically wrong input |
| 429 | Too Many Requests | Rate limited |
| 500 | Internal Error | A bug on your side |
| 503 | Unavailable | Overloaded or down; try again later |

Rule of thumb: **4xx = the client should change something; 5xx = the server failed.** Retry logic depends on this
split, because retrying a 400 never helps while retrying a 503 often does.

## Request and response bodies

```http
POST /notes
Content-Type: application/json

{ "title": "Groceries", "body": "milk, eggs", "folder_id": 7 }
```

```http
201 Created
Location: /notes/42

{ "id": 42, "title": "Groceries", "body": "milk, eggs", "folder_id": 7,
  "created_at": "2026-10-24T10:15:00Z" }
```

- The **server** assigns ids and timestamps. Never trust the client for those.
- Return the created object, so the client doesn't need a second request.
- Use one error shape everywhere:
  ```json
  { "error": { "code": "title_required", "message": "A note needs a title." } }
  ```

## REST, gRPC or GraphQL?

| Style | Good for |
|-------|----------|
| **REST + JSON** | Public APIs, browsers, caching; the default choice |
| **gRPC** | Service-to-service calls: fast binary format, typed contracts, streaming |
| **GraphQL** | Many different clients needing different slices of a large data graph |

Start with REST. Reach for the others when you feel a specific pain they solve.

## Try it

Design the API for a **to-do app**: lists, items in lists, marking an item done, and sharing a list with a friend.
Write method, path and success status for each.

<details>
<summary>One possible answer</summary>

```
GET    /lists                       200
POST   /lists                       201
GET    /lists/:id/items             200
POST   /lists/:id/items             201
PATCH  /items/:id    {done: true}   200
DELETE /items/:id                   204
POST   /lists/:id/members {email}   201   (409 if already shared)
```
Marking done is a `PATCH` of one field. Sharing creates a membership, which is a resource of its own.
</details>

## Key takeaways

- Model resources as nouns; HTTP methods are the verbs.
- Respect method promises: GET is safe, PUT and DELETE are idempotent, POST is not.
- Use precise status codes, because clients and retries depend on the 4xx/5xx split.
- The server owns ids and timestamps; use one consistent error shape.

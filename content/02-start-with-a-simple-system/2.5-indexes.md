# Indexes

Your `orders` table has 50 million rows. `SELECT * FROM orders WHERE user_id = 42` takes 9 seconds. Add one index and
it takes 2 milliseconds. Indexes are the single biggest performance lever in most backends.

## What an index is

Without an index, the database reads **every row** to find matches (a *sequential scan*). An index is a separate
sorted structure, usually a **B-tree**, that maps column values to row locations, like the index at the back of a book.

```
B-tree on user_id
            [ 500 | 1000 ]
          /       |        \
   [..|42|..]  [..|..]   [..|..]      ← leaf pages: user_id → row pointers
        │
        └─▶ rows 18, 9031, 77211 ...
```

Finding a key takes a handful of page reads (log of the row count), not millions.

## What indexes speed up

A B-tree index on `(user_id)` helps:
- `WHERE user_id = 42`
- `WHERE user_id IN (1, 2, 3)`
- `WHERE user_id BETWEEN 10 AND 20`
- `ORDER BY user_id` (already sorted)

It does **not** help:
- `WHERE lower(email) = 'x'` unless the index is on `lower(email)`
- `WHERE name LIKE '%son'` (a leading wildcard can't use the sort order)

## Composite indexes and column order

```sql
CREATE INDEX orders_user_created ON orders (user_id, created_at DESC);
```

This is sorted by `user_id` first, then by `created_at` within each user. So it serves:
- `WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20` ✅ (perfect: no sort needed)
- `WHERE user_id = 42` ✅
- `WHERE created_at > '2026-10-01'` ❌ (`created_at` isn't the leading column)

**Leftmost-prefix rule:** a composite index helps queries that filter on its leading columns. Put equality columns
first, then range or sort columns.

## Reading a query plan

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;
```

```
Limit  (actual time=0.041..0.072 rows=20)
  ->  Index Scan using orders_user_created on orders  (rows=20)
        Index Cond: (user_id = 42)
Planning Time: 0.1 ms   Execution Time: 0.09 ms
```

Look for:
- **Seq Scan** on a big table: usually a missing index.
- **Sort** above a scan: an index in the right order could remove it.
- **Estimated vs actual rows** far apart: stale statistics (`ANALYZE` the table).

## Indexes aren't free

| Cost | Why |
|------|-----|
| Slower writes | Every `INSERT`/`UPDATE` must also update every index on the table |
| Disk and memory | Indexes can be as large as the table; they compete for RAM |
| Planner confusion | Too many similar indexes and the planner may pick a poor one |

Index for the queries you **actually run**, and check periodically for indexes nobody uses.

## Special-purpose indexes

| Index | For |
|-------|-----|
| **Unique** | Enforcing uniqueness (doubles as a lookup index) |
| **Partial** (`WHERE status = 'active'`) | Indexing only the rows you query |
| **Covering** (`INCLUDE (total)`) | Answering a query from the index alone, without reading the table |
| **GIN** | Full-text search, JSONB, arrays |
| **GiST / BRIN** | Geo data / huge append-only tables like logs |

## Try it

The query is
`SELECT id, total FROM orders WHERE status = 'pending' AND created_at < now() - interval '1 hour'`.
99% of orders are `completed`. What index would you add?

<details>
<summary>Answer</summary>

A **partial index**: `CREATE INDEX pending_old ON orders (created_at) INCLUDE (total) WHERE status = 'pending';`.
It only contains the 1% of rows that are pending, so it's tiny and cheap to maintain. It's sorted by `created_at`
for the range condition, and `INCLUDE (total)` lets the query skip reading the table at all.
</details>

## Key takeaways

- Without an index the database scans everything; a B-tree finds rows in a few page reads.
- In composite indexes, column order matters: equality columns first, then range or sort columns.
- Use `EXPLAIN ANALYZE` to see what the database really does.
- Every index slows writes and costs memory, so index the queries you run.

# Streaming and perceived latency

A good answer from a large model often takes 5-15 seconds to generate. You usually can't make that number small,
but you can change what the user **experiences**: the first words on screen after half a second feel fast, even if
the last word arrives eight seconds later. This lesson covers token streaming, the infrastructure it needs, one
technique that really does make generation faster (speculative decoding), and how to budget latency for an AI feature.

## Token streaming over SSE

Model APIs can return tokens as they are decoded. The standard transport to the browser is **server-sent events**
(SSE): a normal HTTP response with `Content-Type: text/event-stream` that stays open and sends small chunks.

```
browser ──POST /chat──► API server ──stream=true──► model API
        ◄── data: {"delta":"The"}      ◄── token
        ◄── data: {"delta":" refund"}  ◄── token
        ◄── ...
        ◄── data: [DONE]
```

SSE suits this better than WebSockets for most chat UIs: one direction, plain HTTP, works through proxies and CDNs,
easy to authenticate. WebSockets make sense when the client also streams (voice, collaborative editing). See
[lesson 6.1](#/lesson/6.1) for the general comparison.

## What streaming does to your infrastructure

| Concern | What to do |
|---------|------------|
| Proxy buffering | Turn it off for the stream route (e.g. nginx `proxy_buffering off` or the `X-Accel-Buffering: no` header), or tokens arrive in one lump at the end |
| Idle and total timeouts | LB, proxy and CDN timeouts must exceed the longest generation; send a keep-alive comment every ~15 s |
| Concurrent connections | 100 chats/s × 8 s each = 800 open streams per server fleet: size by connections, as in [lesson 6.2](#/lesson/6.2) |
| Cancellation | When the user closes the tab or presses stop, **abort the upstream call**: otherwise you pay for and occupy GPU time for tokens nobody reads |
| Errors mid-stream | The 200 status is already sent; signal errors as an event and let the client offer "retry" |
| Moderation | Output filters must run on partial text (chunks or sentences), or you lose streaming's benefit (lesson 29.3) |
| Resumption | For long answers, persist tokens as they arrive so a reconnect can resume ([lesson 6.5](#/lesson/6.5)) |

## Perceived latency: what users feel

Two numbers from 26.2 decide the experience:

- **TTFT**: the wait before anything happens. Users notice above about 1 s.
- **Tokens per second**: people read about 4-5 words per second. A stream at 30+ tokens/s outpaces reading, so
  making it faster barely changes perceived speed for prose. It matters for code, long documents and agents, where
  someone waits for the whole result.

So for chat, **optimise TTFT first**: shorter prompts, prefix caching (26.5), a closer region, less queueing on the
GPUs, and doing slow steps (retrieval, reranking, tool calls) in parallel rather than in sequence.

Other UI moves that buy patience:

- Show progress for the steps before the first token ("Searching 3 help articles...").
- Render the citations or the sources as soon as retrieval finishes, before the answer.
- Ask the model to answer first and elaborate after, so the useful sentence is the first one.
- For non-chat features, precompute in the background (summaries generated when a ticket arrives, not when an agent
  opens it).

## Speculative decoding: actually faster tokens

Decode is memory-bound: the GPU reads all the weights to produce a single token and leaves compute idle (26.3).
Speculative decoding uses that spare compute:

```
1. a small draft model (or extra heads on the big model) guesses the next k tokens: "the refund will be"
2. the big model checks all k positions in ONE forward pass
3. accept the longest correct run of guesses, plus one token from the big model; discard the rest
```

With the right acceptance rule the output distribution is **the same** as the big model alone: it is a pure latency
optimisation, not a quality trade. The original papers reported about 2-3x faster generation; real gains depend on how
predictable the text is (code and structured output accept more guesses than creative prose) and drop at large batch
sizes, where compute is no longer idle. Variants like Medusa and EAGLE attach draft heads to the target model instead of
running a separate draft model. vLLM, SGLang and TensorRT-LLM support it, and API providers use it behind the scenes.

## A latency budget for an AI feature

Budget it like any request path in [lesson 12.2](#/lesson/12.2), but split into "before the first token" and
"streaming":

| Step | Budget (p95) |
|------|--------------|
| Gateway, auth, rate limit | 20 ms |
| Embed query | 30 ms |
| Vector + keyword search (in parallel) | 50 ms |
| Rerank top 50 | 120 ms |
| Model queueing + prefill (TTFT) | 500 ms |
| **First token on screen** | **~0.75 s** |
| Stream 400 tokens at 60/s | 6.7 s |

Every step before the model is pure added TTFT. If retrieval grows to 1.5 s through sequential calls, the user waits
2+ s for the first word, and no streaming will hide it.

## Explore it

In the sandbox, the LLM node's latency is its time to first token; turning batching on adds about 30% to it in
exchange for several times the throughput. Wire a cache and vector DB in front in the
[chat serving scenario](#/sandbox?preset=ai-chat-serving) and read the end-to-end latency along the path.

## Try it

Your "summarise this ticket thread" button takes **6 seconds** before anything appears, then shows the whole
summary at once. Make it feel instant.

<details>
<summary>Reference</summary>

1. **Stream it.** Switch to SSE; disable proxy buffering. The first words appear after TTFT (~0.5-1 s) instead of 6 s.
2. **Trim TTFT.** Put the static instructions first so they hit the prefix cache; drop quoted email history and
   signatures from the thread before sending.
3. **Shape the output.** Ask for a one-line summary first, then bullets; cap `max_tokens`. Shorter output also cuts
   total time.
4. **Precompute.** Generate the summary in a background job ([lesson 7.1](#/lesson/7.1)) when a new message arrives,
   store it next to the ticket, and show it instantly; regenerate on change. The button now reads from the database.
5. **Show progress** if anything is still slow ("Reading 23 messages..."), and allow cancelling, which aborts the
   upstream call.
6. If generation itself is still the bottleneck, use a smaller model for summaries, or speculative decoding if you
   self-host.
</details>

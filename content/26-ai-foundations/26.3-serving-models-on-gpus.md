# Serving models on GPUs

If you self-host a model, or just want to understand why API providers behave the way they do, the whole game is
**GPU memory**. It holds the weights and the KV cache, and the KV cache decides how many requests you can serve at
once. This lesson does the memory math, then shows the two ideas that made modern serving engines (vLLM, SGLang,
TensorRT-LLM) fast: continuous batching and PagedAttention.

## Memory part 1: the weights

```
weight bytes = parameters × bytes per parameter
```

| Model | FP16/BF16 (2 B) | FP8 / INT8 (1 B) | INT4 (0.5 B) |
|-------|-----------------|------------------|--------------|
| 8B | 16 GB | 8 GB | ~4-5 GB |
| 70B | **140 GB** | 70 GB | ~35-40 GB |
| 405B | 810 GB | 405 GB | ~200+ GB |

An H100 or H200 has 80 or 141 GB of HBM. A 70B model in FP16 does not fit on one 80 GB GPU, so you split it across
GPUs with **tensor parallelism** (each layer's matrices split across GPUs on fast NVLink inside one server). Across
servers you add **pipeline parallelism** (different layers on different machines), which costs more in latency.

## Memory part 2: the KV cache

During decode, each new token attends to every previous token. Recomputing the keys and values for all of them at
every step would be wasteful, so the engine keeps them: the **KV cache**.

```
KV bytes per token = 2 (K and V) × layers × kv_heads × head_dim × bytes per value
```

For Llama 3 70B (80 layers, 8 KV heads thanks to grouped-query attention, head_dim 128) in FP16:

```
2 × 80 × 8 × 128 × 2 B = 327,680 B ≈ 0.33 MB per token
```

| Sequence length | KV cache for one sequence |
|-----------------|---------------------------|
| 2k tokens | 0.67 GB |
| 8k tokens | 2.7 GB |
| 32k tokens | 10.7 GB |
| 128k tokens | 42 GB |

Without grouped-query attention (64 KV heads instead of 8) it would be 8x larger, 2.6 MB per token. This is why
model architecture choices like GQA matter to whoever runs the fleet.

## Putting it together: how many users fit?

Four 80 GB H100s = 320 GB. Engines reserve some memory for activations and runtime (vLLM uses 90% by default):

```
usable      = 320 × 0.9            = 288 GB
weights     = 140 GB (FP16)
KV budget   = 288 − 140            = 148 GB
tokens      = 148 GB / 0.33 MB     ≈ 450,000 tokens of KV cache
concurrency ≈ 450k / 4k avg context ≈ 110 sequences, or ≈ 14 at 32k
```

On **two** GPUs the weights fit (160 × 0.9 = 144 GB) but leave 4 GB, about 12k tokens: one user. "It fits" and "it
serves" are different questions. The KV budget, not the weights, sets your concurrency.

## Batching: why it matters so much

Decode is memory-bandwidth-bound (26.2): each step reads all 140 GB of weights to produce one token. If 64 sequences
share that step, the same read produces 64 tokens. Throughput rises almost linearly with batch size until compute or
KV memory runs out, while each user's tokens/s drops only a little.

**Static batching** groups requests and runs them until the longest one finishes:

```
req A ████████████████████████  (500 tokens)
req B ████░░░░░░░░░░░░░░░░░░░░  (finished at 80, slot idle)
req C ██████████░░░░░░░░░░░░░░  (finished at 200, slot idle)
new requests wait for the whole batch
```

**Continuous batching** (iteration-level scheduling, introduced by the Orca paper) re-forms the batch at **every
decode step**: finished sequences leave, waiting ones join immediately. No idle slots, no waiting for the slowest.
Anyscale measured up to about 23x throughput over naive per-request serving with it combined with memory
optimisations.

## PagedAttention

Early engines reserved one contiguous KV region per request sized for the maximum length. Most requests are much
shorter, so most of that memory sat empty: fragmentation and over-reservation wasted a large share of KV memory.

**PagedAttention** (the vLLM paper, 2023) borrows virtual memory from operating systems:

```
logical KV of a sequence:  [blk 0][blk 1][blk 2][blk 3 (partly full)]
block table:                  │      │      │      │
physical GPU memory:       [ 17 ] [ 3 ] [ 42 ] [ 8 ]   fixed-size blocks, e.g. 16 tokens each
```

- Memory is allocated in small blocks on demand, so waste is limited to the last block of each sequence (the vLLM
  team reports under 4%).
- More sequences fit, so batches are bigger, so throughput rises: the paper reports 2-4x over earlier systems.
- Blocks can be **shared**: several samples of one prompt, or many requests with the same system prompt, point at the
  same physical blocks. This is the basis of automatic prefix caching (26.5).

When KV memory does run out, the scheduler **preempts** a sequence (evicts its blocks and recomputes later). That shows
up as latency spikes under load: watch KV cache utilisation as a first-class metric.

## Quantisation

Storing weights (and sometimes the KV cache) in fewer bits halves or quarters memory and the bytes read per decode
step:

| Option | Memory vs FP16 | Quality | Use |
|--------|----------------|---------|-----|
| FP8 weights (+ FP8 KV) | 1/2 | usually close to FP16 | default on H100-class GPUs |
| INT4 (AWQ, GPTQ) | ~1/4 | small but measurable loss | fit big models on fewer GPUs |
| FP8 KV cache only | KV 1/2 | small loss | double concurrency |

70B in FP8 on two H100s: 144 − 70 = 74 GB of KV budget, about 225k tokens. Always re-run your evals after
quantising; the loss is task-dependent.

## Operational consequences

- **Scale on the right metric.** CPU is meaningless; scale on queue depth, KV cache utilisation and TTFT.
- **Cold starts are slow.** Pulling and loading 140 GB of weights takes minutes, so keep warm capacity; you can't
  autoscale from zero for a spike the way you would stateless web servers.
- **Long prompts hurt neighbours.** A 100k-token prefill stalls decode for everyone in the batch. Engines use
  **chunked prefill**, and large fleets **disaggregate** prefill and decode onto separate GPU pools.
- **Route by prefix.** Sending requests that share a prefix to the same replica raises prefix cache hits (26.5).

## Try it

You must serve Llama 3 70B to **50 concurrent users with up to 8k tokens of context each**, on 80 GB H100s. How many
GPUs do you need in FP16? What changes with FP8 weights and an FP8 KV cache?

<details>
<summary>Reference</summary>

- KV: 50 × 8,192 × 0.33 MB ≈ **134 GB**. Weights: **140 GB**. Total ≈ 274 GB.
- 4 GPUs give 288 GB usable at 90%: it just fits with ~14 GB of headroom. Tensor parallelism of 4 works well (64
  attention heads and 8 KV heads divide evenly). For safety at peak, use **8 GPUs** (two replicas of 4) or accept
  queueing.
- FP8 weights (70 GB) + FP8 KV (67 GB) = 137 GB: fits on **2 GPUs** (144 GB usable), barely. Comfortable on 4 with
  room for ~3x the users. Re-run your quality evals before switching.
- Remember 8k is the maximum; if the average context is 3k, the real KV need is ~50 GB and continuous batching with
  paged KV lets you pack many more users in.
</details>

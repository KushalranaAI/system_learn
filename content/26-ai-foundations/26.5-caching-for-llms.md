# Caching for LLMs

In module 3 a cache saved a 5 ms database read. In front of a model, a cache hit saves **seconds and real money** on
every request. But "the same request" is fuzzier for prompts than for URLs, and a wrong cache hit doesn't return
stale data, it returns a confidently wrong answer. There are three different caches here, at three different layers.

| Cache | Key | Saves | Hit rate | Risk |
|-------|-----|-------|----------|------|
| Exact response cache | hash of the full request | the whole call | low for chat, high for fixed prompts | stale answers |
| Prefix (prompt) cache | the leading tokens of the prompt | prefill compute and input cost | high if prompts are structured for it | almost none |
| Semantic cache | embedding of the query | the whole call | medium | **wrong answers** |

## 1. Exact response cache

The familiar cache-aside pattern ([lesson 3.3](#/lesson/3.3)) in Redis:

```
key = sha256(model + version + system_prompt + messages + temperature + tools + tenant)
```

- Every input that changes the output must be in the key: model version, parameters, retrieved context, and anything
  user-specific. Forgetting the tenant leaks one customer's answer to another.
- Great for **deterministic, repeated work**: classifying the same product title, summarising the same article,
  generating descriptions in a batch job. Use temperature 0 for these.
- Poor for open chat: almost no two conversations are byte-identical.
- Invalidate when the model, prompt template or source data changes: put a version number in the key
  ([lesson 3.5](#/lesson/3.5)).

## 2. Prefix caching (prompt caching)

This one lives **inside the serving engine**. Prefill computes the KV cache for the prompt (26.3). If the next
request starts with the same tokens, the engine can reuse those KV blocks instead of recomputing them. vLLM does it
automatically by hashing each full KV block together with everything before it, so a block hash identifies the whole
prefix up to that point.

Model APIs expose the same idea: OpenAI caches automatically for prompts over about 1,024 tokens; Anthropic lets you
mark cache breakpoints. Cached input tokens are billed at a steep discount, roughly 50-90% off depending on the
provider, and TTFT drops because prefill is skipped. Entries expire after minutes of inactivity.

The design rule is about **prompt layout**: static first, variable last.

```
GOOD                                     BAD
[system prompt, 2,000 tokens]  cached    [today's date + user name]   ← breaks the prefix
[tool definitions, 1,500]      cached    [system prompt]                 nothing after this
[help articles, 6,000]         cached    [tool definitions]              is reused
[conversation history]         cached*   [conversation history]
[new user message]                       [new user message]
* each turn extends the previous turn's prefix
```

A timestamp or request ID at the top of the prompt silently disables prefix caching. Self-hosted fleets also need
**prefix-aware routing**: a load balancer that sends requests with the same prefix to the same replica, since the
KV cache lives in that replica's GPU memory (consistent hashing, [lesson 19.1](#/lesson/19.1)).

## 3. Semantic cache

Embed the user's query (27.2), look up the nearest previous query in a vector index, and if it is similar enough,
return the stored answer.

```
query ──► embed (~10-30 ms) ──► ANN search (~5 ms) ──► similarity ≥ threshold? ──yes──► cached answer
                                                              │no
                                                              └──► LLM ──► store (embedding, answer)
```

"How do I reset my password?" and "forgot my password, how to change it" can share one answer. Open-source tools
like GPTCache and several gateways implement this. In the sandbox, a cache node placed in front of an LLM acts as a
semantic cache.

### Its wrong answers

Embeddings measure topical similarity, not equivalence of meaning:

| Query A (cached) | Query B (new) | Similar? | Same answer? |
|------------------|---------------|----------|--------------|
| How do I cancel my order? | How do I **not** cancel my order? | very | no |
| Shipping cost to **Canada** | Shipping cost to **Mexico** | very | no |
| What's my balance? (user 17) | What's my balance? (user 42) | identical | **no, and a data leak** |
| Is the API down? (yesterday) | Is the API down? (now) | identical | no, stale |

Defences:

- **Scope the cache.** Only cache answers that don't depend on the user or on time; partition by tenant, language,
  and product version; never cache answers built from private data across users.
- **Threshold high**, tuned on labelled pairs (see Try it), and per use case.
- **Short TTLs** for anything time-sensitive; invalidate when source documents change.
- **Cache retrieval, not answers**, when answers must be personal: reuse the retrieved documents but still generate.
- Track **false-hit rate** from sampled reviews and thumbs-down on cached answers.

## Where the caches sit

```
client ─► gateway ─► [exact cache] ─► [semantic cache] ─► model API / vLLM (prefix cache inside)
```

Exact and semantic caches save the whole call; the prefix cache makes the calls that do happen cheaper. Most
production systems get the biggest, safest win from the prefix cache.

## Explore it

The [semantic cache simulation](#/sims/semantic-cache) lets you move the similarity threshold and watch hit rate

## Try it

You labelled 10 query pairs from your logs. Pick a similarity threshold for a semantic cache in a support bot.

| Pair | Cosine similarity | Same answer? |
|------|-------------------|--------------|
| 1 | 0.98 | yes |
| 2 | 0.97 | yes |
| 3 | 0.96 | no (different country) |
| 4 | 0.95 | yes |
| 5 | 0.94 | yes |
| 6 | 0.93 | no (negation) |
| 7 | 0.92 | yes |
| 8 | 0.90 | no |
| 9 | 0.88 | yes |
| 10 | 0.85 | no |

<details>
<summary>Reference</summary>

At each threshold, count hits (pairs at or above it) and wrong hits:

| Threshold | Hits | Wrong hits | Precision |
|-----------|------|------------|-----------|
| 0.97 | 2 | 0 | 100% |
| 0.95 | 4 | 1 | 75% |
| 0.92 | 7 | 2 | 71% |
| 0.85 | 10 | 4 | 60% |

Only a threshold of 0.97 or higher keeps pair 3 out, and it catches just 2 of the 6 equivalent pairs. For a support
bot a wrong answer costs much more than a miss, so pick **0.97**, and fix pair 3's failure mode another way:
partition the cache by country (it's in the user's profile), and add a cheap check for negation words. Then
re-test: with the country partition, 0.95 may become safe. Ten pairs is far too few for a real decision; label a few
hundred, and set the threshold per intent.
</details>

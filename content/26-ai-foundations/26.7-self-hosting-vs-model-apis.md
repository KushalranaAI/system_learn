# Self-hosting vs model APIs

"Should we run our own models?" is the AI version of "should we run our own data centre?". APIs are pay-per-token
with zero fixed cost; self-hosting is a fixed monthly GPU bill whose cost per token depends entirely on how busy you
keep the GPUs. This lesson turns that into a break-even calculation, then covers the reasons that aren't about cost.

## Two cost curves

```
monthly cost
   │                                   / API: price × tokens (a straight line)
   │                                 /
   │                    ___________/_____  self-hosted: steps of fixed GPU replicas
   │         __________|         /
   │  ______|          break-even
   │_|_____________/________________________ tokens per month
```

- **API:** cost = tokens × price per million. No idle cost, no capacity planning, elastic to the provider's rate
  limits.
- **Self-hosted:** cost = replicas × GPU price × hours, plus engineers to run it. Each replica handles a fixed
  throughput, so the curve is a staircase. You pay for peak capacity (and redundancy) all month.

## Cost per million tokens when self-hosting

```
cost per 1M tokens = hourly cost of a replica / (tokens per second × 3,600 × utilisation / 1,000,000)
```

Example with assumed numbers (measure your own; GPU prices vary widely by provider and commitment, roughly $2-6 per
H100-hour on demand, less with reservations):

| Item | Value |
|------|-------|
| Replica | 70B model in FP8 on 4 H100s |
| GPU cost | 4 × $3/hour = $12/hour ≈ $8,800/month |
| Throughput at good batching | assume 3,000 tokens/s (input + output) |
| At 100% utilisation | 10.8M tokens/hour → **$1.11 per 1M tokens** |
| At 30% average utilisation | **$3.70 per 1M tokens** |

**Utilisation is the whole game.** Traffic is diurnal: if your peak is 3x your average, a fleet sized for the peak
averages ~33% busy. You also need a spare replica for failures and deploys. The provider pools thousands of
customers' traffic and keeps its GPUs much busier than you can, which is a big part of why APIs are often cheaper.

Ways to raise utilisation: fill the troughs with batch work (embeddings, evals, back-fills at night), use smaller or
quantised models (26.3), share one fleet across features, and burst to an API at peak instead of buying for peak.

## The break-even point

```
fixed monthly cost F  = replicas × replica cost + operations (people, monitoring, on-call)
API cost              = T (millions of tokens/month) × P (blended $ per 1M)
break-even            T* = F / P
```

Then **check capacity**: the fleet that costs F must actually serve T* at peak. If not, F steps up and so does T*.

Worked example. Two replicas (one for redundancy) = $17,600/month; half an engineer's time ≈ $10,000/month; so
F ≈ $27,600.

| Blended API price for a comparable model | Break-even tokens/month | Average tokens/s |
|------------------------------------------|-------------------------|------------------|
| $1 per 1M (cheap hosted open model) | 27.6B | ~10,500 |
| $5 per 1M (mid-tier) | 5.5B | ~2,100 |
| $15 per 1M (frontier) | 1.8B | ~700 |

Two caveats. First, compare against an API serving a model **of similar quality**: self-hosting an open 70B model is
cheap, but if your product needs a frontier model you cannot self-host it at all. Second, hosted open-weight models
from inference providers are often priced close to their cost, so the realistic comparison for a 70B model may be
the first row.

## Reasons that aren't cost

| Factor | Favours self-hosting | Favours APIs |
|--------|----------------------|--------------|
| Data control | Data must not leave your network or region; regulated industries | Provider terms (no training on API data, regional endpoints, private deployments in your cloud) are enough |
| Model quality | An open model meets your eval bar | You need the best available model |
| Customisation | Fine-tuned weights, custom decoding, LoRA adapters per tenant | Prompting plus retrieval is enough |
| Latency | Co-located with your services; dedicated capacity, no noisy neighbours | Providers' global footprint and speculative decoding are hard to beat |
| Rate limits | No provider quota; your own capacity | Spiky traffic that needs elastic capacity |
| Team | You have people who can run GPU fleets | You don't, and won't hire them |
| Velocity | Stable workload | New models every few months; switching is a config change behind a gateway |

A middle path is common: dedicated or "provisioned throughput" capacity from a cloud provider, open models served by a
specialist inference provider, or self-hosting the high-volume simple task (classification, embeddings) while
sending complex requests to an API through the same gateway (26.4).

## Try it

Your product does 20,000 conversations a day, about 7,000 tokens each (input + output), with a peak 3x the average.
A comparable API costs about $3 per 1M tokens blended. Using the replica above (3,000 tokens/s, $8,800/month) and
$10,000/month of operations, find the break-even and decide.

<details>
<summary>Reference</summary>

- Volume: 20,000 × 7,000 = 140M tokens/day ≈ **4.2B tokens/month**. Average 1,620 tokens/s, peak ≈ 4,900 tokens/s.
- API cost: 4,200 × $3 ≈ **$12,600/month**.
- Self-hosting: the peak needs 2 replicas (6,000 tokens/s), plus one spare for failures = 3 × $8,800 = $26,400,
  plus $10,000 ops ≈ **$36,400/month**. Utilisation ≈ 1,620 / 9,000 ≈ 18%.
- Break-even at this fleet: 36,400 / 3 ≈ 12.1B tokens/month (~3x today's volume). But at 3x volume the peak is
  ~14,700 tokens/s, needing 5 replicas plus a spare, so F rises to ~$63,000 and the break-even moves to ~21B
  tokens/month. Each step of growth pushes it further while utilisation stays low.
- **Decision: use the API.** Revisit if volume grows by an order of magnitude, if a cheaper API is not allowed for
  data reasons, or if you can fill off-peak GPU time with batch work.
</details>

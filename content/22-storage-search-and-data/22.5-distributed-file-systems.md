# Distributed file systems

In 2003 Google described the **Google File System (GFS)**: one file system spanning thousands of cheap machines,
built on the assumption that disks and servers fail every day. Hadoop's **HDFS** copied the design, and Google's
successor **Colossus** fixed its biggest limit. The ideas (separate metadata from data, big chunks, replicate across
racks, repair automatically) underpin object stores (lesson 22.1) and most big-data storage today.

## The GFS / HDFS architecture

```
                     ┌──────────────────────────┐
   client ──meta───▶ │  master (GFS)            │  namespace: /logs/2026/10/24/part-0001
                     │  NameNode (HDFS)         │  file → [chunk handles]
                     │  all metadata in RAM     │  chunk → [chunkserver locations]
                     └──────────────────────────┘
      │                         ▲ heartbeats + chunk reports
      │ data (direct)           │
      ▼                         │
  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
  │chunksrv 1│ │chunksrv 2│ │chunksrv 3│ │chunksrv 4│ …  (DataNodes in HDFS)
  └──────────┘ └──────────┘ └──────────┘ └──────────┘
```

- Files are split into large **chunks**: 64 MB in GFS, 128 MB by default in HDFS. Big chunks keep metadata small and
  favour long sequential reads and writes, the workload these systems were built for (crawls, logs, MapReduce input).
- Each chunk is **replicated 3 times** on different machines and racks.
- The **master holds all metadata in memory**: fast lookups, but total file count is limited by its RAM. Metadata
  changes go to an **operation log** replicated to other machines, with periodic checkpoints.
- **Clients never move data through the master.** They ask "where is chunk 7 of this file?", cache the answer, and
  read from a chunkserver directly.

## A read

```
1. client → master: (file /logs/…/part-0001, chunk index 3)
2. master → client: handle 0x9f2a, replicas [cs-14 (same rack), cs-201, cs-388]
3. client → cs-14: read handle 0x9f2a bytes 0–1 MB      ← nearest replica
4. cs-14 verifies the block checksum; on mismatch the client reads another replica
   and the master re-replicates the corrupt one
```

## A write

GFS gives one replica a **lease** (time-limited, around 60 s) to act as **primary** for that chunk, so all replicas
apply mutations in the same order:

```
1. client asks master who holds the lease → primary cs-14, secondaries cs-201, cs-388
2. client pushes data along a chain: client → cs-14 → cs-201 → cs-388
   (pipelined, each forwards while still receiving: uses every link's bandwidth)
3. client → primary: "write"; primary assigns a serial number, applies, forwards order to secondaries
4. all ack → primary → client: success. Any failure → client retries.
```

GFS's relaxed consistency (retried **record appends** could leave duplicates or padding that readers had to skip)
pushed work onto applications. HDFS simplified to single-writer, append-only files.

## Placement: rack awareness

HDFS's default for 3 replicas: the first on the writer's node (or a random one), the second on a node in a
**different rack**, the third on another node in that same remote rack. One rack loss (a top-of-rack switch or power
failure) can't take all copies, while only one copy crosses between racks during the write.

## Detecting and repairing failure

HDFS DataNodes heartbeat every 3 seconds. After about **10.5 minutes** of silence, the NameNode declares the node
dead (the delay avoids re-replication storms from short blips such as a reboot). It then finds every block that has
dropped below its replication target and schedules copies from surviving replicas, prioritising blocks with only one
copy left.

Background **scrubbing** reads blocks and checks checksums to find silent corruption before a client does.

## The master problem, and Colossus

One master is simple but a ceiling: every file and block costs RAM (an often-quoted HDFS rule of thumb is about 150
bytes per object), so billions of small files exhaust it, and it's a single point of failure. HDFS added an HA standby
NameNode and **federation** (several NameNodes each owning part of the namespace).

Google's **Colossus** replaced the single master with metadata stored in **Bigtable**, scaling metadata horizontally,
and uses Reed–Solomon erasure coding for most data instead of plain 3× replication. Clients talk to "curators" for
metadata and to "D" file servers for data. Object stores followed the same path: a scalable metadata service plus
dumb storage nodes.

## Try it

A cluster has so many disks that **one fails every hour** on average. Each disk is 16 TB and 70% full. Show how the
system survives, and why repair must be spread out rather than sent to a hot spare.

<details>
<summary>Reference</summary>

Each failure leaves about 11.2 TB of blocks with one fewer replica.

- **Rebuild onto one replacement disk** at ~200 MB/s: 11.2 TB / 200 MB/s ≈ 56,000 s ≈ **15.5 hours**. With a failure
  every hour, about 15 more disks die during that window; some blocks will lose a second replica, and eventually some
  a third. Data loss becomes likely.
- **Many-to-many re-replication**: the lost blocks' surviving replicas are spread across the whole cluster, so with
  1,000 nodes each copying ~11 GB at a throttled 100 MB/s, repair finishes in about **2 minutes** of wall time
  (11.2 TB / 100 GB/s), long before the next failure. The window during which any block is under-replicated is tiny.

Also needed: rack-aware placement so correlated failures don't hit all replicas, prioritising blocks down to one copy,
a failure-detection delay long enough to ignore reboots but short enough to keep the window small, throttling so repair
doesn't starve user traffic, checksums and scrubbing, and enough free capacity everywhere to absorb the repaired data.
Replacing physical disks then becomes a weekly batch job, not an emergency.
</details>

## Key takeaways

- GFS/HDFS: one metadata master, many chunkservers; large chunks; clients move data directly.
- Three replicas across racks; leases give one primary per chunk to order writes.
- Heartbeats and block reports drive automatic re-replication; checksums and scrubbing catch corruption.
- The single in-memory master limits file counts; Colossus moved metadata into a scalable store and adopted erasure
  coding.
- Survive constant failure by repairing many-to-many across the cluster, fast.

# From MapReduce to Spark and dataflow

How do you compute something over 50 TB of logs? Not on one machine. Over 20 years the answer moved from
**MapReduce** (2004), to **Spark** (in-memory DAGs), to **dataflow** engines like Flink, Beam/Google Dataflow and
Kafka Streams that treat batch as a special case of streaming. Each step fixed the previous one's biggest cost.
Lessons 17.4 and 17.5 introduced stream processing and batch vs stream; this one shows the machinery.

## MapReduce: map, shuffle, reduce

Word count over a pile of documents:

```
input splits (one per HDFS block, lesson 22.5)
   │
 map(doc)            → emit (word, 1) for each word
   │                   "to be or not to be" → (to,1)(be,1)(or,1)(not,1)(to,1)(be,1)
   │ combiner (local pre-sum) → (to,2)(be,2)(or,1)(not,1)
   │
 SHUFFLE: partition each pair by hash(word) mod R, sort by key,
          write to local disk; each reducer pulls its partition from every mapper
   │
 reduce(word, [counts]) → (word, sum)       written to HDFS, 3 replicas
```

The framework handles the hard parts: running map tasks next to their data, retrying failed tasks (tasks are
deterministic, so re-running is safe), and **speculative execution**: when a few stragglers lag (a slow disk, a noisy
neighbour), launch backup copies and take whichever finishes first.

The cost: every job reads its input from the distributed file system and writes its output back, replicated. A
pipeline of 10 jobs (clean → join → aggregate → …) writes 10 full intermediate datasets to disk, and iterative
algorithms (machine learning, graph processing) pay that cost per iteration.

## The shuffle is the expensive part

Every engine since has the same core problem. A shuffle moves **every** record across the network to the machine that
owns its key:

- M mappers × R reducers = M × R small transfers (10,000 × 1,000 = 10 million).
- Data is serialised, often spilled to disk and sorted.
- **Skew**: if one key ("the", or one huge customer) has 10% of records, one reducer does 10% of the work alone and
  the job waits for it. Fixes: combiners, salting hot keys (`key#0..key#9`, then a second aggregation), or broadcast
  joins for small tables.

## Spark: DAGs in memory

Spark expresses a whole pipeline as a graph of transformations on datasets (RDDs, now DataFrames):

```python
logs   = spark.read.parquet("s3://logs/2026/10/")
errors = logs.filter(logs.status >= 500)                     # narrow
by_svc = errors.groupBy("service").count()                   # wide → shuffle
top    = by_svc.orderBy("count", ascending=False).limit(20)  # wide → shuffle
top.show()                                                   # action: now it runs
```

- **Lazy**: nothing runs until an action; the optimiser (Catalyst) sees the whole plan, pushes filters down into the
  Parquet scan, and reads only the needed columns (lesson 22.3).
- **Stages**: narrow transformations (filter, map) are pipelined inside one stage; each wide one (groupBy, join)
  ends a stage with a shuffle. This job is 3 stages.
- **In memory**: intermediate data stays in executors' memory where possible, instead of replicated files.
- **Lineage** for fault tolerance: a lost partition is recomputed from its parents, instead of being stored 3 times.

For multi-step and iterative work this is often 10× or more faster than chained MapReduce jobs.

## Dataflow: streams first

Batch jobs answer "what happened yesterday" hours late. Streaming engines run the same kind of DAG **continuously**
over unbounded input (Kafka topics), keeping state between events:

| Concept | Meaning |
|---------|---------|
| **Event time** vs processing time | When it happened vs when we saw it; mobile events can arrive hours late |
| **Windows** | Tumbling (each hour), sliding, session (until 30 min of inactivity) |
| **Watermark** | "I believe all events up to time T have arrived"; triggers window results |
| **Allowed lateness** | Accept and correct results for events behind the watermark, up to a limit |
| **State** | Per-key running values (counts, sums, last seen) stored locally, e.g. in RocksDB |

## Exactly-once, really

Messages will be redelivered after failures (lesson 15.4). "Exactly-once" in Flink and friends means the **effect on
state and output** is as if each event were processed once:

```
1. The source injects a checkpoint BARRIER into the stream (e.g. every 30 s).
2. Each operator, when the barrier has arrived on all its inputs, snapshots its state
   (to S3/HDFS) and forwards the barrier.
3. When every operator and the sink have acknowledged, checkpoint n is complete;
   Kafka source offsets are part of it.
4. On failure: restore all state from checkpoint n and rewind Kafka to its offsets.
   Events after n are replayed, but against state as of n, so they count once.
```

That covers internal state. For the **output** you need either a **transactional sink** (Kafka transactions committed
when the checkpoint completes: two-phase commit, lesson 16.2) or an **idempotent sink** (upsert by a deterministic key,
so a replayed write overwrites itself). Side effects like sending emails remain at-least-once; deduplicate them with
idempotency keys (lesson 12.4).

## Try it

A nightly batch job computes **daily revenue per merchant** from the day's payment records and writes it to a table
merchants see in their dashboard at 6 AM. Merchants want it live. Turn it into a streaming job.

<details>
<summary>Reference</summary>

- **Source**: payment events from Kafka (via the outbox pattern or CDC from the payments DB, lessons 16.4 and 17.3),
  partitioned by `merchant_id`.
- **Keying and windows**: key by `merchant_id`; a **tumbling 1-day event-time window** in the merchant's time zone,
  using the payment's timestamp, not arrival time.
- **Early results**: trigger every 30–60 s with the running sum, so the dashboard updates live; the final result fires
  when the watermark passes midnight.
- **Late events**: watermark with a few minutes of out-of-orderness; allowed lateness of, say, 2 days; late events
  update the window and re-emit.
- **Refunds and corrections**: treat them as negative events in the same stream.
- **State**: per merchant per open day, a sum and count, in RocksDB; checkpoints every 30 s to object storage.
- **Sink**: upsert into `merchant_daily_revenue (merchant_id, day) → revenue` keyed on that pair, so replays after
  recovery are idempotent.
- **Keep the batch job** as a nightly reconciliation that recomputes yesterday from the source of truth and fixes any
  drift; it also handles backfills when the logic changes. Alert if streaming and batch disagree beyond a threshold.
</details>

## Key takeaways

- MapReduce: map, shuffle by key, reduce; simple and fault tolerant, but every job round-trips through disk.
- The shuffle (network, sorting, skew) dominates the cost in every engine.
- Spark builds a lazy DAG, pipelines narrow steps into stages, keeps data in memory and recovers by lineage.
- Dataflow engines run the DAG continuously with event-time windows, watermarks and per-key state.
- Exactly-once = consistent checkpoints + replayable sources + transactional or idempotent sinks.

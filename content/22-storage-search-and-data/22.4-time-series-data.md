# Time-series data

Metrics, sensor readings, prices, request latencies: a value per thing per moment, arriving forever. Time-series data
is append-mostly, read mostly as recent ranges, and its value fades with age. Those properties let specialised
stores (Prometheus, Mimir/Thanos, VictoriaMetrics, InfluxDB, TimescaleDB) be 10× more efficient than a general
database, and they also produce one failure mode you have to design against: cardinality.

## The data model

```
http_requests_total{service="checkout", method="POST", status="500", pod="checkout-7f9c"}
      metric name                    labels
         → (1761300000000 ms, 1027)  (1761300010000, 1031)  (1761300020000, 1040) …
              timestamp      value      ← samples
```

A **series** is one unique combination of metric name + label values. Each series is a stream of
`(timestamp, float64)` **samples**: 16 bytes raw.

## Storage: Prometheus's TSDB

```
scrape → append to HEAD block (in memory, last ~2 h)  +  WAL on disk (crash recovery)
          every 2 h: head → immutable block on disk:
             chunks/   compressed samples, grouped per series
             index     label → posting list of series IDs (an inverted index, lesson 22.2)
             meta.json time range
          background compaction merges 2 h blocks into larger ones (up to ~10% of retention)
          retention: delete whole blocks older than the limit (default 15 days)
```

Deleting old data means deleting whole directories: no per-row deletes, no vacuum (compare lesson 21.5). Queries
pick the blocks overlapping the time range, look up series in the label index (`service="checkout" AND status="500"`
→ intersect posting lists), then decode their chunks.

## Compression: Gorilla encoding

Facebook's Gorilla paper (2015) showed how to shrink samples from 16 bytes to an average of about **1.37 bytes**:

- **Timestamps, delta-of-delta.** Scrapes arrive every 10 s: `t, t+10, t+20, t+30…`. Deltas are `10, 10, 10`, and the
  delta of deltas is `0, 0, 0`, stored as **one bit** each. Jitter of a few ms costs a few more bits.
- **Values, XOR with the previous value.** A gauge that barely changes shares sign, exponent and leading mantissa bits
  with the previous sample. XOR gives mostly zeros; store only the meaningful bits in the middle. An unchanged value
  is **one bit**.

Prometheus uses this scheme for its chunks. Real-world ratios depend on the data: smooth, regular metrics compress
well; noisy high-precision values compress much less.

## Cardinality: the thing that breaks you

Cost scales with the **number of active series**, not the number of samples per series. Labels multiply:

```
http_requests_total by service (50) × method (5) × status (10) × pod (40)
  = 100,000 series. Fine.

… add user_id (2,000,000 users)
  = 200,000,000,000 possible series. Not fine.
```

Each active series costs memory in the head block (index entries, label strings, open chunk), on the order of a few
KB. Unbounded label values (user IDs, request IDs, full URLs with IDs in them, email addresses, error messages) blow up
memory and the index; a single bad deploy that adds such a label can take the monitoring system down exactly when you
need it. Rules:

- Labels are for **bounded** dimensions you aggregate by. Per-user or per-request detail belongs in logs or traces.
- Enforce per-tenant series limits and drop labels at ingestion (relabelling) when needed.
- Track `prometheus_tsdb_head_series` and alert on its growth rate.

## Downsampling and retention

Nobody needs 10-second resolution from last year. Typical tiers:

| Age | Resolution | Kept as |
|-----|------------|---------|
| 0–15 days | Raw (10–15 s) | Every sample |
| 15–90 days | 1 min or 5 min | Rollups |
| 90 days–2 years | 1 hour | Rollups |

Store **min, max, sum and count** per rollup interval, not just the average: averages of averages are wrong, and a
5-minute average hides a 20-second spike that max would show. Counters are downsampled by keeping enough points to
compute rates. Thanos and Mimir do this by compacting blocks in object storage; long-term data lives cheaply in S3.

## Scaling past one node

One Prometheus server handles a few million active series. Beyond that: shard scraping across servers (by target
hash), run pairs for HA, and push to a horizontally scalable backend (Mimir, Cortex, VictoriaMetrics, Thanos) that
shards series by hash of labels across ingesters, replicates each series to 3 ingesters, and writes blocks to object
storage.

## Try it

Design metrics storage for **1 million active series** scraped every 10 seconds. Estimate ingest rate, disk for 15
days of raw data, memory, and what you'd do for 1-year retention.

<summary>Reference</summary>

- **Ingest**: 1,000,000 / 10 s = **100,000 samples/s**, 8.64 billion samples a day.
- **Disk, raw**: at ~1.37 B/sample ≈ 11.8 GB/day; budget ~2 B/sample for real data plus index → ~17 GB/day →
  **about 250 GB for 15 days** per replica (×2–3 with replication).
- **Memory**: a few KB per active series → several GB for the head block; give each ingester headroom (and limit
  series per tenant).
- **Architecture**: scrapers (or agents) remote-write to a Mimir/VictoriaMetrics-style cluster with ~3 ingesters per
  shard, replication factor 3; blocks shipped to object storage; queriers fan out across ingesters (recent) and the
  store (old).
- **1 year**: keep raw for 15 days, 5-minute rollups (min/max/sum/count) for a year: 1M series × 105,120 points × 4
  aggregates ≈ 420 billion values, a few hundred GB to ~1 TB compressed in object storage. Cheap.
- **Guard rails**: cardinality limits per metric and tenant, alerts on series growth, recording rules for expensive
  dashboard queries.
</details>

## Key takeaways

- A series is metric + label set; samples are (timestamp, float) appended in time order.
- Prometheus-style TSDBs keep a 2-hour in-memory head plus WAL, then immutable blocks with an inverted label index.
- Delta-of-delta timestamps and XOR-encoded values shrink 16-byte samples to about 1–2 bytes.
- Cost tracks active series; unbounded labels cause cardinality explosions.
- Downsample with min/max/sum/count, expire whole blocks, and push long-term data to object storage.

# Object storage

S3 and its cousins (Google Cloud Storage, Azure Blob, Ceph RGW, MinIO) store **objects**: a key, some bytes, some
metadata. No partial updates, no directories (just key prefixes), no locking. That narrow interface is what lets them
hold exabytes and promise durability numbers like "eleven nines". This lesson looks at how.

## The parts

```
             PUT /photos/2026/cat.jpg
                       │
               ┌───────▼────────┐
               │  front end     │  auth, request routing, rate limits
               └───┬────────┬───┘
       ┌───────────▼─┐   ┌──▼────────────┐
       │ metadata /  │   │  placement    │  where should new bytes go?
       │ index       │   │               │
       └───────────┬─┘   └──┬────────────┘
                   │        │
         ┌─────────▼────────▼──────────────────┐
         │ storage nodes: millions of disks,    │
         │ spread across racks and zones        │
         └──────────────────────────────────────┘
```

- **Metadata/index**: maps `bucket + key` → object version, size, checksum and the locations of its pieces. It's a
  huge, sharded, replicated key-value store, and every request touches it.
- **Placement**: decides which disks get a new object's pieces, spreading them across failure domains.
- **Storage nodes**: dumb, numerous, failing all the time.

A `PUT` writes the data pieces first, then commits the metadata entry. Only when the metadata points at the new
pieces does the object "exist". A `GET` reads metadata, then fetches pieces in parallel.

## Durability: replication vs erasure coding

Disks fail constantly at this scale. Two ways to survive it:

**Replication**: store 3 full copies in 3 zones. Simple and fast to read and repair, but 3× the raw storage.

**Erasure coding (Reed–Solomon k + m)**: split the object into **k** data fragments, compute **m** parity fragments,
and store all k + m on different disks. *Any k* of them reconstruct the object.

```
object (8 MB) → 8 data fragments × 1 MB  +  4 parity fragments × 1 MB
                stored on 12 disks in different racks/zones
                any 8 of 12 survive → object readable
```

| | 3× replication | 8+4 erasure coding |
|-|----------------|--------------------|
| Raw bytes per logical byte | 3.0 | 12/8 = **1.5** |
| Failures tolerated | 2 copies lost | **4** fragments lost |
| Read cost (healthy) | Read 1 copy | Read 8 fragments (or the k data fragments) |
| Repair one lost piece | Copy 1 piece | Read **8** fragments, recompute 1 |
| Small objects | Fine | Overhead and metadata per fragment hurt; often batched or replicated instead |

Erasure coding gives more durability for half the storage; the price is CPU, more disks per read, and expensive
repair traffic. Real systems mix both: replicate small or hot objects, erasure-code the rest, sometimes across zones
(e.g. fragments spread over three availability zones so a whole zone can be lost).

## Where "11 nines" comes from

99.999999999% annual durability means: store 10 billion objects and expect to lose about one per decade. The number
is a model, not a measurement. It comes from:

- probability of a disk failing in a year (annual failure rate of a few percent),
- **time to repair**: how long a lost fragment stays missing before it's rebuilt (hours, if re-replication is spread
  over many disks; lesson 22.5),
- how many more failures in the same object's fragment set would cause loss in that window,
- correlated failures (same rack, same batch of disks, same software bug), which dominate in practice.

Fast detection and repair matter as much as the code: durability falls sharply if a failed disk sits unrepaired for
days. Checksums on every fragment plus background **scrubbing** catch silent corruption (bit rot) before it piles up.

What 11 nines doesn't cover: you deleting the object, a bug in your code overwriting it, or the region being
unavailable. Durability isn't availability (S3 Standard is designed for 99.99% availability), and neither is a backup.
Versioning, object lock and cross-region replication cover those.

## Consistency

Until December 2020, S3 was eventually consistent for some operations: a `GET` right after an overwrite, or a `LIST`
after a `PUT`, could return stale results. Since then S3 provides **strong read-after-write consistency** for all
`PUT`, `GET`, `LIST` and `DELETE` operations, at no extra cost. It's the metadata layer that makes this work: a write
is acknowledged only once the index reflects it, and reads go through the index.

Still no transactions across objects, no compare-and-swap on older APIs (conditional writes with `If-None-Match`/
`If-Match` arrived later), and `LIST` is slow for huge prefixes. Design keys so you never need to list millions.

## When the metadata goes down: S3, February 2017

On February 28, 2017 at 9:37 AM PST, an engineer debugging S3's billing system in us-east-1 ran a playbook command to
remove a small number of servers. One input was mistyped, and far more servers were removed, including ones supporting
the **index** and **placement** subsystems. Both had to be fully restarted, which hadn't been done in the large regions
for years and took much longer than expected: GET/LIST/DELETE came back at 12:26 PM, and PUTs only at 1:54 PM.

No data was lost; the bytes were safe on disk. But without the index, nothing could find them, and much of the
internet (including AWS's own status dashboard) depended on S3 in us-east-1. See [lesson 24.6](#/lesson/24.6) and
[open it in the sandbox](#/sandbox?preset=out-s3-2017).

Lessons: the metadata layer is the availability bottleneck; tools should refuse to remove capacity below a safe
minimum; and subsystems should be partitioned into cells so a restart is small and routine.

## Try it

You have **1 PB** of user photos. Estimate raw storage and failure tolerance for 3× replication vs 8+4 erasure coding,
and what it costs to repair one failed 20 TB disk in each case.

<details>
<summary>Reference</summary>

- **3× replication**: 3 PB raw. Tolerates losing any 2 copies of an object. Repairing a failed 20 TB disk means
  copying 20 TB from surviving replicas: 20 TB read, 20 TB written.
- **8+4 erasure coding**: 1 PB × 12/8 = **1.5 PB raw**, half the disks. Tolerates any **4** lost fragments. Repairing
  20 TB of lost fragments means reading 8 fragments for each one: about **160 TB read**, 20 TB written, plus the CPU for
  decoding. Spread across hundreds of disks it still finishes in hours, but repair bandwidth must be budgeted.

With, say, 1.5 PB of savings at a few dollars per TB per month, erasure coding wins easily for cold, large photos; keep
small thumbnails or very hot objects replicated if the per-fragment overhead or read fan-out hurts.
</details>

## Key takeaways

- Object stores = front end + metadata index + placement + huge numbers of storage nodes.
- Erasure coding (k+m) gives more durability than 3× replication at half the storage, at the cost of repair traffic.
- 11 nines comes from fast repair and spreading pieces across independent failure domains; it isn't availability or
  backup.
- S3 has been strongly consistent since December 2020; the metadata layer is what makes that, and outages, happen.

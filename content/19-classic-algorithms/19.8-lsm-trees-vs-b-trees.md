# LSM trees vs B-trees

Under every database is a **storage engine** that decides how bytes are laid out on disk. Two designs dominate, and
they make opposite tradeoffs between reads and writes.

## B-trees: update in place

Used by Postgres, MySQL/InnoDB, SQL Server, and most relational databases.

```
           [ 100 | 200 ]
        /       |        \
 [..50..]   [..150..]   [..250..]     ← fixed-size pages (e.g. 8 KB) on disk
```

- Data lives in sorted pages; a write finds the page and **modifies it in place** (plus a WAL record for crash
  safety).
- Reads: a few page lookups (log n), usually cached in memory. **Fast, predictable reads.**
- Writes: random I/O to many pages; page splits; each change is written twice (WAL + page).

## LSM trees: append, then merge

Used by RocksDB, LevelDB, Cassandra, ScyllaDB, HBase, and many key-value stores.

```
write → WAL (append) + memtable (sorted, in memory)
memtable full → flush as an immutable sorted file (SSTable) to disk
background compaction merges SSTables into bigger sorted files, dropping overwritten/deleted keys
```

- Writes are **sequential appends**: very fast, even on slow disks.
- Reads may check the memtable plus several SSTables. **Bloom filters** per SSTable (lesson 19.2) skip files that
  can't contain the key, and a sparse index finds the block quickly.
- Deletes write a **tombstone**; space is reclaimed later by compaction.

## The amplification triangle

| | B-tree | LSM tree |
|-|--------|----------|
| **Write amplification** (bytes written per byte of data) | Moderate–high (page rewrites) | Varies with compaction (leveled: high; tiered: lower) |
| **Read amplification** (files/pages read per lookup) | Low | Higher (mitigated by Bloom filters and caches) |
| **Space amplification** | Some fragmentation | Old versions until compaction |
| Sweet spot | Read-heavy, transactional, range scans | Write-heavy, high ingest, time series |

You can tune an LSM toward reads (**leveled** compaction: fewer overlapping files, more rewriting) or toward writes
(**tiered/size-tiered**: less rewriting, more files to check).

## Practical consequences

- **Write-heavy workloads** (metrics, events, IoT, messaging): LSM engines sustain far higher ingest.
- **Read-heavy OLTP** with complex queries and transactions: B-trees give stable latency.
- LSM **compaction storms** can cause latency spikes. Throttle compaction and give it I/O headroom.
- On B-trees, **random-key inserts** (UUID v4) hurt more than time-ordered ones (lesson 12.6).

## Try it

A telemetry service ingests 500,000 small writes per second, and reads are mostly "the last hour for device X". Which
engine suits it, and what would you tune?

<details>
<summary>Answer</summary>

An **LSM** engine (Cassandra, ScyllaDB or a RocksDB-based store): sequential writes absorb the ingest. Partition by
device and cluster by time, so "last hour" reads one partition's recent SSTables; use time-window compaction (old
windows compact once and then sit untouched), Bloom filters, and TTL-based expiry, so old data is dropped as whole
files.
</details>

## Key takeaways

- B-trees update pages in place: fast, predictable reads; more random writes.
- LSM trees append and compact: very fast writes; reads use Bloom filters to stay quick.
- The tradeoff is read vs write vs space amplification, tunable via compaction strategy.
- Choose by workload: read-heavy OLTP → B-tree; heavy ingest → LSM.

# Count-min sketch

"How many times has each search term appeared today?" With millions of distinct terms, an exact hash map is large.
A **count-min sketch** estimates frequencies in a **fixed** amount of memory, and its estimates never undercount.

## How it works

A grid of `d` rows × `w` columns of counters, and one hash function per row.

```
add(x):      for each row r: counters[r][h_r(x) % w] += 1
estimate(x): min over rows r of counters[r][h_r(x) % w]
```

Different items can share a cell (collisions only ever *add*), so each row overestimates. Taking the **minimum**
across rows picks the least-polluted one.

```
         col: 0  1  2  3  4  5  6  7
row 1:        0  5  0  2  9  0  1  0      "cat" → col 4 (9)
row 2:        3  0  7  0  0  4  0  2      "cat" → col 2 (7)
row 3:        0  0  1  6  0  0  8  0      "cat" → col 3 (6)
estimate("cat") = min(9, 7, 6) = 6     (true count ≤ 6)
```

## Error bounds

With `w = ⌈e / ε⌉` columns and `d = ⌈ln(1/δ)⌉` rows:

> estimate ≤ true count + ε × (total items), with probability ≥ 1 − δ

E.g. ε = 0.001 and δ = 0.01 gives w = 2,719 and d = 5: about **13,600 counters** (~54 KB) for **any** number of
distinct items. Heavy hitters are estimated accurately; rare items may be overestimated a little.

## Heavy hitters (top-K)

Pair the sketch with a small min-heap of the current top K:

```
on each item x:
  sketch.add(x)
  est = sketch.estimate(x)
  if x in heap: update it; elif est > heap.min: replace the min with x
```

That's trending hashtags, top URLs, the noisiest API clients or the hottest cache keys (lesson 14.3), in kilobytes.

## Mergeable

Two sketches with the same dimensions and hashes merge by **adding** their counters cell by cell, so each server or
partition can count locally and a coordinator sums them.

## Uses

- Trending topics and top queries in streaming pipelines.
- Hot-key detection in caches and databases.
- Network monitoring: heavy flows per IP.
- Rate limiting by approximate counts per client at huge cardinalities.

## Try it

You track request counts per client IP across 50M IPs and want to find IPs above 10,000 requests/hour. Why is a
count-min sketch a good fit, and what does an overestimate mean in practice?

<details>
<summary>Answer</summary>

Memory is fixed (kilobytes to a few MB) regardless of 50M distinct IPs, and heavy hitters are estimated well. Because
it only **overestimates**, every IP truly above 10,000 will be flagged (no misses). A few lighter IPs may also be
flagged, so confirm candidates with an exact count (or tolerate it, since the cost is a closer look).
</details>

## Key takeaways

- A count-min sketch estimates item frequencies in fixed memory.
- It never undercounts; error ≤ ε × total with probability 1 − δ.
- Pair it with a heap for top-K heavy hitters.
- Sketches merge by adding, which is ideal for distributed counting.

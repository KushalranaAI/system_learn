# Rate limiter algorithms

Lesson 8.2 compared the algorithms. This lesson implements the token bucket and the sliding-window counter precisely,
and traces a burst through each.

## Token bucket (lazy refill)

```ts
interface Bucket { tokens: number; last: number }   // last = ms timestamp

function allow(b: Bucket, now: number, capacity: number, ratePerSec: number): boolean {
  const elapsed = (now - b.last) / 1000;
  b.tokens = Math.min(capacity, b.tokens + elapsed * ratePerSec);   // refill since last call
  b.last = now;
  if (b.tokens >= 1) { b.tokens -= 1; return true; }
  return false;
}
```

No timers: state is just two numbers per key, updated on each request.

### A trace (capacity 5, rate 1/s)

| Time | Event | Tokens before | Result | Tokens after |
|------|-------|---------------|--------|--------------|
| 0.0 s | 6 requests at once | 5 | 5 allowed, 1 rejected | 0 |
| 1.0 s | 1 request | 1.0 | allowed | 0 |
| 1.5 s | 1 request | 0.5 | **rejected** | 0.5 |
| 4.0 s | 3 requests | 3.0 | 3 allowed | 0 |

The burst capacity (5) and the sustained rate (1/s) are separate knobs.

## Sliding-window counter

```ts
// counts per fixed window: windows[t] = count in [t, t+W)
function allowSliding(windows: Map<number, number>, now: number, W: number, limit: number): boolean {
  const cur = Math.floor(now / W) * W;
  const prev = cur - W;
  const elapsedFrac = (now - cur) / W;
  const estimate = (windows.get(cur) ?? 0) + (windows.get(prev) ?? 0) * (1 - elapsedFrac);
  if (estimate >= limit) return false;
  windows.set(cur, (windows.get(cur) ?? 0) + 1);
  return true;
}
```

### The boundary burst, revisited (limit 10 per 60 s)

| Algorithm | 10 requests at 0:59 + 10 at 1:01 |
|-----------|----------------------------------|
| Fixed window | All 20 allowed (two different windows) |
| Sliding window counter | At 1:01: estimate = 0 + 10 × (1 − 1/60) ≈ 9.8 → allows about 1 more, rejects the rest |
| Token bucket (capacity 10, refill 10/min) | At 1:01: ~0.3 tokens refilled → rejects nearly all |

## Distributed versions

- Put the state in Redis and run the logic **atomically** in a Lua script (lesson 8.2), so concurrent servers can't
  race.
- Use Redis server time (`TIME`) or pass monotonic timestamps carefully, since clocks differ across app servers
  (lesson 12.5).
- Set a key expiry ≈ the time to refill fully, so idle keys disappear.

## Generic cell rate algorithm (GCRA)

A neat variant used by some gateways (e.g. redis-cell): store only a single "theoretical arrival time" per key. It's
mathematically equivalent to a token bucket, with less state and simpler atomic updates.

## Try it

With a token bucket of capacity 3 and rate 2/s, a client sends requests at t = 0, 0.1, 0.2, 0.3, 0.8 and 2.0 s. Which
are allowed?

## Key takeaways

- A token bucket needs two numbers per key and lazy refill; capacity and rate are independent.
- The sliding-window counter blends two fixed windows to smooth edge bursts.
- Distributed limiters run the logic atomically (Lua) with one clock source.
- GCRA is a compact, equivalent token-bucket formulation.

# Geohash and quadtrees

"Find drivers within 2 km of me." A normal B-tree index on `(lat, lng)` can't answer that well: it sorts by latitude
first, so "near me" becomes a huge latitude band filtered by longitude. Spatial indexes fix this by turning 2D space
into something sortable or into a tree.

## Geohash: space as a string

Repeatedly split the world in half, alternating longitude and latitude, and record which half you're in as bits;
encode them in base32.

```
Bengaluru (12.97, 77.59) → "tdr1y…"
longer prefix = smaller cell:
  "t"     ~5,000 km     "tdr"   ~156 km     "tdr1y" ~4.9 km     "tdr1yv" ~1.2 km
```

**Points that share a prefix are near each other.** So "nearby" becomes a prefix query on an ordinary index:

```sql
SELECT * FROM drivers WHERE geohash6 IN ('tdr1yv', <its 8 neighbours>);
```

Edge problem: two points a metre apart can fall in different cells. Always search the target cell **plus its 8
neighbours**, then filter by exact distance.

## Quadtrees: adaptive cells

Recursively split a region into 4 quadrants, but only where there are many points:

```
┌───────┬───────┐
│       │ ┌─┬─┐ │   dense city centre → deep, small cells
│       │ ├─┼─┤ │   empty countryside → one big cell
├───────┼─┴─┴─┤
│       │       │
└───────┴───────┘
```

- Each leaf holds at most K points (say 100); overflowing leaves split.
- Nearby search walks down to the cell, then checks neighbouring cells.
- It adapts to density (Manhattan vs a desert) better than fixed-size geohash cells.

## Other options

| Index | Notes |
|-------|-------|
| **R-tree** (PostGIS GiST) | Bounding-box tree; great for shapes and polygons ("which delivery zone contains this point?") |
| **S2** (Google) | Maps the sphere onto a cube, then a Hilbert curve; hierarchical cells with excellent locality |
| **H3** (Uber) | Hexagonal hierarchical cells; uniform neighbour distances, popular for analytics and pricing zones |
| **Redis GEO** | Geohash-based sorted sets: `GEOADD`, `GEOSEARCH … BYRADIUS 2 km` |

## Moving objects (drivers)

Drivers update their location every few seconds. Keep live locations **in memory** (Redis GEO, or an in-memory
quadtree per city shard), never as constant updates in your main database. Persist only trip-relevant positions.

```
driver app every 4 s → location service → GEOADD drivers:blr lng lat driver_42
rider request        → GEOSEARCH drivers:blr FROMLONLAT … BYRADIUS 2 km ASC COUNT 20
```

## Try it

Design "nearby restaurants" for a food app: 500k restaurants (static locations), plus "nearby available riders": 80k
riders updating every 5 s. Pick an index for each.

<details>
<summary>Answer</summary>

Restaurants are static, so a **geohash or S2 column with a B-tree index** (or a PostGIS GiST index) in the main
database, with the target cell plus neighbours, then a distance filter. Results are cacheable per cell. Riders change
16,000 locations per second, so keep them in **Redis GEO** (sharded by city) or an in-memory quadtree service with
TTLs on stale riders, and query by radius.
</details>

## Key takeaways

- Ordinary indexes can't do "near me"; spatial indexes map 2D to sortable keys or trees.
- Geohash: a shared prefix means nearby; search the cell plus its 8 neighbours.
- Quadtrees adapt to density; R-trees handle shapes; S2 and H3 are modern hierarchical cell systems.
- Keep fast-moving objects in memory (Redis GEO), not in the main database.

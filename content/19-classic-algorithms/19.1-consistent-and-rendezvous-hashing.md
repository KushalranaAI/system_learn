# Consistent and rendezvous hashing

Lesson 14.2 explained *why* consistent hashing matters. Here's how to build it, and its simpler cousin, and measure
how many keys move.

## A consistent-hash ring in ~25 lines

```ts
import { createHash } from "node:crypto";
const h = (s: string) => parseInt(createHash("md5").update(s).digest("hex").slice(0, 8), 16); // 32-bit

class Ring {
  private points: { pos: number; node: string }[] = [];
  constructor(private vnodes = 128) {}
  add(node: string) {
    for (let i = 0; i < this.vnodes; i++) this.points.push({ pos: h(`${node}#${i}`), node });
    this.points.sort((a, b) => a.pos - b.pos);
  }
  remove(node: string) { this.points = this.points.filter((p) => p.node !== node); }
  get(key: string): string {
    const k = h(key);
    let lo = 0, hi = this.points.length;          // binary search: first point with pos >= k
    while (lo < hi) { const mid = (lo + hi) >> 1; this.points[mid].pos < k ? (lo = mid + 1) : (hi = mid); }
    return this.points[lo % this.points.length].node;   // wrap around
  }
}
```

## Measure the movement

```ts
const keys = Array.from({ length: 100_000 }, (_, i) => `user:${i}`);
const ring = new Ring(); ["a", "b", "c", "d"].forEach((n) => ring.add(n));
const before = keys.map((k) => ring.get(k));
ring.add("e");
const moved = keys.filter((k, i) => ring.get(k) !== before[i]).length;
console.log(moved / keys.length);   // ≈ 0.20  (1/5: only the new node's share moves)
```

Compare with `hash % N`: going from 4 to 5 nodes moves ≈ **80%** of keys.

## Virtual nodes and balance

| Virtual nodes per node | Typical max/avg load (10 nodes) |
|------------------------|---------------------------------|
| 1 | ~2–3x (very uneven) |
| 16 | ~1.3x |
| 128 | ~1.1x |
| 512 | ~1.05x |

More virtual nodes give better balance, at the cost of a bigger ring in memory (still tiny).

## Rendezvous (highest random weight) hashing

```ts
function rendezvous(key: string, nodes: string[]): string {
  let best = "", bestScore = -1;
  for (const n of nodes) {
    const s = h(`${key}|${n}`);
    if (s > bestScore) { bestScore = s; best = n; }
  }
  return best;
}
```

- Each key picks the node with the highest score.
- Removing a node only moves the keys that node owned; adding one steals ~1/N of the keys.
- No ring to maintain, and naturally even, but O(N) per lookup. Great for tens of nodes (e.g. picking a cache shard
  or a CDN edge).
- For R replicas, take the **top R** scores.

## Where you'll see them

- Cassandra and Dynamo (ring + virtual nodes)
- Memcached clients (ketama)
- Load balancers with affinity (Maglev hashing, a fast variant)
- Kafka? No: it uses `hash % partitions` with a fixed partition count, which is why the count should rarely change.

## Try it

Run the snippet with 4 → 5 nodes using `hash % N` instead of the ring, and compare the moved fraction. Then try
`vnodes = 1` and look at how uneven the per-node key counts get.

## Key takeaways

- A ring with virtual nodes and binary search gives consistent hashing in a few lines.
- Adding a node to N moves ~1/(N+1) of the keys, versus ~N/(N+1) with modulo.
- More virtual nodes give better balance.
- Rendezvous hashing is simpler and even, O(N) per lookup; take the top R for replicas.

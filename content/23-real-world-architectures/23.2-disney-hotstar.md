# Disney+ Hotstar: tens of millions watching one match

Netflix's audience is spread across thousands of titles and every time zone. A cricket final is the opposite: one
stream, one country, one evening, and a crowd that grows by millions in minutes when a star batter walks out. Hotstar
(now part of JioHotstar) has repeatedly set records for concurrent viewers on one live stream. Its approach can be
summed up as: don't scale reactively, scale in advance.

## The problem at their scale

| Peak concurrent viewers | Match | Date |
|-------------------------|-------|------|
| 10.3 million | IPL final | May 2018 |
| 18.6 million | IPL final | May 2019 |
| 25.3 million | World Cup semi-final, India v New Zealand | 10 July 2019 |
| 53 million | World Cup semi-final, India v New Zealand | 15 November 2023 |
| 59 million | World Cup final, India v Australia | 19 November 2023 |

For the 25.3M match, Hotstar's re:Invent 2019 talk reported **over 1 million requests per second** and **over 10
Tbps** of video. The talk also said the audience could grow by **over a million users per minute**.

Two things make the load hard:

- **Spikes come from the game.** A wicket, a famous batter coming in, the toss, the last over. Traffic follows the
  match, not the clock.
- **The API spike and the video spike are different.** When a popular batter gets out, many viewers leave the stream at
  the same moment and land on the home page. Video concurrency drops while API traffic jumps. Hotstar calls these
  surges "tsunamis".

## The architecture

```
 phones (mostly mobile, mostly India)
   │
   ├── video segments ──► multiple CDNs (HLS/DASH ladders: 240p ... 1080p)
   │                        origin: live encoders → packagers
   │
   └── API calls ───────► edge / gateway ──► services: auth, home page, playback, ads,
                                              concurrency counter, recommendations, social
                              ▲
     scaling control ─────────┘   capacity set ahead of time by a ladder:
                                  "at N million viewers, run M servers per service"
     panic switches ─────────────► turn off non-critical features under stress
```

## Key decisions and why

**1. Pre-scale before the match. Don't wait for autoscaling.** The 2019 talk set out why reactive autoscaling failed
at this scale. A new server took about **90 seconds** to boot and become healthy, while the crowd could grow by a
million a minute. Auto Scaling groups hit insufficient-capacity errors, step-size limits and capacity gaps between
availability zones. So Hotstar estimates the peak for each match and warms the platform up before the toss, using
fully baked machine images. See [lesson 4.7](#/lesson/4.7) for why reactive scaling lags.

**2. Scale on a ladder keyed to concurrency.** Hotstar's engineering blog describes **static ladders** from 2018:
capacity steps up or down based on the headroom left, driven by the live concurrency count rather than CPU. This was
safe but needed humans watching and cost money. On Kubernetes from 2019, Hotstar scaled on request counts, and it ran
autoscaling in shadow mode before trusting it. Concurrency is a **leading** signal: if you know how many people are
watching, you know roughly how many will hit the home page when the next wicket falls.

**3. Panic mode: decide in advance what to switch off.** During a live match there is no time for a 15-20 minute
fix. The talk's guidance was to turn off non-critical features, such as recommendations and personalisation, to
protect the critical path: **video playback, login and payments**. A degraded home page is better than a failed
stream. See [lesson 12.3](#/lesson/12.3) and [lesson 7.6](#/lesson/7.6).

**4. Rehearse at full size.** Project HULK generated synthetic load from about **108,000 CPUs** across 8 regions,
pushing 200 Gbps. Game days replayed match-day traffic shapes, and chaos tests injected push-notification surges,
delayed scale-ups, CDN failures and added latency.

## What went wrong along the way

- **The load test was itself an outage risk.** Hotstar reported that HULK's traffic once caused problems because the
  public-cloud network it ran on was shared. Test traffic needs limits too.
- **Autoscaling trust took years.** Ladders worked but were expensive and manual. Moving to Kubernetes ran into
  cluster limits, and before the 2023 tournaments the self-managed clusters could not reach 50 million concurrency
  and had to be rebuilt.
- **Push notifications cause their own spikes.** One "India needs 20 off 6 balls!" notification sent to millions of
  phones produces a tsunami a few seconds later. Notifications have to be rate-spread and counted in the capacity
  plan.

## Try it

Plan capacity for a **50 million viewer** final. Use Hotstar's 2019 ratios as a starting point: about 1M API
requests/s and 10 Tbps of video at 25M viewers. Assume one API server handles 2,000 requests/s at a safe load, a
wicket causes a 3x API tsunami for about a minute, and a new server takes 90 s to become healthy. How many API servers
do you run at the toss, and what goes in your panic list?

<details>
<summary>Reference</summary>

**Base API load:** 1M/s per 25M viewers scales to about **2M requests/s** at 50M.

**Tsunami:** 3 x 2M = **6M requests/s** for about a minute. A 90 s boot cannot catch a one-minute spike, so the
capacity must already be running. 6M / 2,000 = **3,000 API servers** at peak moments. A ladder might be: 1,000 servers
at 15M viewers, 2,000 at 30M, 3,000 from 40M up, plus 10-20% for a lost zone.

**Video:** about 10 Tbps per 25M scales to roughly **20 Tbps**, split across several CDNs so one CDN failing isn't
fatal. Lower the default bitrate if a CDN degrades.

**Panic list, in order:** recommendations and "continue watching" rows, then personalised home page (serve a cached
generic one), social/chat features, then high bitrates. Never: playback, login, entitlement checks, ads that pay for
the stream. Rate-spread push notifications over 1-2 minutes.
</details>

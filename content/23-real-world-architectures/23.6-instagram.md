# Instagram: scaling Postgres

Instagram started in 2010 as a Django app on PostgreSQL, and Postgres remained at the core as it grew. Its early
engineering posts are among the clearest public accounts of sharding a relational database by hand. They cover choosing
the shard key, decoupling logical from physical shards, and generating unique, sortable IDs without a central
service.

[Open it in the sandbox](#/sandbox?preset=cs-instagram)

## The problem at their scale

| Number | Value | When |
|--------|-------|------|
| Writes when the sharding post was published | more than 25 photos and 90 likes per second | September 2011 |
| ID bits per shard per millisecond | 1,024 IDs | 2011 design |
| Monthly active users | 2 billion | October 2022 |
| Monthly active users | 3 billion | September 2025 |

Small team, fast growth, and data that outgrew one Postgres primary. They needed to split the data without rewriting
the app and without a new single point of failure.

## The architecture

```
 Django app ─► "which shard?"  user_id → logical shard (one of thousands)
                                logical shard → physical Postgres server (mapping in config)

   physical DB 1                 physical DB 2                 physical DB N
   ┌──────────────────┐          ┌──────────────────┐
   │ schema shard_0   │          │ schema shard_8   │          each logical shard is a
   │ schema shard_1   │          │ schema shard_9   │          Postgres SCHEMA with its own
   │ ...              │          │ ...              │          tables and its own ID sequence
   └──────────────────┘          └──────────────────┘

 feeds / activity / inbox ─► Cassandra (from 2012; replaced Redis for these)
```

## Key decisions and why

**1. Shard by user.** A user's photos, and most of what you show on their profile, live on one shard. Most requests
touch one shard, and a user's data can be moved as a unit. The cost is cross-user queries, such as "all likes on
this photo from people I follow", which need fan-out or a different store. See [lesson 9.3](#/lesson/9.3) and
[lesson 9.4](#/lesson/9.4).

**2. Many logical shards on few physical machines.** Instagram created **thousands of logical shards** up front, each a
Postgres **schema**, and placed many on each physical server. Growing means moving whole schemas to new machines
(replicate, then flip the mapping). You never re-hash individual rows. The logical shard count is fixed forever, so
it was chosen far larger than needed. See [lesson 14.5](#/lesson/14.5).

**3. IDs generated inside Postgres.** They wanted IDs that sort by time (so "newest first" is an index scan), fit in
64 bits, and need no new service. They rejected UUIDs (128 bits, unordered), Twitter's Snowflake (a separate service
with ZooKeeper to run) and a ticket-server database (a central dependency). Their scheme, run as a PL/pgSQL function
per shard:

```
| 41 bits: ms since custom epoch | 13 bits: logical shard id | 10 bits: per-shard sequence % 1024 |
  about 41 years of IDs            up to 8,192 shards             1,024 IDs per shard per ms
```

Because the shard id is **inside the ID**, any photo ID tells you which shard holds it: no lookup table. Compare
[lesson 12.6](#/lesson/12.6) and [lesson 19.11](#/lesson/19.11).

**4. Use a different store for write-heavy lists.** Feeds and activity were first kept in Redis, which hit memory
limits. From 2012 Instagram moved them to **Cassandra**, which is cheaper per GB for data that doesn't have to live in
RAM.

## What went wrong along the way

- **Redis ran out of room.** Keeping every feed in memory got too expensive as users grew, which pushed feeds to
  Cassandra.
- **Cassandra's tail latency.** By 2018, average reads were about 5 ms but p99 was 25-60 ms, mostly from JVM garbage
  collection. Instagram built **Rocksandra**, a RocksDB-based storage engine for Cassandra, which cut p99 reads from 60
  ms to 20 ms and GC stall time from 2.5% to 0.3%.
- **Cross-shard features are always harder.** Anything that isn't "one user's stuff" (counts on popular posts, search,
  explore) needs a second index, a cache or a separate pipeline. The shard key decides which features are cheap.

## Try it

Choose a shard key for **likes**. The queries are: (a) "how many likes does post P have?", shown on every view; (b)
"did I like post P?", shown on every view; (c) "list the people who liked P"; (d) "show posts I liked". Writes: like
and unlike. A celebrity post can get 1 million likes in an hour. Options: shard by `user_id` (the liker) or by
`media_id`.

<details>
<summary>Reference</summary>

**Shard by `media_id`** for the main likes table: `(media_id, user_id)` primary key.
- (a), (b) and (c) are single-shard queries. "Did I like P?" is a primary-key lookup on P's shard.
- Writes for one post land on one shard, and that is the risk: 1M likes/hour is about 280 writes/s on one post, which
  Postgres handles, but the **count** must not be `COUNT(*)` on every view. Keep a counter (cached, or a sharded
  counter flushed every few seconds; see [lesson 12.8](#/lesson/12.8)).

**For (d), "posts I liked":** write a second copy keyed by `user_id` (on the liker's shard), asynchronously
through a queue. It can lag by a second, and it avoids a scatter-gather across every shard.

**Why not `user_id` only:** (a) and (c) would need to scan every shard for one post, which is a scatter-gather on the
hottest query in the app.

Rule: shard by the key of your **hottest read**, and build the other access path as a derived index.
</details>

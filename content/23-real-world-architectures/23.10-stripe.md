# Stripe: payments that never double-charge

A payments API faces the hardest version of the retry problem from [lesson 12.2](#/lesson/12.2). A client sends "charge
$50", the connection drops, and the client can't tell whether the charge happened. Retrying might charge twice, and
not retrying might lose a sale. Stripe built its public API so that **retrying is always safe**, keeps a ledger that
proves where every cent went, and lets integrations written years ago keep working.

No case-study sandbox scenario for this one. The [payments interview scenario](#/sandbox?preset=iv-payments) and the
[payments ledger lab](#/labs/payments-ledger) cover the same ideas.

## The problem at their scale

| Number | Value | When |
|--------|-------|------|
| Total payment volume | about $1.4 trillion, up 38% | 2024 |
| Ledger events processed | about 5 billion per day | February 2024 |
| Dollar volume fully ingested and verified within 4 days | 99.99% | February 2024 |
| Backwards-incompatible API changes shipped | almost 100, all older versions still served | 2011-2017 |

The users are other developers' code, running on servers Stripe doesn't control, on networks that drop packets. Every
mistake costs real money and real trust.

## The architecture

```
 merchant server
   POST /v1/charges   Idempotency-Key: 6f1c...   Stripe-Version: 2024-06-20
        │
        ▼
 API layer ─► idempotency layer: seen this (account, key)?
        │        yes, finished        → return the SAVED status + body (even a saved 500)
        │        yes, still running   → 409 conflict, try later
        │        yes, different params → error: key reused for a different request
        │        no                   → lock the key, run the request
        ▼
 version layer: run on the current internal model, then transform the response
                backwards through each change module to the account's pinned version
        ▼
 payment logic ─► card networks / banks (external, cannot be rolled back)
        │
        └─► events ─► Ledger: immutable double-entry log, every movement balanced
                       clearing accounts must return to zero, or an alert fires
```

## Key decisions and why

**1. Idempotency keys on every mutating request.** The client generates a unique key (Stripe suggests a V4 UUID, up to
255 characters) and sends it in the `Idempotency-Key` header. Stripe's API v1 saves the status code and body of the
first request once execution begins, and returns exactly that on any retry with the same key. That includes a `500`:
the result is replayed, not recomputed. Keys can be pruned after at least 24 hours. Reusing a key with different
parameters is an error, which catches client bugs. Requests that fail validation, or that collide with a concurrent
request, aren't saved, so they can be retried. See [lesson 7.3](#/lesson/7.3) and [lesson 12.4](#/lesson/12.4).

**2. Retries with exponential backoff and jitter, built into the client libraries.** Stripe's 2017 post recommends
waiting about 2^n x a base interval after the n-th failure, plus random jitter, so thousands of clients that failed
together don't retry together. Stripe's own libraries add an idempotency key automatically, so their retries are safe.
See [lesson 12.2](#/lesson/12.2).

**3. Atomic phases around external calls.** You can't roll back a card network. Brandur Leach (then at Stripe)
described a design for this in 2017: store the key with a **recovery point**, split the work into **atomic phases**
(each one a local database transaction), and make exactly one external call between phases. A retry, or a background
"completer", resumes from the last recovery point instead of starting over. See [lesson 16.3](#/lesson/16.3) and
[lesson 16.4](#/lesson/16.4).

**4. A ledger that must balance.** Stripe's Ledger (described in 2024) is an **immutable, double-entry** log. Every
movement is a debit and a matching credit, and nothing is edited or deleted, so any past balance can be rebuilt by
replaying events ([lesson 17.1](#/lesson/17.1)). Money passing through intermediate **clearing accounts** should leave
them at zero. A non-zero clearing balance means something is missing, late or wrong, and it can be found with a
simple query.

**5. Date-named API versions, pinned per account.** Each account is pinned to the API version current at its first
request (for example `2017-05-24`). Each breaking change is a small module that converts a response back to the older
shape. The newest code runs once, and the response is transformed backwards through the modules to the version the
caller expects. Old integrations keep working, and core code doesn't fill up with `if version < X`.

## What went wrong along the way

Stripe hasn't published a single defining outage here. The design responds to failures every payments system has:

- **"Timeout, so retry" caused double charges** in naive integrations. Hence keys, and replaying the saved response
  rather than re-running.
- **Partial failure across systems:** the card was charged, but the local write failed. Recovery points and
  completers exist so a crash in the middle is resumed, not forgotten.
- **Silent data drift:** an event that never arrives produces no error. It shows up only as a balance that doesn't
  return to zero. Ledger turns "missing" into something a query can detect.
- **Version sprawl:** by 2017 there were almost 100 breaking changes. Without change modules, each one would be a
  permanent branch in core code.

## Try it

Make `POST /charges {amount, currency, card_token}` safe to retry. The handler writes a `charges` row, calls a card
processor (which can time out), and records the result. Clients will retry after timeouts, sometimes concurrently.
Describe the table, the flow and what a retry sees in each failure case.

<details>
<summary>Reference</summary>

**Table** `idempotency_keys(account_id, key, request_hash, locked_at, recovery_point, response_code, response_body,
created_at)`, unique on `(account_id, key)`.

**Flow:**
1. `INSERT ... ON CONFLICT DO NOTHING`, then `SELECT ... FOR UPDATE`.
   - If `request_hash` differs from this request: **422**, key reused.
   - If a response is stored: return it, byte for byte.
   - If `locked_at` is recent: **409**, another attempt is running.
   - Otherwise lock it (`locked_at = now()`).
2. **Phase 1 (one transaction):** create the `charges` row with status `pending`, and set recovery point
   `charge_created`.
3. **External call:** charge the processor, passing **our charge id as the processor's idempotency key**, so even a
   duplicate call there is harmless.
4. **Phase 2 (one transaction):** update the charge to `succeeded`/`failed`, write ledger entries (debit customer,
   credit merchant balance), enqueue the receipt email through an outbox, store `response_code/body`, set recovery point
   `finished`, clear the lock.

**Failures:**
- Crash before phase 1 commits: nothing happened, and the retry starts fresh.
- Crash after the processor call, before phase 2: the retry resumes at `charge_created`, calls the processor again with
  the **same** key, gets the original result, and finishes.
- Concurrent retry: gets 409, backs off, then gets the stored response.
- A background completer finishes keys stuck in a recovery point, and a reaper deletes keys older than 24-72 hours.
</details>

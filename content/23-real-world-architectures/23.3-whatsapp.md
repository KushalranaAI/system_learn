# WhatsApp: millions of connections per server

WhatsApp is the standard example of a very small team running a very large service. When Facebook bought it in 2014,
it had a few dozen engineers and hundreds of millions of users. That worked because of a runtime built for millions of
small concurrent tasks, a deliberately narrow product, and servers that keep a message only until it is delivered.

[Open it in the sandbox](#/sandbox?preset=cs-whatsapp)

## The problem at their scale

| Number | Value | When |
|--------|-------|------|
| TCP connections on one server | over 2 million | early 2012 (WhatsApp blog) |
| Monthly users | 465 million | March 2014 (Erlang Factory talk) |
| Messages per day | 19 billion in, 40 billion out | March 2014 |
| Peak concurrent connections | 147 million | March 2014 |
| Servers / cores | about 550 servers, over 11,000 cores | March 2014 |
| Engineers | about 50, for 900 million users | September 2015 (Wired) |
| Users | 2 billion | February 2020 |
| Messages per day | about 100 billion | October 2020 |

"In" vs "out" in 2014 is fan-out: one message to a group of five is one in and five out.

Each phone holds one long-lived connection, idle most of the time. The cost is **memory and scheduling per
connection**, not CPU per request. The design goal was to make each connection cheap.

## The architecture

```
 phone ── TLS/TCP (custom XMPP-derived protocol) ──► chat server (Erlang/BEAM, FreeBSD)
                                                       one lightweight process per connection
                                                         │
                     ┌───────────────────────────────────┼─────────────────────────┐
                     ▼                                   ▼                         ▼
           session/route lookup              offline store (per user)       media servers
           "which server holds Bob?"         keep until delivered,          (photos, video:
                     │                       then delete                     upload once, fetch by id)
                     ▼
           Bob's chat server ──► Bob's process ──► Bob's phone ──► ack ──► "delivered" tick to Alice
```

1. Alice's message reaches her chat server. Her connection's Erlang process looks up which server holds Bob's
   connection and sends the message there.
2. If Bob is online, his process pushes it down his socket. Bob's phone acks, and Alice sees two ticks.
3. If Bob is offline, the message waits in his offline queue. When he reconnects, it is delivered and then
   **deleted**. Messages are stored only while in transit.

## Key decisions and why

**1. Erlang/BEAM: one process per connection.** BEAM processes are not OS threads. Each starts with a few hundred
words of memory, has its own heap and mailbox, and the runtime's scheduler preempts it fairly. Two million connections
means two million small isolated processes. A crash in one (a malformed packet, say) kills only that process, and a
supervisor tree restarts what's needed. Erlang also allows hot code loading, though by 2014 most WhatsApp upgrades were
rolling restarts. See [lesson 6.2](#/lesson/6.2) for why holding connections is mostly a memory problem.

**2. Store-and-forward, not store-forever.** The server is a post office, not an archive. In 2014, about half of
messages were read within 60 seconds, and a write-back cache delivered 98% of them before they touched disk. Message
history lives on the phones, so the server-side storage problem stays small. End-to-end encryption, rolled out in
2016, made the same choice a privacy property too. See [lesson 7.3](#/lesson/7.3) for at-least-once delivery and
acks.

**3. Tune the box, then leave headroom.** The team patched FreeBSD and BEAM: more timer wheels, less lock contention,
partitioned tables. They pushed one server past 2 million connections in 2012, then deliberately ran chat servers at
about **1 million** each by 2014 to absorb peaks and failovers. The record shows what is possible. The operating point
is what's safe.

**4. Partition everything, keep it simple.** Services were split 2 to 32 ways (mostly 32), in primary/secondary pairs.
The Mnesia databases were kept in small "islands" of two nodes, which made schema operations manageable under load.
Fewer moving parts meant fewer people were needed to run them.

## What went wrong along the way

- **22 February 2014, about 210 minutes down.** A back-end router dropped a VLAN, which caused a mass
  disconnect/reconnect of nodes across the cluster. The process-group subsystem (`pg2`) generated n^3 messages during
  the reconnect storm, and queues grew from zero to 4 million messages in seconds. The team had to shut everything
  down and cold-start it, which they hadn't done in years. Lesson: **recovering can be harder than failing**, and
  reconnect storms need backoff ([lesson 6.5](#/lesson/6.5)).
- **Mnesia at scale** was a repeated source of pain: hash chains thousands of entries long where seven were expected,
  and slow reloads after upgrades.
- **Big groups** made some users' offline mailboxes so large that the team evicted them from the cache, because they
  slowed it for everyone.

## Try it

Size a chat fleet for **2 billion users**. Assume 40% are connected at the evening peak, one server safely holds 1
million connections, and you need to survive losing a whole data centre out of four. Messages: 100 billion a day, peak
hour at 2x the average rate. How many chat servers, and what is the peak message rate?

<details>
<summary>Reference</summary>

**Connections:** 2B x 0.4 = **800 million** concurrent. At 1M per server, that's **800 servers**.

**Survive losing one DC of four:** the other three must hold all 800M, so each DC needs 800 / 3 = about 267 servers,
and the fleet is 4 x 267 = about **1,070 servers**. Add some for deploys (rolling restarts take servers out) and you
might run about 1,200.

**Messages:** 100B / 86,400 s = about **1.16M messages/s** average, about **2.3M/s** at peak, more on New Year's Eve
(plan for a 3-5x day). Each message is a lookup, a forward and an ack, so the router and session registry need to
handle several times that.

**Storage:** store-and-forward keeps it small. Even if 10% of messages wait an hour for an offline phone, that's
about 0.1 x 2.3M x 3,600 = about 830M messages in flight, a few hundred GB. Small next to storing history forever.
</details>

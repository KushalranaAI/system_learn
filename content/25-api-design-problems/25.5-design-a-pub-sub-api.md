# Design a pub-sub API

Microservices that call each other synchronously fail together (lesson 12.1). A **publish-subscribe** service lets
one service announce "order placed" without knowing who listens: billing, email, analytics and search each subscribe
on their own. Module 15 covered Kafka from the inside; this lesson designs a managed pub-sub **API**, in the spirit of
Google Cloud Pub/Sub or Amazon SNS + SQS, that other teams consume.

## 1. Requirements

**Functional**
- Create topics; publish messages (with attributes) to a topic.
- Create subscriptions on a topic; each subscription gets every message.
- Consume by **pull** (the consumer asks) or **push** (the service POSTs to an endpoint).
- Acknowledge messages; redeliver unacknowledged ones; dead-letter messages that keep failing.
- Optional ordering per key; replay from a point in time.

**Non-functional**
- At-least-once delivery (consumers must be idempotent).
- Publish p99 < 50 ms; end-to-end delivery p99 < 1 s.
- 1M messages/s across all topics; messages up to 1 MB; retained 7 days.

## 2. Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Delivery guarantee | At-least-once, with an optional exactly-once *processing* mode via dedupe ids | Exactly-once delivery across networks isn't achievable in general (lesson 15.4) |
| Consumption | Pull (streaming gRPC or batched HTTP) and push (HTTPS webhooks) | Pull suits servers with variable capacity; push suits serverless |
| Acks | Per message, with an **ack deadline** (lease) the consumer can extend | Unacked messages are redelivered after the deadline |
| Ordering | Off by default; on per **ordering key** | Global ordering kills throughput; per-key keeps parallelism |
| Flow control | Max outstanding messages/bytes per consumer | Protects slow consumers (backpressure, lesson 7.6) |
| Failures | Max delivery attempts → dead-letter topic | One poison message mustn't block the rest |
| Transport | gRPC for high-throughput clients; REST/JSON for everyone else | Same model, two encodings (lesson 20.5) |

## 3. The API

```
PUT  /v1/topics/orders                                        → 201 (idempotent create)
POST /v1/topics/orders:publish
     {"messages": [{"data": "eyJvcmRlcl9pZCI6...", "attributes": {"type": "order.placed"},
                    "ordering_key": "customer_42", "message_id_hint": "ord_91-placed"}]}
→ 200 {"message_ids": ["8812736123"]}

PUT  /v1/subscriptions/billing-orders
     {"topic": "orders", "ack_deadline_seconds": 30, "filter": "attributes.type = \"order.placed\"",
      "enable_ordering": true, "dead_letter": {"topic": "orders-dlq", "max_attempts": 10},
      "retry": {"min_backoff": "10s", "max_backoff": "600s"},
      "push": null}                                            → 201

POST /v1/subscriptions/billing-orders:pull {"max_messages": 100}
→ 200 {"received": [{"ack_id": "a1…", "message": {...}, "delivery_attempt": 1}]}
POST /v1/subscriptions/billing-orders:acknowledge {"ack_ids": ["a1…"]}          → 200
POST /v1/subscriptions/billing-orders:modifyAckDeadline {"ack_ids": [...], "seconds": 60}  → 200
POST /v1/subscriptions/billing-orders:seek {"time": "2026-10-27T00:00:00Z"}     → 200  (replay)

Push subscriptions:  POST https://billing.internal/hooks/orders  (signed; 2xx = ack, else retry with backoff)
```

## 4. Cross-cutting

- **Auth:** per-topic publish rights and per-subscription consume rights (IAM roles); push endpoints authenticated with
  signed tokens.
- **Quotas:** publish throughput per topic and project; message and batch size limits; `429`/`RESOURCE_EXHAUSTED` with
  backoff hints.
- **Schemas:** optional schema per topic (Avro or Protobuf) validated on publish, so producers can't break consumers.
- **Observability:** per subscription: backlog size, **oldest unacked message age** (the key alert), delivery attempts,
  dead-letter count.

## 5. Evaluation

- Publish: the API acks after the message is replicated in at least two zones: ~10-30 ms.
- Delivery: messages are stored in partitions; consumers pull in batches; end-to-end latency is mostly batching delay
  and the consumer's own processing.
- Failure modes: a slow consumer grows its backlog without affecting others (each subscription has its own cursor and
  acks); a crashing consumer redelivers after the ack deadline; a poison message goes to the DLQ after 10 attempts.
- Hot ordering keys limit throughput for that key to one consumer at a time, the same trade-off as Kafka partitions.

## Try it

Billing must never charge twice, and the subscription is at-least-once. What does billing's consumer do?

<details>
<summary>Answer</summary>

Use a stable business id (`order_id`, or the publisher's `message_id_hint`) as an idempotency key: in one transaction,
insert it into a `processed_messages` table (unique constraint) and create the charge; if the insert conflicts, it's a
duplicate, so ack and skip. Ack only after the transaction commits. Extend the ack deadline for slow charges rather than
letting the message be redelivered mid-processing.
</details>

## Key takeaways

- Topics fan out to subscriptions; each subscription tracks its own progress and acks.
- At-least-once delivery with ack deadlines, retries with backoff and dead-letter topics; consumers dedupe.
- Ordering per key, flow control per consumer, schemas per topic.
- Alert on the oldest unacked message age, not just backlog size.

# Design a social feed API

A social network like Twitter/X has a deceptively small API: post something, read a timeline, follow someone, like a
post. Underneath, the home timeline is one of the most famous scaling problems there is (lesson 30.7 covers Twitter's
fan-out on write vs read). The API's job is to make timelines fast and stable to scroll, to keep posting safe to
retry, and, for a public developer API, to price and limit access fairly.

## 1. Requirements

**Functional**
- Post (text, media, replies, quotes); delete own posts.
- Home timeline (people you follow, ranked or chronological), user timelines, a post's replies.
- Follow and unfollow; like and repost; search.
- A public developer API for reading and posting, with streaming of filtered posts.

**Non-functional**
- Timeline p95 < 300 ms; posting p95 < 500 ms; new posts visible to followers within seconds.
- Hundreds of millions of daily users; celebrity accounts with 100M+ followers.
- Developer API: tiered access, abuse prevention.

## 2. Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Timeline pagination | Cursor with `since_id` / `until_id` (or an opaque token) | New posts arrive constantly; offsets would duplicate and skip |
| IDs | Time-ordered 64-bit ids (Snowflake, lesson 26.11), sent as **strings** in JSON | Sortable by time; JavaScript can't represent 64-bit integers exactly |
| Posting | `POST /posts` with an idempotency key; media uploaded first | Safe retries on mobile; small post bodies |
| Timeline assembly | Precomputed home timelines (fan-out on write) for most users; celebrity posts merged at read time | The hybrid that keeps both reads and writes bounded |
| Expansions and fields | `?expansions=author_id&post.fields=created_at,public_metrics` | One call returns posts with their authors, without over-fetching |
| Real-time | A filtered stream (long-lived HTTP stream) for developers; push notifications and in-app refresh for users | Polling a timeline every second for millions of users is wasteful |

## 3. The API

```
POST /v2/media/uploads ... → {"media_id": "1849…"}          (resumable for video, lesson 25.3)
POST /v2/posts  Idempotency-Key: …   {"text": "…", "media_ids": ["1849…"], "reply_to": "1850…"}
→ 201 {"data": {"id": "1851023446912040960", "text": "…"}}

GET /v2/timelines/home?max_results=50&pagination_token=…&expansions=author_id,attachments.media_keys
→ 200 {"data": [{"id": "…", "text": "…", "author_id": "…", "created_at": "…",
                 "public_metrics": {"like_count": 812, "repost_count": 40}}],
       "includes": {"users": [ … ], "media": [ … ]},
       "meta": {"newest_id": "…", "oldest_id": "…", "next_token": "…"}}

GET  /v2/timelines/home?since_id=<newest_id>       → only newer posts ("12 new posts" banner)
GET  /v2/users/:id/posts?pagination_token=…
PUT  /v2/users/me/following/:target_id             → 204 (idempotent follow)
DELETE /v2/users/me/following/:target_id           → 204
PUT  /v2/users/me/likes/:post_id                   → 204
GET  /v2/posts/stream?rules=lang:hi has:media      → long-lived stream of matching posts (developer API)
```

`includes` deduplicates related objects: 50 posts from 12 authors carry 12 user objects, not 50.

## 4. The developer API as a product

- **Pricing and tiers** define the contract as much as endpoints (lesson 19.3). X moved its API from free access to
  paid tiers in 2023 and to pay-per-use (a price per post read and per post created) as the default in February 2026;
  integrations that didn't budget for it stopped.
- **Limits** per app and per user token, per 15-minute window and per month, with `x-rate-limit-*` headers and `429`.
- **Auth:** OAuth 2 (authorization code + PKCE) to act on behalf of users; app-only bearer tokens for public reads.
- **Compliance:** deleted posts must be deleted downstream too; the API sends deletion events that developers are
  required to honour.

## 5. Evaluation

- **Home timeline read:** fetch the precomputed list of post ids for the user from a cache (~2 ms), merge recent posts from
  the few celebrities they follow (~10 ms), rank (~20-50 ms), hydrate posts and authors from caches in batches (~10 ms):
  well within 300 ms including the network.
- **Post write:** store the post (~10 ms), respond, then fan out asynchronously to followers' timelines (seconds for
  big accounts; celebrity posts skip fan-out).
- **Hot posts:** a viral post's like count is a hot key: counters are sharded and approximate counts are shown
  (lesson 12.8).

## Try it

Why are tweet/post ids returned as strings in JSON, and what breaks if they aren't?

<details>
<summary>Answer</summary>

They're 64-bit integers. JavaScript numbers are double-precision floats with 53 bits of integer precision, so
`JSON.parse` silently turns `1851023446912040961` into `1851023446912041000`, the same number it gets for
`…960`. Clients then request or link to the **wrong post**. Twitter famously added `id_str` next to `id` for exactly this reason. Opaque string
ids also leave room to change the id scheme later.
</details>

## Key takeaways

- Timelines need cursor pagination (`since_id`/`until_id` or tokens) and time-ordered ids sent as strings.
- Make posting idempotent; upload media first; use expansions and `includes` to avoid N+1 calls.
- Precompute timelines for most users and merge celebrity posts at read time.
- For a public API, pricing, limits and compliance events are part of the contract.

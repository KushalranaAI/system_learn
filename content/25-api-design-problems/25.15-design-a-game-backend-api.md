# Design a game backend API

An online multiplayer game has two kinds of traffic that couldn't be more different. During a match, the game client
and a game server exchange tiny state updates 20-60 times a second, where 100 ms of lag decides who wins. Around the
match, everything is ordinary APIs: sign in, load your profile and inventory, buy a skin, find a match, see the
leaderboard. Designing a game backend means keeping those two worlds apart.

## 1. Requirements

**Functional**
- Accounts and sessions across platforms (PC, console, mobile).
- Profiles, inventories, in-game store purchases.
- Matchmaking by skill, region and mode; parties of friends.
- Real-time matches on dedicated servers; results and rewards afterwards.
- Leaderboards (global, regional, friends) and seasons.

**Non-functional**
- In-match latency < 50-100 ms; matchmaking within ~30-60 s.
- Season launches: millions of logins in an hour.
- Purchases exactly once; no cheating through the API.

## 2. The real-time plane

| Concern | Typical design |
|---------|----------------|
| Transport | UDP with a custom protocol (or a library like ENet, or QUIC), not HTTP |
| Authority | The **server** simulates the game; clients send inputs, not results ("I pressed jump", not "I'm at x=40") |
| Tick rate | Server updates 20-128 times a second depending on the genre |
| Hiding latency | Client-side prediction, server reconciliation, interpolation of other players |
| Placement | Game servers in many regions; matchmaking picks the region with the best ping for the group |

The APIs below never touch this loop. They hand out a ticket to join a server, and receive results afterwards.

## 3. The service APIs

```
POST /v1/sessions {"platform": "steam", "platform_token": "…"}          → 200 {"access_token", "refresh_token", "player_id"}
GET  /v1/players/me                                                     → 200 {profile, level, ranks}
GET  /v1/players/me/inventory?cursor=…                                  → 200

POST /v1/store/purchases  Idempotency-Key: …  {"offer_id": "skin_dragon", "price": {"amount": 1200, "currency": "GEMS"}}
→ 201 {"purchase_id": "pur_7", "granted": ["skin_dragon"]}     (409 if the price changed, 402 if not enough gems)

POST /v1/matchmaking/tickets {"mode": "ranked_5v5", "party_id": "pty_3", "regions_ping_ms": {"ap-south": 28, "me-central": 61}}
→ 202 {"ticket_id": "tkt_91", "status": "searching", "estimated_wait_s": 40}
GET  /v1/matchmaking/tickets/tkt_91        (or a push over the player's notification socket)
→ 200 {"status": "found", "match_id": "m_4", "server": {"host": "203.0.113.40", "port": 7777},
       "join_token": "<signed, single-use, expires in 60 s>"}
DELETE /v1/matchmaking/tickets/tkt_91      → 204 (leave the queue)

Game server → backend (server credentials, not player tokens)
POST /v1/matches/m_4/results {"players": [{"id": "…", "outcome": "win", "stats": {...}}]}   → 200

GET /v1/leaderboards/season-12/ranked?around=me&limit=20                → 200 (from Redis sorted sets, cached briefly)
```

## 4. Decisions worth defending

| Decision | Why |
|----------|-----|
| Matchmaking tickets are async resources | Matching takes tens of seconds; clients poll or get a push, and can cancel |
| A signed, single-use **join token** for the game server | The game server verifies it locally; no lookup per connection, and it can't be reused or shared |
| **Only game servers** report results and stats | Clients are under the player's control and will be tampered with |
| Purchases with idempotency keys, an explicit price, and a ledger | Retries after a crash or network blip must not double-charge or double-grant; a stale price is rejected |
| Login queue during spikes | `503` + `Retry-After` with a queue position ("you're in line: ~2 min") beats a crash |
| Leaderboards in sorted sets (`ZADD`, `ZREVRANK`) | Rank queries in O(log n), "around me" pages are cheap |

## 5. Evaluation

- **Season launch:** logins jump 3-10x. Pre-scale auth and profile services, cache profiles, and admit players through a
  login queue so the backend stays below its capacity. [The game backend sandbox](#/sandbox?preset=api-game-backend)
  plays a 3x spike.
- **Matchmaking:** tickets wait in pools per mode and region; a matcher runs every few seconds, widening the skill range
  the longer a ticket waits.
- **Cheating through APIs:** clients can call any API directly; all rewards, currency and stats are computed server-side
  and validated (e.g. a match result's kill count must be plausible for its duration).

## Try it

A player buys a skin; the game crashes right after the tap. On restart, how does the client know whether the purchase
happened, without risking a second charge?

<details>
<summary>Answer</summary>

The client saved the purchase intent and its Idempotency-Key locally before sending. On restart it retries the same
request with the same key: if the first attempt went through, the server returns the stored `201` with
`purchase_id` and the granted items; if not, it processes it now. Either way, exactly one charge and one grant. The
client can also reconcile with `GET /v1/players/me/inventory` and `GET /v1/store/purchases?since=…`.
</details>

## Key takeaways

- Keep the real-time match loop (UDP, server-authoritative) separate from the service APIs.
- Matchmaking tickets are async; join tokens are signed, short-lived and single-use.
- Only game servers report results; every reward is computed server-side.
- Purchases are idempotent with explicit prices; spikes are handled with pre-scaling and login queues.

# Design a search API

Search is the front door of most products: a marketplace, a docs site, a music app. Users type a few characters and
expect suggestions before they finish; they press enter and expect relevant, filterable results in a blink. Behind it
sits an index (lesson 29.2), but the API decides how fast it *feels*, how much load reaches the index, and how hard it is
to abuse.

## 1. Requirements

**Functional**
- Suggest completions as the user types.
- Search by text with filters (category, price, location), sorting and facet counts.
- Page through results; open a result.

**Non-functional**
- Suggestions p95 < 100 ms; results p95 < 300 ms (in-region).
- 30,000 searches/s at campaign peaks; heavily skewed (a few hundred queries are a large share).
- Results may be a few seconds stale; the index updates continuously.

## 2. Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Two endpoints | `suggest` separate from `search` | Very different budgets and data: suggestions come from a small prefix index |
| Method | `GET` with the query in the URL | Safe, cacheable, shareable and bookmarkable |
| Pagination | Opaque cursor (`search_after`), depth capped | Deep offsets are expensive on a sharded index and unstable as scores change |
| Filters and sorts | A documented allowlist | Every filter needs index support; arbitrary ones invite slow queries |
| Client behaviour | Debounce (~150 ms), min 2 chars, cancel stale requests | Fewer requests, no stale flashes |
| Caching | CDN/edge cache for popular queries (30-60 s); suggestions cached longer | Skewed traffic means high hit ratios |

## 3. The API

```
GET /v1/suggest?q=wire&limit=8&locale=en-IN
→ 200 {"suggestions": [{"text": "wireless earbuds", "type": "query"},
                       {"text": "Wireless Mouse M185", "type": "product", "id": "prd_91"}]}

GET /v1/search?q=wireless+earbuds&category=audio&price_max=5000&sort=relevance&limit=20&cursor=…
→ 200 {
  "results": [{"id": "prd_91", "title": "…", "price": {"amount": 249900, "currency": "INR"},
               "rating": 4.4, "image": "https://img…/prd_91/w320.avif", "highlight": "<em>wireless</em> earbuds…"}],
  "facets": {"brand": [{"value": "Acme", "count": 132}], "price": [{"range": "0-2000", "count": 410}]},
  "next_cursor": "c2NvcmU6MTIuMyxpZDpwcmRfOTE=",
  "total_estimate": 1840,
  "query_id": "q_7f3a"            ← for click analytics and relevance tuning
}

GET /v1/listings/:id                                   → 200, the full item
POST /v1/search/events {"query_id", "result_id", "position", "action": "click"}  → 202
```

Errors: `400` for unknown filters or sorts (with the allowed list), `422` for a query that's too long, `429` with
`Retry-After` for bursts.

## 4. Cross-cutting

- **Auth:** public search may be anonymous, but rate-limited per IP and per device; signed-in users get personalised
  ranking.
- **Abuse:** scrapers love search. Cap page depth (e.g. 50 pages), cap `limit` (≤ 50), rate-limit deep paging harder,
  and watch for unusual query patterns.
- **Freshness:** responses carry `Cache-Control: public, s-maxage=30` for anonymous queries; personalised ones are
  `private`.
- **Analytics:** `query_id` connects searches to clicks and purchases, which is how relevance gets measured and improved.

## 5. Evaluation and latency budget

| Part (results, p95) | Budget |
|---------------------|--------|
| Network (warm connection, ~40 ms RTT) | 50 ms |
| Edge cache hit | done in ~10 ms (most popular queries) |
| Gateway + auth | 5 ms |
| Query parsing, spell correction | 10 ms |
| Index: 4 shards in parallel, top-k each | 100 ms |
| Merge, rerank top 100 | 20 ms |
| Hydrate prices/stock (batched cache read) | 15 ms |
| Serialise + compress | 5 ms |
| Headroom | 95 ms |
| **Total** | **300 ms** |

Suggestions: a prefix index (a trie or edge n-grams) held in memory, ~5-10 ms of work, mostly network; and the
client's debounce adds its wait on top, so keep it short. Capacity: at 30,000 searches/s with a 60-70% cache hit
ratio, the index sees ~10,000/s. [Try the search sandbox](#/sandbox?preset=api-search) and its 3x campaign spike.

## Key takeaways

- Split suggest and search: different budgets, different indexes.
- GET with the query in the URL, an allowlist of filters and sorts, cursor pagination with a depth cap.
- Debounce and cancel on the client; cache popular queries at the edge.
- Return a query id to connect searches to clicks and measure relevance.

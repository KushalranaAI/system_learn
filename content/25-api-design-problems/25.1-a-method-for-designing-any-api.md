# A method for designing any API

The rest of this module designs fifteen APIs, from search to payments to games. They all follow the same six steps.
Using the same steps every time means you won't forget security or retries on the fourth design, and it gives a design
review (or an interview) a clear structure.

## The six steps

| # | Step | Questions | Output |
|---|------|-----------|--------|
| 1 | **Requirements** | Who calls it and from where? What must they do? How fast, how often, how reliable? | Functional and non-functional requirements, with numbers |
| 2 | **Resources and operations** | What are the nouns? What happens to them? What are their states? | A resource list and state machines |
| 3 | **Style and transport** | Request/response, push, or async? REST, GraphQL, gRPC? JSON or binary? | A justified choice per audience (lesson 20.6) |
| 4 | **The contract** | Endpoints, request and response bodies, errors, pagination | Endpoint table, examples, an OpenAPI/proto sketch |
| 5 | **Cross-cutting concerns** | Auth, limits, idempotency, versioning, caching, events | A checklist applied to each endpoint |
| 6 | **Evaluate** | Does it meet the numbers? What fails, and what happens then? | Latency budget, failure modes, trade-offs |

## Step 1 in detail: requirements with numbers

```
Functional       "Members can borrow a copy of a book and see their loans."
Non-functional   p95 < 300 ms in-region · 99.9% monthly availability · 2,000 req/s peak
                 read/write ratio 50:1 · payloads < 50 KB · data retained 7 years
Audience         own mobile app (lags 6 months behind), web app, 2 partner schools
```

Ask for numbers even when nobody has them; an estimate (lesson 1.4) is better than "fast".

## Step 2: states before endpoints

Many APIs are really **state machines**. Draw them first:

```
loan:   active ──renew──▶ active      payment:  requires_confirmation ─▶ processing ─▶ succeeded
          │                                         │                       └────────▶ failed
          ├──return──▶ returned                     └─▶ requires_action (3-D Secure) ─▶ processing
          └──(due date passes)──▶ overdue ──return──▶ returned
```

Each arrow becomes an operation (and often an event); each state appears in responses.

## Step 5: the cross-cutting checklist

For every endpoint, decide:

| Concern | Question |
|---------|----------|
| AuthN / AuthZ | Who may call it? Which scope? Which object check? (21.5) |
| Validation | What's the schema, and what are the size limits? (21.3) |
| Idempotency | Safe to retry? If POST, does it take an Idempotency-Key? (22.4) |
| Limits | Rate limit and quota? Is it expensive? (22.5) |
| Caching | Public, private or no-store? ETag? (23.3) |
| Pagination | Is it a list? Cursor and max page size? (22.3) |
| Events | Does it emit an event or webhook? (22.6) |
| Versioning | Does it fit the versioning and deprecation policy? (22.1) |
| Observability | Request id, metrics, audit log? (23.5) |

## Step 6: evaluate

- **Latency budget** at a percentile (lesson 24.4): does each endpoint fit, including the network?
- **Capacity**: requests per second per endpoint, and what each one costs downstream.
- **Failure modes**: what if a dependency is slow, a response is lost, a client retries, a region fails?
- **Trade-offs**: what did you give up, and why is that acceptable?

## Try it

Run the six steps on a to-do list API for a mobile app with offline support and shared lists.

<details>
<summary>Answer</summary>

1. 5M users, p95 < 200 ms, offline edits sync later, lists shared with up to 50 people.
2. Resources: `lists`, `tasks`, `members` (sharing), `changes` (a sync feed). Task states: open → done → archived.
3. REST + JSON for the app; push "list changed" notifications over a WebSocket or mobile push.
4. `GET/POST /lists`, `GET/PATCH/DELETE /lists/:id`, `POST /lists/:id/members`, `GET/POST /lists/:id/tasks`,
   `PATCH /tasks/:id` (with `If-Match`), `GET /sync?since=<token>` returning changes and tombstones.
5. OAuth tokens; membership check on every list and task; client-generated task ids (`PUT /tasks/:uuid`) make offline
   creates idempotent; conflicts resolved by version (`412` → client merges); cursor pagination; `private` caching.
6. Sync is one round trip on reconnect; concurrent edits produce `412`s that the client merges field by field; a
   shared list with 50 members gets fan-out notifications, not polling.
</details>

## Key takeaways

- Six steps: requirements, resources and states, style, contract, cross-cutting concerns, evaluation.
- Get numbers for the non-functional requirements; draw state machines before endpoints.
- Run every endpoint through the same cross-cutting checklist.
- Finish with a latency budget, failure modes and the trade-offs you chose.

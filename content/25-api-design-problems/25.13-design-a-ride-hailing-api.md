# Design a ride-hailing API

A ride-hailing app like Uber is two apps talking to one platform: riders who want a car now, at a price they agreed to,
and drivers who stream their location every few seconds and accept or decline trips. The API has to handle a long-lived
**state machine** (requested → matched → arriving → on trip → completed), a firehose of **location updates**, and
prices that must not change between the quote and the ride. (Lesson 30.5 covers Uber's architecture; the "ride dispatch"
lab covers geospatial matching.)

## 1. Requirements

**Functional**
- Riders: get a price quote, request a ride, see the driver approaching, cancel, pay, rate.
- Drivers: go online/offline, stream location, receive and accept offers, update trip status.
- Both: live trip updates; receipts.

**Non-functional**
- Driver locations every ~4 s from millions of drivers: hundreds of thousands of updates a second.
- Matching within a few seconds; rider sees driver movement with < 2 s delay.
- A ride request must not create two rides; a quote's price must be honoured.

## 2. Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Quotes as resources with expiry | `POST /quotes` → price, valid ~2 minutes | The price the rider saw is the price they pay (fare locked by quote id) |
| Ride requests are idempotent | Client-generated request id / Idempotency-Key | A retry on a flaky network must not book two cars |
| Ride is a state machine | Explicit states and allowed transitions; `409` for invalid ones | Rider and driver apps race (cancel while accepting) |
| Driver location | A persistent connection (WebSocket, gRPC stream or MQTT), batched updates, latest-wins | Hundreds of thousands of tiny messages/s; old positions are useless |
| Live updates to riders | Server push over the same kind of connection; the trip resource as fallback | Smooth map, resilient to drops |
| Matching | Asynchronous after the request is accepted | Can take seconds and several offers |

```
rider: requested ─▶ matching ─▶ driver_assigned ─▶ driver_arriving ─▶ on_trip ─▶ completed
           │             │               │                 │
           └─────────────┴──── canceled (rules and fees depend on the state) ─┘
           matching ─▶ no_drivers (after a timeout)
```

## 3. The API

```
Rider
POST /v1/quotes {"pickup": {"lat": 19.076, "lng": 72.8777}, "dropoff": {...}, "product": "go"}
→ 201 {"id": "qt_6M", "fare": {"amount": 31200, "currency": "INR"}, "eta_pickup_s": 240, "expires_at": "…"}

POST /v1/rides  Idempotency-Key: 9a1…   {"quote_id": "qt_6M", "payment_method": "pm_…"}
→ 201 {"id": "ride_3T", "status": "matching"}         (409 if the quote expired: get a new quote)
GET  /v1/rides/ride_3T                                 → 200 {"status": "driver_arriving", "driver": {...},
                                                              "vehicle": {...}, "driver_location": {...}, "eta_s": 180}
POST /v1/rides/ride_3T/cancel {"reason": "…"}          → 200 {"status": "canceled", "fee": {...}}
WS   /v1/rides/ride_3T/updates                         ← {"type": "driver_location", "lat", "lng", "heading", "ts"}
                                                        ← {"type": "status", "status": "on_trip"}

Driver
PUT  /v1/drivers/me/availability {"online": true}      → 200
WS   /v1/drivers/me/stream   → {"type": "location", "lat", "lng", "heading", "speed", "ts"} every ~4 s
                             ← {"type": "offer", "ride": "ride_3T", "pickup": {...}, "expires_in_s": 15}
POST /v1/offers/off_81/accept                          → 200 (409 if another driver got it or it expired)
POST /v1/rides/ride_3T/events {"type": "arrived" | "started" | "completed", "location": {...}}   → 200
```

## 4. Cross-cutting

- **Authorization:** a rider sees only their rides; a driver sees pickup details only after accepting; exact addresses
  are hidden in receipts afterwards.
- **Validation:** coordinates in range and plausible (no 500 km jumps between updates; GPS spoofing checks).
- **Limits:** quote requests per rider per minute (quotes are expensive and leak pricing); location updates capped per
  driver.
- **Privacy:** phone numbers masked through a calling proxy; location history retained only as needed.

## 5. Evaluation

- **Location ingestion:** 1M online drivers ÷ 4 s = 250,000 updates/s, written to an in-memory geospatial index (geohash or
  H3 cells, lesson 26.9) partitioned by city, latest position only, plus a stream for analytics.
- **Request:** validate the quote, create the ride, respond: ~100 ms; matching runs async, offering to the best driver
  with a 15 s timeout, then the next.
- **Races:** the driver accepts as the rider cancels: transitions are checked atomically (compare-and-set on the ride's
  version); one wins, the other gets `409`.
- **Failure:** the rider's app loses its connection mid-trip and recovers state with `GET /rides/:id`.

## Try it

Two drivers tap "Accept" on the same offer at the same moment. What does the API do?

<details>
<summary>Answer</summary>

Offers are per driver, but suppose a bug or a re-offer means two are live. `POST /offers/:id/accept` runs a conditional
update on the ride: `UPDATE rides SET driver_id = $1, status = 'driver_assigned', version = version + 1 WHERE id = $2 AND
status = 'matching' AND version = $3`. Exactly one update succeeds; that driver gets `200`, the other `409 Conflict`
("this ride is no longer available") and is returned to the pool. The rider receives one `driver_assigned` event.
</details>

## Key takeaways

- Quotes with expiry lock prices; idempotent ride requests prevent double bookings.
- Model the ride as a state machine; reject invalid transitions with `409`, using conditional updates against races.
- Stream driver locations over persistent connections, latest-wins, into a geospatial index.
- Match asynchronously and push updates; the ride resource is the fallback for any missed event.

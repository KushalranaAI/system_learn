# Design a messaging API

A messaging app like Messenger or WhatsApp has three promises that are hard to keep at once: a message is delivered
**once** (never lost, never duplicated), conversations stay **in order**, and messages show up in **under a second**,
across phones that go offline, switch networks and run app versions from last year. The API design is what makes those
promises keepable. (Lesson 30.3 looks at WhatsApp's architecture; lab "chat delivery" covers the backend.)

## 1. Requirements

**Functional**
- One-to-one and group conversations (up to ~1,000 members).
- Send text, media and reactions; edit and delete own messages.
- Delivery and read receipts; typing indicators; presence ("online").
- Multiple devices per user; history syncs to a new device.

**Non-functional**
- p95 delivery < 500 ms when both sides are online; no lost or duplicate messages.
- Billions of messages a day; mobile clients offline for hours.
- End-to-end encryption for message content.

## 2. Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Sending | `POST` with a **client-generated message id** | Retries after a lost response don't create duplicates (lesson 22.4) |
| Ordering | Server assigns a **per-conversation sequence number** on accept | One authoritative order everyone converges on; partition by conversation id |
| Real-time delivery | One persistent connection per device (WebSocket or MQTT) | Server pushes messages, receipts and typing events |
| Offline catch-up | `GET /sync?since=<cursor>` returns everything since the device's last cursor | Push is best-effort; the sync cursor is the source of truth |
| Receipts | Events in the same stream, coalesced ("read up to seq 812") | One receipt covers many messages |
| Encryption | Client-side (Signal protocol); the server stores and forwards ciphertext | The API carries opaque payloads plus routing metadata |
| Media | Upload separately (presigned URL), message carries a reference | Keeps messages small; media served by CDN |

## 3. The API

```
POST /v1/conversations/cnv_7/messages
     {"client_message_id": "c0f1…b2", "type": "text", "ciphertext": "…", "reply_to": "msg_812"}
→ 201 {"id": "msg_813", "seq": 813, "sent_at": "2026-10-28T10:00:01.234Z"}
   (retrying with the same client_message_id returns the same 201 body)

GET  /v1/sync?cursor=dev_9:812&limit=500
→ 200 {"events": [{"type": "message", "conversation": "cnv_7", "seq": 813, ...},
                  {"type": "receipt", "conversation": "cnv_7", "user": "u_2", "read_up_to": 813},
                  {"type": "message_deleted", ...}],
       "next_cursor": "dev_9:950", "has_more": false}

GET  /v1/conversations/cnv_7/messages?before_seq=700&limit=50      → 200 (scroll back in history)
POST /v1/conversations/cnv_7/receipts {"read_up_to": 813}           → 204
PATCH /v1/messages/msg_813 {"ciphertext": "…"}                      → 200 (edit window, e.g. 15 min)
DELETE /v1/messages/msg_813?for=everyone                            → 204

WebSocket wss://chat…/v1/stream   (authenticated in the first frame)
  ← {"type": "message", "conversation": "cnv_7", "seq": 813, ...}
  ← {"type": "typing", "conversation": "cnv_7", "user": "u_2", "ttl_ms": 5000}
  → {"type": "ack", "cursor": "dev_9:813"}
```

## 4. Cross-cutting

- **Authorization:** membership checked on every send, read and sync; removed members stop receiving immediately.
- **Limits:** per-user send rates; per-conversation fan-out limits; anti-spam on new accounts.
- **Idempotency:** `client_message_id` scoped per sender; dedupe window of days (phones retry after coming back
  online).
- **Versioning:** event types are an open enum; old clients must ignore unknown event types (new features like polls
  ship without breaking them).
- **Privacy:** with end-to-end encryption, server-side search, previews and moderation work only on metadata or on
  user reports.

## 5. Evaluation

- Send path: accept, persist with sequence, ack: ~20-50 ms; push to online recipients over their open connections:
  ~50-150 ms more. Within the 500 ms budget.
- A group of 1,000: one write, then fan-out of 1,000 pushes (and many devices each). Large groups are hot partitions;
  [the messenger sandbox](#/sandbox?preset=api-messenger) shows one creating consumer lag.
- Offline: a phone back after 6 hours makes one `sync` call (paginated), not thousands of pushes.
- Failures: a lost push is fixed by the next sync; a lost send response is fixed by retrying with the same
  `client_message_id`.

## Try it

A user sends a message in a tunnel. The app shows a spinner. What exactly happens, step by step, until both sides show
the message once?

<details>
<summary>Answer</summary>

The app stores the message locally with a `client_message_id` and shows "sending". It POSTs; the request (or the
response) is lost. When connectivity returns, it retries with the same id. The server either accepts it now (first time
it sees it) or finds the id already stored and returns the original `seq`. The app replaces "sending" with "sent"
and orders the message by `seq`. The recipient got it by push if online, or will get it in its next `sync`. Duplicates
are impossible because both the server and clients dedupe by `(sender, client_message_id)` and order by `seq`.
</details>

## Key takeaways

- Client-generated message ids make sending idempotent; server-assigned per-conversation sequences give order.
- Push over a persistent connection for speed; a sync cursor for correctness.
- Receipts are coalesced events; event types are an open enum.
- End-to-end encryption turns the server into a router of ciphertext and metadata.

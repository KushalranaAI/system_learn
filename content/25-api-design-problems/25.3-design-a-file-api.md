# Design a file API

A file API looks like `PUT` a file, `GET` it back. Then real users show up with 3 GB videos on train Wi-Fi,
attachments that must be virus-scanned, files shared with expiring links, and downloads that resume halfway. Files are
the one place where bytes, not round trips, dominate, and where pushing those bytes through your API servers is
usually a mistake.

## 1. Requirements

**Functional**
- Upload files up to 5 GB, resumable after a dropped connection.
- Download files, including partial (range) downloads.
- Metadata: name, type, size, owner, created date; list and search a user's files.
- Share a file with a link that expires.
- Scan uploads for malware; generate previews.

**Non-functional**
- Uploads survive several drops; no byte uploaded twice in the happy path.
- Metadata calls p95 < 200 ms; downloads start in < 300 ms.
- Durable storage (object storage, lesson 29.1); 1,000 uploads/s completing at peak.

## 2. Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Upload session as a resource | `POST /uploads` creates it | Resumability needs server-side state: which bytes arrived |
| Where bytes go | **Presigned URLs** straight to object storage | API servers never carry gigabytes; storage scales on its own |
| Chunking | Multipart / resumable chunks of 8-16 MB | A drop costs one chunk; the simulation below shows the trade-off |
| Processing | Async after completion: queue → scanners and preview workers | Seconds to minutes of work shouldn't hold a request |
| Downloads | Short-lived signed URLs, often via a CDN; `Range` support | Resume and stream; no proxying through the API |
| Protocol | REST + JSON for control; the tus open protocol or the storage provider's multipart API for bytes | Standard, client libraries exist |

## 3. The API

```
POST /v1/uploads {"name": "trip.mp4", "size": 2147483648, "type": "video/mp4", "sha256": "…"}
→ 201 {"id": "upl_5Kd", "chunk_size": 16777216,
       "parts": [{"number": 1, "url": "https://storage…/upl_5Kd?part=1&X-Signature=…", "expires": "…"}, …]}

PUT  <presigned part URL>      (bytes, straight to storage)          → 200 ETag: "part-etag-1"
GET  /v1/uploads/upl_5Kd       → 200 {"received_parts": [1,2,3,5], "status": "uploading"}   (resume after a drop)
POST /v1/uploads/upl_5Kd/complete {"parts": [{"number": 1, "etag": "…"}, …]}
→ 202 {"file_id": "fil_9Qa", "status": "processing"}

GET  /v1/files/fil_9Qa         → 200 {"id", "name", "size", "status": "ready", "preview_url", …}
GET  /v1/files/fil_9Qa/content → 302 Location: https://cdn…/fil_9Qa?sig=…&exp=…   (supports Range)
POST /v1/files/fil_9Qa/links {"expires_in": 86400, "access": "view"} → 201 {"url": "https://…/s/Xy8k"}
GET  /v1/files?folder=…&cursor=…                                    → 200 (cursor-paginated)
DELETE /v1/files/fil_9Qa       → 204 (soft delete, purged after 30 days)
```

Events: `file.ready`, `file.rejected` (malware), delivered by webhook or pushed to the app.

## 4. Cross-cutting

- **Authorization:** the API checks quota, type and size **before** issuing upload URLs; URLs are scoped to one object,
  one method and a short expiry.
- **Validation:** don't trust the declared type; sniff magic bytes after upload, re-encode images, scan everything,
  quarantine until clean.
- **Integrity:** per-part checksums and a whole-file hash; reject mismatches.
- **Idempotency:** `POST /uploads` takes an Idempotency-Key; re-uploading a part is naturally idempotent (same part
  number overwrites).
- **Cleanup:** abandoned upload sessions expire (and their parts are deleted) after 24-72 hours.

## 5. Evaluation

- A 2 GB upload at 10 Mbps takes ~27 minutes. With a drop every 10 minutes, a single `PUT` almost never finishes;
  16 MB chunks lose at most one chunk per drop.
- API servers handle only small JSON calls: ~3 per chunk-batch plus `complete`, regardless of file size.
- Processing at 1,000 completions/s needs enough workers to keep the queue drained
  ([file uploads sandbox](#/sandbox?preset=api-file-uploads)).

## Try it

Use the upload simulation: 2 GB, 10 Mbps, 6 drops an hour. Compare one PUT with resumable chunks of 1 MB, 8 MB and
256 MB.

<details>
<summary>Answer</summary>

One PUT: only ~30% of uploads finish within 5 attempts, and ~1.5x the file size is sent. Resumable 8 MB chunks: all
finish, about 1% extra bytes. 1 MB chunks: all finish but slower (a round trip per chunk). 256 MB chunks: some fail,
and each drop wastes up to 256 MB. The [video uploads lab](#/labs/api-video-uploads) adds the endpoint design and the
processing queue.
</details>

## Key takeaways

- Model uploads as sessions; send bytes to object storage with presigned URLs, never through API servers.
- Chunked, resumable uploads survive flaky networks; ask the server what it has before resuming.
- Validate type and size before issuing URLs, scan and re-encode after, and process asynchronously.
- Serve downloads through signed, expiring URLs with Range support.

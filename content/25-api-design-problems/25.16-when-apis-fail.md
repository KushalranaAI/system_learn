# When APIs fail

On the evening of 6 May 2020, Spotify, TikTok, Pinterest, Venmo, DoorDash and dozens of other iOS apps started crashing
the moment they opened, including for people who had never used Facebook login. None of those companies had shipped
anything. A server-side configuration change at Facebook sent their iOS SDK data it didn't expect, and the SDK, embedded in
all those apps, crashed on launch. Facebook rolled the change back after a few hours; a similar failure hit again in July.

API failures are rarely about one bad request. They're about **dependencies**: the APIs you call, the APIs your
libraries call, and the people calling you.

## Three classic failures

### Knight Capital, 2012: a deploy that wasn't

A trading firm deployed new code to seven of its eight servers. The eighth still had old code that a reused flag now
triggered, and it sent millions of unintended orders to the market in 45 minutes, losing about $440 million. Lesson
31.14 tells the full story.

**API lesson:** a flag or field whose meaning changes is a breaking change, even inside one company. Never reuse
identifiers (feature flags, enum values, Protobuf field numbers) for new meanings, deploy consistently, and have a kill
switch.

### Amazon S3, 2017: one command, a region down

An engineer debugging a billing issue ran a command with a typo that removed far more servers than intended from two S3
subsystems in us-east-1. S3 there was unavailable for about four hours, and so were large parts of the internet that
depended on it, including AWS's own status dashboard. Lesson 31.6 has the details.

**API lesson:** your API is only as available as its dependencies. Know which ones are on your critical path, have a
plan for each one being down (cached data, degraded mode, another region), and make sure your status page doesn't depend
on the thing that's broken.

### Facebook SDK, 2020: someone else's code inside your app

The Facebook SDK fetched configuration from Facebook's servers at app start. When the server sent an unexpected value, the
SDK's parsing code crashed the host app. Every app embedding the SDK inherited the failure, and couldn't ship a fix faster
than Facebook could roll back.

**API lesson:** an SDK is an API client running inside other people's products. Validate every server response, fail
safe (log and continue, never crash the host), stage server-side config changes like code, and let integrators isolate
your SDK (lazy init, timeouts, kill switches).

## Patterns behind API failures

| Pattern | Example | Mitigation |
|---------|---------|------------|
| **Breaking change shipped by accident** | A field type changes; an enum gains a value strict clients can't parse | Contract tests and breaking-change checks in CI (lesson 22.2), tolerant readers |
| **Config or data change, not code** | Facebook SDK 2020, Cloudflare 2025's oversized feature file (lesson 31.2) | Validate configs, stage rollouts, fast rollback (staged rollout simulation) |
| **Dependency outage** | S3 2017; a payment provider or maps API down | Timeouts, circuit breakers, fallbacks, multi-provider for critical paths |
| **Auth and permission changes** | A partner's tokens suddenly lack a newly required scope after a webhook or version change | Treat scope and permission changes as breaking; announce and migrate like any other |
| **Quota and pricing changes** | A free tier ends; rate limits tighten | Monitor usage against limits; budget; abstract providers |
| **Retry storms** | Clients hammer a recovering API | Backoff with jitter, retry budgets, load shedding (lesson 12.2) |
| **Certificate or DNS expiry** | Expired TLS certificate on an API domain | Automated renewal and expiry alerts (lesson 21.2) |

## Designing to survive them

**As a provider:**
- Ship changes in stages (canary → small percentage → everyone), including config and data.
- Detect breaking changes before deploy; version and deprecate deliberately.
- Publish a status page hosted independently, with per-API components.
- Write postmortems, and share them with integrators when they were affected.

**As a consumer:**
- Wrap every third-party API in an adapter with timeouts, retries (for idempotent calls), a circuit breaker and metrics.
- Validate responses; never let a surprising payload crash your process.
- Know your fallback for each dependency: cached data, a second provider, a degraded feature, or a clear error.
- Watch providers' changelogs and deprecation headers, and test against their sandbox in CI.

## Try it

Your app embeds a third-party analytics SDK and calls a maps API and a payments API. Write a one-page mitigation plan.

<details>
<summary>Answer</summary>

- **Analytics SDK:** initialise it lazily after the first screen, inside a try/catch, behind a remote kill switch; pin
  its version; never block app start on it.
- **Maps API:** cache tiles and recent geocodes; if the API is down, show the last known map and a text address; budget
  and alert on quota; keep the integration behind an adapter so a second provider can be added.
- **Payments API:** idempotency keys on every write, timeouts and retries only on network errors and 5xx, a circuit
  breaker that shows "payments are temporarily unavailable" instead of hanging, webhook-based reconciliation, and a daily
  job comparing your records with the provider's.
- For all three: dashboards of error rate and latency per dependency, alerts, and a runbook entry for "provider X is down".

## Key takeaways

- Many API failures come from dependencies: the APIs and SDKs you call, and the config they fetch.
- Knight Capital: never reuse identifiers for new meanings. S3: know and plan for your critical dependencies. Facebook
  SDK: validate responses and never crash the host.
- Breaking changes, config changes, quota changes and retry storms are recurring patterns with known mitigations.
- Providers stage, detect and communicate; consumers isolate, validate and fall back.

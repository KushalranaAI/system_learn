# Design a code judge API

On a practice site like LeetCode, users submit code in a dozen languages and expect a verdict ("Accepted", "Wrong
Answer on test 37", "Time Limit Exceeded") within seconds. The code is untrusted, it may loop forever or try to escape,
and on Sunday mornings tens of thousands of contestants submit within the same few minutes. The API has to accept
submissions instantly and judge them safely somewhere else.

## 1. Requirements

**Functional**
- Browse problems; read a problem with examples, constraints and starter code per language.
- Run code against custom input ("Run") and submit it against hidden tests ("Submit").
- See verdicts with runtime and memory; see submission history.
- Contests: timed problem sets, a live leaderboard, penalties for wrong submissions.

**Non-functional**
- Verdict p95 < 5 s normally, < 30 s during contest peaks.
- Untrusted code never reaches anything but its sandbox.
- Normal load ~500 submissions/s; contest starts bring 4-10x spikes.

## 2. Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Submission is asynchronous | `POST /submissions` → `202` + id | Judging takes seconds; holding requests open ties up servers and breaks on mobile networks |
| Queue + judge workers | Separate queues for "run" (interactive) and "submit"; contests get their own priority | A contest surge mustn't starve practice users, and vice versa |
| Sandbox | Each run in an isolated container or microVM (gVisor, Firecracker): no network, read-only filesystem, CPU, memory, process and time limits | Untrusted code |
| Verdict delivery | Poll `GET /submissions/:id` (with `Retry-After`) or subscribe over SSE/WebSocket | Cheap, works everywhere |
| Rate limits | Per user (e.g. 1 submit every 5 s, more for "run"), per IP for anonymous runs | Stop one user flooding the judges |
| Tests | Hidden test files stored server-side, versioned per problem | Users never see them; rejudging is possible after a fix |

## 3. The API

```
GET  /v1/problems?tag=graphs&difficulty=medium&cursor=…        → 200 (public, cacheable)
GET  /v1/problems/two-sum                                       → 200 {"statement", "examples", "constraints",
                                                                       "starter_code": {"python3": "…", "cpp": "…"}}
POST /v1/submissions {"problem": "two-sum", "language": "python3", "code": "…", "contest": null}
     Idempotency-Key: …
→ 202 {"id": "sub_8Yd", "status": "queued", "position": 1240}
     Location: /v1/submissions/sub_8Yd   Retry-After: 2

GET  /v1/submissions/sub_8Yd
→ 200 {"status": "running", "tests_passed": 12, "tests_total": 63}
→ 200 {"status": "finished", "verdict": "accepted", "runtime_ms": 48, "memory_kb": 17120,
       "percentile": {"runtime": 82.4}}
→ 200 {"status": "finished", "verdict": "wrong_answer", "failed_test": {"input": "…", "expected": "…", "got": "…"}}

GET  /v1/submissions/stream?ids=sub_8Yd                          → SSE: status updates as they happen
POST /v1/runs {"problem", "language", "code", "input"}           → 202 (same lifecycle, fewer tests, shorter limits)
GET  /v1/contests/weekly-512/leaderboard?cursor=…                → 200 (cached a few seconds)
```

Errors: `413` for code over the size limit, `422` for unsupported languages, `429` with `Retry-After` when submitting
too fast, `409` when the contest has ended.

## 4. Cross-cutting

- **Security:** the API never executes code; workers pull jobs and run them in sandboxes with no credentials and no
  network. Outputs are size-limited and treated as untrusted when shown.
- **Fairness in contests:** submissions are timestamped when accepted by the API, not when judged, so queue delays don't
  cost contestants penalty time.
- **Caching:** problem pages and editorials are public and cached at the CDN; leaderboards are cached for a few seconds;
  submissions are private.
- **Idempotency:** a double-tap of Submit with the same key creates one submission (and one penalty).

## 5. Evaluation

- **Normal:** 500 submissions/s × ~2 s of judging each = ~1,000 sandbox slots busy; plus headroom.
- **Contest:** a 4x spike for the first ten minutes. Options: pre-scale the judge fleet before the contest starts
  (it's scheduled), give contest submissions priority, and let practice "runs" queue longer.
  [The code judge sandbox](#/sandbox?preset=api-code-judge) plays the surge.
- **Verdict latency:** queue wait + container start (~100-300 ms warm) + compile + tests. Keep a pool of warm sandboxes
  per language to avoid cold starts.

## Try it

Why does `POST /submissions` return `202` and not wait for the verdict, given that most verdicts take only 2 seconds?

<details>
<summary>Answer</summary>

Because 2 seconds is the typical case, not the worst: during a contest the queue may hold submissions for 30 seconds,
mobile connections drop, load balancers and proxies time out, and every waiting request holds a server connection. With
`202`, accepting is fast and constant; the submission is durable once accepted; clients can reconnect and poll or
stream; and the judge fleet can be scaled independently of the API servers.
</details>

## Key takeaways

- Accept untrusted work with `202` and judge it asynchronously in sandboxes.
- Separate queues and priorities keep contests and practice from starving each other.
- Deliver results by polling with `Retry-After` or by streaming; timestamp fairness at acceptance.
- Pre-scale for scheduled spikes and keep warm sandboxes per language.

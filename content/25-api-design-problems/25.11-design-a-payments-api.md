# Design a payments API

A payment gateway like Stripe hides one of the most complicated systems most developers will ever touch: card
networks, issuing banks, 3-D Secure challenges, fraud scoring, currency conversion, settlement days later, refunds and
disputes months later. Its API has to make that feel like a few calls, while guaranteeing the one thing merchants
care about most: **a customer is charged exactly once, for the right amount**. (Lesson 30.10 covers Stripe's
architecture; lesson 32.14 the payment system as an interview problem.)

## 1. How a card payment works

```
customer ─▶ merchant checkout ─▶ payment gateway (Stripe) ─▶ acquirer ─▶ card network (Visa, Mastercard, RuPay)
                                                                                 │
                                                       issuing bank (the customer's bank) ◀┘
1. Authorisation   issuer checks funds and fraud, may ask for 3-D Secure (a challenge in the bank's app); places a hold
2. Capture         merchant confirms the amount to actually take (immediately, or later, e.g. when the order ships)
3. Clearing and settlement   in batches, usually 1-3 days later, money moves issuer → network → acquirer → merchant
4. Later           refunds, chargebacks/disputes (weeks or months), payouts to the merchant's bank
```

Two consequences for the API: **outcomes can be asynchronous** (3-D Secure, bank delays), and **the network can time out
after the bank said yes**.

## 2. Requirements

**Functional**
- Create a payment for an amount and currency; confirm it with a payment method (card, UPI, wallet).
- Handle extra authentication (3-D Secure) and asynchronous methods.
- Capture later, cancel, refund fully or partly; handle disputes.
- Notify merchants of every state change.

**Non-functional**
- **Never** double-charge; never lose a successful payment.
- Confirm p95 < 2 s (bank-dependent); API availability 99.99%.
- Thousands of merchants on integrations that may be years old.

## 3. Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Payment as a stateful resource | A `payment` (Stripe: PaymentIntent) with a state machine | One object tracks every attempt, challenge and outcome |
| Idempotency | `Idempotency-Key` on every POST, stored atomically with the result | Merchant retries after timeouts must be harmless (lesson 22.4) |
| Async outcomes | Signed webhooks + the resource as the source of truth | Banks and challenges finish later |
| Amounts | Integer minor units + ISO currency (`{"amount": 4999, "currency": "INR"}`) | No floating-point money |
| Card data | Collected by the gateway's own UI/SDK and tokenised; merchants handle only tokens | Keeps merchants out of PCI DSS scope |
| Versioning | Account-pinned, date-based versions with request overrides | Old integrations keep working (lesson 22.1) |

```
requires_payment_method ─▶ requires_confirmation ─▶ processing ─▶ succeeded
          ▲                         │                    │
          └──── payment failed ─────┤                    └──▶ requires_capture ─▶ succeeded / canceled
                                    └─▶ requires_action (3-D Secure) ─▶ processing
```

## 4. The API

```
POST /v1/payments  Idempotency-Key: ord_771-pay
     {"amount": 4999, "currency": "INR", "customer": "cus_42", "capture_method": "automatic",
      "metadata": {"order_id": "ord_771"}}
→ 201 {"id": "pay_88", "status": "requires_payment_method", "client_secret": "pay_88_secret_…"}

POST /v1/payments/pay_88/confirm  Idempotency-Key: ord_771-confirm-1   {"payment_method": "pm_card_tok_…"}
→ 200 {"status": "requires_action", "next_action": {"type": "redirect_to_url", "url": "https://acs.bank…"}}
→ 200 {"status": "succeeded", "latest_charge": "ch_19"}

GET  /v1/payments/pay_88                                   → 200 (the source of truth)
POST /v1/payments/pay_88/capture {"amount_to_capture": 4500}  → 200
POST /v1/payments/pay_88/cancel                            → 200
POST /v1/refunds {"payment": "pay_88", "amount": 1000, "reason": "requested_by_customer"}  Idempotency-Key → 201
GET  /v1/events?type=payment.*&after=evt_…                 → 200 (catch-up)

Webhooks: payment.succeeded, payment.failed, payment.requires_action, refund.succeeded, dispute.created
```

Errors carry a stable `code` and a `decline_code` from the bank (`insufficient_funds`, `card_declined`,
`authentication_required`) so merchants can show the right message; `402` is commonly used for card errors.

## 5. Cross-cutting

- **Auth:** secret keys for merchant servers, publishable keys (limited) for browsers and apps; restricted keys with
  scopes; test and live modes with separate keys and data.
- **Idempotency:** keys scoped per account, kept ≥ 24 hours, request fingerprint checked (same key + different body
  → error).
- **Webhooks:** signed, retried for days, deduped by event id, with an events API for catch-up (lesson 22.6).
- **Limits:** per account rate limits; fraud rules (velocity per card, per IP).
- **Audit:** every state change is an immutable event in a double-entry ledger internally.

## 6. Evaluation

| Confirm, p95 | Budget |
|--------------|--------|
| Network merchant ↔ gateway | 100 ms |
| Auth, idempotency lookup, validation | 20 ms |
| Fraud scoring | 50-100 ms |
| Acquirer + network + issuer authorisation | 300-1,500 ms (outside your control) |
| Persist state + outbox event | 20 ms |
| Headroom | rest of 2 s |

**The timeout case:** the issuer approves, but the response to the gateway is lost. The gateway marks the payment
`processing`, queries the network for the outcome (or reverses the authorisation), and tells the merchant by webhook.
Meanwhile the merchant's retry with the same idempotency key returns the same `processing` payment, never a second
charge. [The payments sandbox](#/sandbox?preset=api-payments) shows what happens without these safeguards.

## Try it

Use the idempotency simulation (embedded below): a merchant SDK creates a new key on every retry and saves keys after
the charge. How many double charges per 10,000 payments, and what fixes it?

<details>
<summary>Answer</summary>

A new key per attempt behaves like no key at all: several hundred double charges per 10,000 when ~5% of responses are
lost. One key per payment intent removes almost all of them; saving it in the same transaction as the charge removes
the rest. The [payments API lab](#/labs/api-payments-gateway) walks through the endpoints, key reuse, webhooks and
versioning as checked steps.
</details>

## Key takeaways

- Card payments are multi-step and partly asynchronous; model a payment as a state machine.
- Idempotency keys on every write, stored atomically, are what prevent double charges.
- Webhooks report outcomes; the resource is the source of truth; an events API fills gaps.
- Tokenise card data, use integer minor units, and pin API versions per account.

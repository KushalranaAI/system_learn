# Design a comment API

Comments look trivial: a list of text under a post. Then a celebrity's post gets 400,000 comments in an hour, threads
nest five levels deep, users sort by "top" and "newest", counts must show instantly, spam floods in, and people expect
new replies to appear without refreshing. A comment API is a lesson in pagination, counters and moderation.

## 1. Requirements

**Functional**
- Add, edit and delete comments on any item (post, video, product); reply to comments.
- List top-level comments sorted by newest or top; expand replies.
- React (like) to comments; show counts.
- Report comments; moderators hide or remove them.
- See new comments appear live on open pages.

**Non-functional**
- Read-heavy: ~100 reads per write. Lists p95 < 200 ms.
- Viral items: 1,000 comments/s on one item.
- Counts may lag by a few seconds; a user always sees their own new comment immediately.

## 2. Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Generic target | Comments belong to a `(target_type, target_id)` | One service for posts, videos and products |
| Thread shape | Two levels in the API: top-level comments, and a flat list of replies per comment (with `reply_to` for display) | Deep nesting is hard to paginate and to read on phones |
| Pagination | Cursors, per sort order (`newest`: `(created_at, id)`; `top`: `(score, id)`) | Live lists shift constantly; offsets would duplicate and skip (simulation below) |
| Counts | Precomputed counters, updated asynchronously (sharded counters for hot items, lesson 12.8) | `COUNT(*)` on 400,000 rows per page view doesn't scale |
| Live updates | SSE or WebSocket "new comments since X" notifications; the client fetches with a cursor | Push a small signal, not the whole list |
| Moderation | Every comment has a `status`; automated checks run async; hidden comments disappear for others but stay visible to their author | Keep the write path fast while still filtering |

## 3. The API

```
GET  /v1/comments?target=post:p_123&sort=top&limit=20&cursor=…
→ 200 {"comments": [{"id": "cmt_1", "author": {...}, "text": "…", "created_at": "…",
                     "reaction_counts": {"like": 1532}, "reply_count": 48, "viewer_reacted": true,
                     "replies_preview": [ …first 2 replies… ]}],
       "next_cursor": "…", "total_count": 412873}

GET  /v1/comments/cmt_1/replies?limit=20&cursor=…      → 200 (oldest first)
POST /v1/comments {"target": "post:p_123", "text": "…", "reply_to": "cmt_1"}   Idempotency-Key: …
→ 201 {"id": "cmt_9", "status": "published"}            (or "pending_review")
PATCH  /v1/comments/cmt_9 {"text": "…"}                 If-Match: "v1"  → 200 (marks as edited)
DELETE /v1/comments/cmt_9                                → 204 (soft delete: "[deleted]" if it has replies)
PUT    /v1/comments/cmt_9/reactions/like                 → 204   (idempotent: set, not toggle)
DELETE /v1/comments/cmt_9/reactions/like                 → 204
POST   /v1/comments/cmt_9/reports {"reason": "spam"}     → 202
GET    /v1/comments/stream?target=post:p_123             → SSE: event: new_comments {"since_cursor": "…", "count": 12}
```

Note `PUT` for reactions: "set my like" is idempotent, so double taps and retries are harmless; a toggle endpoint
would undo the like on a retry.

## 4. Cross-cutting

- **Auth:** reading may be public; writing needs a signed-in user; editing and deleting need ownership (or a moderator
  role).
- **Limits:** per-user write limits (e.g. 10 comments/minute), stricter for new accounts; duplicate-text detection.
- **Validation:** length limits (e.g. 2,000 characters), strip or escape HTML, normalise Unicode, check links.
- **Caching:** the first page of a popular item's "top" list can be cached for a few seconds at the edge (anonymous
  viewers); `viewer_reacted` fields come from a separate small per-user call or are merged in a BFF.

## 5. Evaluation

- Reads: the first page for a hot item is one index range read plus a cache of counts: ~10-20 ms of processing.
- Writes on a viral item: 1,000/s into one partition is fine for the comment store (partitioned by target), but the
  **count** is a hot key, which is why counters are sharded and aggregated.
- Read-your-writes: return the created comment in the `POST` response and have the client insert it locally, so the
  author sees it even if a replica lags.

## Try it

Use the pagination simulation: page through a fast-moving "newest" list with offsets, then with a cursor. Why do
offsets hurt comments in particular?

<details>
<summary>Answer</summary>

New comments arrive at the top of "newest" while someone scrolls, pushing older ones down, so with offsets the next
page repeats comments; deletions (moderation) pull comments up past the reader, who never sees them. Deep pages also
get slower. A cursor on `(created_at, id)` is stable and constant-cost.
</details>

## Key takeaways

- Attach comments to a generic target; keep the API to two levels of threading.
- Cursor pagination per sort order; precomputed (sharded) counters; idempotent `PUT` reactions.
- Push "new comments" signals, not data; let the client fetch with its cursor.
- Moderation status on every comment, async checks, and per-user write limits.

# Design a price tracker API

Price trackers like CamelCamelCamel and Keepa show the price history of millions of Amazon products and email you when a
price drops below your target. Their interesting problem isn't their own API, which is fairly simple. It's that their
whole product depends on **someone else's API**: its quotas, its outages and its migrations. This lesson designs both
sides: the tracker's API for its users, and how it consumes the retailer's.

## 1. Requirements

**Functional**
- Look up a product (by URL or id) and see its price history chart.
- Create price alerts ("tell me when this is under ₹2,000"); manage them.
- Get notified by email or push when an alert triggers.
- Browse popular price drops.

**Non-functional**
- Tens of millions of tracked products; popular ones checked every few minutes, the long tail daily.
- Stay within the upstream API's quota and terms; survive its outages.
- Alerts fire within minutes of a price change for popular products.

## 2. The upstream problem

| Upstream constraint | Design response |
|---------------------|-----------------|
| **Quota** (requests per second and per day, often tied to the account's sales) | A scheduler that spends the budget where it matters: popularity, volatility and number of alerts decide how often each product is checked |
| **Batch endpoints** (e.g. up to 10 items per call) | Group checks into batches |
| **Throttling** (`429`) and outages | Back off with jitter, honour `Retry-After`, pause the scheduler, show "last checked" times |
| **Data terms** (what may be stored and shown, for how long) | Store only what's permitted; refresh within the allowed time |
| **API migrations** | Amazon's Product Advertising API 5.0 is being replaced by the Creators API (with OAuth 2.0 auth) in 2026. An **adapter layer** isolates the integration so you can switch without touching the rest |
| **Unexpected data** (missing prices, new formats) | Validate every response (OWASP API10); quarantine odd values instead of alerting on them |

```
scheduler ─▶ check queue ─▶ fetch workers ─▶ upstream adapter ─▶ retailer API
                                  │
                                  └▶ price points (time-series store) ─▶ alert evaluator ─▶ notification queue ─▶ email/push
```

## 3. The tracker's own API

```
GET  /v1/products/lookup?url=https://www.amazon.in/dp/B0C…    → 200 {"id": "prd_B0C…", "title", "current_price", "last_checked"}
GET  /v1/products/prd_B0C…/prices?from=2026-01-01&resolution=day
→ 200 {"series": [{"t": "2026-01-01", "min": 199900, "max": 214900, "close": 209900}, …], "currency": "INR"}
     Cache-Control: public, max-age=300

POST /v1/alerts  Idempotency-Key: …  {"product": "prd_B0C…", "target_price": 200000, "channel": "email"}  → 201
GET  /v1/alerts?cursor=…                                          → 200
PATCH /v1/alerts/alr_5 {"target_price": 190000}                  → 200
DELETE /v1/alerts/alr_5                                          → 204
GET  /v1/deals?category=electronics&min_drop_pct=20&cursor=…      → 200 (cached at the edge)
```

Price history is downsampled by resolution (day, week) so a 10-year chart is a few hundred points, not millions.

## 4. Cross-cutting

- **Limits:** per-user alert caps (alerts drive upstream checks, which cost quota); rate limits on lookups (each new
  product costs an upstream call).
- **Caching:** product pages and charts are public and cache well; "last checked" tells users how fresh they are.
- **Notifications:** deduplicate (one email per alert per drop), respect quiet hours, include unsubscribe links.
- **Abuse:** scrapers want your price history; rate-limit and paginate, and watch for bulk access patterns.

## 5. Evaluation

- **Quota math:** with, say, 1,500 upstream calls/s of 10 items each, you can do 15,000 product checks/s ≈ 1.3 billion
  a day. Split it: the top 1% of products every 5 minutes, alerted products hourly, the rest daily.
- **Alert latency:** a price change is seen at the next check (minutes for popular products), evaluated against alerts
  indexed by product (one lookup), and queued for notification.
- **Upstream outage:** checks stop, the backlog is discarded rather than replayed (old prices are worthless), and the UI
  shows staleness. [The price tracker sandbox](#/sandbox?preset=api-price-tracker) has the check workers falling behind.

## Try it

The upstream API announces it will shut down in six months and the replacement uses different authentication, field
names and quotas. Plan the migration.

<details>
<summary>Answer</summary>

Because all upstream access goes through one adapter with an internal model (`ProductOffer {asin, price, currency,
availability, fetched_at}`), you write a second adapter for the new API, run both in parallel for a sample of products and
compare results, then shift traffic gradually (per category or by percentage) while watching error rates and quota use.
Update the scheduler's budget for the new quota rules. Keep the old adapter as a fallback until the sunset date, then
delete it. Nothing outside the adapter changes.
</details>

## Key takeaways

- When your product depends on another company's API, its quota, outages and migrations are your design constraints.
- Schedule upstream calls by value; batch, back off, validate responses and show staleness.
- Isolate the integration behind an adapter so you can switch versions or providers.
- Your own API can be simple: lookups, downsampled history, idempotent alerts, cached deals.

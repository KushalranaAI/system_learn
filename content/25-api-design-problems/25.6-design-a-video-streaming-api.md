# Design a video streaming API

On a video platform like YouTube, the API carries almost none of the video. Creators upload through resumable upload
sessions; a processing pipeline turns each upload into dozens of renditions; viewers' players fetch a small
**manifest** from the API and then pull video segments from a CDN, switching quality every few seconds as their
network changes. The API's job is to orchestrate, authorise and describe; the bytes go elsewhere. (Lesson 30.8 looks at
YouTube's architecture.)

## 1. Requirements

**Functional**
- Upload videos (often 1-20 GB) from phones and desktops; see processing progress.
- Set metadata (title, description, visibility, thumbnails); publish.
- Play videos on any device, with quality adapting to the network; resume where you left off.
- Count views; like and comment (lesson 25.4).

**Non-functional**
- Playback starts in < 2 s and rarely stalls; uploads survive dropped connections.
- Hundreds of thousands of concurrent viewers per popular video; global audience.
- Private and unlisted videos must not leak through guessable URLs.

## 2. How streaming works

```
upload ─▶ object storage ─▶ transcode into a ladder ─▶ package as segments ─▶ CDN
                          240p  360p  480p  720p  1080p  4K   (H.264 / VP9 / AV1, several bitrates)

player: GET manifest (HLS .m3u8 or DASH .mpd) ─▶ lists renditions and segment URLs
        GET segment 1 (2-6 s of video) at a quality the bandwidth allows ─▶ measure ─▶ adjust ─▶ GET segment 2 …
```

**Adaptive bitrate (ABR)**: the player picks each next segment's quality from its measured throughput and buffer
level. **HLS** (Apple) and **MPEG-DASH** are the two standard formats; CMAF lets one set of segments serve both.

## 3. The API

```
Creator side
POST /v1/uploads {"size", "type", "name"}             → 201 resumable session (lesson 25.3)
POST /v1/videos {"upload_id", "title", "visibility": "private"}   Idempotency-Key  → 201 {"id": "vid_3Jq", "status": "processing"}
GET  /v1/videos/vid_3Jq                               → 200 {"status": "processing", "progress": 0.6,
                                                              "renditions_ready": ["360p", "720p"]}
PATCH /v1/videos/vid_3Jq {"title", "description", "visibility": "public", "publish_at": "…"}  → 200
webhook / push: video.processing_completed, video.processing_failed

Viewer side
GET /v1/videos/vid_3Jq/playback?device=android&codecs=av1,h264
→ 200 {"manifest_url": "https://cdn…/vid_3Jq/master.m3u8?token=…&exp=…",
       "resume_position_s": 734, "captions": [...], "ads": {...}}
GET <manifest and segments from the CDN>               (signed, cacheable, Range-friendly)
POST /v1/videos/vid_3Jq/watch-events {"position_s": 760, "event": "heartbeat", "session": "ws_…"}  → 202
```

## 4. Decisions worth defending

| Decision | Why |
|----------|-----|
| Playback goes through `GET /playback`, not a fixed URL | The API checks visibility, region rights and age gates, then issues a **short-lived signed** manifest URL |
| Segments are public-cacheable but URL-signed | CDN hit ratios stay high; tokens expire so links can't be shared forever (DRM for premium content) |
| Processing status is a resource plus events | Transcoding takes minutes; clients poll cheaply or get a push |
| Watch events are fire-and-forget batches (`202`) | Millions of heartbeats a second go to a queue/stream, not a database |
| View counts are approximate and delayed | Counted in a stream processor with fraud filtering, then shown (lesson 26.4 on counting at scale) |
| Codec negotiation in the playback call | Newer codecs (AV1) save bandwidth on devices that support them |

## 5. Evaluation

- **Startup time:** `GET /playback` (~100 ms) + manifest from the CDN (~30 ms) + first segment at low quality (~200-500
  ms on mobile). Starting at a low rung and stepping up keeps startup fast.
- **Scale:** API calls per view are a handful; segment requests are thousands per view, nearly all served by the CDN.
- **Uploads:** resumable chunks; the simulation in lesson 25.3 shows why.
- **Failure modes:** CDN region issues → players fail over to another CDN host listed in the manifest; transcoding
  backlog → videos stay "processing" longer, which is acceptable; watch-event pipeline lag → counts update late, but
  playback is unaffected.

## Try it

Design what happens when a creator switches a public video to private while 50,000 people are watching it.

<details>
<summary>Answer</summary>

The `PATCH` updates visibility and emits `video.visibility_changed`. New `GET /playback` calls get `403`/`404`. Existing
viewers hold signed manifest URLs that remain valid until expiry, so keep signatures short (minutes) and have players
refresh tokens through the API, which now refuses. The CDN is told to purge or the origin refuses new segment requests
for that video. Within a few minutes, playback stops everywhere without breaking the CDN's caching for every other video.
</details>

## Key takeaways

- The API orchestrates and authorises; the CDN serves the bytes.
- Uploads are resumable sessions; processing is asynchronous with status resources and events.
- Players use HLS/DASH manifests and adaptive bitrate; the API issues short-lived signed manifest URLs.
- Watch events and view counts go through a stream, not the request path.

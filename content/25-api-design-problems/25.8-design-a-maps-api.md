# Design a maps API

A maps platform like Google Maps Platform is really a family of APIs with very different shapes: **tiles** that are
the same for everyone and cache forever, **search and geocoding** that turn text into places, and **routing** that
computes a fresh answer for every request using live traffic. Each one has its own caching, pricing and latency story.

## 1. Requirements

**Functional**
- Render a map at any zoom level (raster or vector tiles).
- Geocode ("221B Baker Street" → coordinates) and reverse geocode.
- Search places ("coffee near me") with autocomplete.
- Directions between points by car, foot or transit, with ETAs based on live traffic.

**Non-functional**
- Tiles load in < 100 ms; autocomplete < 100 ms; directions < 500 ms.
- Hundreds of thousands of tile requests per second; billed per call to API customers.
- API keys embedded in public apps must not be abusable by others.

## 2. Decisions

| API | Shape | Caching |
|-----|-------|---------|
| **Tiles** | `GET /tiles/v42/{z}/{x}/{y}.mvt` (vector) or `.png`; immutable for a style version | CDN + client cache, `immutable`; new style = new version in the URL |
| **Geocoding** | `GET /geocode?address=…` / `?latlng=…` | Popular addresses cache well; respect the provider's terms on storing results |
| **Places** | `GET /places:autocomplete?input=caf&location=…&session=…` then `GET /places/:id?fields=…` | Short-lived; **session tokens** group autocomplete keystrokes with the final selection for billing |
| **Directions / ETA** | `POST /routes:compute {origin, destination, mode, departure_time}` | Hardly cacheable (traffic changes); computed per request |

**Field masks** (`fields=displayName,location,rating`) let clients pay only for the data they use: Google's Places API
bills by the fields requested.

## 3. Tile addressing

The world is projected onto a square (Web Mercator) and split into a quadtree: zoom 0 is one tile; each zoom level
splits every tile into four. At zoom `z` there are `2^z × 2^z` tiles; a 256-pixel tile at zoom 15 covers roughly a city
block.

```
z=0: 1 tile        z=1: 4 tiles       …      z=15: 1.07 billion tiles
{z}/{x}/{y}  ─ every tile has a stable address, so the same tile is one cache entry for every user on Earth
```

Vector tiles (Mapbox Vector Tile format, Protobuf-encoded) send geometry and let the device render styles, labels and
rotation; one tile set serves many styles.

## 4. Cross-cutting

- **API keys in public apps:** restrict each key by referrer (web), app signature (Android/iOS) and allowed APIs; set
  per-key quotas and budget alerts.
- **Billing:** per SKU (per type of call); since March 2025 Google Maps Platform gives a free monthly allowance per
  SKU (for example 10,000 for many "Essentials" SKUs, more for map tiles). Clients reduce cost by caching tiles,
  debouncing autocomplete and using session tokens.
- **Rate limits:** per key per second plus daily quotas; `429` with `Retry-After`.
- **Licensing:** map data has terms; the API controls what may be cached and for how long.

## 5. Evaluation

| Call | Budget | Where the time goes |
|------|--------|---------------------|
| Tile (CDN hit) | < 50 ms | Edge round trip; >95% hit ratio |
| Tile (miss) | < 200 ms | Render or fetch from the tile store, then cached |
| Autocomplete | < 100 ms | Prefix index per region, ~10 ms; mostly network; client debounce |
| Directions | < 500 ms | Routing on a preprocessed road graph (contraction hierarchies or similar) with live traffic weights: tens to hundreds of ms |

## Try it

Why do tile URLs include a version (`/v42/tiles/12/2154/1428`), and how would you roll out a new map style without
melting the tile servers?

<details>
<summary>Answer</summary>

A versioned URL lets tiles be cached as `immutable` for a year; a new style or data release changes the version, so
no purge is needed and old clients keep working. To roll out: pre-render (or pre-warm the CDN with) the most popular
tiles for the new version, ship the style to a small percentage of clients first, and keep the old version cached so
you can roll back instantly. Otherwise every client asks for uncached tiles at once and the hit ratio collapses.
</details>

## Key takeaways

- Maps is several APIs: immutable tiles, search and geocoding, and per-request routing.
- Address tiles by `{z}/{x}/{y}` and a version so they cache forever at the edge.
- Use field masks and session tokens to keep places calls cheap; restrict public API keys.
- Budget each API separately: tiles are about cache hits, routing about compute.

# Design a video conferencing API

In a video call, a delay of 300 ms already makes people talk over each other, and a frozen frame is worse than a blurry
one. That rules out most of what web APIs usually do: no retries, no queues, no TCP for the media. A conferencing
platform like Zoom therefore has two very different planes: a **control plane** (normal APIs to create meetings, join,
manage participants) and a **media plane** (real-time audio and video over UDP).

## 1. Requirements

**Functional**
- Schedule and start meetings; join by link with an optional waiting room and passcode.
- Audio, video and screen sharing for up to ~1,000 participants (more as view-only webinars).
- Mute, remove, promote to host; chat; recording.
- Integrations: create meetings from calendars, webhooks when meetings start or recordings are ready.

**Non-functional**
- Mouth-to-ear latency < 200-300 ms; join in < 3 s.
- Graceful degradation on bad networks (lower resolution, audio first).
- Media encrypted in transit; optional end-to-end encryption.

## 2. Media: how the bytes flow

| Topology | How | Fits |
|----------|-----|------|
| **Peer-to-peer (mesh)** | Every participant sends to every other | 2-3 people |
| **MCU** (multipoint control unit) | Server decodes everyone, mixes one composite stream per participant | Old systems; heavy server CPU |
| **SFU** (selective forwarding unit) | Server forwards streams without decoding; each sender sends a few qualities (**simulcast**), the SFU picks per receiver | Modern standard (Zoom, Meet, Teams, LiveKit) |

Media runs over **RTP/SRTP on UDP** (WebRTC in browsers), with ICE/STUN/TURN to get through NATs and firewalls. Lost
packets are concealed or recovered with forward error correction, not retransmitted.

## 3. The control-plane API

```
POST /v1/meetings {"topic", "start_time", "duration_min", "settings": {"waiting_room": true, "passcode": "…"}}
→ 201 {"id": "mtg_4H2", "join_url": "https://meet.example/j/4H2…", "host_key": "…"}

POST /v1/meetings/mtg_4H2/join {"display_name": "Asha", "passcode": "…", "device": {...}}
→ 200 {"participant_id": "prt_17", "status": "admitted" | "waiting",
       "signaling_url": "wss://sig-mum-3.meet.example/v1", "token": "<short-lived JWT for this meeting>",
       "ice_servers": [{"urls": "turns:turn-mum.meet.example:443", "username": "…", "credential": "…"}],
       "media_region": "ap-south-1"}

WebSocket (signalling):  offers/answers (SDP), ICE candidates, "who's speaking", mute state, layout, chat,
                         "host admitted you", "you were removed"
PATCH /v1/meetings/mtg_4H2/participants/prt_17 {"audio": "muted"}       → 200  (host action)
DELETE /v1/meetings/mtg_4H2/participants/prt_17                         → 204
POST /v1/meetings/mtg_4H2/recordings:start                              → 202
Webhooks: meeting.started, participant.joined, recording.completed (with a signed download URL)
```

## 4. Decisions worth defending

| Decision | Why |
|----------|-----|
| A join call that returns a **meeting-scoped, short-lived token** and a signalling server | The SFU and signalling servers verify tokens locally; no per-packet auth lookups |
| Pick the media region nearest the participants (or cascade SFUs across regions) | Round trips dominate media latency |
| Signalling over WebSocket, media over UDP with TURN-over-TLS on 443 as a fallback | Works through strict corporate firewalls at some latency cost |
| Simulcast + per-receiver selection | Each viewer gets a quality their network can handle, without re-encoding |
| Recording and transcription as async jobs with webhooks | They take minutes; integrations want to be told |
| Host actions are REST calls *and* signalling events | Integrations and the host's client can both manage the meeting |

## 5. Evaluation

- **Join:** `POST /join` (~150 ms) + WebSocket connect (~1-2 RTT) + ICE and DTLS setup (~2-3 RTT) + first media: ~1-2 s.
- **In-call latency:** capture and encode (~20-40 ms) + network to the SFU and on to receivers (~2 × one-way) +
  jitter buffer (~30-80 ms) + decode and render: under 200 ms in-region.
- **Scale:** a 1,000-person meeting is mostly the SFU choosing which few video streams each receiver gets (active
  speaker plus a page of thumbnails); audio is mixed or forwarded only for the loudest few.
- **Failures:** an SFU dies → clients reconnect to another via signalling within seconds; packet loss → lower simulcast
  layer, then audio only.

## Try it

Design the waiting room: a participant joins, the host admits them. What does each side see, and which API calls and
events are involved?

<details>
<summary>Answer</summary>

`POST /join` returns `status: "waiting"` with a token that only allows the signalling connection, not media. The host's
signalling channel receives `participant.waiting {prt_17, name}`. The host calls `POST
/meetings/mtg_4H2/participants/prt_17:admit` (or sends the signalling equivalent). The server upgrades the participant's
permissions and sends them `admitted` with a refreshed token that the SFU accepts; their client starts ICE and media.
A `participant.joined` webhook fires for integrations.
</details>

## Key takeaways

- Separate the control plane (REST + WebSocket signalling) from the media plane (RTP over UDP via WebRTC).
- SFUs with simulcast are the standard way to scale multi-party calls.
- Join returns a short-lived meeting token, a signalling URL and TURN servers in the nearest region.
- Recording, transcription and integrations are asynchronous, with webhooks.

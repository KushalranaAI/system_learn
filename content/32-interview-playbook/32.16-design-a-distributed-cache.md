# Design a distributed cache

"Design Memcached/Redis Cluster" asks you to build infrastructure rather than a product. The interviewer wants
partitioning that survives nodes coming and going, a replication choice with honest tradeoffs, eviction that fits the
workload, and a plan for the one key everybody wants.

## Clarifying questions

- Pure cache (data can be lost and refetched) or a primary store? (A cache; the database is the source of truth.)
- Data size and traffic? (10 TB of hot data, 5M ops/s, 90% reads.)
- Value sizes? (Mostly < 10 KB; a few up to 1 MB.)
- Latency? (p99 < 2 ms within a region.)
- Data types? (Strings with TTL; maybe counters.)
- Multi-region? (One region per cluster; each region has its own.)

## Requirements

**Functional**
1. `get`, `set` with TTL, `delete`, and atomic `incr`.
2. Add and remove nodes without downtime.
3. Evict when full.

**Non-functional**
- p99 < 2 ms; 5M ops/s total.
- Losing a node loses at most a small fraction of the cache, and only briefly.
- No single node or key can take the cluster down.

## Estimates

```
memory:   10 TB data + ~30% overhead (keys, metadata, fragmentation) ≈ 13 TB
nodes:    usable 64 GB per node (on 96-128 GB machines) → 13 TB / 64 GB ≈ 200 primaries
replicas: 1 replica each → ~400 nodes
ops:      5M ops/s / 200 primaries = 25k ops/s per primary (comfortable; a node does ~100k+)
network:  5M × ~2 KB average value = 10 GB/s cluster-wide ≈ 50 MB/s per node (fine on 10-25 Gbit NICs)
loss:     one node = 1/200 = 0.5% of keys → 0.5% of traffic falls through to the DB until refilled
```

Memory, not CPU, decides the node count.

## API

```
GET k → value | miss       SET k v [TTL]       DEL k       INCR k [by]
MGET k1 k2 ...             (batch, routed to several nodes and merged by the client)
admin: add_node, remove_node, cluster_map
```

## Data model

On each node: a hash table of key → (value, expiry, LRU metadata), memory split into size-class slabs (Memcached) or a
general allocator (Redis). Cluster-wide: a **map of slots → nodes**, versioned, held by a config service and cached in
every client.

## High-level design

```
app + cache client (knows slot map) ──→ node 17 (primary for slots 5,000-5,200) ──async──→ node 17' (replica)
       │                                  ...
       └─ on MOVED/stale map → refresh from config service (Raft/etcd-backed)
health:  gossip or config service detects failure → promotes replica → bumps map version
```

Routing options: **smart client** (one hop, used by Redis Cluster), a **proxy tier** (Twemproxy/mcrouter-style:
simpler clients, one more hop), or server-side redirection (`MOVED`).

## Deep dive 1: partitioning

- `hash(key) mod N` moves almost every key when N changes: a cluster-wide cache miss.
- **Consistent hashing** with virtual nodes ([lesson 14.2](#/lesson/14.2), [lesson 26.1](#/lesson/26.1)): adding a
  node moves ~1/N of keys.
- **Fixed slots** (Redis Cluster uses 16,384): `slot = CRC16(key) mod 16384`; nodes own slot ranges. Rebalancing moves
  whole slots, and the map is small enough to ship to every client.
- Hash tags (`{user:42}:profile`) keep related keys in one slot when multi-key operations need it.

## Deep dive 2: replication and failure

- **Async replication** to one replica: writes stay fast; a failover may lose the last few writes. For a cache that is
  acceptable (the DB has the truth).
- Failure detection by heartbeats / gossip ([lesson 26.6](#/lesson/26.6)) with a quorum of observers, so one flaky
  link can't trigger a failover. Promote the replica, bump the map version.
- **Cold node:** a replacement starts empty; warm it from the replica or let traffic refill it, protecting the DB with
  request coalescing ([lesson 3.6](#/lesson/3.6)).
- **Split brain:** a primary that loses contact with the majority stops accepting writes after a timeout.

## Deep dive 3: eviction and hot keys

- **Eviction** ([lesson 3.4](#/lesson/3.4)): approximate LRU (sample 5-10 keys, evict the oldest) is cheap and close to
  true LRU; LFU is better when a scan of one-off keys would flush the working set. Expired keys are removed lazily on
  access plus a background sampler.
- **Hot keys:** one key at 500k reads/s overloads one node.
  - Detect with per-node top-k counters ([count-min sketch](#/lesson/26.3)).
  - **Client-side local cache** for a short TTL (1-5 s) absorbs most of it.
  - **Replicate the hot key** to several nodes (`key#1..key#8`) and read a random copy.
  - Read from replicas for hot read-only keys.
- **Big values:** split > 1 MB values or keep them out of the cache; they block a single-threaded node.

## Bottlenecks and failure modes

- **Thundering herd** after a node loss or a mass expiry: jittered TTLs and coalescing.
- **Stale slot maps:** clients get `MOVED` and refresh; map versioning prevents flapping.
- **Rebalancing traffic:** migrate slots gradually with rate limits so it doesn't hurt p99.
- **Network partition:** minority side refuses writes; clients fall back to the DB (with a limit so it survives).

## What interviewers listen for

- Memory-driven node math, with replicas.
- Consistent hashing or fixed slots, and why not `mod N`.
- Async replication with the "may lose recent writes, it's a cache" tradeoff stated.
- Concrete hot-key mitigations and stampede protection.

## Common mistakes

- `hash mod N` partitioning.
- Treating the cache as durable storage.
- Synchronous replication across many replicas, then wondering why p99 rose.
- No plan for what happens to the database when 0.5% (or 100%) of the cache disappears.

## Try it

**Build a 10 TB cache cluster.** On paper: how many nodes, how are keys placed, what happens when one node dies, and
what happens when a single key gets 500k reads/s? Then compare with the [key-value store lab](#/labs/key-value-store),
which partitions and replicates the same way.

## Key takeaways

- Size by memory: data + overhead ÷ usable RAM per node, then add replicas.
- Fixed slots or consistent hashing keep rebalancing to ~1/N of keys.
- Async replication is right for a cache; plan for brief loss and cold nodes.
- Approximate LRU/LFU for eviction; local caches and key replication for hot keys.

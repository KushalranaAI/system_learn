# Design a video platform

"Design YouTube" or "Design Netflix" is mostly about bytes: getting big uploads in, turning them into many formats, and
serving terabits per second to viewers without your origin servers ever seeing most of that traffic.

## Clarifying questions

- User uploads (YouTube) or a curated catalogue (Netflix)? (User uploads.)
- Live streaming? (Out of scope; video on demand only.)
- Scale? (1M concurrent viewers at peak, 100k uploads a day.)
- Devices? (Web, phones, TVs, so many resolutions and codecs.)
- Recommendations: design them or just mention them? (A short sketch.)

## Requirements

**Functional**
1. Upload a video (resumable); see processing status.
2. Watch with adaptive quality (switches with network speed).
3. Video page with metadata, view counts; home page with recommendations.

**Non-functional**
- Playback starts in < 2 s; rebuffering rare.
- Uploads never lost; processed within minutes for typical videos.
- Massive read bandwidth at sensible cost; high availability for playback.

## Estimates

```
viewers:   1M concurrent × ~5 Mbit/s average bitrate        = 5 Tbit/s egress  → only a CDN can do this
uploads:   100k/day × 10 min average × ~50 MB/min source    = 50 TB/day of source video
renditions: ~6 resolutions × 2 codecs, together ≈ 1-1.5x the source size → ~60 TB/day more
storage:   ~110 TB/day ≈ 40 PB/year (before replication or erasure coding)
transcode: 100k × 10 min = 1M video-minutes/day; at ~1 CPU-min per output minute × 12 outputs
           ≈ 12M CPU-min/day ≈ 8,300 CPUs busy around the clock
metadata reads: 1M viewers start a video every ~5 min → ~3.3k/s video page loads (easy)
```

Egress and transcoding dominate cost. Metadata is ordinary.

## API

```
POST /uploads                     {title, size, content_type}   → {upload_id, chunk_urls[] (presigned)}
PUT  <presigned chunk URL>        (bytes straight to object storage)
POST /uploads/{id}/complete                                      → 202 {video_id}
GET  /videos/{id}                                                → {title, status, manifest_url, thumbnails}
GET  <CDN>/videos/{id}/master.m3u8 → per-rendition playlists → 4-6 s segments
GET  /feed/home?cursor=                                          → recommended video ids
```

## Data model

| Entity | Key | Store |
|--------|-----|-------|
| video | video_id → owner, title, status, durations, renditions | sharded SQL (YouTube used MySQL sharded with Vitess) |
| source and segments | `videos/{id}/{rendition}/{n}.ts` | object storage |
| views | (video_id) counter | sharded/approximate counters ([lesson 12.8](#/lesson/12.8)) |
| watch events | (user, video, ts) | Kafka → warehouse, for recommendations |

## High-level design

```
upload:  client ─chunks→ object store (presigned) → "uploaded" event → queue
                                                     ↓
         split into segments → transcode workers (parallel per segment × rendition) → object store
                                                     ↓
         assemble manifests, thumbnails, checks → mark video READY → notify uploader
watch:   client → API (metadata, manifest URL) ; player → CDN edge → (miss) regional cache → origin object store
```

## Deep dive 1: upload and transcoding pipeline

- **Resumable chunked uploads** direct to object storage with presigned URLs; API servers never touch the bytes.
- **Split, then parallelise:** cut the source at keyframes into ~10-second chunks. Each (chunk, rendition) is an
  independent job, so a 2-hour film finishes in minutes on many workers ([lesson 7.7](#/lesson/7.7)).
- **Ladder:** 240p to 4K at several bitrates; H.264 for compatibility plus a newer codec (VP9/AV1/HEVC) for bandwidth
  savings on popular videos. Transcode the expensive codecs only once a video gets views.
- **Orchestration:** a DAG per video (split → transcode → join → package → thumbnails → moderation) with retries and
  idempotent steps ([lesson 7.3](#/lesson/7.3)); a poison chunk goes to a dead-letter queue, not an infinite loop.

## Deep dive 2: delivery with adaptive bitrate

- **HLS/DASH:** the player downloads a manifest, then small segments, picking the rendition per segment from measured
  bandwidth. Switching quality needs no server logic.
- **CDN** ([lesson 3.7](#/lesson/3.7)): segments are immutable, so cache them for a long time. Popular videos hit
  >95% at the edge. Netflix goes further and places its own caches inside ISPs ([lesson 30.1](#/lesson/30.1)).
- **Long tail:** most videos are rarely watched; they live only at origin (or a regional tier) and cost little.
- **Pre-positioning:** push expected hits (a new episode) to edges before release.

## Deep dive 3: views and recommendations

- View counts: aggregate watch events in a stream job ([lesson 17.4](#/lesson/17.4)) and write per-minute increments;
  dedupe bots and replays before counting.
- Recommendations: candidate generation (similar videos, subscriptions, trending) → ranking model on features like
  watch time → top N, precomputed per user in batch and refreshed with recent watch events. Same shape as
  [the ranked feed](#/lesson/32.4).

## Bottlenecks and failure modes

- **Transcode backlog** after a spike in uploads: autoscale workers on queue depth ([lesson 7.6](#/lesson/7.6)); give
  short videos priority so most users wait less.
- **CDN miss storm** on a viral video: request coalescing at edges and a regional mid-tier shield the origin.
- **Origin outage:** cached content keeps playing; new uploads queue.
- **Metadata DB:** shard by video id; cache video pages heavily.

## What interviewers listen for

- Bandwidth math that makes the CDN obvious.
- Bytes bypass app servers (presigned uploads, CDN downloads).
- Parallel per-chunk transcoding with a DAG and retries.
- Adaptive bitrate streaming explained in a sentence.

## Common mistakes

- Uploading through API servers or serving video from them.
- Transcoding a whole video serially on one machine.
- Treating all videos the same (popular vs long tail need different storage and codecs).
- Spending the whole interview on recommendations.

<summary>Reference</summary>

1M viewers x 5 Mbit/s = 5 Tbit/s. With a 95% edge hit ratio the origin and regional tier still serve ~250 Gbit/s, so
add a mid-tier cache to cut origin to a few percent of that. Segments are immutable with long TTLs. Uploads go straight
to object storage; a queue feeds per-chunk transcode workers that autoscale on queue depth; the video is marked ready
only after manifests are written.

## Key takeaways

- Video is a bandwidth problem: CDN and adaptive bitrate do the heavy lifting.
- Keep bytes away from app servers: presigned uploads, CDN downloads.
- Transcode in parallel per chunk and rendition, orchestrated as a retryable DAG.
- Popular and long-tail videos deserve different treatment.

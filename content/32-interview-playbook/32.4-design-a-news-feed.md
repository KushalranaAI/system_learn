# Design a news feed

"Design the Facebook/Instagram/Twitter home feed" is asked everywhere because it has one famous hard part: getting each
post to millions of followers' feeds quickly, when some users have 100 followers and some have 100 million.

## Clarifying questions

- Text only, or photos and video too? (Posts with text and media; media served from a CDN.)
- Chronological or ranked? (Ranked, but start chronological.)
- Scale? (300M daily users, average 200 follows, a few accounts with 50M+ followers.)
- How fresh must the feed be? (A new post appears for followers within ~10 seconds.)
- Out of scope: ads, stories, comments, search.

## Requirements

**Functional**
1. Create a post.
2. Follow / unfollow users.
3. Read a home feed of posts from people you follow, newest or best first, with infinite scroll.

**Non-functional**
- Feed load p99 < 300 ms.
- New posts visible to followers within ~10 s (eventual consistency is fine).
- Posts are never lost; the feed itself is a rebuildable cache.
- Highly available: a stale feed beats an error page.

## Estimates

```
feed reads:  300M users × 10 opens/day        = 3B/day ≈ 35k/s average, ~100k/s peak
posts:       300M × 0.5 posts/day             = 150M/day ≈ 1.7k/s, ~5k/s peak
fan-out:     150M posts × 200 followers        = 30B feed inserts/day ≈ 350k/s
feed cache:  500 post ids × 8 B = 4 KB per user × 300M ≈ 1.2 TB (Redis, sharded)
posts store: 150M × 1 KB metadata              ≈ 150 GB/day ≈ 55 TB/year (media separately in object storage)
```

Reads are ~20x posts, but fan-out turns each post into ~200 writes. That tension is the whole problem.

## API

```
POST /posts                 {text, media_ids[]}           → 201 {post_id}
POST /users/{id}/follow                                   → 204
GET  /feed?cursor=&limit=20                               → {posts: [...], next_cursor}
```

Cursor pagination ([lesson 2.3](#/lesson/2.3)), because new posts arrive at the top while you scroll.

## Data model

| Entity | Key | Store |
|--------|-----|-------|
| post | post_id (time-ordered, [Snowflake](#/lesson/26.11)) | sharded by author_id (SQL or wide-column) |
| follow edge | (follower_id, followee_id), plus reverse index | sharded graph table, both directions |
| feed | user_id → list of (post_id, score), capped at ~500 | Redis lists/sorted sets |
| media | object key | object storage + CDN |

## High-level design

```
write: client → API → posts DB ─→ Kafka "post_created" → fan-out workers
                                                         ├─ look up followers (graph store)
                                                         └─ push post_id into each follower's feed (Redis)
read:  client → API → feed service → Redis feed (ids) → hydrate posts + authors (cache → DB) → rank → response
                                   └─ merge recent posts from followed celebrities (pull)
```

## Deep dive 1: fan-out on write vs on read

| | Fan-out on write (push) | Fan-out on read (pull) |
|-|------------------------|------------------------|
| Post | write post id to every follower's feed | write once |
| Read | read one precomputed list | query every followee, merge, sort |
| Good for | fast reads, normal users | users with huge follower counts; inactive readers |
| Bad for | a 50M-follower post = 50M writes | 200 followees per read x 100k reads/s = 20M lookups/s |

**Hybrid** is the expected answer ([lesson 15.5](#/lesson/15.5), [Twitter's timelines](#/lesson/30.7)): push for normal
authors; for authors above a threshold (say 100k followers), don't fan out. At read time, merge the user's precomputed
feed with the latest posts of the few celebrities they follow (cached per celebrity). Also skip pushing to users who
haven't logged in for 30 days; build their feed on demand when they return.

## Deep dive 2: ranking

Chronological is a sorted merge. Ranking is a pipeline:

1. **Candidates:** ~500 recent post ids from the feed cache plus celebrity posts.
2. **Features:** author affinity, post age, engagement so far, media type (from a feature store).
3. **Score** with a model; take the top 20; apply diversity rules (not five posts from one author in a row).
4. **Cache the ranked page** briefly so scrolling is stable; the cursor points into that ranked list.

Keep ranking within the latency budget: ~50 ms for scoring 500 candidates. If the ranker is slow or down, fall back
to chronological. The [ranked feed lab](#/labs/ranked-feed) builds this pipeline.

## Deep dive 3: hydration and hot posts

Feeds store ids, not posts, so edits and deletes need no rewrite of millions of lists. Hydration fetches 20 posts and
their authors from a post cache; a celebrity's new post is read by millions at once, so it's a hot key
([lesson 3.6](#/lesson/3.6)): replicate it across cache shards or keep it in a local cache. Like counts use sharded or
approximate counters ([lesson 12.8](#/lesson/12.8)).

## Bottlenecks and failure modes

- **Fan-out backlog:** 350k inserts/s average with spikes; Kafka absorbs bursts and workers scale on lag
  ([lesson 15.3](#/lesson/15.3)). Followers see posts late, not never.
- **Feed cache loss:** rebuild lazily from the follow graph + posts (slow first load) rather than all at once.
- **Unfollow and delete:** filter at read time (check the post still exists and the follow is current) instead of
  scrubbing every list.
- **Graph store hotspots:** a celebrity's follower list is huge; page through it in fan-out workers.

## What interviewers listen for

- The fan-out tradeoff, with numbers, and the celebrity problem raised by you.
- Feeds hold ids; posts are hydrated, so the feed is a rebuildable cache.
- Async fan-out through a queue, with lag as the main metric.
- A ranking pipeline sketch with a fallback.

## Common mistakes

- Pure fan-out on write with no celebrity handling.
- Pure fan-out on read with a giant SQL `JOIN ... ORDER BY created_at` across shards at 100k/s.
- Offset pagination on a feed that changes underneath you (duplicates and gaps).
- Storing full post bodies in every feed list.

## Key takeaways

- Fan-out on write for normal users, on read for celebrities: the hybrid is the standard answer.
- Store post ids in feeds, hydrate at read time, and treat feeds as rebuildable caches.
- Fan out asynchronously through a log; watch consumer lag.
- Ranking is candidates → features → score → top-k, with a chronological fallback.

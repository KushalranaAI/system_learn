# Design metrics and monitoring

"Design Datadog / Prometheus" is a write-heavy time-series problem with a twist: the system that tells you everything
else is broken must itself keep working, and it must page someone within seconds. The interviewer listens for
compression, cardinality and an alerting path that doesn't depend on the slow parts.

## Clarifying questions

- Metrics only, or logs and traces too? (Metrics only.)
- Push (agents send) or pull (server scrapes)? (Either; let's decide.)
- How many series, how often? (1M active series, every 10 s.)
- Retention? (Raw 15 days, downsampled 1 year.)
- Alerting latency? (Alert within 30 s of a condition becoming true.)

## Requirements

**Functional**
1. Ingest samples: `(metric name, labels, timestamp, value)`.
2. Query and graph: sums, rates, percentiles over time ranges, grouped by labels.
3. Alert rules (e.g. `error_rate > 5% for 1m`) that notify on-call.
4. Retention and downsampling.

**Non-functional**
- Alert within 30 s; dashboards over the last hour load in < 1 s.
- Ingestion never blocks the monitored services.
- Monitoring must keep working when the systems it watches are failing.
- Tolerant of a few lost samples; not tolerant of missing an alert.

## Estimates

```
samples:   1M series / 10 s                   = 100k samples/s
per day:   100k × 86,400                      = 8.64B samples/day
storage:   ~1.37 B/sample with Gorilla-style compression → ≈ 12 GB/day raw
           (vs 16 B uncompressed = 138 GB/day); 15 days ≈ 180 GB
downsampled: 5-min rollups (min/max/sum/count) → ~1/30th of the points → small for a year
memory:    head block of last ~2 h in memory: 1M series × 720 samples × ~1.4 B ≈ 1 GB + index
queries:   a dashboard of 20 panels × 100 series × 360 points = 720k points: must come from memory or compressed blocks
```

One well-sized node could hold this; we'll still shard for growth and replicate for availability.

## API

```
ingest:  POST /api/v1/write   [ {name, labels{}, samples:[(ts, v)]} ]     (or scrape GET /metrics on targets)
query:   GET /api/v1/query_range?q=rate(http_errors_total[1m])&start&end&step
rules:   PUT /rules/{id}  {expr, for: "1m", severity, route}
alerts:  → alert manager → dedupe/group/silence → PagerDuty, Slack, email
```

## Data model

| Data | Key | Store |
|------|-----|-------|
| series | series_id = hash(name + sorted labels) | inverted index: label=value → series ids |
| samples | (series_id, time block) | compressed chunks: delta-of-delta timestamps, XOR'd floats |
| blocks | 2 h blocks → compacted to larger ones | local disk, then object storage for long-term |
| rollups | (series_id, 5 min) | min/max/sum/count |
| alert state | rule × label set | pending/firing, since |

## High-level design

```
services/agents → ingest gateways (validate, cardinality limits) → Kafka (buffer, partitioned by series hash)
                                                        ↓
                        TSDB shards (in-memory head + WAL → compressed blocks → object storage)
                                                        ↓
              query service (fan out to shards, merge) ← dashboards
alerting:  rule evaluators read recent data from the head (or the stream) every 10-15 s → alert manager → pager
meta-monitoring: a separate, small stack (different failure domain) watches the monitoring system
```

## Deep dive 1: storage and compression

- Samples arrive in time order per series, so storage is append-only by series: an LSM-like design
  ([lesson 26.8](#/lesson/26.8)) with a **WAL** for crash safety ([lesson 26.13](#/lesson/26.13)).
- **Gorilla compression** (Facebook, 2015): timestamps stored as delta-of-delta (regular scrapes compress to ~1 bit),
  values XOR'd with the previous value (unchanged or similar floats compress to a few bits). Facebook reported an average
  of 1.37 bytes per sample on its production data (noisier data compresses less well). Prometheus uses the same ideas.
- Recent 2 hours in memory for fast queries and alerting; older blocks compacted, then downsampled for long ranges
  ([lesson 29.4](#/lesson/29.4)).

## Deep dive 2: alerting within 30 seconds

```
scrape/push interval 10 s + ingest ~2 s + rule evaluation every 10 s + notify ~2 s ≈ 25 s worst case
```

- Evaluate rules against the **in-memory head** (or directly on the ingest stream), not long-term storage.
- `for: 1m` deliberately adds delay to avoid flapping: if the goal is "within 30 s", use `for: 20s` or a rate-based
  condition and say so.
- **Alert manager** dedupes (many replicas fire the same alert), groups related alerts, applies silences and routes.
- Run two evaluator replicas; the alert manager dedupes their output so a lost evaluator doesn't miss an alert.
- Alert on SLO burn rates rather than raw thresholds to reduce noise ([lesson 18.1](#/lesson/18.1)).

## Deep dive 3: cardinality

Series count = product of label values. `http_requests{route, status, pod}` with 50 routes x 10 statuses x 200 pods =
100k series. Add `user_id` with 1M values and you have 100B series: the system dies.

- Enforce **limits at ingest**: max series per metric and per tenant; reject or drop new label values beyond them.
- Ban unbounded labels (user ids, request ids, raw URLs); use logs or traces for those.
- Track the top series-producing metrics and show teams their cost.

## Bottlenecks and failure modes

- **Ingest spike** (a deploy restarts 1,000 pods, new series per pod): Kafka buffers; the series index absorbs churn.
- **Query of death** (a year of a high-cardinality metric): query limits on series and points; timeouts.
- **TSDB shard down:** replicate ingest to two shards (or from Kafka replay); queries merge and dedupe.
- **Monitoring shares the failure** (same region, same network): meta-monitoring and a dead-man's-switch alert
  (an alert that fires when alerts *stop* arriving).

## What interviewers listen for

- Write-heavy numbers and compression that make storage small.
- Alerting computed from recent in-memory data with an explicit latency budget.
- Cardinality as the main scaling risk, with limits.
- Monitoring isolated from the things it monitors.

## Common mistakes

- Storing every sample as a row in a relational database.
- Alerting by running queries against long-term storage every minute.
- Ignoring cardinality until it explodes.
- Pull vs push debated for 10 minutes (pick one, mention the other: pull makes "target is down" obvious; push suits
  short-lived jobs).

## Key takeaways

- 1M series at 10 s is 100k samples/s; Gorilla-style compression makes it ~12 GB/day.
- Alert from the in-memory head with an explicit budget; dedupe in an alert manager.
- Cardinality is the scaling risk: limit labels at ingest.
- Keep monitoring in a separate failure domain and watch the watcher.

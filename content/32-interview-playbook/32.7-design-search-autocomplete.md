# Design search autocomplete

Type "sys" and ten suggestions appear before you type the next letter. The interview tests whether you see that this is
a **read-mostly, precomputed** problem: the heavy work happens offline, and the online path is a single key lookup that
must finish in tens of milliseconds.

## Clarifying questions

- Suggestions ranked by what? (Popularity of past queries, with some boost for recent trends.)
- How many suggestions? (Top 10.)
- Personalised? (Not in v1; maybe a light per-user history merge on the client.)
- How fresh? (Daily popularity is fine; trending events should show up within ~15 minutes.)
- Languages and filtering? (English first; offensive suggestions must be removable quickly.)

## Requirements

**Functional**
1. Given a prefix, return the top 10 completions by popularity.
2. Suggestions update as query popularity changes; trending queries appear within ~15 minutes.
3. Block-list terms removable within minutes.

**Non-functional**
- 50 ms end-to-end per keystroke (so ~10-20 ms at the server).
- Very high availability; if it fails, search still works without suggestions.
- Read-heavy and tolerant of slightly stale results.

## Estimates

```
requests:  100M daily users × 10 searches × ~6 prefix requests (after debouncing) = 6B/day
           6B / 86,400 ≈ 70k/s average, ~200k/s peak
distinct queries kept: ~10M popular queries (long tail dropped)
prefixes:  ~10M queries × avg ~10 useful prefixes, heavily shared → ~50-100M distinct prefixes
storage:   100M prefixes × 10 suggestions × ~30 B ≈ 30 GB (+ overhead → ~50-60 GB)
logs:      6B keystrokes/day aren't needed; only ~1B completed searches/day feed the counts
```

30-60 GB fits in memory across a handful of servers, replicated for throughput.

## API

```
GET /suggest?q=sys&locale=en-US&limit=10   → {suggestions: ["system design", "systemctl", ...]}
```

Small JSON, cacheable by (prefix, locale): `Cache-Control: max-age=300`.

## Data model

| Data | Key | Store |
|------|-----|-------|
| query counts | (query, day) | data warehouse / column store, built from search logs |
| prefix → top 10 | prefix (+ locale) | in-memory trie or KV (Redis / RocksDB), rebuilt periodically |
| trending counts | query → count over last 15 min | stream processor state |
| block-list | term | small config set pushed to all servers |

## High-level design

```
online:  browser (debounce 100 ms, local cache) → CDN (short prefixes cached) → suggest service (in-memory map) → response
offline: search logs → Kafka → daily batch: count queries, build prefix→top10 table → publish snapshot → servers load
fresh:   Kafka → stream job: counts over last 15 min → "trending" top-k per prefix → merged at query time
```

## Deep dive 1: trie vs precomputed prefix table

A **trie** finds a prefix in O(length), but finding the top 10 below a node means walking a subtree, which can be
millions of nodes for "s". The fix is to **store the top 10 at every node**, so a lookup is: walk to the node, return
its list.

Once each node holds its answer, you don't need the tree online at all: a **hash map prefix → top10** is simpler, and
it shards cleanly. Build it offline:

```
for each query q with count c:
    for each prefix p of q (up to ~20 chars):
        push (p, q, c) → group by p → keep top 10 by c
```

This is a classic MapReduce or Spark job ([lesson 29.6](#/lesson/29.6)). Use sampling of logs (say 1 in 10) to cut
cost; counts stay proportionally right.

## Deep dive 2: caching and latency

- **Client:** debounce keystrokes (~100 ms), cache responses in the page (backspace is free), and prefetch the next
  likely prefix.
- **CDN** ([lesson 3.7](#/lesson/3.7)): prefixes of 1-3 characters are few (~50k) and requested constantly; cache them
  at the edge for minutes.
- **Servers:** the whole table in memory; replicas behind a load balancer. Shard by prefix hash if one node can't hold
  it, but avoid sharding by first letter ("s" is far bigger than "x").
- Budget: ~20-40 ms of network for most users + ~1 ms lookup leaves headroom for 50 ms.

## Deep dive 3: freshness and safety

- **Two layers:** the daily table (stable, big) plus a trending layer from a stream job ([lesson 17.4](#/lesson/17.4))
  counting the last 15 minutes with a [count-min sketch](#/lesson/26.3) or exact counts for heavy hitters. At query
  time, merge: boost trending entries whose recent rate far exceeds their daily average.
- **Snapshots:** build the new table, load it on new servers or a second in-memory slot, then switch atomically
  (blue-green), never half-updated.
- **Block-list** applied at query time as a filter so removal takes minutes, not a rebuild.

## Bottlenecks and failure modes

- **Build job fails:** keep serving yesterday's snapshot; alert. Stale suggestions are fine.
- **Hot prefixes** ("a", "w"): absorbed by the CDN and client caches.
- **Bad snapshot** (empty or corrupted): validate size and spot-check before switching; roll back to the last good one.
- **Suggest service down:** the search box still works; fail silently.

## What interviewers listen for

- Precompute top-k per prefix offline; the online path is a lookup.
- Caching at every layer, with the client debounce in the latency math.
- A freshness story (batch + trending stream) and atomic snapshot swaps.
- Data size estimated to show it fits in memory.

## Common mistakes

- Running a `LIKE 'sys%' ORDER BY count` query against a database per keystroke.
- A trie without stored top-k, then walking subtrees online.
- Updating the trie in place on every search (lock contention, no benefit at this freshness).
- Sharding by first letter.

## Key takeaways

- Precompute top 10 per prefix; serve from memory with a single lookup.
- Cache at the client, the CDN and the server; debounce keystrokes.
- Rebuild offline, add a small trending layer, swap snapshots atomically.

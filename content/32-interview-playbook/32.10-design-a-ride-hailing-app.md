# Design a ride-hailing app

"Design Uber/Lyft" combines a firehose of location writes, a geospatial "who is near me" query, and a matching step
that must never give one driver to two riders. The trip itself is a small state machine that has to survive phones
dropping off the network.

## Clarifying questions

- Riders and drivers only, or also food delivery? (Rides only.)
- How does matching work: nearest driver, or best ETA? (Best ETA among nearby available drivers.)
- Pricing and surge? (Mention surge; payments out of scope beyond "charge at the end.")
- Scale? (1M drivers online at peak, 20M trips/day, many cities.)
- How fast must a match be? (Under a second to pick and offer a driver.)

## Requirements

**Functional**
1. Drivers report location every few seconds while online.
2. A rider requests a ride, sees a fare estimate, and gets matched with a nearby driver who accepts.
3. Both see each other's live location; the trip moves through requested → accepted → arrived → in progress → completed.

**Non-functional**
- Matching decision < 1 s; location on the rider's map < 2-3 s old.
- A driver is never assigned to two trips at once.
- Trip state is durable; location history may be lossy.
- Cities are independent; one city's load shouldn't hurt another.

## Estimates

```
location writes: 1M drivers / 4 s                 = 250k updates/s
payload:         ~100 B → 25 MB/s; history 250k × 86,400 × 100 B ≈ 2 TB/day (if kept)
trips:           20M/day ≈ 230/s average, ~1k/s peak requests
nearby queries:  each request checks ~10-50 candidates; plus riders' map views ~ tens of k/s
live index:      1M drivers × ~100 B ≈ 100 MB, fits in memory many times over
```

The live index is tiny but written 250k times a second: keep it **in memory**, not in a database.

## API

```
POST /drivers/me/location        {lat, lng, heading, ts}       (or a WebSocket stream)
POST /rides                      {pickup, dropoff, idempotency_key}   → {ride_id, status: REQUESTED, fare_estimate}
POST /rides/{id}/accept          (driver)                       → 200 or 409 if already taken
POST /rides/{id}/status          {ARRIVED | STARTED | COMPLETED}
WS   /rides/{id}/live            → driver location, status changes
```

## Data model

| Data | Key | Store |
|------|-----|-------|
| live driver location | driver_id → cell, lat/lng, status, ts | in-memory geo index sharded by city/region (or Redis GEO) |
| cell index | geo cell → set of available driver_ids | same in-memory service |
| ride | ride_id → rider, driver, state, version, timestamps | SQL, sharded by city or ride_id |
| location history | (driver_id, time bucket) | wide-column / Kafka → object store |

## High-level design

```
driver app ─WS→ location gateway → Kafka "locations" ─→ geo index service (per city, in memory)
                                                    └─→ history store, ETA/traffic models
rider app → API → ride service ─→ matching service ─→ geo index: nearby available drivers
                     │                 └─ rank by ETA → offer to driver (push, 10-15 s timeout) → next if declined
                     └─ ride DB (state machine, conditional updates)
live trip: ride service → pub/sub → rider/driver WebSockets
```

## Deep dive 1: geo indexing

Options ([lesson 26.9](#/lesson/26.9)):

| Index | How | Notes |
|-------|-----|-------|
| Geohash | lat/lng → base32 string; nearby cells share prefixes | simple, works with any KV; edge cells need neighbour lookups |
| Quadtree | split a cell when it has too many points | adapts to density; harder to shard |
| **H3 hexagons** | fixed hexagon grid at many resolutions | equal-distance neighbours; [Uber uses it](#/lesson/30.5) |

Query: take the rider's cell plus its ring of neighbours (expand if too few drivers), filter by status = available,
then rank the ~20 closest by **road ETA**, not straight-line distance. Each location update moves a driver from one
cell set to another; that is a cheap in-memory operation.

## Deep dive 2: matching without double-booking

1. Matching picks the best driver and sends an **offer** with a deadline.
2. Driver accepts → `UPDATE rides SET driver=?, state='ACCEPTED' WHERE id=? AND state='REQUESTED'` and atomically
   mark the driver busy (`... WHERE driver_id=? AND status='AVAILABLE'`). If either affects 0 rows, return 409.
3. Only one offer per driver at a time: a short lease on the driver in the matcher ([lesson 12.7](#/lesson/12.7)).
4. Decline or timeout → next candidate. Rider retries are safe thanks to the idempotency key.

At scale, matchers batch requests every second or two per area and solve them together (better total ETAs than
greedy one-by-one), and surge pricing rises when demand per cell exceeds supply.

## Deep dive 3: trip state and flaky phones

- Trip transitions are a **state machine** with versions; each change is a conditional update, so duplicated or
  out-of-order requests from a reconnecting phone are rejected safely ([lesson 12.4](#/lesson/12.4)).
- The driver app buffers locations while offline and uploads the trail on reconnect, which fare calculation needs.
- Stale drivers: no update for ~30 s → mark unavailable so they're never matched.

## Bottlenecks and failure modes

- **250k writes/s:** gateways batch into Kafka partitioned by city; geo index servers own cities (geo-sharding).
- **Big city hotspot:** split a city into several shards by region; replicate the index for reads.
- **Geo index node dies:** rebuild from the last few seconds of the Kafka stream (state is soft and short-lived).
- **Ride DB failover:** rides in progress continue on the apps; state changes retry with idempotency.

## What interviewers listen for

- In-memory geo index sharded by city, fed by a stream, with numbers.
- An index choice explained (geohash/quadtree/H3) with the neighbour problem.
- An atomic accept that prevents double assignment.
- The trip as a state machine resilient to retries and disconnections.

## Common mistakes

- Writing every location update to a SQL table and querying `WHERE lat BETWEEN ...`.
- Matching by straight-line distance only.
- Assigning without a conditional update (two riders get one driver).
- Ignoring drivers who go silent.

## Key takeaways

- Keep live locations in a sharded in-memory geo index fed by a stream.
- Find candidates by cell + neighbours, rank by ETA.
- Accept with conditional updates; model the trip as a versioned state machine.
- Shard by geography so cities scale and fail independently.

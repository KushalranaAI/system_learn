# Design file sync (Dropbox)

"Design Dropbox / Google Drive" is about moving as few bytes as possible. A user edits a 2 GB video project; the naive
design uploads 2 GB to the server and downloads 2 GB to every other device. The good design moves a few megabytes. The
other half of the problem is metadata: knowing what changed, telling devices, and handling two devices that edit the
same file offline.

## Clarifying questions

- Any file type and size? (Yes, up to tens of GB.)
- Multiple devices per user, and sharing between users? (Both; sharing folders in v2.)
- Offline edits? (Yes; sync when back online.)
- Version history? (30 days of versions.)
- Scale? (500M users, 100M daily active, ~2 GB stored each on average.)

## Requirements

**Functional**
1. Upload, download, update and delete files and folders from any device.
2. Changes appear on the user's other devices automatically.
3. Conflicts are detected and never silently lose data.
4. Version history for 30 days.

**Non-functional**
- Bandwidth-efficient: an edit to a large file transfers roughly the changed part.
- Durable: never lose a committed file (object storage at 11 nines, [lesson 29.1](#/lesson/29.1)).
- Change propagation to other online devices within seconds.
- Strongly consistent metadata per user/namespace (a file listing never goes backwards).

## Estimates

```
storage:   500M users × 2 GB              = 1 EB logical; dedupe across users saves a sizable share
blocks:    1 EB / 4 MB                    = 250B blocks → block index 250B × ~100 B ≈ 25 TB (sharded)
changes:   100M DAU × 20 file changes/day = 2B changes/day ≈ 23k/s average, ~70k/s peak (metadata writes)
upload:    if each change sends ~1 changed 4 MB block → 2B × 4 MB = 8 PB/day ≈ 93 GB/s (≈ 740 Gbit/s) ingress
notify:    100M devices online holding long-polls/WebSockets
```

Two very different systems: a **block store** (huge, simple, immutable) and a **metadata service** (small rows,
transactional, latency-sensitive).

## API

```
POST /blocks/check        {hashes[]}                   → {missing: [hash...]}
PUT  /blocks/{hash}       (bytes, ≤ 4 MB)              → 201  (presigned to object storage)
POST /files/commit        {path, blocklist[], parent_rev}  → {rev} | 409 conflict
GET  /changes?cursor=     (long-poll)                  → {entries: [{path, rev, blocklist}], cursor}
GET  /blocks/{hash}                                     → bytes (via CDN/presigned URL)
```

## Data model

| Entity | Key | Fields | Store |
|--------|-----|--------|-------|
| file version | (namespace_id, path, rev) | blocklist (ordered hashes), size, mtime, device | sharded SQL by namespace |
| namespace journal | (namespace_id, seq) | change entry | same shard; the sync cursor is a seq |
| block | SHA-256 hash | storage location, ref count | KV index + object storage |
| device cursor | (device_id, namespace_id) | last seq seen | client-side, echoed to server |

Dropbox describes exactly this: files split into **4 MB blocks**, each hashed with SHA-256, and a file identified by
its **blocklist** of hashes.

## High-level design

```
client watcher → chunk + hash → POST /blocks/check → upload only missing blocks → block store (object storage)
                                                   → POST /files/commit (blocklist, parent_rev) → metadata DB
                                                                                    ↓
                                                         append to namespace journal (seq++)
                                                                                    ↓
other devices ← notification service (long-poll/WebSocket "something changed") → GET /changes?cursor → fetch missing blocks
```

## Deep dive 1: chunking and dedupe

- A 2 GB file at 4 MB = **512 blocks**. Edit 1 MB in the middle in place → 1 block changes → upload **4 MB**, not 2 GB.
- **Dedupe:** before uploading, ask which hashes the server lacks. The same block (a shared PDF, a re-uploaded file)
  is stored once; moving or copying a file uploads nothing.
- **Insertions shift fixed blocks:** inserting 10 bytes at the start of a fixed-block file changes every block after
  it. **Content-defined chunking** (a rolling hash picks boundaries where the content matches a pattern) re-aligns
  after the edit, so only one or two chunks change. Mention it as the fix; average chunk size stays a few MB.
- Compress blocks before upload; encrypt at rest.

## Deep dive 2: metadata and change notification

- Every change appends an entry to the namespace's **journal** with an increasing seq. A device's sync state is one
  number: "I've seen up to seq 1,042."
- Notification: devices hold a long-poll ([lesson 6.1](#/lesson/6.1)); the server only says "new changes"; the device
  then pulls `/changes?cursor=1042`. Missed notifications don't matter because the cursor catches up
  ([lesson 6.5](#/lesson/6.5)).
- Commit is a transaction in one shard: write the new rev, append the journal entry, bump block ref counts.
- Shard metadata by namespace (a user's root or a shared folder), so commits stay single-shard.

## Deep dive 3: conflicts

- Each commit carries `parent_rev`. If the server's current rev differs, someone else changed it: **409**.
- The client then saves its version as "file (Laptop's conflicted copy 2026-10-24)" and downloads the server
  version. No data is lost; the user merges ([lesson 13.7](#/lesson/13.7)).
- Deletes vs edits: an edit wins over a concurrent delete (resurrect the file) to avoid loss.
- Clocks are never used to decide winners ([lesson 12.5](#/lesson/12.5)).

## Bottlenecks and failure modes

- **Upload interrupted:** blocks already uploaded are kept; resume uploads only the missing ones.
- **Metadata shard hot** (a huge shared team folder): split namespaces, rate-limit sync clients.
- **Block garbage collection:** reference counting with a delay (versions keep blocks alive for 30 days); never delete
  a block in the same moment a commit might reference it.
- **Reconnect storm:** millions of clients after an outage; jittered backoff, cheap cursor queries.

## What interviewers listen for

- Splitting block storage from metadata, and the numbers that justify it.
- Hash-addressed blocks, "which blocks are missing?", and dedupe.
- Cursor-based sync with a per-namespace journal.
- A conflict strategy that never loses data.

## Common mistakes

- Uploading whole files on every change.
- Pushing file content through the notification channel.
- Last-write-wins by timestamp (silent data loss).
- Ignoring that a 2 GB upload will be interrupted.

The client splits the file into 512 x 4 MB blocks and hashes each. After a 1 MB in-place edit only one hash changes;
`/blocks/check` returns that one hash as missing, the client uploads 4 MB (~1 MB compressed for many formats) and
commits a new blocklist with `parent_rev`. The journal gets a new seq; other devices are told "changed", pull
`/changes?cursor`, see one new hash, and download 4 MB. Total transfer: ~8 MB instead of 4 GB. With content-defined
chunking, an insertion near the start also changes only one or two chunks.

## Key takeaways

- Content-addressed blocks + dedupe + "send only missing hashes" make sync cheap.
- Keep metadata (small, transactional) separate from blocks (huge, immutable).
- Sync with a cursor into a per-namespace journal; notifications only say "pull now."
- Detect conflicts with parent revisions and keep both copies.

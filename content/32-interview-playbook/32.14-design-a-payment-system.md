# Design a payment system

"Design the payment backend for an e-commerce site" has modest traffic and brutal correctness rules: never charge twice,
never lose money, and always be able to explain every cent. The interviewer is listening for idempotency, a ledger, and
what you do when the card provider times out.

## Clarifying questions

- Are we a merchant using a payment service provider (Stripe, Adyen), or are we the provider? (A merchant/platform
  using external PSPs; we never store raw card numbers.)
- Pay-ins only, or also payouts to sellers? (Pay-ins and seller payouts.)
- Refunds? Multiple currencies? (Refunds yes; one currency per payment.)
- Scale? (10M payments/day, peaks 10x on sale days.)

## Requirements

**Functional**
1. Charge a customer for an order; show success/failure.
2. Refund fully or partially.
3. Track balances owed to sellers; pay them out daily.
4. Reconcile our records with the PSP's settlement reports.

**Non-functional**
- **Exactly-once effect:** a payment is charged at most once, even with retries and crashes.
- Every money movement is recorded and auditable forever.
- Availability matters, but correctness wins: better to say "pending" than to guess.
- PCI scope minimised (card data handled by the PSP's tokenisation).

## Estimates

```
payments:  10M/day ≈ 115/s average; ×10 on sale days → ~1,200/s peak
ledger:    each payment ≈ 2-4 ledger entries → ~5k entries/s peak
storage:   10M × 4 entries × ~200 B ≈ 8 GB/day ≈ 3 TB/year (kept for years: plan tiering)
PSP calls: ~1,200/s peak, p99 latency often 1-3 s → ~3,600 calls in flight
```

Throughput is small. The design is driven by **consistency and failure handling**, not scale.

## API

```
POST /payments    {order_id, amount, currency, payment_method_token}   Idempotency-Key: <uuid>
                  → 201 {payment_id, status: SUCCEEDED | PENDING | FAILED}
GET  /payments/{id}
POST /payments/{id}/refunds  {amount}   Idempotency-Key: <uuid>
POST /webhooks/psp           (PSP → us: async status updates, signed)
```

## Data model

| Entity | Key | Fields | Store |
|--------|-----|--------|-------|
| payment | payment_id; unique (merchant, idempotency_key) | order_id, amount, status, psp_reference, version | SQL (ACID) |
| payment attempt | attempt_id | payment_id, psp request id, result, raw response | SQL |
| ledger entry | entry_id | txn_id, account, debit/credit, amount, created_at; **append-only** | SQL (same DB or a ledger service) |
| account balance | account_id | derived from entries (cached/materialised) | SQL |
| outbox | event_id | "payment.succeeded" etc. | same DB, relayed to Kafka |

## High-level design

```
checkout → payment API ─ idempotency check (unique key) → payment row PENDING
                │
                ├─→ PSP adapter (timeouts, retries with the SAME PSP idempotency key, circuit breaker) → PSP
                │         ↑ webhooks (signed) ───────────────────────────────────────────────┘
                ├─→ on result: one DB transaction: payment status + ledger entries + outbox event
                └─→ outbox relay → Kafka → order service, emails, analytics
nightly:   reconciliation job: PSP settlement file ⟷ our payments and ledger → mismatches queue
payouts:   scheduler → seller balances → payout via PSP (same idempotent pattern)
```

## Deep dive 1: idempotency end to end

- The client sends an **Idempotency-Key**. The first request inserts `(merchant, key)` with a unique constraint; a
  retry finds the row and returns the stored result instead of charging again ([lesson 12.4](#/lesson/12.4)).
- If the first request is still in flight, the retry waits or gets 409 "in progress".
- We pass our own idempotency key (e.g. the payment_id) to the PSP, so our retries to the PSP are also safe. This is the
  pattern [Stripe describes](#/lesson/30.10).

## Deep dive 2: the ledger

Double-entry bookkeeping: every transaction is a set of entries whose debits and credits sum to zero.

```
customer pays 100:   debit  psp_receivable   100
                     credit seller_payable    90
                     credit platform_revenue  10
```

- Entries are **append-only**; a refund is new reversing entries, never an update.
- Balances are sums of entries (materialised for speed, verifiable at any time).
- Write payment status, ledger entries and the outbox event in **one transaction** ([lesson 16.4](#/lesson/16.4)), so
  "charged but not recorded" can't happen inside our system.

## Deep dive 3: provider failures and reconciliation

| PSP response | Meaning | Action |
|--------------|---------|--------|
| Success | charged | record SUCCEEDED + ledger |
| Declined | definitely not charged | FAILED, tell the user |
| 5xx / timeout | **unknown**, may or may not have charged | mark PENDING; retry with the same PSP key, or query PSP status; wait for webhook |

- Never treat a timeout as failure and charge again with a new key: that's the double charge.
- Webhooks can arrive late, twice or out of order: process idempotently, accept only valid state transitions
  (PENDING → SUCCEEDED, never SUCCEEDED → PENDING).
- **Reconciliation** daily: compare our records with the PSP's settlement file. Mismatches (they charged, we show
  failed) go to an automated fixer or a human queue. This is the safety net that catches every bug above.
- Multiple PSPs: route by cost and health; a circuit breaker fails over new payments, never in-flight ones.

## Bottlenecks and failure modes

- **DB primary down:** synchronous replication for the payments DB (RPO = 0); payments pause during failover rather
  than risk loss ([lesson 13.2](#/lesson/13.2)).
- **PSP outage:** queue retries for PENDING ones; show "processing" to users; fail over new payments to another PSP.
- **Crash between PSP success and our commit:** the payment stays PENDING; the webhook or the status poller completes it.
- **Hot accounts:** the platform revenue account gets every entry; shard it into sub-accounts and sum them.

## What interviewers listen for

- Idempotency keys at both our API and the PSP call.
- Timeouts treated as "unknown", resolved by query/webhook/reconciliation.
- An append-only double-entry ledger written atomically with status and events.
- Reconciliation as a first-class component.

## Common mistakes

- Updating a `balance` column in place with no entry history.
- Retrying a timed-out charge with a fresh request.
- A distributed transaction (2PC) with the PSP, which external providers don't support ([lesson 16.2](#/lesson/16.2)).
- Spending the interview on throughput when correctness is the hard part.

## Key takeaways

- Idempotency keys everywhere money moves, including calls to the provider.
- Timeouts mean "unknown": resolve, don't retry blindly.
- Append-only double-entry ledger, written in the same transaction as status and events.
- Reconciliation catches whatever the rest of the system gets wrong.

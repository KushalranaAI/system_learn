# Design a rate limiter

"Design a rate limiter" tests whether you know the algorithms ([lesson 8.2](#/lesson/8.2)) and, more importantly,
whether you can make them work across many servers without adding latency or a new single point of failure.

## Clarifying questions

- Is this a library inside one service, or a shared limiter for a public API? (A shared limiter for an API gateway.)
- What do we limit by: user, API key, IP, route? (API key, with different limits per plan.)
- Hard limit or soft? Is allowing 1-2% over the limit for a moment acceptable? (Small overshoot is fine.)
- What happens to rejected requests? (429 with `Retry-After`.)
- Scale? (50 API servers, ~1,000 active API keys, 200k requests/s total.)

## Requirements

**Functional**
1. Allow or reject each request based on rules like "key K: 1,000 requests/minute, bursts of 100".
2. Different rules per plan and per route; rules changeable without deploys.
3. Return 429 with `Retry-After` and `X-RateLimit-Remaining` headers.

**Non-functional**
- Adds < 1 ms p99 to each request.
- Accurate within a few percent across all 50 servers.
- The limiter failing must not take the API down.
- Out of scope: bot detection and DDoS at the network edge (that's the CDN/WAF's job).

## Estimates

```
checks:     200k requests/s → 200k limiter decisions/s
state:      1,000 keys × a few routes × ~100 B per counter  ≈ 1 MB  (even 10M keys ≈ 1 GB)
central:    one Redis node ≈ 100k ops/s, so 200k/s needs ~3-4 shards (by key) with headroom
latency:    same-AZ Redis round trip ≈ 0.3-0.5 ms → fits the 1 ms budget, but only just
```

Memory is trivial; **round trips and the hot path** are the real constraints.

## API

The limiter has an internal API, not a public one:

```
check(key, route, cost=1) → {allowed: bool, remaining, reset_at, retry_after}
PUT /rules/{plan}            {route, limit, window, burst}      (admin)
```

## Data model

| Data | Key | Store |
|------|-----|-------|
| rules | plan + route | config DB, cached in every server, pushed on change |
| token bucket | `rl:{api_key}:{route}` → {tokens, last_refill} | Redis hash, TTL = a couple of windows |
| sliding window counter | `rl:{key}:{route}:{window_start}` → count | Redis integer with TTL |

## High-level design

```
client → LB → API server ─┬─ local limiter (in-memory buckets, rules cache)
                          └─ Redis cluster (sharded by api_key), one Lua script per check
                                   ▲
              rules service ───────┘ (pushes rule changes to servers)
```

## Deep dive 1: which algorithm

| Algorithm | Memory per key | Bursts | Accuracy | Notes |
|-----------|----------------|--------|----------|-------|
| Fixed window | 1 counter | 2x at window edges | poor at edges | simplest |
| Sliding log | 1 entry per request | exact | exact | too much memory at high limits |
| Sliding window counter | 2 counters | smooth | ~1% error | a good default |
| **Token bucket** | 2 numbers | explicit burst size | exact | most APIs (Stripe, AWS) describe theirs this way |
| Leaky bucket | queue | none (smooths) | exact | shapes output rather than rejecting |

Pick **token bucket** for an API: "rate R, burst B" maps directly to plan limits. See
[token bucket internals](#/lesson/26.10).

## Deep dive 2: limits across 50 servers

Three options ([lesson 8.4](#/lesson/8.4)):

1. **Split the limit locally:** each server allows limit/50. No network calls, but load balancing is never perfectly
   even, so a key that lands mostly on 10 servers gets only 20% of its limit. Unfair.
2. **Central counter in Redis:** each check runs one Lua script that refills and takes tokens atomically (no
   read-modify-write race). Accurate; costs one round trip per request.
3. **Hybrid:** each server keeps a local bucket and **syncs with Redis every ~100 ms** (or after N requests), taking a
   batch of tokens at a time. Almost no added latency; overshoot is bounded by batch size x servers.

For 1,000 keys and 200k/s, option 2 with a sharded Redis is fine and the easiest to explain. Mention option 3 for keys
with very high limits, where one Redis key would become hot ([lesson 14.3](#/lesson/14.3)).

## Deep dive 3: when the limiter fails

- **Fail open** (allow) when Redis is unreachable: you lose protection for a while but the API stays up. Fall back to
  local per-server limits (limit/50) so protection degrades instead of vanishing.
- **Fail closed** only for limits that protect money or abuse (e.g. "SMS sends").
- Put a **short timeout** (a few ms) on the Redis call and a circuit breaker around it ([lesson 12.3](#/lesson/12.3)).
- **Clock skew:** compute refills using Redis server time inside the script, not each API server's clock.

## Bottlenecks and failure modes

- One huge customer = one hot Redis key: use the hybrid scheme or split their bucket into N sub-keys.
- Redis shard failover: replicas are async, so a few counters reset. That means a brief overshoot, which is acceptable.
- Retry storms: clients that ignore `Retry-After` hammer the limiter; rejections must be cheap (no DB calls).
- Multi-region: keep limits per region (limit split by region traffic) rather than a global synchronous counter.

## What interviewers listen for

- Algorithm choice with a reason (bursts, memory, accuracy), not a list.
- Atomicity: "two servers read 99, both write 100" and how a Lua script or `INCR` avoids it.
- Where it runs: gateway vs middleware vs sidecar, and the latency it adds.
- A clear fail-open/fail-closed decision.

## Common mistakes

- `GET` then `SET` in Redis from the app (a race that lets bursts through).
- Limiting by IP only, which punishes whole offices and mobile carriers behind NAT ([lesson 8.3](#/lesson/8.3)).
- Making the limiter a synchronous dependency with no timeout, so Redis slowness becomes API slowness.
- Forgetting headers: clients can't back off politely without `Retry-After`.

## Key takeaways

- Token bucket fits API limits; sliding window counter is a good low-memory alternative.
- Make each check atomic (Lua or `INCR` with TTL) and keep it to one round trip.
- Plan the failure mode: fail open to local limits for most routes, fail closed for costly ones.

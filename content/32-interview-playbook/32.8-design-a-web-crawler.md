# Design a web crawler

A crawler looks like a loop: take a URL, fetch it, extract links, repeat. At a billion pages a month the loop becomes a
distributed system with three hard parts: a **frontier** that decides what to fetch next, **politeness** so you don't
hammer any one site, and **deduplication** of URLs and content.

## Clarifying questions

- Purpose? (Feed a search index, so we store HTML.)
- HTML only, or also images, PDFs, JavaScript rendering? (HTML only; no JS rendering in v1.)
- Scale and freshness? (1B pages a month; popular pages re-crawled more often.)
- Must we obey robots.txt? (Yes, always.)
- How long do we keep pages? (Latest copy of each page; older versions out of scope.)

## Requirements

**Functional**
1. Start from seed URLs, fetch pages, extract links, add new ones to the frontier.
2. Store page content for an indexer.
3. Re-crawl pages based on importance and how often they change.

**Non-functional**
- Politeness: obey robots.txt, at most ~1 request per host every few seconds by default.
- Throughput: 1B pages/month, horizontally scalable.
- Robust to traps (infinite calendars, session ids in URLs), slow servers and malformed HTML.
- Don't fetch the same URL twice per cycle; don't store the same content twice.

## Estimates

```
pages:      1B / 2.6M s/month                ≈ 400 pages/s (design for ~1,000/s peak)
size:       ~100 KB average HTML             → 400 × 100 KB = 40 MB/s ≈ 320 Mbit/s download
storage:    1B × 100 KB = 100 TB/month raw; ~25 TB compressed
latency:    ~1 s per fetch → 400 fetches in flight on average; ~2,000 with slow sites
URLs seen:  ~10B over time; Bloom filter at 1% false positives ≈ 9.6 bits each ≈ 12 GB
DNS:        400 lookups/s if uncached → cache DNS per host
```

The CPU and network are modest; the challenge is **coordination**: per-host queues and dedupe.

## API

Internal interfaces rather than a public API:

```
frontier.enqueue(urls[], priority)        frontier.next(worker_id) → url
fetcher.fetch(url) → {status, headers, body}
store.put(url, content_hash, body)        seen.check_and_add(url) → bool
```

## Data model

| Data | Key | Store |
|------|-----|-------|
| URL record | normalised URL hash | wide-column / KV: last_crawled, next_crawl, priority, content_hash |
| page content | content hash | object storage (compressed) |
| seen-URL filter | URL | Bloom filter in memory, sharded by host |
| robots.txt | host | cache with ~24 h TTL |
| host queue | host → URLs | per-host FIFO in the frontier |

## High-level design

```
seeds → frontier ──────────────────────────────────────────────┐
         │ front queues (by priority) → back queues (one per host, with next_allowed_time)
         ↓
      fetcher workers ─ DNS cache, robots cache ─→ fetch HTML
         ↓
      parser → extract links → normalise → URL filter (seen? Bloom) → frontier
         └─→ content dedupe (hash / SimHash) → object store → Kafka "page_fetched" → indexer
```

Partition everything by **host hash**: one host's queue, robots.txt and rate limit live on one frontier shard.

## Deep dive 1: the frontier and politeness

The classic design (the Mercator crawler) uses two levels of queues:

- **Front queues by priority:** PageRank-like importance, freshness need, or domain quality decide which queue a URL
  enters. Higher-priority queues are drained more often.
- **Back queues by host:** each back queue holds URLs for one host, and a heap of `next_allowed_time` per host decides
  which host is ready. After fetching from a host, set its next time to now + delay (e.g. 10x the last response time,
  or the robots.txt `Crawl-delay`).

This guarantees no host gets more than one request at a time, while thousands of hosts are fetched in parallel.

## Deep dive 2: dedupe

- **URL normalisation:** lowercase host, strip fragments, sort query params, drop tracking params like `utm_*`.
- **URL seen test:** a [Bloom filter](#/lesson/26.2) answers "definitely new" in memory. A false positive means
  skipping a new URL ~1% of the time, which is acceptable; back it with the URL table for important URLs.
- **Content dedupe:** an exact hash (SHA-256) catches identical mirrors; **SimHash** catches near-duplicates (same
  article, different ads). Store content once, map many URLs to it.

## Deep dive 3: traps, failures and recrawl

- **Traps:** cap URL length and path depth, cap pages per host per cycle, and detect repeating path segments.
- **Slow servers:** short connect timeouts, a cap on body size (e.g. 10 MB), and per-host failure counts that back
  off.
- **Recrawl scheduling:** pages that changed (different content hash) get a shorter interval next time; unchanged ones
  a longer one. Use `If-Modified-Since` / ETags to save bandwidth.
- **Worker crash:** frontier leases a URL to a worker with a timeout ([lesson 7.2](#/lesson/7.2)); if not acked, it
  returns to the queue.

## Bottlenecks and failure modes

- **DNS** becomes the bottleneck surprisingly early: run a local caching resolver.
- **One giant host** (a site with 100M pages) can't go faster than politeness allows; its crawl takes long by design.
- **Frontier shard down:** its hosts pause; persist queues to disk (or Kafka) so nothing is lost.
- **Storage growth:** compress, store only the latest version, tier old content to cold storage ([lesson 9.1](#/lesson/9.1)).

## What interviewers listen for

- Politeness as a design constraint, with per-host queues.
- Bloom filters with a stated false-positive rate and memory size.
- Partitioning by host and why.
- Traps and recrawl policy, not just the happy path.

## Common mistakes

- A single global FIFO queue (one host fills it, and you DDoS them).
- Checking "seen" with a database query for every extracted link (tens of thousands per second).
- Forgetting robots.txt, DNS caching or URL normalisation.
- Treating all pages equally instead of prioritising.

## Key takeaways

- The frontier is priority queues in front of per-host queues with next-allowed times.
- Partition by host so politeness, robots.txt and dedupe stay local.
- Bloom filters for URL seen-tests, hashes/SimHash for content dedupe.
- Defend against traps and schedule recrawls by change rate.

# Design a URL shortener

"Design bit.ly" is the classic warm-up. It looks trivial, which is the trap: the interviewer wants to see you size it,
pick a key scheme you can defend, and make a read path that survives 100k redirects a second.

## Clarifying questions

- Do users choose custom aliases, or only get generated codes? (Both; custom is optional.)
- Do links expire? Can they be edited or deleted? (Optional expiry; no editing.)
- Do we need click analytics? Real-time or daily? (Counts per link, a few minutes late is fine.)
- How short must the code be? (As short as possible; 7 characters is fine.)
- Scale: how many new links and redirects? (100M new links a month, 100:1 reads.)

## Requirements

**Functional**
1. Create a short link for a long URL (optional custom alias, optional expiry).
2. Redirect `GET /{code}` to the long URL.
3. Show click counts per link.

**Non-functional**
- Redirect p99 < 50 ms at the server; very high availability on redirects (99.99%).
- Links never collide and never get lost once created.
- Analytics may lag by minutes; they must never slow a redirect.
- Out of scope: accounts and billing, link previews, spam scanning (mention it, don't design it).

## Estimates

```
writes:   100M / month ÷ 2.6M s       ≈ 40 creates/s   (peak ~5x → 200/s)
reads:    100 × 40                     ≈ 4,000 redirects/s average
          peak ×5                      ≈ 20,000/s; design for 100k/s (viral links, the "Try it")
storage:  100M × 12 months × 5 years   = 6B links
          6B × ~500 B per row          ≈ 3 TB
keyspace: 62^7                         ≈ 3.5 trillion codes, ~600x what 5 years needs
```

Conclusions: writes are tiny, one database handles them. Reads are 100x writes and very skewed (a few links get most
clicks), so **caching decides this design**. 3 TB of metadata fits a few database shards or one large key-value
cluster.

## API

```
POST /links            {long_url, alias?, expires_at?}   → 201 {code, short_url}
GET  /{code}                                            → 302 Location: long_url  (404 / 410 if missing/expired)
GET  /links/{code}/stats?from=&to=                      → {clicks, by_day: [...]}
DELETE /links/{code}                                    → 204
```

## Data model

| Entity | Key | Fields | Store |
|--------|-----|--------|-------|
| link | `code` | long_url, owner_id, created_at, expires_at | key-value store or sharded SQL, keyed by code |
| click event | (code, ts) | referrer, country, user agent | Kafka topic → analytics store |
| daily count | (code, day) | clicks | column store or counters table |

The only hot query is "code → long_url": a perfect key-value lookup.

## High-level design

```
create:   client → LB → API → key generator → links DB
redirect: client → CDN/edge (cached 302s) → LB → API → Redis → links DB
                                             └─ click event → Kafka → stream job → counts DB
stats:    client → API → counts DB
```

## Deep dive 1: generating the code

| Scheme | How | Good | Bad |
|--------|-----|------|-----|
| Hash + truncate | base62(md5(url))[:7] | stateless, same URL → same code | collisions need a check-and-retry loop |
| Global counter + base62 | id 125 → "21" | no collisions, short | a single counter is a bottleneck and makes codes guessable |
| **Counter ranges** | each API server leases 10,000 ids at a time from a DB/ZooKeeper counter | no collisions, no per-request coordination | lost ranges on crash (fine), sequential codes |
| Pre-generated keys | a key service fills a table of unused random codes | random, fast | another service to run |

A strong answer: **counter ranges + base62**, optionally shuffled (multiply by a large number coprime to 62, mod 62^7) so codes
aren't enumerable. Custom aliases use a conditional insert (`INSERT ... IF NOT EXISTS`) and fail with 409 if taken.
See [unique IDs](#/lesson/12.6) and [Snowflake IDs](#/lesson/26.11).

## Deep dive 2: the redirect path at 100k/s

- **301 vs 302** ([lesson 3.7](#/lesson/3.7)): 301 is cached by browsers forever, which saves load but loses click
  counts and makes deletes impossible. Use **302** (or 301 with short `Cache-Control`) when analytics matter.
- **CDN/edge cache** for the hottest links with a short TTL (say 60 s): a viral link is served without reaching you.
- **Redis cache-aside** ([lesson 3.3](#/lesson/3.3)): link rows are tiny (~500 B), so 20M hot links = 10 GB. With a 95%
  hit ratio, 100k/s becomes 5k/s at the database.
- **Negative caching:** cache "not found" briefly so scanners hammering random codes don't reach the database.
- **Hot keys** ([lesson 3.6](#/lesson/3.6)): one viral code can exceed one Redis shard; add a small in-process cache
  with a few seconds of TTL on each API server.

## Deep dive 3: analytics without slowing redirects

Never write to a database inside the redirect. Emit a click event to Kafka asynchronously (fire and forget, or a local
buffer), aggregate per (code, minute) in a stream job ([lesson 17.4](#/lesson/17.4)), and write counts in batches.
Unique visitors can use [HyperLogLog](#/lesson/26.4). If Kafka is down, drop or buffer events: redirects come first.

## Bottlenecks and failure modes

- **Redis down:** the database sees the full 100k/s and falls over. Use replicas, shard the cache, and have the
  database protected by a limit so it degrades instead of dying.
- **Key generator down:** servers still have leased ranges; creates continue for a while.
- **Database primary down:** redirects keep working from cache and replicas; creates pause until failover.
- **Abuse:** rate-limit creates per user/IP ([Module 8](#/lesson/8.1)), scan URLs for malware asynchronously.

## What interviewers listen for

- You notice reads dominate and put the cache, CDN and 301/302 choice at the centre.
- A key scheme with a clear answer to "what about collisions?" and "can two servers hand out the same code?"
- Analytics off the hot path.
- Concrete sizing: keyspace math, cache memory, database load after the cache.

## Common mistakes

- Designing analytics as a synchronous `UPDATE clicks = clicks + 1` per redirect (a hot-row disaster).
- Hash-and-truncate with no collision handling.
- Picking 301 without realising it breaks analytics and deletes.
- Spending 15 minutes on base62 encoding and never reaching the read path.

## Try it

**Handle 100k redirects/s.** [Build it in the sandbox](#/sandbox?preset=iv-url-shortener): start from the plain
API-plus-database design, push redirect traffic to 100k/s, and add a cache and CDN until p99 holds; then flush the cache

At 100k/s with no cache, the database sees all 100k reads, far beyond one node. Add Redis with ~95% hits: the database

## Key takeaways

- Reads are ~100x writes and highly skewed: CDN + Redis + negative caching carry the load.
- Counter ranges + base62 give short, collision-free codes without per-request coordination.
- Choose 302 (or short-lived 301) when you need analytics; count clicks asynchronously.

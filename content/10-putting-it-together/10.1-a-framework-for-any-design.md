# A framework for any design

You've learned the parts. Now you need a repeatable way to go from a blank page to a defensible design, whether in a
design review at work or in a 45-minute interview.

## The seven steps

| # | Step | Output | Interview time |
|---|------|--------|----------------|
| 1 | **Requirements** | 3–5 functional, 3–5 non-functional with numbers, out of scope | 5 min |
| 2 | **Estimates** | QPS (peak), read:write ratio, storage/year, bandwidth | 3–5 min |
| 3 | **API** | The main endpoints with methods, inputs and outputs | 3–5 min |
| 4 | **Data model** | Core entities, keys, the store for each | 5 min |
| 5 | **High-level design** | Boxes and arrows for the main request paths | 5–10 min |
| 6 | **Deep dives** | The 2–3 hardest parts, in depth | 10–15 min |
| 7 | **Bottlenecks and failures** | What breaks first, what happens when X dies, how it grows 10x | 5 min |

## 1. Requirements: narrow the problem

Ask until you can write numbers down. "Design Twitter" becomes: post short text, follow users, see a home timeline;
300M daily users; timeline p99 < 300 ms; posts must never be lost; out of scope: ads, DMs, search.

## 2. Estimates: let the numbers pick the design

The key outputs are **peak QPS per path**, **read:write ratio** and **data size**. They tell you whether you need a
cache, a CDN, replicas, queues or shards, and they tell the interviewer you think quantitatively.

## 3. API: the contract

Write 3–6 endpoints. It forces clarity: `GET /timeline?cursor=` reveals pagination, `POST /tweets` reveals
idempotency, `GET /users/:id/followers` reveals fan-out.

## 4. Data: entities and the store for each

Name the tables or collections and their keys. Choose stores by access pattern (lesson 2.6): relational for core
entities, object storage for media, a cache for hot reads, a log or queue for events.

## 5. High-level design: the request paths

Draw the **write path** and the **read path** separately; they often differ a lot.

```
write: client → LB → API → DB  (+ queue → fan-out workers)
read:  client → CDN → LB → API → cache → DB
```

Start simple, then add parts only where the numbers demand them.

## 6. Deep dives: where the real thinking is

Pick the parts that are **hard for this problem**:
- the timeline: fan-out on write vs on read, and celebrities (Module 15);
- a booking system: double-booking under concurrency (lesson 1.6, Module 16);
- chat: ordering, delivery and offline users (Module 6).

Go deep on 2–3, not shallow on 10.

## 7. Bottlenecks and failures

Walk the design and ask, for each component:
- What happens when it **dies**? (detection, failover, data loss)
- What happens at **10x load**? (which part saturates first)
- What's the **single point of failure**?

## Try it

Run the framework on **"a URL shortener for 100M new links a month"** in 20 minutes on paper. Then compare with the
[Link shortener lab](#/labs/link-shortener).

## Key takeaways

- Use the same seven steps every time: requirements, estimates, API, data, high-level, deep dives, failures.
- Let numbers drive which components you add.
- Draw write and read paths separately.
- Spend the most time on the 2–3 parts that are hard for this problem.

# Explaining your design

A design that's right but explained badly loses to a decent design explained clearly, in interviews and in real
design reviews. Explaining is a skill you can practise.

## Narrate decisions, not boxes

| Weak | Strong |
|------|--------|
| "Then there's a cache." | "Reads are 100x writes and the same links are clicked repeatedly, so a cache in front of Postgres cuts DB load ~80%. I'll use cache-aside with a 10-minute TTL." |
| "We use Kafka." | "Posting must stay fast even though fan-out to 10,000 followers is slow, so the API writes the post and publishes an event; fan-out workers consume it." |

The pattern: **need → choice → why → cost.**

## State tradeoffs out loud

"I'm choosing async replication: writes stay fast, but a failover can lose a second of writes. For likes that's
fine; for payments I'd use synchronous replication or a single-region primary."

Naming the cost shows you saw the alternative.

## Draw clearly

- Clients on the left, data stores on the right; requests flow left → right.
- Label arrows with **what** flows and **how much**: "reads 20k/s", "events (async)".
- Separate the write path and the read path, in different colours if you can.
- Mark async edges differently (dashed).
- Keep it readable. Split into two diagrams rather than one with 30 boxes.

## Handle "what if…?"

Interviewers and reviewers probe: *"What if the cache dies?" "What if a celebrity posts?" "What if traffic 10x?"*

1. **Restate** the scenario briefly.
2. **Trace** what happens in your current design.
3. **Name** the failure or bottleneck.
4. **Propose** a fix and its cost.

*"If Redis dies, reads fall back to Postgres. At 20k reads/s that's above its 15k capacity, so it would overload. I'd
add a replica for headroom, coalesce misses, and use a Redis replica with automatic failover so the cache comes back
in seconds."*

## Say what you'd do next

End with priorities: "First I'd launch with one region and a single primary. At 5x I'd add read replicas. Sharding
only if writes pass ~10k/s." It shows judgment about **when**, not only **what**.

## Practise with video

Record yourself explaining a design for 10 minutes using the sandbox (presenter mode, `P`). Watch it back:
- Did you state numbers?
- Did you name tradeoffs?
- Did you rush through boxes without saying why?

## Try it

Explain to a friend (or a camera) why the [Edge preset](#/sandbox?preset=edge) has a rate limiter *before* the load
balancer rather than after it. Use need → choice → why → cost.

<details>
<summary>One way to say it</summary>

"A scraper sends 30k req/s for random URLs (**need**: stop it before it costs anything). I put the limiter at the edge,
before the LB (**choice**). Blocked requests then never use LB, server, cache or DB capacity (**why**). The cost: the
edge only knows the IP, not the user, so the per-IP limit must stay generous for shared IPs, and fine-grained
per-account limits happen later, in the app."
</details>

## Key takeaways

- Explain each component as need → choice → why → cost.
- Say the tradeoffs out loud.
- Draw left-to-right, label flows with volumes, and separate read and write paths.
- Answer "what if" by tracing, naming the failure, and proposing a fix.

# Algorithms

"100 requests per minute" sounds precise. It isn't. Different algorithms answer "may this request go through?" very
differently, especially for bursts and at window edges.

## Fixed window counter

Count requests per key per calendar window (`12:01:00–12:01:59`).

```
key = rl:{user}:{minute}    INCR → if > 100 → reject    (EXPIRE 60 s)
```

- ✅ One counter, very cheap.
- ❌ **Boundary burst:** 100 requests at 12:01:59 plus 100 at 12:02:00 = 200 in two seconds.

## Sliding log

Store a timestamp for every request; count those in the last 60 s.

- ✅ Exact.
- ❌ Memory per request: 100 timestamps per user per minute. Costly at scale.

## Sliding window counter

Blend the current and previous fixed windows by how far into the current window you are:

```
estimate = current_count + previous_count × (1 − elapsed_fraction)
at 12:02:15 (25% into the minute): 30 + 80 × 0.75 = 90  → allowed (≤ 100)
```

- ✅ Two counters per key, and it smooths the boundary burst.
- ❌ An approximation (it assumes the previous window's requests were evenly spread). That's good enough in practice.

## Token bucket: the most common

Each key has a bucket that holds up to **B** tokens and refills at **R** tokens per second. Each request takes a
token; with no tokens, it's rejected.

```
capacity B = 20 (burst), refill R = 5/s (average)
idle client → bucket full → can burst 20 requests at once → then 5/s sustained
```

- ✅ Allows short bursts (real clients are bursty) while capping the average.
- ✅ Cheap: store `(tokens, last_refill_time)` and refill lazily on each request.
- Used by AWS, Stripe and most API gateways.

## Leaky bucket

Requests enter a queue that drains at a fixed rate R; if the queue is full, they're rejected.

- ✅ Perfectly smooth output, which is good for protecting a fragile downstream.
- ❌ Adds latency (requests wait); no bursts.

## Comparison

| Algorithm | Memory per key | Bursts | Accuracy | Typical use |
|-----------|----------------|--------|----------|-------------|
| Fixed window | 1 counter | 2x at edges | Low | Coarse limits, daily quotas |
| Sliding log | 1 entry per request | None | Exact | Low-volume, strict limits (logins) |
| Sliding window counter | 2 counters | Smoothed | Good | General API limits |
| Token bucket | 2 numbers | Controlled (up to B) | Good | **Default for APIs** |
| Leaky bucket | A queue | None | Exact rate | Shaping outbound calls |

## Token bucket in Redis (Lua, atomic)

```lua
-- KEYS[1]=bucket  ARGV: capacity, refill_per_sec, now_ms
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local cap, rate, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)
local allowed = tokens >= 1
if allowed then tokens = tokens - 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
return allowed and 1 or 0
```

## Try it

A limit is "10 per second". A client sends nothing for a minute, then 30 requests in 100 ms. What happens under a
fixed 1 s window, and under a token bucket with capacity 10 and refill 10/s?

<details>
<summary>Answer</summary>

**Fixed window:** 10 allowed, 20 rejected (unless the burst straddles a window edge, in which case up to 20 pass).
**Token bucket:** the full bucket allows 10 immediately; in the next 100 ms it refills ~1 token, so ~11 pass and ~19
are rejected. The same average, but you can tune the bucket's capacity separately from its rate.
</details>

## Key takeaways

- Fixed windows are cheap but allow double bursts at the edges.
- Sliding window counters fix that with two counters; sliding logs are exact but costly.
- The token bucket is the default: capacity = burst, refill = average rate.
- The leaky bucket smooths output for fragile downstreams.

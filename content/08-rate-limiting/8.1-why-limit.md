# Why limit

Your public API is humming along at 2,000 req/s. One customer's buggy script starts sending 40,000 req/s in a tight
loop. Every other customer's requests slow down and time out. **Rate limiting** decides how much each client may ask
for, so one client can't take the service from everyone else.

## What limits protect against

| Threat | Example |
|--------|---------|
| **Abuse** | Scrapers, credential stuffing (trying leaked passwords), spam |
| **Accidents** | A retry loop with no backoff, a misconfigured cron |
| **Unfairness** | One big tenant consuming capacity meant for everyone |
| **Cost** | Endpoints that call paid APIs (SMS, LLMs, maps) |
| **Overload** | Protecting the database and dependencies during spikes |

## Answering "no" properly

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 12
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 12
Content-Type: application/json

{"error": {"code": "rate_limited", "message": "Slow down: 100 requests per minute."}}
```

- **429** says "you, specifically, are sending too much". (503 says "the server is overloaded for everyone".)
- **Retry-After** tells well-behaved clients exactly when to retry.
- The **RateLimit-** headers let clients pace themselves before they hit the wall.

## Writing a policy

A policy says **who** is limited, **how much**, over **what window**, and on **which endpoints**.

| Endpoint | Key | Limit |
|----------|-----|-------|
| `POST /login` | IP **and** username | 5 / min per username, 30 / min per IP |
| `POST /sms/send` | account | 10 / min, 200 / day |
| `GET /api/*` | API key | 1,000 / min (by plan) |
| Everything | IP | 300 / min (coarse backstop) |

- Expensive or sensitive endpoints get **tighter** limits.
- **Plans** (free/pro/enterprise) usually differ mainly in limits.
- Allow **short bursts** above the average: real clients are bursty (lesson 8.2).

## Where limits live

```
Client ─▶ [Edge / CDN / WAF limits by IP] ─▶ [API gateway limits by key or user] ─▶ [Service limits per tenant/endpoint]
```

Edge limits stop floods cheaply before they reach you. Application limits know who the user is, so they can be fair
per account.

## Try it

Write a policy for a password-reset endpoint that emails a reset link. What do you key on, and why more than one key?

<details>
<summary>Answer</summary>

Key on the **target email/account** (e.g. 3 per hour, to stop harassing one user's inbox) **and** the **IP** (e.g. 20
per hour, to stop one attacker hitting many accounts). Respond the same way whether or not the account exists, so the
endpoint doesn't reveal which emails are registered.
</details>

## Key takeaways

- Rate limits stop abuse, accidents, unfairness and runaway costs.
- Reply with 429 plus Retry-After and RateLimit headers.
- Policies define key, limit, window and endpoint; sensitive endpoints get tighter limits.
- Layer limits: coarse at the edge, fair per user or tenant in the app.

# Limits across many servers

A limit of 100 req/min per user is easy on one server: keep a counter in memory. With 20 servers behind a load
balancer, each keeps its own counter, and the user gets **2,000** req/min.

## Option 1: A central counter store

All servers check one shared store, usually Redis:

```
INCR rl:user42:2026-10-24T10:15   → 87
EXPIRE … 60
if 87 > 100 → 429
```

Use **atomic** operations (`INCR`, or a Lua script for a token bucket, as in lesson 8.2). A read-then-write from the
app races: two servers both read 99 and both allow.

- ✅ Accurate across all servers.
- ❌ One extra round trip (~0.5 ms) per request.
- ❌ Redis becomes critical: decide what happens when it's down (next section).
- ❌ Hot keys: one huge tenant's counter on one Redis node.

## Option 2: Local limits + sync

Each server enforces `limit ÷ number_of_servers` locally, or keeps local counters and syncs them to Redis every few
hundred milliseconds.

- ✅ No round trip on the hot path.
- ❌ Approximate: uneven load balancing lets some users exceed or fall short of the limit; the share changes when
  servers scale.

## Option 3: At the edge or gateway

Let the API gateway, service mesh or CDN do it (Envoy, Kong, NGINX, Cloudflare). They use the same techniques
internally, but you configure instead of building.

## When the limiter's store fails

| Choice | Effect |
|--------|--------|
| **Fail open** (allow) | The service stays up; limits are briefly unenforced |
| **Fail closed** (deny) | Abuse is blocked, but so is everyone: your limiter caused an outage |

Most APIs **fail open** for general limits, with a local in-memory fallback limit, and **fail closed** only for the
most sensitive endpoints (e.g. login attempts).

## Accuracy vs cost

You rarely need perfect accuracy. "Roughly 100/min, never more than ~110" is fine for most APIs. Use exact central
counting for money, security and quotas customers pay for; use local or approximate counting for floods.

## Multi-region

Each region typically enforces its own limit (cheap and fast). A global limit across regions needs cross-region sync,
which is slow and usually approximate. Either split the quota per region or sync asynchronously.

## Try it

You run 12 servers, a limit of 600 req/min per API key, and Redis for counters. Redis has a 2-minute outage. What
should the servers do, and how?

<details>
<summary>Answer</summary>

Fail open with a local fallback: each server enforces ~600 ÷ 12 = 50 req/min per key in memory while Redis is
unreachable (with a short timeout on Redis calls so requests don't hang). That's slightly unfair but safe. Alert on
the fallback; for login endpoints, fall back to a stricter local limit rather than none.
</details>

## Key takeaways

- Per-server counters multiply the limit by the number of servers.
- Central atomic counters (Redis INCR or Lua) are accurate at the cost of a round trip.
- Local or synced limits are faster but approximate.
- Decide fail-open vs fail-closed per endpoint; usually fail open with a local fallback.

# What to count by

A limit is only as fair as its **key**. Count by the wrong thing and you either block innocent users or don't stop the
attacker at all.

## Common keys

| Key | Good for | Pitfalls |
|-----|----------|----------|
| **API key / account** | Fair per-customer limits, plans | Only after authentication; free sign-ups can mint new keys |
| **User id** | Per-user fairness inside an app | Logged-in traffic only |
| **IP address** | Anonymous traffic, login pages, floods | NAT: many users share one IP; attackers rotate IPs |
| **IP + endpoint** | Tight limits on sensitive routes | Same NAT issue |
| **Target resource** | "5 password resets per account per hour" | Stops harassment of one victim, not broad attacks |
| **Global** | Last-resort protection of a dependency | Punishes everyone equally: real users get 429s too |

## The NAT problem

Behind one public IP there may be:
- one person on home broadband (~1–5 req/s when active);
- an office of 200 people;
- a university or a **mobile carrier's NAT** with thousands of phones.

A strict per-IP limit (say 10 req/s) blocks the whole office whenever a few people are busy. In the simulator's model,
about 3% of real traffic comes from shared IPs at ~40 req/s each. Set a per-IP limit below that, and the Hud's "Real
users 429'd" counter lights up.

**Rules of thumb**
- Per-IP limits should be **generous**: they're a flood backstop, not fairness.
- Real fairness comes from **authenticated** keys (user, account, API key).
- IPv6: limit by **/64 prefix**, since one user may get billions of addresses.

## What doesn't work

| Key | Why not |
|-----|---------|
| **URL path / slug** | Scrapers request *different* paths every time, so a per-path limit never catches them. It only throttles your most popular pages |
| **User-Agent** | Trivially faked |
| **Cookie or session for anonymous users** | Attackers just don't send it |

## Layer the keys

```
edge:   per IP 300/min          (stops floods, generous for NATs)
login:  per IP 30/min + per username 5/min
API:    per API key by plan     (fair use)
global: per dependency (e.g. SMS 500/s total) to protect cost and quota
```

## Beyond counting

Determined attackers rotate thousands of IPs (residential proxies). Rate limiting slows them down, but you also need:
- bot detection (behaviour and fingerprinting, often via a CDN/WAF);
- challenges (CAPTCHA) on suspicious traffic;
- making the attack pointless (no data worth scraping without an account).

## Try it

A coupon site limits `GET /coupon/:code` to 20 req/s **per code**. A scraper fetches every possible code. What
happens, and what would work better?

<details>
<summary>Answer</summary>

The scraper asks for a different code each time, so it never trips a per-code limit. Meanwhile your most popular
coupon gets throttled for real users. Better: limit per IP (generously) and per account, add bot detection, and make
codes long and random so enumeration is hopeless.
</details>

## Key takeaways

- The key decides fairness: authenticated keys for fair use, IP as a generous backstop.
- Shared IPs (offices, carriers) make strict per-IP limits hurt real users.
- Per-path limits don't catch scrapers; global limits hit everyone.
- Layer keys, and add bot detection for determined attackers.

# Sharding

When one database server can't hold your hot data or absorb your writes, even the biggest one, you split the data
across **many** servers. Each server (a **shard**) holds a slice of the rows and handles writes for that slice only.

```
user_id → router → shard 0 (users 0, 4, 8…)
                  → shard 1 (users 1, 5, 9…)
                  → shard 2 …
                  → shard 3 …
```

Unlike replicas, which copy everything and only add read capacity, **shards add write capacity and storage**. In the
simulator, a database's **Shards** setting multiplies both read and write capacity, at about 85% efficiency per shard,
because keys never spread perfectly.

## Choosing the shard key

The shard key decides everything. A good key:

1. **Spreads load evenly:** many distinct values, no single huge value.
2. **Keeps related data together:** the most common queries hit **one** shard.
3. **Doesn't change:** moving a row between shards is expensive.

| App | Good key | Why | Bad key | Why |
|-----|----------|-----|---------|-----|
| SaaS | `tenant_id` | All of a tenant's data together; queries are per tenant | `created_at` | All new writes hit the newest shard |
| Social | `user_id` | Profile, posts and settings together | `country` | India's shard would be enormous |
| Chat | `conversation_id` | All messages of a chat together | `message_id` | Reading one chat touches every shard |

## Sharding strategies

| Strategy | How | Pros | Cons |
|----------|-----|------|------|
| **Hash** | `shard = hash(key) % N` | Even spread | Range queries hit all shards; changing N moves almost everything (use consistent hashing, Module 14) |
| **Range** | Key ranges per shard (A–F, G–M…) | Range scans on one shard | Hot ranges (sequential ids, recent dates) |
| **Directory** | A lookup table: key → shard | Flexible; move any tenant anywhere | The directory must be fast and highly available |

Many systems shard with **many small logical shards** (say 1,024) mapped onto a few physical servers. Rebalancing
then means moving whole logical shards between servers, not re-hashing rows.

## What sharding costs

- **Cross-shard queries:** "top 10 posts globally" must ask every shard and merge (scatter-gather).
- **Cross-shard transactions:** moving money between users on different shards needs sagas or 2PC (Module 16).
- **Unique constraints** across shards (e.g. a unique email) need a separate lookup table or a global service.
- **Operations:** N databases to back up, upgrade, monitor and fail over.
- **Resharding** when shards fill up (lesson 9.4).

That's why sharding is the **last** step after archiving, partitioning, scaling up, replicas and splitting by feature.

## Try it

A multi-tenant project-management SaaS has 40,000 tenants; the largest is 3% of all data; 99% of queries are within
one tenant. Write volume has outgrown the largest database instance. Pick a shard key and a strategy.

<details>
<summary>Answer</summary>

Shard by **`tenant_id`**, so every query stays on one shard. Use a **directory** (tenant → shard), or hashing onto
many logical shards, so big tenants can be moved or given a dedicated shard. Keep global tables (users' logins,
billing) in a small separate database. Cross-tenant analytics go to a warehouse.
</details>

## Key takeaways

- Sharding splits data across servers, adding write capacity and storage.
- The shard key must spread load, keep related data together and never change.
- Hash spreads evenly; range keeps scans local; a directory is flexible.
- Cross-shard queries, transactions and uniqueness are the price, so shard last.

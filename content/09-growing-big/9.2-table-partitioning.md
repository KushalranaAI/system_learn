# Table partitioning

**Partitioning** splits one huge table into smaller physical tables *inside the same database*. Queries still talk to
one logical table; the database routes to the right partitions.

```
orders  (logical table)
 ├─ orders_2026_08
 ├─ orders_2026_09
 └─ orders_2026_10   ← today's writes land here
```

## Partitioning schemes

| Scheme | Splits by | Good for |
|--------|-----------|----------|
| **Range** | Value ranges (usually time) | Time-series, orders, logs: "recent data is hot" |
| **List** | Explicit values (`country IN ('IN','LK')`) | Data naturally grouped by region or tenant type |
| **Hash** | `hash(key) % N` | Spreading load evenly when there's no natural range |

```sql
CREATE TABLE orders (
  id bigint, user_id bigint, created_at timestamptz NOT NULL, total numeric
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_10 PARTITION OF orders
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

## What you gain

- **Partition pruning:** `WHERE created_at >= '2026-10-01'` only touches October's partition.
- **Cheap deletes:** dropping a whole month is `DROP TABLE orders_2024_01`, instant and without vacuum, instead of
  deleting 60M rows one by one.
- **Smaller indexes per partition**, so hot partitions' indexes fit in memory.
- **Maintenance per partition:** vacuum, reindex and backup old partitions separately.

## What to watch

- Queries **without** the partition key must scan every partition. If most queries filter by `user_id`, range
  partitioning by time helps them less.
- **Unique constraints** must include the partition key (Postgres needs that to enforce them).
- Too many partitions (thousands) slow down query planning. Choose a granularity of days, weeks or months to keep
  the count reasonable.
- Create future partitions **ahead of time** (automate it, e.g. with pg_partman), or inserts fail at midnight on the
  1st.

## Partitioning vs sharding

| | Partitioning | Sharding |
|-|--------------|----------|
| Where | One database server | Many servers |
| Helps with | Big tables, deletes, index size, maintenance | Write throughput and data beyond one machine |
| Transactions and joins | Normal | Hard across shards |
| Complexity | Low–medium | High |

Partitioning is usually the step **before** sharding, and often makes sharding unnecessary.

## Try it

An `events` table gets 50M rows a day; you keep 30 days; queries are almost always "the last 24 hours for one account".
Pick a partitioning scheme and an index.

<details>
<summary>Answer</summary>

**Range partition by day** on `created_at` (30–31 live partitions). Drop the oldest partition daily instead of
deleting rows. Index each partition on `(account_id, created_at)`, so "last 24 hours for account X" prunes to 1–2
partitions and uses the index.
</details>

## Key takeaways

- Partitioning splits a big table into smaller ones inside one database.
- Range (time) partitioning makes recent data fast and old data cheap to drop.
- Queries must filter on the partition key to benefit.
- Partition before you shard.

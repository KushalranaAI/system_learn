# Serving many regions

Your servers are in Mumbai. A user in São Paulo is ~300 ms of round trip away, and every request pays it at least
once (more for a cold TLS connection). No amount of code optimisation beats the speed of light.

## The levers, from cheapest to hardest

| Lever | What it does | Effort |
|-------|--------------|--------|
| **CDN** for static files and public pages | Serves from an edge near the user | Low |
| **TLS termination at the edge** | Handshakes happen nearby; the edge keeps warm connections to origin | Low (most CDNs) |
| **Edge caching of API responses** | Public, cacheable API calls answered near users | Low–medium |
| **Regional read replicas** | Reads served in-region; writes still go home | Medium |
| **Regional app servers + replicas** | The whole read path is local | Medium |
| **Data homed per region** (EU users' data in the EU) | Reads *and* writes local for most users | High |
| **Multi-region active-active** | Every region takes writes | Highest (Module 18) |

## Regional read replicas

```
São Paulo users ─▶ app (São Paulo) ─reads─▶ replica (São Paulo)
                                    └writes─▶ primary (Mumbai) ── async ──▶ replica
```

- Reads become fast; writes still cross the world.
- **Replication lag** is now cross-ocean (100 ms – seconds). Read-your-writes (lesson 5.3) matters even more.

## Homing data by geography

Assign each user (or tenant) a **home region**, and store their data there. Their reads and writes are local; only
cross-region interactions (a Brazilian messaging an Indian user) cross the ocean.

This is sharding by geography (lesson 9.3). It also helps with **data residency** laws that require some data to stay
in a country or region.

## What to measure

- Latency **per region** (p95/p99), not a global average: averages hide the far-away users.
- Time to first byte from real users (RUM).
- How many round trips a page load needs. Cutting 5 sequential calls to 1 saves 4 × 300 ms for distant users.

## Fewer round trips

For distant users, **round trips** matter more than bytes:
- batch API calls (one request that returns what the page needs);
- HTTP/2 or HTTP/3 to reuse connections;
- avoid sequential "call A, then use its result to call B" chains from the client.

## Try it

A Mumbai-hosted SaaS gets 30% of its users from Europe. European p99 page load is 2.4 s versus 0.6 s in India. The page
makes 6 sequential API calls. Give three improvements in order of effort.

<details>
<summary>Answer</summary>

1. **CDN** for assets, with TLS at the edge (cuts handshake round trips).
2. **Combine the 6 sequential calls** into 1–2 (saves ~4–5 × 120–150 ms round trips).
3. **Regional app servers + read replica in Europe** for the read path. Longer term, home EU tenants' data in the EU
   (also helps with GDPR).
</details>

## Key takeaways

- Distance sets the floor on latency: move work and data closer to users.
- Start with CDNs and edge TLS; then regional reads; then homing data per region.
- Measure latency per region, and cut round trips for distant users.

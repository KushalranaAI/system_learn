# Living with shards

Sharding solves the capacity problem and creates three new ones: queries that span shards, shards that get hot, and
shards that fill up.

## Cross-shard queries

| Need | Approach |
|------|----------|
| "Get user 42's orders" | Route by `user_id` to one shard. The common case, and fast |
| "Find user by email" | A **global index table** `email → user_id` (in its own small DB or a key-value store) |
| "Top products across all users" | **Scatter-gather**: query all shards in parallel, merge, or precompute in a warehouse |
| Reporting and analytics | Stream all shards into a **data warehouse** (CDC, Module 17); never query production for this |

Scatter-gather latency is the **slowest shard's** latency, so tail latency grows with shard count.

## Hot shards

Even with a good key, one shard can get hot:
- a **celebrity** user or a giant tenant;
- a **sequential key** under range sharding (all new rows go to the last shard);
- a **viral** item.

Fixes:
- Move the hot tenant to its **own dedicated shard** (easy with a directory).
- **Split** the hot shard's key range.
- **Salt** the key for write-heavy hot items: `post:9001#0..7` spreads writes across 8 shards; reads combine them.
- Cache hot reads in front (Module 3).

## Resharding

Shards fill up, or you need more write capacity. Moving data while serving traffic is the hardest operational job in
this module.

### Why `hash % N` hurts
Changing N from 4 to 5 changes the shard for **~80% of keys**. You'd move almost everything.

### Better approaches
- **Many logical shards** (e.g. 1,024) on a few servers: moving a logical shard is a bounded, well-understood unit of
  work. Adding a server means reassigning some logical shards to it.
- **Consistent hashing** (Module 14): adding a node moves only ~1/N of the keys.
- **Directory-based:** update the lookup table entry after copying a tenant.

### An online move, step by step
```
1. Copy:      bulk-copy the shard's rows to the new server
2. Catch up:  stream ongoing changes (CDC / logical replication) until it's in sync
3. Cut over:  briefly pause writes for that shard (seconds), apply the last changes, flip the routing entry
4. Verify:    compare counts and checksums; keep the old copy for rollback
5. Clean up:  delete the moved rows from the old shard
```

## Operations at N×

Every routine task now happens N times: schema migrations (run them shard by shard, backwards-compatibly), backups,
failovers, upgrades. Automate everything, and test the migration tooling on one shard first.

## Try it

You shard by `hash(user_id) % 8`. You need a 9th shard. Roughly what fraction of users move? How could you have set
things up to make this cheaper?

<details>
<summary>Answer</summary>

With modulo hashing, changing 8 → 9 remaps about **8/9 ≈ 89%** of keys. Better: hash into **many logical shards**
(e.g. 1,024) and map those onto 8 servers. Adding a 9th server moves ~1/9 of the logical shards (about 114) and no
re-hashing. Or use consistent hashing.
</details>

## Key takeaways

- Route single-entity queries to one shard; use global index tables and warehouses for the rest.
- Scatter-gather is as slow as the slowest shard.
- Handle hot shards by isolating, splitting or salting keys.
- Avoid `hash % N`; use logical shards or consistent hashing; move data with copy → catch up → cut over.

# Inside a load balancer

Lesson 4.4 treated the load balancer as a box that spreads requests. At large scale it's a tier of its own, usually
two tiers, and the interesting problems are keeping each connection on the same backend, surviving the load
balancers' own failures, and removing servers without dropping users.

## L4 vs L7

| | L4 (transport) | L7 (application) |
|-|----------------|------------------|
| Sees | IP + TCP/UDP headers | Full HTTP: path, headers, cookies |
| Unit of balancing | A connection (or flow) | A request |
| Terminates TCP/TLS? | No (forwards packets) | Yes, then opens its own backend connections |
| Cost per connection | Tens of bytes of state | Kernel socket buffers + TLS state + HTTP parser: KB per connection |
| Can do | Spread flows, survive DDoS at line rate | Route `/api` vs `/static`, retries, rate limits, auth, gRPC per-request balancing |
| Examples | Google Maglev, Facebook Katran, AWS NLB, IPVS | Envoy, NGINX, HAProxy, AWS ALB |

The common large-scale shape:

```
               internet
                   │  (anycast VIP, lesson 20.5)
         ┌─────────┴─────────┐
      router              router        ECMP: hash each flow to one L4 node
   ┌────┼────┐         ┌────┼────┐
  L4   L4   L4        L4   L4   L4      Maglev/Katran: consistent hash → L7 node
   └──┬─┴────┴──┬──────┘
     L7   L7   L7   L7                  Envoy/NGINX: TLS, HTTP routing
     │     │    │    │
   backends (pooled, long-lived connections)
```

## How an L4 balancer forwards a packet

1. A packet arrives for VIP `203.0.113.10:443`. The L4 node hashes the 5-tuple (src IP, src port, dst IP, dst port,
   protocol).
2. It looks up the **connection tracking table**. Known flow? Send to the same backend. New flow? Pick a backend with
   consistent hashing and record it.
3. It **encapsulates** the packet (GRE/IP-in-IP) and sends it to the backend, which still sees the client's real IP.
4. With **direct server return (DSR)** the backend replies straight to the client, bypassing the balancer. Responses
   are usually far larger than requests, so the L4 tier only carries the small inbound half.

## Why consistent hashing, not round robin

Routers spread flows across L4 nodes with ECMP, and when an L4 node is added or fails, ECMP reshuffles some flows to
**different L4 nodes**. Those nodes have no conntrack entry for the flow. If each node picked backends independently
(random, least-connections), the flow would land on a different backend mid-connection and break. If every node
computes the **same hash → backend mapping**, a flow that moves between L4 nodes still reaches the same backend.

## Maglev hashing, worked through

Maglev (Google, NSDI 2016) builds a lookup table of M slots (a prime, e.g. 65,537 in practice). Each backend gets a
preference list: a permutation of slots `(offset + j × skip) mod M` from two hashes of its name. Backends take turns
claiming their next preferred free slot until the table is full. Lookup is `table[hash(5-tuple) mod M]`: O(1).

Tiny example, M = 7, backends A, B, C:

```
A: offset 3, skip 4 → prefers 3, 0, 4, 1, 5, 2, 6
B: offset 0, skip 2 → prefers 0, 2, 4, 6, 1, 3, 5
C: offset 3, skip 1 → prefers 3, 4, 5, 6, 0, 1, 2

round 1: A→3   B→0   C→4 (3 taken)
round 2: A→1   B→2   C→5
round 3: A→6   table full

slot:   0  1  2  3  4  5  6
owner:  B  A  B  A  C  C  A
```

Now B fails. Rebuild with A and C: A→3, C→4, A→0, C→5, A→1, C→6, A→2.

```
slot:   0  1  2  3  4  5  6
before: B  A  B  A  C  C  A
after:  A  A  A  A  C  C  C
```

Slots 0 and 2 (B's) moved, as they must. Slot 6 moved from A to C: a little **extra disruption**. Maglev trades that
for near-perfectly even load (each backend gets M/N slots ± 1). With M = 65,537 the extra movement is a small
fraction of a percent, and conntrack keeps existing flows on their old backend anyway; only new flows use the new
table.

## Connection tracking at scale

Each tracked flow costs maybe 64–128 bytes. Ten million flows is about 1 GB: fine for one machine. The hard part is
churn and attacks: a SYN flood creates millions of half-open entries. Mitigations: SYN cookies, short timeouts for
unestablished flows, and falling back to pure hashing (no state) when the table is under pressure.

## Draining

Removing a backend (deploy, scale-in) without dropping requests:

1. Mark it **draining**: health checks fail on purpose or the control plane removes it, so **no new** connections
   or requests are sent.
2. Let in-flight requests finish. For HTTP/1.1 send `Connection: close`; for HTTP/2 send `GOAWAY` so clients open a new
   connection elsewhere.
3. After a **deadline** (e.g. 30–300 s), close what's left. WebSockets and long streams need the app to reconnect
   cleanly (lesson 6.5).
4. Only then stop the process.

Draining L7 nodes themselves is the same, one level up: the L4 tier stops sending them new flows.

## Try it

Design a load balancer tier for **10 million concurrent client connections** (mostly HTTPS and WebSockets, 200k new
connections per second at peak) in front of 2,000 backend servers.

<details>
<summary>Reference</summary>

- **Entry**: anycast VIPs announced from each region/PoP; routers ECMP flows across the L4 tier.
- **L4 tier**: Maglev/Katran-style, consistent hashing + conntrack, DSR. 10M flows × ~128 B ≈ 1.3 GB of state per
  node if every node may see any flow; a handful of nodes per site handle the packet rate, run N+2.
- **L7 tier**: terminates TLS and WebSockets. Budget roughly 20–50 KB per connection (socket buffers, TLS, HTTP
  state): 10M × ~30 KB ≈ 300 GB of memory across the fleet. At about 250k connections per node that's 40 nodes; add
  headroom for a site or zone loss (×1.5) → **about 60 L7 nodes**. TLS handshakes are the CPU cost: 200k/s new
  connections needs session resumption and enough cores (thousands of handshakes per second per core).
- **Backends**: L7 nodes keep pooled long-lived connections to the 2,000 backends, so backend connection count is
  small and independent of client count. Least-request balancing at L7.
- **Operations**: health checks at both tiers; draining with GOAWAY and a reconnect-with-jitter policy for WebSockets
  so a drained node doesn't cause a reconnect storm (lesson 6.5); raise file-descriptor and conntrack limits; watch
  ephemeral port usage on L7 → backend paths.
</details>

## Key takeaways

- L4 balances flows cheaply at packet level; L7 terminates connections and balances requests.
- Large sites stack them: ECMP → L4 consistent hashing → L7 proxies → pooled backends.
- Every L4 node must compute the same mapping (Maglev) so flows survive LB changes; conntrack keeps existing flows put.
- Drain by stopping new work first, then finishing or redirecting in-flight work before a deadline.

# HTTP/2, HTTP/3 and QUIC

The meaning of HTTP (methods, status codes, headers) hasn't changed since HTTP/1.1. What changed is how requests are
put on the wire. Each version fixes a bottleneck of the one before.

## HTTP/1.1: one request at a time per connection

```
conn 1: GET /app.js ─────────── response ───── GET /a.png ─── response
conn 2: GET /app.css ── response ── GET /b.png ─────── response
...up to ~6 connections per host in browsers
```

A connection carries one request/response at a time. Browsers open about six connections per host to get
parallelism, each paying its own TCP and TLS handshake and its own slow start (lesson 20.2). Headers are plain text
and repeated on every request: the same 500–800 bytes of cookies and user agent, again and again.

## HTTP/2: many streams, one connection

HTTP/2 splits everything into binary **frames** on numbered **streams**, interleaved over one TCP connection.

```
Frame header (9 bytes):
+-----------------------------------------------+
| Length (24 bits)                              |
| Type (8) | Flags (8)                          |
| R | Stream Identifier (31 bits)               |
+-----------------------------------------------+
| Payload (HEADERS, DATA, SETTINGS, RST_STREAM…)|
```

```
TCP: [H s1][H s3][D s1][D s3][H s5][D s1][D s5][D s3] ...
```

- **Multiplexing**: dozens or hundreds of requests in flight on one connection; responses come back in any order.
- **HPACK header compression**: a static table of 61 common headers, a per-connection dynamic table of recently
  sent headers, and Huffman coding. A repeated cookie header shrinks to a byte or two after the first request.
- **Flow control per stream** and priorities, so one big download doesn't starve small requests.

The catch is the layer underneath. All streams share one TCP byte stream, so a single lost packet stalls **every**
stream until it's retransmitted: **TCP head-of-line blocking**. On a clean wired network that's rare. On a phone with
2% packet loss it can make HTTP/2 slower than six HTTP/1.1 connections.

HTTP/2's cheap streams also enabled a new attack: **Rapid Reset** (CVE-2023-44487, October 2023). A client opens a
stream and immediately cancels it with RST_STREAM, over and over; the server does work for each, while the client
never hits its concurrent-stream limit. Google reported a peak of about 398 million requests per second. Servers now
limit resets per connection.

## QUIC: transport rebuilt on UDP

QUIC (RFC 9000) re-implements reliable streams in user space on top of UDP, with TLS 1.3 built in. HTTP/3 (RFC 9114)
is HTTP mapped onto it.

| Feature | TCP + TLS + HTTP/2 | QUIC + HTTP/3 |
|---------|-------------------|---------------|
| Handshake before first request | TCP 1 RTT + TLS 1 RTT | **1 RTT** combined; 0-RTT on resumption |
| Loss on one stream | Stalls all streams | Stalls **only that stream** |
| Encryption | Payload only; TCP headers visible | Almost everything, including most transport headers |
| Identity of a connection | (src IP, src port, dst IP, dst port) | A **connection ID** |
| Header compression | HPACK | QPACK (works with out-of-order streams) |
| Where it runs | Kernel | User space, ships with the app or server |

**Connection migration** is the mobile win. A TCP connection is identified by its IP/port four-tuple; when a phone
walks out of Wi-Fi onto 5G, its IP changes and every connection dies, then has to handshake again. A QUIC connection
is identified by a connection ID, so the client just keeps sending from the new address and the server validates the
path and carries on.

## The costs of QUIC

- **UDP gets blocked or throttled** on some corporate and hotel networks. Clients must fall back to HTTP/2 over TCP.
  Servers advertise HTTP/3 with an `Alt-Svc` header or an HTTPS DNS record; browsers race the two.
- **CPU**: user-space packet processing with per-packet encryption costs more than kernel TCP, though GSO and other
  offloads narrow the gap.
- **Load balancers** must route by connection ID, not four-tuple, or migrated connections land on the wrong server
  (lesson 20.6).
- **Debugging**: packet captures show encrypted headers; you need qlog or key logging.

## Which to use

| Situation | Choice |
|-----------|--------|
| Browser-facing site | Serve HTTP/2 and HTTP/3; let the client pick. CDNs do this for you. |
| Mobile app on flaky networks | HTTP/3 with HTTP/2 fallback |
| Service-to-service in a data centre | HTTP/2 (e.g. gRPC) over long-lived connections; loss is low, TCP is well understood |
| Huge single downloads | Any; the transport matters less than bandwidth |

## Try it

You're choosing the protocol stack for a food-delivery mobile app. Users are often on mobile data, move between Wi-Fi
and cellular, and the app makes many small API calls plus some image downloads. What do you choose and what do you
need to watch out for?

<details>
<summary>Reference</summary>

**HTTP/3 over QUIC, with automatic fallback to HTTP/2 over TCP.**

- 1-RTT handshakes (0-RTT on resumption, for idempotent GETs only) cut cold-start latency on high-RTT mobile links.
- Independent streams: a lost packet on an image download doesn't stall the "order status" call.
- Connection migration keeps the session alive when the rider leaves Wi-Fi mid-order.

Watch out for: networks that block UDP (measure the fallback rate), your load balancer or CDN supporting QUIC and
routing by connection ID, extra server CPU, client library support (use the platform's HTTP stack or a maintained
library such as Cronet), and observability: log the negotiated protocol per request so you can compare latency and
error rates between HTTP/3 and HTTP/2 users. Keep using one long-lived connection rather than many.
</details>

## Key takeaways

- HTTP/1.1: one request per connection at a time, ~6 connections per host.
- HTTP/2: binary frames, multiplexed streams and HPACK on one TCP connection, but TCP head-of-line blocking remains.
- QUIC moves reliability to user space over UDP: combined handshake, per-stream loss recovery, connection migration.
- Serve both and let clients choose; HTTP/3 helps most on lossy, mobile networks.
